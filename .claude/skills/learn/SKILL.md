# 通用學習 skill

把「我想和 Claude 一起學 X」流程化：規劃課綱 → 逐章寫教材 → 練習與總結專案。每一門課最後都會是一本獨立、可讀、可動手的書——而且要是一本**厚書**，覆蓋面廣、挖得夠深、範例夠多。

核心信條：**教材越多越深越好**。寧可多寫一個「進階」章節也不要留白；寧可把底層原理講清楚也不要只示範 API 呼叫；寧可給三個例子也不要給一個；每個延伸閱讀資源都要附上解釋，讀者不應該自己猜「這篇在說什麼、我要從哪裡開始讀」。

## 什麼時候啟動這個 skill

- 使用者說：「我想學 X」「來學 X 吧」「幫我規劃 X 的學習路徑」
- 使用者說：「繼續寫某個課程資料夾裡面的內容」「把某個課程目錄補齊」
- 使用者要求新增一個主題到 repo

若使用者只是問某個概念，**不要**啟動這個 skill — 直接回答就好。這個 skill 是為「成系列、成冊」的學習材料而存在。

## 工作流程

### Step 1 — 釐清學習目標（務必先問，不要猜）

先和使用者對齊，最多一次問完：

- **主題與範圍**：要學的是「X 全貌」還是「X 的某一塊」？
- **既有背景**：使用者對這個主題已經會什麼？（決定是否補基礎章節）
- **深度目標**：偏會用 API？還是要懂底層原理？還是要能讀 source code？
- **實作要求**：純概念，或每章都要能跑？要生產等級還是 PoC？
- **預計規模**：預設 **25–40 章**；有特殊需求再調。少於 20 章通常代表範圍太窄或深度不足。

如果使用者已經給了這些資訊，就別再問。

---

### Step 2 — 提出課綱草稿

依 `compilers/compiler_frontend/README.md` 的格式在對話裡提出「課程地圖」草稿。必須包含：

- 課程簡介（一句說為什麼學這個、學完後你在什麼位置）
- **分 Part 的章節大綱**（每章一句話說明它在整體中的定位）
- 章節規模指引：
  - **普通章** 300–450 行
  - **原理深挖章**（底層架構、實作剖析、演算法推導）400–550 行
  - **練習** 400–600 行（含完整題目規格、多組測試、參考解答）
  - **Final Project** 500–700 行
- 練習位置：**每個 Part 結束後至少一個練習**，全課至少 3 個
- Final Project（除非主題真的不適合，否則一律要有）

**先得到使用者確認或修改，再動手寫檔案**。課綱是骨架，骨架錯了後面全部要改。

---

### Step 3 — 建立資料夾骨架

課綱確認後：

1. 在合適的分類下建立 `<category>/<topic>/`（topic 用 snake_case；沒有合適分類就新建，別丟 repo root）
2. 寫 `README.md`（課程地圖，格式見下方模板）
3. 建立所有章節空檔（只有標題行），讓整體架構一次看得見
4. 讓使用者確認檔名與 README 再開始填內容

---

### Step 4 — 逐章撰寫

**一次寫一章**，寫完後暫停讓使用者 review 再繼續。例外：使用者明確說「整批寫完再看」才批次。

每一章**必須**包含以下幾個維度（缺一不可）：

| 維度 | 說明 |
|---|---|
| **概念建立** | 是什麼、解決什麼問題、為什麼這樣設計 |
| **底層機制** | 它內部怎麼運作——不能只停在「呼叫這個函式就好」 |
| **多組具體範例** | 至少 2–3 個可跑的例子，覆蓋正常路徑 + 邊界情況 |
| **對比 / 演進** | 和舊方法、替代方案、相似概念的差異 |
| **踩雷集錦** | 列出 3–5 個常見錯誤或誤解，每條給明確糾正 |
| **進階延伸** | 「如果你想更深入」——下一步去哪、進階用法、生產注意事項 |
| **延伸閱讀** | 3–5 條高品質資源（論文、部落格、RFC、書籍），**每條都要附上解釋**：讀哪裡、學到什麼、和本章的關聯 |

如果某章因主題性質確實不需要某維度（例如純歷史背景章不需要踩雷），可以省略並在章節開頭說明原因。

---

### Step 5 — 練習與 Final Project

練習要做到「合上書能獨立完成」的程度，不能是「對著解答抄」的程度：

- **任務規格**：精確描述輸入輸出、限制條件、驗收標準
- **多組測試用例**：包含邊界、非法輸入、效能邊界
- **分段實作建議**：至少 4–5 步，每步說明要達到的子目標
- **完整參考解答**：包含說明，藏在 `<details>`
- **常見卡點提示**：3–5 條「如果你卡住了，先想想...」
- **延伸挑戰**（加分題）：給學有餘力的人再多一層

Final Project 要能整合全課至少 70% 的核心概念，不能只是最後幾章的延伸。

## 教學設計原則

這一節說的是**怎麼教**，不只是**教什麼**。頂級教材和普通教材的差距，80% 在這裡。

### 直覺先行，形式化後補

永遠先給讀者一個心智圖像或直覺，再引入精確定義或程式碼。讀者如果腦中沒有模型，看再多 code 也只是在抄。

錯誤順序：「`epoll_wait()` 的語意是監控一組 fd，當有事件觸發時返回就緒列表。以下是範例。」  
正確順序：「想像一個服務員看著 N 張桌子——不是輪流跑每桌問『你好了嗎』，而是站在中間等任何一桌叫他。這就是 epoll 的模型。現在看 code：」

### 具體先行，抽象後補

先給一個具體例子，讓讀者看到它，再歸納一般規律。不要先寫「X 的一般化定義是...」然後給例子。人腦從具體歸納抽象，不是從抽象演繹具體。

### 歷史演進脈絡

每個核心概念都要說：在這個東西出現之前，人們怎麼做？為什麼舊方法不夠好？這個設計的歷史背景能讓讀者理解「為什麼要這樣設計」，而不是死記一套規則。

### 設計決策的「為什麼不」

好的教材不只解釋「選了什麼」，還解釋「為什麼沒選 B 或 C」。設計空間的形狀比最終選擇更有教育意義。例：「Rust 為什麼不用 GC？不是 GC 不好——是 GC 無法保證 latency，而這對系統程式設計是硬限制。」

### 橫向連結

當一章用到之前學過的概念，明確標示，不要讓讀者在腦中自己找。格式：

```
> 如果你對 X 還不熟，先回看 [Ch N — 標題](./0N-xxx.md) 的「Y 節」。
```

前面的章節教過的東西，後面的章節可以引用，但要給路標。讀者不會記得所有內容，幫他們連線是作者的責任。

### 認識論誠實

寫作時遇到以下情況，**一定要明確標示**，不能假裝不存在：

- 行為是版本特定的（「這是 Linux kernel 5.15+ 的行為；舊版不同」）
- 行為是平台特定的（「Windows 上這個 syscall 不存在」）
- 效能宣稱是有條件的（「在 cache hit rate 高的情況下；否則反而更慢」）
- 主題有真實的爭議（「這個領域對 X 沒有共識；主流實作做法是 Y，但 Z 也有道理」）
- 某個說法是簡化模型（「這個類比在 A 和 B 的情況下成立，但碰到 C 就會出問題」）

不說清楚的後果：讀者帶著錯誤的絕對化認知去實作，碰壁後不知道為什麼。

### 主動回憶，而非被動閱讀

自我檢核的問題要逼讀者**回憶**，不是逼讀者看著章節抄答案。好的問題格式：
- 「不看筆記，能不能用自己的話解釋 X？」
- 「如果有人在面試問你 Y，你會怎麼回答？」
- 「想一個你現在工作中遇到的問題，這章的概念怎麼應用到它？」

壞的問題格式：「X 是什麼？」「Y 的用法是什麼？」——這些問題讀者把書翻回去就能回答，對記憶沒有幫助。

### 版本與環境釘定

工具類主題的章節，開頭一定要有：

```
> **環境**：本章以 <工具名> <版本> 在 <OS/架構> 上操作。<版本 X 以下有行為差異的地方會特別標注。>
```

不釘版本的教材時效性很差，讀者在不同環境跑出不同結果時找不到原因。

### 失敗是教學素材

在某些情況下，先**故意展示錯誤的做法或失敗的輸出**，再展示正確做法，比直接給正確答案更有效。這讓讀者理解「為什麼要這樣」而不是只知道「這樣做」。

尤其適合：編譯錯誤、記憶體問題、並發 bug、效能退化——這些情況展示失敗比展示成功更能建立直覺。

- 章節檔名兩位數字前綴，kebab-case，從 `00` 或 `01` 開始

- Final Project 以 `final-project-` 開頭
- 全部小寫 + 連字號，不用底線不用空白

## 資源品質標準

寫「延伸閱讀」時，對每一條資源的要求：

### 什麼資源算「值得列」

**論文**：優先列 USENIX（OSDI、ATC、NSDI）、ACM（SOSP、PLDI、CCS）、IEEE S&P、NDSS、頂級期刊，或某個技術的原始論文（那篇「我們就是從這裡開始的」）。不要列連 Google Scholar 引用數都個位數的隨機論文。

**部落格 / 技術文章**：優先選：
- 工具 / 語言的**核心開發者**或維護者寫的（Brendan Gregg 寫 perf、Russ Cox 寫 Go runtime、Dan Luu、Julia Evans、Eli Bendersky、Aphyr……）
- 大廠的**系統工程部落格**（Netflix Tech Blog、Cloudflare Blog、Facebook Engineering、LMAX Disruptor blog……）
- 解釋**底層原理**而非只是「10 分鐘學會 X」的文章
- 有明確**作者署名**且能查到背景的文章

避免：SEO 農場文、Medium 上「入門 X 的 5 個步驟」、沒有作者署名的教程、純 ChatGPT 生成內容的技術部落格。

**官方文件 / Spec**：RFC、W3C spec、語言標準、工具官方 manual。要標明具體小節，不要只丟首頁 URL。

**書籍**：優先選業界公認的「那本書」（《CSAPP》《APUE》《OSTEP》《Dragon Book》《The Linux Programming Interface》……），或特定領域的標準教科書。列出版年，超過 10 年的書要說明是否仍然適用。

### 每條資源的必填說明

不管是哪種類型，每條資源都必須回答這三個問題：
1. **讀什麼**：具體章節、小節、或段落，不是「整本書」「官網」
2. **能學到什麼**：這條資源補充了本章哪個沒有展開的地方，或把哪個概念推得更深
3. **前提知識**：讀者需要先懂什麼才能看得懂（避免讀者開了連結兩分鐘就關掉）

寫完每章之前，自己跑一遍這個 checklist：

```

□ 第一個 code block 出現之前，有沒有先建立心智模型或直覺？
□ 這章有沒有解釋歷史背景：在這個設計之前，人們怎麼做？為什麼不夠好？
□ 有沒有說明「為什麼不選替代方案 B 或 C」，而不只是說「我們選了 A」？
□ 所有術語有沒有在第一次出現時定義，或標注「見 Ch N」？
□ 有沒有橫向連結到之前學過的相關概念？
□ 如果是工具章節，有沒有在開頭釘定版本與環境？

內容深度
□ 底層機制的部分，讀者讀完之後能不能在腦中畫出執行流程？
□ 有沒有說清楚「為什麼這樣設計」，而不只是「怎麼用」？

□ 範例有沒有至少 2 個，覆蓋正常路徑和至少一個失敗 / 邊界情況？

收尾
□ 踩雷有沒有至少 3 條，每條有明確的「錯誤直覺 → 正確認識」？
□ 有沒有一個「進階延伸」區塊，讓讀者知道下一步去哪？

□ 自我檢核的問題有沒有要求主動回憶，而非只是能翻書找答案？

## 規模指引

課程章節數的指導原則：

| 主題範疇 | 建議章節數 | 建議練習數 |
|---|---|---|
| 一個工具（如 GDB、Docker） | 20–30 章 | 3–4 個 |
| 一個語言（如 C++、Go） | 30–45 章 | 4–6 個 |
| 一個領域（如密碼學、網路） | 35–50 章 | 4–6 個 |
| 一個子主題（如 GDB remote） | 12–18 章 | 2–3 個 |

如果課綱草稿章節數明顯低於下限，先問使用者：是範圍縮窄了，還是某些主題要合併？合理的原因包括：主題本身就小、使用者只想要入門不要深入。沒有好原因就擴展，不要留白。

## 風格指南（不要偏離）

以 `compilers/compiler_frontend/` 為基準。

### 語言

- **繁體中文（台灣）**，不用簡體
- 專有名詞第一次出現寫中英並陳：「詞法分析（Lexer / Scanner）」
- 程式碼、工具名、flag 保持英文原文

### 口吻

- 直接、有觀點、不官腔。「別只讀」「工具會幫你罵你」「這樣做比較好」
- 第一人稱複數「我們」，把讀者拉進來
- 敢下判斷：不要什麼都寫「可以考慮」
- 承認歷史與誤解：「有人問過...」「一個常見誤解是...」

### 結構細節

- 章節開頭一律用 `> **目標**：...` blockquote
- 流程或架構先放一張 ASCII code block 圖
- 概念對照用 markdown 表格
- 「XXX **不關心** YYY」「**不會** 生成 ZZZ」— 粗體強調邊界
- 結尾一律 `## 自我檢核` + checkbox（包含理解性問題，不只操作）+ `## 延伸閱讀` + 一句話 + `→ [下一章連結]`

### 範例要求

- 範例要具體、能跑、有輸出。不要抽象碼（`foo()`, `bar`）
- **多個例子**：一個最小可工作例子，一個真實情境例子，一個邊界或錯誤例子
- 如果是工具類主題，給 before → after 對照
- 「把分號刪掉，看它怎麼罵你」——故意弄錯是這套教材的核心手法
- 範例必須在對應的環境真的能跑，不允許只是示意的偽代碼（除非整章都是概念性的）

### 長度

- 普通章：300–450 行
- 原理深挖章（底層機制為主）：400–550 行
- 練習：400–600 行
- Final Project：500–700 行
- README：60–100 行

寧可長也不要短。如果一章寫完只有 150 行，表示某個維度沒寫到，找出來補上。

### 不要做的事

**口吻與用語**

- 不要寫純 AI 腔 meta 話（「在本章中，我們將探討...」「讓我們開始吧！」）
- 不要無意義的過場句（「接下來，我們繼續...」「綜上所述...」）
- 不要用 emoji（除非使用者明確要求）
- **嚴禁輕描淡寫詞**：`just`、`simply`、`trivially`、`obviously`、`easily`、`只需要`、`很簡單`、`顯然`——這些詞是在告訴讀者「你應該覺得這很簡單」，讓卡住的讀者覺得是自己的問題。刪掉。

**概念說明**

- 不要在術語**未定義**的情況下使用它——每個術語在第一次出現時要定義，或明確標注「這在 Ch N 有介紹」
- 不要「之後會說明」的延遲交代——如果現在不能解釋，就說「先用著，之後你會看到為什麼，這不影響現在的理解」；不要讓讀者帶著懸念繼續，以為自己漏看了什麼
- 不要用**誤導性的類比**——類比是教學工具，但如果類比在邊界條件下會給讀者錯誤的心智模型，比沒有類比更糟。如果類比有限制，說清楚：「這個比喻在 A 的情況下成立；碰到 B 就不適用了」
- 不要做**假精確**——「這個演算法是 O(n log n)」但省略「在平均情況下、假設 hash 均勻分布的前提下」。精確要麼完整，要麼說「粗略地說」
- 不要用**被動語態掩蓋主語**——「記憶體被釋放了」不如「OS 把這個 physical page 回收進 free list」；主語不清楚，讀者就不理解誰在做什麼

**範例品質**

- 不要只有 happy path——每個概念至少有一個展示**失敗或邊界情況**的例子：錯誤輸出、exception、行為不符預期的情況
- 不要範例裡有未解釋的 **magic number 或 magic constant**——`0x400000`、`4096`、`255`——它們為什麼是這個值，說清楚
- 不要只有 snippet、不給 **runnable context**——讀者要能複製貼上跑起來；如果篇幅不允許完整程式，至少說明缺少什麼以及如何補上
- 不要做**無根據的效能或安全宣稱**——「這樣做比較快」「這樣做比較安全」——要嘛給 benchmark、給具體條件，要嘛換成「在 X 場景下通常比較快，原因是 Y」

**平台與版本**

- 不要**平台差異手波**——「在 Windows 上行為可能不同」這句話毫無意義。要嘛說清楚 Windows 的差異是什麼，要嘛說「本課只涵蓋 Linux，Windows 差異不在範圍內」，選一個
- 不要省略版本資訊——工具行為、API 語意、編譯器行為都可能隨版本改變，說清楚適用的版本範圍

**資源**

- 不要把完整解答直接貼在練習正文 — 一定用 `<details>` 摺起來
- 不要把「延伸閱讀」寫成泛泛的「可以參考官方文件」——要給具體章節和解釋
- 不要列沒有解釋的裸連結——每條資源都要說讀哪裡、學什麼、前提是什麼
- 不要因為「找不到論文」就只列部落格——多數成熟技術都有原始論文或頂會論文，找到它
- 不要列 Medium 上的「N 分鐘學會 X」或 SEO 農場文當作延伸閱讀

## 常見狀況處理

### 使用者只丟了一個主題名就要你開始

先按 Step 1 問清楚，不要直接動筆。「學 Kubernetes」可以是 10 章的入門也可以是 40 章的深入，差很多。

### 使用者想繼續寫既有的課程資料夾

1. 先看 README 是否存在、章節檔是否存在
2. 若完全是空的，走完整 Step 1–5
3. 若已有 README 或部分章節，從現有內容推斷課綱，**向使用者確認後**再繼續
4. 對已完成的章節，若發現深度不足，可以提出「補強」建議

### 使用者要求改章節結構

課綱變了之後，**同步更新**：
- `README.md` 裡的課程地圖
- 被影響章節結尾的 `→ 下一章` 連結
- 檔名（如果順序變了）

### 使用者說「快速入門就好，不要太深」

這是合理需求。調整方法：
- 章節數可以縮到 12–18 章
- 每章仍然要有底層機制區塊，但可以縮短（至少給「這邊可以更深入的方向」一段）
- 踩雷仍然必要，但可以只列 2–3 條
- 延伸閱讀縮到 1–2 條
- **不能完全省略深度**——差別是「少說一點」而不是「不說」

### 使用者要求整個 skill 操作為英文

以使用者當下語言為準。但這個 repo 的既有內容是繁體中文，切換語言前先確認：是整個 repo 換，還是只這一門課換？

## 和使用者的互動節奏

- **先規劃，不急動手**：Step 1、Step 2 完成前不要建檔。
- **寫一章停一章**：除非使用者說「一口氣寫完」。
- **對深度標準負責**：每章寫完之前，自己先跑一遍深度 checklist。不要等使用者要求才補底層機制。
- **變更要回報**：寫後面的章節時發現前面有錯或結構不合理，**提出來**讓使用者決定，而不是偷偷繼續。
- **保持觀點**：使用者問「這樣寫好嗎」時，給明確意見。這是教材，不是維基。
- **主動提建議深化**：如果某個主題你認為值得再多一章，說出來。這個 skill 的目標是教材越完整越好，不是越省越好。
- **對資源品質負責**：列延伸閱讀時主動查資料，給出真實存在、品質高的資源，並為每條資源附上解釋。不要用「你可以自行搜尋」當藉口敷衍。
