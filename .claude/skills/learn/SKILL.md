# 通用學習 skill

把「我想和 Claude 一起學 X」這件事流程化：規劃課綱 → 逐章寫教材 → 練習與總結專案。每一門課最後都會是一個獨立、可讀、可動手的小書。

## 什麼時候啟動這個 skill

- 使用者說：「我想學 X」「來學 X 吧」「幫我規劃 X 的學習路徑」
- 使用者說：「繼續寫某個課程資料夾裡面的內容」「把某個課程目錄補齊」
- 使用者要求新增一個主題到 repo

若使用者只是問某個概念，**不要**啟動這個 skill — 直接回答就好。這個 skill 是為「成系列、成冊」的學習材料而存在。

## 工作流程

### Step 1 — 釐清學習目標（務必先問，不要猜）

先和使用者對齊這幾件事，最多一次問完：

- **主題與範圍**：要學的是「X 全貌」還是「X 的某一塊」？（例：GDB 全貌 vs GDB remote debug）
- **既有背景**：使用者對這個主題已經會什麼？（這決定要不要補基礎章節）
- **深度偏好**：偏直覺快速上手，還是要深入原理？
- **是否要實作**：純概念，還是每章都要能跑？
- **預計章節數**：不強求，但抓個量級（5 章 / 10 章 / 15 章）

如果使用者已經把這些資訊給了，就別再問第二次。

### Step 2 — 提出課綱草稿

依 `compilers/compiler_frontend/README.md` 的格式，在對話裡提出「課程地圖」草稿。至少包含：

- 課程簡介（一句為什麼學這個）
- 分 Part 的章節大綱（每章一句話說明它在整體中的位置）
- 練習題位置（通常放在每個 Part 結束後）
- 最終專案（可選）

**先得到使用者確認或修改，再動手寫檔案**。課綱是骨架，骨架錯了後面全部要改。

### Step 3 — 建立資料夾骨架

課綱確認後：

1. 在合適的分類下建立 `<category>/<topic>/` 資料夾（topic 用 snake_case，例：`security/gdb`、`systems/distributed_systems`）。沒有合適分類就新建一個分類資料夾，別丟在 repo root
2. 寫 `README.md`（即課程地圖，格式見下方）
3. 先建立所有章節檔名（空檔或只有標題），讓整體架構一次看得見
4. 讓使用者檢視一次檔名與 README 再開始填內容

### Step 4 — 逐章撰寫

**一次寫一章**，寫完後暫停，讓使用者 review 再繼續。原因：

- 第 1 章的用詞、深度、範例風格會訂下基調，後面幾十章都會依它走。早期修正便宜，後期改痛苦。
- 使用者可能在讀的過程中才想到補充 / 重切章節。

如果使用者明確說「整批寫完再一起看」，才批次寫。

### Step 5 — 練習與 final project

依課綱排好的位置寫練習題。練習的文檔長度通常比章節長，因為要包含：完整題目規格、期望輸入輸出、實作步驟建議、參考解答（藏在 `<details>` 裡）、測試用例、自我檢核。

## 命名與檔案結構

```
<category>/<topic>/
├── README.md                       # 課程地圖
├── 00-environment-setup.md         # Ch 0：環境搭建（若需要）
├── 01-<topic>-overview.md          # Ch 1：全貌 / 為什麼學
├── 02-<concept>.md
├── ...
├── practice-a-<name>.md            # 第一個練習
├── practice-b-<name>.md
├── ...
└── final-project-<name>.md         # 最終專案（可選）
```

規則：

- 章節檔名兩位數字前綴，kebab-case，從 `00` 或 `01` 開始
- 練習檔名以 `practice-a-` / `practice-b-` / ... 開頭
- 最終專案以 `final-project-` 開頭
- 全部小寫 + 連字號，不用底線不用空白

## 風格指南（很重要，不要偏離）

寫作風格以 `compilers/compiler_frontend/` 為標準。具體要求：

### 語言

- **繁體中文（台灣）**，不用簡體
- 專有名詞第一次出現寫中英並陳：「詞法分析（Lexer / Scanner）」
- 程式碼、工具名、flag 保持英文原文

### 口吻

- 直接、有觀點、不官腔。「別只讀」「工具會幫你罵你」「不全然」
- 第一人稱複數「我們」，把讀者拉進來
- 敢下判斷：「這樣做比較好」「實務上我們不這麼寫」— 不要什麼都寫「可以考慮」
- 承認歷史與誤解：「有人問過...」「一個常見誤解」

### 結構細節

- 章節開頭一律用 `> 目標：...` blockquote
- 流程或架構先放一張 ASCII code block 圖，比文字更快懂
- 概念對照用 markdown 表格
- 「XXX **不關心** YYY」「**不會** 生成 ZZZ」— 粗體強調邊界
- 結尾一律 `## 自我檢核` + checkbox + 一句話 + `→ [下一章連結]`

### 範例

- 範例要具體、能跑、有輸出。不要抽象碼（`foo()`, `bar`）
- 如果是 code generator / 工具類主題，給 before → after 對照
- 故意錯一次：「把分號刪掉，看它怎麼罵你」— 這是這套教材的核心手法

### 長度

- 章節 150–250 行為主；概念密的章可以到 300 行
- 練習 250–350 行（因為有參考解答）
- README 50–80 行

### 不要做的事

- 不要寫純 AI 腔的 meta 話（「在本章中，我們將探討...」「讓我們開始吧！」）
- 不要無意義的過場句（「接下來，我們繼續...」）
- 不要用 emoji（除非使用者明確要求）
- 不要把完整解答直接貼在練習正文 — 一定用 `<details>` 摺起來

## 範例參考

當不確定寫法時，直接打開這兩個檔案抄格式：

- 章節範本：`compilers/compiler_frontend/01-frontend-overview.md`
- 練習範本：`compilers/compiler_frontend/practice-a-c-tokenizer.md`
- README 範本：`compilers/compiler_frontend/README.md`

## 常見狀況處理

### 使用者只丟了一個主題名就要你開始

先按 Step 1 問清楚，不要直接動筆。一個「學 Kubernetes」可以是五章的入門也可以是三十章的深入，差很多。

### 使用者想繼續寫既有的課程資料夾（例如 `security/gdb/` 目前是空的）

1. 先看 README 是否存在、章節檔是否存在
2. 若完全是空的，走完整 Step 1–5
3. 若已有 README 或部分章節，從現有內容推斷課綱，**向使用者確認後**再繼續

### 使用者要求改章節結構

課綱變了之後，**同步更新**：
- `README.md` 裡的課程地圖
- 被影響章節結尾的 `→ 下一章` 連結
- 檔名（如果順序變了）

### 使用者要求整個 skill 操作為英文

以使用者當下語言為準。但這個 repo 的既有內容是繁體中文，切換語言前先確認：是整個 repo 換，還是只這一門課換？

## 和使用者的互動節奏

- **先規劃，不急動手**：Step 1、Step 2 完成前不要建檔。
- **寫一章停一章**：除非使用者說「一口氣寫完」。
- **變更要回報**：如果你在寫後面的章節時發現前面有錯或結構不合理，**提出來**讓使用者決定要不要回頭改，而不是偷偷繼續。
- **保持觀點**：使用者問「這樣寫好嗎」時，給明確意見而不是「都可以」。這是教材，不是維基。
