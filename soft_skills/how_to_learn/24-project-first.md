# Ch 24 — Project-First：從實戰倒推

> 傳統學習順序：**先學理論、再做應用**。**Project-First 顛倒這個順序**：**先選一個真實專案，遇到缺什麼就學什麼**。這一章講為什麼這個順序對多數技能學習更有效、以及怎麼做。

## 傳統順序的問題

**傳統順序**：

```
讀理論 → 做例題 → 小練習 → 最後做真實專案
```

**例子**：

- 學 Python → 讀語法 → 做小練習（LeetCode）→ 最後寫一個真實工具
- 學投資 → 讀書 → 看案例 → 最後投真實的錢
- 學寫作 → 讀寫作書 → 練段落 → 最後寫文章

**這個順序的問題**：

### 問題 1：動機不足

**讀理論很無聊**。沒有具體的目的。

結果：你**在「讀理論」階段就放棄**。或讀完一半，沒到真實專案就累了。

### 問題 2：你不知道理論的應用

**沒做過真實專案**，你不知道**哪個理論重要、哪個是細節**。

結果：你讀很多，吸收很少，因為**沒有錨點**。

### 問題 3：真實專案跟你學的不一樣

**教科書的例子**通常是**乾淨、清楚、封閉**的。

**真實問題**是**髒、模糊、開放**的。

結果：你做完所有練習，但**第一個真實專案仍然崩潰**。

## Project-First 的順序

**Project-First**：

```
選一個真實專案 → 開始做 → 遇到卡點 → 針對性學 → 繼續做 → ...
```

**例子**：

- 想學 Python → 定一個你想做的工具（例：下載 YouTube 影片、資料處理、遊戲）→ 開始寫 → 遇到「怎麼做 HTTP 請求」 → **針對學這個** → 繼續
- 想學投資 → 選一家你有興趣的公司 → 開始分析 → 遇到「怎麼看財報」 → **針對學**財報 → 繼續
- 想學寫作 → 寫一篇你想寫的文章 → 開始 → 遇到「怎麼讓句子有節奏」 → **針對學**節奏 → 繼續

### 為什麼有效

**優點 1：動機強**

你**有具體的目的**。**每個小突破都看到進展**。

**優點 2：學的東西就是需要的**

你**不浪費時間**學「以後用得到」的東西。**學的都是當下卡點需要的**。

**優點 3：深度編碼**

你遇到困難，**掙扎著解決，然後學理論**。這是**生產性失敗**（Ch 5）— 最深的編碼方式。

**優點 4：直接面對真實的複雜性**

**你從 day 1** 就面對真實問題。沒有「練完例題才做真實專案」的落差。

## Project-First 的具體流程

### 步驟 1：選一個「剛好超過你能力」的專案

**關鍵**：**剛好超過**（Ch 10 的學習區）。

**壞**：選一個**完全不會**的專案（例：第一次寫程式就想做 AI 聊天機器人）
- 結果：完全卡住、放棄

**壞**：選一個**完全會**的專案
- 結果：沒學到新東西

**好**：你能**大致想像怎麼做**，但**有些部分你不確定**。

**例**：

- 你會寫簡單 Python，想進階 → 選「寫一個網路爬蟲」
- 你會基礎投資，想深入 → 選「分析一個你熟的產業的一家公司」
- 你會寫部落格，想進階 → 選「寫一篇需要研究的長文」

### 步驟 2：開始做，而不是先計畫

**大多數人卡在「先計畫好一切」**：

- 花幾週寫規格
- 研究完所有的工具選擇
- 讀完所有相關書

**然後開始做 = 三個月後**。很多人**在這中間放棄**。

**正確**：**直接開始做**，**邊做邊調整**。

- 第一天就寫第一行程式、第一段文章、第一頁分析
- 做錯也沒關係
- 做的過程會**自然引導你**下一步

### 步驟 3：卡點時針對性學

**這是 Project-First 的核心動作**。

**當你卡住時**：

- **停下**，辨認卡點
- **針對這個卡點** 找資源（書、文件、影片、問人）
- **學到「剛好夠」** 的程度
- **回到專案**繼續做

**「剛好夠」很重要**：不要過度學習。不要讀完整本書、整章、整個 API 文件。**只學你卡住的那一點**。

**例**：

- 你卡在「Python 怎麼做 HTTP 請求」 → **讀 requests 庫的 tutorial** 前 5 段 → 回到寫程式
- 不要一次讀完整個 requests 庫的文件

### 步驟 4：完成第一版（即使很爛）

**第一版的目標**：**能動**。

- 程式：能跑，即使很醜
- 文章：寫完，即使很粗糙
- 分析：有結論，即使不完整

**完成第一版的重要性**：

- 你從頭到尾走過一遍
- 你看到整個專案的全景
- 你知道哪裡最弱

### 步驟 5：反覆改進

**做出第一版後**，**改進**：

- 識別最爛的部分
- **學**怎麼改
- 改

**每次迭代你學更多**。

### 步驟 6：做下一個專案

**做完一個**，選**稍微難一點**的下一個。

**每個專案**都是學習區（Ch 10）。

**幾個專案後**，你真的**會**這個技能了。

## Project-First vs Tutorial Hell

**Tutorial Hell**（Ch 15）是 Project-First 的反面。

| Tutorial Hell | Project-First |
|---|---|
| 永遠在看別人做 | 自己做 |
| 跟著教學的順序學 | 照自己專案的需求學 |
| 「先學好再做」 | 「做的過程中學」 |
| 看起來很用功 | 產出真實的東西 |
| 三年後還是新手 | 三年後能做真實的事 |

**Tutorial 不是不能看**。**看完是為了應用到你的專案，不是為了「完成教學」**。

## 一個隱含的挑戰：專案的選擇

**Project-First 的難點**：**選對專案**。

**常見錯誤**：

### 錯誤 1：專案太大

「我要做一個完整的電商平台」 — 太大，永遠做不完。

**對策**：**切小**。MVP（Minimum Viable Product）。先做**能動的最小版本**。

### 錯誤 2：專案太小

「我寫一個 hello world」 — 太小，學不到什麼。

**對策**：**挑戰自己**，**剛好超過現在的能力**。

### 錯誤 3：沒有真實用戶 / 需求

「我做一個隨便什麼東西」 — 沒有終點。

**對策**：**為一個真實需求做**：
- 自己的需求（解決你自己的問題）
- 朋友的需求（幫人做）
- 假想用戶的需求（模擬真實情境）

**有用戶 / 需求** 的專案**強迫你做到真的能用**，不只是「跑完」。

### 錯誤 4：太像別人做過的

「我做一個 todo list」 — 網路上有 10 萬個 todo list 教學，你跟著做 = tutorial hell。

**對策**：**加一個獨特元素**。例：todo list **加上同步到 Google Calendar**、或**加上生產力分析**。這個獨特元素**強迫你獨立解決問題**。

## 專案清單建議（依技能）

### 學 Python

**新手專案**：
- 自動化你的重複工作（改名一堆檔案、抓資料）
- 寫一個小遊戲（猜數字、井字棋）
- 做一個簡單的網路爬蟲

**中階專案**：
- 寫一個 web app（Flask / FastAPI）
- 做一個機器學習應用
- 寫一個 CLI 工具

**進階專案**：
- 寫一個真實的服務（部署到雲端）
- 實現一個小型 interpreter / compiler
- 做開源貢獻

### 學投資

**新手專案**：
- 分析一家你熟的公司（寫一個一頁 thesis）
- 做一個小組合（虛擬投資，記錄 6 個月）
- 讀一年的 10-K，做筆記

**中階專案**：
- 深入分析一個產業
- 寫一個投資 thesis 部落格
- 實際投資小錢（能承受損失的）

**進階專案**：
- 持續追蹤幾家公司 2+ 年
- 撰寫公開的分析文章
- 嘗試具體策略（價值、成長、GARP 等）

### 學寫作

**新手專案**：
- 每天寫 200 字（日記）
- 每週寫一篇短文章
- 重寫自己的舊作，比較差別

**中階專案**：
- 維護一個部落格 / Substack
- 寫一篇長文（5000 字）
- 編輯別人的文章

**進階專案**：
- 寫一本書（即使只有第一章）
- 接受編輯的批評
- 實際發表文章到媒體

## 一個真實的故事：Project-First 的威力

我認識一個人想學程式。他**用傳統方法學了兩年**：

- 讀了 5 本 Python 書
- 看完 3 門線上課程
- 做了幾百道 LeetCode

**結果**：他**還是不會做真實的東西**。

他換成 Project-First：

- 定一個目標：**做一個自己的個人網站**
- 開始做：卡在 HTML → 學幾個 tag → 繼續
- 卡在 CSS → 學基本 → 繼續
- 卡在後端 → 學 Flask → 繼續
- 卡在部署 → 學 Vercel → 部署

**3 個月後**：他有一個**能動的網站**。

**6 個月後**：他加了更多功能，開始做第二個專案。

**2 年後**：他是一個**真正會寫 web 應用的人**。

**對比前兩年**：前兩年他**學了很多但不會做**。Project-First 之後 **學的少但真的會**。

## Project-First 的一個誤用

**誤用**：**只做 project，完全不讀理論**。

**結果**：你的專案能動，但**爛**。你用低效方法解決問題。

**正確的 Project-First**：

- **遇到卡點時讀理論**
- **做完一個階段後反思**（看看有沒有更好的做法）
- **定期補**：看看這個領域的好書、學習更成熟的模式

**Project-First 是「倒置傳統順序」，不是「消除理論」**。

## 與本課其他方法的結合

Project-First 跟本課其他方法完美結合：

- **Project + Deliberate Practice**（Ch 10）：專案中針對弱點刻意練
- **Project + Active Recall**（Ch 8）：卡點時先試自己解，再查
- **Project + Spaced Repetition**（Ch 9）：把學到的核心放 Anki
- **Project + Feynman**（Ch 11）：寫關於你做的專案的部落格
- **Project + Transfer**（Ch 21）：一個專案學到的用到下一個

**所有方法匯聚在真實專案中**。
