# Ch 23 — ceval.c：bytecode eval loop（三個 VM 的第三個）

> **目標**：讀懂 CPython 的心臟——`_PyEval_EvalFrameDefault` 這台 bytecode VM。這是本課第三台 VM（Lua Ch 4、SQLite Ch 9 是前兩台），三台共用同一個骨架：取指→分派→執行→前進。但 CPython 3.13 藏了一個你不先拆穿就會迷路的機關：**opcode 的實作不是手寫在 `ceval.c`，而是用一個 DSL 寫在 `bytecodes.c`、由工具生成 `generated_cases.c.h`、再被 `ceval.c` include**。這章先拆生成關係（這本身是「讀生成碼」的重要一課，接 `reading_code` Ch 22），再讀 dispatch 機制與一個 opcode 的完整生命。

> **目標codebase**：CPython `v3.13.1`（commit `0671451`）

## 為什麼需要這個？

你在 Lua 的 `luaV_execute` 裡看過一個乾淨的 VM 主迴圈：一個大 `switch`，每個 `case` 是一個 opcode 的實作，跑完 `goto` 回迴圈頭取下一個。SQLite 的 `sqlite3VdbeExec` 也是同一個形狀。你自然會期待 CPython 的 `_PyEval_EvalFrameDefault` 也長這樣——打開它，找 `case BINARY_OP:`，讀那段實作。

**然後你會撞牆。** 你 grep `case BINARY_OP` 在 `ceval.c` 裡找不到完整實作。你會開始懷疑自己讀錯檔案。這正是 `reading_code` Ch 22（讀懂巨集與 metaprogramming）警告的陷阱：**當一段 code 是生成出來的，你在「原始碼」裡找不到它，因為它根本不是手寫的**。CPython 3.11 起把 eval loop 逐步搬到一套自製 DSL，3.12/3.13 完全成形。不先理解這個生成關係，你讀 eval loop 會處處碰壁。

所以這章的順序刻意反直覺：**先拆生成機制，再讀 VM 本身**。

## 先建立直覺：一台 VM 的四拍，加上一層「生成」

任何 bytecode VM 都是這個四拍循環：

```
   ┌─────────────────────────────────────────────┐
   │  取指 fetch     next_instr 指向的 opcode      │
   │  解碼 decode    拆出 opcode + oparg            │
   │  分派 dispatch  跳到這個 opcode 的處理碼      │
   │  執行 execute   做事、動 stack、DECREF        │
   │  前進 advance   next_instr++，回到取指        │
   └───────────────────────┬─────────────────────┘
                           │ (loop)
```

Lua、SQLite、CPython 三台 VM 的四拍完全同構。CPython 3.13 的特殊之處在**「執行」那一拍的 code 是生成的**：

```
   bytecodes.c  ──(Tools/cases_generator/tier1_generator.py)──▶  generated_cases.c.h
   （opcode DSL 定義，「原始碼」）                                （生成，"Do not edit!"）
                                                                        │
                                                                        │ #include
                                                                        ▼
                                                          ceval.c 的 _PyEval_EvalFrameDefault
                                                          （四拍框架，把生成碼夾在 dispatch 裡）
```

**心智模型**：`ceval.c` 提供 VM 的「骨架」（取指、分派、迴圈、錯誤處理），`bytecodes.c` 提供每個 opcode 的「肉」（用一種類 C 的 DSL 寫），生成工具把肉編織進骨架。你讀 opcode 語意去 `bytecodes.c`，讀 VM 機制去 `ceval.c`，讀「編織後長怎樣」去 `generated_cases.c.h`。

## 核心一：拆穿生成關係——三個檔案的分工

先在真 source 裡把這三個檔案的關係一次看清。**`bytecodes.c` 的檔頭自己說明了它是什麼**：

```c
// This file contains instruction definitions.
// It is read by generators stored in Tools/cases_generator/
// to generate Python/generated_cases.c.h and others.
// Note that there is some dummy C code at the top and bottom of the file
// to fool text editors like VS Code into believing this is valid C code.
// ...
// The actual instruction definitions start at // BEGIN BYTECODES //.
```
（`Python/bytecodes.c:1-8`，v3.13.1）

注意第 4-5 行：這個檔**不是可編譯的 C**。它上下有假的 C code 只為了騙編輯器語法高亮。它是一種 DSL，被 `Tools/cases_generator/` 的工具讀取。

**生成檔 `generated_cases.c.h` 的檔頭也自我標示**：

```c
// This file is generated by Tools/cases_generator/tier1_generator.py
// from:
//   Python/bytecodes.c
// Do not edit!
```
（`Python/generated_cases.c.h:1-4`，v3.13.1）

「Do not edit!」——這是生成碼的通用標記（`reading_code` Ch 22 教你一看到就知道「別在這改，去改上游」）。

**`ceval.c` 把生成檔 include 進 eval loop**：

```
$ rg -n "generated_cases.c.h" Python/ceval.c
787:#include "generated_cases.c.h"
```

這個 `#include` 位在 `_PyEval_EvalFrameDefault`（`Python/ceval.c:682`）函式體**內部**的 dispatch 區塊裡。看 include 前後的骨架：

```c
    DISPATCH();

    {
    /* Start instructions */
#if !USE_COMPUTED_GOTOS
    dispatch_opcode:
        switch (opcode)
#endif
        {

#include "generated_cases.c.h"
```
（`Python/ceval.c:778-787`，v3.13.1）

看懂了嗎？`generated_cases.c.h` 就是那一大堆 opcode 的 `case`/`TARGET`。在「非 computed goto」的 build 裡，它們是 `switch(opcode)` 的 `case`；在 computed goto 的 build 裡，它們是一堆 label。這正是你在 `ceval.c` 裡 grep 不到 `case BINARY_OP` 的原因——它在被 include 的生成檔裡，不在 `ceval.c` 本身。

### DSL 長什麼樣：LOAD_FAST 的定義

看 `bytecodes.c` 裡 `LOAD_FAST` 的定義，感受這套 DSL：

```c
        replicate(8) pure inst(LOAD_FAST, (-- value)) {
            value = GETLOCAL(oparg);
            assert(value != NULL);
            Py_INCREF(value);
        }
```
（`Python/bytecodes.c:232-236`，v3.13.1）

拆解這行 DSL：
- `inst(LOAD_FAST, (-- value))`：定義一個 opcode `LOAD_FAST`，stack 效果是 `(-- value)`——左邊（消耗）是空、右邊（產出）是一個 `value`，即「push 一個值上 stack」。
- `pure`：這個 opcode 沒有副作用（除了 stack），生成器可據此優化。
- `replicate(8)`：生成 8 個變體（`LOAD_FAST_0`…`LOAD_FAST_7`），這是 3.13 的效能技巧。
- body：`value = GETLOCAL(oparg)` 取區域變數、`Py_INCREF(value)` 增引用計數（因為值要進 stack，多一個引用）。

**DSL 幫你做掉的事**：你只寫「消耗什麼、產出什麼」（`(-- value)`），生成器自動幫你算 stack pointer 怎麼動、生成 `stack_pointer[0] = value; stack_pointer += 1;`。這就是為什麼要用 DSL——手寫 stack 操作在幾百個 opcode 裡極易出錯。

### 生成後長什麼樣

同一個 `LOAD_FAST`，生成到 `generated_cases.c.h` 之後：

```c
        TARGET(LOAD_FAST) {
            frame->instr_ptr = next_instr;
            next_instr += 1;
            INSTRUCTION_STATS(LOAD_FAST);
            PyObject *value;
            value = GETLOCAL(oparg);
            assert(value != NULL);
            Py_INCREF(value);
            stack_pointer[0] = value;
            stack_pointer += 1;
```
（`Python/generated_cases.c.h:4284-4293`，v3.13.1）

對照著看：你在 DSL 寫的三行 body（`GETLOCAL`/`assert`/`Py_INCREF`）原封不動出現，但生成器**在前後補上了**：更新 `instr_ptr`、`next_instr += 1`（前進一格）、統計、以及最關鍵的 `stack_pointer[0] = value; stack_pointer += 1;`（把 `(-- value)` 的 stack 效果翻成真實指標運算）。**這就是 DSL 的價值——你宣告意圖，生成器負責樣板。**

## 核心二：dispatch 機制——computed goto

VM 的「分派」那一拍，決定了 eval loop 的效能。CPython 用的是 **computed goto**（GCC/Clang 的 `&&label` 擴充），看 `ceval_macros.h`：

```c
#if USE_COMPUTED_GOTOS
#  define TARGET(op) TARGET_##op:
#  define DISPATCH_GOTO() goto *opcode_targets[opcode]
#else
#  define TARGET(op) case op: TARGET_##op:
#  define DISPATCH_GOTO() goto dispatch_opcode
#endif
```
（`Python/ceval_macros.h:73-79`，v3.13.1）

兩種 build：
- **computed goto**（預設，編譯器支援時）：每個 opcode 是一個 label（`TARGET_LOAD_FAST:`），`opcode_targets[]` 是一張「opcode → label 位址」的表，`goto *opcode_targets[opcode]` 直接跳過去。
- **fallback**：每個 opcode 是 `switch` 的 `case`，`goto dispatch_opcode` 回到 switch 頭。

為什麼 computed goto 快？一個大 `switch` 每次分派都從同一個點跳出，CPU 的分支預測器只有一個歷史記錄，命中率低。computed goto 讓**每個 opcode 結尾各有一個 dispatch 點**，分支預測器能對「這個 opcode 後面常接哪個」建立獨立的預測——對 bytecode 這種有規律的序列（`LOAD_FAST` 後常接 `LOAD_FAST` 或 `BINARY_OP`）命中率大增。

分派巨集本身：

```c
#define DISPATCH() \
    { \
        NEXTOPARG(); \
        PRE_DISPATCH_GOTO(); \
        DISPATCH_GOTO(); \
    }
```
（`Python/ceval_macros.h:109-114`，v3.13.1）

`NEXTOPARG()` 取指 + 解碼（讀出 `opcode` 和 `oparg`），`DISPATCH_GOTO()` 跳到那個 opcode 的處理碼。每個 opcode 的 body 結尾都以 `DISPATCH()` 收場——這就是「執行完 → 前進 → 取下一個」的循環閉合。**這是三台 VM 共通的 dispatch pattern**（Lua 用 label + computed goto、SQLite 用 switch），Ch 26 與 Ch 27 會把三者並排對照。

## 核心三：一個 opcode 的完整生命——BINARY_OP

把 `a + b` 追一遍，看 opcode 從 DSL 到執行的全貌。`a + b` 編成三個 opcode：`LOAD_FAST a`、`LOAD_FAST b`、`BINARY_OP(NB_ADD)`。前兩個把 `a`、`b` push 上 stack，`BINARY_OP` 是重點。

DSL 定義（`bytecodes.c`）把 `BINARY_OP` 拆成兩個 micro-op 組合：

```c
        op(_BINARY_OP, (lhs, rhs -- res)) {
            assert(_PyEval_BinaryOps[oparg]);
            res = _PyEval_BinaryOps[oparg](lhs, rhs);
            DECREF_INPUTS();
            ERROR_IF(res == NULL, error);
        }

        macro(BINARY_OP) = _SPECIALIZE_BINARY_OP + _BINARY_OP;
```
（`Python/bytecodes.c:4064-4071`，v3.13.1）

讀這段：
- `(lhs, rhs -- res)`：消耗 stack 上兩個值 `lhs`、`rhs`，產出一個 `res`。
- `_PyEval_BinaryOps[oparg]`：`oparg` 是運算種類（`NB_ADD`=加、`NB_SUBTRACT`=減…），這張表把它映射到 C 函式。`+` 對應 `NB_ADD`，查表得 `PyNumber_Add`。
- `DECREF_INPUTS()`：兩個輸入用完了，各減一次引用（DSL 巨集，生成時展開）。
- `ERROR_IF(res == NULL, error)`：出錯就跳到錯誤處理。
- `macro(BINARY_OP) = _SPECIALIZE_BINARY_OP + _BINARY_OP`：完整的 `BINARY_OP` 是「特化探測」+「泛型加法」兩個 micro-op 串起來（特化是 3.11+ 的 adaptive specialization，先跳過）。

那張表就在 `ceval.c`：

```c
const binaryfunc _PyEval_BinaryOps[] = {
    [NB_ADD] = PyNumber_Add,
    [NB_AND] = PyNumber_And,
    ...
    [NB_SUBTRACT] = PyNumber_Subtract,
    ...
};
```
（`Python/ceval.c:313-316`，v3.13.1）

生成後，這個 DSL 在 `generated_cases.c.h` 裡展開成（節錄 `_BINARY_OP` 那段）：

```c
            // _BINARY_OP
            {
                assert(_PyEval_BinaryOps[oparg]);
                res = _PyEval_BinaryOps[oparg](lhs, rhs);
                Py_DECREF(lhs);
                Py_DECREF(rhs);
                if (res == NULL) goto pop_2_error;
            }
            stack_pointer[-2] = res;
            stack_pointer += -1;
            DISPATCH();
```
（`Python/generated_cases.c.h:129-140`，v3.13.1）

**對照 DSL 與生成碼**，你看到生成器做了三件翻譯：
- `DECREF_INPUTS()` → 展開成 `Py_DECREF(lhs); Py_DECREF(rhs);`（它知道輸入是 `lhs`、`rhs` 兩個）。
- `ERROR_IF(res == NULL, error)` → `if (res == NULL) goto pop_2_error;`（它算出出錯時 stack 上有 2 個要 pop，跳去對應的 `pop_2_error`）。
- `(lhs, rhs -- res)` 的 stack 效果 → `stack_pointer[-2] = res; stack_pointer += -1;`（吃掉 2 個、放回 1 個，淨 -1）。

`res = _PyEval_BinaryOps[oparg](lhs, rhs)` 這行把控制權交給 `PyNumber_Add`——下一站是 object model 的型別 slot（`PyNumber_Add` → `nb_add` slot → `long_add`），那是 Ch 24 的主場，也是練習 E 要你親手追完的路。

### 真跑：用 `dis` 看真 bytecode，用 gdb 看真 call chain

別只信教材。build 完 CPython（`./configure --with-pydebug && make -j`）後，用內建 `dis` 模組看 `a + b` 真的編成什麼（把它放進函式才會走 `LOAD_FAST`——模組層級走的是 `LOAD_NAME`）：

```
$ ./python -c "

def f(a, b):
    return a + b
dis.dis(f)
"
  4           RESUME                   0
              LOAD_FAST_LOAD_FAST      1 (a, b)
              BINARY_OP                0 (+)
              RETURN_VALUE
```

（在 WSL2 / Python 3.13.1 debug build 真跑輸出。）注意兩個小細節印證前文：`LOAD_FAST_LOAD_FAST` 是把兩個相鄰 `LOAD_FAST` 合成的「super-instruction」（3.13 的效能技巧，正是 DSL `replicate`/super-instruction 那條線的產物）；`BINARY_OP 0 (+)` 的 `0` 就是 `oparg`，等於 `NB_ADD`——對上 `_PyEval_BinaryOps[NB_ADD] = PyNumber_Add`。

再用 gdb 在 `PyNumber_Add` 下中斷點，跑 `f(3, 4)`，看真實 call stack：

## 底層機制：_PyInterpreterFrame——一次呼叫的執行上下文

eval loop 操作的「當前 frame」是 `_PyInterpreterFrame`（`Include/internal/pycore_frame.h`）。每次 Python 函式呼叫產生一個 frame，eval loop 在它上面跑：

```c
typedef struct _PyInterpreterFrame {
    PyObject *f_executable; /* Strong reference (code object or None) */
    struct _PyInterpreterFrame *previous;
    PyObject *f_funcobj;
    PyObject *f_globals;
    PyObject *f_builtins;
    PyObject *f_locals;
    PyFrameObject *frame_obj;
    _Py_CODEUNIT *instr_ptr; /* Instruction currently executing (or about to begin) */
    int stacktop;
    uint16_t return_offset;
    char owner;
    PyObject *localsplus[1];
} _PyInterpreterFrame;
```
（`Include/internal/pycore_frame.h:61-75`，v3.13.1）

關鍵欄位：
- `instr_ptr`：指令指標，指向當前 opcode。eval loop 的 `next_instr` 就是從這裡起跑，`DISPATCH()` 時前進。
- `previous`：指向呼叫者的 frame——這是 call stack 的鏈，`a()` 呼叫 `b()` 時 `b` 的 frame `previous` 指向 `a` 的。
- `localsplus[1]`：一個 flexible array，同時裝**區域變數**（`LOAD_FAST` 的 `GETLOCAL(oparg)` 從這取）和**運算堆疊**（`stack_pointer` 在這上面滑動）。這是 3.11+ 的「frames 攤平在一塊連續記憶體」設計，取代舊版一個 frame 一個堆積物件，省下大量配置。

**3.11 的大改動**：舊 CPython 每次呼叫都 malloc 一個 `PyFrameObject`；3.11+ 改成 `_PyInterpreterFrame` 直接長在一塊 data stack 上（只有需要暴露給 Python（如 traceback、`sys._getframe()`）時才 lazy 建出重量級的 `PyFrameObject`，即這裡的 `frame_obj`）。這是 CPython 近年最大的效能來源之一。你追 eval loop 時看到 `frame->localsplus`、`frame->instr_ptr`，就是在這個攤平結構上操作。

## 對比與取捨

| 面向 | Lua `luaV_execute` | SQLite `sqlite3VdbeExec` | CPython `_PyEval_EvalFrameDefault` |
|---|---|---|---|
| VM 型別 | register VM | register VM | **stack VM** |
| opcode 實作寫在哪 | 手寫在 `lvm.c` | 手寫在 `vdbe.c` | **DSL `bytecodes.c` → 生成** |
| dispatch | computed goto | switch | computed goto（可退 switch） |
| 值在哪 | register（`TValue` 陣列） | register（`Mem` 陣列） | stack（`localsplus` 上滑動） |
| frame | `CallInfo` 鏈 | 無（單一 program） | `_PyInterpreterFrame` 攤平鏈 |

三台 VM 最大的取捨差異：**Lua/SQLite 是 register VM**（opcode 直接指名操作哪個 register，指令數少、每指令肥），**CPython 是 stack VM**（opcode 隱含操作 stack 頂，指令數多、每指令瘦）。stack VM 的 code 好生成（不用配 register），這也呼應了 CPython 選 DSL 生成的方向。Ch 27 會把這組對比展開成完整的三 VM 橫向比較。

## 踩雷集錦

1. **錯誤直覺：opcode 實作在 `ceval.c` 用 `switch/case` 手寫，grep `case BINARY_OP` 就找得到。** → 正確認識（3.13 專屬）：實作在 DSL `bytecodes.c`，生成到 `generated_cases.c.h`，被 `ceval.c:787` include。你在 `ceval.c` 找不到完整 opcode body，那不是你讀錯，是它根本不手寫在那。要讀語意去 `bytecodes.c`，要讀展開結果去 `generated_cases.c.h`。
2. **錯誤直覺：`bytecodes.c` 是可編譯的 C 檔。** → 正確認識：它是 DSL，檔頭明說「上下有假 C code 只為騙編輯器」（`bytecodes.c:4-5`）。裡面的 `inst(...)`, `op(...)`, `macro(...)`, `(lhs, rhs -- res)` 都是 DSL 語法，不是 C。直接 `gcc bytecodes.c` 不會過也沒意義。
3. **錯誤直覺：改 opcode 行為就改 `generated_cases.c.h`。** → 正確認識：那是生成檔，檔頭寫「Do not edit!」。改它會在下次 `make`（重跑生成器）時被覆蓋。要改行為改上游 `bytecodes.c`，重跑生成。這是所有生成碼的通則（`reading_code` Ch 22）。
4. **錯誤直覺：CPython 是 register VM（像 Lua）。** → 正確認識：CPython 是 **stack VM**。`BINARY_OP` 不指名運算元，而是隱含吃 stack 頂兩個、放回一個。看 `(lhs, rhs -- res)` 這種 stack 效果標記就知道——它描述的是 stack 進出，不是 register 編號。
5. **錯誤直覺：每次 Python 函式呼叫都 malloc 一個 frame 物件。** → 正確認識（3.11+）：`_PyInterpreterFrame` 攤平在一塊連續 data stack 上，不是每次 malloc。重量級的 `PyFrameObject` 只在需要暴露給 Python 層（traceback、`sys._getframe`）時才 lazy 建出。看到 `frame->localsplus` 在連續記憶體上，就是這個設計。

## 進階：再往深一層

- **adaptive specialization（PEP 659）**：`BINARY_OP` 的完整 macro 是 `_SPECIALIZE_BINARY_OP + _BINARY_OP`。前者是 3.11+ 的「自適應特化」：VM 觀察到某個 `BINARY_OP` 一直在加兩個 int，就把它就地改寫成 `BINARY_OP_ADD_INT`（跳過型別檢查、直接算）。`generated_cases.c.h:111-127` 那段 `ADAPTIVE_COUNTER_TRIGGERS` 就是特化觸發邏輯。這是 CPython 3.11+ 提速的另一大來源，`Python/specialize.c` 是它的家。
- **tier 2 / JIT（3.13 實驗性）**：3.13 引入實驗性的 tier-2 optimizer 與 copy-and-patch JIT。`bytecodes.c` 的 micro-op（`op(_BINARY_OP, ...)`）拆分正是為了讓 tier-2 能把多個 micro-op 串成 trace 再優化。`generated_cases.c.h` 開頭的 `#ifdef TIER_TWO` 就是這條線。你今天讀的是 tier 1（傳統 bytecode 直譯），知道有 tier 2 這層即可。
- **`Tools/cases_generator/` 的生成器本身**：想真正理解生成關係，讀 `tier1_generator.py` 和 `analyzer.py`。它們用一個小 C lexer/parser 解析 `bytecodes.c` 的 DSL，算出每個 opcode 的 stack 效果、展開巨集、輸出 C。這是「讀生成器來理解生成碼」的終極手段——但屬按需深潛，只在你要改 DSL 本身時才動用。

## 本章重點整理

- CPython 的 eval loop 是 `_PyEval_EvalFrameDefault`（`Python/ceval.c:682`），本課第三台 bytecode VM，四拍循環（取指→分派→執行→前進）與 Lua/SQLite 同構。
- **3.13 生成關係（最重要）**：opcode 語意寫在 DSL `bytecodes.c` → 工具 `tier1_generator.py` 生成 `generated_cases.c.h`（"Do not edit!"）→ `ceval.c:787` 把它 include 進 dispatch 區塊。
- DSL 用 `(lhs, rhs -- res)` 標 stack 效果，生成器自動翻成真實 `stack_pointer` 運算與 `Py_DECREF`/`goto error`——你宣告意圖，它產樣板。
- dispatch 用 computed goto（`goto *opcode_targets[opcode]`），比大 switch 的分支預測命中率高；可退回 switch。
- CPython 是 **stack VM**（對照 Lua/SQLite 的 register VM）；frame 是攤平的 `_PyInterpreterFrame`（3.11+），不再每次 malloc。
