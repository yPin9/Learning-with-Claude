# Ch 31 — 打造持續讀碼的訓練習慣

> **目標**：畢業之後，怎麼讓你的 pattern 庫**繼續長大**而不萎縮。設計一套可執行的持續訓練：定期限時攻堅硬 codebase、參與開源 review、patch-diff 讀漏洞、建自己的 pattern 筆記系統。給你一份能真正跑起來的季度訓練計畫。

> **本章不讀 code**：這是一章關於「把讀碼變成長期習慣」的方法章，不引用新 source。它把前 30 章的技能收尾成一個可持續的循環。

## 為什麼需要這個？

你剛拿到 pattern 字典（Ch 30）。但這裡有個殘酷的事實：**技能會退化，pattern 庫會萎縮。** 六個月不碰陌生 codebase，你認出 arena allocator 的速度會慢回去，冷啟動的膽識會鈍化，費曼複述會變得吞吞吐吐。讀碼是肌肉，肌肉不練會掉。

這門課叫「讀碼健身房」不是隨便取的。**健身房的價值不在你去過一次，在你養成固定去的習慣。** 你可以在這門課的六個 Part 練出漂亮的攻堅動作，但如果畢業後就不再碰新 codebase，一年後你和沒上過課的人差別不大——差別只在你「曾經會」。

這一章解決「怎麼持續」。不是雞湯式的「保持學習」，是一套**具體、可排進行事曆、有交付物、能自我檢驗**的訓練協定。目標：讓「限時攻堅一個陌生 codebase」變成像跑步一樣的日常，pattern 字典每季度多幾張卡。

## 先建立直覺：三種訓練強度

不是每次都要 90 分鐘全套攻堅。像重訓有輕重日，讀碼訓練也分強度，混搭才能持續：

```
   ┌─ 高強度（每季 1-2 次，2-4 小時）────────────────────
   │   限時冷啟動攻堅一個全新硬 codebase
   │   → 全套 SOP：偵察→假設→追路徑→外化→費曼→萃取 pattern
   │   → 這是 Final 那種等級，最累但長最多肌肉
   │
   ├─ 中強度（每週 1 次，30-60 分鐘）──────────────────
   │   在熟悉或半熟的專案裡追一條沒追過的路徑
   │   或 review 一個 open source PR、讀一個 CVE patch-diff
   │   → 局部攻堅，維持手感、擴充特定 pattern
   │
   └─ 低強度（每天/隨手，5-15 分鐘）─────────────────
       讀一小段陌生 code + 記一張 pattern 卡
       通勤讀一個函式、工作中多讀一層依賴、隨手 rg 一個好奇的機制
       → 保持 pattern 辨識的「在線」狀態，成本極低
```

**關鍵：低強度天天做維持在線，中強度每週做維持手感，高強度每季做真正成長。** 只做高強度會累到放棄；只做低強度不會成長。混搭。

## 訓練法一：定期限時攻堅硬 codebase（高強度）

這是 Final 的常態化。**每季挑一個你領域最硬、最沒碰過的中型 codebase，限時攻堅一次。**

**選目標的標準**（和 Final 一致）：中型（2 萬–15 萬行）、活躍、有測試、陌生但用過/聽過、能 build。刻意挑**跨出舒適圈**的——你是後端就挑一個前端 runtime、你懂 C 就挑一個 Rust/Go 專案、你做應用層就挑一個 kernel 子系統。**舒適圈內的攻堅是複習，舒適圈外的才是成長。**

**每次攻堅固定產出三樣**（Final 的縮小版）：

1. **一張架構地圖**：偵察 60 分鐘，畫出模組分層 + 核心 struct + 主流程骨架。
2. **一條關鍵路徑的完整 trace**：挑一個使用者可觀察行為，從觸發追到底，全程外化（畫圖、記假設、能 gdb 就 gdb 驗）。
3. **至少 3 張 pattern 卡**，標明哪些是字典裡已有 pattern 在新專案重現（複利發生的證據）、哪些是**新 pattern**（字典擴充）。

**碼表是重點。** 不限時你會無限拖延或無限鑽 rabbit hole。限時逼你收斂——這正是 `reading_code` Ch 11 的紀律在真實世界的延續。3 小時攻不完是正常的（一個成熟專案本來就攻不完），目標不是讀懂全部，是**在時限內從「零背景」推進到「能畫地圖 + 追一條路徑 + 講一段費曼」**。

## 訓練法二：參與開源 review（中強度，接 `open_source` 課）

**Review 別人的 PR 是被低估的讀碼訓練。** 為什麼特別有效：

- **有明確範圍**：一個 PR 就是一小塊 diff，天然收斂，不會迷失在整個專案裡。
- **有正確答案的壓力**：你 review 會被公開檢視，逼你真讀懂而非假裝懂——這是最強的費曼測試（Ch 29），因為聽眾是真人維護者。
- **強迫你進入陌生 code 的上下文**：要判斷一個 diff 對不對，你得讀懂它周圍的 code、它改的機制、它會不會弄壞別的東西——這是精準的局部攻堅。
- **累積特定專案的 pattern**：長期 review 同一個專案，你會內化它的慣例、命名、架構 pattern——這是最快變成某專案「本地人」的路。

**具體做法**（`open_source` 課教的協作技能在此變成訓練工具）：

1. 挑一個你用的、活躍的開源專案，訂閱它的 PR。
2. 每週挑 1-2 個規模適中的 PR，**當作攻堅任務讀**：這個 PR 改什麼機制？我讀懂它周圍的 code 了嗎？它的假設對嗎？有沒有漏掉的 case？
3. 從「只讀不評」開始，讀懂了再留有建設性的 comment。**能用一句話向作者複述「你這個 PR 在做什麼、為什麼」就是你讀懂了的證明。**
4. 進階：認領一個 `good first issue`，自己發 PR。你會被迫從 reviewer 視角讀自己的 code——雙視角讀碼。

## 訓練法三：patch-diff 讀漏洞（中強度，接 `reading_code` Ch 32 / `code_auditing`）

**讀安全補丁是密度極高的讀碼訓練**——一個 CVE 的修補 diff，濃縮了「哪裡出錯、為什麼危險、怎麼修對」三件事。

為什麼有效：

- **極致收斂**：一個安全 patch 常常只改幾行。但要讀懂那幾行**為什麼**是漏洞、**為什麼**這樣改能修好，你得把周圍的 data flow、假設、邊界條件全讀通。這是「兩百行收斂」的極限版。
- **訓練對抗式讀碼**：安全視角逼你問「這裡的假設能不能被打破？如果輸入是惡意的會怎樣？」——這是普通讀碼練不到的肌肉，也是 patch-diff 讀碼的核心（`reading_code` Ch 32）。
- **pattern 的暗面**：你會累積「漏洞 pattern」——整數溢位、UAF、TOCTOU、邊界 off-by-one……這些是 pattern 字典的安全篇。

**具體做法**：

1. 挑一個你熟的專案（甚至本課六個之一——它們都有 CVE 歷史）的一個 CVE。
2. 找到修補 commit（`git log`、CVE 資料庫、專案 security advisory）。
3. **先看 diff 前的 code，自己猜「漏洞在哪、怎麼觸發」**（先猜後讀，Ch 29）。
4. 看 diff，驗證你的猜測；讀懂「為什麼原本錯、為什麼這樣修對」。
5. 用 `git log -S`/`blame`（`reading_code` Ch 17）考古：這行有問題的 code 是誰、何時、為什麼寫進來的？
6. 記一張「漏洞 pattern 卡」進字典。

這條訓練直接餵給 `code_auditing`——讀漏洞 patch 讀多了，你自己就開始能在陌生 code 裡嗅出可疑處。

## 訓練法四：建自己的 pattern 筆記系統（貫穿全部）

前三種訓練都會產出 pattern 卡、攻堅 journal、漏洞筆記。**這些東西不系統化保存，等於沒訓練**——三個月後全忘。你需要一個個人 pattern 筆記系統。

**系統的三個部分**：

```
   ┌─ pattern 字典（活的）──── Ch 30 那張表的個人版
   │   每張卡：beacon / 見於哪些專案（持續加）/ 遷移到 / 變體 / 反例
   │   每次攻堅撞見已有 pattern → 在「見於」欄加一筆（複利可視化）
   │   撞見新 pattern → 加一張新卡
   │
   ├─ 攻堅 journal（一次一篇）── 每場攻堅的 Ch 29 六階段記錄
   │   任務界定 / 偵察地圖 / 假設與推翻 / pull chain 圖 / 費曼摘要 / TODO
   │   價值：事後 review 自己的 SOP、回看「我攻過哪些系統」
   │
   └─ TODO / rabbit hole 池 ── 攻堅時忍住沒追的坑
       每個坑一句話 + 在哪個專案哪個檔
       下次沒靈感時，從這裡撈一個開一場小攻堅
```

**工具不重要**（純文字檔、Obsidian、個人 wiki 都行），**結構和習慣才重要**。核心原則：

- **一次攻堅一定產出可保存的東西**（至少一張 pattern 卡 + 一份 journal）。沒產出的攻堅=沒發生。
- **pattern 卡的「見於」欄要持續加**。同一個 pattern 在第五個專案又見到，就在卡上加第五筆——這一欄的增長就是你複利的儀表板。
- **每季回看一次**：翻攻堅 journal，你會看到自己 SOP 的進步（早期到處迷路、後期直線收斂），也會發現重複踩的雷（拿去改進 SOP）。

## 一份可執行的季度訓練計畫（照抄即可跑）

方法講完，給你一份**能直接排進行事曆**的 13 週計畫。這不是建議清單，是一張你可以每季重跑的表。目標：一季結束，pattern 字典多 6-10 張卡、攻堅 journal 多 2 篇、手感全程在線。

```
   ┌─ 第 1 週：定錨 ─────────────────────────────────────
   │   • 挑好本季的高強度攻堅目標（1 個舒適圈外的中型專案）
   │   • clone 下來、記 commit hash、確認能 build
   │   • 開一份本季 journal，寫下「為什麼挑它、我最怕它哪裡」
   │
   ├─ 第 2 週：高強度攻堅 #1（3 小時，Final 等級）────────
   │   • 全套 SOP，產出地圖 + 一條路徑 + 3 張 pattern 卡
   │   • 至少 1 張是字典 pattern 重現（複利證據）
   │
   ├─ 第 3-6 週：中強度維持（每週 45 分鐘）──────────────
   │   • 單數週：review 1 個該專案（或你常用專案）的 PR，
   │             用一句話向作者複述「這 PR 在幹嘛」
   │   • 雙數週：讀 1 個 CVE patch-diff（先猜後讀 → 記漏洞卡）
   │   • 每天 10 分鐘低強度：讀一個陌生函式、rg 一個好奇機制
   │
   ├─ 第 7 週：高強度攻堅 #2（3 小時）─────────────────────
   │   • 換一條該專案沒追過的路徑，或換一個新專案
   │   • 對比第 2 週的 journal——你這次快了嗎？迷路少了嗎？
   │
   ├─ 第 8-11 週：中強度維持（同第 3-6 週節奏）──────────
   │
   ├─ 第 12 週：整併 ────────────────────────────────────
   │   • 把本季所有 pattern 卡歸進主字典，更新「見於」欄
   │   • 挑 1 場攻堅寫成公開文章/內部分享（最高階費曼）
   │
   └─ 第 13 週：回顧 + 下季定錨 ─────────────────────────
       • 翻本季 2 篇 journal：SOP 哪裡進步了？重複踩什麼雷？
       • 把重複的雷寫進「我的 SOP 改進清單」
       • 挑下季目標，回到第 1 週
```

**這張表的設計邏輯**：兩次高強度（真成長）夾著持續的中/低強度（維持 + 擴充），首尾各一週做定錨和回顧（讓訓練有方向、可檢驗進步）。**每季照跑一次，一年四季 = 8 場硬攻堅 + 40 張 pattern 卡起跳 + 一份會說話的 journal 歷史。** 三年後回看，你的 SOP 和 pattern 庫會是碾壓性的。

**降級版**（真的很忙）：砍掉一次高強度攻堅、中強度改兩週一次。**但別砍每天 10 分鐘的低強度**——那是維持「在線」狀態的最低成本保險，斷了最傷。

## 底層機制：這個循環為什麼會複利

把四種訓練 + 筆記系統畫成一個閉環，看複利怎麼發生：

```
        ┌──────────────────────────────────────────────┐
        │                                                │
        ▼                                                │
   限時攻堅陌生 codebase                                  │
   （高強度，每季）                                       │
        │                                                │
        │ 產出：地圖 + 路徑 trace + pattern 卡            │
        ▼                                                │
   pattern 筆記系統 ◄──── open source review（每週）     │
   （字典 + journal）◄──── patch-diff 讀漏洞（每週）      │
        │                 ◄──── 隨手讀（每天）           │
        │                                                │
        │ 字典越大 →                                      │
        ▼                                                │
   下次攻堅時「一眼認出」的 pattern 越多                   │
   → 攻堅更快 → 能攻更硬的目標 → 撞見更多新 pattern ──────┘
                    （複利飛輪）
```

**飛輪的關鍵齒輪**：字典越大 → 攻堅越快 → 敢攻更硬的目標 → 更硬的目標有更多新 pattern → 字典又變大。這是正回饋。**每一次攻堅都比上一次省力一點，因為你認出的 pattern 又多了一個。** 這正是 Ch 27 三個 VM 對照證明的「讀懂第三個只要 30 分鐘」——只是把它從一門課擴展成一輩子。

反過來，不轉這個飛輪的人，pattern 庫是靜態的：他這輩子讀 code 的速度不太會變，因為他不累積可遷移的 chunk，每個新專案都從零讀。**你和他的差距，每年拉開一點。**

## 對比與取捨：可持續 vs 一次性

| | 一次性衝刺（多數人）| 可持續訓練（本章）|
|---|---|---|
| 節奏 | 上完課/讀完書就停 | 高/中/低強度混搭，長期跑 |
| pattern 庫 | 靜態，慢慢萎縮 | 每季擴充，飛輪複利 |
| 攻堅速度 | 幾年不變 | 逐年變快 |
| 產出 | 課程結束就無 | 持續累積的個人字典 + journal |
| 成本 | 一次性高投入 | 分散、低日常成本、可持續 |
| 三年後 | 「曾經會攻堅」| 「攻堅是日常，字典幾百張卡」|

**取捨在於：可持續訓練要求你接受「慢但不停」，而非「快但一次性」。** 每週 30 分鐘 review 一個 PR、每天 10 分鐘讀一個函式，短期看不出效果——但複利是指數的，三年後的差距是碾壓性的。願不願意接受「慢但不停」，是這章唯一要你做的決定。

## 踩雷集錦

1. **只做高強度、把自己累垮。** 每次都要 3 小時全套攻堅，兩個月後你會放棄。**混搭強度**：高強度每季、中強度每週、低強度每天。持續性比單次強度重要一百倍。

2. **攻堅不產出可保存的東西。** 讀了很爽但不記 pattern 卡、不寫 journal——三個月後全忘，等於沒訓練。鐵律：**一次攻堅至少產出一張 pattern 卡 + 一份 journal**，沒產出的攻堅視為沒發生。

3. **永遠待在舒適圈。** 每次都攻自己熟的領域/語言，那是複習不是成長。**刻意挑你不會的語言、不懂的領域**——不舒服才長肌肉。後端挑前端 runtime、C 挑 Rust、應用挑 kernel。

4. **pattern 字典建好就不維護。** Ch 30 的字典是起點不是終點。不持續往「見於」欄加筆、不加新卡，它就過期了。字典是**活的**——每次攻堅都餵它。

5. **把 review/讀 patch 當義務而非訓練。** Review PR、讀 CVE 如果只是機械看過，沒有「先猜後讀、費曼複述、記 pattern」的動作，就浪費了。**每個 PR/patch 都當一場小攻堅**，帶著全套動作去讀。

## 進階：再往深一層

- **找一個讀碼夥伴/讀書會**：定期和人「pair reading」一個 codebase，或輪流費曼複述給對方聽。聽眾是真人時，費曼測試的壓力最大、效果最好。這也接 `open_source` 的社群協作。
- **把攻堅 journal 寫成公開文章/talk**：「我如何攻堅 X 的 Y 子系統」這種文章，強迫你把 journal 整理到別人能懂的程度——是最高等級的費曼測試，也建立你的技術聲譽。
- **建立領域專屬的 pattern 子字典**：如果你深耕某領域（資料庫、瀏覽器、kernel），除了通用 pattern，累積該領域專屬的 pattern（MVCC、JIT deopt、cross-cache…）。通用字典 + 領域字典雙軌，讓你在該領域的攻堅速度斷層領先。

## 本章重點整理

- **技能會退化、pattern 庫會萎縮**：這門課的價值不在上過一次，在把「攻堅陌生 codebase」變成日常習慣。
- **三種訓練強度混搭**：高強度（每季全套攻堅硬目標）、中強度（每週 review PR / 讀 patch-diff）、低強度（每天隨手讀 + 記卡）。混搭才可持續。
- **四種訓練法**：限時攻堅硬 codebase、參與 open source review（接 `open_source`）、patch-diff 讀漏洞（接 `code_auditing`/`reading_code` Ch 32）、建 pattern 筆記系統。
- **筆記系統三部分**：活的 pattern 字典（持續加「見於」欄）、攻堅 journal（一次一篇）、rabbit hole 池。一次攻堅必產出可保存的東西。
- **複利飛輪**：字典越大 → 攻堅越快 → 敢攻更硬目標 → 撞見更多新 pattern → 字典又變大。願意接受「慢但不停」的人，逐年拉開差距。
