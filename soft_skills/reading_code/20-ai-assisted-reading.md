# Ch 20 — AI 輔助讀碼

> **目標**：把 LLM（大型語言模型，如 Claude、GPT）正確地嵌進讀碼流程——用它加速你不擅長或耗時的部分（解釋陌生片段、翻譯陌生語言慣用法、生初步假設、生 summary），同時清醒地認識它的致命缺陷（幻覺不存在的 API、對大 codebase 全局無知、自信說錯、版本混淆）。這章的靈魂是一句認識論命題：**LLM 是加速器，不是真相來源。** 它產假設，你用前面所有工具（Ch 10 假設驅動、Ch 12–17 靜態/歷史、Ch 18–19 動態）驗證。把這條線內化，AI 讓你快數倍；不內化，AI 讓你自信地讀錯。

> **環境**：本章以概念與工作流為主，少量真跑。示範用的沙包仍是 `~/reading_code_lab/redis`（redis 7.4.0），用來演示「LLM 說某件事、我們用 rg/gdb 戳破或證實」的具體情境。本章不綁定特定 LLM 產品，但示範時以 agentic 讀碼工具（Claude Code 類）與模型（如 Claude Opus 4.8）為例。

## 為什麼這章危險，也為什麼重要

前面十九章我們建立的是一套**可驗證**的讀碼方法：rg 找的字串就在那裡、cscope 反查的呼叫者是真的、gdb backtrace 是程式真的走過的路徑、git blame 是不可變的歷史。每一個工具的輸出你都能當作**事實**接受。

LLM 打破了這個性質。它是第一個會「**流暢地、自信地、對你說錯話**」的讀碼工具。它不查你的 codebase（除非你餵它），它從訓練資料裡「回憶」出一個**聽起來對**的答案——而聽起來對和真的對，是兩件事。這使得 AI 輔助讀碼同時是**最強的加速器**和**最危險的錯誤來源**。

但拒絕用它是愚蠢的。一個資深研究者面對一段完全陌生的 Rust unsafe、一個沒見過的 template metaprogramming、一坨十層巢狀巨集——LLM 在三秒內給你一個**可能對**的解釋，讓你有個起點去驗證，這比你從零硬啃快一個數量級。關鍵不是「用不用」，是「**怎麼用才不會被騙**」。

這章要教的核心工作流只有一句話，但它決定了你是被 AI 加速還是被 AI 帶溝裡：

> **LLM 產假設 → 你用工具驗證 → 只接受驗證過的結論。**

這其實就是 Ch 10「假設驅動讀碼」的自然延伸：LLM 是一台**極高產能的假設生成器**。它能在你想到一個假設的時間裡生成十個。但假設終究是假設——Ch 10 教你的驗證紀律，在 AI 時代不是放鬆了，是**變得更重要**了，因為假設的產量暴增，而它們的平均可信度**下降**了。

## LLM 擅長什麼：把它當成一個「博學但會唬爛的同事」

先建立正確的心智模型。LLM 不是搜尋引擎、不是編譯器、不是文件。最貼切的類比是：**一個讀過海量 code 但沒讀過「你這個」codebase 的資深同事，記性很好但偶爾記混、而且從不說「我不確定」。** 這個同事在幾件事上極其有用：

**1. 解釋陌生片段——降低「冷啟動」門檻。** 你貼一段沒背景的 code，它給你一個結構化的「這大概在做什麼」。對於你完全沒領域知識的東西（一段密碼學常數運算、一個 lock-free 演算法、一個你沒學過的語言的慣用法），這是最快的**入門解釋**。它不一定全對，但能讓你從「完全看不懂」跳到「有個框架可以驗證」。

**2. 翻譯陌生語言/框架的慣用法。** 你是 C 專家，第一次看 Rust 的 `?` 運算子、`impl Trait`、生命週期標註；或第一次看某個 DSL、某個框架的魔法。LLM 把「這個語言/框架特有的寫法」翻譯成你熟悉的概念（「這個 `?` 相當於 C 裡的 `if (err) return err;`」），這是**跨語言讀碼**（Ch 29）的加速器。

**3. 生初步 summary 與命名意圖猜測。** 一個縮寫的變數名 `rdb_ch`、一個沒註解的函式 `sdscatlen`——LLM 猜「這大概是 RDB channel」「這大概是 SDS 字串的 concat with length」。**猜命名意圖**是它的強項，因為命名慣例是它訓練資料裡的高頻模式。猜對了幫你省時間，猜錯了你也很快能驗證。

**4. 生初步假設（承接 Ch 10）。** 「這個函式看起來像是命令分派的入口，我猜它會查一個命令表然後呼叫對應的 handler」——這種**方向性假設**，LLM 生成得又快又多。你不必自己憋，讓它先吐五個假設，你挑最像的去驗證。

這四件事的共同點：**它們都是「加速你形成一個可驗證的起點」，而不是「給你最終答案」。** 用對了這個定位，LLM 就是純加速。

## LLM 危險在哪：五種會咬你的失效模式

現在講會咬人的部分。這些不是「偶爾的小錯」，是**結構性的、可預測的**失效模式——認識它們，你才知道每個 AI 輸出該用哪個工具去驗。

**1. 幻覺不存在的 API / 函式 / 參數。** 這是最致命的一種。LLM 會**流暢地編造**一個聽起來完全合理、但根本不存在的函式名、參數、旗標。它不是「查不到就說不知道」，它是「查不到就編一個像的」。例子：你問「redis 怎麼註冊一個命令的 handler」，它可能自信地告訴你有個 `registerCommand(name, proc, arity)` 函式——聽起來完美，但 redis 根本沒這個函式（命令是靠 JSON 表 + 程式碼生成註冊的）。你若照著這個幻覺去 grep，會浪費半天找一個不存在的東西。

**2. 對大 codebase 的全局無知。** LLM 的 context window 再大（現代模型如 Claude Opus 4.8 有到 1M token 的 context），也塞不下一個五十萬行的專案，而且它預設**看不到你的 codebase**——它只看到你貼給它的片段。所以它對「這個函式在**你這個專案**裡實際被誰呼叫、實際走哪條路徑、你們團隊的特殊 convention」一無所知。它給的是「一般而言 redis 這類專案大概怎樣」，不是「你手上這份 redis 7.4.0 的第 3884 行實際怎樣」。**全局性的問題（誰呼叫誰、data flow、實際控制流）它答不準，那是 cscope/gdb 的地盤。**

**3. 自信地說錯——沒有校準的不確定性。** 人類同事說錯時，語氣通常會透露猶豫（「我記得好像是……不確定」）。LLM **不會**——它對編造的幻覺和確鑿的事實用**完全相同的自信語氣**。這在認識論上極其危險：你無法從它的**語氣**判斷可信度。一段話裡對的和錯的混在一起，都用同樣篤定的口吻說出來。**永遠不要把 LLM 的自信當成正確性的訊號。**

**4. 版本混淆。** 它的訓練資料橫跨某個 API 的多個版本。它可能把 redis 6 的行為、redis 7 的行為、某個早已被移除的舊 API 混在一起講。你問的是 7.4.0，它給你的可能摻雜了 5.0 時代的 `redis.c`（那時檔案還沒改名成 `server.c`——Ch 17 我們挖過這段歷史）。**版本相關的細節（某個函式簽名、某個旗標是否存在、某個行為）最不可信。**

**5. 把註解/文件當事實。** LLM 傾向相信 code 裡的註解和 docstring。但 Ch 1–2 我們反覆強調：**註解會過期、會說謊、會描述早被重構掉的舊邏輯。** LLM 讀到一段誤導的註解，會忠實地把那個**錯的**理解傳達給你，還說得頭頭是道。它沒有「懷疑註解」的本能——那是你要補上的。

## 示範：LLM 說一件事，工具戳破/證實它

抽象講完了，來看具體的。這是 AI 輔助讀碼的**核心動作**——每一個 LLM 斷言，都對應一個驗證它的工具指令。以下情境改編自真實的「LLM 給了一個聽起來對的答案、我們用 rg/gdb 驗證」的過程（redis 上的事實是真跑 `rg` 查證的）。

**情境一：幻覺 API 被 rg 戳破。**

假設你問 LLM：「redis 裡註冊命令 handler 的函式叫什麼？」一個典型的、聽起來很合理的幻覺回答是：

> 「redis 用 `registerRedisCommand(name, proc, arity, flags)` 來註冊每個命令的處理函式。」

聽起來完美——命名符合慣例、參數合理。但這是**驗證動作**，不是接受動作。用 rg 查這個函式到底存不存在：

```
$ rg -n "registerRedisCommand" src/
（無輸出）
```

**零結果。這個函式不存在，是幻覺。** LLM 把「一般框架會有註冊函式」這個模式，編造成一個 redis 根本沒有的具體 API。真相是 redis 的命令表是由 `commands.def`（從 JSON 定義自動生成）填的——你用 rg 查真正存在的東西才找得到：

```
$ rg -n "int processCommand" src/server.c
3884:int processCommand(client *c) {
```

`processCommand`（第 3884 行，簽名 `int processCommand(client *c)`）是真的存在、真的是命令處理入口——這是 Ch 18 我們用 gdb 斷點親眼驗證過的。**LLM 給了你一個方向（「有個地方在處理命令」是對的），但它編的具體 API 是假的。你用 rg 花三秒就分辨了真假。**

**情境二：簽名幻覺被 rg 證實/修正。**

你問：「redis 的 `lookupKeyRead` 函式簽名長怎樣？」LLM 可能回答（憑訓練記憶，可能對可能摻了舊版）：

> 「`robj *lookupKeyRead(redisDb *db, robj *key, int flags)`——它接受一個 flags 參數控制查詢行為。」

這個**部分對、部分錯**——正是最危險的一類。用 rg 查真相：

```
$ rg -n "robj \*lookupKeyRead\b" src/db.c
145:robj *lookupKeyRead(redisDb *db, robj *key) {
```

真相是 `lookupKeyRead(redisDb *db, robj *key)`——**只有兩個參數，沒有 `flags`。** LLM 把它跟**另一個真實存在**的函式 `lookupKeyReadWithFlags(redisDb *db, robj *key, int flags)`（Ch 17 我們追過它的演化史）搞混了。這種混淆極其典型：兩個名字相近的函式，LLM 把簽名張冠李戴。如果你照著幻覺的三參數簽名去讀 call site，會處處對不上。**rg 一查，真相立現。**

**情境三：命名慣例——LLM 猜對，rg 證實。**

不是每次都被戳破。你問「redis 的事件迴圈主函式叫 `ae_main` 還是 `aeMain`？」LLM 答「redis 用 camelCase，所以是 `aeMain`」——這次它對了，rg 證實：

```
$ rg -n "void aeMain" src/ae.c
474:void aeMain(aeEventLoop *eventLoop) {
```

`aeMain` 確實存在（Ch 0/18 我們都遇過它）。**重點不是「LLM 對了」，而是「你不知道它這次對不對，所以你還是驗了」。** 驗證是廉價的（一條 rg），被幻覺誤導的代價是昂貴的（半天白工）。**廉價的驗證 vs 昂貴的錯誤——這個不對稱，就是「永遠驗證」的全部理由。**

這三個情境示範了同一個鐵律：**LLM 的每一個具體斷言（函式名、簽名、行為、呼叫關係），都是一個「待驗證的假設」，不是「已知的事實」。** 而驗證工具你早就有了——rg（Ch 12）驗存在性、cscope（Ch 14）驗呼叫關係、gdb（Ch 18）驗實際控制流、git（Ch 17）驗版本與歷史。**AI 沒有取代這些工具，它給了這些工具更多待驗證的輸入。**

## 正確工作流：把 LLM 接進 Ch 10 的假設驅動迴圈

現在把它系統化。Ch 10 的假設驅動讀碼迴圈是：**觀察 → 形成假設 → 設計驗證 → 執行驗證 → 修正**。LLM 插進來的位置很明確——它是**假設生成的渦輪增壓**，但迴圈的其餘部分（尤其驗證）**完全不變、且更重要**：

```
   ┌─────────────────────────────────────────────────┐
   │  1. 觀察陌生 code / 提出問題                       │
   └───────────────────┬─────────────────────────────┘
                       ▼
   ┌─────────────────────────────────────────────────┐
   │  2. 【LLM 加速】產生候選假設 / 解釋 / summary      │  ← AI 在這裡，且只在這裡當主力
   │     「這函式可能是 X」「這段像在做 Y」             │
   └───────────────────┬─────────────────────────────┘
                       ▼
   ┌─────────────────────────────────────────────────┐
   │  3. 【你 + 工具】驗證每一個 LLM 斷言               │  ← 這裡絕不能讓 AI 代勞
   │     rg 驗存在 / cscope 驗呼叫 / gdb 驗控制流 /     │
   │     git 驗版本 / 親自讀那幾行 source              │
   └───────────────────┬─────────────────────────────┘
                       ▼
   ┌─────────────────────────────────────────────────┐
   │  4. 接受驗證過的、丟棄被戳破的、修正部分對的       │
   └─────────────────────────────────────────────────┘
```

幾條把這個迴圈用好的鐵則：

- **餵它真實 context，別讓它憑空回憶。** 現代 agentic 讀碼工具（Claude Code 類）能真的讀你的檔案、跑 rg、跑 grep——這比「純聊天貼片段」可信得多，因為它的斷言是**基於你 codebase 的實際內容**，不是訓練記憶。但即便如此，它讀了之後的**推論**仍可能錯，仍要驗。「有沒有讀到真實 code」決定了幻覺的機率高低，但不改變「要驗證」的紀律。

- **把 LLM 的輸出當「搜尋查詢的種子」，不當答案。** 它說「可能有個 `registerCommand` 函式」——你不是接受它，你是**拿這個詞去 rg**。查到了，好；查不到,你剛剛零成本地排除了一個幻覺。LLM 幫你**生成要搜什麼**，工具幫你**確認搜到什麼**。

- **要求它給「可驗證的具體」，而非「模糊的正確」。** 問「這段 code 大概在幹嘛」得到的模糊解釋難驗證；問「這段 code 呼叫了哪些函式、改了哪個全域變數」得到的具體斷言**可以逐條 rg/gdb 驗**。逼它具體，你才驗得動。

- **交叉檢查高風險斷言。** 涉及版本、安全、並發、你要據以改 code 的關鍵結論——不要只信一次 LLM 輸出。用工具驗，必要時換個問法再問一次看它自己是否一致，最終**以工具的輸出為準，不以 LLM 的一致性為準**（它可能兩次都錯得一致）。

## 工具生態：從聊天到 agentic 讀碼

AI 輔助讀碼的形態正在快速演化，大致三代，各有適用場景：

- **純聊天貼片段（第一代）**：你手動複製 code 到對話框問。優點是快、無需設定；缺點是 LLM 完全看不到你 codebase 的其餘部分，幻覺率最高，全局問題基本沒戲。適合「解釋一小段孤立的陌生 code」。

- **RAG / embedding 檢索（第二代）**：把整個 codebase 切塊、算 embedding（向量表示）、存進向量資料庫；提問時先用語意檢索找出最相關的幾塊 code 餵給 LLM。這讓 LLM「看得到」大 codebase 的相關部分，比純聊天可信。但檢索本身可能漏掉關鍵片段（語意相似 ≠ 真正相關），且它看到的仍是**片段拼湊**，不是完整的呼叫圖。適合「在大 codebase 裡問語意問題」（「處理登入的邏輯在哪」）。

- **Agentic 讀碼工具（第三代，如 Claude Code、aider、Cursor 類）**：LLM 被賦予**工具**——它能自己跑 rg、grep、讀檔、甚至跑測試，然後基於**真實讀到的內容**回答。這是目前最強的形態，因為它的斷言有機會建立在「它剛剛真的 grep 到的東西」上，而非訓練記憶。它某種程度上**自己在做我們前面教的驗證**——但注意：(a) 它的**推論與綜合**仍可能出錯（讀對了 code，總結錯了意思）；(b) 它可能沒讀全就下結論；(c) 它一樣不會可靠地說「我不確定」。所以**你的驗證角色沒有消失，只是上移了**——從「驗證每個函式名」上移到「驗證它的整體結論與關鍵推論」。

不管哪一代，那條認識論的線都不變：**工具的角色是加速假設生成與初步檢索，人 + 可驗證工具的角色是確認真相。** 第三代把很多低階驗證自動化了，但**最終的「這個結論我信不信、敢不敢據以改 code」的判斷,仍在你身上。**

## 對比與取捨

| 面向 | LLM 輔助讀碼 | 傳統可驗證工具（rg/cscope/gdb/git） |
|---|---|---|
| 本質 | 機率性的、從訓練記憶生成「聽起來對」的內容 | 確定性的、輸出即事實 |
| 最擅長 | 解釋陌生片段、翻譯陌生語言、猜命名、生假設/summary | 找存在性、查呼叫關係、看實際控制流、查歷史 |
| 全局理解 | 弱（看不全大 codebase，靠片段/檢索） | 強（cscope/clangd 精確反查，gdb 看真實路徑） |
| 可信度 | 無校準——自信 ≠ 正確，會幻覺、混版本 | 高——輸出可重現、可驗證 |
| 速度 | 極快生成初稿 | 秒級精確查詢 |
| 正確用法 | **產假設、降冷啟動門檻** | **驗證假設、確認真相** |
| 致命誤用 | 把它的輸出當最終答案、照幻覺 API 去找 | （無——它們不會騙你） |

**一句話取捨**：LLM 和傳統工具**不是替代關係，是上下游關係**——LLM 在上游高速產出待驗證的假設，傳統工具在下游確認哪些是真的。跳過下游，你就是在拿幻覺當地基蓋房子。

## 踩雷集錦

1. **照著 LLM 幻覺的 API 去 grep，找一個不存在的東西找半天。**
   - 錯誤直覺：「LLM 說有 `registerCommand`，那一定有，是我沒找對地方。」
   - 正確認識：**先 rg 驗存在性**。零結果就是幻覺，立刻丟棄，別懷疑是自己找法不對。LLM 編造不存在的 API 是最常見、最耗時的坑。

2. **把 LLM 的自信語氣當成正確性訊號。**
   - 錯誤直覺：「它講得這麼篤定、這麼有條理,應該是對的。」
   - 正確認識：LLM 對幻覺和事實用**完全相同的自信口吻**。語氣零資訊量。唯一能判斷對錯的是**工具驗證**，不是它的篤定程度。

3. **問全局問題（誰呼叫誰、實際走哪條路徑），信 LLM 的答案。**
   - 錯誤直覺：「它讀過這麼多 code，應該知道這個函式被誰呼叫。」
   - 正確認識：全局呼叫關係是 **cscope/clangd/gdb 的地盤**,不是 LLM 的。它看不全你的 codebase,對「你這個專案實際」的呼叫圖是瞎猜。全局問題一律用交叉引用工具或動態 trace 驗。

4. **忽略版本，讓 LLM 把不同版本的行為混著講。**
   - 錯誤直覺：「redis 就是 redis，它講的應該通用。」
   - 正確認識：LLM 訓練資料橫跨多版本，會把 redis 5/6/7 的 API 混講（甚至用早已改名的 `redis.c`）。**明確告訴它版本、且版本相關的細節一律用 rg 對照你手上這份 source 驗證。**

5. **相信 LLM 對註解的複述。**
   - 錯誤直覺：「code 裡註解這樣寫,LLM 也這樣說,那就是對的。」
   - 正確認識：註解會過期說謊（Ch 1–2）。LLM 沒有懷疑註解的本能,會忠實傳達錯的理解。**把 LLM 對「意圖/為什麼」的說法當假設,用 git blame/commit message（Ch 17）驗真正的設計意圖。**

6. **用 agentic 工具就以為不用驗了。**
   - 錯誤直覺：「它自己會跑 rg、讀真檔,那它的結論一定基於事實。」
   - 正確認識：它讀對 code ≠ 綜合對意思;它可能沒讀全就下結論;它一樣不說「不確定」。**驗證角色上移了(從驗函式名到驗整體結論),沒有消失。** 越是要據以改 code 的關鍵結論,越要親自讀那幾行 source 確認。

## 進階：再往深一層

- **用 LLM 做「橡皮鴨」而非「答案機」**：與其問它「這段在幹嘛」,不如把**你的**理解講給它聽、要它挑戰。「我認為這個函式是命令分派入口,理由是 A、B、C——這個推理有漏洞嗎?」這種用法把它從「可能幻覺的答案來源」轉成「幫你檢查推理的對手」,更安全也更能深化你自己的理解(接 Ch 36 費曼測試)。

- **讓 agentic 工具生「驗證腳本」而非「結論」**:與其信它的結論,不如要它產出**你能自己跑的驗證動作**——「給我一條 rg 指令驗證你剛說的呼叫關係」「給我一個 gdb 腳本驗證這條路徑真的會走到」。把 AI 的產出從「要我信的結論」轉成「我能自己驗的動作」,認識論上安全得多。

- **RAG 的檢索盲區意識**:當你用 RAG/embedding 工具時,記得「它沒檢索到的 = 它當作不存在的」。語意檢索會漏掉命名不語意相關但邏輯關鍵的片段(例如一個叫 `x` 的關鍵全域變數)。**LLM 說「沒有處理 X 的地方」時,永遠再用 rg 全域搜一次**——它的「沒有」可能只是「沒檢索到」。

- **prompt 裡明確要求「不確定就說不確定」**:雖然 LLM 的不確定性校準不可靠,明確在提問時要求它「區分你確定的和你在推測的、不知道就說不知道、不要編造 API 名稱」,能顯著降低(但不消除)幻覺率。這是廉價的防護,值得養成習慣。

- **模型能力在變,認識論不變**:模型會越來越強、context 越來越大、幻覺率越來越低(現代前沿模型如 Claude Opus 4.8 已比早期模型可靠得多)。但**「機率性生成 vs 確定性驗證」的根本區別不會消失**。哪怕幻覺率降到 1%,你也不知道**這一次**是不是那 1%,所以驗證紀律永遠成立。別因為模型變強就放鬆驗證——那正是被咬的時刻。

## 動手練習

（可用任何 LLM/agentic 工具搭配 redis 沙包做。）

1. **抓一次幻覺**:問你的 LLM「redis 裡負責把命令名對應到 handler 的資料結構/函式叫什麼」,把它給的**具體名字**用 `rg` 查證。記錄它有沒有幻覺、你花幾秒戳破。

2. **簽名對照**:問 LLM 三個 redis 函式(如 `setKey`、`dbAdd`、`expireIfNeeded`)的簽名,全部用 `rg -n` 對照真實 source,標出哪些對、哪些摻了錯參數或舊版。

3. **全局問題交給對的工具**:問 LLM「`aeMain` 被誰呼叫」,再用 `cscope -d -L -3 aeMain`(Ch 14)查真相,比較兩者。體會「全局呼叫關係該問 cscope 不該問 LLM」。

4. **LLM 產假設 → gdb 驗**:讓 LLM 猜「一個 `GET` 命令會經過哪幾個函式」,把它的猜測當假設,用 Ch 18 的 gdb backtrace 驗證真實路徑,列出它猜對/漏掉/多講了哪些。

5. **橡皮鴨練習**:挑一段你已經(用工具)讀懂的 redis code,把你的理解講給 LLM 聽並要它挑戰,看它能不能指出你理解裡真實存在的盲點——同時警惕它挑的「毛病」本身也可能是幻覺,一樣要驗。

## 本章重點整理

- **LLM 是加速器,不是真相來源。** 它機率性地生成「聽起來對」的內容,自信 ≠ 正確。
- 它**擅長**:解釋陌生片段、翻譯陌生語言慣用法、猜命名意圖、生初步假設與 summary——都是「加速形成可驗證起點」。
- 它**危險**在五種結構性失效:幻覺不存在的 API、對大 codebase 全局無知、自信說錯(無校準)、版本混淆、把過期註解當事實。
- 核心工作流(承接 Ch 10):**LLM 產假設 → 你用工具(rg/cscope/gdb/git)驗證 → 只接受驗過的。** 每個 LLM 斷言都是待驗證的假設。
- 驗證是廉價的(一條 rg),被幻覺誤導是昂貴的(半天白工)——這個不對稱是「永遠驗證」的全部理由。
- 工具生態三代:純聊天(幻覺最高)→ RAG/embedding(看得到片段)→ agentic(自己跑工具讀真檔,最強但仍要驗**推論與結論**)。
- 模型會變強、幻覺率會降,但**機率性生成 vs 確定性驗證**的認識論區別永不消失,驗證紀律永遠成立。
