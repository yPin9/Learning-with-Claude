# Ch 4 — 三種閱讀模式：掃讀 / 精讀 / 追蹤

> **目標**：把上一章的認知機制落地成三種可操作的閱讀模式——**掃讀（skim）**建全局、**精讀（study）**吃透一段、**追蹤（trace）**跟一條路徑穿越模組。學會判斷什麼時候用哪種、怎麼在三種間切換，避開兩個致命錯誤：對整個 codebase 精讀（淹死）、只掃讀不精讀（永遠不懂細節）。三種模式各拿 redis 真跑一次。

## 先建立直覺：讀 code 不是只有一種「讀」

多數人讀 code 只有一檔速度——逐行、一樣的專注度、一樣的節奏，從上讀到下。這就像你看任何文件都用同一種讀法：讀電話簿、讀合約、讀小說都逐字啃。**荒謬，但這正是多數人讀 code 的樣子。**

熟練讀者有三種**變速箱**，對應三種目的：

```
              目的                     動作              速度   認知學對應(Ch 3)
 ┌──────────┬────────────────────┬──────────────────┬──────┬──────────────────┐
 │ 掃讀 skim │ 建全局印象、找地標 │ 快翻目錄/header/  │ 極快 │ 鋪 beacon、       │
 │          │ 不求懂細節         │ 型別/函式名       │      │ 搭 top-down 假設  │
 ├──────────┼────────────────────┼──────────────────┼──────┼──────────────────┤
 │ 精讀 study│ 吃透一小段關鍵code │ 逐行、查每個符號、│ 慢   │ bottom-up chunk   │
 │          │                    │ 必要時動態驗證    │      │ 一小塊            │
 ├──────────┼────────────────────┼──────────────────┼──────┼──────────────────┤
 │ 追蹤 trace│ 跟一條執行/資料路徑│ 沿呼叫/資料流跳   │ 中   │ 建 program model  │
 │          │ 穿越多個模組       │ 穿多個檔          │      │ (控制流/資料流)   │
 └──────────┴────────────────────┴────────────────────┴──────┴──────────────────┘
```

三者不是難度階梯（不是「先學掃讀再學精讀」），是**三把不同用途的工具**，一次攻堅裡你會反覆切換。這章教你各自怎麼用、以及最關鍵的——**怎麼判斷此刻該用哪把**。

## 掃讀（skim）：建地圖，不進房間

掃讀的目的是**建全局印象、標出地標**，明確**不求懂任何細節**。你在做的是 Ch 3 的 top-down 準備動作：快速鋪 beacon，好生成「這專案大概怎麼組織」的假設骨架。

掃讀看什麼、跳過什麼：

- **看**：目錄結構、檔名、header、主要 struct/型別、函式**名**（不是 body）、README、build 檔、明顯的字串。
- **跳過**：任何函式 body、任何演算法細節、任何你現在不懂的東西——**看不懂就跳，這是紀律不是偷懶**。掃讀時停下來鑽細節是最常見的失敗。

### 在 redis 上掃讀一次（真跑）

**第一眼——規模與組成**（`cloc`，真實輸出）：

```
$ cloc --quiet src/
Language          files      blank    comment       code
C                   115      15755      32001     100023
JSON                401          2          0      24565
```

三秒鐘你知道：十萬行 C 為主體、註解勤勞（1:3）、401 個 JSON（後面會發現是命令定義表）。**沒讀任何一行邏輯，已有規模感。**

**第二眼——header 當地圖**（真實輸出）：

```
$ ls src/*.h | head -15
src/adlist.h   src/ae.h      src/anet.h    src/atomicvar.h
src/bio.h      src/cluster.h src/config.h  src/connection.h ...
```

光看檔名就能猜出模組：`ae.h`（async event，事件迴圈）、`anet.h`（網路）、`cluster.h`（叢集）、`connection.h`（連線）。**檔名是最便宜的 beacon。**

**第三眼——主要型別**（真實輸出）：

```
$ rg -n "^typedef struct|^struct redisServer|^struct client" src/server.h | head
70:typedef struct redisObject robj;
968:typedef struct redisDb {
...
```

`redisObject`（值物件）、`redisDb`（一個資料庫）、`redisServer`、`client`——這幾個 struct 是整個系統的骨架名詞。認得它們，之後讀任何函式簽名 `robj *`、`client *c` 你都有 chunk 可打包。

掃完這三眼，你花不到十分鐘，就有了「redis 是十萬行 C、事件驅動、圍繞 redisObject/redisDb/client 這幾個型別、命令定義在 JSON 表」的**地圖**——足以支撐後面的 top-down 假設。**這就是掃讀的產出：地圖，不是理解。** Ch 5「60 分鐘偵察」把掃讀 SOP 化。

## 精讀（study）：進一個房間，把每寸看清

精讀是另一個極端：**對一小段關鍵 code 逐行吃透**。這是 Ch 3 的 bottom-up——沒有現成 chunk 時，老實逐行建。精讀慢、費工作記憶，所以**只用在真正關鍵、且值得的一小塊**（一個核心函式、一段你要改的邏輯、一處可疑的安全 sink）。

精讀的動作：

- 逐行讀，每個不認識的符號都查定義（jump-to-definition / `rg`）。
- 邊讀邊**外化**（Ch 3 實務啟示）：把每個變數的意義、每個分支的條件記在旁邊，別靠工作記憶硬撐。
- 不確定的地方**動態驗證**：靜態讀不出的（間接呼叫、實際走哪條）就 gdb 跑（Ch 18）。

### 在 redis 上精讀 `expireIfNeeded`（真跑）

假設你要改「key 過期」的行為，`expireIfNeeded`（`src/db.c:1974`）就是那塊值得精讀的關鍵 code。逐行吃它的開頭（真實輸出）：

```c
keyStatus expireIfNeeded(redisDb *db, robj *key, int flags) {
    if (server.lazy_expire_disabled) return KEY_VALID;   // 關閉惰性過期 → 一律當有效
    if (!keyIsExpired(db,key)) return KEY_VALID;          // 沒過期 → 有效（早退）
    ...
    if (server.masterhost != NULL) {                      // 我是 replica？
        if (server.current_client && (server.current_client->flags & CLIENT_MASTER))
            return KEY_VALID;                             // 指令來自 master → 別自己刪
        if (!(flags & EXPIRE_FORCE_DELETE_EXPIRED))
            return KEY_EXPIRED;                           // 標記過期但不刪
    }
    ...
    deleteExpiredKeyAndPropagate(db,key);                 // 真的刪 + 傳播 DEL
    return KEY_DELETED;
```

精讀時你**必須**搞清楚：`keyStatus` 三態（`KEY_VALID`/`KEY_EXPIRED`/`KEY_DELETED`）差在哪？`flags` 每個 bit（`EXPIRE_FORCE_DELETE_EXPIRED`）誰帶進來？為什麼 replica 分支存在（上一章講過：主從一致性）？這些你**逐一查、逐一記**。精讀完這一個函式，你對 redis 過期機制的 mental model 就扎實了——但代價是十幾分鐘只讀懂了一個函式。**這就是精讀的取捨：深，但貴。所以它只配得上關鍵的一小塊。**

> 關鍵紀律：**精讀前先問「這塊值得精讀嗎？」** 如果只是想知道它大概幹嘛（好繼續追別的），掃它的名字/註解就夠，別掉進逐行的黑洞。精讀是稀缺資源，花在刀口上。

## 追蹤（trace）：跟一條路徑穿越整個系統

追蹤是第三種，也是攻堅陌生 codebase 最常用的——**跟一條執行路徑或資料路徑，從起點穿過多個模組到終點**。它建的是 Ch 3 的 program model（「這件事怎麼一步步發生」）。追蹤既不像掃讀那樣不進細節，也不像精讀那樣鑽死一塊；它是**沿著一條線移動**，每站只讀「足以接到下一站」的程度。

### 在 redis 上追蹤「一個 GET 指令怎麼被處理」（真跑）

問題（帶著問題進場，Ch 1 信條）：**client 送 `GET foo`，redis 內部走哪條路徑？** 用 cscope/rg 一站站追（以下呼叫關係都在 WSL 上用 cscope 反查驗證過）：

```
main()                         server.c:6917   ← 入口（掃讀時已知）
  └─ aeMain(server.el)         server.c:7251   ← 事件迴圈
       └─ (事件觸發讀取、解析出 argv) ...
            └─ processCommand(c)          server.c:3884
                 └─ call(c, flags)        server.c:4206 → 3524
                      └─ c->cmd->proc(c)  server.c:3575   ← 函式指標派發(Ch 2!)
                           └─ getCommand(c)          t_string.c:316
                                └─ getGenericCommand(c)   t_string.c:302
                                     └─ lookupKeyReadOrReply(c, argv[1], ...)  db.c:163
                                          └─ lookupKeyRead(c->db, key)   db.c:145
                                               └─ lookupKeyReadWithFlags(...)  db.c:138
                                                    └─ lookupKey(db, key, flags)   db.c:75
                                                         └─ expireIfNeeded(...)   db.c:1974
```

追蹤這條線時你**沒有精讀任何一站**——`processCommand` 幾百行你只確認「它最終呼叫 `call`」；`call` 你只確認「它 `c->cmd->proc(c)`」。每站只讀「怎麼接到下一站」，其餘全跳。這樣你用中等速度，從入口一路穿到「GET 最終會觸發過期判斷」的全貌——**這是掃讀給不了（太淺）、精讀給不了（會卡死在第一個函式）的東西。**

追蹤怎麼站站接上？靠 cscope 反查（Ch 0 示範過的 `-3` 找呼叫者、`-2` 找被呼叫者），或 clangd 的 call hierarchy。真實的一站（`lookupKeyReadOrReply` 誰呼叫，真跑）：

```
$ cscope -d -L -3 lookupKeyReadOrReply
src/t_hash.c   hgetCommand   2274  ...lookupKeyReadOrReply(c,c->argv[1],...)
src/geo.c      geodistCommand 987  ...
...
```

你也能反過來追（往下：這函式呼叫誰）。追蹤的方向——往上找呼叫者、往下找被呼叫者——就是 Ch 8（data flow）和 Ch 9（control flow / call graph）的核心，這裡先建立手感。**注意這條鏈裡的 `c->cmd->proc(c)`——追蹤到這站，靜態會斷（函式指標，不知道進哪），正是上一章講的間接控制流；要嘛去讀命令表確認 GET → getCommand，要嘛 gdb 斷點動態看。追蹤最常在這種 indirection 處要動靜態結合。**

## 決策樹：此刻該用哪種模式？

三種模式的價值全在「用對時機」。一張決策樹（讀碼中隨時在心裡跑）：

```
                  我現在想知道什麼？
                          │
      ┌───────────────────┼────────────────────────┐
      ▼                   ▼                         ▼
「這專案/模組       「這一小段 code           「這件事(一個請求/
 大概怎麼組織?」     到底在幹嘛、             一筆資料)怎麼
 「有哪些地標?」     每個細節?」               一步步發生?」
      │                   │                         │
      ▼                   ▼                         ▼
   ┌──────┐           這段關鍵/值得嗎?          ┌──────┐
   │ 掃讀 │            ┌────┴────┐              │ 追蹤 │
   │ skim │            ▼         ▼              │trace │
   └──────┘         值得       不值得            └──────┘
   建地圖         ┌──────┐   掃它名字/註解         沿路徑跳，
   找 beacon      │ 精讀 │   就好，別鑽           每站只讀
                  │study │   (回追蹤/掃讀)        「接下一站」
                  └──────┘
                  逐行吃透+外化
                  +動態驗證
```

實戰裡一次攻堅長這樣（三種模式交織，對應 Ch 3 的 Letovsky 機會主義切換）：

1. **掃讀**整個專案建地圖（10 分鐘）→ 得到 top-down 假設。
2. 帶著具體問題**追蹤**一條關鍵路徑（GET 怎麼處理）→ 建 program model，中途在函式指標處**動態驗證**。
3. 追到那個「你要改/要懂的關鍵函式」（`expireIfNeeded`）→ 切**精讀**逐行吃透。
4. 精讀中發現新的子問題 → 可能再**追蹤**一條支線，或**掃讀**一個新模組補背景。
5. 循環，直到問題解決。

**沒有哪種模式是主角。攻堅 = 三種模式圍繞一個具體問題不斷切換。**

## 對比與取捨

| 維度 | 掃讀 skim | 精讀 study | 追蹤 trace |
|---|---|---|---|
| 目的 | 建全局地圖、找地標 | 吃透一小段細節 | 跟一條路徑穿越系統 |
| 速度 | 極快 | 慢 | 中 |
| 讀的範圍 | 廣但淺（名字/型別/結構） | 窄但深（一個函式/一段） | 沿一條線（多檔，每站淺） |
| 認知學對應 | 鋪 beacon、搭 top-down 假設 | bottom-up chunk 一塊 | 建 program model |
| 產出 | 架構印象、假設骨架 | 一塊扎實的 mental model | 一條路徑的完整因果 |
| 主要工具 | cloc、ls、rg 掃名字、看 header | jump-to-def、外化筆記、gdb | cscope 反查、call hierarchy、gdb |
| 失敗模式 | 停下來鑽細節（變成龜速精讀） | 對整個 codebase 精讀（淹死） | 每站都精讀（追不動） |
| 何時用 | 剛接觸、換新模組 | 鎖定了關鍵/要改的那塊 | 要懂「某事怎麼發生」 |

一句話取捨：**掃讀求廣、精讀求深、追蹤求連。三者用錯場景都會癱瘓——關鍵不是學會三種讀法，是學會此刻該切哪一種。**

## 踩雷集錦

1. **錯誤直覺**：「認真讀 = 從頭到尾精讀整個 codebase。」
   **正確認識**：對十萬行 codebase 精讀 = **淹死**。精讀一個函式就要十幾分鐘，十萬行你算算要多久，而且工作記憶早就爆了、讀到後面忘光前面。精讀是**稀缺資源**，只配得上你鎖定的關鍵一小塊。大範圍用掃讀+追蹤，精讀留給刀口。

2. **錯誤直覺**：「快速掃一遍我就懂這專案了。」
   **正確認識**：只掃讀 = **永遠停在表面**。掃讀給你地圖和地標，但地圖不是理解——你知道「有 `expireIfNeeded` 這函式」不代表你懂過期機制。細節必須靠精讀/追蹤補。掃讀是**開始**不是結束。

3. **錯誤直覺**：「掃讀時遇到看不懂的，停下來搞懂再繼續才踏實。」
   **正確認識**：掃讀時停下鑽細節，是掃讀最常見的失敗——你會在第一個看不懂的函式卡住，掃讀退化成龜速精讀，永遠掃不完、建不出地圖。**掃讀的紀律就是「看不懂就跳」**，標記起來，等地圖建好、確定它重要了，再回頭精讀它。

4. **錯誤直覺**：「追蹤一條路徑時，每經過一個函式都該讀懂它。」
   **正確認識**：追蹤時每站都精讀 = **追不動**，一條路徑十幾站，每站十分鐘你半天追一條線。追蹤時每站**只讀「怎麼接到下一站」**（它最終呼叫誰），其餘全跳。哪站真的關鍵，標記起來事後精讀。追蹤求「連」，不求每站都「深」。

5. **錯誤直覺**：「選好一種模式就一路讀到底最有效率。」
   **正確認識**：真實攻堅是三種模式**不斷切換**（掃讀建地圖 → 追蹤一條路 → 撞到關鍵切精讀 → 冒出子問題再追一條支線）。死守一種模式反而卡——這正是 Ch 3 Letovsky「機會主義切換」的實戰形態。判斷「此刻該切哪種」的能力，比任何單一模式都重要。

## 進階：再往深一層

- **模式切換的觸發訊號**：怎麼知道該切了？幾個實用訊號——掃讀時「同一個名字反覆出現、看來很核心」→ 標記，之後追蹤或精讀它；追蹤時「這站的邏輯我完全接不上下一站」→ 切精讀這一站；精讀時「這函式的行為取決於某個我不懂的子系統」→ 切掃讀那個子系統補背景。把切換訊號變成本能，是 Part 2 攻堅 SOP 的核心肌肉。

- **時間箱（time-boxing）強迫切換**：讀碼容易在精讀時無限下鑽（yak shaving）。給每種模式**設時限**——掃讀 15 分鐘、追一條路徑 30 分鐘、精讀一個函式 20 分鐘。時限到了強迫抬頭問「我離目標更近了嗎？該切模式嗎？」。這是 README 學習建議「計時」的實作，也是對抗「鑽進兔子洞出不來」最有效的紀律。

- **三種模式對應三種工具強項**：掃讀吃 ripgrep/cloc/ls（快、廣、文字級）；追蹤吃 cscope/clangd 的交叉引用（跟呼叫關係）；精讀吃 clangd 語意跳轉 + gdb 動態（要精準、要看實際值）。Part 3 整個工具鏈章節，某種程度就是「把每種模式配上最鋒利的武器」。你選模式，工具跟著模式選。

## 動手練習

1. **掃讀計時**：給自己 **10 分鐘**，只用 `cloc`、`ls src/*.h`、`rg` 掃函式名/型別，對 redis 的 `src/cluster*.c`（你大概不熟的子系統）建地圖。時間到，**憑記憶**寫下「這子系統大概有哪些模組、圍繞哪些型別」。全程紀律：**看不懂就跳，絕不停下鑽細節**。體會掃讀的速度與克制。

2. **精讀一個函式**：挑 `src/db.c` 的 `expireIfNeeded`，**逐行**精讀（`sed -n '1974,2035p' src/db.c`）。邊讀邊在紙上外化：三態 `keyStatus` 各代表什麼、`flags` 每個 bit 誰帶進來、每個 `return` 的條件。計時，感受「深但貴」——你花多久才真正吃透這一個函式？

3. **追蹤一條路徑**：帶著問題「`GET foo` 怎麼被處理」，從 `processCommand` 開始，用 cscope（`cscope -d -L -2 <func>` 找它呼叫誰）**一站站往下追**到 `expireIfNeeded`。每站只讀「怎麼接下一站」，別精讀。把你追出的呼叫鏈畫成圖，跟本章那張對照。追到 `c->cmd->proc(c)` 時，想想為什麼靜態在這裡會斷、你怎麼確定它進 `getCommand`。

4. **三模式一次攻堅**：綜合題。選一個你沒碰過的 redis 功能（如 `EXPIRE` 指令或 `SUBSCRIBE`），依決策樹：先掃讀定位相關檔 → 追蹤它的處理路徑 → 對最關鍵那個函式精讀。全程記錄你**切換模式的每個時刻與原因**。這份切換記錄，就是你攻堅 SOP 的雛形（Ch 38 會正式打造）。

## 本章重點整理

- 讀 code 有三種變速箱：**掃讀 skim**（建地圖、找地標、不求懂細節、極快）、**精讀 study**（逐行吃透一小塊、慢、費工作記憶）、**追蹤 trace**（沿一條路徑穿越多模組、中速、每站只讀接下一站）。
- 認知學對應（Ch 3）：掃讀鋪 beacon 搭 top-down 假設、精讀做 bottom-up chunking、追蹤建 program model。
- 兩個致命錯誤：**對整個 codebase 精讀 = 淹死**；**只掃讀不精讀/追蹤 = 永遠停在表面**。
- 掃讀的紀律是「看不懂就跳」；精讀的紀律是「先問這塊值不值得」；追蹤的紀律是「每站只讀接下一站，別精讀」。
- 真實攻堅 = 三種模式**圍繞一個具體問題不斷切換**（Letovsky 機會主義切換的實戰形態）；判斷「此刻該切哪種」比精通任一模式更重要。
- 追蹤常在 indirection（函式指標 `c->cmd->proc(c)`）處要動靜態結合——這是 Ch 2 的間接控制流在追蹤時的具體遭遇。

## 延伸閱讀

- **Diomidis Spinellis,《Code Reading: The Open Source Perspective》(Addison-Wesley, 2003), Ch 2「Basic Programming Elements」與全書導讀策略**
  - **讀哪裡**：看他如何示範「先掃大結構、再挑重點深入」，以及跟讀一段真實開源 code 的節奏。
  - **學到什麼**：把掃讀/精讀/追蹤的節奏用大量真實 code 示範出來，是本章三模式最好的實作範本。
  - **和本章關聯**：本章三模式的方法論母體，尤其掃讀與精讀的取捨。

- **Felienne Hermans,《The Programmer's Brain》(Manning, 2021), Ch 3–5**
  - **讀哪裡**：講「如何讀 code」的實作章——如何有效 chunk、如何用 beacon、如何處理不熟的 code。
  - **學到什麼**：把 Ch 3 的認知機制轉成「讀 code 時具體怎麼做」的技巧，正好補上本章三模式背後的「為什麼這樣讀有效」。
  - **和本章關聯**：三模式的認知學依據（掃讀=鋪 beacon、精讀=chunking），與本章互為表裡。

- **redis 原始碼：親手追一次 `processCommand → call → proc → getCommand` 這條線（redis 7.4.0, src/server.c + src/t_string.c + src/db.c）**
  - **讀哪裡**：用 cscope 反查，不必讀懂每個函式的 body，只求接出呼叫鏈。
  - **學到什麼**：把「追蹤」從概念變成手感——這是你之後每個陌生服務都要做的「跟一條請求路徑」的原型。
  - **和本章關聯**：本章追蹤示範的活體，也是 Ch 8/9（data flow / call graph）的預習。
