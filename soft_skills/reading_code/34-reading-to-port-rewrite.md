# Ch 34 — 為了移植/重寫而讀

> **目標**：學會為了「把 X 搬到別的平台」或「把 X 重寫成 Y 語言」而讀碼——這是讀碼的最高難度模式，因為你不只要懂 code **做了什麼**，還要反推它**承諾了什麼**（規格），再判斷哪些承諾是本質、哪些只是這個實作的偶然。讀完你有一套「讀 X → 萃取 spec → 重寫成 Y」的方法框架，並能認出移植時最常翻船的隱藏假設（endianness、word size、UB 依賴、隱含 timing）。

## 為什麼這是最難的讀碼模式？

前面所有章的讀碼都有一個共同的終點：**理解**。你讀懂了，任務就結束了。但移植/重寫不一樣——**理解只是起點**。你讀完之後還要產出一份「等價但不同」的實作。這逼出一個前面沒認真面對的問題：

> **「等價」到底指什麼？哪些行為必須一模一樣，哪些可以不一樣？**

這個問題的答案，就是這段 code 的**規格 (spec)**。而殘酷的現實是：**幾乎沒有專案的 spec 是寫下來的。** 唯一權威的 spec，就是那份 source 本身。所以移植/重寫的本質是一個逆向工程任務：

> **從實作反推出規格，判斷哪些是規格（必須保留）、哪些是實作偶然（可以拋棄），然後用新的材料重新實現規格。**

這比「讀懂」難一個量級，因為「讀懂」允許你對某些細節含糊——「這裡大概是在做邊界處理」就夠了。但重寫不允許：你含糊的每一個細節，都可能是一個你即將破壞的 spec。

## 先給直覺：實作是規格的「有損壓縮」再解壓

想像原作者腦中有一份清晰的規格（「這個函式接受一個字串，回傳它的 CRC64，遇到 NULL 回傳 0」）。他把這份規格**編碼**成 C code。但這個編碼過程是**有損**的，而且**加了雜訊**：

- **有損**：規格裡「為什麼這樣做」的意圖沒了，只剩「怎麼做」。
- **加雜訊**：為了讓 C code 能跑，他被迫做出一堆規格沒要求的決定——用哪種迴圈、變數叫什麼、記憶體怎麼配、在這台機器上剛好能用的某個 trick。

你讀 source，看到的是「規格 + 雜訊」的混合物。移植/重寫的核心技藝，就是**把雜訊濾掉，還原出乾淨的規格**。濾錯了會出兩種災難：

- **把雜訊當規格**：你忠實複製了一個實作偶然（例如某個只在小端序成立的假設），新平台上就爆炸。
- **把規格當雜訊**：你以為某個奇怪的邊界處理是多餘的，砍掉，結果那正是原作者血淚換來的 bugfix。

這一章就是教你怎麼分辨這兩者。

## 底層機制：什麼是「行為契約」

我們把「規格」講得更精確一點。一段 code 對外的**行為契約 (behavioral contract)** 由這幾個面向組成，逐項問，你就在萃取 spec：

| 契約面向 | 該問的問題 |
|---|---|
| **輸入定義域** | 合法輸入的範圍是什麼？NULL？空？負數？超大值？ |
| **輸出值域** | 回傳什麼？成功/失敗怎麼表達？錯誤碼還是 errno 還是拋例外？ |
| **前置條件 (precondition)** | 呼叫者必須先保證什麼？（例如「buf 至少 n 位元組」「必須先 init」） |
| **後置條件 (postcondition)** | 呼叫後保證什麼成立？（例如「回傳的指標非 NULL 且 owns 這塊記憶體」） |
| **副作用** | 改了哪些全域/傳入的東西？有沒有 I/O、鎖、系統呼叫？ |
| **不變式 (invariant)** | 執行前後有什麼一直成立？（例如「這棵樹永遠平衡」） |
| **錯誤語意** | 失敗時的狀態是什麼？回滾了嗎？部分完成嗎？ |
| **資源語意** | 誰負責釋放？記憶體所有權怎麼轉移？ |

**注意這張表裡沒有一項是「用哪種迴圈、變數叫什麼、內部怎麼配置記憶體」**——那些是實作偶然，不屬於契約。萃取 spec 就是把這張表填滿，同時**刻意忽略**沒進這張表的細節。

## 本質複雜度 vs 偶然複雜度

這是 Fred Brooks《No Silver Bullet》的經典區分，移植時是生死線：

- **本質複雜度 (essential complexity)**：問題本身固有的難度。CRC64 演算法的多項式除法、TCP 的擁塞控制狀態機、JSON 的巢狀結構解析——這些不管你用什麼語言、什麼平台，都躲不掉。**這是規格，必須完整搬過去。**
- **偶然複雜度 (accidental complexity)**：這個特定實作為了讓它跑起來而引入的、跟問題本身無關的複雜。手動的記憶體管理、為了繞過某編譯器 bug 的 workaround、為了在 1990 年代的機器上省 cache 而做的 bit-packing、某個只因為用 C 才需要的 `goto cleanup` 模式——**這些是雜訊，重寫時該用新語言/平台的慣用法取代，甚至直接消失。**

判斷法則：**問「如果我換一個語言/平台重新解這個問題，這個複雜度還會出現嗎？」** 會 → 本質；不會 → 偶然。

舉例：你在把一段 C 的 hash table 重寫成 Rust。

- 「用開放定址還是鏈結法解衝突」——這**可能**是本質（如果 spec 承諾了特定的迭代順序或最壞複雜度），也**可能**是偶然（如果外界只在乎「能存能取」）。**你得去讀呼叫端才能判斷**——這就是為什麼萃取 spec 不能只讀函式本身。
- 「手動 `malloc`/`free` 那套所有權管理」——幾乎肯定是偶然。Rust 的 ownership 會用完全不同的方式表達同一個資源語意。你要搬的是「所有權語意」（本質），不是「`free` 的呼叫位置」（偶然）。

## 移植的四大隱藏殺手

這四類假設在原平台上「剛好成立」，所以原作者根本沒寫下來，你讀 code 時也極容易滑過去。它們是移植 bug 的最大來源。

### 1. Endianness（位元組序）

原作者在 x86（小端）上開發，把一個 `uint32_t` 直接 `memcpy` 進磁碟或網路——這在小端機器上「就是能用」，但搬到大端機器（或反過來，你重寫的目標要跨端序）就資料錯亂。redis 這種要做持久化（RDB）與跨機複製的專案，把這件事處理得很明白，值得一看：

```c
/* src/endianconv.h（redis 7.4.0，真實檔案） */
/* variants of the function doing the actual conversion only if the target
 * host is big endian */
#if (BYTE_ORDER == LITTLE_ENDIAN)
#define memrev16ifbe(p) ((void)(0))     /* 小端：什麼都不做 */
...
#else
#define memrev16ifbe(p) memrev16(p)     /* 大端：真的翻轉位元組 */
...
#endif
```

`ifbe` = "if big endian"。redis 選定 RDB 檔案格式是**小端**，所以在小端主機上讀寫是 no-op，在大端主機上才反轉。**移植時的教訓**：如果你在讀一段「把整數直接寫進 buffer / 檔案 / socket」的 code，第一個要問的就是「它假設了哪種位元組序？spec 要求哪種？」。原作者若像 redis 這樣把假設**顯式**寫出來，你很幸運；更多專案是**隱式**依賴，你得自己嗅出來——看到 `memcpy(&x, buf, 4)` 或 `*(uint32_t*)ptr` 這種「把 raw bytes 當整數」的地方就要警覺。

### 2. Word size / 型別寬度

`int` 是 16、32 還是 64 位？`long` 在 LP64（Linux 64-bit）是 8 位元組，在 LLP64（Windows 64-bit）是 4 位元組。`size_t`、指標寬度隨平台變。原作者若寫了 `int len = strlen(s)`，在他 64 位機器上 `strlen` 回傳 `size_t`（8 位元組）被截成 `int`（4 位元組）——只要字串不超過 2GB 就「剛好沒事」。你移植到一個 `int` 是 16 位的嵌入式平台，或處理超大輸入時，這個隱式截斷就是 bug。**萃取 spec 時要問**：這個變數的「規格寬度」是什麼？作者用 `int` 是因為 spec 真的只需要 32 位，還是只是圖方便？

### 3. 對 UB（未定義行為）的隱性依賴

原 code 可能踩在 UB 上卻「一直沒事」，因為原編譯器/平台剛好給了它想要的行為：有號整數溢位、`memcpy` 重疊區、讀未初始化記憶體、嚴格別名（strict aliasing）違規、shift 超過型別寬度。這些在原環境「能跑」，換編譯器/開最佳化/換架構就變。**這是最陰險的一類**，因為 code 看起來完全正常，只有跑起來（換平台跑）才現形。移植前用 `-fsanitize=undefined`（UBSan）跑一遍原 code 的測試，是揪出這類隱性依賴的實用手段——UBSan 會在執行到 UB 時當場報告位置。

### 4. 隱含的 timing / 並發假設

原 code 可能默默假設「這兩個操作之間沒有別的 thread 介入」「這個 callback 一定在同一個 thread 跑」「這個硬體暫存器讀寫有特定延遲」。這些假設在原平台的執行模型下成立，換到不同的排程器、不同的記憶體模型（例如從 x86 的 strong memory ordering 搬到 ARM 的 weak ordering）就崩。**萃取 spec 時要問**：這段 code 的正確性依賴哪些「沒被鎖保護、但剛好沒事」的順序？x86 上一堆缺 memory barrier 的 lock-free code 搬到 ARM 會壞，正是這個原因。

## 「讀 X → 重寫成 Y」的方法框架

把上面的觀念串成一個可操作的流程。假設任務是「把一個 C 模組重寫成 Rust」（或任何 X→Y）：

**Step 1 — 圈定邊界，找出對外介面。**
先不管內部。這個模組對外 export 哪些函式/型別？誰呼叫它、它呼叫誰（用 cscope/clangd 反查，Ch 13/14）？**契約只存在於邊界上**——內部怎麼實作是你要拋棄重寫的，只有邊界的行為是你必須保留的。畫出這個介面清單，就是你 spec 的骨架。

**Step 2 — 對每個介面函式，填「行為契約」表。**
拿上面那張八行的契約表，逐一填。輸入定義域、輸出值域、前後置條件、副作用、錯誤語意、資源語意。**這一步就是萃取 spec 的主體。** 填的過程中，你會被迫去讀每個邊界情況的處理——那些 `if (x == NULL) return -1`、那些 `goto err`，正是契約的「錯誤語意」與「輸入定義域」的證據。

**Step 3 — 用既有測試當 spec 的第二來源。**
source 是 spec 的權威來源，但**測試是 spec 的「可執行版本」**，而且往往更誠實——測試明白寫出「輸入 A 應該得到輸出 B」。把原專案的測試讀一遍（甚至跑一遍），你會得到一堆免費的、具體的契約斷言。更強的做法：**把原測試也移植到 Y，讓它們變成你新實作的驗收標準**。原測試通過 = 你至少沒破壞被測到的那部分 spec。（警告：測試覆蓋不到的 spec 仍可能被你破壞，見踩雷。）

**Step 4 — 分離本質 vs 偶然，決定「照搬」還是「重寫」。**
對內部每一塊複雜度，用前面的「換語言還會出現嗎」法則分類。本質複雜度（演算法、狀態機、格式定義）→ 忠實搬，甚至逐行對照。偶然複雜度（記憶體管理、C 特有的 idiom、workaround）→ 用 Y 的慣用法重新表達，別逐行翻譯。**逐行翻譯偶然複雜度是重寫最大的反模式**——你會得到一份「用 Rust 寫的 C」，既沒 C 的簡單也沒 Rust 的安全。

**Step 5 — 盤點四大隱藏殺手。**
專門過一遍：這段 code 有沒有 endianness 假設？型別寬度假設？UB 依賴（UBSan 跑一遍）？timing/並發假設？每一項都要在 spec 裡顯式標註「原假設 = X，我的目標平台 = Y，需不需要處理」。

**Step 6 — 增量重寫 + 差分測試（differential testing）。**
不要一次重寫完再測。理想做法：讓新舊實作**並存**，同一批輸入餵給兩者，比對輸出是否一致（differential / back-to-back testing）。redis、SQLite、壓縮庫的移植都愛用這招——它把「我的重寫正確嗎」變成一個可以跑一百萬組隨機輸入來逼近的問題，遠比人腦 review 可靠。

## 真跑：對 redis `crc64` 萃取一份 spec

把方法框架套一次到真實 code。目標是 redis 的 `crc64`，它對外只有兩個函式（`src/crc64.h`，真實檔案）：

```c
void crc64_init(void);
uint64_t crc64(uint64_t crc, const unsigned char *s, uint64_t l);
```

**Step 1 圈邊界**：對外介面就這兩個。`crc64_init` 建查表、`crc64` 算校驗和。內部那張 `static uint64_t crc64_table[8][256]`（8-slice 演算法的查找表）是實作細節，重寫時不必照搬結構——那是「怎麼算快」的偶然，不是「算什麼」的本質。

**Step 2 填契約表**（讀 `src/crc64.c` 主體推出）：

| 契約面向 | `crc64(crc, s, l)` 的答案 |
|---|---|
| 輸入定義域 | `crc`：起始值（串接多段時傳上一段結果，首段傳 0）；`s`：指向 `l` 個位元組；`l`：長度，可為 0 |
| 輸出值域 | 一個 `uint64_t` CRC；`l==0` 時原樣回傳 `crc`（單位元） |
| 前置條件 | 呼叫前必須先 `crc64_init()`（否則查表全 0，結果錯）；`s` 至少可讀 `l` 位元組 |
| 後置條件 | 純函式：相同 `(crc,s,l)` 永遠給相同結果 |
| 副作用 | **無**（`crc64_init` 有：寫全域查表；`crc64` 本身無） |
| 錯誤語意 | 沒有錯誤回傳——它不驗證輸入，`s` 給爛指標就 UB |
| 資源語意 | 不配置、不釋放任何記憶體 |
| 不變式 | 用的多項式固定為 `POLY = 0xad93d23594c935a9`（reflected 變體，見 `crc64.c` 開頭註解的參數表）——**這是本質，必須位元對位元一致，否則跟既有 RDB/資料不相容** |

**Step 3 測試當第二來源**：`crc64.c` 底部的 `crc64Test` 直接寫死了「輸入 `"123456789"` → 應得 `e9c6d914c4b8d9ca`」這種 golden vector。這一行測試比你讀十遍演算法更能釘死 spec——**你的 Rust 重寫只要對同一輸入吐同一個值，本質就對了**。

**Step 4 分本質/偶然**：多項式與位元反射規則 = 本質（換語言照樣要）；`[8][256]` 8-slice 查表、`crc64_init` 那套預算表 = 偶然（那是為了 CPU 快取效率的優化，Rust 版可以用更簡單的單表甚至 crate，只要輸出一致）。**逐行翻譯那張 8-slice 查表是反模式**——你會搬來一坨看不懂的優化，卻沒搬到「它算的是哪個 CRC 變體」這個真正重要的事。

**Step 5 盤點隱藏殺手**：CRC 對位元組序**不敏感**（逐位元組處理），所以 endianness 這關過；但 `l` 是 `uint64_t`，你若重寫成一個 `l` 只有 32 位的語言/平台要小心大輸入截斷。UB 面：`s` 為 NULL 且 `l>0` 是 UB，spec 沒承諾防呆，重寫時要決定「照抄這個不防呆，還是加防禦」——這是一個你要**顯式記錄**的偏離點。

十分鐘，你就有了一份「不看原 code 也能照著重寫、且能被 golden vector 驗證」的 spec。這比「我讀懂 crc64 了」扎實一個量級。

## 對比與取捨

| 策略 | 何時用 | 優點 | 風險 |
|---|---|---|---|
| **逐行直譯（transliteration）** | 演算法密集、本質複雜度高的核心（如 CRC、加密） | 最不容易改錯語意 | 把偶然複雜度也搬過來；不 idiomatic |
| **重寫（rewrite from spec）** | 偶然複雜度多、原 code 爛、或換範式（過程式→函數式） | 產出乾淨、符合 Y 慣用法 | 容易漏掉沒寫進 spec 的隱藏契約 |
| **包裝（wrap / FFI）** | 原 code 太複雜、暫時不想重寫 | 快、零 spec 風險 | 沒真的移植，扛著原依賴；跨語言邊界成本 |
| **差分並存過渡** | 高風險核心、不能出錯 | 可用海量輸入驗證等價 | 要維護兩份、比對基礎設施成本 |

**實戰建議**：一個模組裡通常**混用**——本質核心逐行直譯確保語意，外圍膠水碼重寫成 idiomatic，整體用差分測試兜底。不要對整個模組套單一策略。

另一個核心取捨：**「忠實」vs「改進」**。重寫時你會不斷看到原 code 的缺陷，手癢想順便修。要克制——**在你能證明新舊等價之前，任何「改進」都會污染你的差分測試基準**，讓你分不清「輸出不同是因為我修了 bug，還是我引入了 bug」。正確順序：先做到 bug-for-bug 等價（連原 bug 都複製），差分測試綠燈，**之後**再一個一個刻意地修，每修一個記錄一次「這裡我故意偏離原行為，因為……」。

## 反模式現場：「用 Rust 寫的 C」長什麼樣

Step 4 反覆警告「別逐行翻譯偶然複雜度」，這裡給你一個具體的對照，讓你認得出這個反模式。假設原 C 有一段典型的 `goto cleanup` 資源管理：

```c
/* 原 C：goto cleanup 是 C 的偶然複雜度（因為 C 沒有 RAII/析構） */
int do_work(const char *path) {
    int ret = -1;
    FILE *f = fopen(path, "r");
    if (!f) goto out;
    char *buf = malloc(SIZE);
    if (!buf) goto close_f;
    if (read_into(f, buf) < 0) goto free_buf;
    ret = process(buf);
free_buf:  free(buf);
close_f:   fclose(f);
out:       return ret;
}
```

**逐行直譯版（反模式，「用 Rust 寫的 C」）**——手動模擬 goto、手動 free、到處 `unsafe`，既沒 C 的簡潔也丟了 Rust 的安全：

```rust
// 反模式：把 C 的資源管理慣用法硬搬過來
fn do_work(path: &str) -> i32 {
    let mut ret = -1;
    let f = unsafe { libc_fopen(path) };        // 硬搬 FILE*
    if f.is_null() { return ret; }
    let buf = unsafe { libc_malloc(SIZE) };     // 硬搬 malloc
    // ... 手動 free、手動 goto 模擬 ...          // 把 C 的痛苦原封不動搬來
}
```

**萃取 spec 後的重寫版（正確）**——`do_work` 的**契約**是「讀 path 的內容、處理、回傳結果碼，過程中不洩漏資源」。`goto cleanup` 只是 C 為了實現「不洩漏資源」這個契約的偶然手段。Rust 有 RAII，同一個契約用慣用法一行就達成：

```rust
fn do_work(path: &str) -> Result<Output, Error> {
    let mut f = File::open(path)?;              // ? 傳播錯誤，取代 goto out
    let mut buf = Vec::with_capacity(SIZE);     // 離開 scope 自動釋放，取代 free
    f.read_to_end(&mut buf)?;                    // 取代 goto free_buf
    process(&buf)                                // 資源在此自動清理
}
```

**看出差別**：本質（讀檔→處理→回傳、不洩漏資源）兩版都在；但偶然（`goto` 標籤、手動 `free`、錯誤碼 `-1`）在正確版裡**消失了**，被 Rust 的 `?`/RAII/`Result` 取代。你搬的是契約，不是 `free` 的呼叫位置。認得出這個差別，你的重寫才會是 idiomatic Y，而不是穿著 Y 皮的 X。

## 踩雷集錦

1. **錯誤直覺：「測試通過就代表移植對了。」** 正確認識：測試只覆蓋 spec 的一部分，**沒被測到的契約你照樣會破壞**。原 code 可能有一個「NULL 輸入回傳 0」的行為從來沒被測，你重寫成「NULL 輸入 crash」，測試全綠但 spec 破了。測試是 spec 的下界，不是全部。要補：讀 code 找出測試沒覆蓋的邊界，手動加進 spec。

2. **錯誤直覺：「這段 code 一直在生產跑，所以它是對的，照搬就好。」** 正確認識：「一直沒出事」不等於「沒 UB / 沒平台假設」。它可能踩在 UB 上，只是原編譯器/平台縱容了它。照搬到新平台，縱容消失，bug 現形。移植前務必 UBSan/ASan 跑原 code，把「隱性依賴」顯性化。

3. **錯誤直覺：「重寫就是把每一行翻譯成新語言。」** 正確認識：逐行翻譯是把偶然複雜度也一起搬過來的反模式，產出「用 Y 寫的 X」。本質複雜度才逐行對照；偶然複雜度要用 Y 的慣用法重新表達。分不清兩者，你的重寫既不安全也不好維護。

4. **錯誤直覺：「這個奇怪的邊界檢查看起來多餘，砍掉讓 code 乾淨點。」** 正確認識：陌生 code 裡「看起來多餘」的檢查，極高比例是原作者用線上事故換來的 bugfix。動它之前先 `git blame`/`git log`（Ch 17）查它的來歷——commit message 常直接告訴你「這是為了修 issue #XXXX」。把 bugfix 當雜訊砍掉是移植經典翻車。

5. **錯誤直覺：「我懂這個函式做什麼了，可以開始重寫了。」** 正確認識：你懂「它做什麼」，不代表你懂「它承諾什麼」。前者是實作，後者是契約。你要重建的是契約。沒填完那張八行契約表就動手，你會在「錯誤語意」「資源所有權」這種不讀 code 主體、只看快樂路徑會漏掉的地方翻船。

6. **錯誤直覺：「並發/順序的東西在我機器上跑對了就對了。」** 正確認識：x86 的強記憶體序會「幫你補上」很多你漏掉的 barrier。同一段 lock-free code 搬到 ARM/RISC-V 的弱序模型會壞。移植並發 code，記憶體序假設要當一等公民顯式盤點，不能靠「在我機器上跑對了」。

## 進階：再往深一層

- **形式化你的 spec**：對關鍵函式，把萃取出的契約寫成前後置條件斷言（甚至用 property-based testing 框架如 Hypothesis / QuickCheck 表達成性質）。這逼你把模糊的「大概是這樣」變成機器可驗的命題，並且直接變成差分測試的 oracle。
- **從 spec 反查原 code 的 bug**：萃取 spec 的過程常會發現「這裡的行為根本不自洽」——原 code 兩條路徑對同一輸入給不同結果。這是原 code 的 bug。移植是難得的深度 code review，你會比原作者更懂某些角落。記錄下來，回報上游（接 open_source 課的貢獻流程）。
- **移植是最好的 spec 文件產生器**：一個沒文件的專案，「有人認真移植過它」往往就順帶產出了它史上第一份 spec。如果你的移植筆記夠好，它本身就是對原專案的重大貢獻——把契約表整理成文件回饋上游。
- **編譯器/平台差異的深水區**：strict aliasing、`-ffast-math` 下的浮點不可再現、`volatile` 的語意在不同平台的落差、struct padding/alignment 的 ABI 差異——這些在跨平台移植（尤其涉及序列化 struct、硬體暫存器映射）時會咬人。移植嵌入式或 kernel code 時，這是必修的一層，接你的 arm / c_interview / mtk_firmware 課會深挖。

## 動手練習

1. **對 redis `crc64.c` 萃取 spec**：讀 `src/crc64.c`（一個相對獨立、本質複雜度高的模組），填完本章那張八行「行為契約」表：`crc64()` 的輸入定義域、輸出、前後置條件、副作用。特別注意它有沒有 endianness 或型別寬度假設。目標：產出一份「不看 code 也能照著重寫成 Rust」的 spec。
2. **分本質 vs 偶然**：對 `crc64.c` 裡每一塊，標記「本質」還是「偶然」，並對每個「偶然」寫一句「如果重寫成 Rust，這塊會變成什麼/消失嗎」。
3. **抓隱藏殺手**：在 redis `src/rdb.c` 裡用 `rg -n "memrev|intrev|ifbe"` 找出所有處理位元組序的地方，挑一處，說明「若沒有這行、在大端機器上會發生什麼」。體會顯式的 endianness 處理長什麼樣。
4. **UBSan 揪隱性依賴**：寫一個小 C 檔，故意放一個「在你機器上剛好沒事」的有號整數溢位或 shift 過寬，用 `gcc -fsanitize=undefined` 編譯執行，看 UBSan 怎麼在執行時報告 UB 位置。體會「移植前跑 UBSan」為什麼能救你。
5. **（選）差分測試骨架**：挑一個小函式（如某個字串 hash），用 Python 快速重寫一版，然後寫個 loop 餵一萬組隨機輸入給「C 版（用 ctypes/子行程呼叫）」和「Python 版」，比對輸出。體會差分測試怎麼把「等價嗎」變成可自動逼近的問題。

## 本章重點整理

- 移植/重寫的本質是逆向工程：從實作反推規格，分辨本質複雜度（必留）與偶然複雜度（可拋）。
- 實作是規格的「有損壓縮 + 加雜訊」；讀碼的技藝是濾掉雜訊、還原乾淨的契約。
- 行為契約八面向：輸入定義域、輸出值域、前置/後置條件、副作用、不變式、錯誤語意、資源語意——填滿它就是萃取 spec。
- 本質 vs 偶然的判準：「換語言/平台重解，這複雜度還會出現嗎？」會→本質，不會→偶然。
- 四大隱藏殺手：endianness、word size/型別寬度、UB 依賴、timing/並發假設——原平台「剛好成立」所以沒寫下來，是移植 bug 最大來源。
- 方法框架六步：圈邊界找介面 → 填契約表 → 測試當第二 spec 來源 → 分本質/偶然 → 盤點隱藏殺手 → 增量重寫 + 差分測試。
- 先做到 bug-for-bug 等價再談改進；逐行直譯偶然複雜度是最大反模式。

## 延伸閱讀

- **Fred Brooks, "No Silver Bullet — Essence and Accident in Software Engineering"（1986）**
  - **讀哪裡**："Does It Have to Be Hard? — Essential Difficulties" 一節。原文不長，讀那段對 essence/accident 的定義。
  - **學到什麼**：本章「本質 vs 偶然複雜度」的思想源頭。Brooks 的原始論證比任何轉述都清晰，讀完你對「哪些複雜度是問題固有的、哪些是我們自找的」會有牢固的判準。
  - **前提**：無，經典短文。

- **[C FAQ / comp.lang.c — Portability 相關條目](https://c-faq.com/)**
  - **讀哪裡**：搜 "byte order"、"alignment"、"sizeof"、"integer overflow" 相關問答。
  - **學到什麼**：C 語言裡所有「在我機器上剛好能用」的可攜性陷阱的系統整理——endianness、對齊、型別寬度、整數提升規則。移植 C code 前把這幾類掃一遍，能預防大半的翻車。
  - **前提**：C 基礎。

- **[LLVM/Clang UndefinedBehaviorSanitizer 文件](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)**
  - **讀哪裡**："Available checks" 那張表，看它能抓哪些 UB。
  - **學到什麼**：移植前「把隱性 UB 依賴顯性化」的最實用工具。這張表本身就是一份「原 code 可能踩了、換平台會爆的 UB 清單」，對照著讀原 code 特別有收穫。
  - **前提**：懂什麼是 UB（有號溢位、越界、strict aliasing）。搭配你的 c_interview 課的 UB 章。
