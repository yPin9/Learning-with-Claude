# Ch 36 — 費曼測試

> **目標**：給你一把最誠實的尺，量「你到底是真懂還是自以為懂」。核心命題：**能把一段 code 教會別人，才算真的讀懂了它。** 這章把「讀懂」從一個模糊的主觀感覺，變成一個可驗證的產出。你會學到費曼技巧的四步、怎麼刻意找出「講不清楚的地方」（那就是你沒懂的洞），以及一套把理解逼到現形的檢查法。這章收束 Part 5 的「內化」主題——外化（Ch 35）把理解倒出來，費曼測試檢查倒出來的是不是真貨。

## 為什麼「感覺懂了」極度不可靠

先講一個你一定中過招的經驗：**你讀完一段 code，點頭「嗯，懂了」。隔天有人問你「那這裡為什麼要先檢查 A 再檢查 B？」你張口結舌。** 你昨天那個「懂了」是假的。

這不是你的問題，是人腦的系統性 bug，認知科學給它取了名字——**「解釋深度的錯覺」(Illusion of Explanatory Depth, IOED)**，由 Rozenblit 與 Keil 在 2002 年提出。他們的實驗經典而殘酷：請人評估自己對「拉鍊如何運作」「馬桶如何運作」的理解程度（1–7 分），大多數人給自己打高分；接著請他們**寫出詳細的運作機制**；寫完再重新評分——**分數普遍暴跌**。人們「以為自己懂」，直到被要求**詳細解釋**時才發現滿是漏洞。

關鍵在那句：**「直到被要求詳細解釋時」。** 熟悉感（我看過這段 code、每個字都認得）被大腦誤判成理解（我知道它為什麼這樣運作）。而戳破這個錯覺的唯一可靠手段，就是**強迫自己輸出一個完整、連貫、經得起追問的解釋**。這就是費曼測試的全部立論：

> **理解是「能生成解釋」，不是「能認得內容」。而檢驗前者的方法，是真的去生成那個解釋——最好是解釋給一個會追問的對象聽。**

## 這有科學背書：self-explanation effect

費曼測試不只是「聽起來有道理」，它有直接的實證支持。Chi 等人 1989 年在 *Cognitive Science* 的經典研究（"Self-Explanations: How Students Study and Use Examples in Learning to Solve Problems"）發現：學生從範例學習時，**學得好的人和學得差的人，差別不在智力，而在「自我解釋」的量**——好學生研讀同一個範例時，自發產生的解釋陳述遠多於差學生（研究中好學生平均產出 52 條 idea statements，差學生只有 18 條），而且他們的解釋不斷在「這一步為什麼要這樣做」上打轉，並回頭連結到背後的原理。

這個「自我解釋效應 (self-explanation effect)」對讀碼的啟示直接：**主動對自己解釋每一步的理由，會逼出比被動閱讀深得多的理解。** 被動讀 code 時你的大腦在「識別」；主動解釋時你的大腦在「重建因果」。後者才是理解。費曼測試就是把 self-explanation 從「順便做做」升級成「刻意的驗收關卡」。

## 底層機制：解釋為什麼能戳破錯覺

解釋這個動作之所以有效，是因為它強迫你的理解通過三道它平常能繞過的關卡：

1. **連貫性關卡**：講一個故事必須首尾相連。你腦中的理解可能是一堆孤島（「這裡在配記憶體」「那裡在檢查 flag」），彼此沒接起來你也沒察覺。一旦要**連著講**，島與島之間的斷橋立刻現形——你會卡在「然後……呃……這裡怎麼接到那裡的？」。**那個卡住的接縫，就是你沒懂的地方。**

2. **因果關卡**：解釋不能只說「做了什麼」（What），必須說「為什麼」（Why）。「這裡呼叫 `freeClientAsync`」是複述；「這裡用 async 版是因為此刻正在遍歷 client list，直接 free 會讓迭代器失效」才是理解。IOED 的錯覺幾乎全長在 What/Why 的縫隙裡——你以為懂了 Why，其實只記得 What。

3. **受眾關卡**：教一個**外行**（或一隻鴨子）時，你不能用行話搪塞。「這裡做了 epoll 的 event loop」對懂的人是解釋，對外行是咒語。被迫用大白話重講，你會發現很多你以為懂的術語，你只會念不會拆——**能不能不用術語重講，是理解的試金石**。

費曼測試就是刻意去撞這三道關卡，讓它們替你標出理解的洞。

## 費曼技巧的四步（讀碼版）

費曼技巧原本是學習法，套到讀碼上是這樣：

**Step 1 — 選定目標，假裝要教會一個外行。**
挑一段你「覺得懂了」的 code（一個函式、一條路徑、一個機制）。設定受眾：一個聰明但完全不懂這個 codebase、甚至不太懂這個領域的人。可以是真人（同事、rubber duck），也可以是想像的。

**Step 2 — 用大白話從頭講一遍，全程不許看 code。**
關鍵是**不看 code**（或至少不逐行照念）。憑你腦中的理解，把「這段 code 在幹嘛、為什麼這樣幹、輸入怎麼變成輸出」講成一個連貫的故事。用最白的話，術語出現就要當場拆解。**寫下來或講出聲**——在腦中默想會自動跳過卡住的地方，必須外化成語言（呼應 Ch 35）。

**Step 3 — 標記每一個卡住 / 含糊 / 只能用術語搪塞的地方。**
這是整個技巧的核心。你講到某處「呃……這裡大概是……反正就是會處理掉」——**停。那個「大概」「反正」就是一個洞。** 誠實地標記它，別滑過去。講到一個術語你只會念不會拆——標記。講到兩步之間接不起來——標記。**這些標記就是你的「沒懂清單」，比任何自評分數都準。**

**Step 4 — 帶著沒懂清單回去讀 code，補洞，重講。**
針對每個標記，回到 code（和你 Ch 35 的筆記）把它搞清楚，然後**重新完整講一遍**。反覆直到你能一口氣、不卡、不靠術語、不看 code 講完。能做到，你才真的懂了。

這個循環的美妙之處：**它自己會告訴你「還差多少」。** 你不必猜「我懂了嗎」，你的解釋裡還剩幾個「大概」「反正」，就是你還差幾個洞。

## 五種費曼測試的具體形式

同一個原理，五種可操作的形式，依場合選用：

| 形式 | 怎麼做 | 最適合抓什麼洞 |
|---|---|---|
| **用自己的話重述** | 不看 code，白話講一遍這段在幹嘛、為什麼 | 連貫性斷裂、What/Why 混淆 |
| **畫給別人看** | 對著一個人邊畫圖邊講（接 Ch 35 的圖） | 結構與關係的洞——畫不出的箭頭就是洞 |
| **寫一頁 summary** | 逼自己用一頁 A4 寫完這個模組的完整解釋 | 「以為懂全貌其實只懂片段」；一頁塞不下代表你沒抓到主幹 |
| **rubber duck** | 對著橡皮鴨/任何無生命物，出聲逐步解釋 | 獨自作業時的自我解釋，出聲比默想更能暴露卡點 |
| **刻意找「講不清楚的地方」** | 主動掃自己的解釋，獵捕每個含糊詞 | 上面四種的元技巧——把 IOED 的錯覺當獵物 |

**rubber duck debugging** 值得多說一句：它的原理正是本章講的——**出聲解釋強迫你的理解通過連貫性/因果關卡**，於是你常在「講到一半」就自己發現了 bug 或理解漏洞，鴨子一句話沒說。很多人以為 rubber duck 是玄學，其實它是 self-explanation effect 的日常應用，有紮實的認知科學基礎。

「寫一頁 summary」也值得強調：**一頁的限制是刻意的約束**。一頁塞不下所有細節，逼你決定「什麼是主幹、什麼是枝節」——而能不能分出主幹枝節，正是「懂全貌」和「只懂一堆片段」的分野。寫不出一頁 summary，通常不是你話多，是你還沒抓到這個模組的骨架。

## 一個真實走過一遍的費曼測試

抽象講半天，我們拿一段真實 redis code 走一次，讓你看到「洞」怎麼在解釋中現形。目標：redis `dict`（雜湊表）的**漸進式 rehash（incremental rehashing）**——一個「以為懂了其實常沒懂」的經典機制。

**第一次嘗試（不看 code，憑印象講）：**

> 「redis 的 dict 在需要擴容時不會一次搬完所有 key，而是分批搬——每次操作順便搬一點，避免一次 rehash 造成長時間卡頓。所以它同時維護兩張表，慢慢把舊表的東西挪到新表……呃，然後查詢的時候……大概兩張表都要查吧？搬到一半新來的 key 放哪我不太確定，反正就是會處理掉。」

停。這段解釋裡有三個明晃晃的標記詞：

- **「大概兩張表都要查吧」**——含糊。到底怎麼查？先查哪張？這是一個洞。
- **「新來的 key 放哪我不太確定」**——直接承認的洞。rehash 進行中，`INSERT` 一個新 key，放舊表還是新表？
- **「反正就是會處理掉」**——經典的搪塞詞，Ch 35 講過。這裡藏著我沒懂的核心。

**帶著這三個洞回 code（`src/dict.c`），補完再講第二次：**

> 「rehash 進行中，dict 的 `rehashidx` 記錄舊表搬到第幾個 bucket。每次 `dictAddRaw`/`dictFind`/`dictDelete` 這些操作，會順手呼叫 `_dictRehashStep` 搬一個 bucket 過去。**查詢時兩張表都查**，但有優化：如果沒在 rehash（`rehashidx == -1`）就只查第一張。**新增的 key 一律放新表（`ht[1]`）**——因為舊表只會縮不會長，這樣保證舊表的 key 單調減少，rehash 一定會結束。搬完最後一個 bucket，把新表變成主表、釋放舊表、`rehashidx` 設回 -1。」

第二次解釋裡，三個洞都補上了，而且補的過程逼我讀懂了「為什麼新 key 放新表」這個**設計的因果**（保證 rehash 收斂）——這正是 IOED 錯覺原本藏著的 Why。**注意：第一次的「大概/不確定/反正」精準地標出了我真正沒懂的三個點，一個不多一個不少。** 這就是費曼測試的診斷力：它不會冤枉你已經懂的部分，只會揪出你含糊的部分。

（你不必記住 rehash 的細節——重點是感受「解釋裡的含糊詞如何精準定位你的理解洞」這個機制。真要驗證上面的描述，`rg -n "rehashidx|_dictRehashStep|ht\[1\]" src/dict.c` 自己讀一遍。）

## 把費曼測試變成可驗證產出

費曼測試最大的價值，是把「讀懂」這個飄渺的內在狀態，變成**外部可檢查的產出**。這對你、對團隊、對面試都有直接好處：

- **對自己**：一份「我能不看 code 講完」的解釋，是「我真的讀完了」的硬證據。沒有它，你永遠在 IOED 的錯覺裡自我感覺良好。
- **對團隊**：你費曼測試時寫的那頁 summary、畫的那張圖，稍加整理就是團隊缺的 onboarding 文件或設計註解（接 Ch 35 的團隊外化）。你驗證自己理解的副產品，直接幫了下一個讀這段 code 的人。
- **對面試/研究**：安全研究、逆向、系統面試最愛問「解釋一下這個機制怎麼運作」。平常做費曼測試的人，這種問題是主場；平常靠「感覺懂」的人，一被追問 Why 就露餡——因為面試官問的正是 IOED 錯覺藏洞的那些縫。

**產出化的關鍵動作**：每次費曼測試，留下一個 artifact——一頁 summary、一段錄下來的口頭解釋、一張圖、或一則寫進 code 的註解。「我覺得我懂了」不是產出；「這裡有一份我不看 code 寫的、經得起追問的解釋」才是。

## 費曼測試的四種作弊法（以及怎麼不作弊）

費曼測試唯一的敵人是**你自己**——因為評分和被評的是同一個腦，作弊太容易。四種最常見的自我作弊，以及對治：

1. **偷看 code 邊講**：一邊講一邊掃著 code，等於照著念，連貫性關卡整個被繞過。**對治**：物理上把 code 關掉/移到另一個螢幕，逼自己憑理解講。真的忘了某處，就標成一個洞，講完再回去查——不要當場偷看補上。

2. **用術語打包含糊**：講到不懂的地方甩一個術語（「這裡做 copy-on-write」）就滑過去，聽起來很專業其實是搪塞。**對治**：立一條規矩——**每個術語都要能就地拆解成大白話**。拆不了的術語一律當成洞。

3. **降低受眾標準**：假想的受眾其實是「一個跟我一樣懂的人」，於是我省略了一堆「他反正也懂」的環節。**對治**：把受眾設成**具體的、比你笨的人**——你剛入職的實習生、非本領域的朋友。對他們講，你不能省略任何一步。

4. **講完就算，不追問**：講了一遍很流暢，就宣布「我懂了」。但流暢 ≠ 正確，你可能流暢地講了一個錯的模型。**對治**：講完**針對每個關鍵斷言問一次「為什麼是這樣，不是那樣？」**——「為什麼新 key 放新表而不是舊表？」如果答不出「否則 rehash 不收斂」這種因果，你只是描述了 What，沒懂 Why。

這四條的共同精神：**費曼測試的嚴格度，取決於你有多願意對自己誠實。** 一個願意標記自己每個「大概/反正」的人，能從費曼測試榨出巨大價值；一個急著宣布「我懂了」的人，會把測試作弊成一場自我安慰。**這也是為什麼真人受眾這麼寶貴——真人不會替你作弊，他的困惑臉和追問會強制拉高標準。**

## 一頁 summary 的模板

「寫一頁 summary」是留 artifact 最划算的形式，但很多人寫成流水帳。這裡給一個結構化的骨架——每一格都是一個費曼問題，填不出來的格子就是你的洞：

```markdown
# <模組/機制名> —— 一頁理解

## 一句話（電梯簡報）
它解決什麼問題？（一句，講不出一句代表你還沒抓到本質）

## 輸入 → 輸出
餵它什麼、它吐什麼。（用大白話，不用型別簽章搪塞）

## 核心機制（3-5 步）
1. ...
2. ...   ← 每一步都要能回答「為什麼是這步而不是省略它」
3. ...

## 關鍵設計決策 + 為什麼
- 為什麼用 X 而不是更直覺的 Y？（這格最容易露餡——多半是效能/正確性取捨）

## 我還沒完全確定的地方
- （誠實列出，這格空著才可疑——沒有任何模組是你 100% 懂的）
```

這個模板的狠處在最後兩格。「關鍵設計決策 + 為什麼」逼你面對 What/Why 的縫隙；「還沒確定的地方」逼你對抗 IOED——**如果你這格寫「沒有，我全懂了」，那幾乎肯定是錯覺**，一個真讀進去的複雜模組總會留下幾個你存疑的角落。這格空白，通常不是你真懂了，是你還沒讀到會讓你存疑的深度。

一頁的**篇幅約束**是刻意的：它逼你在「一句話」和「3-5 步」裡做取捨，而取捨的過程就是分辨主幹與枝節。寫不進一頁，代表你還沒把這個機制壓縮成一個乾淨的心智模型——你腦中還是一堆沒組織的細節碎片。**能不能壓進一頁，本身就是一個費曼測試。**

## 對比與取捨

| 檢驗「懂了沒」的方法 | 可靠度 | 成本 | 抓得到的洞 |
|---|---|---|---|
| 自評「我覺得懂了」 | 極低（IOED 主場） | 零 | 幾乎抓不到，錯覺本身 |
| 再讀一遍 code | 低 | 中 | 熟悉感增加，理解未必增加 |
| 用自己的話重述 | 中高 | 低 | 連貫性、What/Why 混淆 |
| 教會一個會追問的真人 | 最高 | 高（要有人） | 幾乎所有洞——追問會挖到你最深的含糊處 |
| 寫一頁 summary / 畫圖 | 高 | 中 | 主幹/枝節之分、結構的洞 |

**實戰策略**：日常獨自讀碼用 **rubber duck + 自己話重述**（成本最低、隨時能做）；讀完一個重要模組用**寫一頁 summary**（留下 artifact）；有機會就找真人教一遍（最高 ROI，因為真人的追問會挖到你 rubber duck 挖不到的深洞）。

一個要小心的取捨：**費曼測試的「深度」要匹配任務**。不是每段 code 都值得費曼測試到滴水不漏——你只是路過的膠水碼，掃讀模式（Ch 4）確認「它大概在幹嘛」就夠，硬要費曼測試是浪費。**該用重兵的是「你要改的那 200 行」（Ch 11）、你要移植的核心（Ch 34）、你要找洞的關鍵函式（Ch 32）**——這些地方「以為懂了其實沒懂」的代價最高，最值得用費曼測試把理解逼到現形。判準：這段 code 我理解錯的代價有多大？大 → 費曼測試；小 → 掃讀放行。

## 踩雷集錦

1. **錯誤直覺：「我每一行都看得懂，所以我懂這段 code。」** 正確認識：看得懂每一行 ≠ 懂整段。理解是**能把行與行的因果串成連貫故事**，而 IOED 的錯覺正好長在「每行都認得、但串不起來」這個縫裡。檢驗法：不看 code 從頭講一遍，卡住的接縫就是你以為懂其實沒懂的地方。

2. **錯誤直覺：「在腦中默想一遍解釋就等於做了費曼測試。」** 正確認識：腦中默想會自動「跳過」卡住的地方而你不自覺——大腦很擅長在含糊處腦補一個「反正就是這樣」滑過去。必須**外化成語言**（講出聲/寫下來），語言的線性與連貫性才會強迫卡點現形。這就是為什麼 rubber duck 要真的出聲，不是心裡想。

3. **錯誤直覺：「講的時候用專業術語，代表我很懂。」** 正確認識：往往相反。術語是**理解的替代品**——你用「這裡做 memory barrier」搪塞過去，正是因為你不會用大白話拆解它到底防止了什麼重排、為什麼這裡需要。**能不能不用術語、對外行重講，才是試金石。** 術語講得溜可能只是背得熟。

4. **錯誤直覺：「講不清楚的地方跳過，反正不影響我用它。」** 正確認識：那個「講不清楚的地方」正是費曼測試要你獵捕的獵物，跳過它等於把測試作弊掉。你讀碼的目的（改它、移植它、找它的洞）恰恰最可能卡在你現在想跳過的那個洞上。**含糊處不是雜訊，是任務風險的預警。**

5. **錯誤直覺：「費曼測試是學習法，讀碼是工作，用不上這種學生把戲。」** 正確認識：讀碼的本質就是學習一個陌生系統，費曼測試是驗證學習成果最可靠的手段之一，且有 self-explanation effect 的實證背書。資深工程師的「講得清楚」不是天賦，是他們（有意或無意）反覆對自己和同事解釋的結果。

6. **錯誤直覺：「每段 code 都要費曼測試到完美才算讀過。」** 正確認識：過猶不及。費曼測試成本不低，只該用在「理解錯代價高」的關鍵 code。路過的膠水碼掃讀放行即可。把重兵用在你要改/移植/找洞的核心，才是聰明的資源配置。

## 進階：再往深一層

- **從「教會別人」到「別人真的學會」**：更嚴格的費曼測試不是「我講完了」，而是「聽的人能複述/能用」。真人受眾的價值在此——他的**追問**會挖到你 rubber duck 挖不到的洞，他的**卡住**會標出你解釋裡的斷層。找一個比你資淺的人講一遍你剛讀懂的模組，是壓力測試自己理解的最強手段（也順帶做了 Ch 35 的團隊外化）。
- **費曼測試 × 假設驅動讀碼**：Ch 10 的假設、Ch 35 三欄筆記裡那些「已驗證的發現」，正是費曼測試的原料。你的解釋若在某處只能靠一個「未驗證假設」硬撐，那就是一個偽裝成理解的洞——費曼測試會逼你把它降級回「待查」。兩章的工具在這裡合流：外化提供素材，費曼測試檢驗素材的成色。
- **對 AI 做費曼測試**（接 Ch 20）：把你的口頭解釋丟給 LLM，請它扮演會追問的外行，針對你解釋裡的每個含糊處反問「為什麼」。這是低成本模擬「真人追問」的方式——但要挑對 prompt 讓它真的挑戰你，而不是禮貌地附和。反過來也成立：AI 給你的 code 解釋，你要對它做費曼測試（要求它拆解每個術語、串起因果），才能分辨它是真解釋還是流暢的幻覺。
- **費曼測試作為終身校準器**：IOED 是永久性的認知 bug，不會因為你變資深就消失——資深人的錯覺長在更深、更專業的地方。把費曼測試變成讀關鍵 code 的固定收尾動作，是你一輩子對抗「以為懂了」的校準器。它不是新手練習，是專家紀律。

## 動手練習

1. **對 redis `processCommand` 做完整費曼測試**：讀 `src/server.c` 的 `processCommand`（命令分派中樞），然後**不看 code**，用大白話從頭講一遍：一個命令進來後，它怎麼被查表、被權限/記憶體/叢集等前置檢查攔截、最後怎麼被執行。全程錄音或寫下來，標記每一個「呃/大概/反正」。數一數你有幾個洞。
2. **補洞重講**：針對上一題的每個標記，回 code + 你的 Ch 35 筆記補清楚，然後重講一次，直到能一口氣不卡講完。對照兩次解釋，體會「感覺懂」和「真懂」的落差有多大。
3. **寫一頁 summary**：用一頁 A4（或等量 markdown）寫完「redis 如何處理一個 client 請求的完整生命週期」。刻意的一頁限制會逼你分主幹/枝節。寫不下時，注意你砍掉的是枝節還是你根本沒抓到的主幹。
4. **rubber duck 抓自己的洞**：挑一段你「確定懂了」的硬核 code（例如 `src/ziplist.c` 或 `src/dict.c` 的 rehash），對著一隻鴨子/一面牆出聲解釋。記錄你在「講到一半自己發現原來沒懂」的每一個瞬間——那正是 self-explanation effect 在替你工作。
5. **術語拆解挑戰**：從你上面的解釋裡揪出所有專業術語（epoll、rehash、encoding、RESP……），對每一個問自己「我能不能不用這個詞、對一個外行講清楚它是什麼、為什麼這裡需要它」。講不清楚的，就是你會念不會懂的術語，加進沒懂清單。

## 本章重點整理

- 核心命題：能把一段 code 教會外行，才算真懂。理解是「能生成解釋」，不是「能認得內容」。
- IOED（解釋深度的錯覺，Rozenblit & Keil 2002）：人普遍高估自己的理解，直到被要求詳細解釋才發現滿是洞。熟悉感被誤判成理解。
- self-explanation effect（Chi et al. 1989）：學得好壞的差別在「主動自我解釋的量」，不在智力。主動解釋逼出遠深於被動閱讀的理解。
- 解釋戳破錯覺靠三道關卡：連貫性（斷橋現形）、因果（What/Why 縫隙）、受眾（不許用術語搪塞）。
- 費曼四步：假裝教外行 → 不看 code 白話講 → 標記每個卡住/含糊/術語搪塞處 → 補洞重講，直到不卡。
- 五種形式：自己話重述、畫給別人看、寫一頁 summary、rubber duck、刻意獵捕含糊詞。
- 把費曼測試變成可驗證產出（留下 artifact）；深度要匹配任務（重兵給要改/移植/找洞的核心）。

  - **前提**：無，認知科學經典短論文。
