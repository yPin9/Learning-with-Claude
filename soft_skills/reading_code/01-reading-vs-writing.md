# Ch 1 — 讀碼 vs 寫碼的不對稱

> **目標**：搞清楚一件多數工程師從沒認真想過的事——為什麼讀別人的 code 比自己寫還累。這不是你菜，是這個過程本質上就不對稱。看穿這個不對稱，你才知道後面整門課的技巧到底在對抗什麼。

## 先建立直覺：寫碼是有損壓縮，讀碼是解壓縮

你腦子裡有一個意圖：「我要一個 LRU cache，容量滿了淘汰最久沒用的那個，thread-safe，而且 miss 的時候去 DB 撈」。這個意圖裡塞滿了 context——為什麼要 thread-safe（因為多個 worker 共用）、為什麼是 LRU 而不是 LFU（因為當初 benchmark 過）、容量為什麼設 1024（拍腦袋的，將來要調）。

你把它寫成 code。寫完之後，螢幕上剩下的是：

```c
struct lru_cache { ... };
void *cache_get(struct lru_cache *c, const char *key);
```

**你腦中那一大坨意圖，絕大部分沒進到 code 裡。** 「為什麼 thread-safe」進不去（頂多一個 mutex 欄位，但「為什麼需要」不見了）；「為什麼 1024」進不去（就一個 `#define CACHE_SIZE 1024`，理由蒸發）；「當初 benchmark 過 LFU 更差」完全沒留痕跡。

這就是關鍵的不對稱：

```
 寫碼（compression / 有損壓縮）
 ┌────────────┐         ┌──────────┐
 │  意圖       │         │          │
 │  + context  │ ──────▶ │   code   │   意圖與 context 大量流失
 │  + 理由     │  丟失   │          │
 │  + 試錯     │         └──────────┘
 └────────────┘

 讀碼（decompression / 解壓縮，但資料已經丟了）
 ┌──────────┐         ┌────────────┐
 │          │ ??????  │  意圖？     │
 │   code   │ ──────▶ │  context？  │   要從殘缺線索反推被丟掉的東西
 │          │  反推   │  理由？     │
 └──────────┘         └────────────┘
```

寫是**編碼**：意圖 → 符號，你有全部的原料，只是把它壓成一種機器能執行的形式。讀是**解碼**：符號 → 意圖，但你手上只有壓縮後的產物，原始意圖裡那些「為什麼」在壓縮過程中被當成冗餘資訊丟掉了。**你不是在讀一份完整的說明書，你是在對一份殘缺的證物做鑑識。**

這對做過 binary reverse engineering 的人應該無比熟悉：source → binary 也是一次有損壓縮（變數名沒了、型別沒了、註解沒了）。讀 source 比逆 binary 幸運的地方，就在於命名、型別、結構這些「上一層的線索」還在——但**意圖與理由這一層，source 和 binary 一樣都丟了**。這是下一章的主軸，這裡先埋下伏筆。

## 底層機制：為什麼三種東西必然流失

不是寫 code 的人偷懶。是「把意圖變成 code」這個動作**在資訊理論上就會丟東西**。具體丟三類：

### 1. 意圖（intent）— code 只記錄「怎麼做」，不記錄「要做什麼」

看這段 redis 真實的 code（`src/db.c` 的 `expireIfNeeded`）：

```c
if (server.masterhost != NULL) {
    if (server.current_client && (server.current_client->flags & CLIENT_MASTER)) return KEY_VALID;
    if (!(flags & EXPIRE_FORCE_DELETE_EXPIRED)) return KEY_EXPIRED;
}
```

code 精確告訴你**發生什麼**：如果我是 replica，而且指令來自 master，就當 key 還有效。但它沒告訴你**為什麼**——為什麼 replica 不能自己過期 key？（因為過期是 master 說了算，master 會送 DEL 過來；replica 自己刪會導致主從資料不一致。）這個「為什麼」是整段邏輯存在的唯一理由，而它**不在 code 裡**。

redis 這裡算佛心，上面有一大段註解解釋了。但註解是作者額外的善意，不是 code 本身攜帶的資訊——**大部分 code 沒有這種註解，而有註解的地方註解還可能是騙人的舊資訊**（Ch 2 詳談）。

### 2. Context（上下文）— 寫的時候在腦中，讀的時候要從零重建

寫這段 code 的人，腦中同時掛著：master/replica 的複製協定、`expireIfNeeded` 的所有呼叫者、`flags` 每一個 bit 的意義、`KEY_VALID`/`KEY_EXPIRED`/`KEY_DELETED` 三態的差別。這些 context 讓他寫這五行毫不費力。

你來讀的時候，這些 context **一個都不在你腦中**。你得先搞懂什麼是 `EXPIRE_FORCE_DELETE_EXPIRED`、誰會帶這個 flag 進來、`current_client` 什麼時候是 master——光是把作者寫這五行時「免費擁有」的背景重建起來，你就要跳去看四五個地方。這是讀碼累的核心來源：**你花在「補 context」上的力氣，遠大於花在「看懂這五行語法」上的力氣。**

### 3. 試錯歷史（the roads not taken）— code 只留下勝者，不留失敗的嘗試

那 1024 為什麼是 1024？作者可能試過 512（cache miss 太高）、試過 4096（記憶體吃太兇）、最後定 1024。**這個試錯過程完全不在 code 裡。** 你讀到 `1024` 只會想「這是不是隨便寫的?能不能改?」——而作者早就用血淚知道改了會出事。code 是決策的**結果**，不是決策的**過程**；過程只可能藏在 git log、issue 討論、或某個人的腦子裡（Ch 17「git 當考古工具」就是去挖這個）。

## 認知負荷：同一段邏輯，寫 vs 讀的大腦負擔天差地別

把上面三點翻譯成大腦的語言。**寫的時候**，所有 context 都在你的工作記憶（working memory，人腦暫存少量資訊的短期容量，Ch 3 詳談）裡，是「熱」的——你不需要 look up，直接用。**讀的時候**，這些 context 全是「冷」的，你得一個一個 look up，把它們搬進工作記憶。

而工作記憶容量極小（後面會看到約只有 4 個 chunk）。於是讀陌生 code 時經常發生這種事：你追 `expireIfNeeded` 追到需要理解 `flags`，去看 `flags` 的定義，看懂了回來——結果剛才追到哪裡忘了。**工作記憶被 context lookup 擠爆了。** 寫的人從不會遇到這個問題，因為他的 context 早就固化在長期記憶（long-term memory）裡了。

```
 寫：context 都是「熱」的（在工作記憶 / 長期記憶）
   ┌─────────────────────────┐
   │ [master協定][flags語意]  │  ← 全部就位，寫 code 只是輸出
   │ [三態差別][呼叫者]        │
   └─────────────────────────┘

 讀：context 都是「冷」的，要現場 lookup 搬進來
   ┌─────────────────────────┐
   │ [???] ← 現在讀到 flags   │  去 db.c 找定義……
   │ [???] ← 剛才追到哪?忘了  │  ← lookup 把工作記憶擠爆了
   └─────────────────────────┘
```

這就是為什麼「讀懂一段 code」花的時間，常常是「寫出同一段 code」的好幾倍。不是你笨。是這場遊戲對讀的人設計得就不公平。

## 抽象：對寫友善，對讀不友善

軟體工程教你「用抽象管理複雜度」——把細節封進函式、類別、模組，呼叫端只看介面不看實作。這對**寫**是天大的恩惠：我用 `cache_get(c, key)` 就好，不必每次都想它內部怎麼實作。

但同一個抽象對**讀**是負擔。因為讀碼常常要「打穿抽象」：你想知道 `cache_get` 真正做了什麼、在什麼情況會回 NULL、有沒有 side effect——這時抽象不是幫你隱藏細節，是擋在你和真相之間的一道牆。你得跳進去（jump to definition），跳進去可能又呼叫三個別的函式，再各跳三次……

redis 的 `getCommand` 是教科書級例子（`src/t_string.c`）：

```c
void getCommand(client *c) {
    getGenericCommand(c);
}
```

`getCommand` 這個「你以為是 GET 指令實作」的函式，body 只有一行——它把活全丟給 `getGenericCommand`。你要懂 GET 到底幹嘛，得再跳一層。而 `getGenericCommand` 裡又呼叫 `lookupKeyReadOrReply`，那又是另一層，裡面才真正碰到過期判斷、型別檢查……**寫的人靠這種分層把每個函式維持得很小很乾淨；讀的人得把這條 delegation 鏈一路跳穿，才拼得出「GET 一個 key 到底會發生什麼」的全貌。** 抽象把一件完整的事切成了散落各處的碎片，寫的人享受了切割的整潔，讀的人承擔了重組的成本。

這不是說抽象不好——沒有抽象 codebase 根本無法維護。而是要你認清：**你在讀碼時感受到的「跳來跳去、抓不住全貌」的痛苦，很大一部分是良好抽象的必然副作用。** 對抗它的方法不是抱怨，是策略（Ch 23「讀懂 indirection」整章在講）。

## 那到底差幾倍？查證過的數據

「讀碼比寫碼花更多時間」這句話流傳很廣，但常被講得含糊。把幾個站得住腳的來源攤開：

- **Robert C. Martin（《Clean Code》, 2008）**：直接寫「讀 vs 寫的時間比**遠超過 10:1**（well over 10 to 1）。我們寫新 code 時不斷在讀舊 code。」——這是業界最常被引用的說法，但要誠實講：它是 Martin 的**經驗論斷與修辭**，不是量測數據。當成「方向正確、數字別當精確值」來用。

- **Xia et al.（ICSE 2018，《Measuring Program Comprehension: A Large-Scale Field Study with Professionals》）**：這是**實證研究**，追蹤 78 位職業開發者共 3,148 個工時，結論是開發者平均把約 **58% 的時間**花在「程式理解（program comprehension）」活動上。這是我看過方法最扎實的數字之一，而且它還發現：**資深開發者花在理解上的時間比例顯著低於資淺開發者**——這正暗示「讀碼是可以練、可以變快的技能」，也就是這門課存在的理由。

- **Peter Hallam（微軟工程師，部落格文章）**：主張約 70% 的時間花在理解既有實作上。這比 Xia 的數字高，但它是**個人論述而非受控研究**，我把它當作「同一方向的旁證」，不當作硬數據。

把這幾條放在一起，可以誠實地說：**「讀佔開發時間的大頭」有實證支持（保守約 58%），「讀比寫多好幾倍」在方向上被廣泛認同，但具體倍數（10:1 之類）是經驗估計、非精確量測。** 這門課不需要你信某個精確倍數；你只要接受一個方向明確的事實：**你職涯絕大部分時間在讀 code，而幾乎沒人系統地教過你怎麼讀。**

## 核心信條：讀碼要主動，不能被動逐行掃

前面所有分析導向一個實踐結論。既然：

- 意圖、context、理由在 code 裡**大量缺失**，
- 你的工作記憶**小到裝不下**重建 context 的負擔，
- 抽象**逼你不斷跳轉**，

那麼「從第一行讀到最後一行、逐行看懂」這種**被動掃描**式讀法必然失敗——你會在補 context 的過程中反覆爆掉工作記憶，讀到第 200 行忘了前 50 行，最後淹死在細節裡卻拼不出全貌。

正確的姿態是**主動讀碼（active reading）**：

- **帶問題進場**：不是「這個檔案在幹嘛」，而是「GET 一個過期的 key 會回什麼？這條路徑經過哪些函式？」——具體問題像探照燈，只照亮你要的路徑，其餘全部略過。
- **帶假設驗證**：看到 `expireIfNeeded` 先猜「它應該負責判斷 key 過期沒、過期就刪」，然後只讀足以確認或推翻這個假設的部分，而不是把整個函式從頭讀到尾（Ch 10「假設驅動讀碼」整章在講）。
- **主動外化**：把重建出來的 context 立刻寫下來/畫出來，從工作記憶卸載到紙上，騰出腦容量（Ch 35「外化理解」整章在講）。

這正是逆向工程師攻堅 binary 的姿態——沒人會從 `_start` 逐條反組譯到 `main`，你是帶著「這程式怎麼驗證授權碼」這種問題，直奔目標。**讀 source 要用同一套主動、目標導向、假設驅動的攻堅心法，而不是把它當小說從頭讀到尾。** 這句話是整門課的地基。

## 對比與取捨

| 維度 | 寫碼 | 讀碼 |
|---|---|---|
| 資訊方向 | 意圖 → code（編碼 / 有損壓縮） | code → 意圖（解碼 / 資料已丟失） |
| 意圖與理由 | 在你腦中，完整 | 大量流失，只能反推 |
| Context | 「熱」的，隨手可用 | 「冷」的，要現場 lookup 重建 |
| 工作記憶負擔 | 低（context 已就位） | 高（不斷被 lookup 擠爆） |
| 抽象的作用 | 幫你隱藏細節，是恩惠 | 擋在你和真相間，是牆 |
| 試錯歷史 | 你親身經歷 | 完全不可見（除非挖 git/issue） |
| 有效策略 | 由內而外，逐步構建 | 由外而內，帶問題、帶假設 |

一句話取捨：**寫是把腦中完整的世界輸出成殘缺的符號；讀是從殘缺的符號重建腦中的世界——後者永遠更難，因為你重建的原料本身就不全。**

## 踩雷集錦

1. **錯誤直覺**：「我讀不懂這段 code 是因為我程度不夠 / 語法不熟。」
   **正確認識**：多數時候你語法完全看得懂（`if`、`return`、位元 AND 你都會），卡住的是**缺 context**——不知道 `EXPIRE_FORCE_DELETE_EXPIRED` 為何存在、`current_client` 何時是 master。把「讀不懂」正確歸因為「context 缺失」而非「能力不足」，你才會去補對的東西（追呼叫者、查歷史），而不是懷疑人生重讀語法書。

2. **錯誤直覺**：「認真點，從第一行逐行讀到最後一行，總能讀懂。」
   **正確認識**：逐行被動掃描是**最沒效率**的讀法，對大 codebase 幾乎必敗。你會在補 context 的跳轉中反覆爆掉工作記憶，讀完最後一行也拼不出全貌。正確做法是帶著具體問題主動出擊，只讀與問題相關的路徑。

3. **錯誤直覺**：「這個 `1024`（或某段怪邏輯）看起來沒道理，八成是隨手寫的，我改掉應該沒差。」
   **正確認識**：code 只留決策的**結果**，不留**過程**。那個看似隨意的值/分支，很可能是作者踩過坑、benchmark 過、修過某個 production bug 才變成現在這樣。「看不出理由」不等於「沒有理由」——理由只是隨著意圖一起被壓縮掉了。動它之前先挖 git blame（Ch 17）。

4. **錯誤直覺**：「有好的抽象/分層，code 應該更好讀。」
   **正確認識**：好抽象對**寫**更友善，對**讀**經常更不友善——它把一件完整的事切成散落各處的碎片，逼你不斷跳轉重組。這不是抽象的錯，是讀寫不對稱的必然。認清這點，你才會準備好對抗 indirection（Ch 23）的工具，而不是天真期待「乾淨的 code 讀起來就輕鬆」。

## 進階：再往深一層

- **「自我文件化的 code」是半個神話**：好的命名確實能把部分意圖塞回 code（`expireIfNeeded` 這名字就洩漏了意圖）——這是 code 唯一能自帶的線索，值得珍惜也值得你反過來善用（從命名反推語意，Ch 2）。但命名再好也**塞不進「為什麼」和「試過什麼」**。別指望靠讀好 code 就免除挖歷史、追 context 的功夫。

- **這個不對稱正是「重寫誘惑」的根源**：很多工程師寧可把一段陌生 code **重寫**也不願讀懂它（Jeff Atwood 那篇〈When Understanding Means Rewriting〉講的就是這個）。因為寫是你熟悉的、context 在腦中的順向過程，讀是逆向的、要重建 context 的逆水行舟。**但重寫會把作者踩過的坑全部重踩一遍**（那些被壓縮掉的試錯歷史）。認清這個誘惑的來源，你才不會在該讀懂的時候逃去重寫。

- **AI 讀碼工具在補的正是「context 重建」這一環**：現在的 LLM 讀碼助手，本質上是幫你快速重建冷 context、生成假設。它們對「補 context」很有用，但對「意圖與試錯歷史」同樣無能為力（那些資訊根本不在 code 裡，模型也變不出來）。Ch 20 專門談怎麼用、和它的邊界在哪。

## 動手練習

1. **體感編碼→解碼的落差**：找一段你**三個月前自己寫**、之後沒碰過的 code（100 行以上有點邏輯的）。先別看，寫下你記得的「它為什麼這樣設計」。然後打開讀。你會驚訝於**連自己寫的 code，三個月後的你都得重建 context**——因為當初那坨意圖，同樣沒進到 code 裡。這就是讀陌生 code 的困境，只是對象換成別人。

2. **抓「被壓縮掉的理由」**：在 WSL 打開 redis，讀 `src/db.c` 的 `expireIfNeeded`：
   ```bash
   wsl -e bash -lc 'cd ~/reading_code_lab/redis && sed -n "1974,2010p" src/db.c'
   ```
   列出這段裡**至少 3 個「code 說了怎麼做、但沒說為什麼」**的地方（提示：`masterhost != NULL` 那段、`isPausedActionsWithUpdate` 那段、`refcount == OBJ_STATIC_REFCOUNT` 那段）。感受一下：沒有那些註解，你能反推出多少「為什麼」？

3. **量一次抽象的深度**：從 `getCommand` 開始，用 jump-to-definition（或 `rg`）一路往下跳，數數「一個 GET 指令的實作，被切成了幾層函式、散在幾個檔案」。體會抽象對讀者施加的重組成本。

## 本章重點整理

- 寫碼是**有損壓縮**（意圖 → code），讀碼是**解壓縮**（code → 意圖），但關鍵資訊在壓縮時已丟失——這是讀比寫難的根本原因。
- 必然流失三類東西：**意圖**（code 只記怎麼做，不記要做什麼）、**context**（寫時在腦中，讀時要重建）、**試錯歷史**（只留勝者，不留失敗嘗試）。
- 認知負擔不對稱：寫時 context 是「熱」的，讀時是「冷」的，要現場 lookup，把小小的工作記憶擠爆。
- 抽象對寫友善、對讀不友善：它把完整的事切成碎片，逼讀者不斷跳轉重組。
- 數據（查證過）：讀佔開發時間大頭有實證支持（Xia 2018 約 58%）；「讀比寫多好幾倍」方向被廣泛認同，但 10:1 之類是經驗估計非精確量測。
- 核心信條：讀碼要**主動**（帶問題、帶假設、主動外化），不能被動逐行掃——這是整門課的地基。

## 自我檢核

- [ ] 不看筆記，能不能用「壓縮/解壓縮」的比喻，跟同事解釋為什麼讀別人的 code 通常比自己寫還累？
- [ ] 「意圖、context、試錯歷史」這三類流失的資訊，各舉一個你自己 codebase 裡的例子。
- [ ] 面試官問「你怎麼看待『工程師大部分時間在讀 code』這說法？有數據嗎？」——你能不能既給方向、又誠實區分「實證數字」與「經驗論斷」？
- [ ] 為什麼「好的抽象讓 code 更好讀」這句話對**寫**成立、對**讀**常常不成立？
- [ ] 為什麼「逐行從頭讀到尾」對大 codebase 幾乎必敗？主動讀碼具體要「主動」做哪三件事？

## 延伸閱讀

- **Robert C. Martin,《Clean Code: A Handbook of Agile Software Craftsmanship》(Prentice Hall, 2008), Ch 1**
  - **讀哪裡**：第 1 章「Clean Code」開頭那段「reading vs writing ratio well over 10:1」的論述。
  - **學到什麼**：業界最經典的「讀多於寫」立論。讀的時候練習分辨：哪些是實證、哪些是他的經驗修辭。本章的數據討論就是拿它當靶。
  - **和本章關聯**：直接對應「差幾倍」那節，是流傳最廣但要謹慎引用的來源。

- **Xia, Bao, Lo, Xing, Hassan, Li,《Measuring Program Comprehension: A Large-Scale Field Study with Professionals》(IEEE TSE / ICSE 2018)**
  - **讀哪裡**：Abstract 與 Results 兩節即可，看它怎麼量「comprehension 佔 58%」、以及「senior 花的比例更低」這個發現。
  - **學到什麼**：一個方法扎實的實證數字，取代含糊的「聽說讀很花時間」。PDF 可在作者頁（baolingfeng.github.io）取得。
  - **和本章關聯**：本章唯一當「硬數據」引用的來源；也支撐了「讀碼是可練的技能」這個全課前提。

- **Jeff Atwood,〈When Understanding Means Rewriting〉(Coding Horror, 2006)**
  - **讀哪裡**：整篇很短，看他從 Peter Hallam 的觀察延伸出「工程師為何寧可重寫」的討論。
  - **學到什麼**：讀寫不對稱在心理上的後果——「重寫誘惑」。理解它你才不會在該讀懂時逃去重寫。
  - **和本章關聯**：對應「進階」那節的重寫誘惑；也是接觸 Peter Hallam 70% 說法的入口。
