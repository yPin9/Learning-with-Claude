# Ch 38 — 打造你自己的讀碼 SOP

> **目標**：把整門課 38 章的方法論收斂成**一張可執行的個人 SOP**——從「拿到一個陌生 repo」到「能安全改一行」的完整流程。含時間盒、工具動用順序、決策樹、筆記模板。這一章是全課方法論的最終收斂；讀完你有一份可以直接抄走、貼在牆上、每次攻堅照著跑的 checklist，並知道怎麼把它客製成你自己的。

## 為什麼要有 SOP？

前面每一章都是一件武器或一招心法。武器多了，反而有個新問題：**臨場時你記不得該先用哪個、什麼順序、何時停。** 攻堅一個陌生 codebase 時你壓力大、時間緊，這時候需要的不是「更多選擇」，是**一條預設路徑**——不用思考就能開始跑的流程。SOP 就是這個。

逆向工程師都有自己的 SOP：拿到一個 binary，先 `file`、再 `strings`、再看 entry、再標 imports……不是因為每次都一樣，是因為**有一條預設路徑，你就不會呆在原地不知從何下手**。讀 source 一樣。SOP 的價值不在「每次都照做」，在於**它給你一個起手式和一套 fallback**：卡住時回到 SOP，看下一步該做什麼。

這章給你一份**參考 SOP**——一個經過本課驗證、合理的預設流程。但最後一節會強調：**SOP 必須客製化**。C kernel 專案跟 TypeScript 前端專案的攻堅節奏完全不同；你的 SOP 該長成你的樣子。

## SOP 的骨架：六個階段 + 時間盒

整個攻堅分六階段，每階段有明確產出和建議時間盒。時間盒不是硬規定，是**逼你收斂、防止 rabbit-hole（Ch 37 反模式 3）的機制**——時間到就強制檢查「我在主線上嗎」。

```
 階段              產出                         時間盒（中型專案）
 ──────────────────────────────────────────────────────────────
 0  界定任務       一句話寫清「我要幹嘛」        5 分鐘
 1  偵察 recon     規模/結構/entry/build 印象    45-60 分鐘
 2  建圖 map       架構地圖（模組+資料+呼叫）    30-60 分鐘
 3  定位 locate    鎖定「要改/要懂的那幾百行」   30 分鐘
 4  追蹤 trace     一條關鍵路徑的完整 data flow  30-60 分鐘
 5  驗證 verify    用 gdb/trace 釘死假設         按需
 6  改動 change    改一行→驗證→（可選）PR        按需
```

時間盒是給「中型專案 + 中等目標」的基準。小專案砍半，Linux kernel 某子系統可能每階段乘三。重點是**每個階段都有明確產出**——沒產出就別進下一階段，這是防止「假裝在前進」的閘門。

---

## 階段 0：界定任務（5 分鐘）— 別跳過

在打開任何檔案之前，用一句話寫下**你這次到底要達成什麼**。這是整個 SOP 最容易被跳過、也最不該跳過的一步。

```
本次任務：___________________________________
成功標準：___________________________________
不需要懂：___________________________________
```

三欄都要填。「不需要懂」那欄尤其關鍵——它是你對抗完美主義（Ch 37 反模式 8）的預先聲明。例如：

> **任務**：搞懂並能改 redis `OBJECT ENCODING` 對 list 的判斷邏輯
> **成功標準**：能說出 list 何時從 listpack 轉 quicklist，並能改動門檻且驗證
> **不需要懂**：quicklist 內部的壓縮節點、listpack 的位元組編碼細節

有了這三行，接下來每一步你都能問「這幫我達成成功標準嗎？」——**目標感是整套 SOP 的定盤星**。

---

## 階段 1：偵察（45-60 分鐘）— 建立全局印象

目標：不讀任何函式體，建立「這專案有多大、怎麼組織、從哪進入、怎麼編」的骨架印象。呼應 Ch 5。

**動作清單**（照順序，每個都是一條指令）：

```bash
# 1. 規模體檢——多大、什麼語言、註解勤不勤
cloc --quiet src/

# 2. 目錄結構——模組怎麼切
tree -L 2 -d          # 或 ls 各層

# 3. 讀 README / docs / CONTRIBUTING——作者親口說的架構
#    （最快的架構情報，別跳過）

# 4. 找所有 entry point（別假設只有一個）
rg -n "int main" src/*.c
#    以及語言慣例的入口：main()/_start/WinMain/if __name__

# 5. build 系統一瞥——怎麼編、哪些檔真的參與
ls Makefile CMakeLists.txt configure meson.build 2>/dev/null

# 6. 建索引，為後續階段鋪路
ctags -R --languages=C,C++ src/
cscope -b -q -R -s src
bear -- make -j$(nproc)      # 產 compile_commands.json 給 clangd
```

**產出**：一段「偵察筆記」——三五句話 + 幾個數字（規模、主要語言、entry 在哪、build 用什麼）。這時候你對整個系統**一無所知，但知道它的形狀**。這正是關鍵——你有了一張空白地圖的邊框。

> **時間盒到了怎麼辦**：60 分鐘一到，強制停偵察、進建圖，就算還有沒看的目錄。偵察是「印象」不是「精讀」，你不需要看完每個檔。沒看的記成 TODO。

---

## 階段 2：建圖（30-60 分鐘）— 把骨架畫出來

目標：把偵察的印象**外化成一張架構地圖**——三張圖，對應三個問題。呼應 Ch 7、Ch 9、Ch 35。

- **模組圖**：有哪些子系統、怎麼分層、誰依賴誰。（從目錄結構 + `#include` 關係推）
- **核心資料結構圖**：這系統圍繞哪幾個 struct 轉？（找「到處被傳來傳去」的那幾個型別——它們是系統的名詞）
- **主流程圖 / call graph**：從 entry 到主迴圈，控制流大致長怎樣。

```bash
# 從 main 往下畫兩層呼叫圖
cflow --depth=2 -m main src/server.c

# 找核心資料結構——哪個 struct 出現最頻繁
rg -o "struct \w+" src/ | sort | uniq -c | sort -rn | head

# 主迴圈通常靠 cscope 反查某個 *Main / *loop / event dispatch
cscope -d -L -3 aeMain    # 誰呼叫事件迴圈 → 那就是心臟
```

**產出**：三張手繪或文字圖（ASCII 也行），存進你的 reading journal。這一步強迫你**把還很模糊的理解外化**——畫不出來就是還沒懂，正好暴露盲點。

---

## 階段 3：定位（30 分鐘）— 收斂到你要改的那幾百行

目標：從整個系統收斂到**跟你任務直接相關的那幾個函式/檔案**。呼應 Ch 11——這是全課「攻堅」二字的核心。

**定位策略**（多管齊下，看哪個先命中）：

```bash
# 策略 A：從使用者可見的字串反推——命令名、log 訊息、錯誤字串
rg -n "OBJECT|encoding" src/object.c

# 策略 B：從命令/API 分派表定位 handler
rg -n "objectCommand|\"encoding\"" src/

# 策略 C：從相關資料結構反查誰碰它
cscope -d -L -0 strEncoding   # 找定義
cscope -d -L -3 strEncoding   # 找呼叫者
```

**決策：這時候用哪種閱讀模式？**（呼應 Ch 4 的決策樹）

```
                拿到一個候選函式/檔案
                        │
          ┌─────────────┼─────────────┐
    只想確認「是不是   想搞懂「它到底    想知道「資料/控制
     這裡」            怎麼運作」        怎麼流過它」
          │             │                │
        掃讀           精讀             追蹤
      (看簽名/          (逐行讀，        (順 data flow /
       註解/            記假設)          call chain 走)
       結構)
```

**產出**：一句話 + 幾個檔案:行號——「我要改/要懂的是 `src/object.c` 的 `strEncoding()`（928 行）跟 `src/t_list.c` 的轉換邏輯（37 行起）」。收斂完成，接下來只碰這幾百行。

---

## 階段 4：追蹤（30-60 分鐘）— 一條路徑走到底

目標：對鎖定的那條路徑，做**完整的 data flow / control flow 追蹤**——資料從哪進來、經過哪些函式、怎麼變、到哪裡輸出。呼應 Ch 8、Ch 9。

**工具動用順序**（這是整個 SOP 最該內化的一條）：

```
rg           → 快速定位「這符號出現在哪」（廣、快、不精準）
  ↓
ctags        → 跳到定義（一次一個符號）
cscope/global→ 反查呼叫者 / 被呼叫者（建呼叫鏈骨架）
  ↓
clangd(LSP)  → 需要精準時：同名符號辨析、巨集展開後的真相、跨 TU
  ↓
gdb/trace    → 靜態讀不確定時：實際走哪條、變數真的是什麼（階段 5）
```

**這條順序的邏輯**：從**廣而快**到**窄而精**，從**靜態**到**動態**。永遠先用便宜的工具（rg）撒網，命中後才動用貴的工具（clangd/gdb）精確打擊。反過來（一開始就開 gdb 硬追）會慢死。

**產出**：一條「路徑筆記」——`函式A → 函式B → 函式C`，每一跳標註「這裡資料變成什麼、為什麼跳這條」。留下未確認的假設（`?`）給階段 5。

---

## 階段 5：驗證（按需）— 用執行釘死假設

目標：階段 4 留下的每一個「我猜這裡……」，用動態手段確認。呼應 Ch 18、Ch 19。這一步是對抗「只讀不跑」（Ch 37 反模式 5）的核心。

**驗證手段選擇**：

```
想確認「這行有沒有走到 / 變數是什麼值」  → gdb 斷點 + print
想確認「呼叫了哪些函式、什麼順序」        → uftrace / gdb backtrace
想確認「碰了哪些 syscall / 檔案 / 網路」  → strace
想確認「呼叫了哪些 libc / 動態符號」      → ltrace
想確認「整體行為對不對」                  → 直接跑，餵輸入看輸出
```

一個典型的驗證 loop（我們在 Ch 39 會完整示範）：

```bash
gdb -p $(pidof redis-server)
(gdb) break t_list.c:37
(gdb) commands
        printf "list len=%d encoding=%d\n", lpLength(o->ptr), o->encoding
        continue
      end
(gdb) continue
# 然後在另一個 terminal 對 server 做操作，看斷點打出的真實值
```

**產出**：把每個 `?` 假設標記成「✓ 已驗證」或「✗ 猜錯了，實際是……」。猜錯的那些最有價值——它們是你心智模型的漏洞被補上的地方。

---

## 階段 6：改動（按需）— 改一行並驗證

目標：做出最小改動，並證明它有效。這是「能安全改一行」的畢業動作。

**安全改動 checklist**：

```
[ ] 改動前：這行/這函式還有沒有別的 caller？（cscope 反查，別改壞別人）
[ ] 改動前：有沒有測試覆蓋這裡？（跑一次現有測試當 baseline）
[ ] 改動：做最小的、可回退的修改
[ ] 驗證：重編（最好增量編）→ 跑 → 確認行為如預期
[ ] 驗證：跑原有測試，確認沒弄壞別的
[ ] 回退：git diff 留底，確認能一鍵還原
```

**產出**：一個經過驗證的 diff。如果目標是貢獻開源，接 Ch 33（code review 視角）把它整理成 PR-ready。

## 決策樹：卡住時查這張

攻堅過程中最常見的三個岔路，直接給決策樹：

```
Q1：這個符號/函式，我該花多少力氣讀？
    是我路徑上的關鍵節點？──是──▶ 精讀 + 驗證
                          └─否──▶ 掃簽名，當黑盒，記 TODO

Q2：我靜態讀不確定它的行為，怎麼辦？
    能不能跑起來觸發這條路徑？──能──▶ gdb 下斷點看真相（階段 5）
                            └─不能─▶ 找測試/寫最小 harness 觸發它
                                     真的跑不了 ──▶ 標「未驗證，理論推測」繼續

Q3：我追進一個 indirection（函式指標/vtable/dispatch），要不要展開？
    我這條路徑需要知道具體實作嗎？──是──▶ gdb 看實際跳去哪（別窮舉所有實作）
                                └─否──▶ 當黑盒，記「這裡分派到某 handler」繼續

Q4：時間盒到了，但我還沒懂/沒追完，怎麼辦？
    ──▶ 強制停，把未完成記成 TODO，退回上一階段的產出，
        問「用現在的理解，我能不能推進任務？」能就推進，不能才續追
```

## 可直接抄走的 reading journal 模板

呼應 Ch 35。這是一份 markdown 模板，每攻堅一個專案就複製一份填。**直接抄走客製化。**

```markdown
# Reading Journal — <專案名> @ <版本/commit>

## 0. 任務界定
- 本次任務：
- 成功標準：
- 不需要懂：

## 1. 偵察（recon）
- 規模：____ 行 / 主要語言 ____ / 註解比 ____
- 目錄結構（模組）：
- entry point：<檔案:行>（共 __ 個，真正的是哪個 & 為什麼）
- build 系統：____（怎麼編：`____`）
- 第一印象/疑問：

## 2. 架構地圖
- 核心資料結構：<struct 名> —— 一句話它是什麼
- 模組依賴：A → B → C
- 主流程/主迴圈：<檔案:行> ——
  （這裡貼你的 ASCII 圖）

## 3. 定位
- 任務相關的關鍵函式/檔案：
  - <檔案:行> `funcName()` —— 為什麼是它

## 4. 路徑追蹤（一條）
- 觸發點：<使用者動作 / API / 命令>
- 路徑：funcA → funcB → funcC
  - funcA（檔:行）：資料進來長怎樣 →
  - funcB（檔:行）：做了什麼變換 →
  - funcC（檔:行）：輸出/副作用 →

## 5. 假設與驗證
| # | 假設 | 驗證方式 | 結果 |
|---|------|---------|------|
| 1 | 我猜 X | gdb break … | ✓ / ✗ 實際是… |

## 6. 費曼摘要（Ch 36）
（用一段大白話，講給不懂這專案的人聽：這個機制到底怎麼運作）

## 7. 改動（如有）
- 改了什麼（檔:行）：
- 為什麼安全（誰還 call、測試覆蓋）：
- 怎麼驗證的：
- diff：

## TODO / 未解之謎
- [ ] （rabbit-hole 忍住沒追的岔路）
```

這份模板的每一節都對應 SOP 的一個階段。它同時是**流程檢查表**（每節填了沒 = 每階段做了沒）和**理解外化的容器**（防止讀懂又忘）。

## 最重要的一節：客製化你的 SOP

上面是一份**參考 SOP**，不是聖經。真實攻堅時，你要按三個維度調整它：

**按語言/生態調**。C/kernel 專案：cscope/ctags 極強、gdb 是命脈、build 系統（`#ifdef`）要重視。動態語言（Python/JS）：靜態索引弱，更依賴「跑起來 + 動態 trace + 讀測試」。Rust/Go：LSP 極強，ctags 反而次要。你的工具動用順序要隨生態變。

**按目標調**。目標是「修一個明確的 bug」：偵察可以砍很短，直接從 bug 的 symptom（錯誤訊息、crash stack）反向定位，跳過大量建圖。目標是「onboarding 整個專案」：反過來，建圖階段要加重，改動階段可能根本不需要。目標是「找漏洞」（Ch 32）：整個重心移到 data flow + 信任邊界，決策樹要換一套。

**按你自己調**。你個人的「高危反模式」（Ch 37 那份自我盤點）決定你的 SOP 要在哪加防護。你老愛 rabbit-hole？把時間盒設更緊、鬧鐘設更密。你老是只讀不跑？在階段 4 之後強制插一個「必須驗證至少一個假設才能繼續」的閘門。**SOP 是給你自己的護欄，該補在你最常摔的地方。**

一份好的個人 SOP 是**活的**：每攻堅完一個專案，回看 journal，問「這次哪一步浪費了時間、哪一步救了我」，然後改 SOP。跑個五六個專案，你會收斂出一份**你自己的、比這章這份更適合你**的版本。那份才是你真正的畢業證書。

## 踩雷集錦

1. **錯誤直覺**：「SOP 就是每次都要照著一字不差跑完六階段。」→ **正確認識**：SOP 是**預設路徑 + fallback**，不是流水線。小任務可以三階段解決、某階段可以幾分鐘帶過。它的價值是「卡住時知道下一步做什麼」，不是「強迫你做滿所有步驟」。照本宣科跑完六階段去改一個 typo，是另一種完美主義。

2. **錯誤直覺**：「時間盒到了但我快懂了，再追一下沒關係。」→ **正確認識**：「快懂了」是 rabbit-hole 最常見的自我欺騙。時間盒的意義正是在你「感覺快懂了」時強制你抬頭確認「這跟任務有關嗎」。多數「再追一下」會變成再追一小時。到點就停、記 TODO，是紀律不是妥協。

3. **錯誤直覺**：「工具動用順序不重要，順手用哪個就哪個。」→ **正確認識**：順序**就是效率**。一開始就開 gdb 硬追（跳過 rg 撒網）會慢十倍；全程只用 rg（不動用 clangd）會被同名符號淹死。「廣而快 → 窄而精、靜態 → 動態」這條順序是本課壓縮出的精華，內化它。

4. **錯誤直覺**：「journal 是給別人看的文件，要寫得漂亮完整。」→ **正確認識**：journal 是**給你自己**的工作記憶外接硬碟，草、亂、半句話都行。它的讀者是「三天後忘光的你」。追求漂亮反而讓你懶得寫——降低門檻、隨手記，才是它有用的前提。

5. **錯誤直覺**：「別人的 SOP 更完整，直接用別人的。」→ **正確認識**：SOP 的威力來自「貼合你的生態、目標、弱點」。抄一份不適配你的 SOP，跟不用 SOP 一樣沒效。這章這份是**起點**，不是終點——用它跑幾次，然後改成你的。

## 動手練習

1. **抄模板、填空跑一遍**：把上面的 reading journal 模板複製到你的筆記工具，挑一個你半熟的專案，照六階段跑一次填滿。感受「有結構」跟「憑感覺讀」的差別。

2. **客製你的工具順序**：拿你最常讀的那個語言/生態，把「工具動用順序」那張圖改寫成適合它的版本（例如 Python 專案該把哪個工具往前移、哪個拿掉）。

3. **綁定你的反模式**：翻出 Ch 37 練習 1 的自我盤點（你的高危反模式），在你的 SOP 裡對每一條加一道護欄（時間盒？強制驗證閘門？journal 必填欄？）。

4. **限時實跑**：挑一個中型陌生專案，嚴格按時間盒跑階段 0-3（界定→偵察→建圖→定位），設鬧鐘。四階段內你應該能指著某幾個函式說「我要改的在這」。做不到的話，回看是哪個階段超時、為什麼。

## 本章重點整理

- SOP 的價值是「卡住時給你一條預設路徑和 fallback」，不是強迫照本宣科。
- 六階段：界定任務 → 偵察 → 建圖 → 定位 → 追蹤 → 驗證 → 改動，每階段有明確產出和時間盒；沒產出不進下一階段。
- 工具動用順序是效率核心：`rg → ctags/cscope → clangd → gdb/trace`，廣而快到窄而精、靜態到動態。
- 決策樹處理三大岔路：讀多深、靜態不確定怎麼辦、要不要展開 indirection、時間盒到了怎麼辦。
- reading journal 模板把「流程檢查」和「理解外化」合一，直接抄走客製。
- 最重要的是**客製化**：按語言、按目標、按你自己的弱點調——跑五六個專案後收斂出你自己的版本，那才是畢業證書。
