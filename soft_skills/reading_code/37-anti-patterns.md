# Ch 37 — 常見誤區與反模式

> **目標**：把整門課「不要做的事」集中成一張黑名單。前面 37 章教你「該怎麼攻堅」，這一章反過來——列出讀碼者最常掉進去的坑，每一個都給「反模式 → 為什麼害人 → 正確做法」，並連回教你正解的那一章。讀完你手上有一份 anti-pattern checklist：卡住的時候拿出來對，十有八九是踩了其中一條。

## 為什麼要專門講反模式？

你已經學過一整套方法論。但方法論的問題是：**知道正確做法，不等於不會做錯事。** 錯誤的讀碼習慣多半是「預設值」——是你沒學方法之前的本能反應，壓力一大就會退回去。

逆向工程界有句話：卡關的人不是不夠聰明，是**用錯策略而不自知**。讀 source 完全一樣。你盯著螢幕兩小時毫無進展，通常不是那段 code 真的難到爆，而是你正在做一件根本不該做的事——線性硬讀、深潛無關細節、盲信一個騙人的註解。你感覺不到自己在犯錯，因為每一步「看起來」都在前進。

所以這章的價值不是教新東西，是**幫你在犯錯的當下認出來**。我們把最常見的反模式做成一份對照表，每條都是真實會發生、代價昂貴、而且**有明確解藥**的。把它們背起來，卡住時逐條自檢。

### 反模式為什麼這麼難根除？

在展開清單之前，先講清楚一件事：這些反模式不是「笨」造成的，聰明人一樣天天犯。原因有三，理解它們你才不會覺得「我知道啊怎麼還犯」而自責：

- **它們短期有正向回饋**。線性讀「感覺」在前進（游標一直往下）、rabbit-hole「感覺」在學東西（真的懂了 endianness）、乾讀「感覺」在掌控（不用面對「我猜錯了」）。壞策略騙你的方式，是給你即時的、虛假的進展感。真正的進展（離目標更近）反而是延遲、抽象、難以感知的。
- **它們是壓力下的預設值**。deadline 逼近、卡關焦慮時，人的認知會退化到最省力的模式——而最省力的往往正是這些反模式。方法論是「刻意的」，反模式是「本能的」，壓力一大，本能就接管。
- **它們自我隱藏**。你在 rabbit-hole 裡的時候，感覺不到自己在 rabbit-hole——你覺得自己在「深入研究」。反模式最陰險的地方是**它們在當下看起來都很合理**，只有事後或旁觀者才看得清。

這就是為什麼「知道」不夠，要「當場認出」——而當場認出需要一份清單放在手邊。下面就是那份清單。

## 反模式 1：線性讀（從第一行讀到最後）

**症狀**：打開 `server.c`，游標停在第 1 行，開始一行一行往下讀，指望讀到最後就懂了。三千行之後你腦子一片漿糊，記不得前面看過什麼。

**為什麼害人**：source code 不是小說。它的**書寫順序跟執行順序、跟重要性都無關**。檔案開頭往往是一堆 include、全域變數宣告、工具函式——全是雜訊。真正的主線（entry point、主迴圈、核心資料結構）散在各處，靠 `#include` 和函式呼叫串起來，不是靠行號順序。線性讀等於拿到一本字典從 A 讀到 Z 想搞懂一個語言：技術上可行，實際上白痴。

**正確做法**：分閱讀模式（Ch 4）。**掃讀**（skim）建立全局印象——看檔案結構、函式名、註解標題，不進函式體。**精讀**（study）只對你鎖定的關鍵函式做。**追蹤**（trace）沿著呼叫鏈或 data flow 走，跟著程式的邏輯順序而非行號順序。永遠先問「我現在要建立全局、還是搞懂一個點、還是追一條路徑」，再選對應模式。

具體對照：redis 的 `server.c` 有近七千行。線性讀你會從第 1 行的 `#include` 開始，讀幾百行工具函式後才碰到 `main`（在 6917 行）——而 `main` 裡真正重要的是那一句 `aeMain(server.el)`（主迴圈）。正確的做法是直接 `rg -n "int main" src/server.c` 跳過去、掃 `main` 的結構找到主迴圈、再從主迴圈追下去。**你關心的順序是執行順序，不是行號順序。** → [Ch 4 三種閱讀模式](./04-three-reading-modes.md)

## 反模式 2：過早深潛（沒建全局就鑽細節）

**症狀**：第一次打開專案，你看到 `dictAdd()` 覺得「這看起來很核心」，一頭鑽進 hash table 的 rehash 實作，花 40 分鐘搞懂漸進式 rehash 的每個細節——然後發現你連這個 dict 是給誰用的、在整個系統哪個位置都不知道。

**為什麼害人**：沒有全局地圖時，你**無法判斷一個細節重不重要**。你可能把 20% 的精華跟 80% 的邊角料花同樣力氣讀，甚至反過來。更糟的是，孤立地讀一個函式，你缺少上下文（它的 caller 保證了什麼前提？它的回傳給誰用？），理解會是錯的或殘缺的。

**正確做法**：先偵察、再建圖、最後才深潛。Ch 5 的 60 分鐘偵察逼你先看規模、目錄結構、README、entry point——建立「這專案大概長怎樣」的骨架。Ch 7 教你把骨架畫成架構地圖。**有了地圖，你才知道哪個細節值得深潛。** 順序是不可逆的：地圖 → 定位 → 深潛。→ [Ch 5 第一次接觸](./05-first-contact-recon.md)、[Ch 7 建立架構地圖](./07-building-architecture-map.md)

## 反模式 3：rabbit-hole（追一個細節追到出不來）

**症狀**：你在追 `LPUSH` 怎麼存資料，追到 listpack 編碼，發現 listpack 用了一種變長整數編碼，於是去研究那個編碼格式，然後發現它跟 CPU 的位元組序有關，於是去查 redis 怎麼處理 endianness……兩小時後，你對 endianness 瞭若指掌，但完全忘了你本來想搞懂 `LPUSH`。

**為什麼害人**：codebase 的細節是**無底洞**。每個函式都呼叫別的函式，每個資料結構都有它的實作細節，你可以無限往下追。「順著好奇心追」感覺像在學習，其實是**失去目標的漫遊**。你的 working memory 被無關細節塞滿，離原本的問題越來越遠。這是新手跟老手差最多的地方——老手也會好奇，但他們**知道什麼時候該把好奇心關掉**。

**正確做法**：兩個武器。一是**假設驅動**（Ch 10）：進任何一個函式前，先寫下「我期待這裡做 X，我要驗證的是 Y」。一旦當前的探索跟 Y 無關，立刻停。二是**時間盒**：給每條追蹤設上限（例如 15 分鐘），時間到就強制回到主線，把岔路記成 TODO（「listpack 的 varint 編碼——之後有需要再看」）留給筆記。**目標感是解藥**：你追的每一步都要能回答「這幫我離『搞懂 LPUSH』更近了嗎」。→ [Ch 10 假設驅動讀碼](./10-hypothesis-driven-reading.md)

## 反模式 4：盲信註解與命名

**症狀**：函式叫 `isValidUser()`，你就假設它驗證使用者合法性，繼續往下讀。註解寫 `// this is thread-safe`，你就當它 thread-safe。結果 bug 就藏在「名字/註解說的」跟「code 實際做的」之間的落差。

**為什麼害人**：註解和命名是**人寫的，會過期、會撒謊、會誤導**。code 改了，註解沒跟著改，這是所有專案的常態。名字取於三年前，功能早就長歪了。爛 code（Ch 30 的主題）尤其如此——`temp`、`data2`、`handleStuff()` 這種名字給你的資訊是負的。你**信了一個騙你的訊號**，理解從一開始就錯，後面全盤皆錯，還很難察覺，因為你「有一個看似合理的解釋」。

**正確做法**：**以 code 的實際行為為唯一真相來源**（Ch 30）。註解和命名當「線索/假設」看待，不當「事實」。可疑時就驗證——讀實作、跑起來看、用 debugger 確認。把註解讀成「作者當時的意圖」（有價值，說明為什麼），但別把它當「現在的行為」（那要看 code）。老手讀 code 時對名字有一種健康的不信任：名字告訴你「這裡大概想幹嘛」，實作告訴你「它真的幹了嘛」。→ [Ch 30 讀爛 code](./30-reading-bad-code.md)

## 反模式 5：只讀不跑（腦內模擬執行）

**症狀**：你盯著一段有五層 `if`、兩個 callback、一個 macro 展開的 code，在腦子裡模擬「如果輸入是這樣，它會走這條路……應該吧？」你推論出一個結論，然後基於這個沒驗證過的結論繼續讀。

**為什麼害人**：人腦的「執行模擬器」爛透了。你會**默默假設一個 `if` 的走向、漏掉一個 early return、猜錯一個 macro 展開、忽略一個並發交錯**。靜態閱讀複雜控制流的錯誤率高得驚人，而且你的錯誤會**沉默地累積**——沒有任何東西告訴你「你剛才猜錯了」。你以為讀懂了，其實建了一個錯誤的心智模型。

**正確做法**：**能跑就跑，讓機器告訴你真相**。Ch 18 的 debugger-driven reading——在你猜的那行下斷點，跑起來看它真的走哪條、變數真的是什麼值。Ch 19 的 tracing——用 `strace`/`ltrace`/`uftrace` 看實際的呼叫序列。一次真實的執行勝過一小時的腦內推理。我們在 Ch 39 會示範：對著 redis 下斷點看 `LPUSH` 真的呼叫了哪條轉換函式、list 長度真的是多少——五分鐘的 gdb 抵得上半天的乾讀。**猜測要用執行來釘死。** → [Ch 18 debugger-driven reading](./18-debugger-driven-reading.md)、[Ch 19 tracing 讀執行](./19-tracing-execution.md)

## 反模式 6：不用工具硬讀（Ctrl+F 逐檔翻）

**症狀**：想知道某個函式誰呼叫的，你打開一個又一個檔案，用編輯器的 Ctrl+F 搜函式名，人工翻結果。想知道一個 struct 欄位在哪被改，你 grep 一下欄位名，得到 300 個結果，然後開始肉眼過濾。

**為什麼害人**：這是把「找」和「連」——讀碼真正的瓶頸（Ch 0 講過）——用最慢的方式做。反查呼叫者、跨檔跳定義、看呼叫圖，這些都有**專門的工具能秒級回答**，你卻用滑鼠和肉眼幹幾百次。一天讀不完一個模組，不是因為 code 難，是因為你把時間全花在人工檢索上。而且人工檢索**會漏**——300 個 grep 結果你肉眼過濾，一定會看漏關鍵那個。

**正確做法**：把每一種「找」變成一條指令（Ch 12-16）。`ripgrep` 做快速文字定位（Ch 12）；`ctags` 跳定義、`cscope`/`global` 反查呼叫者（Ch 14）；`clangd`（LSP）做語意精準跳轉（Ch 13）；`tree-sitter` 做結構化查詢（Ch 15）；靜態分析工具畫呼叫圖（Ch 16）。策略是分層：**ripgrep 快速定位 → ctags/cscope 建骨架 → clangd 精準確認**。

一個殺手級對照：「誰呼叫了 redis 的事件迴圈 `aeMain`？」——這是「反查呼叫者」，肉眼 grep 會漏、會被同名干擾。`cscope -d -L -3 aeMain` 一條指令，秒級告訴你 `server.c:7251` 的 `aeMain(server.el)` 就是伺服器心臟。人工翻十萬行找這個，你要翻半天還不一定找對。工具不是選配，是讓你比別人快一個數量級的關鍵。→ [Ch 12 grep/ripgrep 的藝術](./12-grep-ripgrep-art.md) 起整個 Part 3

## 反模式 7：不做筆記（同一段 code 讀懂又忘）

**症狀**：週一你花一小時搞懂了 redis 的 `robj` 引用計數怎麼運作，很有成就感。週四你要碰另一個功能，又遇到 `robj`，發現全忘了，只好**再讀一次**。這種重複勞動吃掉你大量時間，而你甚至沒意識到。

**為什麼害人**：人的 long-term memory 對「一次性讀懂的複雜機制」保留率極低。**理解是易失性的**——不外化就會蒸發。更關鍵的是，讀大型 codebase 的理解是**逐步累積**的：你今天搞懂 A，明天要靠 A 去理解 B。如果 A 沒記下來，明天你得先重建 A 才能碰 B，效率崩潰。腦中讀不算讀，因為腦記不住。

**正確做法**：**邊讀邊外化**（Ch 35）。不是讀完再寫報告，是**讀的當下**就把理解倒出來：一句話記下「這函式做什麼」、畫一個 data flow 箭頭、寫下「我猜這裡是 X（待驗證）」。筆記、圖、心智模型三種形式互補。外化還有個副作用——**寫的時候你會發現自己其實沒懂**（費曼測試的前奏，Ch 36）。筆記是你對抗遺忘、也是對抗「假懂」的武器。→ [Ch 35 外化理解](./35-externalizing-understanding.md)

## 反模式 8：完美主義（非懂 100% 不罷休）

**症狀**：你的任務是「改掉 `OBJECT ENCODING` 的一個判斷」，但你決定「要改它得先徹底搞懂整個 object system」，於是開始啃每一種編碼的實作、每一個轉換路徑、記憶體佈局……一週過去，你什麼都沒改，但「學到很多」。

**為什麼害人**：codebase 大到你**不可能全懂，也不需要全懂**。追求 100% 理解在經濟上是災難——邊際效益遞減得極快。你的任務通常只需要理解相關的那條路徑（Ch 11 的核心：從 50 萬行收斂到你要改的 200 行）。把力氣平均撒在整個系統上，等於在你不需要的地方過度投資，在你需要的地方投資不足。而且「等我全懂再動手」是**拖延的完美藉口**——它讓不作為看起來很負責任。

**正確做法**：**目標導向，夠用就走**（Ch 11）。先明確「我這次要達成什麼」（修一個 bug？加一個功能？理解一個機制？），然後只讀達成它所需的最小範圍。判準是「我能不能安全地做出改動並驗證」，不是「我懂不懂全部」。對任務外的部分，維持一個「黑盒 + 已知介面」的理解就夠——知道它輸入輸出、不用知道內部。**能改對一行，勝過懂全不敢動。** → [Ch 11 收斂到你要改的 200 行](./11-narrowing-to-change-site.md)

## 反模式 9：忽略 build system 與歷史

**症狀**：你讀到一段 `#ifdef HAVE_ATOMIC` 包起來的 code，直接假設它有效，卻不知道在當前的 build 設定下它根本沒被編進去——你讀了一段死 code。或者你看到一個奇怪的、明顯繞路的實作，百思不得其解，其實 `git log` 一查就知道那是為了修某個 bug 加的 workaround。

**為什麼害人**：source code 不是孤立存在的。**它怎麼被編（build system）決定了哪些 code 真的生效**——`#ifdef`、平台分支、生成的檔案，光讀 source 看不出來。**它為什麼長這樣（歷史）藏在 commit 裡**——每段醜 code 背後常有一個 commit message 解釋原委。忽略這兩者，你會（a）讀死 code、（b）誤解意圖、（c）對著一個「明明可以更簡單」的實作困惑半天，其實它有你不知道的理由。

**正確做法**：把 build 和歷史當一等公民。Ch 21 教你讀 build system——搞清楚哪些檔案真的參與編譯、哪些 flag 開了、生成檔從哪來。你的 `compile_commands.json`（Ch 0）本身就是 build 資訊的結晶。Ch 17 教你把 git 當考古工具——`git blame` 查某行的來歷、`git log -S` 追某個字串何時引入、讀 commit message 找「為什麼」。**當一段 code 讓你困惑時，先問「它怎麼編的」和「它從哪來的」，往往比硬讀更快解惑。** → [Ch 21 讀懂 build system](./21-reading-build-systems.md)、[Ch 17 git 當考古工具](./17-git-as-archaeology.md)

## 反模式 10：抽象潔癖（見 indirection 就追到底）

**症狀**：你追一個呼叫，遇到一個函式指標／virtual method／回呼註冊表，於是你停下來，非要搞清楚「這個指標在執行期到底指向哪個實作」——把所有可能的實作全找出來、全讀一遍，才肯繼續。

**為什麼害人**：大型系統充滿 indirection（Ch 23 的主題）——函式指標、vtable、plugin 註冊、事件分派。這些是**設計上的解耦**，它們的存在就是為了讓你**不需要**在讀 caller 時知道具體 callee。每遇到一層 indirection 就展開所有實作，你會指數爆炸——一個有 10 個實作的介面，你追進去就多讀 10 倍的 code，其中 9 個跟你的路徑無關。

**正確做法**：**按需展開，不見獵心喜**（Ch 23）。遇到 indirection 時先問「我這條路徑上，它實際指向哪一個？」——用動態手段（gdb 斷點看實際跳去哪，Ch 18）比靜態窮舉快得多、準得多。如果暫時不需要知道具體實作，就把這層 indirection 當黑盒（「這裡會分派到某個 handler，先繼續」），記下來，需要時再回頭。**indirection 是讓你少讀的機制，別把它變成讓你多讀的理由。** → [Ch 23 讀懂 indirection](./23-reading-indirection.md)

## 反模式 11：一次讀太多（working memory 爆掉）

**症狀**：為了搞懂一個功能，你同時開了 20 個檔案的分頁，在它們之間瘋狂切換，試圖「一次把整條鏈裝進腦子」。切到第 8 個檔案時，你已經忘了第 2 個檔案在幹嘛。

**為什麼害人**：人的 working memory 只能同時抓住約 4-7 個 chunk（Ch 3 講過的認知科學基礎）。一次塞 20 個未消化的檔案，遠超容量，結果是**每個都記不牢，切換成本吃掉所有進展**。你感覺很忙、很努力，但實際吞吐量趨近於零——這是認知過載的典型表現。

**正確做法**：**chunking + 外化，分批消化**（Ch 3、Ch 35）。一次只深追一條線，把已經理解的部分**壓縮成一個 chunk**（「這三個函式合起來就是『解析請求』，記成一個盒子」）再往下。把中間結論寫進筆記（Ch 35），騰空 working memory 去裝下一段。老手看起來能「同時理解很多」，其實是他們把大量細節壓成了少數幾個高階 chunk，佔用的槽位很少。**降低同時在腦中的活動項數，是可持續讀碼的關鍵。** → [Ch 3 程式設計師怎麼理解程式](./03-how-programmers-understand-code.md)

## 反模式 12：迷信 AI 產出

**症狀**：你把一段看不懂的 code 貼給 LLM，它給你一段流暢的解釋，你**照單全收**，基於它繼續往下。但那段解釋裡有一個關鍵細節是 AI 幻覺出來的——它把一個 `xor` 說成 `or`，或者編了一個根本不存在的函式行為。

**為什麼害人**：LLM 讀碼有**兩個致命弱點**：它會**自信地胡說**（幻覺），而且它**看不到你的完整上下文**（它不知道你這個版本、這個 build 設定、這個 caller 保證的前提）。它的解釋讀起來永遠很順、很有說服力——這正是危險所在。你失去戒心，把一個可能錯的解釋當事實，錯誤又一次沉默地進入你的心智模型。

**正確做法**：**AI 當助手，不當權威**（Ch 20）。它擅長的：快速給一段陌生 code 的「初步假設」、解釋不熟的語言慣例、生成搜尋關鍵字、總結一個大檔案的結構。但它給的每一個**具體斷言都要用 code/執行去驗證**——把 AI 的輸出當成「一個需要驗證的假設」（接回 Ch 10 假設驅動），而非結論。用它加速「產生假設」，用你的工具（rg/gdb/trace）完成「驗證假設」。**它是加速器，不是真相來源。** → [Ch 20 AI 輔助讀碼](./20-ai-assisted-reading.md)

## 反模式之間怎麼互相餵養

前面十二條是「一個個」列的，但真實攻堅裡它們**成串發作**，一個觸發下一個。認清這些連鎖，你抓一個就能扯出一串：

```
 不做筆記(7) ──逼你──▶ 一次讀太多(11) ──導致──▶ 認知過載
     │                                              │
   (讀懂又忘，想「一口氣讀完免得忘」)              (working memory 爆)
     
 過早深潛(2) ──引發──▶ rabbit-hole(3) ──強化──▶ 抽象潔癖(10)
     │                     │                        │
  (沒地圖亂鑽)         (追到忘了目標)          (見 indirection 就窮舉)

 完美主義(8) ──驅動──▶ 抽象潔癖(10) + 忽略 build/歷史(9)
     │                （非把每層每個 ifdef 都搞懂不可）

 只讀不跑(5) ──放大──▶ 盲信註解(4) + 迷信 AI(12)
     │              （沒有執行當事實檢查，就只能信文字）
```

最核心的三個「病灶反模式」——**過早深潛(2)、只讀不跑(5)、不做筆記(7)**——各自會拖出一整串。所以攻堅時如果只能記三件事：**先建全局再深潛、能跑就跑、邊讀邊記**。守住這三條，剩下九條大半自動避開。

## 踩雷集錦

這章本身就是一份踩雷清單，但這裡補幾個「元層次」的坑——關於這些反模式本身的誤解：

1. **錯誤直覺**：「這些反模式我都知道了，不會犯。」→ **正確認識**：知道跟做到差很遠。反模式是壓力下的**預設行為**，deadline 逼近、卡關焦慮時，你會不自覺退回線性讀、退回硬猜。解藥不是「知道」，是把 checklist 放在手邊，卡住時**強制自檢**——「我現在是不是在 rabbit-hole？我是不是只讀不跑？」

2. **錯誤直覺**：「反模式一定是絕對錯的，永遠不能做。」→ **正確認識**：它們是**預設下的壞習慣**，不是絕對禁令。線性讀一個 50 行的小工具檔完全 OK；某些情況你就是得追完一層 indirection。判準是**成本效益跟目標感**：這麼做有沒有讓你更接近目標？還是純粹出於慣性或逃避？反模式的本質是「在不該用的場合用了某策略」，不是策略本身邪惡。

3. **錯誤直覺**：「我一次只會犯一個反模式。」→ **正確認識**：它們**成串出現、互相餵養**。過早深潛（2）常引發 rabbit-hole（3）；不做筆記（7）逼你一次讀太多（11）想「一口氣讀完免得忘」；完美主義（8）驅動你窮舉每一層 indirection（10）。認出一個，往往能順藤扯出一整串。

4. **錯誤直覺**：「只讀不跑是因為我懶得配環境。」→ **正確認識**：更常見的真實原因是**心理慣性**——乾讀讓你感覺「在掌控」，跑起來要面對「我猜錯了」的難堪。但正是那個難堪最有價值。克服它，你的讀碼準確率會跳一個檔次。

## 動手練習

1. **反模式自我盤點**：回想你上一次讀一個陌生 codebase（工作專案、開源、CTF 都行）。對著這 12 條，誠實勾出你當時犯了哪幾條。多數人會勾中 3-5 條——這就是你個人的「高危反模式」。

2. **抓現行犯**：下次讀碼時，設一個 25 分鐘計時器，時間到就暫停問自己：「剛才這 25 分鐘，我有沒有在做這 12 條裡的任何一條？」連做幾輪，你會開始在犯錯的**當下**（而非事後）察覺。

3. **配對解藥**：把 12 條反模式的「正確做法」欄，跟它連回的章節配對，回去翻那一章的核心工具/方法。確認你不只知道「別做什麼」，也真的會「該做什麼」。

4. **（進階）給同事做 code walk**：找個人，讓他看你讀一段陌生 code 的過程並喊停——「你剛才那個追下去，跟你的目標有關嗎？」外部視角最容易抓到你自己看不見的反模式。

## 本章重點整理

- 反模式不是「不知道正解」，是「壓力下退回預設的壞習慣」——解藥是把 checklist 放手邊、卡住時強制自檢。
- 12 條核心反模式，每條都有明確解藥並連回對應章節：線性讀→分模式、過早深潛→先偵察、rabbit-hole→假設+時間盒、盲信註解→以行為為準、只讀不跑→debugger/trace、硬讀→工具鏈、不記筆記→外化、完美主義→夠用就走、忽略 build/歷史→Ch21/17、抽象潔癖→按需展開、讀太多→chunking、迷信 AI→當助手不當權威。
- 反模式常成串出現、互相餵養——認出一個往往扯出一整串。
- 它們是「錯場合用錯策略」，不是絕對禁令；判準永遠是**成本效益與目標感**。
