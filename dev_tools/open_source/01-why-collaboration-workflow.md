# Ch 1 — 為什麼需要協作流程

> **目標**：建立貫穿全課的心智模型。你已經會 commit/push/pull，但那是「單機 git」。這章說清楚：多人一起寫同一個專案時，會出現哪些單機時根本不存在的問題，以及人類發明了哪些流程（branch、PR、review）來馴服它們。

> **環境**：概念為主，git 2.40+、GitHub。

## 為什麼先談「問題」而不是「指令」

你大可以直接背「fork、開 branch、發 PR」這套流程。但只要不懂它在解決什麼問題，你就會：在不該 rebase 的時候 rebase、force-push 蓋掉同事的 commit、不知道為什麼要開 branch 而不是直接 push main。

這章不教任何新指令。它教的是「為什麼有這些流程」——懂了問題，流程就從一堆要背的規矩，變成你能自己推導的常識。

## 先建立直覺：一個人 vs 一群人

想像寫一本書。

**一個人寫**：你想到哪寫到哪，改錯了自己負責，版本你自己記得。這是你現在的 git——`commit` 存檔、`push` 備份到雲端。

**十個人寫同一本書**：災難立刻浮現。
- 兩個人同時改第三章，誰的版本算數？
- 有人偷偷把第五章整段刪了，你怎麼知道、怎麼擋？
- 新人想加一段，但他寫得好不好，誰來把關？
- 大家都往同一份檔案塞東西，怎麼不互相覆蓋？

```
   單機 git（你現在）            多人協作（這門課）
   ┌──────────┐                ┌──────────┐  ┌──────────┐  ┌──────────┐
   │   你     │                │   你     │  │  同事 A  │  │  同事 B  │
   │ commit   │                │          │  │          │  │          │
   │ push     │                └────┬─────┘  └────┬─────┘  └────┬─────┘
   └────┬─────┘                     │ 同時改同一個專案            │
        ▼                           ▼            ▼               ▼
   ┌──────────┐                ┌────────────────────────────────────┐
   │  雲端備份 │                │  共享的專案（誰能改？怎麼不撞？     │
   └──────────┘                │   壞的改動怎麼擋？）                 │
                               └────────────────────────────────────┘
```

協作流程，就是人類為了讓「右邊那張圖」不變成災難而發明的一整套規矩。

## 多人世界的四個核心問題

### 問題一：併發修改（誰改了什麼、會不會撞）

十個人同時在改，你 `push` 之前同事可能已經 `push` 了。git 的 `push` 預設**拒絕**覆蓋別人的 commit（non-fast-forward rejected）——這是好事，它保護你不會無聲蓋掉別人的工作。但這也意味著你得學會：先 `pull` 整合別人的改動、解決衝突、再 push。單機時你從沒遇過這個。

### 問題二：誰能改主線（信任與權限）

一個開源專案，主線（main 分支）是發布給全世界用的。**不能**讓任何人隨便 push 到 main——否則一個惡意或粗心的 commit 就毀了整個專案。所以協作的核心是：**main 受保護，改動要先經過某種審查才能進去。** 這就是 Pull Request 的存在理由（Ch 10）。

### 問題三：品質把關（review）

新人加的一段 code 可能有 bug、不符風格、漏了測試。在進主線前，要有人看過、確認 OK——這就是 **code review**。它不是不信任，是「四隻眼睛比兩隻眼睛好」的工程紀律。

### 問題四：隔離未完成的工作（branch）

你做一個新功能要三天，這三天 main 還在被別人更新、還在發布。你的半成品不能丟進 main（會壞掉發布），又不能不存檔。解法：**開一條 branch**，在自己的分支上慢慢做，做完再整批合進去。branch 是「隔離區」，讓未完成的工作不污染主線。

## 解法的全貌：協作流程地圖

這四個問題，催生了一套標準流程。先看全貌，後面章節逐塊放大：

```
   1. main 受保護         ← 沒人能直接 push（問題二）
        │
   2. 開 branch 做你的事   ← 隔離未完成工作（問題四）  Ch 3
        │
   3. push 你的 branch
        │
   4. 開 Pull Request      ← 「請把我的 branch 合進 main」（問題二）Ch 10
        │
   5. CI 自動檢查          ← 機器把關：測試過了嗎、lint 過了嗎  Ch 14
        │
   6. Code Review          ← 人把關：這 code 可以嗎（問題三）  Ch 13,29
        │
   7. 解決衝突（若有）      ← 整合別人的改動（問題一）  Ch 8
        │
   8. Merge 進 main        ← 通過審查，正式進主線
```

整門課其實就是把這 8 步的每一步講透——加上做這些事需要的中階 git（branch/merge/rebase/衝突，Part 2）、跟人溝通的軟實力（Part 4）、和反過來當審查者/維護者的視角（Part 6）。

你已經會的 commit/push/pull，只是第 3 步的零件。協作是把它們組織成一套**社會流程**——一半是技術，一半是人。

## 為什麼是「分散式」讓這一切成立

你可能聽過 git 是「分散式版本控制（DVCS）」。這個設計是協作能運作的根本，值得理解。

**集中式（舊時代，如 SVN）**：只有一個中央伺服器有完整歷史，你的本機只是一份工作副本。要 commit 必須連上中央伺服器。

**分散式（git）**：**每個人的本機都有完整的歷史副本**。你能離線 commit、開 branch、看 log，完全不需要連網。「中央」（GitHub 上的 repo）只是大家約定的「同步點」，技術上它和你本機的 repo 地位平等。

```
   集中式 (SVN)              分散式 (git)
   ┌─────────┐              ┌─────────┐   ┌─────────┐
   │ 中央伺服器│             │  你的    │   │ 同事的   │
   │（唯一歷史）│            │ 完整 repo│   │ 完整 repo│
   └────┬────┘              └────┬────┘   └────┬────┘
        │                       │             │
   ┌────┴────┐                  └──── GitHub ──┘
   │工作副本  │                    （約定的同步點，
   │(沒歷史)  │                     地位和大家平等）
   └─────────┘
```

為什麼這對協作關鍵？因為它讓**每個人都能獨立工作**——你在自己的完整 repo 上開 branch、實驗、commit，完全不影響別人，做好了才推到共享點請求合併。**fork**（Ch 10）就是這個概念的極致：你複製一份完整的 repo 到自己名下，愛怎麼搞怎麼搞，最後用 PR 請原作者拉你的改動。集中式做不到這種「人人有完整副本、各自獨立、最後再整合」的模式。

> 歷史脈絡：git 是 Linus Torvalds 在 2005 年為了 Linux kernel 開發寫的——一個有上千名貢獻者、分散全球、互不信任的超大協作專案。集中式工具撐不住這種規模，所以 git 從第一天就是為「大規模分散式協作」設計的。你學的協作流程，根源都在這。

## 「流程」是社會契約，不是 git 功能

一個重要觀念：**很多協作「規矩」不是 git 強制的，是團隊/社群約定的。**

- git **沒有** Pull Request 這個東西——PR 是 GitHub（平台）加的功能（Ch 10）。
- git **不強制**你開 branch——是團隊約定「不准直接 push main」。
- git **不要求** code review——是工程文化要求的。
- 「commit message 要寫清楚」「branch 要怎麼命名」——都是約定，不是 git 規則。

所以協作有兩個層次：**git/GitHub 提供的機制**（技術），和**團隊/社群選擇怎麼用它的約定**（流程）。同樣的 git，不同團隊有不同流程（Ch 22 會看 GitHub Flow vs Git Flow vs trunk-based）。理解「哪些是死規矩、哪些是團隊選擇」，你進新團隊/新專案時才知道要問什麼、能改什麼。

## 踩雷集錦

1. **以為協作就是「多人一起 push main」**：那是災難。協作的核心恰恰是「**不**直接改主線」——透過 branch + PR + review 把關。
2. **把 PR 當成 git 功能**：PR 是 GitHub/GitLab 等平台的功能，不是 git 本身。純 git 的對應概念是 `git request-pull`（幾乎沒人用）。Ch 10 細談。
3. **不懂為什麼 push 被拒絕**：`push` 被拒（non-fast-forward）不是 bug，是 git 保護你不覆蓋別人的 commit。要先整合別人的改動（pull / fetch + merge/rebase）。
4. **以為所有規矩都是 git 強制的**：branch 命名、commit 格式、要不要 review——多半是團隊約定。進新專案先讀它的 CONTRIBUTING（Ch 16）。
5. **單機習慣帶進協作**：直接在 main 上 commit、push、不開 branch——單機沒事，協作會撞車、會被 review 流程擋下、會惹同事。

## 進階：再往深一層

- **為什麼 git 的 commit 有 parent**：每個 commit 指向它的前一個（parent），形成有向無環圖（DAG）。協作的 merge/rebase 本質都是在操作這個 DAG。深挖見 [dev_tools/git](../git/README.md) 的 git objects 章。
- **「中央」是約定不是必然**：技術上你可以用任何 repo 當同步點，甚至直接從同事的 repo `pull`（去中心化協作）。GitHub 只是最流行的約定中心。
- **trunk-based vs feature-branch 的哲學差異**：有些團隊極度反對長命 branch（主張頻繁合進 main），有些重度依賴 branch。這是工程文化之爭，Ch 22 展開。
- **monorepo vs polyrepo**：一個大 repo 放所有專案 vs 每個專案一個 repo——協作模式差很多（Ch 35）。
- **AI 時代的協作**：大量 AI 生成的 PR 正在衝擊開源（維護者被淹沒），這正在改變貢獻禮儀與審查流程。Ch 20、31 會談。

## 動手練習

1. 不開 branch，直接在某 repo 的 main 上做兩個本機 commit；另一個 clone（模擬同事）也在 main 做 commit 並先 push。換你 push 時觀察 `non-fast-forward` 被拒——親身體驗「問題一：併發修改」。
2. 對著本章的「協作流程地圖」8 步，說出每一步在解決四個核心問題中的哪一個。
3. 找一個你常用的開源專案（如某 npm/pip 套件），看它的 GitHub：main 能不能直接 push（看有沒有 protected branch 標示）、它怎麼接受貢獻（有沒有 CONTRIBUTING）、最近的 PR 長怎樣。觀察真實的協作流程。
4. 想一個你「一個人寫」時從沒遇過、但「多人寫」一定會遇到的問題，對照本章四個核心問題歸類。

## 本章重點整理

- 單機 git（commit/push/pull）只是協作的零件；協作是把它們組織成一套社會流程。
- 多人世界的四個核心問題：併發修改、誰能改主線、品質把關、隔離未完成工作。
- 解法地圖：main 受保護 → 開 branch → push → PR → CI → review → 解衝突 → merge。
- git 是分散式的（人人有完整 repo），這讓「各自獨立工作、最後整合」成為可能——fork/PR 的根基。
- 很多「規矩」是團隊/社群約定，不是 git 強制；分清死規矩與團隊選擇。
