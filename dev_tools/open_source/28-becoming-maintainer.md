# Ch 28 — 從貢獻者到維護者

> **目標**：切換到維護者視角。理解維護者的職責與貢獻者完全不同、心態怎麼轉變、維護者真正的工作是什麼（多半不是寫 code）、以及「擁有一個專案」意味著什麼責任。這是 Part 6 的開場——之後幾章是維護者的具體技能（審 PR、triage、release、社群、安全）。

> **環境**：概念為主。前置：整個 Part 1-5（你要先當過貢獻者，才懂維護者在想什麼）。

## 為什麼要學維護者視角

你可能想：「我只是想貢獻，幹嘛學當維護者？」三個理由：

1. **懂維護者，你的貢獻更好**：知道維護者怎麼想、在意什麼、被什麼困擾，你的 PR/issue 會更貼心、更容易被接受（Part 4 一直在說「換位思考」，這章把那個「位」講透）。
2. **你遲早會是維護者**：自己開專案、在公司負責某個 repo、成為某開源專案的 committer——你會從「貢獻別人的」變成「別人貢獻你的」。
3. **這是不同的技能**：維護者的工作和貢獻者**完全不同**——多半不是寫 code，而是審、決策、溝通、規劃、說不。沒準備好，你會被淹沒、burnout。

這章是心態轉換的開場，後面 Ch 29-34 是具體技能。

## 先建立直覺：從「蓋房子」到「當市長」

```
   貢獻者                          維護者
   ─────────                      ─────────
   蓋一間房子（做一個改動）          管理一座城市（照顧整個專案）
   專注自己的 PR                    照顧所有人的 PR + issue + 方向 + 社群
   做完就走                        要長期維護、負責後果
   「我想加這個」                   「這對專案整體好嗎？誰來維護它？」
   寫 code 為主                    審、決策、溝通、規劃為主（寫 code 反而少）
```

最大的心態轉變：**貢獻者想的是「我的改動」，維護者想的是「專案的長期健康」。** 同一個 PR，貢獻者看到「我做的好功能」，維護者看到「這要維護多久？誰維護？符合方向嗎？增加多少複雜度？」。理解這個視角差，是這章的核心。

## 維護者的真正工作（多半不是寫 code）

新手以為維護者就是「最會寫 code 的人」。錯。維護者大部分時間花在**非寫 code 的事**：

```
   維護者的時間花在：
   ├─ 審 PR（Ch 29）——別人的 code，比寫自己的累
   ├─ 回 issue / triage（Ch 30）——分類、回應、關閉、判斷優先序
   ├─ 回答問題 / 支援使用者
   ├─ 決策——要不要加這功能、走什麼方向、拒絕什麼
   ├─ 溝通——和貢獻者、使用者、其他維護者
   ├─ 規劃——roadmap、release（Ch 32）
   ├─ 經營社群（Ch 31）——歡迎新人、處理衝突、找幫手
   ├─ 維運——CI、文件、安全（Ch 34）
   └─ ……寫 code 反而是其中一小塊
```

這顛覆很多人的想像。維護一個熱門專案，光是審 PR、回 issue 就佔掉大部分時間——很多維護者抱怨「我已經好幾個月沒空寫 code 了」。當維護者，你要準備好「主要工作是管理人和決策，不是寫程式」。

## 最難的技能：說「不」

維護者最重要、也最難的技能：**拒絕。**

```
   貢獻者：「我加了一個超酷的功能！」
   維護者要評估：
   - 這符合專案的方向/scope 嗎？
   - 它增加多少複雜度、多少維護負擔？
   - 誰來長期維護它？（貢獻者做完就走，留下你維護）
   - 它值得專案承擔嗎？
   → 常常答案是「不」——即使 code 寫得很好
```

為什麼說不這麼難又這麼重要：

- **每個「yes」都是長期負擔**：加一個功能 = 永遠要維護它、測試它、不能隨便移除（使用者會依賴）。功能只增不減，專案會臃腫到無法維護。
- **scope creep 是專案殺手**：什麼都收，專案失去焦點、變成什麼都做但什麼都做不好的怪物。
- **但說不會傷人**：貢獻者花了時間做 PR，被拒會失望。所以要**有技巧地、尊重地拒絕**（Ch 29）——解釋原因、感謝付出、可能的話指引別的方向。

維護者的核心判斷是「**這值得專案長期承擔嗎？**」——而答案常常是不，即使 code 很好。學會優雅地說不，是維護者的成年禮。

## 「擁有」一個專案的責任

當你成為維護者，你「擁有」這個專案——但這是責任不是特權：

- **使用者依賴你**：人們把你的專案用在他們的產品/工作裡。你的 bug 是他們的問題、你的棄坑是他們的災難。
- **安全責任**（Ch 34）：你的專案有漏洞，是供應鏈風險，影響所有使用者。
- **持續性**：開源最大的問題是維護者 burnout / 棄坑（很多重要專案靠一兩個累壞的人撐著）。你接了，就有某種持續維護的隱性承諾。
- **社群的調性由你定**：你怎麼對待貢獻者，決定社群是友善還是有毒（Ch 31）。

> 認識論誠實 + 重要提醒：**你沒有義務無限付出。** 開源維護者多半無償，burnout 是真實且嚴重的問題（Ch 31）。「擁有專案」的責任不代表你要犧牲自己——設界限、找幫手、必要時誠實說「我沒空維護了」都是正當的。健康的維護者觀念是「負責任地維護或負責任地交棒/封存」，不是「燃燒自己到崩潰」。

## 怎麼成為維護者

兩條路：

### 路徑一：自己開專案

你寫了個有用的東西、開源它——你就是維護者。從第一天起，把它設定成「準備好接受貢獻」（練習 F / Ch 33）。多數人的第一次維護經驗。

### 路徑二：被邀請成為某專案的維護者

持續貢獻一個專案，建立信任和能力，維護者邀你成為 committer / co-maintainer（Ch 37）：

```
   持續貢獻 → 品質穩定 + 得體溝通 → 維護者信任你 →
   開始幫忙審別人的 PR / triage → 被邀請成為 maintainer
```

這是長期投資的回報——不是「我想當維護者」就能當，是「持續貢獻 + 展現責任感和判斷力」自然贏得的。Ch 37 會講這條職涯路徑。

## 貢獻者 vs 維護者：心態對照總表

| 面向 | 貢獻者 | 維護者 |
|---|---|---|
| 關注 | 我的改動 | 專案長期健康 |
| 主要工作 | 寫 code | 審、決策、溝通、規劃 |
| 對功能 | 「我想加」 | 「值得長期承擔嗎？誰維護？」 |
| 對 PR | 希望被接受 | 評估該不該接受 |
| 時間軸 | 做完就走 | 長期負責 |
| 最難的事 | 讓 PR 被接受 | 優雅地說不 |
| 對社群 | 融入 | 塑造 + 經營 |

理解這張表，你既能當更好的貢獻者（懂維護者），也準備好當維護者。

## 踩雷集錦

1. **以為維護者主要是寫 code**：大部分時間在審、回、決策、溝通。準備好「管理 > 寫碼」。
2. **什麼 PR 都收（不會說不）**：scope creep、複雜度爆炸、維護負擔失控。每個 yes 是長期負擔，學會說不。
3. **拒絕得很傷人**：直接「不要」傷貢獻者。要有技巧地拒絕——解釋、感謝、指引（Ch 29）。
4. **燃燒自己到 burnout**：以為「擁有專案」=無限付出。設界限、找幫手、必要時交棒（Ch 31）。
5. **想當維護者卻沒先當好貢獻者**：被邀請當維護者靠的是「持續貢獻 + 信任」，不是宣告「我要當」。
6. **開了專案卻沒準備接受貢獻**：沒 CONTRIBUTING、沒回應 issue/PR——貢獻者來了卻碰壁。開專案就要準備好基礎設施（Ch 33）。
7. **只想到特權不想到責任**：「維護者」是責任（使用者依賴、安全、持續性），不是炫耀的頭銜。

## 進階：再往深一層

- **maintainer 的決策框架**：好的維護者對「要不要加 X」有一致的判準（符合 scope？複雜度？維護成本？有人維護？）——而不是憑心情。把判準寫進 CONTRIBUTING/ROADMAP（Ch 33）讓決策透明。
- **BDFL vs 治理模型**：小專案常是 BDFL（Benevolent Dictator For Life，創辦人說了算）；大專案演化出委員會/治理結構（如 Python 的 steering council）。理解專案怎麼做決策。
- **bus factor**（Ch 31）：專案靠幾個人撐？只有一個維護者 = bus factor 1 = 他消失專案就死。健康的專案要分散維護責任。
- **co-maintainer 的重要性**（Ch 31）：找到能信任的共同維護者，是避免 burnout、確保持續性的關鍵。
- **「負責任地棄坑」**：維護者有權停止維護，但該負責任地做——公告、找接手人、或 archive repo（明確標示不再維護），而非無聲消失（留使用者茫然）。
- **維護者的回報**：雖然累，但維護一個被廣泛使用的專案有獨特的成就感、學習、聲譽、職涯價值（Ch 37）。理解付出與回報的平衡。

## 動手練習

1. 對著「貢獻者 vs 維護者對照表」，回想你（練習 C/D）當貢獻者時的想法，對比維護者會怎麼看同一件事。
2. 找一個你用的開源專案，看它最近被**拒絕/關閉**的幾個 feature PR——分析維護者為什麼拒絕（scope？複雜度？方向？），學「說不」的判準與技巧。
3. 找一個專案的 ROADMAP 或「non-goals」（明說不做什麼）文件——理解維護者怎麼用它來做「說不」的依據。
4. 看一個維護者寫的「為什麼我 burnout / 為什麼棄坑」的文章（很多）——理解維護的真實壓力。
5. 反思：如果你開了一個受歡迎的專案，你準備好花大部分時間在「審 PR、回 issue、說不」而非寫 code 嗎？
6. （為練習 F/Ch 33 鋪路）想一個你可能開源的小專案，列出當維護者你要承擔什麼責任。

## 本章重點整理

- 維護者視角和貢獻者完全不同：貢獻者想「我的改動」，維護者想「專案長期健康」。
- 維護者的真正工作多半不是寫 code——是審 PR、triage issue、決策、溝通、規劃、經營社群。
- 最難的技能是**優雅地說不**——每個 yes 是長期維護負擔，scope creep 是專案殺手；核心判斷是「值得專案長期承擔嗎」。
- 「擁有專案」是責任（使用者依賴、安全、持續性、社群調性），不是特權；但你沒有義務無限付出（burnout 是真問題，設界限/找幫手/負責任交棒都正當）。
- 成為維護者：自己開專案，或持續貢獻+建立信任被邀請（Ch 37）。
- 懂維護者視角讓你既是更好的貢獻者，也準備好當維護者。
