# Ch 20 — 開源溝通與禮儀

> **目標**：把開源最被低估、卻最決定你能走多遠的軟實力講透——非同步溝通、時區與文化差異、語氣與用詞、耐心、尊重維護者的時間、避免常見的失禮，以及 AI 時代的新挑戰（AI 生成的低品質 PR 正在淹沒維護者）。技術讓你的 PR 能跑，溝通讓它被接受。

> **環境**：概念為主，無 git 操作。前置：Ch 16-19。

## 為什麼溝通比 code 更決定你的開源之路

殘酷的事實：**一個 code 普通但溝通得體的人，比一個 code 厲害但溝通糟糕的人，在開源走得遠得多。**

開源的本質是「一群互不相識、分散全球、多半無償的人協作」。在這種環境，code 只是一部分——你怎麼提問、怎麼回應、怎麼對待維護者的時間、怎麼處理分歧，決定了人們願不願意跟你協作。一個傲慢、沒耐心、不尊重流程的貢獻者，再好的 code 也會被冷處理；一個謙遜、清楚、體貼的貢獻者，即使 code 普通也受歡迎、被願意指導。

這章是整個 Part 4 的靈魂——把貢獻從「技術行為」提升為「與人協作」。

## 先建立直覺：對面是一個無償的真人

每次你在 GitHub 留言、開 issue、回應 review，記住：**螢幕另一頭是一個真人，多半在用自己的業餘時間、無償地維護這個專案。**

```
   你看到的：一個「應該幫我解決問題」的服務
   實際是：  一個工程師，下班後/週末，免費花時間
            維護一個你在白用的東西，還要應付幾十個
            像你一樣的陌生人的請求
```

這個視角改變一切。維護者不欠你任何東西——他免費提供了你在用的工具，還願意看你的貢獻。帶著「感謝 + 體貼 + 降低他負擔」的態度，而非「客戶要求服務」的態度。整章的禮儀都是這個視角的延伸。

## 非同步溝通：開源的基本模式

開源溝通幾乎都是**非同步**的——你留言，對方可能幾小時、幾天、幾週後才回（不同時區、業餘時間、優先序）。這跟即時聊天完全不同：

**非同步溝通的原則：**

- **一次把話說完整**：別「在嗎？」然後等對方回了才說正事。直接把問題/脈絡/你試過什麼一次講清楚——對方一次就能完整回應，省下來回。
- **提供完整脈絡**：對方不在你的上下文裡。「那個 bug」對方不知道是哪個——附 issue 連結、版本、複現步驟（Ch 12）。
- **可被搜尋/留存**：你的留言會被未來的人看到（搜尋 issue 的人）。寫得清楚 = 幫到未來的人。
- **耐心等待**：回應慢是常態，不是被無視。別幾小時沒回就焦慮 ping。

> 「不要問能不能問」（Don't ask to ask）：新手常開頭問「有人能幫我嗎？」「我可以問個問題嗎？」然後等——這浪費一個來回。直接問你的問題（附完整脈絡），有人會的話自然會回。這是非同步社群的基本禮貌。

## 語氣與用詞

文字溝通失去了語氣、表情、肢體語言——很容易被誤讀。同一句話，當面說和打字說感受可能差很多。所以：

```
   容易顯得失禮（即使你沒惡意）        較好的寫法
   ─────────────────────              ─────────────
   "This is wrong."                   "I think there might be an issue here — ..."
   "Why did you do it this way?"       "I'm curious about the reasoning for X — ..."
   "Just do X."                        "Maybe we could do X? What do you think?"
   "Obviously..." / "Simply..."        （刪掉這些詞，它們暗示對方笨）
   "ASAP" / "urgent"                   （你的急不是別人的急，尤其無償專案）
```

幾個用詞原則：

- **多問少斷言**：「我理解錯了嗎？」比「你錯了」好——給雙方台階，也許錯的是你。
- **避免「顯然/簡單/只要」**（承 Ch 寫作原則）：這些詞暗示「這很簡單，你怎麼不懂」，讓人不舒服。
- **感謝**：「Thanks for maintaining this!」「Thanks for the review!」——廉價但有效，認可對方的付出。
- **假設善意**：對方的簡短回應、慢回應，多半不是針對你（文化/時區/忙），別腦補敵意。
- **跨文化體諒**：開源是全球的，很多人英文不是母語。對方用詞生硬可能只是語言問題，不是不禮貌。你自己英文不完美也沒關係——清楚 > 華麗。

## 尊重維護者的時間

維護者最寶貴、最稀缺的就是時間。**處處為他省時間**，是最好的禮儀：

- **做足功課再問**（Ch 17）：別問「怎麼設定環境」如果 README 寫了。先讀文件、搜尋既有 issue。維護者最煩「懶得查就伸手」。
- **PR 小而清楚**（Ch 11/18）：好 review 的 PR = 省維護者時間。
- **完整的 bug report**（Ch 12）：能複現的 report 省維護者來回問。
- **別重複問/開**（Ch 12）：搜尋有沒有人問過/回報過。
- **回應及時但不催促**：你回應快讓 PR 推進，但別反過來催維護者。
- **不要求手把手**：「教我怎麼做這個 PR」是過分的要求（除非是 first-timers-only 那種明確新手專案）。

> 「免費客服」心態是大忌：把開源維護者當成「我付費的客服」——要求快速回應、要求功能、要求修你的特定問題、不滿意就罵——是開源最讓人反感的行為。你沒付錢，對方沒義務。感謝你能免費用、能貢獻。

## 常見的失禮（要避免）

整理新手最常踩的禮儀雷：

1. **+1 / "any updates?" 洗版**：在 issue 下狂留「+1」「我也是」「有進展嗎？」——對解決問題沒幫助，只是製造通知噪音。用 👍 reaction 表達「我也要」，別留言洗版。
2. **連環催促**：PR/issue 沒回就每天 ping、@ 維護者。耐心，真的久了禮貌 ping 一次（Ch 19）。
3. **無視範本/CONTRIBUTING**：清空 PR/issue 範本亂填、不照貢獻流程——顯得不尊重專案。
4. **跨平台騷擾**：GitHub 沒回就跑去維護者的 Twitter/email/LinkedIn 催——非常失禮，越界。
5. **要求 + 不感謝**：只會要功能/要修 bug，從不感謝維護者的付出。
6. **公開抱怨/情緒化**：PR 被拒/沒回就公開罵專案/維護者——斷送關係，也讓社群反感。
7. **把問題開成 issue**（Ch 12）：用法問題該去 Discussions/論壇，不是佔用 issue。

## AI 時代的新禮儀挑戰

近年開源面臨一個新問題，你必須意識到：**大量 AI 生成的低品質 PR/issue 正在淹沒維護者。**

```
   問題：有人用 AI 一鍵生成「貢獻」（為了刷 commit / Hacktoberfest T-shirt /
        履歷），但自己沒理解、沒測試、沒複現——維護者要花時間審一堆
        看似合理但實際沒價值/有錯的 AI slop。
```

這對你（學習貢獻的人）的意涵：

- **別當製造 AI slop 的人**：用 AI 輔助沒問題（幫你理解 codebase、起草），但**你必須自己理解、複現、測試、確認品質**才送出。送一個你自己都沒看懂的 AI 生成 PR，是浪費維護者時間、傷害社群信任。
- **你的貢獻要證明「人在迴路」**：清楚的描述、真實的複現、自己跑過的測試、得體的 review 回應——這些證明你是認真的人，不是 AI 噴的垃圾。在 AI slop 氾濫的時代，「認真的人類貢獻者」更稀有、更受珍惜。
- **理解維護者的戒心**：有些專案因此對新貢獻者更謹慎、甚至限制 AI 生成內容。別覺得被冒犯——他們在自保。

> 認識論誠實：這是 2024-2025 正在演變的議題，各專案政策不一（有些禁 AI 生成、有些要求揭露）。原則不變：**你對你送出的東西負責，必須自己理解和驗證**。AI 是工具不是替你貢獻的人。

## 一個完整的「得體溝通」心法

```
   每次互動前問自己：
   1. 我做足功課了嗎？（沒讓對方查我能查的）
   2. 脈絡完整嗎？（對方不用追問就能回應）
   3. 語氣 OK 嗎？（沒有斷言/催促/「顯然」）
   4. 我在省對方時間還是浪費他時間？
   5. 我感謝了對方的付出嗎？
   6. 這是我自己理解/驗證過的嗎？（不是 AI slop）
```

核心一句話：**把每次互動當成「跟一個你尊敬、但很忙、且免費幫你的人協作」——謙遜、清楚、體貼、感謝。**

## 踩雷集錦

1. **「免費客服」心態**：要求、催促、不滿就罵。維護者無償、沒義務。感謝 + 體貼。
2. **「在嗎？可以問嗎？」式開頭**：浪費來回。直接問，附完整脈絡（don't ask to ask）。
3. **斷言式/命令式語氣**："This is wrong" / "Just do X"——多問少斷言，多商量少命令。
4. **+1 洗版、連環催促**：製造噪音。用 reaction，耐心等。
5. **跨平台騷擾維護者**：GitHub 沒回跑去 Twitter 催——嚴重越界。
6. **送出自己沒理解的 AI 生成內容**：AI slop 浪費維護者時間、傷信任。自己理解+驗證才送。
7. **沒做功課就伸手**：問文件已寫的、不搜尋既有 issue——浪費維護者時間。

## 進階：再往深一層

- **Code of Conduct（CoC）**：多數專案有行為準則，規範社群互動（禁騷擾、歧視等）。違反可能被 ban。你當維護者也要立 CoC（Ch 31）。
- **文化與時區的現實**：協作者可能在地球任何角落。對「為什麼這時間還沒回」「為什麼用詞這樣」多一份體諒。
- **公開 vs 私下**：技術討論留在公開的 issue/PR（讓社群受益、可搜尋）；敏感事情（安全漏洞 Ch 34、人際衝突）才私下。別把該公開的塞私訊。
- **建立聲譽是長期的**（Ch 37）：每次得體互動累積信任，讓維護者願意指導你、給你更多責任。溝通是長期投資。
- **maintainer burnout**（Ch 31）：理解維護者可能 burnout（無償、壓力大、被各種要求轟炸）。你的體貼是減輕、你的苛求是加重。
- **給新人的善意（當你進階後）**：你受過的善意，將來回饋給更新的人——這是開源社群運轉的方式（Ch 31）。

## 動手練習

1. 找三個真實開源 issue/PR 的討論串，分析：哪些留言得體、哪些失禮？維護者怎麼回應得體 vs 失禮的人？
2. 把幾句「失禮版」改寫成「得體版」（如 "this is wrong" → ...，"any updates?" → ...）。
3. 練習寫一個「don't ask to ask」式的好提問：完整脈絡 + 你試過什麼 + 具體問題，一次到位。
4. 讀一個專案的 Code of Conduct，理解它規範什麼。
5. 反思：你（假設）最近一次想在開源社群問/做的事，有沒有「免費客服」心態的影子？怎麼改成體貼版？
6. 思考 AI slop 問題：如果你用 AI 輔助貢獻，你會怎麼確保送出的是「你理解+驗證過」的東西？

## 本章重點整理

- 溝通比 code 更決定你的開源之路；對面是無償、用業餘時間、沒義務幫你的真人。
- 非同步溝通：一次說完整、提供完整脈絡、耐心等、「don't ask to ask」（直接問別問能不能問）。
- 語氣：多問少斷言、避免「顯然/簡單/只要」、感謝、假設善意、體諒跨文化/非母語。
- 尊重維護者時間：做足功課、PR 小而清楚、別重複、別催促、別要求手把手——別當「免費客服」心態。
- 避免失禮：+1 洗版、連環催促、跨平台騷擾、無視範本、公開情緒化。
- AI 時代：別送自己沒理解的 AI slop；你對送出的東西負責，必須自己理解+驗證；認真的人類貢獻更稀有珍貴。
