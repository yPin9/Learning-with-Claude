# Ch 19 — 在 review 中迭代

> **目標**：PR 開出去後，真正的考驗是 review 的來回。本章接續 Ch 13（被審的操作），聚焦**開源情境下的迭代與判斷**：怎麼面對一輪輪 changes requested、怎麼處理技術分歧、什麼時候該堅持、什麼時候該讓步、什麼時候該放手讓 PR 死掉。這些判斷決定你是「順利貢獻者」還是「卡在無止境來回的人」。

> **環境**：GitHub。前置：[Ch 13 Code Review（被審方）](./13-code-review-as-author.md)。

## 為什麼 review 迭代是貢獻的真正難關

開 PR 只是開始。對開源貢獻，**PR 開出去之後的 review 來回，才是真正決定它能不能被合併的階段**——而且這個階段比寫 code 更需要軟實力。

Ch 13 教了操作面（怎麼回應 comment、push 更新、force-push 時機）。但開源情境有更難的東西：你面對的是陌生的維護者（不是同事）、可能來回很多輪、可能遇到你不同意的意見、可能等很久沒回應、甚至 PR 最後無疾而終。這些情境的判斷——堅持還是讓步、繼續還是放手——沒人教你就會踩雷。這章補這塊。

## 先建立直覺：你在跟一個有自己想法的人協作

最重要的認知：**維護者不是「幫你 merge PR 的客服」，是一個對自己專案有想法、有標準、有時間限制的人。**

```
   新手的錯誤期待                  現實
   ─────────────                 ─────────────
   "我發了 PR，他應該合"           他要評估這值不值得進專案、誰來長期維護
   "我改了他要的，他該馬上合"       他可能有別的優先序、業餘時間有限
   "我的解法明明對"               他更懂專案的方向和歷史包袱
   "他為什麼不回我"               他可能根本沒空、或在思考
```

理解這個，你的 review 迭代就會從「為什麼他這麼龜毛/慢」變成「我怎麼讓這個忙碌的人願意花時間合我的 PR」。整章的判斷都建立在這個認知上。

## 面對一輪輪 changes requested

開源 PR 常常不是一輪 review 就過——尤其大一點的改動，可能來回三五輪。每一輪：

```
   維護者 review → request changes → 你改 → re-request → 又 review → ...
```

怎麼撐過多輪而不崩潰、不惹毛維護者：

- **每輪都認真、完整處理**（Ch 13）：別這輪改一半、下輪再改另一半，拖長戰線。一次到位。
- **保持正面語氣**：第三輪還在改可能讓你煩躁，但語氣要穩。「Thanks for the careful review!」比帶刺的回應讓維護者更願意繼續。
- **理解每輪都在收斂**：review 來回是在逼近「可合併」的狀態，不是維護者在刁難。每輪 PR 都變更好。
- **節奏感**：改完及時 push + re-request，別讓 PR 冷掉；但也別一條改一次 push（洗版通知）。一輪 review 一次回應。

> 認識論誠實：多輪 review 是品質專案的常態，不是你做得差。Linux kernel、大型專案的 PR 來回十幾輪很正常。把它當「一起把 code 打磨好」而非「我一直被打回票」。但如果**輪數異常多且都是小事**，可能是溝通沒對齊——主動問「是不是我誤解了你的整體方向？要不要我們先對齊一下？」

## 處理技術分歧

你不同意維護者的意見時——這是 review 最微妙的部分。承 Ch 13 的「有理有據地不同意」，開源情境再加幾層：

**分清三種分歧：**

```
   1. 客觀對錯（你的有 bug / 他的記錯了）
      → 用證據（測試、文件、benchmark）說明，對事不對人
      
   2. 設計取捨（兩種寫法各有優劣）
      → 說明你的理由，但這是他的專案，最終尊重他的選擇
      
   3. 純風格偏好（用 map 還是 for loop）
      → 直接讓步，不值得爭
```

**判斷準則：**

- **客觀問題**：拿證據（「這個測試證明...」「文件說...」），平和指出。但即使你對，也別「我早就說了」的態度。
- **設計分歧**：表達你的觀點一次，附理由。如果維護者堅持，**讓步**——這是他要長期維護的 code，他有最終決定權（Ch 20）。你只是貢獻一次，他要維護一輩子。
- **風格偏好**：直接照他的來。為 `map` vs `for` 爭三回合不值得，浪費雙方時間、傷關係。

黃金句式（不同意但尊重）：

```
"I see your point. I originally chose X because <reason>, but I'm
happy to switch to Y if that fits the project's conventions better.
Let me know which you'd prefer."
```

這句話：表達了你的理由、承認對方觀點、把決定權交給維護者、保持合作。**「我願意照你的，但讓你知道我的考量」** 幾乎總是對的姿態。

## 什麼時候該堅持

讓步是默認，但不是永遠。**該堅持的情況：**

- **維護者的建議會引入 bug / 安全問題**：這是客觀錯誤，要平和但堅定指出（附證據）。
- **你有對方不知道的重要資訊**：「這個改法在 X 情況會壞，我遇過」——提供資訊，但仍尊重最終決定。

即使堅持，也是「提供資訊 + 表達擔憂」，不是「我不改」。最終如果維護者堅持，你可以：照做（並在 PR 留記錄你的擔憂）、或禮貌撤回 PR（如果你真的無法認同）。但**為技術正確性堅持，和為自尊堅持，是兩回事**——前者可貴，後者有害。

## 什麼時候該放手

殘酷但必要的技能：**有些 PR 就是不會被合併，該放手。** 認清這些訊號：

```
   該考慮放手的訊號：
   - 維護者明說「我們不想要這個功能/方向」（不是改 code 能救的）
   - PR 開了幾個月，維護者完全不回（專案可能停滯，Ch 16 健康度）
   - 來回十幾輪還在根本性分歧（方向沒對齊，越改越遠）
   - 維護者的要求超出你願意投入的（無止境的「再加這個」）
```

放手的方式：

- **方向被拒**：禮貌接受、感謝 review、學到東西、把 code 留在你的 fork（也許你自己用）。「Thanks for considering this. I understand it doesn't fit the project's direction.」
- **維護者消失**：禮貌 ping 一兩次（間隔幾週），還是沒回就放生。別連環 @、別在別處抱怨。那條 code 可以留在你 fork 自用。
- **無止境要求**：評估「繼續投入值不值得」。學習階段，走通一個簡單 PR 比死磕一個大 PR 有價值。

放手不是失敗——**它是判斷「投入產出比」的成熟**。把力氣轉移到會被接受的貢獻，比死磕一個注定不合的 PR 聰明。

## 一個完整的 review 迭代心法

```
   收到 review
   ├─ 客觀錯誤（我有 bug）→ 立刻改、感謝抓到
   ├─ 設計分歧 → 表達理由一次 → 維護者堅持就讓步（他維護一輩子）
   ├─ 風格偏好 → 直接讓步
   ├─ 我有重要資訊 → 提供 + 表達擔憂 → 仍尊重最終決定
   └─ 方向被拒 / 維護者消失 / 無止境要求 → 評估放手

   全程：正面語氣、一次到位、及時回應、把決定權給維護者
```

核心一句話：**為技術正確性溫和地發聲，為設計與風格慷慨地讓步，為投入產出比理性地放手。**

## 踩雷集錦

1. **把多輪 review 當被刁難**：品質專案多輪 review 是常態，每輪 PR 都變好。心態擺正。
2. **為風格偏好爭到底**：`map` vs `for` 爭三回合，浪費時間傷關係。小事讓步。
3. **為自尊堅持（不是為對錯）**：「我的解法就是好」式堅持有害。堅持只該為客觀正確性，且附證據、保持尊重。
4. **設計分歧不讓步**：忘了這是維護者要長期維護的 code，他有最終決定權。表達一次理由就好。
5. **維護者沒回就連環 ping / 公開抱怨**：業餘時間，耐心。禮貌 ping 一兩次，還沒回就放生，別 spam、別在 Twitter 罵。
6. **死磕注定不合的 PR**：方向被拒還一直改，越改越遠。認清訊號，放手轉移力氣。
7. **改一半就回應、拖長戰線**：每輪一次到位，別讓 review 拖成連續劇。

## 進階：再往深一層

- **主動對齊大方向**：大 PR 來回多輪時，與其逐條改，不如主動問「我們先對齊整體方向好嗎？我理解的目標是 X，對嗎？」——省下逐條來回。
- **把 reviewer 當隊友**：用「我們」（"how should we handle X?"）而非對立的「你/我」，心理上拉近距離。
- **維護者的 "Add suggestion"**：對小修，維護者可能直接給建議 code（Ch 13），一鍵接受最快。
- **撤回 PR 的禮儀**：真的要放棄，禮貌關閉 PR 並說明（「Closing this as it doesn't fit the project's direction. Thanks for the review!」），別默默消失留個爛攤。
- **從被拒中學**：被拒的 PR 教你這個專案的方向、標準、維護者的偏好——下次貢獻更準。
- **長期關係 > 單個 PR**：對你想長期貢獻的專案，每次得體的互動都在累積信任（Ch 37）。為一個 PR 撕破臉，斷送長期機會，不值得。

## 動手練習

1. 回顧練習 C（你扮演兩角色）的 review 來回，分析你的回應屬於「客觀/設計/風格」哪種分歧、處理得當嗎。
2. 練習寫三種回應：(a) 維護者抓到你的 bug（感謝+改）；(b) 設計分歧（表達理由+願讓步）；(c) 風格偏好（直接讓步）。
3. 練習寫一個「禮貌堅持」的回應——維護者的建議會引入問題，你附證據平和指出。
4. 練習寫一個「放手」的回應——PR 方向被拒，你禮貌接受並關閉。
5. 找一個真實開源專案「來回很多輪最後合併」的 PR，和一個「來回後被關閉」的 PR，分析雙方的溝通——學什麼姿態有效、什麼無效。
6. 想一個你（假設）很堅持的技術意見，練習把它寫成「提供資訊+尊重決定」而非「我是對的」的版本。

## 本章重點整理

- 維護者是有想法、有標準、時間有限的人，不是幫你 merge 的客服——這個認知決定你怎麼迭代。
- 多輪 changes requested 是品質專案常態（每輪 PR 變好），不是被刁難；每輪一次到位、保持正面語氣、及時回應。
- 分歧分三種：客觀對錯（附證據指出）、設計取捨（表達一次理由後讓步，他維護一輩子）、風格偏好（直接讓步）。
- 堅持只為客觀正確性/安全（附證據、保持尊重），不為自尊；最終仍尊重維護者決定權。
- 認清「該放手」的訊號（方向被拒、維護者消失、無止境要求），理性轉移力氣——放手是成熟不是失敗。
- 核心：為正確性溫和發聲、為設計風格慷慨讓步、為投入產出比理性放手。
