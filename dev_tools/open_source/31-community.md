# Ch 31 — 經營社群

> **目標**：維護不只是技術——本章講維護者最軟、卻最決定專案長期生死的工作：經營社群、Code of Conduct、歡迎與留住貢獻者、避免 burnout、找 co-maintainer、bus factor。一個技術很好但社群有毒/維護者燒壞的專案會死;一個技術普通但社群健康的專案能長青。

> **環境**：概念為主。前置：Ch 20（溝通禮儀）、Ch 28（維護者心態）、Ch 29/30（審 PR/triage）。

## 為什麼社群決定專案生死

殘酷的事實：**很多技術優秀的開源專案死掉，不是因為技術，是因為人。** 維護者 burnout 棄坑、社群變得有毒嚇跑貢獻者、只有一個維護者結果他消失了——這些「人」的問題，比任何技術問題更常殺死專案。

反過來，技術只是中等但社群健康的專案能長青——有源源不絕的貢獻者、有多個維護者分擔、有友善的氛圍吸引人留下。**專案的長期存活，社群健康 > 技術品質。** 這章是維護者最被工程師忽略、卻最重要的技能。

## 先建立直覺：你在經營一個志願者組織

```
   貢獻者多半是志願者：
   - 無償、用業餘時間
   - 隨時可以走（沒人綁得住）
   - 為什麼留下？因為被尊重、有成就感、氛圍好、學到東西

   維護者的社群工作 = 經營一個志願者組織：
   - 讓人感到被歡迎、被尊重 → 願意來、願意留
   - 讓貢獻有成就感 → 持續貢獻
   - 維持健康氛圍 → 不被有毒的人破壞
   - 照顧自己（你也是志願者）→ 不燒壞
```

你不能命令志願者、不能用錢留人——只能用「被尊重的體驗、成就感、好氛圍」。理解這個，社群經營的所有做法都是在回答「怎麼讓志願者願意來、願意留」。

## Code of Conduct：社群的底線

**Code of Conduct（行為準則，CoC）** 是社群互動的規則——明訂什麼行為可接受、什麼不行（禁騷擾、歧視、人身攻擊），以及違反怎麼處理。

為什麼需要：

- **保護貢獻者**：尤其弱勢/少數群體——沒有 CoC，有毒行為無從制止，會嚇跑人。
- **給維護者執法依據**：有人在 issue 罵人/騷擾，CoC 讓你有明確依據處理（警告/ban），而非憑感覺。
- **設定基調**：宣告「這是個尊重人的社群」，吸引對的人、勸退有毒的人。

最廣用的是 **[Contributor Covenant](https://www.contributor-covenant.org/)**（Ch 20 提過）——直接採用它，放 `CODE_OF_CONDUCT.md`（Ch 33）。

> CoC 不只是放著好看——關鍵是**執行**。有 CoC 但對違反視而不見，比沒有更糟（顯得虛偽）。維護者要願意執法：對有毒行為警告、必要時 ban。保護好人的代價是對壞行為強硬——這是維護者的責任。

## 歡迎與留住貢獻者

承 Ch 29（review 培養貢獻者）、Ch 30（good first issue 招募），社群經營的核心是**讓人願意來、願意留**：

```
   貢獻者的旅程，每一步都可能流失：
   發現專案 → 第一次互動 → 第一個 PR → 被 review → 合併 → 繼續貢獻 → 成為核心
              ↑友善嗎      ↑門檻低嗎   ↑被尊重嗎  ↑有成就感嗎  ↑被看見嗎
```

留住人的做法：

- **歡迎首次貢獻者**：第一次的 PR 多一點耐心、鼓勵（Ch 29）；welcome bot 自動歡迎；`good first issue` 降低門檻（Ch 30）。
- **及時、尊重的回應**（Ch 20/29）：沒回應/冷酷對待是頭號流失原因。
- **認可貢獻**：感謝、在 release notes 提貢獻者、加進 contributors 列表、給 commit access——讓人覺得「我的貢獻被看見」。
- **降低門檻**：清楚的 CONTRIBUTING、好的文件、容易設定的開發環境（Ch 33）——讓貢獻容易。
- **從貢獻者培養維護者**：信任的貢獻者給更多責任（triage 權限、review 權限、co-maintainer）——既留住人才，也分擔你的負擔。

> 「第一次體驗」決定一切：一個人第一次貢獻的體驗（友善 vs 冷酷、被引導 vs 被刁難），高度決定他會不會繼續。維護者對新人多一份耐心和歡迎，是投資整個社群的未來——今天你溫暖對待的新人，可能是明天分擔你工作的 co-maintainer。

## Burnout：維護者的頭號殺手

開源最嚴重、最普遍的問題：**維護者 burnout（燃燒殆盡）。** 無償、壓力大、被無止境的 issue/PR/要求/抱怨轟炸、有責任感放不下——很多維護者撐到崩潰、然後棄坑（連帶害了所有使用者）。

burnout 的成因與症狀：

```
   成因：無償 + 無止境的需求 + 責任感 + 沒界限 + 孤軍奮戰 + 不感激的使用者
   症狀：對專案失去熱情、看到 issue 就煩、拖延、想逃、最後棄坑
```

避免 burnout（維護者必修）：

- **設界限**：你沒有義務即時回應、沒有義務做每個功能、沒有義務 24/7（Ch 28）。明確告訴社群你的可用性（如「我週末才看」）。
- **學會說不**（Ch 28/29）：每個 yes 是負擔。拒絕不符 scope 的、超出你能力的。
- **別獨自扛**：找 co-maintainer（下面）——孤軍奮戰最容易燒壞。
- **自動化**（Ch 27/30）：把重複工作（lint、triage、welcome）自動化，省下精力。
- **允許自己休息/離開**：可以暫停、可以說「我這陣子沒空」、可以負責任地交棒/封存——這些都正當。**你的健康 > 專案。**

> 重要心態（呼應 Ch 28）：「擁有專案」不等於「犧牲自己」。健康的維護是「在可持續的範圍內負責任地維護」，不是「燃燒自己」。一個 burnout 棄坑的維護者，對專案的傷害比「設好界限、節奏可持續」的維護者大得多。照顧好自己，才能長期照顧專案。

## Bus factor 與 co-maintainer

**Bus factor**（公車係數）：專案要死掉，需要幾個人「被公車撞」（消失）？

```
   bus factor = 1：只有一個維護者
   → 他消失（burnout、生病、沒興趣、被公車撞）= 專案死
   → 極度脆弱！很多重要專案就是這樣（一個累壞的人撐著）

   bus factor = 3+：多個維護者分擔
   → 一個走了，其他人撐得住
   → 健康、可持續
```

提高 bus factor = 找 **co-maintainer**（共同維護者）：

- **從活躍貢獻者中找**：持續貢獻、品質穩定、得體溝通、展現責任感和判斷力的人——邀他成為 co-maintainer（Ch 37 是這條路的貢獻者端）。
- **逐步授權**：先給 triage 權限 → review 權限 → commit 權限 → 完整 maintainer。建立信任的漸進過程。
- **分散知識**：別讓某部分只有你懂（文件化、結對）——避免「只有你能改 X」的 bottleneck（也是 CODEOWNERS 的考量，Ch 24）。

找 co-maintainer 既提高 bus factor（永續），又分擔負擔（防 burnout）——是維護者最該做的長期投資。但要找對人（信任、能力、價值觀契合），給錯人權限也是風險。

## 一個健康社群的要素

綜合本章，一個健康、可持續的開源社群有：

```
   ☑ Code of Conduct（且確實執行）
   ☑ 清楚的貢獻指引（CONTRIBUTING，Ch 33）—— 降低門檻
   ☑ 友善、及時的互動（Ch 20/29）—— 留住人
   ☑ good first issue —— 招募新人（Ch 30）
   ☑ 認可貢獻（感謝、列名、授權）—— 成就感
   ☑ 多個維護者（bus factor > 1）—— 永續
   ☑ 維護者設好界限、不 burnout —— 可持續
   ☑ 從貢獻者培養維護者 —— 良性循環
```

技術品質讓專案「好用」，這些社群要素讓專案「活得久」。

## 踩雷集錦

1. **沒有 / 不執行 CoC**：有毒行為無從制止，嚇跑貢獻者（尤其弱勢群體）。有 CoC 且願意執法。
2. **冷酷對待新人**：第一次體驗差 = 永遠流失。新人多一份耐心和歡迎（投資未來）。
3. **獨自扛 / bus factor 1**：孤軍奮戰最易 burnout，且專案脆弱。找 co-maintainer。
4. **不設界限、想做完所有事**：無止境的需求 + 責任感 = burnout。設界限、說不、自動化。
5. **以為「擁有專案」=無限付出**：你的健康 > 專案。可暫停、交棒、封存——都正當。
6. **不認可貢獻**：人貢獻了卻沒被看見/感謝 = 沒成就感 = 流失。感謝、列名、授權。
7. **給錯人 co-maintainer 權限**：找信任、能力、價值觀契合的，逐步授權建立信任——別倉促給權限。

## 進階：再往深一層

- **治理模型**（Ch 28）：專案大了，從 BDFL 演化出更正式的治理（committee、steering council、RFC 流程）——讓決策不靠單一個人、更可持續。
- **資金與永續**：開源永續的根本矛盾是「免費但要維護成本」。GitHub Sponsors、Open Collective、企業贊助、付費支援——讓維護者能（部分）以此為生，減少 burnout。重要但難。
- **社群空間**：除了 GitHub，很多專案有 Discord/Slack/論壇/mailing list——經營這些空間（也要 CoC 執法）擴大社群。
- **貢獻者階梯**：明訂從「貢獻者→committer→maintainer」的路徑與標準，讓人知道怎麼往上、激勵投入（Ch 37 的另一端）。
- **處理衝突**：社群難免有衝突（技術之爭、人際摩擦、有毒行為）。維護者要會調解、必要時果斷處理（警告/ban）——保護多數好人。
- **diversity & inclusion**：刻意降低門檻、歡迎不同背景的人——更多元的社群更健康、更有韌性。
- **負責任地交棒/封存**（Ch 28）：真的要離開，找接手人、或 archive repo 明確標示不再維護——別讓使用者茫然依賴一個死專案。

## 動手練習

1. 看一個健康的開源專案社群（活躍、友善），找出它的：CoC、CONTRIBUTING、怎麼歡迎新人、有幾個維護者、怎麼認可貢獻——對照本章「健康社群要素」。
2. 讀 Contributor Covenant 的 CoC，理解它規範什麼、違反怎麼處理。
3. 找一篇維護者寫的 burnout / 棄坑文章，分析成因——對照本章「避免 burnout」的做法，哪些他做了/沒做。
4. 評估一個你用的專案的 bus factor（看 contributors 頁面、誰在 merge PR）——如果是 1，它有多脆弱？
5. 練習寫一個「歡迎首次貢獻者」的留言（welcome bot 風格）和一個「邀請成為 co-maintainer」的訊息。
6. 反思：如果你維護一個受歡迎的專案，你會怎麼設界限避免 burnout？怎麼找和培養 co-maintainer？

## 本章重點整理

- 專案長期存活：社群健康 > 技術品質。很多優秀專案死於「人」（burnout、有毒社群、bus factor 1），不是技術。
- 維護者在經營一個志願者組織——只能用「被尊重的體驗、成就感、好氛圍」留住隨時能走的志願者。
- Code of Conduct 是社群底線（保護貢獻者、給執法依據、設基調）——關鍵是**執行**，不只放著。
- 留住貢獻者：歡迎新人（第一次體驗決定一切）、及時尊重回應、認可貢獻、降低門檻、從貢獻者培養維護者。
- Burnout 是頭號殺手：設界限、學說不、別獨自扛、自動化、允許休息/交棒——你的健康 > 專案。
- Bus factor：找 co-maintainer 提高永續 + 分擔負擔——維護者最該做的長期投資。
