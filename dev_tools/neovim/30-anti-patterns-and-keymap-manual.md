# Ch 30 — 常見誤區與你的讀碼鍵位手冊

> **目標**：全課收斂。這一章做兩件事。前半是**反模式盤點**——你這台機器搭好了，但用錯方式一樣慢。八個最常見的讀碼誤區，每條講清楚「為什麼是錯的、為什麼你會這樣做、正確做法是什麼」，並連回對應章節。後半是**你的讀碼鍵位手冊**——全課所有 keymap 收成一張大表，按「移動 / 搜尋 / 結構 / 語意 / 後備 / 外化」六個情境分組。這張表是你帶走的 cheatsheet，貼在螢幕旁邊，攻堅時「這個當口該按什麼」一眼查到。

> **環境**：Neovim v0.12.4，WSL2 / Ubuntu。手冊裡的鍵位都是前面各章教過、config 裡真的綁了的。

## 為什麼需要這個？

你把工具都學會了，但**會用工具和用對工具是兩回事**。同一台配好的 nvim，有人攻堅一個大 repo 順滑如飛，有人卡卡頓頓——差別往往不是工具，是**習慣**。反模式就是那些「你以為在讀碼、其實在拖慢自己」的習慣。它們有個共同特徵：**短期舒適、長期昂貴**——用方向鍵比學 motion 舒服，但你為此付出一輩子的慢。

這一章把八個最貴的反模式挑出來，逐一戳破。看完你會在自己身上認出幾條——那正是你下一步該改的。然後給你一張鍵位手冊，讓「正確做法」隨手可查，把新習慣變反射。

## 反模式盤點

### 反模式 1：一直用方向鍵 / 滑鼠，不用 motion

**症狀**：游標一格一格按 `↓↓↓↓` 挪，或抓滑鼠點。要到某個函式，按著方向鍵滾半天。

**為什麼你會這樣**：方向鍵/滑鼠零學習成本，第一天就會用。motion（`w`/`}`/`f`/`/`/`gg`）要記、要練，短期痛。

**為什麼是錯的**：讀碼是**導航密集**的活，你一天做幾百次「移到某處」。方向鍵一次挪一格，motion 一次跳一個詞/段/函式。這個差距每天累積幾百次，是你和高手速度差的主要來源。更關鍵的是**認知成本**——按方向鍵時你在「操作編輯器」，用 motion 時你已經「到了目標在讀 code」。摩擦偷走的是維持思路的腦力。

**正確做法**：強迫自己用 motion。`w`/`b`（詞）、`}`/`{`（段落/空行間）、`f<char>`（跳到某字元）、`/pattern`（搜尋跳）、`gg`/`G`（檔頭尾）、`%`（配對括號）、`Ctrl-d`/`Ctrl-u`（半頁）。極端手段：把方向鍵停用（`vim.keymap.set("n", "<Up>", "<nop>")`）逼自己戒斷。**連回 Ch 3（基本 motion）、Ch 5（跳轉）、Ch 6（搜尋）。**

### 反模式 2：只用 telescope find_files，不用 symbol / gd

**症狀**：要找一個函式的定義，`<leader>ff` 打檔名、開檔、再肉眼捲動找那個函式。每次都這樣。

**為什麼你會這樣**：`find_files` 是你學的第一個 telescope 功能，順手。而且它「什麼都能找」的錯覺讓你懶得學專門工具。

**為什麼是錯的**：`find_files` 找的是**檔名**，不是**符號**。你要的是「`processCommand` 這個函式在哪」，find_files 幫不上——你得先知道它在哪個檔。這繞了一大圈。**符號查詢（workspace symbol / `gd`）直接跳到定義**，一步到位，還做語意辨析（同名符號給你對的那個）。

**正確做法**：找符號用符號工具。當前檔內的函式清單用 `<leader>ds`（document symbol）；跨檔找某符號用 `<leader>fs`（workspace symbol）；游標在某符號上直接 `gd` 跳定義、`gr` 找引用。find_files 只該用在「我知道檔名、要開這個檔」。**連回 Ch 19（gd/gr）、Ch 20（symbol 搜尋）。**

### 反模式 3：clangd 跪了硬等，不退 gtags

**症狀**：`gd` 沒反應，你反覆按、重開檔、重啟 nvim、甚至重裝 clangd，耗掉半小時。

**為什麼你會這樣**：clangd 平常很神，你預期它一定能動，「它應該要 work」的心理讓你不肯放棄。

**為什麼是錯的**：clangd **精準但脆弱**——它需要 `compile_commands.json` 才能精準跳轉，讀**編不起來的專案**（kernel 某子系統、缺依賴的 repo）時它幾乎必然半殘。你在一個結構性沒法動的東西上死磕，時間全浪費。

**正確做法**：先 `:LspInfo` 判斷 clangd 狀態（Ch 29），確認它半殘（沒 root / 缺 compile db）就**立刻退 gtags**。`global -x foo`（查定義）、`global -rx foo`（反查 caller）不需要編譯、永遠有答案。gtags 不如 clangd 精準（同名符號全給你），但**它不死**。判斷「該退了」是攻堅的關鍵決策。**連回 Ch 17/18（clangd 與 compile db）、Ch 23-25（tags 後備）、Ch 28（何時退）。**

### 反模式 4：開一堆 tab / buffer，不用 harpoon

**症狀**：攻堅一小時，你開了三十個 buffer、十個 tab，要回到某個關鍵函式時在一堆分頁裡翻找。

**為什麼你會這樣**：從 VSCode 帶來的習慣——每個檔一個分頁，靠視覺找。而且開檔零成本，不知不覺就開一堆。

**為什麼是錯的**：buffer list 是**自動累積**的，包含你只瞥一眼的檔，很快變成雜訊。tab 被你當檔案分頁用（那是 VSCode 概念，Vim 的 tab 是佈局容器）。你要回的其實就那**四五個核心函式**，卻要在三十個 buffer 裡撈。

**正確做法**：一條攻堅路徑的四五個熱點，用 `<leader>a` 釘進 harpoon，`<leader>1-4` 一鍵瞬移。harpoon 是**你親手策展的短清單**，永遠只有你在乎的那幾個。開過的雜檔隨它去 buffer list，你只認 harpoon 那四個。**連回 Ch 26（harpoon）、Ch 27（tab 是佈局容器不是分頁）。**

### 反模式 5：不外化，全靠腦記

**症狀**：追 call chain 追到第五個函式，忘了第一個在哪、剛剛想通了什麼，回頭重讀。一天重讀同一段五次。

**為什麼你會這樣**：「我記性好」的錯覺，加上做筆記感覺像「額外工作」、打斷讀碼節奏。

**為什麼是錯的**：這跟記性無關，是**工作記憶的物理上限**（4±1 chunk，`reading_code` Ch 35）。陌生 code 瞬間塞爆你的 slot，沒外化的東西 = 永久遺失、只能重讀。你「記性好」頂多讓 slot 從 4 變 5，面對塞爆 50 個 chunk 的陌生 code 一樣溢位。

**正確做法**：位置和思緒都外化。**位置**釘 harpoon、標大寫 mark；**思緒**（假設/問題/發現）進 `notes.md` 三欄。追進一個函式前，先把「我在想什麼」丟進 notes.md，回來直接續上不必重建。外化不是額外工作，是**騰出腦力跑理解**的必要手段。**連回 Ch 26（marks/harpoon/notes）、`reading_code` Ch 35（為什麼）。**

### 反模式 6：config 抄一堆看不懂的

**症狀**：從網路抄了幾百行 config，一半不知道在幹嘛。某個功能壞了，完全不知道從哪查，只能再 google 貼別人的解法。

**為什麼你會這樣**：抄現成的比自己搭快，「先能用再說」。LazyVim/NvChad 之類發行版更是一鍵到位。

**為什麼是錯的**：這正是 Ch 0 開篇警告的——**工具卡住時你 debug 不了工具，就無法專心 debug code**。`gd` 不動時你分不清是 LSP 沒 attach、缺 compile db、還是抄來的某行把 keymap 綁到別處了。你會卡在「它為什麼不動」而不是「我要怎麼讀這段 code」。

**正確做法**：自建骨架，一章加一塊，每塊都懂（這就是本課的方式）。config 出問題時你 `:checkhealth`/`:LspInfo`/`:Lazy` 五分鐘定位（Ch 29）。想要「開箱即用」而非「精通」，LazyVim 是合理選擇——但那是另一條路，且代價是黑箱。**連回 Ch 0（為什麼自建）、Ch 29（怎麼 debug）。**

### 反模式 7：裝過多外掛，拖慢啟動

**症狀**：nvim 啟動要三五秒，裝了四十個外掛，一半沒在用。

**為什麼你會這樣**：看到別人推薦的酷外掛就裝，「多一個功能總沒壞處」。

**為什麼是錯的**：每個外掛都有啟動成本和維護成本。啟動慢是小事，**維護負擔**才是大的——外掛越多，某個更新後壞掉、API 變了、彼此衝突的機率越高，你的 debug 面積越大。讀碼機器的核心就那幾個工具（telescope/treesitter/clangd/gtags/harpoon），多的都是邊際遞減。

**正確做法**：**克制**。每裝一個外掛問「這解決我讀碼的什麼具體痛點」，答不出來就別裝。定期 `:Lazy profile` 看啟動耗時、揪出拖慢的兇手（Ch 29）。本課的 config 到 Part 6 也才七個外掛——夠用。少即是快、少即是穩。**連回 Ch 29（Lazy profile）。**

### 反模式 8：偵察沒做完就一頭栽進讀函式體

**症狀**：打開一個沒看過的 repo，隨便開一個檔就開始逐行精讀。讀了半小時還不知道 main 在哪、架構怎麼分。

**為什麼你會這樣**：精讀感覺像「真的在讀碼」，偵察感覺像「還沒開始」。急著進入正題。

**為什麼是錯的**：陌生大 codebase 沒有全局印象就精讀，等於在迷宮裡隨機走。你精讀的那個檔可能根本不是核心。**偵察（telescope 看結構 + rg 找 main + document symbol 建地圖）是廣而快的，先建骨架再深入**——這是 SOP 的階段順序（`reading_code` Ch 38），不是形式主義。

**正確做法**：照 SOP 走。先偵察建全局印象（十分鐘）、再建圖、再定位到「我要讀的那幾百行」、才精讀追蹤。工具動用順序是「廣而快 → 窄而精」。**連回 Ch 28（完整流程）、`reading_code` Ch 38（SOP 階段）。**

## 怎麼用這張手冊

1. **貼在螢幕旁**，攻堅時照情境查——「要找符號」看第三/五組、「clangd 跪了」看第六組、「要外化」看第八組。
2. **一次練一組**。別想一天全記住。這週只練「移動」那組到反射，下週練「語意」。反模式 1（用方向鍵）就靠「移動」那組治。
3. **對照 Ch 28 的完整流程**——那章的鍵位表是「一次攻堅按的鍵，照時間順序」，這章是「所有鍵，照情境分類」。一個是動線、一個是字典，配著用。

## 本章重點整理

- 八個反模式的共同特徵：**短期舒適、長期昂貴**。用方向鍵、只 find_files、硬等 clangd、開一堆 tab、不外化、抄黑箱 config、裝過多外掛、跳過偵察——每個都有更快的正確做法。
- 反模式的解藥都連回具體章節：motion（Ch 3-6）、symbol/gd（Ch 19-20）、退 gtags（Ch 23-25）、harpoon（Ch 26）、notes.md（Ch 26）、自建 config（Ch 0/29）、克制外掛（Ch 29）、先偵察（Ch 28）。
- 鍵位手冊按十組情境分類，是你帶走的 cheatsheet：移動 / text object / 搜尋 / 結構 / 語意 / 後備 / 導航歷史 / 外化 / 佈局 / 維護。
- 手冊一次練一組到反射，配 Ch 28 的動線版對照用。
