# Ch 1 — 為什麼 Neovim 是讀碼機器

> **目標**：說清楚一件事——為什麼把 Neovim 當讀碼機器不是「潮」，是有硬道理的。核心論證：讀碼是**導航密集**的活，導航摩擦決定你的速度；Neovim 的模態編輯（modal editing）把導航壓到反射級。同時誠實面對它的學習曲線與「什麼時候別用它」。

> **環境**：Neovim v0.12.4，WSL2 / Ubuntu。本章是心智模型章，沒有可貼的 headless 輸出，重點在建立正確的動機與取捨判斷。

## 為什麼需要這個？

你打開這門課，八成心裡有個聲音在問：「VS Code 開個 clangd 外掛不就有跳定義了嗎？JetBrains 的 CLion 語意分析比誰都準，我幹嘛回去學一個 1990 年代的模態編輯器、還要背一堆鍵？」

這是對的問題。如果我回答不了它，這門課就不該存在。

先講結論：**讀碼不是打字密集的活，是導航密集的活**。你讀陌生 code 的時間，絕大部分不是在敲字，是在「跳」——跳到某個函式的定義、跳回原地、找這個變數在哪被寫過、開另一個檔對照著看、在一個三千行的檔裡定位某個 `if`。這些動作你一天做幾百次。**每一次動作的摩擦，乘以幾百次，就是你讀碼速度的差距。**

Neovim 憑什麼是讀碼機器？不是因為它跳定義比 CLion 準（它不見得），是因為它把**導航的摩擦壓到反射級**——游標移動即命令，全鍵盤、無滑鼠、無模式切換的心智停頓。省下來的不是打字時間，是更貴的東西：**維持思路的認知資源**。

## 先建立直覺：讀碼是一連串的「跳」

把讀一段陌生 code 的過程慢動作拆開，它長這樣：

```
   讀到 foo() 被呼叫
        │
        ▼
   「foo 在哪定義的？」──► 跳到 foo 的定義（別的檔）
        │
        ▼
   讀 foo 內部，看到它呼叫 bar()
        │
        ▼
   「bar 又是什麼？」──► 再跳進 bar
        │
        ▼
   讀懂 bar，腦中壓了個結論
        │
        ▼
   「回去看 foo 剩下的部分」──► 跳回 foo
        │
        ▼
   「回去看最初呼叫 foo 的地方」──► 跳回起點
        │
        ▼
   「這個變數 flags 到底哪裡被設的？」──► 找 flags 所有被寫的地方
```

這是一棵**深度優先搜尋樹**，你是那個在 call graph 上爬的指標。爬一遍下來，「跳進去 / 跳回來 / 找引用 / 開檔對照」這四個動作可能各做了幾十次。`reading_code` 那門課把這叫「追 data flow」與「假設驅動讀碼」——它給你**該往哪跳**的方法論；這門課給你**跳得快**的手。方法對了但手慢，你還是會累死在導航上。

關鍵洞察：**每一次跳，如果需要你「離開鍵盤去摸滑鼠、瞄準一個小圖示、點下去、再回鍵盤」，你付的不只是那零點幾秒。你付的是一次上下文切換——你的注意力從「這段 code 在幹嘛」被拉去「我的滑鼠指標在哪」。** 讀難 code 時你腦中壓著一疊假設（foo 改了這個 flag、bar 依賴那個狀態），這疊假設放在 working memory 裡，很脆弱。每一次「摸滑鼠找目標」的分心，都在動搖那疊假設。讀一天下來累的不是手，是腦。

## 核心：模態編輯是「導航模式」——從讀者角度重講

大部分 Vim 教學從**寫**的角度講模態編輯：「normal mode 不能打字，要按 `i` 進 insert mode 才能輸入。」這對讀者來說是廢話——讀碼你根本很少打字。我們換個角度講。

模態編輯的心智模型，對讀者而言是這樣：

**Neovim 開起來，預設就在 normal mode，而 normal mode 本質上是一個「導航模式」。** 你不打字的時候，整個鍵盤不是拿來輸入字元的，是拿來**下導航命令**的。每一個字母鍵都是一個動作：

- `w` / `b`：往前 / 往後跳一個詞
- `}` / `{`：往下 / 往上跳一個段落（在 C 裡常常剛好是跳過一個函式或一個 block）
- `f(`：跳到本行下一個 `(`
- `%`：跳到配對的括號（讀巢狀 block 神器）
- `gd`：跳到游標下這個符號的定義（LSP）
- `Ctrl-o`：跳回上一個位置
- `*`：找游標下這個字的下一個出現處

看出來了嗎？**在讀碼時，你的手一直放在 home row 上，游標就在整個檔案裡飛。** 沒有滑鼠、沒有方向鍵、沒有「按住往下捲」。要去哪，一兩個鍵就到。這就是「游標移動即命令」——normal mode 讓整個鍵盤變成一台**導航遙控器**。

對比一下你在滑鼠導向編輯器裡怎麼做同一件事，差距會很具體。

### 對照：同一個讀碼動作，滑鼠 vs vim motion

情境：你在讀一個檔，游標停在第 400 行看到 `parse_config(cfg)` 被呼叫，你想跳進 `parse_config` 的定義看它幹嘛，看完跳回來繼續讀第 400 行。

**滑鼠 / 一般 IDE 流程：**

1. 右手離開鍵盤，移到滑鼠
2. 移動滑鼠指標，瞄準 `parse_config` 這個字（它可能只有十幾像素寬）
3. 按住 Ctrl，點下去（或右鍵 → 選單找「Go to Definition」→ 再點）
4. 跳到定義了，讀
5. 讀完要回去——找工具列的「上一步」箭頭，滑鼠移過去瞄準、點
6. 右手移回鍵盤

六步，其中三步在「移動滑鼠並瞄準小目標」——這是最耗注意力的部分。費茲定律（Fitts's Law）說了：目標越小越遠，瞄準越慢越費神。而 code 裡的符號都是小目標。

**Neovim 流程：**

1. 游標本來就在附近，`f p` 或幾個 `w` 把游標挪到 `parse_config` 上（手沒離開 home row）
2. `gd`——跳到定義
3. 讀
4. `Ctrl-o`——跳回剛才第 400 行的**精確位置**

四步，零次滑鼠，零次瞄準。手全程在鍵盤上。而且第 4 步 `Ctrl-o` 跳回的是 jumplist 裡記錄的精確位置，不是「上一個檔的大概某處」——這是 Ch 5 的主題。

這個差距，單看一次是零點幾秒，你覺得無所謂。但你今天要跳三百次。三百次「摸滑鼠 + 瞄準 + 點 + 回鍵盤」對上三百次「`gd` / `Ctrl-o`」，省下的時間是其次，**省下的三百次注意力中斷才是關鍵**。讀完一個複雜函式後你腦中那疊假設還在，因為你的注意力沒被滑鼠拉走過。

### 再一個對照：找引用並逐一巡查

跳定義是最單純的動作。換一個更貼近真實讀碼、更能拉開差距的場景：**「這個全域變數 `g_state` 到底在哪幾個地方被寫過？我要逐一看它們有沒有漏掉 lock。」** 這是 `reading_code` 追 data flow 的典型任務——找出所有寫入點，逐一巡查。

**滑鼠 / 一般 IDE 流程：**

1. 滑鼠瞄準 `g_state`，右鍵 → Find All References（或按快捷鍵）
2. 側邊跳出一個引用清單面板，可能二十幾筆
3. 滑鼠移到面板，捲動、瞄準第一筆、點——跳過去
4. 讀這一處，判斷有沒有問題
5. 滑鼠移回面板、瞄準第二筆、點——跳過去
6. …重複二十次，每次都是「移到面板 → 捲動找位置 → 瞄準 → 點」
7. 中途想「我看到第幾筆了？」——回面板數

每一筆巡查都要一次「回面板 + 瞄準 + 點」，滑鼠在編輯區和面板之間來回二十趟。而你真正該專注的是「這一處有沒有漏 lock」，注意力卻一直被「面板在哪、我點到第幾筆了」瓜分。

**Neovim 流程：**

1. 游標放 `g_state` 上，`gr`——所有引用進 **quickfix list**（Ch 12 的主角，把搜尋結果變成一份可導航的工作清單）
2. `:cnext` 或綁好的 `]q`——跳到下一筆，讀
3. `]q`、`]q`、`]q`……一路巡下去，手不離鍵盤，quickfix 自動記著「你在第幾筆」
4. 想回頭看某筆，`:copen` 開清單、游標選、`<CR>` 跳

差別不只在「快」。差別在**引用清單變成了一條你用鍵盤就能一路走完的軌道**，注意力全程黏在「這處有沒有漏 lock」，而不是「面板在哪」。二十筆巡完，你腦中那張「哪些地方碰 `g_state`」的地圖是清晰的，因為建這張地圖的過程沒被導航偷走注意力。這是 Ch 12「把搜尋變工作清單」的威力預告，也是為什麼這門課把 quickfix 當一個核心主題。

## 導航密集到底有多密集：一段真實讀碼的計數

「一天幾百次」聽起來像誇飾，我們把它算清楚。假設你在讀 nginx 的請求處理，任務是「搞懂一個 HTTP 請求從進來到被某個 handler 處理，中間經過哪些函式」。這是 `reading_code` 那門課「追一條路徑」的典型任務。你實際會做的導航動作，粗略記一下：

- **跳定義**：每遇到一個沒看過的函式呼叫就 `gd` 跳進去。一條中等深度的呼叫鏈輕鬆十幾層，加上每層裡又有旁支函式想確認，`gd` 用個三、四十次不誇張。
- **跳回**：每跳進去看完就 `Ctrl-o` 跳回，跟 `gd` 幾乎一比一，又是三、四十次。
- **找引用**：「這個 `ngx_http_request_t` 的 `phase_handler` 欄位是誰設的？」`gr` 找所有引用，一次任務問個五到十次。
- **本檔內移動**：`}`/`{` 跳段落、`f`/`;` 跳字元、`/` 搜尋、`%` 配對括號——讀每個函式內部都在用，累積上百次。
- **開檔對照**：header 看型別定義、`.c` 看實作，`:e`/telescope 開檔、window 分割對照，一次任務十幾次。

一個小時的專注讀碼，光是有意識的「跳」就三、四百次，還沒算本檔內的細微游標移動。**這不是誇飾，這就是讀碼的本質——你 90% 的時間在導航與閱讀，10% 都不到在打字。** 現在把 Ch 1 開頭那個乘法補完：每個動作的摩擦 × 這個次數 = 你讀碼的速度與續航。一個摩擦低 30% 的導航系統，在這個量級上不是「快一點點」，是「同樣時間你多讀懂一倍，或同樣進度你少累一半」。

這也是為什麼「偶爾讀 code 的人不划算、每天讀的人回本」——回本的門檻就卡在這個「次數」上。次數夠大，摩擦差才會複利成有感的差距。

## 讀者角度的 motion 全景：你其實只需要一小把鍵

新手看到 vim 幾百個命令會怕。但**讀碼者**用到的其實是很小一把，而且都是「移動」與「選結構」這兩類，不是編輯。先給你一張全景，讓你知道要練的沒那麼多，Part 1 會逐一深教：

| 讀碼場景 | 你會用的核心鍵 | 這是哪一章 |
|---|---|---|
| 檔案內大跳（到檔頭/檔尾/某行） | `gg` `G` `{行號}G` | Ch 3 |
| 一格一格精準挪（詞/句/段） | `w` `b` `e` `}` `{` | Ch 3 |
| 本行內瞄一個字元跳過去 | `f{char}` `;` `,` `t` | Ch 3 |
| 選中一個結構（括號內、函式、參數） | `i(` `a{` `if`（treesitter） | Ch 4、Ch 14 |
| 跳定義 / 跳回 / 找引用（語意） | `gd` `Ctrl-o` `Ctrl-i` `gr` | Ch 5、Ch 19 |
| 檔內搜尋 / 找同名符號 | `/` `?` `n` `*` `#` | Ch 6 |
| 跨檔找（模糊找檔/全文） | `<leader>ff` `<leader>fg`（telescope） | Ch 9 |

看清楚了嗎？**讀碼的核心鍵就這一小把，全是導航。** 編輯類的 `d`/`c`/`y` 你讀碼時幾乎不碰。所以「vim 學習曲線陡」對讀者來說被高估了——你不用學那幾百個編輯命令，你要練的是這張表，練到變反射。這門課 Part 1 到 Part 6 就是把這張表一格格填滿、接上 config、練成肌肉。

## 為什麼省的是「認知資源」而不是「時間」

Ch 1 一直強調：Neovim 省的不是打字時間，是**維持思路的認知資源**。這句話值得展開，因為它是整個論證的核心，也是最容易被說成空話的一句。

先講認知科學的骨架（`reading_code` 的《The Programmer's Brain》講得更細）。人讀 code 時，腦裡有一塊很小、很脆弱的**工作記憶（working memory）**，一次只裝得下大約幾個「chunk」。你讀一個複雜函式時，工作記憶裡壓著一疊東西：「這個 lock 在進來前已經拿了」「這個 flag 等於 2 代表 error path」「上一層傳進來的 buffer 可能是 NULL」——這些是你當前理解的鷹架，一旦掉了，你就得回頭重讀。

關鍵在於：**工作記憶對「中斷」極度敏感。** 每一次你把注意力從「這段 code 在幹嘛」切換到「我的滑鼠指標在哪、我要點哪個小圖示」，就是一次上下文切換，那疊脆弱的鷹架會鬆動一格。切換多了，鷹架垮了，你發現「欸我剛剛讀到哪、那個 flag 是幹嘛的」——於是回頭重讀。**重讀才是讀碼最大的時間黑洞，比任何單一動作的耗時都貴。**

所以無滑鼠導航真正省的東西是這樣運作的：`gd` / `Ctrl-o` 這種「手不離鍵盤、不用瞄準」的跳轉，幾乎不占用你的注意力——它像眨眼一樣是背景動作，不會把注意力從 code 上拉走。你的工作記憶那疊鷹架**全程不動**，因為導航沒有偷走它的注意力。於是你能連續讀十幾層深的呼叫鏈而不迷失，讀完回到起點時，腦中那疊假設還完好。這就是「維持思路」的字面意思。

反過來說，這也解釋了一個現象：為什麼有人用 IDE 讀難 code 會覺得「讀得很累、很容易分心、常常要回頭」。不是他不夠聰明，是他的導航系統一直在偷他的注意力。**摩擦不是消耗在手上，是消耗在腦上——而腦是讀碼真正的瓶頸資源。** Neovim 把導航壓到反射級，等於把這個瓶頸資源省下來，全投給「理解 code」本身。這才是它值得學的根本理由，也是為什麼這件事很難用「快了幾秒」量化——省下的是續航與專注，不是碼表上的數字。

## 底層機制：為什麼「模式」反而降低摩擦，而不是增加

新手最大的抗拒是：「有模式不是很麻煩嗎？我還要記現在在哪個模式、還要切來切去。」這是個真實的成本，但方向反了。我們把它想清楚。

無模式編輯器（VS Code、記事本）的設計前提是：**鍵盤主要拿來輸入字元**，所有命令都得靠修飾鍵（Ctrl/Alt/Cmd + 某鍵）或滑鼠選單。這在**寫**的時候合理。但代價是：能綁給命令的鍵位很有限（就那幾個修飾鍵組合），所以複雜操作要嘛靠很長的組合鍵、要嘛靠滑鼠選單。

模態編輯翻轉了這個前提：**normal mode 假設你「預設在下命令」，不是在打字。** 於是整個鍵盤——26 個字母、數字、符號——全都空出來當命令用。這就是為什麼 vim 的導航命令可以短到一兩個鍵：`w`、`b`、`}`、`gg`、`G`、`%`。而且它們能**組合**成一種語言：`d}`（刪到段落尾）、`ci(`（改括號內內容）、`3w`（往前三個詞）——動詞 + 對象 + 次數的語法。讀碼時你主要用它的名詞和移動那半（motion 與 text object，Ch 3、Ch 4），但同一套語法，動一次腦全都通。

所以「切模式的成本」換來的是「整個鍵盤變成低摩擦命令空間」。對一個**導航密集**的任務（讀碼），這筆交易划算得離譜。切模式本身，練到後來是反射，你不會意識到自己按了 `i` 或 `Esc`——就像你打字不會意識到自己按了 shift。

> 這裡有個常被誤解的點：模態編輯的價值不在「按鍵少所以打字快」。讀碼你根本不打字。價值在「導航命令不需要修飾鍵、不需要離開 home row、可組合」，所以在檔案裡移動這件事的摩擦趨近於零。把 vim 當「打字更快的工具」是外行的理解，它真正的殺傷力在**移動**。

## 誠實面對：學習曲線與「裸 nvim 不好用」

我不會騙你這條路很平。兩個真實成本，先講在前面：

**成本一：模態編輯是真的要練。** 頭幾天你會一直在 insert mode 想按 `w` 結果打出一堆 w、或在 normal mode 想打字結果游標亂跳。這個「肌肉還沒長出來」的階段大概一到兩週會很不舒服。撐過去之後它變成反射，你回頭用滑鼠編輯器會覺得慢得難受。這是所有 vim 老手都經歷過的谷底，沒有捷徑，只有 `nvim +Tutor` 跑一遍加上真的拿檔案來按。Part 1 就是帶你度過這個谷底。

**成本二：裸 nvim 對讀碼真的不好用，要配。** 你 `apt install neovim` 開起來，沒有跳定義、沒有模糊找檔、沒有語法感知的高亮，就是個純文字編輯器。它的讀碼能力**全部來自 config 與外掛**——clangd（語意）、telescope（搜尋）、treesitter（結構）、gtags（後備）。這就是為什麼 Ch 0 花整章搭 config 骨架、為什麼這門課叫你自己搭而不是抄黑箱發行版。**Neovim 是引擎，讀碼機器是你組出來的。** 開箱即用不是它的賣點；可以組成一台你完全懂、能改、能 debug 的機器才是。

**成本三：偶爾工具會壞，你得會 debug 工具本身。** clangd 某天不 attach 了、treesitter parser 版本對不上、某個外掛更新後行為變了——這些會發生。用 IDE 你只能等官方修；用自己組的 Neovim，你有能力（也有責任）自己查。這門課花不少篇幅教你怎麼分辨「是工具壞了還是 code 難讀」（`:checkhealth`、`:LspInfo`、Ch 29 除錯 config），因為**工具卡住時你 debug 不了工具，就無法專心 debug code**。這是自己組機器的代價，也是它給你的能力——你的機器沒有黑箱，壞了你修得動。

這三個成本都是真的。願不願意付，取決於你讀碼的量。如果你一週只讀一次別人的 code，別付——這門課不划算，下一節講。

至於怎麼度過成本一的谷底，給你一條具體路徑，不要用意志力硬撐：**第一步 `nvim +Tutor` 完整跑一遍（30 分鐘，把手放對位置）。第二步別急著讀難 code，先拿你已經熟的一個檔，強迫自己全程不碰滑鼠、不碰方向鍵，用 `w`/`b`/`}`/`gg`/`G` 移動，撞牆就查 `:help`。第三步才拿陌生 code 練。** 關鍵是「熟檔 + 限制手段」——在你已經懂內容的檔上練 motion，你的腦不用同時處理「讀懂」和「怎麼移動」兩件事，肌肉長得快。一到兩週後 motion 變反射，你才把它用到真正的攻堅上。這條路徑 Part 1 會帶你走一遍。

## 三個常見反駁，逐一回應

在你決定投不投資之前，把幾個最常見的反駁攤開講清楚。這些不是稻草人，是每個考慮學 Neovim 的人真的會問的。

**反駁一：「現在 AI 都能幫我讀 code 了，Copilot / Claude 讀給我聽，還練 motion 幹嘛？」**

AI 很強，但它改變的是「該往哪跳、這段在幹嘛」的**理解層**，沒有取消「你自己要在 code 裡導航」的**操作層**。你問 AI「這個函式在幹嘛」，它回你一段解釋——然後你還是得跳到它提到的三個相關函式親自確認（AI 會錯、會過時、會漏 edge case，尤其在大型 C 專案）。AI 給你假設，你還是得驗證，而驗證就是導航。更進一步，AI 輔助讀碼（`reading_code` Ch 20）本身就是在編輯器裡進行的——你要把 code 貼給它、拿它的答案回去對照 code、跳去它指的地方。導航摩擦低，你跟 AI 的來回也順。AI 不但沒讓 motion 過時，反而讓「快速在 code 裡驗證 AI 說法」變得更值錢。

**反駁二：「VS Code 也有 Vim 外掛（VSCodeVim），我裝那個不就兩全其美？」**

VS Code 的 Vim 模擬外掛能給你 normal mode 和基本 motion，對「淺嚐模態編輯」是合理起點。但它有兩個天花板。其一，它是**模擬**，很多進階 motion、text object、以及與 quickfix/jumplist 的深度整合要嘛沒有、要嘛行為不對，你練到一半會撞牆。其二，也是更根本的——它終究活在 VS Code 的架構裡，你拿不到這門課後面講的那些「Neovim 特有的讀碼機器組裝」（treesitter textobjects 依結構移動、gtags 後備、session/佈局工作流、自己懂的 config）。VSCodeVim 適合「我想在 VS Code 裡打字快一點」；不適合「我想把編輯器組成一台讀大 codebase 的機器並精通它」。目標不同。

**反駁三：「Neovim 看起來就是給喜歡折騰、想炫技的人玩的，實用性存疑。」**

這個印象有現實根據——網路上確實一堆人把 Neovim 當「無限客製的玩具」，花一週調 config 只為了讓狀態列多個圖示。這門課明確**不走那條路**。我們不折騰視覺、不追潮流外掛、不比誰的 config 行數多。我們只做一件事：把 Neovim 配成讀大型 C 專案的機器，config 每一行都為讀碼服務、每一行你都懂。Ch 0 選 kickstart 精神而非炫酷發行版，就是這個態度。實用性不是存疑，是這門課的唯一標準——不服務讀碼的東西，一律不進你的 config。

回應完這三個，你該有的判斷是：Neovim 讀碼的價值是真的，但它不是給每個人的，也不是拿來炫的。它是給「每天讀大 codebase、把讀碼當核心技能、活在終端」的人的一件趁手工具。下一節把「什麼時候別用」也說清楚，你就能誠實決定。

## 對比與取捨：什麼時候 Neovim 不划算

工具沒有銀彈。誠實地標出 Neovim **不該用**的場景，比吹它更有用。

| 場景 | 更好的選擇 | 為什麼 |
|---|---|---|
| **只偶爾讀一點 code**（一週一兩次） | VS Code | 學習曲線攤不平。VS Code 裝個 clangd 外掛，滑鼠點點就能跳定義，夠用。模態編輯的投資要靠「每天讀」才回本。 |
| **要深度 C++ 語意**（call hierarchy、繼承樹、template 實例化點一點就展開） | JetBrains CLion | JetBrains 的靜態分析引擎在大型 C++ 專案上比 clangd 更強更穩，call hierarchy 的 UI 也更成熟。重度 C++ 讀者，這是務實選擇。 |
| **完全不碰終端、GUI 至上** | VS Code / IDE | Neovim 的家在終端與 SSH。你若整天在 GUI、遠端開發也用 VS Code Remote，硬套 nvim 是逆水行舟。 |
| **在 WSL / SSH / 遠端主機讀大型 C 專案**（kernel、nginx、embedded） | **Neovim** | 這才是它的主場。終端原生、SSH 進去就有全套、無滑鼠延遲、config 一份帶著走。 |
| **每天讀陌生大型 codebase、追求導航反射級** | **Neovim** | 導航摩擦最低、鍵位可完全客製成你的讀碼肌肉、與 rg/gtags/git 等 CLI 工具無縫串。本課的目標讀者。 |

看清楚這張表的用意：**如果你落在前三行，這門課大概不適合你，我寧可你別浪費時間。** 這門課是為落在後兩行的人寫的——WSL、終端、系統/資安/RE 取向，每天要讀 kernel / Lua / nginx / CPython 這種大型 C 專案，把讀碼當核心技能練的人。你若是這種人，往下讀，這台機器會很值得。

還有一個關鍵取捨要說清楚：**Neovim 的語意能力（跳定義準不準）不是它自己的，是 clangd 的。** clangd 在有 `compile_commands.json` 的專案上，跳定義、找引用跟 CLion 是同一個等級（它們背後都是 Clang 的語意引擎）。差別在 UI 打磨與極端 C++ 場景的穩定度。所以「Neovim 跳定義不準」多半不是 Neovim 的錯，是 clangd 沒吃到 compile database——這正是 Ch 18 要解決的。把責任歸對地方，你才 debug 得了工具。

## 這門課是 reading_code 的「手」：SOP 對應到操作

這門課不是獨立存在的，它是 `reading_code` 那套讀碼 SOP 的**執行層**。`reading_code` 教你「該做什麼」，這門課教你「用哪個鍵快速做到」。把它們對起來，你就知道自己在練的每個 motion 服務的是哪個讀碼策略——這也是為什麼 Ch 1 這麼早就要建立這個連結：你不是在學鍵位，你是在給一套已知的方法論裝上快手。

| `reading_code` 的 SOP 步驟 | 在 Neovim 裡對應的操作 | 本課哪裡教 |
|---|---|---|
| **偵察**：60 分鐘摸清架構、找 entry point | telescope 找檔/找符號、`:grep`/rg 掃關鍵字、treesitter outline 看檔案骨架 | Part 2、Ch 20 |
| **找 entry point / 主迴圈** | 全文搜尋 `main`/`init`、跳定義一路往下 `gd` | Ch 6、Ch 19 |
| **追 data flow**（順藤摸瓜一個變數） | `gr` 找所有引用 → quickfix 逐一巡查、`*` 找同名 | Ch 12、Ch 19 |
| **追 control flow / call graph** | `gd` 跳進、`Ctrl-o` 跳回、call hierarchy | Ch 5、Ch 19 |
| **假設驅動**：標下「我猜這裡是…」再驗證 | marks/harpoon 標攻堅點、跳回驗證 | Ch 26 |
| **外化理解**：把地圖記在腦外 | marks、quickfix 當工作清單、多 window 對照 | Ch 7、Ch 12、Ch 26 |
| **收斂到你要改的那 200 行** | 搜尋 + 語意跳轉逐步縮小、session 記住佈局 | Part 2、Ch 27 |

看這張表的用意：**每一個你之後會練到手痠的 motion，背後都有一個 `reading_code` 的策略目的。** 你練 `gr` + quickfix 不是為了炫技，是為了「追 data flow」這件具體的事跑得快。方法（reading_code）× 手速（本課）才是完整的讀碼能力——這門課補的是後半，前半請回去看那門課，兩邊合起來讀。

## 踩雷集錦

1. **以為 Neovim 快在「打字快」**：讀碼你幾乎不打字，這個賣點對你無關。它對讀者的價值在**導航摩擦低**。抱著「打字更快」的期待來學，你會抓不到重點、也練不到該練的（motion 與 text object，不是輸入速度）。
2. **裸開 `nvim` 就想跳定義，發現不能，斷定「Neovim 不能讀碼」**：裸 nvim 是引擎不是整車，讀碼能力全靠 config。你少了 clangd / telescope / treesitter。先做完 Ch 0 的 config 骨架再評價。
3. **頭三天很痛就放棄**：模態編輯有個「肌肉還沒長」的谷底，一到兩週。這是所有人都經歷的，不是你不適合。撐過去它變反射。放棄在谷底最不划算——投資都付了、回報還沒到。
4. **明明只偶爾讀 code 卻硬學 Neovim**：這門課對你不划算，別勉強。工具要配任務。你若不是每天讀大 codebase，VS Code + clangd 外掛是更理性的選擇——這不是背叛，是務實。
5. **把「Neovim 跳定義不準」全怪 Neovim**：多半是 clangd 沒吃到 `compile_commands.json`。語意能力來自 clangd，不是 Neovim 本身。怪錯對象你就永遠 debug 不好（Ch 18）。
6. **一開始就想把 config 調到完美**：新手常犯的反向錯誤——還沒開始讀 code，先花三天挑外掛、調配色、比較發行版。這是把手段當目的。config 從 Ch 0 的最小骨架起步就夠讀碼了，其他一章加一塊、用到了才加。你要練的是 motion 和導航肌肉，不是 config 手藝。把時間花在「拿真檔按到反射」，不是花在「讓狀態列多個圖示」。
7. **練 motion 卻挑陌生難 code 練**：谷底期拿陌生 code 練 motion，你的腦要同時處理「讀懂內容」和「怎麼移動」，兩頭燒，挫折感爆表然後放棄。先拿**你已經熟的檔**練移動——腦不用管內容，肌肉長得快。熟了再上陌生 code。

## 進階：再往深一層

- **模態編輯是一種「動詞-對象」語言，不是一堆快捷鍵**：`d`（delete）、`c`（change）、`y`（yank）是動詞，`w`（word）、`}`（paragraph）、`i(`（inside parens）是對象，組合出 `dw`、`c}`、`yi(`。讀碼時你主要用移動與 text object 那半，但理解它是「語言」而非「快捷鍵表」，你才學得會舉一反三、才不用死背。Ch 3、Ch 4 展開。
- **導航摩擦低的複利效應**：把讀碼想成一次幾百步的搜尋，每步摩擦降低 30%，複利下來是整體讀碼速度與續航的顯著差距。這也是為什麼 `reading_code` 強調「讀碼是速度技能」——速度來自方法（該往哪跳）× 手速（跳得多快），這門課補的是後者。
- **同一套導航肌肉，source 與 binary 兩邊通用**：你在 nvim 裡練出的 motion / jumplist / 搜尋肌肉，讀反組譯輸出（objdump、gdb disassembly 貼進 nvim）時一模一樣好用。`reverse_engineering` 那條線會回頭吃這門課的紅利——讀 source 用 nvim + clangd/gtags，讀 binary 用 nvim + 反組譯，同一雙手。
- **摩擦低讓你敢做「探索式導航」**：這是常被忽略的二階效應。當跳定義、跳回的成本趨近於零，你會更**願意**去跳——「這個函式我不確定，跳進去瞄一眼再回來」變成一個你隨手就做、不用權衡的動作。在高摩擦的環境裡，你會下意識地省著跳（因為每次跳都要摸滑鼠、瞄準、之後還要找路回來），結果是你偷懶不去確認、憑猜測讀碼、然後讀錯。低摩擦不只讓你跳得快，它改變你的讀碼**行為**——讓你變成一個更勤於驗證假設的讀者。這正好餵養 `reading_code` 的「假設驅動」：假設便宜到可以隨時驗，你才會真的去驗。
- **終端原生 = 讀碼環境可攜、可重現**：你的整台讀碼機器是一份 `init.lua` 加一個 `lazy-lock.json`（鎖住每個外掛的 commit）。SSH 進任何機器、任何 WSL、任何容器，`git clone` 你的 config、`nvim --headless "+Lazy! sync" +qa`，五分鐘後你在陌生主機上有一台一模一樣的讀碼機器。這對「今天在本機讀、明天 SSH 進 server 讀 kernel」的系統/資安工作流是實打實的優勢——GUI IDE 做不到這種「一份文字檔就是整個環境」的可攜性。這也呼應 `reading_code` 的可重現性信條（釘 commit、環境一致）。

## 動手體驗：量一下你自己的導航摩擦

這章沒有 config 可跑，但有個實驗能讓「導航摩擦」從抽象變具體，值得花五分鐘做一次——它會決定你要不要繼續這門課。

在你**現在習慣的編輯器**（VS Code、IDE，什麼都行）裡，找一個你正在讀或讀過的中型 C/C++ 專案，開一個檔，做這件事並**留意你的手和注意力**：

1. 挑一個檔案中段的函式呼叫，跳到它的定義。留意：你的右手離開鍵盤幾次？瞄準了幾次？
2. 跳回原來的位置。留意：你怎麼回去的？是準確回到剛才那一行，還是「大概那附近」？
3. 挑一個變數，找出它所有被引用的地方，逐一看過。留意：巡查二十筆的過程，你的注意力有幾次從「這處在幹嘛」被拉去「我點到第幾筆了、面板在哪」？

做完，誠實回答自己一個問題：**這三件事裡，有多少精力花在「操作編輯器」而不是「理解 code」？** 如果答案是「不少」，而你又每天做這些幾百次——那這門課要幫你省的，就是那部分精力。如果答案是「幾乎沒有，我的工具已經很順」，那你可能真的不需要 Neovim，這門課對你邊際效益有限。這個實驗的目的不是說服你，是讓你用自己的手替自己決定。

## 本章重點整理

- **讀碼是導航密集的活，不是打字密集的活**：跳定義、跳回、找引用、開檔對照，一天幾百次；導航摩擦決定速度。
- **Neovim 的殺傷力在導航，不在打字**：normal mode 是「導航模式」，整個鍵盤變成低摩擦命令空間，游標移動即命令，全鍵盤無滑鼠。
- **省的不是時間，是認知資源**：每次「摸滑鼠瞄準」都是一次注意力中斷，會動搖你腦中那疊脆弱的假設。無滑鼠導航保住思路。
- **成本要誠實面對**：模態編輯要練一到兩週的谷底；裸 nvim 不好用、讀碼能力全靠 config 與外掛（clangd/telescope/treesitter）。
- **它不是萬用**：只偶爾讀 → VS Code；重度 C++ 語意點一點 → JetBrains；每天讀大型 C 專案、終端/WSL 取向 → Neovim 才回本。
- **語意能力來自 clangd 不是 Neovim**：跳定義不準多半是缺 compile database，怪對對象才 debug 得了。
- **這門課是 `reading_code` 的「手」**：方法（該往哪跳）× 手速（跳得多快）才是完整的讀碼能力，每個 motion 都對應一個讀碼策略，不是為了炫技。
- **摩擦低改變行為**：跳轉便宜到隨手就做，你才會勤於驗證假設而不憑猜測讀碼——這是低摩擦的二階效應。
- **終端原生 = 環境可攜可重現**：一份 `init.lua` + `lazy-lock.json`，SSH 進任何主機五分鐘重建同一台讀碼機器。
