# Ch 40 — 面試拆題流程：從讀題到寫 code

> 目標：建立一套可重複的面試答題流程，讓你在壓力下也能有條理地展示思維。

## 為什麼需要流程？

面試中的壓力會讓人直接跳到「寫 code」，結果：
- 漏看題目條件
- 邊界 case 沒考慮
- 思路說不清楚，讓面試官不放心

有流程，就有「下一步要做什麼」的錨點，不會慌。

## 五步流程（RUCTS）

### R — Read & Repeat（讀題並複述）

用自己的話把題目說一遍，確認理解正確。

「所以題目是：給一個整數陣列，找一個最短的連續子陣列，使得它的總和 ≥ S，對嗎？」

這步的目的：
- 確認你沒有誤讀（面試官這時會糾正你）
- 讓面試官看到你「先理解再動手」

### U — Understand constraints（確認邊界條件）

主動問或口頭確認：

- 輸入範圍？（n = 10⁵？10⁶？影響複雜度要求）
- 有沒有負數？空陣列？重複元素？
- 答案保證存在嗎？不存在回傳什麼？

**不要假設**。面試中問這些問題是加分的，說明你思考嚴謹。

### C — Consider brute force（說出暴力解）

先說暴力解的思路和複雜度：

「暴力解是枚舉所有子陣列，O(N²)。」

然後說為什麼不夠：「題目說 n = 10⁵，O(N²) 會超時，需要更好的解法。」

這步讓面試官確認你的基礎是對的，也給你時間思考優化。

### T — Think out loud（邊想邊說）

優化的思考過程說出來：

「我在想能不能用 Sliding Window...題目是找最短的，所以是可變窗口...收縮條件是 sum >= S...」

面試官不只看你能不能解題，也看你怎麼思考。說出思路讓他們能介入引導。

### S — Solve & Test（寫 code，然後測試）

**寫 code 時**：
- 先寫函式簽名和 base case
- 再寫主邏輯
- 遇到複雜的細節（如索引計算），口頭說「這裡要小心 off-by-one，讓我確認一下」

**寫完後必做**：
- 自己跑一個例子（在紙上或在 code 旁邊追蹤）
- 說複雜度：「時間 O(N)，空間 O(1)」
- 主動說出 edge case：「如果陣列是空的，這裡 return 0；如果 n=1，...」

## 時間分配建議

| 階段 | 時間 |
|---|---|
| R + U（讀題 + 確認） | 2–3 分鐘 |
| C（暴力解） | 1–2 分鐘 |
| T（思考優化） | 5–8 分鐘 |
| S（寫 code + 測試） | 10–15 分鐘 |

總計約 20–25 分鐘，符合大多數面試的節奏。

## 說複雜度的方式

不要只說「O(N)」，要說清楚：

「外層迴圈跑 N 次，每個元素最多進出 sliding window 各一次，所以總時間是 O(N)，空間是 O(1)。」

面試官想聽的是你「知道為什麼」，不是死背答案。

## 常見失誤 + 對策

| 失誤 | 對策 |
|---|---|
| 直接開始寫，沒說思路 | 強迫自己先說「我打算用 X，因為 Y」 |
| 寫完沒測試 | 寫完後說「讓我跑一個例子確認」 |
| 邊界 case 漏掉 | 寫完後問自己：空輸入？n=1？全部相同？ |
| 想不出優化，沉默 | 說「我先從暴力解開始，同時想有沒有更好的方法」 |
| 複雜度分析說不清楚 | 先說資料結構的操作複雜度，再說迴圈次數 |

## 卡住了怎麼辦？

主動說出你卡在哪裡：

「我現在的問題是：我需要在 O(N) 內找到每個元素右側第一個更大的值，但我想不到比 O(N²) 更好的方法...」

面試官通常會給一個提示（如「想想 Stack 能不能幫上忙」），這不代表失分，代表你能清楚表達卡點。
