# Ch 13 — Core dump 與 post-mortem

> 目標：熟練 core dump 的產生、用 gdb 開 core 做 post-mortem 分析，理解 core 檔裡到底存了什麼、又缺什麼。

## 什麼是 core dump

程式 crash 時（特別是 SIGSEGV、SIGABRT、SIGBUS、SIGFPE），Linux kernel 把 process 的**整個記憶體狀態 + 暫存器 + 一些 metadata** dump 到檔案 — 這就是 **core dump**。

你可以之後用 gdb 打開這個檔，**重建當時現場**：bt、看變數、看 memory、看 register。Process 早已死，但你能做 forensics。

**為什麼重要**：

- **難重現 bug 的救命稻草**：生產環境偶發 crash，不能在 prod 開 gdb；留 core、拿回辦公室慢慢看
- **客戶回報的 crash**：「我這邊跑你的程式會爆」。叫他 send 個 core 檔比你 remote debug 容易 100 倍
- **學習工具**：core 是靜態的，不會逃，可以慢慢看

## 確認 core dump 開啟

Linux 預設可能把 core size limit 設成 0（不寫 core）。確認：

```bash
$ ulimit -c
0            # 0 = 不寫
```

0 就要改：

```bash
ulimit -c unlimited
```

或寫到 `/etc/security/limits.conf` 讓它持久。

## 確認 core 寫到哪

```bash
$ cat /proc/sys/kernel/core_pattern
|/usr/share/apport/apport %p %s %c %d %P
```

Ubuntu 可能用 apport 攔截；CentOS 可能用 systemd-coredump。我們學習階段要**純 core 檔**：

```bash
# 臨時
sudo sysctl -w kernel.core_pattern=core.%p

# 永久
echo "kernel.core_pattern=core.%p" | sudo tee /etc/sysctl.d/50-coredump.conf
sudo sysctl -p /etc/sysctl.d/50-coredump.conf
```

`%p` = pid、`%s` = signal、`%e` = exe 名。更多 format 在 `man core`。

## 產生一個 core

寫個一定 crash 的：

```c
// crasher.c
#include <stdio.h>

int dereference(int *p) {
    return *p;                    // deref NULL
}

int main(void) {
    int *p = NULL;
    return dereference(p);
}
```

```bash
gcc -g crasher.c -o crasher
ulimit -c unlimited
./crasher
Segmentation fault (core dumped)
```

如果你看到 `(core dumped)`，有了。在當前目錄找 `core` 或 `core.12345`：

```bash
$ ls core*
core.12345
```

systemd-coredump 可能把 core 收到 `/var/lib/systemd/coredump/` 壓縮存放。用 `coredumpctl` 取出：

```bash
coredumpctl list
coredumpctl gdb crasher             # 直接開 gdb debug 最近一個 core
coredumpctl info <PID>
```

## 打開 core：`gdb <binary> <core>`

```bash
gdb -q ./crasher core.12345
```

輸出：

```
Reading symbols from ./crasher...
[New LWP 12345]
Core was generated by `./crasher'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  dereference (p=0x0) at crasher.c:4
4           return *p;
(gdb)
```

你現在站在 **crash 的那一瞬間**。所有 Ch 2–Ch 5 學的指令（bt、print、info locals、frame）都可用。

```
(gdb) bt
#0  dereference (p=0x0) at crasher.c:4
#1  0x000055abc...11f8 in main () at crasher.c:9

(gdb) frame 1
(gdb) p p
$1 = (int *) 0x0
```

**唯一能做的是看 — 沒法 `continue` 或 `step`**。inferior 不存在了，只是一個 snapshot。

## core 檔裡有什麼

core 檔是 ELF 格式，用 `readelf` 看：

```bash
$ readelf -hn core.12345
ELF Header:
  Type:                              CORE (Core file)
  ...
Displaying notes found at file offset 0x... with length ...
  Owner                Data size   Description
  CORE                 0x0000000a8 NT_PRSTATUS (prstatus structure)
  CORE                 0x000000088 NT_PRPSINFO (prpsinfo structure)
  CORE                 0x000000200 NT_FPREGSET (floating point registers)
  CORE                 0x000000440 NT_X86_XSTATE (x86 XSAVE extended state)
  CORE                 0x000000080 NT_SIGINFO
  CORE                 0x000000178 NT_FILE
  ...
```

關鍵 note：

| Note | 內容 |
|---|---|
| `NT_PRSTATUS` | 暫存器（per thread） |
| `NT_PRPSINFO` | Process info（pid、uid、command line） |
| `NT_FPREGSET` | 浮點暫存器 |
| `NT_SIGINFO` | crash 的 signal 資訊（什麼 signal、什麼位址） |
| `NT_FILE` | 當時載入的檔案列表 |
| `NT_AUXV` | auxiliary vector（環境資訊） |

除了這些 notes，core 裡還有**所有 writable memory** 的實際 content（heap、stack、data）。**唯讀段（例如 `.text`、code）通常不存**，gdb 開 core 時會從 binary 檔補回。

這就是為什麼 **debug core 必須有原始 binary**：core 只有「會變的」部分，靜態的部分要靠 binary 補回。

## 看 core 當時的 signal

```
(gdb) info program
Using the running image of child process 12345.
...
```

或：

```
(gdb) p $_siginfo
$1 = {si_signo = 11, si_errno = 0, si_code = 1, ..., si_addr = 0x0}
```

`si_signo = 11` 是 SIGSEGV、`si_addr = 0x0` 是「嘗試 access `0x0`」— 跟我們 code 裡的 NULL deref 吻合。

## 多 thread 的 core

如果 crash 發生在 multi-thread 程式，core 會記所有 thread 的狀態：

```
(gdb) info threads
  Id   Target Id            Frame
  1    Thread 0x... (LWP ...)  __GI_raise (...) at ...
* 2    Thread 0x... (LWP ...)  dereference (p=0x0) at crasher.c:4
  3    Thread 0x... (LWP ...)  __futex_wait ...
```

`*` 是 crash 當下的 thread，gdb 自動切過去。你可以 `t 3` 切到其他 thread 看它們當時在幹嘛。

這對 deadlock 在 crash 前留下 core 特別有用：可以看到所有 thread 當下 stuck 在哪。

## 生 core 的三種途徑

### 1. Kernel 因 fatal signal 自動生

SIGSEGV、SIGABRT、SIGFPE、SIGILL、SIGBUS、SIGTRAP（非 debugger 設的）、SIGQUIT 等會觸發。

### 2. 主動 `abort()`

```c
#include <stdlib.h>
abort();
```

發 SIGABRT 給自己，產生 core。`assert()` 失敗內部就是呼叫 abort。

### 3. 用 `gcore` 對跑中的 process 生 core（不 kill）

```bash
gcore <PID>                   # 產生 core.<PID> 在當前目錄
gcore -o mycore <PID>         # 指定檔名
```

process 繼續跑。**這是生產環境的黃金工具**：當你發現某 process 狀態異常但還沒 crash，`gcore` 留一份 snapshot、之後慢慢分析，process 繼續服務。

或在 gdb 裡：

```
(gdb) generate-core-file
(gdb) gcore /tmp/snapshot.core
```

## Minidump — 跨平台簡化版

Google 的 Breakpad / Crashpad 產的 crash 紀錄不是傳統 core，而是 minidump — 裁剪版，只留 thread state 與部分 memory。gdb 不能直接讀，但 Breakpad 工具 `minidump_stackwalk` 可以轉換。

這是 Chrome、Firefox、各種 game engine 的現代做法（core 太大不適合網路傳）。學習階段還是用標準 core。

## 限制：core 裡沒有的東西

core 是 snapshot，不是錄影：

- 沒有**執行歷史**（不能 reverse-step）
- 沒有被 `munmap` 的記憶體
- 沒有 **kernel 端**狀態（open file descriptor 數量可見，但 file content 不見）
- 沒有其他 process 的狀態
- 沒有網路 socket 的對端狀態

所以 core 告訴你「當下是這樣」，但「怎麼變成這樣」你要靠 bt + code review 推論。

## Core 分析的工作流

1. `gdb binary core.file`
2. `bt` 看呼叫鏈
3. `info threads` 看是不是 multi-thread，其他 thread 在做什麼
4. `frame N` 切到有 state 的層，`info locals` / `p vars`
5. 看 heap：`p some_global`、追 linked list、看 data structure consistency
6. 看 stack：`x/64gx $rsp` 找奇怪的值（指標指向不該指的地方）
7. 看 register：`info registers`，看 rax / rdi 等暗示參數
8. 拼出故事：rdi 是這個值 → 是 foo 傳進來的 → foo 是誰呼叫？回 bt frame N → 追到源頭

## 一個實戰：compressed core

生產環境 core 通常很大（對記憶體多 GB 的 service，core 可以幾十 GB）。一般會 gzip：

```bash
gzip core.12345                     # 變 core.12345.gz
```

gdb 不能直接讀 .gz，先解壓：

```bash
gunzip core.12345.gz
gdb binary core.12345
```

或用 systemd-coredump 的自動壓縮 + `coredumpctl gdb` 幫你解。

## 常見坑

1. **binary 跟 core 不匹配**：你重編了 binary 再開 core，位址對不上、DWARF 全錯。gdb 會警告 mismatch，但仍會試著開 — 看到的東西不可信。
2. **core 生成失敗，沒 `(core dumped)` 訊息**：檢查 `ulimit -c`、`/proc/sys/kernel/core_pattern`、可寫權限。
3. **core 太大塞滿 disk**：加 `ulimit -c <size_in_blocks>` 或用 core_pattern 的 pipe 限制。
4. **`warning: core file may not match specified executable`**：stripped binary 跟 core 對照時出現，用有 debug info 的 binary 開。
5. **Apport / systemd-coredump 攔截**：Ubuntu/Fedora 預設把 core 收走。禁用或用 `coredumpctl` 取。
6. **無法重現的「core 看起來損壞」**：truncated core（寫到一半被 kill）。只能盡量看前段。
7. **shared library 版本差**：core 生成時用的 libc 跟你本機的 libc 不同 — 看到 libc 內部函式時位址對不上。複製遠端機器的 `/usr/lib` 並 `set sysroot`。

## 動手練習

### 練習一：生 core 並分析

```bash
ulimit -c unlimited
sudo sysctl -w kernel.core_pattern=core.%p

./crasher
gdb -q ./crasher core.*

(gdb) bt
(gdb) p p
(gdb) info registers
(gdb) info threads
(gdb) info signal SIGSEGV
(gdb) p $_siginfo
```

### 練習二：gcore 跑中 process

寫一個無窮 loop 的程式：

```c
#include <unistd.h>
int main(void) {
    volatile int i = 0;
    while (1) { i++; sleep(1); }
}
```

```bash
gcc -g loop.c -o loop
./loop &
pid=$!
sleep 2
gcore $pid                         ; 生 snapshot 不殺 process
gdb -q ./loop core.$pid            ; 看當下狀態

(gdb) p i                          ; 看當時 i 值
```

把 process 留著再做一次 gcore，開新 core，看 i 變大了。

### 練習三：multi-thread core

用 Ch 11 的 deadlock 範例：

```c
// dead.c, 省略 ... 會 deadlock
```

跑起來、另一個 terminal `kill -ABRT <PID>` 發 SIGABRT 強制產生 core。

```bash
gdb -q ./dead core.<PID>
(gdb) thread apply all bt
```

你會看到所有 thread 卡在什麼地方，這是「事後抓 deadlock」的標準做法。
