# Ch 15 — 為什麼需要安全規則

> **目標**：徹底理解 Firebase 安全規則存在的理由——在「前端直連資料庫」的架構下，為什麼前端的任何檢查都不算數、資料的唯一防線就是安全規則，以及沒有規則（或 Test mode）的資料庫有多麼門戶大開。這章是 Part 4 的動機，也是整門課最重要的觀念之一。

> **環境**：概念章。攻擊示範為「在你自己專案上、教學用途」的概念驗證，說明機制以理解防禦。

## 為什麼需要這個？

你在練習 B 做出了留言板，前端很貼心地「只在自己的留言顯示刪除鈕」。但這裡有個致命真相：**前端的刪除鈕藏不藏，跟「能不能刪」一點關係都沒有。**

回想 Ch 1 的架構——前端**直接**連 Firestore，沒有你的伺服器把關。這意味著：任何人打開你的網站，都能拿到你的 `firebaseConfig`（Ch 3 說它本來就公開），然後**繞過你的網頁**，直接用幾行 JavaScript 對你的資料庫為所欲為——刪別人的留言、改別人的資料、把整個集合讀光。

除非——你在**資料庫那一側**設了規則擋住他。這就是安全規則。這章讓你真正「怕」一次，你才會認真對待 Part 4 剩下的內容。

## 先建立直覺：前端是「別人家的」

最關鍵的心智轉變：

```
   傳統架構                          Firebase 架構
   ─────────                        ───────────
   前端 → 你的後端 → 資料庫           前端 → 直接 → 資料庫
          ▲                                ▲
     權限檢查在這裡                    沒有你的後端！
     （你控制的伺服器）                前端在「使用者的電腦」上，
                                     你完全控制不了
```

**你的前端程式碼，跑在使用者的瀏覽器裡——那是「別人的地盤」。** 使用者（或攻擊者）可以：

- 打開開發者工具，看到你所有前端程式碼和 config。
- 修改你的 JavaScript、拿掉你的檢查。
- 根本不開你的網頁，直接寫自己的腳本，用你的 config 連你的資料庫。

所以——**前端做的任何權限檢查（藏按鈕、擋輸入、if 判斷），都只是「體驗」，不是「安全」。** 一個決心搞破壞的人可以完全無視它們。

> 這不是 Firebase 的缺陷，是所有「client 端」的通則。差別是：傳統架構還有個你控制的後端當第二道防線；Firebase 把後端拿掉了，所以**安全規則就是那道防線，而且是唯一一道**。

## 攻擊示範：繞過前端有多容易

假設你的留言板用 Test mode（開放規則）。攻擊者不用任何特殊工具，在**瀏覽器的 console** 貼幾行就能刪掉**別人**的留言：

```js
// 攻擊者在你的網站 console 執行（config 從你的網頁原始碼就能拿到）
import { getFirestore, collection, getDocs, deleteDoc, doc }
  from "https://www.gstatic.com/firebasejs/12.18.0/firebase-firestore.js";
const db = getFirestore(app);

// 讀出所有留言（包括別人的）
const all = await getDocs(collection(db, "messages"));
// 全部刪光——前端的「只顯示自己的刪除鈕」在這裡完全無效
for (const d of all.docs) {
  await deleteDoc(doc(db, "messages", d.id));
}
```

你前端精心設計的「刪除鈕只在自己留言顯示」——攻擊者**根本沒用你的前端**，他直接呼叫 `deleteDoc`。你的 UI 邏輯攔不到他。

**唯一能擋住這段程式碼的，是資料庫端的安全規則**：如果規則寫了「只有 `authorId == 你的uid` 才能刪」，那麼 Firestore 在執行 `deleteDoc` 時就會拒絕他刪別人的留言——不管他從哪裡呼叫、繞過了多少前端。

## Test mode 是什麼、為什麼危險

Ch 3 建資料庫時你選了 Test mode。它套用的規則長這樣：

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.time < timestamp.date(2026, 9, 22);
    }
  }
}
```

翻譯：**在某個日期之前，任何人都能讀、寫、刪任何資料。** 這等於：

- 任何人能讀光你所有使用者的所有資料（隱私外洩）。
- 任何人能改、刪任何東西（資料被毀）。
- 任何人能狂寫垃圾資料（帳單爆炸、Ch 22）。

Test mode 存在的**唯一**理由是「讓你在學習/開發初期不被權限擋住、快速試功能」。它有 30 天期限就是在提醒你「這是暫時的，別忘了關」。

> ⚠️ **絕對不要把 Test mode 的專案上線給真實使用者。** 每隔一段時間就有新聞：某某 App 因為 Firebase 規則設成全開，幾百萬筆使用者資料被爬光。這不是假設，是反覆發生的真實事故。規則沒寫好 = 資料庫裸奔。

## 另一個極端：Production mode（全鎖）

建資料庫時的另一個選項是 Production mode，它的預設規則是：

```
match /{document=**} {
  allow read, write: if false;   // 全部拒絕
}
```

**全部拒絕**——沒有任何人能讀寫任何東西（透過客戶端 SDK）。這很安全，但你的 App 什麼都做不了。所以 Production mode 是「安全的起點」，你要從這個「全鎖」開始，**逐步打開你真正需要的權限**——「使用者能讀公開貼文」「登入者能寫自己的資料」……

這就是安全規則的正確心態：**預設拒絕，明確允許（default deny, explicit allow）**。從全鎖開始，只開必要的門，而不是從全開開始想著要關哪些。

## 安全規則到底是什麼

安全規則是一套**寫在雲端、Firestore 每次讀寫都會執行**的判斷邏輯。它回答一個問題：「**這個請求，該不該被允許？**」

```
   任何讀寫請求（不管從哪來）
        │
        ▼
   ┌─────────────────────────┐
   │  安全規則（在 Firestore   │
   │  伺服器上執行）           │
   │  「這個 uid 能對這筆      │
   │   資料做這件事嗎？」      │
   └─────────────────────────┘
        │              │
     允許 ✓          拒絕 ✗
     執行操作        permission-denied
```

關鍵性質：

- **在伺服器端執行**：規則跑在 Google 的伺服器上，攻擊者改不了、繞不過。這是它和前端檢查的根本差別。
- **每次操作都檢查**：每一次 `getDoc`、`addDoc`、`deleteDoc`、每一筆查詢，都要通過規則。
- **能看到「誰、對什麼、做什麼」**：規則能拿到請求者的身分（`request.auth`，就是 Ch 4 那張 token 解出來的 uid）、要操作的資料、以及現有的資料，據此判斷。

**認證（Part 2）證明「你是誰」，安全規則（Part 4）決定「你能不能做這件事」**——這就是 Ch 4 說的認證 vs 授權，現在授權這一半登場了。前端登入拿到的 uid，透過 token 傳到伺服器，安全規則用 `request.auth.uid` 拿到它來做判斷。

## 對比：三種「檢查」的可信度

| 檢查在哪 | 攻擊者能繞過嗎 | 算安全嗎 | 用途 |
|---|---|---|---|
| **前端 UI**（藏按鈕、if 判斷） | 能，輕易 | ❌ 否 | 體驗（別讓一般使用者看到不該點的） |
| **前端輸入驗證**（擋格式） | 能 | ❌ 否 | 體驗（即時提示） |
| **安全規則**（伺服器端） | **不能** | ✅ 是 | **真正的資料防線** |

一句話：**前端檢查是為了「順手的一般使用者」，安全規則是為了「有心的攻擊者」。** 兩者都要做，但別搞混誰負責安全。

## 踩雷集錦

1. **以為前端藏了按鈕/擋了輸入就安全**：最致命的誤解。前端跑在使用者電腦上，全部可繞過。安全靠伺服器端規則，不靠前端。
2. **把 Test mode 專案上線**：等於資料庫大門敞開。上線前**一定**要把規則改成真正的授權邏輯。反覆發生的真實資料外洩事故就是這樣來的。
3. **以為 `apiKey` 公開所以資料一定不安全**：`apiKey` 公開是正常的（Ch 3），資料安不安全**完全取決於安全規則**。key 公開 + 規則寫好 = 安全；key 公開 + 規則全開 = 裸奔。是規則決定，不是 key。
4. **以為「沒人知道我的專案 ID 就沒事」**：靠隱蔽（security by obscurity）不是安全。config 在你網頁原始碼裡人人可見，別指望沒人發現。
5. **規則寫成 `allow read, write: if request.auth != null`（只要登入就全開）**：這只擋掉「完全沒登入的人」，任何登入使用者（包括匿名登入！）都能改別人的資料。「登入了」不等於「有權限」，要細到「這筆是不是他的」。這是 Ch 16、17 要修的。
6. **前端不做檢查、全靠規則**：反過來也不對。規則保護安全，但前端仍該做體驗性檢查（即時提示、藏不該點的按鈕），不然使用者體驗很差、還會一直撞 `permission-denied`。兩者分工，都要做。

## 進階：再往深一層

- **規則不只管「能不能」，還能管「資料長怎樣」**：安全規則能檢查寫入的**內容**——欄位型別對不對、必填欄位有沒有、值在不在合理範圍。因為 Firestore 沒有強制 schema（Ch 8），規則就兼任了「資料驗證」的角色。這是 Ch 17 的重點之一。
- **規則語言是圖靈不完備的、故意的**：安全規則用一種受限的語言（後面會學），不能跑迴圈、不能呼叫外部 API——這是為了保證每次檢查都**快且可預測**（規則在每次請求的關鍵路徑上，不能慢）。理解這個限制，你就懂為什麼有些「複雜授權」要換方式做（如 custom claims、預先計算好的欄位）。
- **App Check 是另一個維度**：安全規則管「這個使用者能不能」，App Check（Ch 2 提過）管「這個請求是不是來自我真正的 App」。規則擋不住「合法使用者濫用」，App Check 擋「非法客戶端」。兩者互補，大型 App 常一起用。
- **後端繞過規則**：安全規則只管**客戶端 SDK** 的存取。用 **Admin SDK**（在你自己的後端 / Cloud Functions）存取 Firestore 會**完全繞過安全規則**（因為後端是可信環境）。所以「只有管理員能做的高權限操作」常放在 Function 裡用 Admin SDK 做，而不是想辦法在規則裡開一個危險的口子。

## 本章重點整理

- 前端跑在**使用者的電腦**上，攻擊者能看、能改、能繞過——**前端的任何檢查都只是體驗，不是安全**。
- Firebase 拿掉了你的後端，所以**安全規則是資料的唯一防線**，且它在**伺服器端執行**，繞不過。
- **Test mode = 全開 = 裸奔**，只能用於學習，**絕不上線**；正確心態是 **default deny, explicit allow**（從全鎖開始，只開必要的）。
- 攻擊者可以完全不用你的網頁、直接用 config 呼叫資料庫——所以「藏按鈕」擋不住他，只有規則能。
- `apiKey` 公開沒關係，**資料安不安全由規則決定**。
