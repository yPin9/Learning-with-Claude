# Ch 12 — NoSQL 資料建模

> **目標**：學會用 NoSQL 的思維設計 Firestore 資料結構——「先想怎麼查，再決定怎麼存」、什麼時候該巢狀 vs 用 subcollection vs 獨立集合、以及最反直覺的一招：**故意重複資料（反正規化）**。這章沒有新 API，但它決定你的 App 好不好用、快不快、貴不貴。是 Firestore 最需要「換腦袋」的一章。

> **環境**：概念與設計章。範例結構對照 Firestore v12.18.0 的查詢能力。

## 為什麼需要這個？

Firestore 的讀寫 API 很簡單，一天就學會。真正難、也真正決定成敗的是**資料結構怎麼設計**。同樣一個功能，結構設計得好，一次查詢搞定、又快又便宜；設計得差，要查十次、慢、還貴。

而且——如果你有 SQL 背景，你的直覺會**害你**。SQL 教你的「正規化、不要重複資料、用 JOIN 關聯」在 Firestore 這裡**大多是錯的**。這章幫你把腦袋換過來。

## 先建立直覺：SQL 是「先存好再想怎麼查」，NoSQL 相反

```
   SQL（關聯式）思維                  Firestore（NoSQL）思維
   ────────────────                  ──────────────────
   1. 先把資料正規化                  1. 先列出「畫面上要顯示什麼」
      （拆表、消除重複）                 「使用者會怎麼查」
   2. 存成乾淨的多張表                2. 反推「怎麼存，才能一次查到」
   3. 查詢時用 JOIN 拼回來            3. 為了一次查到，
                                       常常故意把資料重複存
   「儲存最佳化，查詢時再組合」        「查詢最佳化，儲存時就備好」
```

**核心心法一句話**：在 Firestore，**「你的查詢決定你的結構」**，不是反過來。因為沒有 JOIN、查詢又受限（Ch 10），你必須讓「一次查詢就能拿到畫面要的所有東西」——這常常意味著把本來該分開的資料**放在一起**或**複製一份**。

## 沒有 JOIN 的世界：三種關聯做法

假設「一篇文章要顯示作者的名字和頭像」。SQL 一個 JOIN 就好，Firestore 沒有 JOIN，你有三個選擇：

### 做法 A：只存 ID，讀完再查作者（正規化，多次讀）

```
posts/post_1 { title: "...", authorId: "uid_alice" }
users/uid_alice { name: "Alice", avatar: "..." }
```

讀一篇文要**兩次讀取**：先讀 post，拿到 `authorId`，再讀 `users/uid_alice`。顯示 20 篇文的列表 → 1 次查 posts + 20 次查作者 = **21 次讀取**。慢又貴。

**適合**：作者資料常變、且不常和文章一起顯示的情況。

### 做法 B：把作者資料「複製一份」進文章（反正規化，一次讀）

```
posts/post_1 {
  title: "...",
  authorId: "uid_alice",
  authorName: "Alice",       ← 複製過來
  authorAvatar: "..."        ← 複製過來
}
```

讀一篇文**一次讀取**就有全部要顯示的東西。顯示 20 篇 → **1 次查詢**搞定。快又便宜。

**代價**：Alice 改名字時，她**所有**文章裡的 `authorName` 都要一起更新（資料重複的宿命）。這通常用 Cloud Functions 監聽 users 變動去批次更新，或接受「舊文章顯示舊名字」。

**這就是反正規化**——為了讀取速度，故意接受資料重複和「更新要同步多處」的麻煩。**在 Firestore，這往往是對的選擇**，因為讀取遠比寫入頻繁，優化讀取划算。

### 做法 C：存必要的快照 + ID 備用（折衷，最常用）

```
posts/post_1 {
  title: "...",
  author: { id: "uid_alice", name: "Alice", avatar: "..." }  ← 存「當下快照」
}
```

顯示用複製的快照（一次讀），需要最新作者資料時用 `id` 再查。**這是實務最常見的折衷**：列表顯示夠用、又保留了關聯鍵。

> **怎麼選？** 問自己：「這個關聯資料**變動頻繁**嗎？它**總是和主資料一起顯示**嗎？」——不常變 + 總是一起顯示 → 大膽複製（B/C）。常變 + 要求即時準確 → 存 ID 再查（A）。多數「作者名字、分類名稱」這種都適合複製。

## 巢狀 vs subcollection vs 獨立集合

「文章的留言」該放哪？三個選項，用「留言會不會很多、要不要獨立查詢」來決定：

### 選項 1：巢狀在文章文件裡（array/map 欄位）

```
posts/post_1 {
  title: "...",
  comments: [ {text:"讚", by:"bob"}, {text:"推", by:"alice"} ]  ← 陣列欄位
}
```

- ✅ 讀文章時留言一起來，一次讀。
- ❌ 留言變多會撞**單文件 1 MiB 上限**；改一則留言要**重寫整份文件**；無法對留言單獨查詢/分頁。
- **只適合**：數量少且固定、總是和主文件一起讀的資料（例如一篇文的 3 個標籤、一個地址）。

### 選項 2：subcollection（子集合）

```
posts/post_1 { title: "..." }
posts/post_1/comments/c1 { text: "讚", by: "bob" }
posts/post_1/comments/c2 { text: "推", by: "alice" }
```

- ✅ 留言可以無限多、能單獨查詢/分頁/排序、改一則不影響文章文件。
- ✅ 讀文章時**不會**自動拉出全部留言（Ch 8）——想要時才查，不會一次拉爆。
- **適合**：會成長、要獨立操作的資料（留言、訂單項目、聊天訊息）。**「屬於某個父文件、且會變多」的東西，預設用 subcollection。**

### 選項 3：獨立的根集合

```
posts/post_1 { title: "..." }
comments/c1 { text: "讚", postId: "post_1", by: "bob" }
```

- ✅ 能跨文章查（例如「bob 在全站的所有留言」用一次 `where("by","==","bob")`）。
- ✅ 適合「留言本身是一等公民、常需要跨父層查」的情況。
- **對照**：subcollection 要跨父層查得用 collection group query（Ch 10 進階）；獨立根集合天生就好跨查，但「某篇文的留言」要靠 `where("postId","==",...)`。

| 放哪 | 資料量 | 能否獨立查 | 適合 |
|---|---|---|---|
| 巢狀陣列/map | 少、固定 | 否 | 標籤、地址、少數固定選項 |
| subcollection | 多、會成長 | 在該父層下可以 | 留言、訂單項、訊息 |
| 獨立根集合 | 多、要跨父查 | 全域可以 | 需跨父層查詢的實體 |

## 心法二：為「讀取路徑」設計，不為「儲存整齊」設計

再強調一次，因為它太重要。設計每個集合前，先問：

1. **這個畫面要顯示什麼？**（列出欄位）
2. **使用者會怎麼查這批資料？**（依什麼排序、篩什麼條件）
3. **怎麼存，才能讓上面那個查詢「一次就到位」且「不需要複雜索引」？**

例子——「使用者的動態牆，顯示他追蹤的人的貼文，按時間排序」：

- SQL 思維：posts 表 JOIN follows 表 → Firestore 沒有 JOIN，卡死。
- Firestore 思維：在**寫入時**就把貼文「散播（fan-out）」到每個追蹤者的 `feeds/{userId}/posts` 子集合。讀動態牆只要 `onSnapshot(feeds/{me}/posts, orderBy(time))` 一次搞定。**寫的時候多做工，換讀的時候超簡單。**

這就是 NoSQL 建模的精髓：**把運算從「讀取時」搬到「寫入時」**。因為讀取通常遠比寫入頻繁，這個交換划算。

## 心法三：善用「以查詢為目的」的欄位

因為查詢受限（Ch 10），常要**額外存一些「為了能查」的欄位**：

- 想「查某使用者的所有文」→ 在每篇文存 `authorId`，用 `where("authorId","==",uid)`。
- 想「查未讀通知」→ 存 `read: false` 布林欄位，用 `where("read","==",false)`。
- 想「按熱門排序」→ 存 `likeCount` 數字欄位（用 `increment` 維護，Ch 9），用 `orderBy("likeCount")`——**不要**試圖「數留言子集合有幾筆再排序」，那 Firestore 做不到，要把計數**存成欄位**。
- 想做「前綴搜尋」→ 存一個 lowercase 的 `nameLower` 欄位配範圍查詢（真正的全文搜尋還是要外部服務）。

**規律**：你想怎麼查，就得有對應的、可以直接被 `where`/`orderBy` 用的欄位。查詢用得到的聚合值（數量、最新時間）要**在寫入時算好存起來**，不要期待讀取時即時算。

## 踩雷集錦

1. **用 SQL 正規化思維設計 Firestore**：拆得很乾淨、零重複、想著 JOIN——結果每個畫面要查十次。NoSQL 要**反正規化**、要**為查詢複製資料**。這是最根本的錯誤。
2. **把會成長的東西塞進陣列欄位**：留言、訂單項塞進文件的 array，遲早撞 1 MiB 上限，且改一項要重寫整份、無法分頁。會成長的用 subcollection。
3. **想在讀取時即時算聚合**：「這篇文有幾則留言」不要每次去數子集合（做不到高效排序、又貴）。用 `increment` 維護一個 `commentCount` 欄位。**聚合值寫入時算好、存成欄位。**
4. **反正規化了卻沒想更新策略**：複製了 `authorName` 進每篇文，作者改名時忘了同步，全站顯示舊名。反正規化的代價就是「更新要同步多處」，設計時就要決定怎麼處理（Functions 批次更新，或接受不同步）。
5. **一律用 subcollection 或一律用根集合**：兩者各有適用。要跨父層查（bob 全站的留言）用根集合或 collection group；只在父層下操作用 subcollection。看查詢需求決定。
6. **忘記「刪父文件不刪子集合」**：建了 subcollection 就要記得刪除時的孤兒問題（Ch 8/9）。這也是建模時要考慮的：這些子資料誰負責清。

## 進階：再往深一層

- **fan-out（寫入時散播）**：如上例的動態牆。寫一篇文時，用 batch/Function 把它複製到所有追蹤者的 feed。極端優化讀取，代價是寫入變重、資料大量重複。Instagram/Twitter 這類 feed 都用類似思路。是否值得，看你的讀寫比和規模。
- **分片計數器（sharded counter）**：如果一個計數器（例如全站按讚總數）被**極高頻**並發寫入，單一文件會成為寫入熱點（Firestore 單文件約每秒 1 次寫入的軟上限）。解法是把計數拆成 N 個分片文件、隨機寫其中一個、讀時加總。一般 App 用不到，但知道這個模式存在。
- **資料重複的「真相來源」原則**：反正規化後同一份資訊存在多處，要明確定義**哪一份是權威（source of truth）**、哪些是為了讀取的複本。更新時只認權威那份，複本靠同步機制跟上。腦中沒有這個區分，資料很快就會各處不一致。
- **建模和安全規則、成本綁在一起**：你的結構直接決定安全規則好不好寫（例如「文件裡有 `owner` 欄位」才好寫「只能改自己的」規則，Ch 17）、以及花多少錢（查幾次 = 幾次讀取計費，Ch 22）。建模不是孤立的——好結構讓規則簡單、帳單便宜。設計時三者一起想。
- **先跑再優化**：不要一開始就過度設計 fan-out、分片。多數個人專案用「B/C 折衷 + 適當 subcollection + 存好查詢欄位」就夠。等真的遇到效能/成本問題再上進階模式。過早優化在這裡也是萬惡之源。

## 本章重點整理

- Firestore 建模心法：**先想怎麼查，再決定怎麼存**——查詢決定結構，不是反過來。
- 沒有 JOIN → 用**反正規化（故意複製資料）**讓「一次查詢拿到畫面要的全部」；代價是更新要同步多處。
- 關聯資料放哪：少而固定用**巢狀欄位**、多而會成長用**subcollection**、要跨父層查用**獨立根集合**。
- 把運算**從讀取時搬到寫入時**（聚合值存成欄位、fan-out）——因為讀通常遠多於寫。
- 想怎麼查，就要有能被 `where`/`orderBy` 直接用的對應欄位。
