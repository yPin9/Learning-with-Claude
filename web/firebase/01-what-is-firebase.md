# Ch 1 — Firebase 是什麼：BaaS 全貌

> **目標**：搞懂 Firebase 到底是什麼、它屬於哪一類技術（BaaS）、它替你省掉了原本要自己做的哪些苦工，以及——同樣重要——什麼時候**不該**用它。這章沒有程式碼，是整門課的地圖與世界觀。讀完你會知道後面每個功能是在解決什麼問題。

## 為什麼需要這個？

想像你要做一個「多人即時待辦清單」網頁：使用者要能註冊登入，各自的清單存在雲端，而且 A 改了清單，B 的畫面要馬上更新。

如果用**傳統做法**，你得自己搞定一長串東西：

```
使用者的瀏覽器
      │
      ▼
┌─────────────────────────────────────────────┐
│  這些全部要你自己寫、自己養：                  │
│                                             │
│  1. 一台伺服器 (租 VPS / 雲主機)             │
│  2. 一個後端程式 (Node/Python/Go... 寫 API)  │
│  3. 一個資料庫 (PostgreSQL/MySQL... 要安裝、  │
│     備份、調校、擴容)                         │
│  4. 使用者系統 (註冊/登入/密碼雜湊/            │
│     session/忘記密碼信/OAuth 串接...)         │
│  5. 檔案上傳的儲存空間                        │
│  6. 即時推送機制 (WebSocket 伺服器)          │
│  7. HTTPS 憑證、網域、部署流程、監控...        │
└─────────────────────────────────────────────┘
```

上面每一項都是一門學問，光是「安全地做好使用者登入」就能讓人踩雷踩到懷疑人生（密碼要怎麼存？token 怎麼發？被撞庫怎麼辦？）。對一個想快速驗證點子的人來說，這些**基礎設施的苦工**佔掉了 90% 的時間，而真正讓你的產品獨特的功能只有 10%。

**Firebase 就是來把那 90% 承包走的。** 你不用租伺服器、不用寫後端 API、不用管資料庫運維、不用自己做登入系統——這些 Google 都幫你做好了，你的網頁程式碼直接呼叫就好。

## 先建立直覺：什麼是 BaaS

Firebase 屬於一類產品叫 **BaaS（Backend as a Service，後端即服務）**。用一個類比：

> 開一家餐廳，你可以選擇**自己蓋一棟樓**——買地、蓋房、拉水電、裝廚房設備、請人維護。也可以選擇**租一個已經裝潢好、水電廚具全備的店面**——你只要專心做菜、招呼客人。
>
> 傳統後端開發是「自己蓋樓」。BaaS 是「租一個全配店面」。你付出的代價是「這棟樓不是你的、規則是房東（Google）訂的」，換來的是「你今天就能開張做生意」。

這個類比在「快速開張」這點上很準；但它有個限制要先說清楚：**租來的店面，你不能隨意打掉承重牆**——BaaS 幫你決定了很多架構，你能客製的範圍比自蓋的少。這個代價我們這章後面會誠實地談。

把 BaaS 拆開看，「後端」被拆成一組現成的服務：

```
    傳統：你自己寫一個大後端              BaaS：租用一組現成服務
 ┌──────────────────────────┐        ┌──────────────────────────┐
 │                          │        │  Authentication  (登入)   │
 │   你的後端伺服器          │        │  Firestore       (資料庫) │
 │   (你寫的所有邏輯 +       │  ═══▶  │  Cloud Storage   (檔案)   │
 │    你養的資料庫 +         │        │  Hosting         (網站)   │
 │    你管的登入系統...)     │        │  Cloud Functions (自訂邏輯)│
 │                          │        │  ... 每個都是獨立、現成的  │
 └──────────────────────────┘        └──────────────────────────┘
   一整坨、全要自己維護                 積木式、要哪個用哪個
```

## Firebase 最反直覺的一件事：前端直接連資料庫

這是 Firebase 和傳統架構**最大的差別**，一定要先理解，否則後面很多設計你會覺得奇怪。

傳統三層架構長這樣，瀏覽器**永遠不直接碰資料庫**：

```
瀏覽器  ──▶  你的後端 API  ──▶  資料庫
            (在這裡檢查權限、        (只信任後端，
             驗證資料、寫邏輯)        不對外開放)
```

Firebase 卻是這樣，**瀏覽器直接連 Firestore 資料庫**：

```
瀏覽器 (帶著 JS SDK)  ──── 直接讀寫 ────▶  Firestore 資料庫
                                          ▲
                                          │
                          「安全規則」在這裡把關
                       (誰能讀誰能寫，寫在雲端資料庫上)
```

第一次看到這個，正常反應是：「**蛤？！前端直接連資料庫，那不是誰都能亂改我的資料？**」

這是好問題，而答案正是 Firebase 的核心設計，也是這門課 Part 4 整整四章要講的**安全規則（Security Rules）**：Google 讓你在**資料庫這一側**寫一套規則，規定「這筆資料誰能讀、誰能寫、寫進來的內容必須符合什麼條件」。前端雖然直接連，但每一個讀寫請求都會先被這套規則檢查。權限判斷從「後端程式碼」搬到了「資料庫規則」。

> **先記住這句話，Part 4 會展開**：在 Firebase 裡，你的資安防線不是「藏起後端」，而是「寫好安全規則」。規則寫錯 = 資料庫門戶大開。這是 Firebase 最重要、也最多人忽略的一課。

## Firebase 能做什麼：核心服務速覽

這門課聚焦這四個核心後端服務（下一章 Ch 2 會給完整生態地圖）：

| 服務 | 一句話 | 幫你省掉的苦工 |
|---|---|---|
| **Authentication** | 使用者登入系統 | 密碼雜湊、token 簽發、Google/Facebook 等第三方登入、忘記密碼信——全部現成 |
| **Cloud Firestore** | 雲端 NoSQL 資料庫，能**即時同步** | 資料庫安裝維運、擴容、以及「資料變動自動推到所有裝置」的即時機制 |
| **Cloud Storage** | 存使用者上傳的檔案（圖片/影片） | 大檔上傳、CDN 分發、存取權限控制 |
| **Hosting** | 把你的網站部署上線 | 伺服器、HTTPS 憑證、全球 CDN、一行指令部署 |

「即時同步」是 Firestore 最有魔法感的功能：你寫一段程式碼「監聽」某筆資料，之後只要那筆資料在雲端變了（不管是誰改的、從哪台裝置改的），你的畫面會**自動更新**，不用你寫任何輪詢或 WebSocket 程式碼。多人協作、聊天室、即時儀表板這類應用，用 Firestore 做會快到不可思議。這是 Ch 11 的主題。

## Firebase 用在哪裡：真實場景

Firebase 特別適合這些情境：

- **MVP / 快速驗證點子**：一個人週末就能做出有登入、有雲端資料的可用產品。創業初期、Hackathon、demo。
- **即時協作應用**：聊天、共同編輯、即時看板、多人遊戲的狀態同步——Firestore 的即時同步是殺手級功能。
- **行動 App 後端**：Firebase 出身就是行動優先，iOS/Android App 常拿它當整個後端。
- **前端工程師想自己包後端**：不想（或不會）架伺服器的前端，用 Firebase 就能獨立做出全端應用。

用過 Firebase 的知名產品：早期的 Duolingo、The New York Times 的部分互動、大量的獨立 App 和新創 MVP。

## 誠實面對：什麼時候**不該**用 Firebase

好的教材要告訴你工具的邊界。Firebase 不是萬靈丹，這些情況要三思：

1. **複雜的關聯查詢**：Firestore 是 NoSQL，**不支援 SQL 的 JOIN、不支援跨多個條件的任意複雜查詢**。如果你的應用核心是「把五張表 join 起來、做複雜的報表聚合」（典型的後台管理、財會系統），關聯式資料庫（PostgreSQL）會輕鬆很多，硬套 Firestore 會很痛苦。
2. **想避免被綁定（vendor lock-in）**：你的資料模型、安全規則、甚至部分程式邏輯都會長成 Firebase 的形狀。哪天想搬到別的平台，成本不低。這是「租店面」的代價。
3. **成本在大規模時可能翻車**：Firebase 按「讀取次數、寫入次數、儲存量、流量」計費。小規模幾乎免費，但某些**讀取密集**的應用（例如每個使用者一進來就要讀幾百筆文件）在規模放大後帳單會很可觀。這需要從資料建模階段就注意（Ch 12、Ch 22 會談）。
4. **需要完全掌控後端邏輯 / 特殊基礎設施**：要跑特定的運算、連特殊硬體、法規要求資料自架——這些 BaaS 給不了你那種控制權。

> **一句話總結取捨**：Firebase 用「放棄一部分控制權和靈活性」換「極快的開發速度和零運維」。對「快速做出即時應用」這個目標，它強到不講理；對「複雜關聯查詢 + 完全掌控」這個目標，它是錯的工具。

## 對比與取捨：Firebase vs 其他做法

| 方案 | 開發速度 | 靈活性/掌控 | 即時同步 | 適合誰 |
|---|---|---|---|---|
| **自架後端**（Node + Postgres + 自租主機） | 慢 | 最高 | 要自己做 | 需要完全掌控、複雜邏輯、大團隊 |
| **Firebase**（BaaS，本課） | 最快 | 中 | 內建、免費午餐 | MVP、即時應用、獨立開發者 |
| **Supabase**（開源 BaaS，底層是 Postgres） | 快 | 中高（有 SQL） | 內建 | 想要 BaaS 便利又想要 SQL 的人 |
| **AWS Amplify** | 中 | 高（整個 AWS 生態） | 內建 | 已在 AWS 生態、要更多雲端服務 |

Supabase 常被拿來和 Firebase 比：它底層是 PostgreSQL，所以你有完整的 SQL 和關聯查詢，補上了 Firestore 最大的弱點；代價是它的即時同步和整體成熟度、行動端整合不如 Firebase。**這門課學 Firebase，但學完你會有能力判斷什麼場景該換 Supabase。**

## 踩雷集錦

1. **以為 Firebase 只是「一個雲端資料庫」**：它是**一整組**服務（登入、資料庫、儲存、部署…）。很多人只知道 Firestore，錯過了 Authentication 幫你省掉的巨量苦工。
2. **以為「前端直連資料庫」等於不安全**：不是不安全，是把安全防線換了位置——從「藏後端」變成「寫安全規則」。危險的不是這個架構，是**沒寫好規則**。這是 Firebase 新手最致命的誤解。
3. **把 Firestore 當關聯式資料庫用**：想著「這張表 join 那張表」去設計 Firestore，一定會撞牆。NoSQL 的建模思維完全不同（Ch 12 專章講）——**你怎麼查，決定你怎麼存**，而不是先正規化再想怎麼查。
4. **以為 Firebase 一定免費**：免費額度很佛心，個人專案通常花不到錢，但它**不是無限免費**。讀寫次數、流量都在計費表上，某些設計會意外燒錢。Ch 22 會教怎麼看帳單、怎麼避雷。
5. **混用新舊版 SDK 寫法**：網路上一堆 `firebase.firestore().collection(...)` 是舊的 v8 命名空間寫法；本課用的 `import { getFirestore }` 是 v9+ 模組化寫法。跟著舊教學抄會和新版對不上——認明寫法（Ch 3 會再強調）。

## 進階：再往深一層

- **Firebase 和 Google Cloud 的關係**：Firebase 其實是架在 Google Cloud Platform（GCP）之上的一層「對開發者更友善的包裝」。Firestore 底層就是 GCP 的 Firestore；Cloud Functions 就是 GCP 的 Cloud Functions。當你的需求超出 Firebase 的簡化介面，可以直接下沉到 GCP 用更完整的控制。理解這層關係，你就懂為什麼 Firebase Console 裡有些設定會把你導去 Google Cloud Console。
- **「即時」是怎麼做到的**：Firestore 的即時同步底層不是你想的「一直去問伺服器有沒有變」（輪詢），而是伺服器主動把變動推給你（透過長連線）。這個機制 Ch 11 會拆開講——它是 Firestore 值錢的核心。
- **離線支援**：Firebase SDK 內建離線快取——網路斷了，你的讀寫會先存在本機，連線恢復後自動同步。這對行動 App 是巨大優勢，且幾乎不用你寫程式碼。本課會在 Firestore 章節帶到。

## 本章重點整理

- Firebase 是 **BaaS（後端即服務）**：把「登入、資料庫、儲存、部署、即時同步」這些後端苦工承包成現成服務，你的前端直接呼叫。
- 最反直覺也最核心的設計：**前端直接連資料庫**，靠**安全規則**在資料庫側把關，而不是靠藏起後端。
- Firebase 強在**開發速度**和**即時同步**；弱在**複雜關聯查詢**、**掌控權**、**大規模成本**。
- 選它是一種取捨：用靈活性換速度。判斷「這個專案適不適合 Firebase」是這章要你帶走的能力。
