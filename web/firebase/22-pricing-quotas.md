# Ch 22 — 計費與額度

> **目標**：搞懂 Firebase 怎麼收費——Spark（免費）和 Blaze（付費）兩個方案、各服務的免費額度、**什麼行為在燒錢**、以及怎麼避免「一覺醒來收到天價帳單」。這是每個 Firebase 開發者的自保知識，也把前面「查詢設計影響成本」「監聽沒關會計費」的伏筆收束起來。

> **環境**：本章的額度數字**擷取自 Firebase 官方 pricing 頁（2026-08）**。**價格與額度會隨時間變動**，實際請以 [firebase.google.com/pricing](https://firebase.google.com/pricing) 為準——這是可查證的斷言，別把本章數字當永久真理。

## 為什麼需要這個？

Firebase 前期幾乎免費，佛心到讓人忘記它會收費。但它的計費模型有幾個「陷阱」——某些設計會在使用者變多時讓帳單指數成長，而且是**你事後才發現**。網路上流傳過「開發者一覺醒來收到幾萬美金帳單」的故事（多半是 bug 造成的失控迴圈）。這章讓你理解計費機制、設好防護，開心用 Firebase 而不提心吊膽。

## 先建立直覺：兩個方案

```
   Spark（免費方案）                   Blaze（隨用隨付）
   ─────────────                      ─────────────
   有固定免費額度                      「先給你 Spark 那份免費額度，
   超過額度 → 服務停止/拒絕              超過才按量收費」
   （不會扣你錢，但 App 會壞）          （超過額度才花錢，用多少算多少）
   
   適合：學習、demo、小專案            適合：要上線、可能超額度、
                                       或要用 Functions 等進階服務
```

關鍵理解：

- **Spark**：完全免費，但額度用完**服務就擋住**（例如 Firestore 讀取超過當日額度，之後的讀取被拒）。適合學習和小專案。**不會讓你負債**。
- **Blaze**：**包含 Spark 的免費額度**，只有**超過**才收費。所以升 Blaze 不代表立刻要付錢——小專案在 Blaze 上一樣可能是 $0。但它需要綁信用卡，理論上額度無上限，所以要設預算警報（下面講）。

> **為什麼有些功能一定要 Blaze？** Cloud Functions、以及某些外部網路存取需要 Blaze。如果你只用本課的 Auth/Firestore/Storage/Hosting，Spark 就能跑很久。要上線且怕被 Spark 的硬額度擋住服務，才升 Blaze。

## 免費額度：各服務給多少

以下為官方 pricing 頁的免費額度（Spark 方案 = Blaze 的免費門檻，**2026-08 擷取，會變動**）：

| 服務 | 免費額度 |
|---|---|
| **Firestore** | 儲存 1 GiB；**讀取 50,000 次/天**、**寫入 20,000 次/天**、刪除 20,000 次/天 |
| **Authentication** | 50,000 MAU（月活躍使用者）※ 這個上限屬 Identity Platform 級別；傳統 Firebase Auth 的 email/Google 登入歷來實質上不按 MAU 計費，實際依方案/供應商而定 |
| **Cloud Storage** | 儲存 5 GB；下載 1 GB/天；上傳操作 20,000/天；下載操作 50,000/天 |
| **Hosting** | 儲存 10 GB；傳輸 360 MB/天 |

對個人專案、學習、小型 App，這些額度**非常夠用**——你大概率長期都在免費範圍。但注意 Firestore 的**讀寫是按「次數」算、每天重置**——這是最容易失控的地方，下面重點講。

## 什麼在燒錢：Firestore 的讀寫次數

Firestore 是最需要盯的服務，因為它按**操作次數**計費，而某些設計會讓次數暴增：

### 每次操作怎麼算

- **讀取（read）**：每讀一份文件算 1 次。**查詢回傳 N 份文件 = N 次讀取**（不是 1 次！）。`onSnapshot` 每收到一份文件（初始 + 每次變動）都算 1 次。
- **寫入（write）**：每寫一份文件算 1 次。批次寫 N 份 = N 次（Ch 14）。
- **刪除（delete）**：每刪一份算 1 次。

### 燒錢的典型設計（呼應前面章節）

1. **列表不加 limit**（Ch 10）：一個 `getDocs(collection)` 讀出 10,000 份文件 = **10,000 次讀取**，一次就吃掉當日額度的 1/5。列表一律 `limit` + 分頁。
2. **監聽器沒關**（Ch 11）：`onSnapshot` 忘了 `unsubscribe`，它持續掛著、每次資料變動都推送計費。一個沒關的熱門集合監聽器，能悄悄燒掉大量讀取。
3. **讀取時即時算聚合**（Ch 12）：「這篇文有幾則留言」每次去 `getDocs` 數整個子集合，而不是維護 `commentCount` 欄位——每次顯示都是 N 次讀取。
4. **N+1 查詢**（Ch 12）：列出 20 篇文，每篇再查一次作者 = 1 + 20 次讀取。反正規化把作者名存進文章，變成 1 次。
5. **規則裡的 `get()`**（Ch 16/17）：每個 `get()` 判斷都算一次讀取，高頻路徑用會累積。

**看出規律了嗎**——這些「燒錢設計」正是前面每章教你**別做**的事。好的建模、查詢、監聽習慣，同時就是**省錢**。這是 Firestore 把「效能」和「成本」綁在一起的設計：**寫得好的 App，天生便宜。**

## 怎麼避免天價帳單：防護措施

### 1. 設定預算警報（Blaze 必做）

如果你升了 Blaze，**第一件事**就是在 Google Cloud 設**預算與警報（budget alerts）**：設一個金額（例如 $10/月），超過就寄 email 通知你。這樣就算有 bug 造成失控，你會**及早收到警告**，而不是月底才發現。

> **重要澄清**：預算警報只是**通知**，不會自動停止服務（Google 沒有內建的「到達金額就斷」硬上限）。要真正硬性停止，得自己寫 Cloud Function 監聽預算、達標時停用計費——進階做法。但至少設警報，讓你能及時反應。

### 2. 用模擬器開發（Ch 21）

開發測試全在模擬器跑，**完全不計費**。真實額度只花在真實使用者身上。這是本課一直強調用模擬器的成本理由。

### 3. 好的資料設計（前面全部章節）

如上所述——加 limit、關監聽、維護聚合欄位、反正規化、少用規則 get。這些既是效能最佳實踐，也是省錢措施。

### 4. 安全規則防濫用（Part 4 + Ch 19）

沒有規則，攻擊者能狂寫垃圾資料（燒寫入額度）、狂傳大檔（燒 Storage）。**安全規則的大小/型別/權限限制，也是成本防線**（Ch 19 特別強調 Storage 的大小限制）。規則沒寫好 = 不只資料裸奔，帳單也裸奔。

### 5. 監控用量

Console 的 Usage 分頁能看各服務的即時用量，Blaze 的話 Google Cloud 有詳細的計費報表。**定期看一眼**，異常暴增及早發現。

## 對照：常見誤解與真相

| 誤解 | 真相 |
|---|---|
| 「Firebase 是免費的」 | 有免費額度，超過要錢（Spark 擋服務、Blaze 收費） |
| 「升 Blaze 就要開始付錢」 | Blaze 含免費額度，小專案一樣可能 $0 |
| 「查詢算一次讀取」 | 查詢回傳 N 份 = N 次讀取 |
| 「Spark 會讓我負債」 | 不會，Spark 額度用完是擋服務，不扣錢 |
| 「設了預算就不會超支」 | 預算只通知不硬停，要自己寫 Function 才能硬斷 |
| 「apiKey 洩漏會被盜刷」 | 盜刷靠的是「沒設好規則讓人狂讀寫」，不是 key 本身（Ch 3/15）——規則寫好就擋住了 |

## 踩雷集錦

1. **以為查詢算一次讀取**：回傳 N 份文件就是 N 次讀取。不加 limit 的大集合查詢會爆額度。列表一律分頁。
2. **升 Blaze 不設預算警報**：Blaze 理論上額度無上限，不設警報，失控時月底才發現。升 Blaze 第一件事就是設警報。
3. **開發連真實專案、狂測試**：每次測試都計費、污染資料。用模擬器（Ch 21）開發，零成本。
4. **監聽器不關**：持續計費的隱形殺手（Ch 11）。務必 unsubscribe。
5. **以為預算警報會自動停服務**：不會，它只通知。要硬停得自己實作。別以為設了就高枕無憂。
6. **Storage 規則不限大小**：等於開放無限上傳，儲存和流量帳單失控（Ch 19）。大小限制是必備。
7. **把成本當上線後才想的事**：成本是**建模時**就決定的（查詢方式、監聽方式）。等帳單來了才改設計，成本已經產生。設計階段就要有成本意識。

## 進階：再往深一層

- **各操作的實際單價**：超過免費額度後，Firestore 大約是「每 10 萬次讀取幾美分」等級（具體數字查 pricing 頁）。單價很低，但**乘上高頻和大量使用者**就顯著。理解「單價低但會被量放大」，你就知道為什麼「省一個 N+1 查詢」在規模化時很值錢。
- **成本歸因與最佳化**：Google Cloud 的計費報表能看到「哪個服務、哪種操作」花最多，據此針對性優化。上規模的 App 會定期做這種成本分析。
- **Firestore 的 TTL 自動刪除**：可以設定文件的「存活時間」，到期自動刪除（如暫存資料、過期 session）。避免無用資料一直佔儲存和累積。
- **快取與離線減少讀取**：SDK 的本機快取（Ch 11）能讓「重複讀同樣資料」命中快取、不計費。善用 `getDocFromCache` 或讓 `onSnapshot` 的快取供應，能省讀取。
- **聚合查詢比讀全部便宜**：`count()`（Ch 10 進階）算數量的計費遠低於「讀出全部再 `.length`」。要數量用聚合查詢。
- **免費額度是「每天重置」還是「每月」**：Firestore 讀寫額度是**每日**重置、Storage 儲存是**當下總量**、Auth 是**月活躍**。搞清楚每個額度的計算週期，才能正確估算。

## 本章重點整理

- 兩個方案：**Spark**（免費，超額**擋服務不扣錢**）、**Blaze**（含免費額度，**超過才收費**，需信用卡）。小專案在兩者上都可能 $0。
- 免費額度對個人專案很夠（Firestore 讀 5 萬/寫 2 萬/天、Auth 5 萬 MAU、Storage 5 GB…），**但數字會變，以官方 pricing 頁為準**。
- Firestore 按**操作次數**計費，**查詢回傳 N 份 = N 次讀取**——燒錢的設計（不加 limit、監聽不關、讀取時算聚合、N+1）正是前面教你別做的事。**寫得好的 App 天生便宜。**
- 防護：升 Blaze **必設預算警報**（但它只通知不硬停）、用模擬器開發（零成本）、好的資料設計、安全規則防濫用。
- 成本是**建模時**決定的，不是上線後才想的事。
