# Ch 8 — 為什麼需求這麼難：自然語言的八種病

> **目標**：理解為什麼用自然語言寫需求天生脆弱——從 EARS 論文歸納的八種缺陷出發，用 before/after 配對看清每種病的樣子，並建立一套能在 AI 時代操作的診斷直覺。

---

## 你腦中的需求 vs 紙上的需求

先想一個場景：你把下列一句話交給另一個工程師去實作：

> 「系統必須快速回應使用者的操作。」

這句話在你腦中其實有一個非常具體的畫面：P95 延遲低於 200ms、在使用者點擊按鈕後 100ms 內給出視覺回饋。但你寫出來的那句話，你的同事讀到的可能是「盡量快一點」，也可能是「不要卡頓就好」。

這就是需求工程（Requirements Engineering）最核心的問題：**語言是有損壓縮**。你把腦中的意圖壓縮成文字傳給別人，對方解壓縮出來的未必等於原來的意圖。人與人之間還能靠問問題、靠共同情境補救；但把這句話交給一個 AI 代理程式，它沒辦法跳出來問你「快速是多少毫秒」——它會默默做個假設然後繼續跑。

在進入工具與技法之前，我們先把這些語言缺陷逐一命名。命名是診斷的前提。

---

## 歷史背景：Rolls-Royce 的發現

2000 年代中期，Alistair Mavin 在 Rolls-Royce 負責分析噴射引擎控制系統的適航法規需求。他發現，即使在航太這種紀律嚴格的產業，需求文件裡仍反覆出現同樣種類的問題。

2009 年，Mavin、Wilkinson、Harwood、Novak 把這些觀察整理成論文 *Easy Approach to Requirements Syntax (EARS)*，發表在第 17 屆 IEEE 國際需求工程研討會（RE'09，2009，pp. 317–322，DOI 10.1109/RE.2009.9）。論文列出八種自然語言需求的系統性缺陷，並提出一套簡單的句型約束來消除它們。

「EARS 的強項就是它的簡單。」——Mavin & Wilkinson，*Ten Years of EARS*，IEEE Software 36(5):10-14，2019

這八種缺陷不是 Mavin 憑空想像的，是從真實工業需求文件歸納出來的。理解它們，等於理解為什麼前人寫出來的那些需求文件那麼難用。

> 如果你對「為什麼需求在 AI 時代突然更重要」還不熟，先回看 [Ch 1 為什麼「規格」突然重要了：AI 把瓶頸推到意圖上](./01-why-specs-matter-now.md)。

## 八種病的全景

先用一張表讓你有整體感，下面每一病再展開：

| # | 缺陷名稱 | 核心問題 | 最常出現的場景 |
|---|---------|---------|--------------|
| 1 | 歧義（Ambiguity） | 同一句話，不同讀者得到不同意思 | 代名詞指涉不清、術語未定義 |
| 2 | 模糊（Vagueness） | 缺乏可量化的精度或結構 | 「快速」「適當」「足夠」 |
| 3 | 複雜（Complexity） | 一個句子裡包含多個互相關聯的子需求 | 長句子連接詞成串 |
| 4 | 遺漏（Omission） | 沒有說清楚異常路徑或邊界情境 | 只描述成功流程 |
| 5 | 重複（Duplication） | 同樣的需求在文件不同地方反覆出現 | 複製貼上式文件 |
| 6 | 冗長（Wordiness） | 不必要的文字稀釋了真正的約束 | 法律風格合約語言 |
| 7 | 不當實作（Inappropriate Implementation） | 需求裡夾帶了設計決策 | 說「用 Redis 快取」而非「快取時間 X」 |
| 8 | 不可測（Untestability） | 無法設計一個測試來驗證是否滿足 | 「應該提升使用者體驗」 |

## 逐一解剖：病症 + Before/After

### 病 1：歧義（Ambiguity）

**定義**：一個詞或片語有兩種以上的有效解釋。

讀這句需求：

> 「系統應允許管理員和一般用戶存取報表。」

至少有兩種讀法：
- 管理員和一般用戶都能存取所有報表
- 管理員能存取所有報表，一般用戶只能存取部分報表

另一個常見歧義來源是代名詞指涉：

> 「當訂單建立後，系統應通知客服。如果他們確認，則發出出貨通知。」

「他們」是誰？客服？訂單建立者？系統？

**Before（有歧義）**
```
系統應允許管理員和一般用戶存取報表。
```

**After（消歧義）**
```
管理員角色的用戶（Admin role）應可存取所有報表，
包括財務報表（Financial Reports）、
使用者活動報表（User Activity Reports）。

一般用戶（Standard User）僅可存取其自身帳號的
使用者活動報表。
```

歧義在人與人之間可以靠問問題解決，但 AI 代理程式遇到歧義會默默選一種解釋繼續跑，而且不一定是你預期的那種。

---

### 病 2：模糊（Vagueness）

**定義**：缺乏精度、結構或具體細節，使需求無法被量化驗證。

模糊和歧義容易混淆：歧義是「有多種意思」，模糊是「意思太空洞，任何實作都算滿足」。

常見的模糊詞彙：快速、靈活、友善、適當、充分、穩健、現代。

**Before（模糊）**
```
登入頁面應快速載入。
```

「快速」沒有數字。你可以把 3 秒的頁面交出去，然後說「3 秒對使用者來說已經夠快了」——沒有辦法反駁。

**After（有精度）**
```
登入頁面應在網路延遲 100ms 以下的環境中，
於用戶提交憑證後 1 秒內顯示首頁儀表板，
以 Largest Contentful Paint (LCP) 衡量，
目標值 ≤ 1000ms（P95，基於 Chrome UX Report 標準）。
```

> 如果你對規格、設計、實作三層的分工還不清楚，先回看 [Ch 7 規格 vs 設計 vs 實作](./07-spec-design-implementation.md)。

---

### 病 3：複雜（Complexity）

**定義**：一個需求句子裡包含多個相互關聯、各有前提的子需求。

**Before（過於複雜）**
```
系統應在用戶登入後，根據其角色（管理員、編輯、訪客）
決定顯示哪些選單項目，並且在角色為管理員時，
如果用戶超過 3 次登入失敗，應鎖定帳號並發送通知，
但如果是在辦公時間以外，應額外通知資安團隊。
```

這一句話裡埋了：
1. 角色型選單顯示規則（3 個角色）
2. 登入失敗鎖定規則（有次數閾值）
3. 時間窗口規則（辦公時間 vs 非辦公時間）
4. 兩條不同的通知路徑

任何一條規則改變，整個句子都要重寫，而且很難確認改了哪裡。

**After（拆解成獨立需求）**
```
REQ-AUTH-01: 選單顯示
  管理員角色：顯示所有選單項目
  編輯角色：顯示內容管理、發布等項目，不顯示用戶管理
  訪客角色：僅顯示公開瀏覽項目

REQ-AUTH-02: 帳號鎖定條件
  當同一帳號連續登入失敗達 3 次時，系統應鎖定該帳號

REQ-AUTH-03: 鎖定後通知—辦公時間
  當帳號被鎖定，且發生時間在辦公時間（09:00–18:00 UTC+8，
  週一至週五，排除公眾假期）之內，系統應通知帳號擁有者

REQ-AUTH-04: 鎖定後通知—非辦公時間
  當帳號被鎖定，且發生時間在辦公時間以外，
  系統應同時通知帳號擁有者及資安團隊
```

複雜需求最常見的危害：某條規則改了，測試人員只更新了一個地方，另一個地方還是舊版——然後出現矛盾。

### 病 4：遺漏（Omission）

**定義**：缺少某些情境下系統應有的行為描述，最常見於異常路徑。

大多數人在寫需求時，腦子裡跑的是成功流程（happy path）。但真實系統有大量邊界情境：網路斷線、用戶輸入不合法、第三方服務超時、磁碟空間不足……

**Before（遺漏異常路徑）**
```
當用戶提交付款時，系統應向支付閘道發起請求，
並在成功後顯示訂單確認頁面。
```

如果支付閘道逾時怎麼辦？如果回傳錯誤碼呢？如果網路中斷呢？訂單是否已建立、款項是否已扣除——這些遺漏在支付場景裡可能變成財務事故。

**After（補充異常路徑）**
```
REQ-PAY-01（成功路徑）
  當用戶提交付款，且支付閘道在 10 秒內回傳成功狀態（HTTP 200,
  status=succeeded）時，系統應建立訂單紀錄並顯示訂單確認頁面。

REQ-PAY-02（閘道逾時）
  如果支付閘道未在 10 秒內回應，則系統應取消該次付款嘗試，
  顯示「付款逾時，請重新嘗試」，並確保未重複扣款（冪等性保護）。

REQ-PAY-03（閘道錯誤）
  如果支付閘道回傳錯誤狀態（status=failed），
  系統應顯示閘道提供的錯誤訊息（不超過 100 字元），
  並提供「更換付款方式」連結。

REQ-PAY-04（網路中斷）
  如果用戶在提交後斷線導致無法確認結果，
  系統應在用戶重新連線後顯示「您的上一筆付款狀態未知，
  請至訂單歷史確認」，並主動查詢支付閘道取得最新狀態。
```

EARS 論文特別強調：遺漏最常發生在「不想要的行為（unwanted behaviour）」上，也就是系統出錯時該怎麼辦。這就是 EARS 的 `If...then` 句型存在的原因。

> 如果你想看 EARS 五種句型的完整介紹，見 [Ch 11 EARS 深入：五種句型馴服英文](./11-ears-notation.md)。

### 病 5：重複（Duplication）

**定義**：同樣的需求在文件不同地方用不同文字反覆陳述。

重複聽起來無害，但它的後果很嚴重：當需求改變時，你要確保所有副本都一致更新。如果漏更新一個地方，文件就開始自我矛盾——讀到不同副本的人會做出不同的實作。

**Before（重複）**
```
第 3 節：認證系統應支援 OAuth 2.0 登入。
...
第 7 節：為了方便企業用戶，系統需要整合第三方身份驗證，
        支援業界標準的 OAuth 2.0 協議。
```

兩段說的是同一件事，但第 3 節改規格時，第 7 節不一定會被找到一起改。

**After（單一來源）**
```
REQ-AUTH-10：第三方身份驗證（Single Source）
  系統應支援 OAuth 2.0 授權碼流程（Authorization Code Flow）
  作為第三方登入機制。

（第 7 節應改為引用：「詳見 REQ-AUTH-10」）
```

在程式碼裡，我們說 DRY（Don't Repeat Yourself）。需求文件同樣適用。唯一可接受的「重複」是引用，而且引用要有明確的編號。

### 病 6：冗長（Wordiness）

**定義**：包含不必要的文字，真正的約束被淹沒在填充語句中。

冗長需求通常來自兩個來源：複製法律合約風格，或者寫需求的人覺得「寫得越多越嚴謹」。

**Before（冗長）**
```
本系統在任何情況下均應，在不影響系統其他功能正常運行的前提下，
盡可能地以符合業界標準的方式，允許具備適當授權的系統管理員
透過系統提供的管理介面對用戶帳號進行必要的管理操作，
包括但不限於帳號的建立、修改及停用等功能。
```

有效資訊是：「系統管理員可透過管理介面建立、修改、停用用戶帳號。」
其他都是填充。

**After（簡潔）**
```
REQ-ADMIN-01：帳號管理操作
  系統管理員應可透過管理介面執行以下操作：
  a) 建立新用戶帳號
  b) 修改既有用戶帳號的屬性（姓名、電子郵件、角色）
  c) 停用用戶帳號（軟刪除，保留歷史記錄）
```

每一個字都要賺到它的位置。「不影響其他功能」是廢話（任何功能都不應該影響其他功能）；「但不限於」會讓測試人員不知道從何測起。

### 病 7：不當實作（Inappropriate Implementation）

**定義**：需求裡夾帶了設計或實作決策，而不是描述系統行為。

這是最隱微的一種病，因為寫需求的人通常知道一些技術，所以會「好心」地建議實作方式。問題是：需求應該描述「系統要做什麼」，而不是「系統要怎麼做」。當需求綁定了實作，它就剝奪了工程師選擇更好方案的空間。

> 如果你對規格和設計的邊界還不清楚，先回看 [Ch 7 規格 vs 設計 vs 實作](./07-spec-design-implementation.md)。

**Before（不當實作）**
```
系統應使用 Redis 快取使用者的工作階段資料，
TTL 設定為 30 分鐘，並將快取叢集部署在與應用服務
相同的 AWS 可用區以降低延遲。
```

這整段都是設計決策：用 Redis、TTL 30 分鐘、AWS 同可用區。如果以後換到 Memcached、改用資料庫 session 存儲、或者遷移到 GCP，這個需求就不再描述現實了。

**After（只描述行為）**
```
REQ-SESSION-01：工作階段持久化
  系統應在用戶登入後建立工作階段，並在用戶無操作
  達 30 分鐘後自動使其失效。

REQ-SESSION-02：工作階段存取效能
  工作階段驗證的回應時間（server-side，不含網路往返）
  應低於 5ms（P99）。
```

TTL 30 分鐘是需求（使用者無操作多久後登出），但用 Redis 實現是設計選擇。效能目標是需求，把快取放在同可用區是設計。

---

### 病 8：不可測（Untestability）

**定義**：無法設計一個具體的測試來確認需求是否被滿足。

不可測需求通常是把願景當需求寫：「提升用戶體驗」「增強系統安全性」「讓介面更直覺」。這些聽起來很合理，但你沒辦法設計一個 pass/fail 的測試來驗證。

**Before（不可測）**
```
系統應提供優秀的使用者體驗，讓用戶感到滿意。
```

如果測試人員問「怎麼判斷使用者體驗是否優秀」，沒有人能給出可驗證的答案。

**After（可測）**
```
REQ-UX-01：初次上手成功率
  使用者在首次使用系統時，應能在不參閱說明文件的情況下，
  在 5 分鐘內完成「建立第一份報表」任務，
  成功率目標：≥ 85%（以 N=20 的使用性測試衡量）。

REQ-UX-02：用戶滿意度評分
  系統應在每次主要任務完成後提供 5 星評分，
  月均評分目標：≥ 4.0 / 5.0。
```

不可測的需求是一種合約漏洞：它讓每個人都能聲稱他們做到了，同時讓任何人都能聲稱他們沒做到。在 AI 時代這尤其危險——AI 代理程式會把不可測的需求理解為「任何實作都算滿足」。

## 八種病的互動關係

這八種病通常不是獨立出現的。一句需求可能同時有多種：

```
「系統應快速並安全地處理用戶資料。」
      ↑                ↑         ↑
    模糊（快速）    模糊（安全）  不當遺漏（什麼資料？什麼操作？）
```

診斷的順序建議：**先找遺漏（有沒有缺少的情境）→ 再找複雜（能不能拆開）→ 再找歧義和模糊（能不能量化或消除多義）→ 最後檢查是否不當夾帶實作、是否可測試**。

## 為什麼 AI 代理程式讓這些病變得更危險

在 AI 時代之前，上面這些問題已經很頭痛了——但至少工程師讀到模糊需求會停下來問。

AI 代理程式的問題是：它**不會停下來問**，它會默默選擇一種解讀繼續生成程式碼。而且它的解讀可能非常有說服力、看起來合理，讓你在驗收前都沒意識到它走錯了路。

Thoughtworks（Liu Shangqi，2025 年 12 月）指出：「結構化的輸入輸出可以顯著提升 AI 的推理品質並降低幻覺（hallucination）。」——這直接對應了 EARS 和其他結構化記法的價值。

這就是為什麼 AWS Kiro 把 EARS 句型直接寫進 `requirements.md` 的範本，GitHub Spec Kit 用範本約束大型語言模型的輸出。這些工具不是在強迫你寫格式，而是在幫你防止上面八種病悄悄溜進你的規格。

> 如果你想看 EARS 的完整句型細節，見 [Ch 11 EARS 深入：五種句型馴服英文](./11-ears-notation.md)。  
> 如果你想看 Given-When-Then 如何解決遺漏和不可測，見 [Ch 10 從驗收條件到 BDD：Given-When-Then](./10-acceptance-criteria-bdd.md)。

## 對比取捨：各種修補策略

當你發現需求有問題，有幾條路可走：

| 策略 | 適用病症 | 優點 | 缺點 |
|-----|---------|------|------|
| 加量化條件 | 模糊、不可測 | 直接可測試 | 需要知道合理的數字從哪來 |
| 拆解為多條需求 | 複雜 | 每條獨立可追蹤 | 文件量增加 |
| 建立術語表（Glossary） | 歧義 | 一次定義處處引用 | 需要維護術語表 |
| EARS 句型 | 遺漏、歧義、模糊 | 格式強制約束缺失欄位 | 學習曲線、不適用所有需求類型 |
| Given-When-Then | 遺漏、不可測 | 直接可執行 | 對非功能需求力道不足 |
| 需求 ID + 引用 | 重複 | 保持單一來源 | 需要文件管理紀律 |
| 刪除、拆解 | 冗長、不當實作 | 去除噪音 | 需要勇氣說「這段沒用」 |

沒有一種策略能解決所有問題。真實專案裡你需要組合使用。

## 踩雷集錦

**錯誤直覺一：「我們是敏捷的，需求文件越短越好，所以不必要的細節就省了。」**

正確認識：精簡和模糊不同。敏捷方法論（敏捷宣言，2001 年）說的是「可工作的軟體勝過詳盡的文件」，意思是不要為了文件而文件，不是說需求可以模糊。每一條需求都應該足夠精確到可測試，不夠精確的需求不是「敏捷」，是「未完成的工作」。

---

**錯誤直覺二：「寫實作方式進需求是為了讓工程師更清楚，不是壞事。」**

正確認識：需求裡的實作細節是技術債的種子。當你說「用 PostgreSQL 儲存訂單」，你就把資料庫選型綁死在需求裡了——日後要換資料庫時，你不只是改設計，還要改「需求」，這在審計和追蹤上是噩夢。正確做法是在需求裡寫行為（「訂單應能持久化並在系統重啟後保留」），在設計文件裡寫 PostgreSQL。

---

**錯誤直覺三：「這個需求我們自己知道是什麼意思，不用寫得那麼明確。」**

正確認識：「我們自己知道」只在當下成立。六個月後新加入的工程師、外包廠商、或者你自己在換了脈絡之後，都不再「知道」了。更重要的是：對 AI 代理程式而言，「大家都知道」根本不存在——它只能讀你寫下來的字。你腦中的默認知識對 AI 是不可見的。

---

**錯誤直覺四：「遺漏的需求等遇到再補就好，現在先做主要功能。」**

正確認識：需求遺漏的成本會隨著開發進度指數增長。如果在需求階段補一條異常路徑需要 1 小時，在設計完成後要改需要重做設計文件；在測試發現需要改程式碼和測試；在生產環境出問題需要緊急修補、可能還有用戶損失。這個倍數效應在 [Ch 6 變更成本曲線](./06-cost-of-change-curve.md) 裡有詳細討論（注意：「1:100」這個比率是常被簡化引用的估算，實際倍數與專案性質有關）。

---

**錯誤直覺五：「AI 生成的需求應該沒有這些問題，因為 AI 很聰明。」**

正確認識：AI 工具可以幫你起草需求，但它的輸出品質取決於你給它的 prompt 品質——而 prompt 本身可能就有歧義和遺漏。AI 是放大器，不是矯正器。糟糕的問題 → 糟糕的需求 → 糟糕的程式碼，整條鏈的起點是你對問題的清晰度。

## 進階延伸：從病症到系統性預防

逐條修病是被動的。成熟的需求工程有更主動的做法：

**需求審查（Requirements Review）**：在實作之前把需求拿給沒有參與撰寫的人讀，包括工程師、測試人員、用戶代表——他們問的「這是什麼意思」就是歧義；他們說「所以如果 X 發生怎麼辦」就是在找遺漏。

**需求可追蹤性矩陣（Requirement Traceability Matrix，RTM）**：把每一條需求對應到設計決策和測試案例，這樣當需求更改時，你知道哪些測試和設計要一起更新，不當實作和重複的問題會在這個過程中浮現。

**需求模板（Requirements Template）**：強制每條需求都填寫特定欄位（觸發條件、前置條件、成功後果、失敗後果、量化指標），未填的欄位就是遺漏。EARS 句型本質上就是一種模板——`While..., When..., the system shall...` 的句型迫使你思考觸發條件和系統回應。

這些工具和方法在後續章節裡會深入展開。這裡先建立診斷意識。

## 動手練習

拿下面這份「電商結帳頁面」的需求初稿，用本章介紹的八種分類，找出所有你能發現的缺陷，並為每一條寫出改進版：

```
需求草稿（刻意設計成有問題的版本）：

R1. 結帳頁面應快速載入，並顯示購物車內容。

R2. 用戶可以選擇配送方式，包含標準配送和快速配送，
    系統應根據地址計算費用，並使用 Google Maps API
    驗證地址的有效性。

R3. 支付時應確保安全，並支援主流支付方式。

R4. 訂單確認後，系統應通知相關人員。

R5. 如果用戶在結帳過程中遇到問題，系統應提供幫助。

R6. 系統應快速確認訂單並存儲到資料庫中，
    資料庫使用 PostgreSQL，並啟用 row-level security。
```

參考答案思路：
- R1：模糊（快速是多快？）、遺漏（購物車空的怎麼辦？）
- R2：複雜（配送費計算和地址驗證是兩件事）、不當實作（Google Maps API 是設計決策）
- R3：模糊（安全是指什麼？主流支付方式有哪些？）
- R4：歧義（相關人員是誰？通知內容是什麼？用什麼方式通知？）
- R5：不可測（「提供幫助」怎麼測試？）、遺漏（什麼問題？哪些情況？）
- R6：不當實作（PostgreSQL + row-level security 是設計選擇，不是需求）

## 本章重點整理

- 自然語言是有損壓縮，意圖在傳遞過程中必然失真。
- EARS 論文（Mavin et al., RE'09, 2009）從工業實踐歸納出八種缺陷：歧義、模糊、複雜、遺漏、重複、冗長、不當實作、不可測。
- 每種缺陷有其特定症狀，診斷順序建議：遺漏 → 複雜 → 歧義/模糊 → 不當實作 → 可測性。
- AI 代理程式無法停下來問問題——這讓上述八種病的風險比人工開發環境更高，而不是更低。
- 修病的策略要組合使用：量化、拆解、術語表、結構化句型、可執行測試、需求 ID。
