# Ch 18 — 子領域：Core / Supporting / Generic

> **目標**：掌握子領域（Subdomain）三分類的判斷邏輯，學會區分 Core、Supporting、Generic，並能把分類結果轉化為「哪裡自己建模、哪裡買現成」的投資決策。

## 問題從這裡開始

2003 年以前，大多數企業系統的架構師面對「把所有業務塞進一個大系統」時，真正的困難不是技術，是優先序的混亂：

- 電商平台把「購物車商品計算邏輯」和「寄送確認信」放在同一個服務物件裡
- 銀行把「利率計算引擎」和「登入帳密管理」用一樣的迭代速度在維護
- 醫療軟體把「診斷規則決策」和「報表格式化」用相同的工程資源在打磨

這三個例子的共通點：所有東西看起來都「很重要」，於是什麼都要自己做到最好，最後什麼都做得不夠好。

Eric Evans 在《Domain-Driven Design》（2003, Addison-Wesley）提出的子領域分類，本質上是一把優先序的刀：**不同種類的子領域，代表著截然不同的投資策略**。

## 直覺心智圖：投資報酬率矩陣

把你的業務邊境想成三個地帶：

```
        競爭差異
    高 ▲
       │  ██████████████
       │  █ CORE       █   ← 你的戰場，每個建模決策都攸關生死
       │  ██████████████
       │
       │  ░░░░░░░░░░░░░
       │  ░ SUPPORTING ░   ← 你的配件，需要客製，但不是核心武器
       │  ░░░░░░░░░░░░░
       │
       │  ···············
       │  · GENERIC    ·   ← 別人的戰場，買現成、用 SaaS
       │  ···············
    低 └──────────────────▶
           業務複雜度
```

更直接的說法：如果你的競爭對手做出跟你一模一樣的這個功能，**你會不會輸掉市場**？會 → Core；不會 → 往下分。

## 正式定義

### 子領域（Subdomain）是問題空間的分區

先澄清一個容易混淆的位置關係：

| 層次 | 術語 | 活在哪裡 |
|------|------|----------|
| 問題空間 | **Subdomain（子領域）** | 業務現實，不是程式碼 |
| 解法空間 | **Bounded Context（限界上下文）** | 你的設計與程式碼 |

子領域是你去「發現」的，限界上下文是你去「設計」的。同一個子領域可能由一個或多個限界上下文來實現；反過來，一個組織混亂的大系統也可能把多個子領域塞進同一個限界上下文（這通常是問題來源）。

> 如果你對限界上下文還不熟，先回看 [Ch 16 Bounded Context：模型在哪裡為真](./16-bounded-context.md)

### 三種子領域

**核心子領域（Core Subdomain）**

這是你的競爭優勢所在。業務的獨特邏輯、你用數年時間打磨的領域知識、讓客戶願意付錢給你而不是競爭對手的那個東西。

特徵：
- 業務規則複雜且持續演化
- 做對了帶來競爭差異，做錯了直接失去市場
- 通常沒有現成產品能完整覆蓋你的需求
- 最好的工程師和最多的建模時間應該在這裡

**支撐子領域（Supporting Subdomain）**

Core 運作所需要的「配件」。沒有它，Core 跑不起來，但它本身不是你的競爭差異。

特徵：
- 業務規則是客製的，但規則相對穩定
- 如果做錯，會讓 Core 出問題，但做得再好也不會讓你贏得市場
- 通常沒有完全匹配的現成產品，但也不值得用最頂尖的工程師去打磨
- 可以交給外包或初階工程師，Core 的人要知道它在做什麼

**通用子領域（Generic Subdomain）**

已經被整個產業解決過的問題。你做的和任何競爭對手做的基本上一樣，所有人都有相同的需求。

特徵：
- 需求高度標準化
- 有成熟的開源方案或 SaaS 產品
- 自己做不會帶來任何競爭優勢，只會浪費工程資源
- 直接買、用現成的

## 具體例子：電商平台

讓我們用一個電商平台來走過分類過程。這個平台主打「個人化推薦」和「動態定價」。

### 先識別業務能力

```
電商平台業務能力清單
├── 商品推薦演算法（個人化）
├── 動態定價引擎
├── 訂單管理
├── 庫存追蹤
├── 物流整合
├── 用戶帳號與登入
├── 電子郵件通知
└── 金流（收款、退款）
```

### 逐項分類

**「商品推薦演算法（個人化）」→ Core**

這個平台的核心賣點就是「比競爭對手更懂你要什麼」。推薦模型的迭代速度、訓練資料的選取、特徵工程的設計，全部都是競爭武器。沒有任何現成的黑盒 SaaS 能精確地嵌入你的業務語境。這裡的領域模型要精雕細琢。

**「動態定價引擎」→ Core**

同理。你的定價規則（季節性、庫存量、競爭者行為、用戶行為）是專有知識，是建立在業務數據和商業判斷之上的核心邏輯。這個模型做對了，毛利率就上去了。

**「訂單管理」→ Supporting**

訂單從建立到完成的流程是客製的——你的訂單狀態機、特定的拆單邏輯、跨境訂單的規則，都是為你的業務設計的。但「訂單管理做得特別好」並不是你的市場賣點。這裡的建模要做，但用「夠用就好」的標準。

**「庫存追蹤」→ Supporting**

庫存規則有業務特異性（例如：虛擬庫存的算法、預售庫存的鎖定邏輯），需要客製，但這不是競爭差異。歸 Supporting。

**「物流整合」→ Supporting / Generic（視情況）**

如果你和第三方物流廠商整合，接口是標準的，那就是 Generic；如果你有自己的配送網絡，有特殊的路由優化，那部分邏輯可以升格到 Supporting 甚至 Core。分類不是一次性的，會隨業務演化。

**「用戶帳號與登入」→ Generic**

OAuth 2.0、MFA、密碼雜湊——這些問題整個產業早就解決了。用 Auth0、Firebase Authentication、Keycloak，任何一個都好。你從頭實作這個，只是在浪費工程師的時間。

**「電子郵件通知」→ Generic**

用 SendGrid、Amazon SES、Postmark。這完全不是你的競爭差異，自己養 SMTP 伺服器是浪費。

**「金流」→ Generic**

用 Stripe、Braintree、藍新。PCI DSS 合規性是你最不想自己搞的事。

### 分類結果

```
電商平台子領域分類
├── Core（建模投入最多）
│   ├── 商品推薦演算法
│   └── 動態定價引擎
├── Supporting（足夠好就行）
│   ├── 訂單管理
│   ├── 庫存追蹤
│   └── 自有配送路由（如果有的話）
└── Generic（買現成，不自建）
    ├── 用戶帳號與登入
    ├── 電子郵件通知
    └── 金流
```

## 判斷方法：三個問題

當你在分類一個子領域時，問自己這三個問題：

**問題一：如果競爭對手也實作了一個「差不多的版本」，你會輸掉市場嗎？**

- 是 → 很可能是 Core
- 否 → 繼續問第二個問題

**問題二：這個領域的規則有業務特異性，沒有現成產品能完整覆蓋嗎？**

- 是 → 可能是 Supporting（客製建置，但不是競爭武器）
- 否 → 繼續問第三個問題

**問題三：這個問題整個產業都有相同的需求，有成熟的現成解法嗎？**

- 是 → Generic（買現成）
- 不確定 → 先當 Supporting，之後再評估是否降級到 Generic 或升級到 Core

## 分類如何影響建模決策

分類不是學術遊戲，它直接影響你的工程策略：

| 子領域類型 | 建模深度 | 建模方法 | 人員配置 | 技術選型 |
|-----------|----------|----------|----------|----------|
| **Core** | 深度建模，反覆精煉 | 通用語言、Event Storming、精細 Aggregate 設計 | 最資深的領域專家+工程師協作 | 自建，不用現成框架強加約束 |
| **Supporting** | 足夠建模，穩定後少動 | 輕量 CRUD，簡單狀態機 | 中階工程師，定義清楚的接口 | 可用框架，但要做好隔離 |
| **Generic** | 零建模（讓供應商建模） | 看 API 文件、讀設定 | 任何能整合 API 的人 | 完全外包給 SaaS / 開源方案 |

**Core 的隔離原則**

Core 子領域的限界上下文要和 Supporting、Generic 嚴格隔離。常見的作法是：Generic 的服務（例如：Auth0）透過 Anticorruption Layer（防腐層）接入你的系統，讓第三方的語言和概念無法污染你的 Core 領域模型。

> 如果你對防腐層和整合模式還不熟，先回看 [Ch 17 Context Mapping 與整合模式](./17-context-mapping.md)

## 底層機制：為什麼三分類有效

在 Evans 提出這個分類之前，業界的主流思路是「統一資料模型」——把整個企業的業務抽象成一個一致的模型。IBM 的企業資料模型、SAP 的通用業務物件，都走這個方向。

問題是：**統一模型讓所有東西平等，但所有東西根本不平等。**

把「推薦演算法」和「發信功能」放在同一張 ER Diagram 裡維護，隱含了一個假設：它們的演化速度、正確性要求、業務複雜度是可比的。這個假設是錯的。

三分類的深層邏輯來自一個商業現實：

**企業的競爭優勢來自做了別人做不到（或做不好）的事，而不是做了別人都在做的事。**

花一年打磨自己的登入系統，和花一年打磨自己的推薦引擎，商業回報是不可能相同的。三分類讓你看清楚這個不對稱性，並把它翻譯成工程決策。

## 子領域與限界上下文的對應關係

這是很多人第一次接觸 DDD 時會卡住的地方，我們把它講清楚：

**一個 Core 子領域，通常對應一個精心設計的限界上下文**（有時是多個，視複雜度而定）。你不想讓 Core 的模型受到任何其他上下文的污染。

**一個 Generic 子領域，通常不對應你自己設計的限界上下文**。它的「限界上下文」是供應商的系統，你要做的是在邊界上做好轉譯（Anticorruption Layer）。

**一個 Supporting 子領域，對應一個輕量的限界上下文**，設計標準是「能滿足需求、接口清晰」，不需要深度領域建模。

```
問題空間（你去發現）          解法空間（你去設計）
─────────────────           ──────────────────────────
Core Subdomain          →   精心設計的 Bounded Context
                            （深度 UL、Entity、Aggregate）

Supporting Subdomain    →   輕量 Bounded Context
                            （CRUD 為主，接口要清晰）

Generic Subdomain       →   第三方系統 + ACL
                            （你不設計它的內部）
```

## 踩雷集錦

### 錯誤一：把「業務流程重要」等同於「是 Core」

**錯誤直覺**：「訂單管理很重要，沒有訂單就沒有收入，所以是 Core。」

**正確認識**：「重要」不是 Core 的判斷標準，「競爭差異」才是。訂單管理流程幾乎每個電商都一樣——建立、付款、出貨、完成。你做得再好，客戶也不會因為「你的訂單流程比競爭對手好 10%」而選你。它是 Supporting。

Core 的判斷問題是：「如果競爭對手複製了你這個功能，你會輸掉市場嗎？」

### 錯誤二：把「技術複雜」等同於「是 Core」

**錯誤直覺**：「我們的登入系統做了 MFA、OAuth、SSO、session management，技術上很複雜，應該是 Core。」

**正確認識**：技術複雜度和業務差異性是兩個維度。登入系統可以技術上很複雜，但它仍然是 Generic——因為這個複雜度已經有 Auth0、Keycloak 這類成熟產品幫你解決了。你在重新發明輪子，而且是一個沒有競爭意義的輪子。

### 錯誤三：Core 子領域永遠不變

**錯誤直覺**：「我們三年前識別的 Core 就是 Core，不需要重新評估。」

**正確認識**：子領域的分類會隨市場演化。當你的「核心差異」變成行業標配，它可能從 Core 降格到 Supporting 或 Generic。例如：十年前「行動支付整合」可能是某些業務的 Core，今天已經是 Generic——有太多成熟的解法。定期重新評估，是維護子領域分類的必要工作。

### 錯誤四：Generic 就是不重要，可以馬虎

**錯誤直覺**：「金流是 Generic，所以隨便選一個就好，不需要認真整合。」

**正確認識**：Generic 的意思是「不是競爭差異」，不是「不重要」。金流出問題一樣會讓你失去客戶。Generic 的策略是「用最好的現成方案，並且做好整合」，而不是「不在乎」。

### 錯誤五：Supporting 可以直接呼叫 Core 的內部

**錯誤直覺**：「Supporting 子領域的訂單服務要拿推薦分數，直接呼叫推薦引擎的內部方法最方便。」

**正確認識**：這會讓 Supporting 的代碼耦合到 Core 的內部，Core 的任何重構都會衝擊 Supporting。正確做法是 Core 暴露一個清晰定義的接口（Open Host Service 或 Published Language），Supporting 透過這個接口取得它需要的資訊。

> 如果你對通用語言在接口設計上的作用還不熟，先回看 [Ch 15 通用語言 Ubiquitous Language](./15-ubiquitous-language.md)

## 進階延伸

### 子領域分類在 AI 輔助建模中的角色

2024-2026 年，DDD 的子領域分類在「LLM 輔助建模」的場景下獲得了新的意義（以下為 version-dependent 的觀察，反映 2024-2026 年的實踐趨勢，可能隨 AI 工具發展而變化）：

**Core 子領域 ≠ AI 可以自動生成的部分**

AI 工具（如 GitHub Copilot、AWS Kiro、Claude）在 Generic 和 Supporting 子領域的程式碼生成上表現很好——因為這些問題已經有大量公開的模式可以學習。但 Core 子領域的領域邏輯，恰恰是最不像「教科書範例」的部分。它需要領域專家的深度參與，AI 生成的代碼必須被仔細驗證。

**結論：越是 Core，越需要人類領域專家介入；Generic 交給 AI 生成就好。**

**子領域作為 LLM 上下文的邊界**

當你把領域模型的描述交給 LLM 輔助開發時，清晰的子領域邊界就是一個天然的「上下文框框」。你不需要把整個系統的所有概念塞進同一個 prompt——你告訴 LLM「現在我們在推薦子領域的限界上下文裡工作，這個上下文的詞彙表是...」，這樣生成的代碼會更符合你的領域模型。

> 這個主題在後面的 [Ch 34 通用語言作為 LLM 的詞彙表](./34-ubiquitous-language-as-glossary.md) 和 [Ch 35 Bounded Context = Agent Scope](./35-bounded-context-agent-scope.md) 會深入展開。

### 子領域分類與組織設計：康威定律的角度

康威定律（Conway's Law）說：組織設計出的系統架構往往反映組織的溝通結構。

子領域分類有一個組織設計的隱喻：

- **Core 子領域**：應該有一個穩定的、有深度領域知識的跨職能團隊負責（包括業務專家+工程師+設計師）。頻繁換人是 Core 建模最大的敵人。
- **Supporting 子領域**：可以是一個功能性的開發團隊，接受 Core 團隊的接口定義。
- **Generic 子領域**：由平台或基礎設施團隊負責選型和維護第三方整合，不需要業務領域知識。

把子領域分類對齊到團隊設計，能讓 Conway's Law 幫你的忙，而不是害你。

## 動手練習

選一個你目前工作或熟悉的軟體系統（任何領域都可以），完成下列步驟：

**步驟一**：列出這個系統至少 8 個主要業務能力（不是技術模組，是業務能力，例如「用戶推薦」而不是「recommendation-service」）。

**步驟二**：對每個業務能力問三個問題：
1. 如果競爭對手也有這個功能，你的業務會受多大影響？（1-5 分）
2. 業務規則有業務特異性嗎？市面上有現成方案能完整覆蓋嗎？
3. 這是整個產業的通用問題嗎？

**步驟三**：根據問題答案把 8 個能力分到 Core / Supporting / Generic 三個桶裡。

**步驟四**：對 Core 子領域，嘗試列出 3-5 個它的關鍵業務規則（用自然語言，不要寫程式碼）。這些規則是你最應該投入建模力氣的地方。

**步驟五**（選做）：識別你的系統裡有沒有「本來應該是 Generic，但現在被當作 Core 在用資源」的情況。如果有，粗估一下每年因此浪費的工程成本。

## 本章重點整理

- 子領域（Subdomain）活在**問題空間**，限界上下文（Bounded Context）活在**解法空間**。不要混淆。
- **Core**：競爭差異所在，業務規則複雜且演化，沒有現成方案能完整覆蓋，投入最多建模力氣與最優秀的人。
- **Supporting**：Core 運作所需的客製配件，需要建置但不是競爭武器，足夠好即可。
- **Generic**：產業通用問題，有成熟解法，直接買，絕對不要自建。
- 分類的判斷標準是**競爭差異性**，不是技術複雜度、業務流程重要性，也不是開發難度。
- 子領域分類是**動態的**：市場演化、競爭格局改變，都可能讓 Core 降格或讓 Supporting 升格。
- 在 AI 輔助開發的場景下，Core 子領域最需要人類領域專家介入；Generic 子領域最適合交給 AI 生成。

- [ ] 我能解釋為什麼子領域（Subdomain）和限界上下文（Bounded Context）不是同一個東西，它們分別活在哪個空間。
- [ ] 我知道 Generic 子領域「不是競爭差異」和「不重要」是兩件事，Generic 的正確策略是什麼。
- [ ] 對我熟悉的一個系統，我能說出哪些部分是 Core（且有把握說出理由），哪些部分目前被錯誤地當作 Core 在投入資源。
- [ ] 我能說明子領域分類在 AI 輔助建模的場景下有什麼新的意義（哪裡讓 AI 做，哪裡不行）。

## 延伸閱讀

**《Domain-Driven Design: Tackling Complexity in the Heart of Software》（Blue Book）** — Eric Evans（Addison-Wesley, 2003）
<https://www.amazon.com/Domain-Driven-Design-Tackling-Complexity-Software/dp/0321125215>
子領域三分類的原始出處。重點讀 Part IV Strategic Design，特別是第 15 章（Distillation）。Evans 在那裡詳細討論如何識別 Core Domain 並讓它與其他部分隔離。這本書的子領域概念在原版裡稱為「核心領域蒸餾」（Distillation of the Core Domain），三分類的術語在後續社群中被明確化。

**《Domain-Driven Design Distilled》** — Vaughn Vernon（Addison-Wesley, 2016）
<https://www.amazon.com/Domain-Driven-Design-Distilled-Vaughn-Vernon/dp/0134434420>
如果 Blue Book 太重，從這裡開始。Vernon 用更現代、更簡潔的語言把子領域分類、限界上下文、Context Map 整合成一個易懂的全景。第 2 章就直接示範如何識別 Core、Supporting、Generic，並說明如何用子領域分類指導 bounded context 設計。

**bliki: Domain Driven Design** — Martin Fowler
<https://martinfowler.com/bliki/DomainDrivenDesign.html>
一頁快速定位 DDD 核心概念（包括子領域分類在戰略設計中的位置）。Fowler 是 Evans 的長期合作者，這篇文章是最常被引用的 DDD 入門定位文，更新於 2020 年 4 月。

**ddd-crew/context-mapping** — DDD Crew（GitHub, contributors incl. Kacper Gunia, Nick Tune）
<https://github.com/ddd-crew/context-mapping>
子領域分類要配合 Context Map 使用才完整。這個 repo 是九種 Context Map 整合模式（ACL、OHS、Conformist 等）最清晰的社群參考。直接讀 README 的決策指南，能幫你決定每個子領域邊界之間應該用哪種整合模式。

**Accelerate your Strategic Design with LLMs** — Thomas Coopman（DDD.academy）
<https://ddd.academy/accelerate-your-strategic-design-with-llms/>
2024-2026 的新視角：如何用 LLM 輔助子領域識別和通用語言精煉，同時說明哪些判斷不能交給 AI（子領域的競爭差異判斷需要人類的業務理解）。這是本章「Core vs AI 生成邊界」討論的延伸讀物。
