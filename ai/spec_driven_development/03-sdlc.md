# Ch 3 — SDLC 到底是什麼

> **目標**：理解「軟體開發生命週期（Software Development Life Cycle，SDLC）」各 phase 為何存在、各自產出什麼、phase 之間的順序要多嚴，以及這場關於「嚴格程度」的爭論為什麼決定了整個軟體工程史的走向。

---

## 先給一張心智圖

```
需求 (Requirements)
  │  ← 「我們要做什麼？為什麼？」
  ▼
設計 (Design)
  │  ← 「我們怎麼做？架構、介面、技術選型」
  ▼
實作 (Implementation)
  │  ← 「寫程式碼」
  ▼
測試 (Testing)
  │  ← 「我們做的和說好的一樣嗎？」
  ▼
部署與維運 (Deployment / Operations)
       ← 「上線、監控、維護、下一輪回饋」
```

這條管線（pipeline）不是憑空發明的。它反映一個很直接的事實：**你不能在不知道蓋什麼的情況下打地基，也不能在不打地基的情況下蓋牆。** 每一個 phase 都依賴上一個 phase 的產出。

問題在於「依賴」這件事究竟有多剛性——這是下面整章要講的。

---

## 歷史脈絡：為什麼我們需要 SDLC

1960 年代之前，軟體開發是個人技藝。一個人腦子裡想好，坐下來就寫，寫完就改。計畫？文件？那是給硬體工程師用的東西。

隨著系統規模擴大——多人團隊、跨年合約、國防與航太——「個人技藝」模式開始瓦解：

- 人員流動導致知識流失：A 離職，沒有人知道那個模組在做什麼。
- 驗收爭議無從解決：「你說要的不是這樣」、「不，就是這樣」。
- 軟體危機（Software Crisis）：1968 年 NATO 研討會第一次正式討論「軟體工程」作為一個學科。

SDLC 是對這些痛點的直接回應：**把腦子裡的隱性知識，轉成可以傳遞、可以驗證的文件。** 每個 phase 都有進入條件（input）和可交付產物（deliverable），讓多人協作成為可能。

Winston Royce 在 1970 年的論文〈Managing the Development of Large Software Systems〉列出七個 phase：

```
系統需求 (System Requirements)
  → 軟體需求 (Software Requirements)
  → 分析 (Analysis)
  → 程式設計 (Program Design)
  → 編碼 (Coding)
  → 測試 (Testing)
  → 維運 (Operations)
```

這張圖後來被人稱為「瀑布（Waterfall）」——但 Royce 自己並沒有用這個詞（「Waterfall」這個名詞是 Bell & Thayer 在 1976 年論文裡才引入的），而且 Royce 明確說過，把這七個 phase 嚴格跑一遍是「risky and invites failure」（有風險且容易失敗）。他的建議是至少要跑兩遍。

> 這個誤會在 [Ch 4 瀑布的真相：Royce 1970 與一個誤會](./04-waterfall-myth.md) 會完整講清楚。現在先記住：SDLC 的 phase 結構是 Royce 的，但「一次走完就好」這個剛性解讀是後人加上去的。

## 每個 Phase 到底在產出什麼

### Phase 1：需求（Requirements）

**輸入：** 利害關係人的想法、問題陳述、業務目標  
**產出：** 需求規格書（Software Requirements Specification，SRS）、使用案例（Use Case）、用戶故事（User Story）

需求 phase 要回答的核心問題是 **WHAT + WHY**：系統要做什麼、為什麼對使用者有價值。

這個 phase 常被低估，卻是整個管線裡最貴的失誤點。Fred Brooks 在〈No Silver Bullet〉（1986）說：

> 「決定到底要蓋什麼，是建造軟體系統中最困難的單一部分。沒有哪個部分在做錯時會更嚴重地損害最終系統，也沒有哪個部分在事後更難修正。」

需求的難點不是技術，是溝通：利害關係人說的和腦子裡想的不一樣，工程師理解的和說的不一樣。Ch 8 到 Ch 12 整個 Part 2 都在處理這個問題。

### Phase 2：設計（Design）

**輸入：** 需求規格  
**產出：** 架構文件、介面規格（API contract）、資料模型、技術決策紀錄（ADR）

設計 phase 要回答的核心問題是 **HOW**：在給定的技術環境和限制條件下，如何把需求實現出來。

注意：設計不是「把程式碼想好再打字」。設計是在更高的抽象層次上做決策——哪些模組？它們怎麼互動？用什麼資料結構？哪些邊界絕對不能跨越？

一個典型的設計產物長這樣：

```
系統邊界圖：
  [使用者瀏覽器]
       │ HTTPS
       ▼
  [API Gateway]
       │
   ┌───┼───────────┐
   ▼   ▼           ▼
[Auth] [Order Svc] [Inventory Svc]
         │               │
         └──── [DB] ─────┘
```

這種圖不能執行，但它確立了每個服務的職責邊界。後面所有的實作決策都在這個框架內進行。

### Phase 3：實作（Implementation）

**輸入：** 設計文件、需求規格  
**產出：** 可執行的程式碼、版本紀錄（commit history）

實作 phase 就是寫程式。從 Brooks 的「本質 vs 意外（Essence vs. Accident）」框架來看，寫程式碼屬於「意外（Accident）」——它是目前生產軟體的技術手段，但不是軟體複雜性的根本來源。

這個判斷在 AI 工具出現後變得非常重要：如果 LLM 可以接近自動化地完成實作，那麼瓶頸和槓桿點就轉移到了需求與設計。Sean Grove 在 2025 年的〈The New Code〉演講（AI Engineer World's Fair, June 3–5, 2025）中直接說：程式碼是「specification 的一個有損投影（lossy projection）」——你從程式碼裡很難還原當初的設計意圖。

> 如果你對「瓶頸轉移到意圖」這個概念還不熟，先回看 [Ch 1 為什麼「規格」突然重要了：AI 把瓶頸推到意圖上](./01-why-specs-matter-now.md)。

### Phase 4：測試（Testing）

**輸入：** 可執行程式碼、需求規格、設計文件  
**產出：** 測試報告、缺陷紀錄（bug report）、品質評估

測試 phase 的根本問題：**「我們做出來的和說好的一樣嗎？」**

這裡有個常被忽視的邏輯：**測試要跟需求對應，不是跟程式碼對應。** 測試驗證的不是「程式碼正確執行」，而是「程式碼的行為符合需求」。如果需求本身是錯的，測試通過也沒有意義。

這就是為什麼驗收測試（Acceptance Testing）要在需求 phase 就開始設計，而不是等到程式碼寫完。

### Phase 5：部署與維運（Deployment / Operations）

**輸入：** 通過測試的程式碼、基礎設施規格  
**產出：** 運行中的系統、監控指標、使用者回饋、下一輪需求的原材料

維運 phase 產生的回饋是整個循環的起點：系統上線後，你才知道哪些需求說清楚了、哪些沒說清楚、哪些根本是錯的。這個回饋如何流回需求 phase，決定了你的開發流程是「一次性瀑布」還是「持續迭代」。

## 每個 Phase 產出什麼：一覽表

| Phase | 核心問題 | 典型產物 | Brooks 的分類 |
|---|---|---|---|
| 需求 | WHAT + WHY | SRS、Use Case、User Story | 本質（Essence）|
| 設計 | HOW（架構層） | 架構圖、API 規格、ADR | 本質（Essence）|
| 實作 | 用什麼語言/框架表達 | 程式碼、commit | 意外（Accident）|
| 測試 | 做的和說好的一樣嗎 | 測試報告、缺陷紀錄 | 驗證（Verification）|
| 維運 | 實際跑起來怎麼樣 | 監控指標、使用者回饋 | 觀察（Observation）|

這張表的重要含義：**大多數的價值和風險集中在最上面兩行**。這是整門規格驅動開發課程的核心前提。

## 「順序要多嚴」：軟體工程史的核心爭論

### 嚴格順序（Sequential）的邏輯

如果你把 SDLC 的每個 phase 看成嚴格依序的——需求必須全部完成才能開始設計，設計必須全部完成才能開始寫程式——那麼理論上你會得到：

- **完整的可追溯性（Traceability）**：每一行程式碼都能追溯到一條需求。
- **驗收有據可查**：客戶說要的，有書面為憑。
- **並行開發成為可能**：設計定案後，多個團隊可以分工實作不同模組。

這個做法在有些領域非常合理——航太、醫療器材、核能。當修改成本極高（火箭上天就不能重開機）、合規要求嚴格（FDA 要求每一個決策都有文件），前期花大量時間鎖定需求是值得的。

### 嚴格順序的代價

問題在於：**需求往往是不可知的，直到你做出一個可以操作的東西讓客戶試用。**

Fred Brooks 在《人月神話（The Mythical Man-Month）》裡說，你能跟客戶解釋清楚你要建的系統，唯一的辦法就是先做一個出來。這不是客戶的問題，是人類溝通的本質限制。

Barry Boehm 在《Software Engineering Economics》（1981）提出「變更成本曲線（Cost of Change Curve）」：越晚發現問題，修復成本越高。這個方向性的結論是可信的，但流傳的精確數字——「1:100」，出處通常被引用為「IBM Systems Sciences Institute 研究」——實際上很可能是無從查證的都市傳說。Hillel Wayne 調查後的結論是：「有一個小問題：那份 IBM Systems Sciences Institute 研究根本不存在。」（The Register, 2021-07-22）

> 關於這條曲線的完整討論與考據，見 [Ch 6 變更成本曲線——以及怎麼誠實引用它](./06-cost-of-change-curve.md)。

如果嚴格順序加上「需求不可知」這兩個前提同時成立，你得到的結果就是：花了大量時間完成的需求文件，在程式碼寫完後才被客戶否定。Standish Group 的 CHAOS 報告長期引用「大多數 IT 專案失敗或延誤」的數字，並把需求問題列為主因之一——不過 CHAOS 的方法論本身受到學術界嚴肅批評（Eveleens & Verhoef, IEEE Software 2010），它對「失敗」的定義太窄，其原始數據也是非公開的。這個數字可以作為軼事引用，但不宜當成精確數據。

### 迭代與敏捷的回應

Royce 1970 年本人就建議「至少跑兩遍」。1990 年代之後，Spiral Model（Barry Boehm, 1988）、Rational Unified Process（RUP）、Extreme Programming（XP）等各種迭代方法陸續出現。

2001 年，17 位軟體從業者在猶他州 Snowbird 簽署了《敏捷軟體開發宣言（Manifesto for Agile Software Development）》，把這場對話結晶成四個價值觀：

```
個人與互動  重於  流程與工具
可工作的軟體  重於  詳盡的文件
與客戶協作  重於  合約協商
回應變化  重於  遵循計劃

「雖然右側的項目有其價值，
 我們更重視左側的項目。」
```

注意最後那行：他們沒有說「文件沒有價值」，只是說「可工作的軟體」更重要。但在實務執行中，這個「重於」常常被簡化成「不需要文件」。

這個簡化帶來了反作用：當 AI 代理進入開發流程，它沒有辦法從「口傳文化」裡提取意圖。它需要結構化的文件。敏捷把文件壓到最少的做法，反而讓 AI 輔助開發更難有效工作。

> 敏捷的完整討論在 [Ch 5 迭代與敏捷：用快速回饋換掉大份前期規格](./05-iterative-agile.md)。

## 相同 Phase、不同嚴格程度：對比

| 向度 | 嚴格序列（Waterfall 精神）| 輕量迭代（Agile 精神）|
|---|---|---|
| 需求何時完成 | 設計開始前全部鎖定 | 每個 sprint 前確認這一輪的需求 |
| 設計的粒度 | 完整的系統架構圖、所有介面 | 足夠讓這個 sprint 動工的架構決策 |
| 測試的時機 | 實作完成後集中測試 | 每個功能完成後立即測試（TDD/CI）|
| 回饋頻率 | 系統全部完成後一次交付客戶 | 每個 sprint 末交付可用功能給客戶 |
| 文件量 | 大量前期文件 | 剛好夠用的文件，code as doc |
| 適用情境 | 需求穩定、監管嚴格、合約固定 | 需求演化、市場探索、容錯空間大 |
| 主要風險 | 後期才發現需求錯誤，修改成本高 | 技術債累積、隱性設計決策難以傳遞 |

沒有一個永遠正確。選哪種取決於你的需求穩定性、交付頻率、監管環境、以及團隊規模。

## 踩雷集錦

### 雷 1：把「有 SDLC」誤認為「一定要嚴格序列」

**錯誤直覺：** 「我們有需求 phase 和設計 phase，那就應該先把需求全部寫完，再開始設計。」

**正確認識：** SDLC 的 phase 是邏輯分類，不是時間上不可重疊的閘門。你可以在設計初稿做完後，發現有些需求說不清楚，回頭去補——這不是流程崩潰，這是正常的。Royce 自己就這樣說。

### 雷 2：需求文件越厚越安全

**錯誤直覺：** 「需求寫得越詳細，後面的工作越安全。反正多費心在前期，後期就不用改。」

**正確認識：** 需求文件的效用有邊際遞減。當需求文件厚到需要幾個月才能讀完，它本身就成了一種風險——因為這幾個月裡業務環境可能已經改變。而且更多的文字帶來更多的解讀歧異。有效的需求文件是「剛好足夠清楚」，不是「越多越好」。

### 雷 3：「敏捷了，就不需要規格」

**錯誤直覺：** 「我們跑 Scrum，每兩週一個 sprint，所以不需要寫什麼規格，用戶故事就夠了。」

**正確認識：** 敏捷重視「可工作的軟體重於詳盡的文件」，但這個「詳盡」指的是不必要的文件——不是指所有文件。當 AI 代理進入流程、當團隊規模成長、當你需要追蹤一個功能的設計意圖時，沒有規格的代價就會浮現。敏捷的精神是「用足夠的規格，快速驗證」，不是「不要規格」。

### 雷 4：把 Standish CHAOS「失敗率」當精確數據引用

**錯誤直覺：** 「根據 Standish Group 研究，X% 的 IT 專案失敗，其中最主要的原因是需求問題。」

**正確認識：** CHAOS 報告的方法論受到學術界批評：成功/失敗的定義只看「是否在估計的時間、成本、功能範圍內完成」，且原始數據非公開。Eveleens & Verhoef（IEEE Software 2010）認為這樣的數字是「無意義的平均」。你可以說「實務經驗和多項研究都指向需求問題是重大風險來源」，但不要把特定百分比當成硬事實引用。

### 雷 5：把「意外（Accident）」誤解為「不重要」

**錯誤直覺：** 「Brooks 說實作是 Accident（意外），所以寫程式碼不重要？」

**正確認識：** Brooks 說的「Accident」不是「不重要的東西」，而是「非本質的、可被工具改善的、不是軟體複雜性根本來源的」。寫程式當然重要，只是這個重要性是 operational（操作層面）而非 essential（本質層面）。AI 工具讓實作的意外成本降低，這不代表工程師不再需要思考——恰恰相反，省掉的打字時間應該要投資在需求與設計上。

## 進階延伸

### SDLC 的多種變體

標準 SDLC 有很多變形，每種都在「phase 之間的嚴格程度」上做了不同取捨：

- **Spiral Model（Barry Boehm, 1988）**：在每個 phase 前先做風險評估，高風險的地方就多做一圈。不是「快」，而是「風險導向的迭代」。
- **V-Model**：把測試 phase 對應到每個開發 phase——系統需求有驗收測試、軟體設計有整合測試、詳細設計有單元測試。強調可追溯性。常見於醫療與汽車軟體（IEC 61508、ISO 26262）。
- **Continuous Delivery（CD）**：把「部署」從一個 phase 變成一個持續的能力。任何時刻 main branch 都可以部署。需要極強的自動化測試覆蓋率支撐。

### Brooks 的「本質 vs 意外」之後

Brooks 1986 年說「沒有銀彈（No Silver Bullet）」——沒有任何工具或方法論能讓軟體生產力在十年內提升一個數量級，因為本質困難無法被「工具化」掉。

這個預測在 AI 時代受到了挑戰：如果 LLM 能把「意外」部分的成本壓到接近零，那麼整體生產力的成長天花板就會更接近「本質」部分能改善多少。这是規格驅動開發這整門課程的核心假設——也是我們需要帶著批判眼光去審視的。

### 形式化方法（Formal Methods）

在「嚴格程度」這個光譜的最右端，是形式化規格語言（Formal Specification Language）：TLA+、Alloy、Z notation 等。這些工具讓你用數學語言描述系統行為，並自動驗證規格的一致性，甚至做模型驗證（model checking）。

Amazon Web Services 的工程師用 TLA+ 驗證過 DynamoDB、S3 等服務的關鍵協議。這不是學術玩具，但學習曲線陡峭，適用於對正確性要求極高的核心協議，不是所有軟體開發的預設選項。

[Ch 13 嚴謹的另一端：形式化規格 TLA+ / Alloy](./13-formal-specs-tla-alloy.md) 會詳細介紹。

## 動手練習

不需要寫程式碼，用紙筆或任何文字編輯器完成。

**情境：** 一個電商平台要新增「定期訂閱配送」功能——使用者可以設定每週/每月自動下單特定商品。

1. **列出這個功能的五個 phase 產物各會是什麼。** 不要太詳細，但要具體：
   - 需求 phase：你要在 SRS 裡寫什麼標題？
   - 設計 phase：你需要哪些新的元件或新的資料欄位？
   - 實作 phase：大概有哪些程式模組要新增或修改？
   - 測試 phase：至少列出三個驗收條件。
   - 維運 phase：上線後你想監控哪個指標？

2. **找出 phase 之間最容易產生資訊缺口的地方。** 例如：需求文件裡的某個細節在設計 phase 會被誰假設掉、如果假設錯了會造成什麼問題？

3. **決定這個功能適合用哪種 SDLC 節奏？** 嚴格序列還是短迭代？你的理由是什麼？

這個練習的答案沒有對錯，重點是讓你把「管線」這個概念跟具體場景連起來。

## 本章重點整理

- SDLC 是對「個人技藝無法 scale」這個問題的直接回應：把隱性知識轉成可傳遞、可驗證的文件。
- 標準五 phase：需求（WHAT+WHY）→ 設計（HOW）→ 實作（用什麼語言/框架表達）→ 測試（做的和說好的一樣嗎）→ 維運（上線後的回饋）。
- 「Phase 的邏輯順序」不等於「Phase 之間不能回頭」。Royce 本人就說要至少跑兩遍。
- Brooks 的「本質 vs 意外」框架：需求與設計是本質困難，寫程式碼是意外困難。工具只能改善意外困難；AI 工具讓意外困難大幅降低，讓本質困難的比重更高。
- Boehm 的變更成本方向是對的（越晚改越貴），但「1:100」的精確倍數是未能查證的數字。
- Standish CHAOS 報告的百分比是方向性參考，不是精確數據，方法論受學術界批評。
- 敏捷宣言說的「可工作的軟體重於詳盡的文件」，不是「不需要任何文件」。
