# Ch 11 — System prompt 設計

> **目標**：學會寫 agent 的 system prompt。讀完你能說出 system prompt 該放什麼、不該放什麼、「適當高度（altitude）」是什麼意思、怎麼結構化它、怎麼用它引導工具使用與行為邊界，以及為什麼把它寫穩定對成本（快取）有直接好處。

> **環境**：概念為主，範例以 Anthropic Messages API 的 `system=` 參數為準（Ch 6 介紹過）。

## 為什麼 system prompt 是高槓桿的一塊

回到 Ch 10 的預算表：system prompt 是 context 裡的「固定成分」——它**每一輪都被送進 context**。這有兩個含義：第一，它影響 agent 的**每一個**決策（不像某則使用者訊息只影響當下那輪），所以它對行為的槓桿極高；第二，它每輪都佔 context 空間，長度與穩定性直接牽動成本（用了快取的話，穩定的它還能走便宜的快取價——見後面「穩定性 = 省錢」一節）。

換句話說，system prompt 是你對 agent **影響力最集中、最持久**的一個位置。一個好的 system prompt 能讓平庸的模型表現穩定；一個爛的——太囉嗦、太死板、或自相矛盾——會讓再強的模型行為飄忽。這章教你怎麼把這塊高槓桿的地方寫好。

## 先建立直覺：system prompt 是「職位說明書」，不是「腳本」

一個常見的錯誤心智模型：把 system prompt 當成「把所有可能情況的應對都寫死進去的腳本」。於是它越寫越長，塞滿 `如果使用者問 X 就回 Y、如果遇到 Z 就做 W` 的條款，最後變成一份兩千行、自相矛盾、沒人敢動的天書。

正確的心智模型是**職位說明書（job description）**。你雇一個能幹的員工，不會給他一本窮舉所有情況的腳本——你給他的是：你的角色是什麼、你負責什麼、你有哪些工具和權限、公司的行事準則是什麼、什麼事情要先請示。然後**信任他的判斷**去處理具體情況。

```
   ❌ 腳本（brittle script）              ✅ 職位說明書（job description）
   ┌──────────────────────────┐         ┌──────────────────────────┐
   │ if 問天氣: 用 get_weather  │         │ 你是客服助理。            │
   │ if 問訂單: 查 DB 然後...    │         │ 你能查訂單、查物流、退款。  │
   │ if 抱怨: 先道歉再...        │   →     │ 退款超過 1000 元要先請示。 │
   │ if 問退款 且 金額>1000:...  │         │ 語氣專業同理。            │
   │ ... (兩千行) ...           │         │ 不確定就問，別亂猜。       │
   └──────────────────────────┘         └──────────────────────────┘
      窮舉、易碎、難維護                     原則、有彈性、好維護
```

這個分野對應一個關鍵概念：**altitude（高度）**。

## 一、altitude：寫在對的「高度」

system prompt 寫得好不好，很大程度取決於它的「高度」對不對——也就是它在「太具體」和「太抽象」之間落在哪。

```
   太高（太抽象、太空泛）
   「請做個好助理，盡力幫忙。」
        ▲   模型不知道你到底要它幹嘛、有哪些工具、邊界在哪
        │
   ─────┼───── 剛剛好的高度 ──────────────────────────
        │   給出角色、能力、邊界、準則，但留判斷空間給模型
        │
        ▼
   太低（太具體、寫死成腳本）
   「步驟1: 呼叫 get_weather('Taipei')。步驟2: 如果回傳含『晴』就說...」
        模型沒有發揮空間、稍微偏離劇本就崩、難維護
```

- **太高**：模型缺乏足夠資訊去做對的決策，行為飄忽。
- **太低**：你把模型當成一個只會照本宣科的執行器，抹殺了它的判斷力——而判斷力正是你用 agent（而非寫死的 workflow，Ch 1）的理由。寫死的腳本還特別脆：稍微遇到沒寫到的情況就崩，而且每加一個情況就要改一次 prompt，難以維護。

**剛剛好的高度**：給足夠的脈絡讓模型能自己做出好決策，但不替它把每個具體動作都決定掉。這呼應 Ch 1——你選擇用 agent，就是因為任務無法被窮舉成固定腳本；那 system prompt 也不該試圖把它窮舉。

> 判準小技巧：如果你發現自己在 system prompt 裡寫 `if... then...` 的具體分支，停下來問「這真的需要寫死嗎，還是給模型原則它自己會判斷？」。大部分時候，把分支換成原則，prompt 更短、agent 更穩。

## 二、一個 agent system prompt 該有的幾塊

不是硬性模板，但一個結構良好的 agent system prompt 通常涵蓋這幾塊。用清楚的標題分段，模型（和維護它的人）都更好讀：

```
## 角色（你是誰）
你是一個 <領域> 助理，負責 <核心職責>。

## 能力（你能做什麼）
你可以使用以下工具：<高層次描述有哪些工具、各自大概用途>。
（細節在工具 schema 裡，這裡給全局感，別重抄 schema——見下方踩雷）

## 邊界與準則（你該怎麼行事 / 什麼不能做）
- 需要精確計算時一定用 calculate 工具，不要心算。
- 涉及金額超過 X 的操作，先向使用者確認再執行。
- 不確定使用者意圖時，提問澄清，不要假設。

## 輸出風格（你怎麼回應）
- 簡潔、專業。
- 程式碼用 markdown code block。
- 不要在每次回應開頭都重複自我介紹。
```

逐塊的要點：

- **角色**：一句話定位。它幫模型「進入狀態」，也約束範圍（一個「退稅助理」不會隨便聊股票）。
- **能力**：給工具的**全局視野**——有哪些工具、整體能做到什麼。注意是「全局感」，不是把每個工具的參數細節重寫一遍（那在 schema 裡，Ch 5、Ch 19）。
- **邊界與準則**：這是 policy（Ch 3）在 prompt 層的展現。什麼要先問人、什麼絕對不做、什麼情況用哪類工具。**用原則寫，不要用窮舉的 if/then**。
- **輸出風格**：語氣、格式、長度傾向。這塊最容易被忽略，但對使用者體驗影響很大。

## 三、用 system prompt 引導工具使用

Ch 5 講過工具 `description` 影響模型用不用工具。system prompt 是另一個槓桿，它管的是**跨工具的行為準則**：

```
## 工具使用準則
- 需要當前資訊（時間、即時數據）或精確計算時，務必使用工具，不要憑記憶或心算回答。
- 一次需要多個獨立資訊時，可以平行呼叫多個工具。
- 工具回傳錯誤時，閱讀錯誤訊息、調整後重試；連續失敗多次就誠實告訴使用者，不要無限重試。
```

`description`（Ch 5）說的是「這個工具是什麼」，system prompt 說的是「你**整體上**該怎麼運用你的工具箱」。兩者分工：個別工具的細節在 schema，跨工具的策略在 system prompt。一個常見且有效的準則是上面第一條——明確告訴模型「該用工具時別偷懶用記憶」，因為模型有時會自信地用過時或編造的資訊回答，而不去用你給的工具。

## 四、穩定性 = 省錢：system prompt 與快取

這裡把 Ch 10 的成本意識接上來。prompt caching（Ch 17 詳談）的運作前提是「**前綴不變**」——當你連續多次請求的開頭部分一字不差地相同，那部分可以走快取、用便宜很多的價格計算。要注意 Anthropic 計算這個「前綴」的順序是 **`tools` → `system` → `messages`**：工具定義在最前、接著 system prompt、最後才是對話歷史。所以工具定義和 system prompt（每輪都一樣）天然落在前綴的最前段，是快取的頭號受益者。

這給 system prompt 設計一個**成本層面的準則**：

- **把不變的東西放前面、變動的東西放後面**。工具定義與 system prompt 天然是穩定前綴，盡量別動它們。
- **小心把會變的東西塞進 system prompt**。最常見的錯誤是把「目前時間」「使用者名字」「今天日期」這種每次都不同的值寫進 system prompt 的本體——這會讓「包含那個值的前綴」每次都不一樣，從那個點之後的快取就**命中不了**，白白浪費。比較精確的說法是：失效的是「含動態值的那一段及其之後」，不是玄學上「整個快取永遠壞掉」。所以解法有兩個層次：(a) 最簡單——這類動態資訊根本別放 system prompt，改放 messages 裡（或用工具取得）；(b) 進階——若真的要放，把 system 拆成多個 block，把 `cache_control` 標在「動態值之前的穩定段」，讓穩定前綴照樣被快取（Ch 17 會示範）。

```
   ✅ system prompt 穩定 → 快取命中 → 省錢
   system: "你是助理...（固定）"   ← 每輪一字不差，走快取

   ❌ system prompt 本體混入動態值 → 從那個值之後的快取落空
   system: "你是助理，現在時間 14:32:07..."  ← 那個時間每輪都變，前綴被破壞
```

記住這個原則，Ch 17 學快取細節時你會發現「system prompt 寫穩定」是省錢的第一步、而且幾乎不花力氣。

## 五、迭代：system prompt 是調出來的，不是寫一次就完

別期待第一版 system prompt 就完美。實務上它是**觀察 → 調整**疊代出來的：

1. 先寫一個合理的初版（角色、能力、邊界、風格）。
2. 跑真實任務，**觀察 agent 哪裡行為不對**：該用工具沒用？語氣不對？越界了？答非所問？
3. 針對觀察到的具體問題，在 system prompt 加一條**原則**（不是加一條 if/then 腳本）。
4. 重複。

關鍵心法：**每一條準則都應該是為了修正一個你真實觀察到的問題而存在**，不是憑空想像「可能會出錯」就先寫一堆防禦條款。後者會讓 system prompt 迅速膨脹成沒人懂的天書。如果你不記得某條準則當初是為了修什麼，它可能該刪。這跟 Ch 34 的 eval 直接相關——你需要能衡量「改了 prompt 之後到底變好還變壞」。

## 失敗示範：兩種典型的爛 system prompt

**爛法一：太空泛（altitude 太高）**

```
你是一個 AI 助理。請盡力幫助使用者，回答要正確、有用、友善。
```

問題：模型不知道它的角色範圍、有哪些工具、什麼能做什麼不能做。結果是行為飄忽——同一個問題不同時候給不同風格的答案，該用工具時不用，該拒絕時亂答。**它沒給模型任何可以據以判斷的脈絡。**

**爛法二：寫死成腳本（altitude 太低）+ 塞動態值**

```
你是客服。現在時間是 2026-06-05 14:32:07，當前使用者是 VIP 等級 3。
規則：
1. 如果使用者說「你好」，回「您好，很高興為您服務」。
2. 如果使用者問訂單，先呼叫 get_order，如果 status 是 "shipped" 就說「已出貨」，
   如果是 "pending" 就說「處理中」，如果是 "cancelled" 就說...
3. 如果使用者問退款且金額 < 500，直接 approve_refund，如果 500-1000，說...
（接下來 1500 行）
```

三個問題疊在一起：(1) **altitude 太低**——把模型當成 switch-case 執行器，遇到沒寫到的情況就崩；(2) **塞了動態值**（時間、使用者等級）進 system prompt，快取永遠失效、白燒錢；(3) **不可維護**——1500 行的條款沒人敢改，改一條怕影響另一條。

**好的版本**：把動態值（時間、使用者資訊）移出去（放 messages 或用工具取得）、把窮舉的條款換成原則（「退款超過 1000 元先請示」一句話取代十條 if/then）、保持結構清楚。短、穩、好維護。

## 踩雷集錦

1. **altitude 太低、寫死成腳本**：用窮舉的 if/then 把模型當執行器，抹殺判斷力又脆弱難維護。改用原則。看到自己在寫具體分支就警覺。
2. **altitude 太高、空泛無物**：「請當個好助理」給不了模型任何判斷依據，行為飄忽。要給角色、能力、邊界、風格。
3. **把動態值塞進 system prompt 本體**：時間、使用者名、日期這種每次都變的東西混進 system prompt，會破壞快取前綴、讓「含該值之後」的部分每次 miss、白燒錢。最簡單的解法是動態資訊放 messages 或用工具取；非放不可就用分段 + breakpoint（Ch 17）。
4. **在 system prompt 重抄工具 schema 細節**：工具的參數細節屬於 schema（Ch 5、Ch 19）。在 system prompt 重寫一遍既浪費 token 又容易跟 schema 不同步。system prompt 給的是工具的「全局感」與「跨工具策略」。
5. **一次想到就加一堆防禦條款**：沒有真實觀察到問題就先寫一堆「以防萬一」的規則，prompt 迅速膨脹成天書。每條準則都該對應一個你真實遇到的問題。
6. **把（初始）system prompt 當成 messages 的第一則**：Ch 6 講過，初始的 system prompt 用獨立的 `system=` 參數，不要把它偽裝成 messages 的第一則 user/assistant。（補充一個較新的例外：在 Opus 4.8+ 上，你可以在對話**中途**用 `{"role": "system"}` 的訊息插入額外的 system 指令，這是為了在不破壞既有快取前綴的前提下追加指示的進階用法——但「整個 agent 的主 system prompt 放 `system=`」這個基本原則不變。別把這個進階例外當成「可以隨便把 system 塞進 messages」。）

## 進階：再往深一層

- **多段 system + 選擇性快取**：`system=` 可以是一個 block 陣列，而不只是一個字串。這讓你能把「永遠不變的核心」和「偶爾變動的部分」分成不同 block，並對穩定的部分標記快取（`cache_control`）。Ch 17 會展示怎麼用這個結構把快取效益最大化。現在知道「system 可以結構化、可以分段快取」即可。
- **system prompt 與 agent 的「人格一致性」**：跨多輪對話，使用者會對 agent 形成一個「它是怎樣的」的預期。system prompt 裡的風格與準則若前後一致、夠具體，agent 的人格就穩定；若太空泛，使用者會覺得它「時好時壞、像不同的人」。一致性本身就是體驗品質。
- **別把安全完全寄望在 system prompt**：你可以在 system prompt 寫「不要執行危險操作」，但**這不是可靠的安全邊界**——夠強的 prompt injection（Ch 36）可能繞過它。真正的安全要靠 harness 層的 permission（Ch 25）與 sandbox（Ch 22）這種「程式碼層級」的硬控制，system prompt 的準則只是第一道、可被突破的軟防線。別把 policy 全押在文字上。

## 動手練習

1. 拿你練習 A 的 mini-agent，把它那句陽春的 system prompt（「你是一個簡潔、誠實的命令列助理」）擴寫成有「角色 / 能力 / 工具使用準則 / 輸出風格」四塊的版本。跑跑看行為有沒有更穩定（例如該用 `calculate` 時更不會偷懶心算）。
2. 故意寫一個「太低 altitude」的版本——把「該用工具時用工具」改寫成具體的 `if 使用者問數學就呼叫 calculate`，然後問一個它沒預料到的問法，觀察它是否變脆。
3. 故意把「現在時間：<某時間>」塞進 system prompt，連續呼叫幾次、印出 `usage` 的 `cache_read_input_tokens`，對比把時間拿掉後的快取命中差異（這題需要先瞄一眼 Ch 17 的快取設定，當作預習）。
4. 把你的 system prompt 拿給另一個人讀，問他「這個 agent 能做什麼、不能做什麼、遇到 X 會怎樣」。如果他答不出來，代表你的 prompt altitude 太高或結構不清。

## 本章重點整理

- system prompt 是 context 的固定成分、每輪都送、影響每個決策——是影響力最集中的高槓桿位置（穩定的話還能走便宜快取價）。
- 心智模型是「職位說明書」不是「腳本」：給角色、能力、邊界、風格與原則，信任模型的判斷，別窮舉 if/then。
- altitude 要剛好：太高（空泛）模型無所依據、太低（寫死）抹殺判斷又脆弱難維護。
- 用清楚分段（角色 / 能力 / 邊界準則 / 輸出風格）；工具細節留在 schema，system prompt 給全局感與跨工具策略。
- 把 system prompt 寫**穩定**（不塞動態值）是省錢第一步——穩定前綴才能被 prompt cache 命中。
- system prompt 是迭代調出來的；每條準則都該對應一個真實觀察到的問題，別堆防禦條款。
- 安全別全押在 system prompt 上，真正的硬控制在 harness 層（permission / sandbox）。
