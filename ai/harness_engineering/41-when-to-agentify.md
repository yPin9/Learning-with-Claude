# Ch 41 — 該不該上 agent：任務選型與導入決策

> **目標**：學會在一個真實任務面前做出「純人工 / workflow / agent」的選型判斷，能用一套可操作的評分維度和損益模型說清楚「為什麼這個任務值得（或不值得）交給 agent」，而不是憑感覺或趕流行。

> **環境**：本章的評分工具用 Python 3.11，不依賴任何外部套件，複製就能跑。其餘是設計方法，與語言無關。

## 為什麼需要這個？

你已經會刻 harness 了（Part 1–6）。但「會刻」和「該刻」是兩件事。生產上 agent 專案失敗，最常見的原因**不是技術做爛了**，而是**一開始就選錯了任務**——把一個本該用三行 `if/else` 或一條固定 pipeline 解決的事，包成一個動態決策的 agent，結果不可控、貴、難 debug，最後被團隊棄用。

[Ch 1](./01-what-is-agent-harness.md) 的「workflow 還是 agent？」一節給了判準的**骨架**：控制結構由誰擁有。這章把它變成**可操作的選型流程**——面對手上這個具體任務，你要怎麼一步步判斷該走哪條路、值不值得投資、上了之後拿什麼指標證明它有用。這是 harness 工程師的「第一個本事」，比迴圈怎麼寫更早用到。

## 先建立直覺：你面前永遠有三條路，不是兩條

很多人一聽到「自動化」就直接跳到「要不要做 agent」。錯。任何一個重複的工作，你其實有三條路可選，成本與可控性遞增：

```
       可控性高、便宜              可控性低、貴
       好 debug                   難 debug
  ┌──────────────┬──────────────────┬─────────────────────┐
  │  ① 純人工      │  ② workflow       │  ③ agent             │
  │  （不自動化）   │  （流程寫死）       │  （模型開車）          │
  ├──────────────┼──────────────────┼─────────────────────┤
  │ 量小、不重複、 │ 步驟固定、能事先   │ 步驟開放、事先說不准  │
  │ 一次性、或     │ 列出來；模型只在   │ 「會經過哪些階段」；   │
  │ 判斷貴到不值   │ 某幾格填空        │ 下一步由模型當場決定  │
  │ 得自動化      │ （分類/抽取/改寫） │                     │
  └──────────────┴──────────────────┴─────────────────────┘
        ←─────── 能往左解決就別往右，往右只在「真的需要」時 ───────→
```

第三條路（agent）是這門課教你刻的東西，但它是**成本與風險最高的一條**。導入決策的核心問題不是「agent 能不能做這個任務」——強模型幾乎什麼都「能試試看」——而是**「這個任務值不值得用 agent 這條最貴的路來做」**。

> 如果你對「workflow 與 agent 的控制權歸屬」這個基本區分還不熟，先回看 [Ch 1 — 什麼是 agent harness？](./01-what-is-agent-harness.md) 的「對比：workflow 還是 agent？」一節。本章假設你已經有那個區分。

## 第一關：這個任務能不能往左推？

導入決策的第一步**不是**評估 agent，而是**盡力把任務往左邊推**。問三個問題：

1. **這值得自動化嗎？** 一個月做兩次、每次五分鐘的事，自動化的開發與維護成本可能永遠賺不回來。留給人。
2. **步驟能事先列出來嗎？** 如果你能畫出一張固定的流程圖（「先 A，若 X 則 B 否則 C」），那就是 workflow。寫死的 pipeline 更可控、更便宜、更好測。即使中間某一格要靠 LLM 判斷（分類、抽取、改寫），只要**整體骨架是你定義且有界的**，它仍然是 workflow，不是 agent。
3. **真正開放的部分有多大？** 很多任務只有**一小塊**是開放的，其餘都是固定流程。這時正解往往是 **workflow 為主、在開放的那一格嵌一個小 agent**，而不是把整件事都做成 agent。

只有當答案是「值得自動化、而且步驟開放到連大概會經過哪些階段都說不準」時，才進入下一關：評估這個 agent 任務的**適配度**。

## 第二關：agent 任務適配度的五個維度

假設任務確實開放、確實值得自動化。它適不適合交給 agent，看五個維度。這五個維度不是「有就好」，而是**每一個都會直接決定你的 harness 好不好做、敢不敢放手**：

### 維度一：可驗證性（成功有沒有客觀訊號？）

agent 會自己決定「做完了沒」（`end_turn` 只代表模型**自認為**講完了，不代表任務**真的**完成——這點 [Ch 7](./07-stop-conditions-turns.md) 講過）。如果這個任務的「做對了沒」有**客觀、可程式化檢查**的訊號（測試通過、schema 驗證過、數值對上、檔案存在且格式正確），你就能寫 eval（[Ch 34](./34-eval.md)）、能設自動驗收、能在 CI 擋回歸。如果「做得好不好」純粹是主觀品味、只有資深人類看得出來，那 agent 的輸出你**驗不了**，放手的風險就高。

- **高可驗證**：「修好這個 bug」（測試會告訴你）、「把這份資料轉成這個 schema」（驗 schema）。
- **低可驗證**：「寫一段有品牌調性的行銷文案」（對錯沒有客觀訊號，只能人看）。

### 維度二：可逆性與 blast radius（做錯了，能收拾嗎？）

agent 會做出你沒預期的動作。問：**最壞情況下它能造成多大破壞、收不收得回來？**

- **可逆／blast radius 小**：在一個臨時工作目錄裡改檔（隨時 `git checkout` 還原）、產生一份草稿（人覆核後才送出）。
- **不可逆／blast radius 大**：直接對 production DB 下 `DELETE`、發真錢的退款、寄信給客戶、改線上設定。

這個維度不是「能不能上 agent」的開關，而是決定你要在 agent 外面包多厚的**安全層**：權限 gate（[Ch 25](./25-permission-model.md)）、`safe_path`、人工核可、預算上限、可恢復的 checkpoint（[Ch 39](./39-determinism-resume.md)）。blast radius 越大，自主程度就要壓越低——這是下一章「信任階梯」的主軸。

### 維度三：決策的工具可達性（agent 缺手缺腳嗎？）

agent 靠工具感知和改變世界。每個**要由 agent 自主執行**的動作，都得有工具可達（[Ch 18–24](./18-tool-schema-design.md)）；不可工具化的步驟，要留給人或外層 workflow。如果任務裡有一步是「打電話跟供應商喬價格」或「去倉庫實地點貨」——沒有工具能做到的事，agent 也做不到。導入前先把任務拆成動作，逐一問「這步有 API/工具能做嗎」。缺關鍵工具的任務，要嘛先補工具、要嘛這步留給人（變成半自動）。

### 維度四：容錯度（偶爾出錯，代價多大？）

LLM 不是每次都對。同一個任務跑十次，可能八次對、兩次跑歪——這是統計性質，不是 bug（所以 eval 要看**通過率**而非單次，[Ch 34](./34-eval.md)）。問：**這個任務能容忍「大部分對、偶爾錯」嗎？**

- **高容錯**：草稿生成、初步分類、給人看的建議——錯了人會抓。
- **低容錯**：金融交易、醫療劑量、法律文件定稿——一次錯就是事故。

低容錯的任務不是不能上 agent，而是**必須**配可靠的驗證關卡和人工覆核，把「偶爾錯」擋在出口之前；驗證關卡本身做不出來的話（見維度一），就別放手。

### 維度五：頻率與一致性回報（值得攤提開發成本嗎？）

agent harness 的開發、eval、observability、維護都是真實成本。任務**頻率越高、越重複**，這些固定成本攤提下來才划算。一個月跑兩次的任務，再開放也通常不值得做成 agent——留給人，或做個半自動 workflow 就好。這一維度把「技術上適合」拉回「經濟上值得」。

## 一個可跑的「任務適配度評分」工具

把五個維度變成一張可填的計分卡。**這不是要給你一個精確的「分數 > X 就上」的神諭**——它的價值是**逼你把每個維度想過一遍、把假設攤開來、讓團隊用同一套語言討論**。分數是討論的起點，不是結論。

```python
# agentify_score.py — 任務適配度計分卡。複製即可跑（純標準庫）。
from dataclasses import dataclass

@dataclass
class TaskAssessment:
    name: str
    verifiability: int      # 1=純主觀無法程式化驗 ... 5=測試/schema 客觀可驗
    reversibility: int      # 1=不可逆且 blast radius 大 ... 5=完全可逆、影響侷限
    tool_coverage: int      # 1=關鍵步驟沒工具能做 ... 5=每步都有現成工具/API
    fault_tolerance: int    # 1=一次錯就是事故 ... 5=偶爾錯有人兜底、代價低
    frequency: int          # 1=一次性/極少 ... 5=高頻重複、攤提得起開發成本

    def __post_init__(self):
        # 計分卡自己先守門：分數必須是 1–5，否則總分與 verdict 都會是無意義的訊號。
        for f in ("verifiability", "reversibility", "tool_coverage",
                  "fault_tolerance", "frequency"):
            v = getattr(self, f)
            if not (isinstance(v, int) and 1 <= v <= 5):
                raise ValueError(f"{f} 必須是 1–5 的整數，收到 {v!r}")

    def gate_flags(self) -> list[str]:
        # 「硬門檻」：某些維度太低，不是扣分，是直接擋下或強制加安全層。
        flags = []
        if self.verifiability <= 2:
            flags.append("驗不了：成功沒有客觀訊號，agent 自報『做完了』你無從查證——"
                         "要嘛先想出可程式化的驗收，要嘛這任務別全自動。")
        if self.reversibility <= 2 and self.fault_tolerance <= 2:
            flags.append("不可逆 × 低容錯：最危險的組合。就算上，也只能停在『agent 產出、"
                         "人核可後才執行』，絕不能讓它直接動手（見 Ch 42 信任階梯）。")
        if self.tool_coverage <= 2:
            flags.append("缺手腳：關鍵步驟沒有工具能做，agent 到那步就卡住——"
                         "先補工具，或把那步留給人做成半自動。")
        return flags

    def verdict(self) -> str:
        score = (self.verifiability + self.reversibility + self.tool_coverage
                 + self.fault_tolerance + self.frequency)
        flags = self.gate_flags()
        lines = [f"=== {self.name} ===", f"五維總分：{score}/25"]
        if flags:
            lines.append("⚠️ 硬門檻警示（先解決這些，分數才有意義）：")
            lines += [f"  - {f}" for f in flags]
        # 硬門檻優先：有 flag 時，結論由門檻主導，不讓總分分類蓋過去。
        # 分數只給「往哪個方向想」的粗略訊號，不是自動決策。
        if flags:
            lines.append("→ 結論：先解掉上面的硬門檻。在那之前別讓 agent 自主執行——"
                         "最多到『agent 產出、人核可後才生效』，或把危險動作加安全層（Ch 42）。")
        elif score >= 20:
            lines.append("→ 傾向：適合 agent。仍要從低自主層級起步（Ch 42）。")
        elif score >= 14:
            lines.append("→ 傾向：邊緣。考慮 workflow 為主、只在開放的那一格嵌小 agent。")
        else:
            lines.append("→ 傾向：別上 agent。純人工或固定 workflow 更划算可控。")
        return "\n".join(lines)


if __name__ == "__main__":
    # 範例一：適合——「在隔離工作目錄裡修好失敗的測試」
    fix_tests = TaskAssessment("修好失敗的單元測試", verifiability=5, reversibility=5,
                               tool_coverage=5, fault_tolerance=4, frequency=4)
    print(fix_tests.verdict())
    print()
    # 範例二：危險——「自動處理客戶退款」
    refund = TaskAssessment("自動審核並執行客戶退款", verifiability=3, reversibility=1,
                            tool_coverage=4, fault_tolerance=1, frequency=5)
    print(refund.verdict())
```

跑起來：

```
=== 修好失敗的單元測試 ===
五維總分：23/25
→ 傾向：適合 agent。仍要從低自主層級起步（Ch 42）。

=== 自動審核並執行客戶退款 ===
五維總分：14/25
⚠️ 硬門檻警示（先解決這些，分數才有意義）：
  - 不可逆 × 低容錯：最危險的組合。就算上，也只能停在『agent 產出、人核可後才執行』，絕不能讓它直接動手（見 Ch 42 信任階梯）。
→ 結論：先解掉上面的硬門檻。在那之前別讓 agent 自主執行——最多到『agent 產出、人核可後才生效』，或把危險動作加安全層（Ch 42）。
```

注意第二個例子：雖然總分有 14，但 `gate_flags` 抓出了**不可逆 × 低容錯**這個硬門檻——所以 `verdict()` **不讓總分分類主導結論**，一旦有 flag 就直接把結論導向「先解門檻、在那之前別放手」。這正是「硬門檻比總分重要」的程式落實。**退款這種任務不是「不能用 agent」，而是「agent 只能負責判斷與草擬，執行那一步（真的把錢退出去）必須是人按下確認、或一條與 agent 解耦的、有金額上限與審計的固定流程」。** 計分卡的真正用途，是把這種「哪裡可以放手、哪裡絕對不行」攤在桌上講清楚。

## ROI：技術上適合，經濟上也得划算

選型過了，還有一關：**值不值得**。agent 不是免費的，三類成本要一起算：

```
總成本 = 建置成本 + 每次執行成本 + 持續維護成本
         (一次性)    (隨次數線性)     (隨時間，常被低估)
```

- **建置成本**：寫 harness、設計工具與 schema、寫 eval、接 observability、設權限與安全層。即使大量沿用前面練習的成果，整合與調校仍是真實工時。
- **每次執行成本**：token（[Ch 37](./37-cost-latency-optimization.md)）、延遲、以及**人工覆核的時間**——這一項最容易漏算。如果每次 agent 跑完都要一個資深工程師花十分鐘檢查它有沒有亂來，那「自動化」省下的工，有一大半被覆核吃掉了。
- **持續維護成本**：模型換版要重測（[Ch 39](./39-determinism-resume.md) 講過行為會飄）、工具背後的 API 變更要跟、eval fixture 會過期要重錄、prompt 要隨真實失敗案例迭代。agent 系統**不是上線就結案**，它是要持續餵養的。

把它跟基準線比：**現在用人工（或現有 workflow）做這件事，一年花多少？** agent 方案的一年總成本若沒有明顯低於這個基準、或沒有換來人工做不到的價值（速度、規模、24 小時可用），那這個導入在經濟上就不成立——技術上再漂亮也一樣。

> 認識論誠實：上面的成本沒有給你具體數字或公式，因為它**高度依賴你的任務、模型定價、團隊薪資**——脫離任務、流程、覆核成本與模型定價的通用「省 X%」比例不可信。這裡能給的是**該把哪幾項算進去**，數字得你拿自己的場景填。

## 對比與取捨

| 路線 | 何時選它 | 可控性 | 成本 | 主要風險 |
|---|---|---|---|---|
| **純人工** | 量小、一次性、判斷貴到無法工具化、低頻 | 最高 | 人力，但無建置/維護 | 不 scale、慢 |
| **Workflow** | 步驟能事先列出、控制骨架有界 | 高 | 中（一次性開發為主） | 流程外的情況處理不了 |
| **Agent** | 步驟開放、事先說不準、且五維適配、ROI 成立 | 低 | 高（建置＋執行＋維護） | 不可控、要完整安全與 eval 才敢放手 |
| **混合（workflow + 嵌入式 agent）** | 大部分固定、只有一小塊開放 | 中高 | 中 | 接縫設計：開放那格的輸出要能被外層流程驗收 |

最後一列**混合**常常是被忽略的最佳解。不要把「上 agent」當成全有全無——讓固定的歸固定、開放的歸 agent，往往比「整件事都 agent」更可控也更便宜。

## 踩雷集錦

1. **「強模型什麼都能做，所以什麼都該交給它」**：模型「能試」不等於這任務「該用 agent」。選型問的是值不值得用最貴最難控的路，不是模型能力上限。把這兩個問題混為一談，是導入失敗的頭號原因。
2. **「先把 agent 做出來，需求之後再想」**：反了。**先確認任務適配、ROI 成立，再動工**。沒有客觀驗收訊號（維度一）就開做，你會做出一個「看起來會動、但沒人能證明它做對了」的東西，最後沒人敢用。
3. **「總分高就上、總分低就不上」**：把計分卡當神諭。硬門檻（不可逆 × 低容錯、缺關鍵工具、驗不了）比總分重要——一個總分 22 但「直接動 production DB 且驗不了」的任務，比總分 15 但完全可逆、可驗的任務危險得多。分數是討論起點，不是自動決策。
4. **「自動化一定省錢」**：漏算了每次的**人工覆核成本**和持續**維護成本**。低容錯任務若每次都要人覆核，省下的工會被覆核吃掉大半；模型換版、API 變更、fixture 過期的維護是長期負擔。算 ROI 要把這些放進去。
5. **「要嘛全自動，要嘛純人工」**：忽略了混合路線和「自主程度是一條光譜」（Ch 1 進階區、下一章信任階梯）。最務實的導入往往是「workflow 為主、開放處嵌小 agent」或「agent 產出、人核可執行」，而不是一步到位全自主。

## 進階：再往深一層

- **從 workflow 漸進演化成 agent**：很多成功的導入不是一開始就是 agent，而是**先做 workflow，等你從真實資料裡看清「哪些情況是固定流程處理不了的」，再把那一塊開放成 agent**。這比一開始就賭「這任務需要全自主」風險低得多——你是用真實證據逼出 agent 的必要性，而不是假設它。
- **「人在迴圈裡」改變整個選型**：如果你接受「agent 產出、人核可後才生效」這種半自動形態，維度二（可逆性）和維度四（容錯度）的門檻會大幅放寬——因為人的覆核變成了那道驗證關卡。代價是 scale 受限於人的覆核速度。這正是下一章信任階梯的核心權衡：**自主程度 ↔ 安全與可控**，不是一個固定選擇，而是隨著你對這個 agent 的信任累積而移動的滑桿。
- **選型會隨模型與工具演進而變**：今天「驗不了」或「缺工具」而被擋下的任務，可能因為明年有了更好的驗證手段或新工具而重新成立。導入決策不是一次性的判決——值得每隔一段時間，拿同一張計分卡重評一次手上被擱置的任務。

## 動手練習

1. 拿**你自己工作中**一個重複任務，填一遍 `agentify_score.py` 的五個維度。先別看總分，先寫下每個維度給這個分數的**理由**——你會發現「想清楚理由」比「得到分數」有價值得多。
2. 故意構造一個「總分高但有硬門檻」的任務（例如高頻、可逆、工具齊全，但成功完全主觀無法驗），跑跑看 `gate_flags` 有沒有抓到。如果你的任務讓計分卡給出「適合」但你直覺覺得危險，問自己：是哪個維度的評分太樂觀，還是有計分卡沒涵蓋的風險？
3. 把同一個任務分別設計成「純 workflow」和「workflow + 嵌入式 agent」兩個版本的草圖（不用實作，畫流程圖即可），比較它們各自把「開放的部分」放在哪、怎麼驗收那部分的輸出。

## 本章重點整理

- 導入決策的核心問題不是「agent 能不能做」，而是「這個任務值不值得用 agent 這條最貴、最難控的路」——能往左（純人工 / workflow）推就先推。
- agent 任務適配度看五個維度：可驗證性、可逆性與 blast radius、工具可達性、容錯度、頻率。其中可驗證性與「不可逆×低容錯」是會直接擋下或強制加安全層的**硬門檻**，比總分重要。
- 技術適配之外還要 ROI 成立：建置 + 每次執行（含人工覆核）+ 持續維護三類成本，跟「現在用人工做一年花多少」的基準比。
- 最務實的導入常是混合路線（workflow 為主、開放處嵌小 agent）或半自動（agent 產出、人核可執行），不是全有全無。
