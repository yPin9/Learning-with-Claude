# Ch 38 — 失敗模式與 debug agent

> **目標**：agent 跑歪了——它卡在迴圈、燒了一堆錢卻沒做完、宣稱「完成了」但其實沒有、或是默默走錯路。傳統程式壞了有 stack trace 指著那一行；agent 壞了，**「bug」往往是模型在某一步做的一個決定**，沒有例外、沒有紅字，而且**換一次跑可能就不重現了**。本章教你怎麼 debug 這種東西：先認得 agent 常見的**失敗模式**（無限迴圈、幻覺工具、context 中毒、過早放棄、錯誤恢復卡死…），再用 Ch 35 的 **trace** 從一坨非確定的行為裡**定位是哪一步、哪一類根因**（prompt / 工具 / context / 模型），最後修掉並**回灌成 eval 案例**（Ch 34）讓它不再復發。核心心態：**debug agent 不是「找那一行錯的程式」，是「找那一步錯的決定，並問它為什麼會那樣決定」。**

> **環境**：Python + Anthropic SDK，但本章重點是**方法論**。強烈依賴前面的工具：trace/replay（[Ch 35](./35-observability.md)）是你的主要儀器、eval（[Ch 34](./34-eval.md)）是回歸防線、停止條件（[Ch 7](./07-stop-conditions-turns.md)）、工具 schema/描述（[Ch 18](./18-tool-schema-design.md)/[Ch 19](./19-tool-descriptions-as-prompt.md)）、結果設計（[Ch 20](./20-tool-result-design.md)）、context 管理（[Ch 10](./10-context-window-budget.md)/[Ch 13](./13-context-compaction.md)/[Ch 16](./16-tool-result-pruning.md)）都會回來當「修法」。

## 為什麼需要這個？agent 的 bug 不長在程式裡

傳統 debug 的流程你很熟：程式炸了 → 看 stack trace → 跳到那一行 → 看變數 → 修。這套在 agent 上**大半失效**，因為：

- **沒有例外可抓**。agent「失敗」常常是**語意上的失敗**：它做完了、回了東西、看起來很合理——但結果是錯的、或繞了遠路、或根本沒做到。程式層面一切正常，沒有 traceback 指給你看。
- **bug 常在「決策」裡，不只在「程式」裡**。很多時候你的 harness 程式完全正確，錯的是模型在第 4 回合「決定」呼叫了錯的工具、或「相信」了一個幻覺——你要 debug 的是一個**機率性的決定**。但也有一大類 bug 真的在程式裡，只是長在**模型與 harness 的互動邊界**上（工具協定接錯、錯誤沒回好、停止條件判錯、結果格式爛）。所以 debug 第一刀就是分清：是「決定錯」還是「執行/協定錯」（下面第一節）。
- **非確定，難重現**。同一個輸入跑兩次路徑可能不同。「我這邊不會重現」是 agent debug 的家常便飯——你不能假設單次重跑就能復刻問題。
- **失敗會傳播**。第 2 回合的一個小幻覺，被寫進 context，後面每一回合都讀到它、在它上面繼續推理——等你發現「結果不對」時，根因在很多步以前。

所以 agent 的 debug 是**取證式**的：你手上要有「它到底做了什麼」的完整記錄（trace），然後像看監視器錄影一樣**逐步回放**，找出「哪一步開始走偏、那一步它看到的 context 長怎樣、為什麼會那樣決定」。**沒有 trace（Ch 35），你只能瞎猜重跑——這就是為什麼 observability 是 debug 的前提。**

## 先建立直覺：debug 的四步迴圈

把 agent debug 收斂成一個可重複的迴圈：

```
   ① 重現 ──→ ② 定位 ──→ ③ 歸因 ──→ ④ 修 + 回灌 eval
   （多跑   （看 trace，   （prompt/    （改完跑 eval
    幾次看   找走偏的       工具/        確認修好、
    頻率）   那一步/span）   context/     且沒造成
                            模型？）       新回歸）
                                              │
                            └──────────────────┘
                            （把這個 bug 變成一個 eval 案例，
                              下次回歸測試自動守住）
```

- **① 重現**：因為非確定，先跑 N 次估「多常壞」。每次都壞 → 是系統性問題（prompt/工具/context），好定位；偶爾才壞 → 是非確定問題（模型取樣**或**環境/harness 的不穩，看 Ch 39），要靠多跑 + trace 抓到壞的那一次，而且**連環境狀態一起記**（外部回應、工具延遲/錯誤、版本、side effect）。
- **② 定位**：用 trace 找出「從哪一步開始，行為偏離了你預期的軌跡」。這是最關鍵也最省時的一步——別從頭重想整個任務，**先框出出錯的那個 span**。
- **③ 歸因**：問「這一步它看到的 context 是什麼？它的決定錯在哪？」歸到四類根因之一（下一節）。
- **④ 修 + 回灌**：對著根因修（不是對著症狀），然後**把這個失敗變成一個 eval 案例**（Ch 34），確認修好且沒引入新回歸。

> **最容易省略、最不該省的是第④步的「回灌」**：修完很爽，但不把它變成 eval 案例，下次換個地方又踩同款、或這次的修法被未來的改動破壞——你不會知道。**每個 debug 過的 bug 都該留下一個守門的 eval。**

## 一、定位：是模型的問題，還是 harness 的問題？

定位時第一個分岔，能砍掉一半的搜尋空間：

```
   看出錯那一步的 trace span：
   ├─ 模型「決定」錯了嗎？        → 決策問題（它的輸入或能力出問題）
   │   （選錯工具、填錯參數、誤讀結果、亂編）
   └─ 模型決定對，但「執行/協定/環境」錯了嗎？ → harness 問題
       （工具協定接錯、工具拋例外、回了壞資料、權限擋下、逾時）
```

注意這一刀分的是「決定 vs 執行」，跟下面第三節的**四類根因**是兩個層次：「決定錯」這一支，再往下拆成 prompt / 工具描述/schema / context 三種「決策輸入」問題，加上「模型能力本身不足」；「執行錯」這一支就是 harness/協定問題。先粗分這一刀，再細歸四類。

具體看 trace 裡那一步的三樣東西（Ch 35 的四類資料）：

1. **它那一步看到的 context**（context snapshot）——它是在什麼資訊下做決定的？是不是 context 裡根本沒有它需要的東西、或塞了會誤導它的東西？
2. **它的決定**（LLM 輸出：選了哪個工具、填了什麼參數、講了什麼）——決定本身合理嗎？
3. **工具的輸入/輸出**（tool I/O）——工具真的照它的意思做了嗎？回的東西對嗎？

**「模型問題 vs harness 問題」這一刀很重要**：模型問題你改 prompt / 工具描述 / schema；harness 問題你改程式 / 錯誤處理 / 結果格式。搞錯方向會白忙——例如它一直選錯工具，你拼命改程式邏輯沒用，根因是工具描述（Ch 19）寫得讓模型分不清。

## 二、失敗模式圖鑑：症狀 → 根因 → 怎麼修

下面是 agent 最常見的失敗模式。每個都給：**怎麼在 trace 認出來**、**典型根因**、**往哪修**。

### (1) 無限迴圈 / 重複同一個動作

- **症狀**：回合數爆增、trace 裡同一個工具用幾乎一樣的參數被呼叫 N 次、成本飆高卻沒進展。
- **根因**：模型沒「意識到」上一次已經做過/失敗了（context 裡的訊號不夠強）、或工具結果沒清楚告訴它「狀態變了沒」、或缺乏停止條件。
- **修**：硬性的**回合上限 + 停止條件**（Ch 7）當安全網；讓**工具結果明確回報狀態變化**（Ch 20，例如「檔案已存在、未變更」而不是默默成功）；偵測「連續相同 tool_use」就中斷並把這事實餵回模型。

### (2) 幻覺工具 / 幻覺參數

- **症狀**：模型呼叫一個不存在的工具、或給了 schema 沒有的參數、或把參數值編出來（例如編一個它沒查過的檔名/ID）。
- **根因**：工具描述含糊讓它「以為」有某能力（Ch 19）、schema 太鬆沒擋住亂填（Ch 18/32）、或 context 裡缺它需要的真實值所以它用猜的。**注意**：用 provider 原生 tool use（把工具清單交給 API）時，模型回的 `tool_use` 名稱通常**落在你給的清單內**——真正「呼叫不存在的工具名」多半出現在你**自己用文字解析模型輸出**（沒用原生 tool use）、**工具註冊表不一致**（prompt 裡列的跟實際註冊的對不上）、**MCP/動態工具清單變動**、或 **replay/版本不符**的情境。先確認你是哪一種，再決定往哪修。
- **修**：收緊 **schema**（`enum`、`required`、`additionalProperties:false` 是 schema 內的約束）並開 **`strict` tool use**（Ch 32——`strict: true` 是工具定義的頂層設定，用 grammar-constrained sampling 保證 tool input 一定符合 schema，跟上面那些 schema keyword 不同層）；**工具描述寫清楚「能做什麼、不能做什麼」**（Ch 19）；對齊工具清單與註冊表（尤其 MCP/動態工具）；幻覺值通常是「該先查卻沒查」——用 prompt/流程逼它先取得真實值再動作。

### (3) Context 中毒（一個早期錯誤被一路放大）

- **症狀**：結果整個歪掉，但回頭看，根因是很多步以前一個小幻覺/誤讀，之後每步都建立在那個錯誤上。
- **根因**：錯誤資訊進了 context 就**一直被重讀**（Ch 6：歷史每回合重送），模型把自己之前說的當事實。
- **修**：這是最難的一類。手段包括：讓 agent **驗證關鍵事實再往下**（別讓未經查證的假設沉澱）、**裁剪/修正**被污染的歷史段（Ch 16）、在偵測到矛盾時主動回頭。預防勝於治療——(2)的幻覺防治就是在堵這個的源頭。

### (4) 過早放棄 / 假裝完成

- **症狀**：任務沒做完，agent 卻回「已完成」或「我無法做到」就停了；或只做了一半就收手。
- **根因**：停止條件判斷太寬鬆、prompt 沒講清「完成的標準」、或它撞到一個工具錯誤就放棄而不是換做法。**還有一大類根因藏在沒正確處理 `stop_reason`**：`max_tokens`（輸出被截斷，harness 卻當成正常結束）、`tool_use`（模型想呼叫工具，harness 沒進工具迴圈就停）、`pause_turn`（長任務暫停，harness 沒把回應接回去續跑）、`refusal` / `model_context_window_exceeded`（模型拒答或 context 超限，harness 沒辨識就當「做完了」）。
- **修**：在 prompt 裡**明確定義「完成」長什麼樣**（可驗收的標準）；**逐一處理每種 `stop_reason`**（[Ch 5](./05-tool-calling-protocol.md) 的工具迴圈、Anthropic「Handling stop reasons」對照表）——`tool_use` 要進工具迴圈、`max_tokens` 要續寫或判定截斷、`pause_turn` 要 resume；工具失敗時回**可恢復的錯誤訊息**（Ch 20，`is_error=True` + 說明）讓它換路，而不是把失敗當終點；必要時加一個「自我檢查是否真的達標」的步驟。

### (5) 忽略指令 / lost-in-the-middle

- **症狀**：你在 system 或早期訊息給的某條規則，到後面被無視了（context 變長後尤其常見）。
- **根因**：關鍵指令埋在很長 context 的中段，模型對「頭尾」注意力高、對「中間」低；或指令被後來的工具結果稀釋。
- **修**：把**關鍵約束放 system prompt 並保持顯眼**（Ch 11）；context 太長要壓縮（Ch 13）；重要的硬規則別只靠 prompt，用 **harness 層強制**（如 permission 閘 Ch 25、輸出驗證）——模型會忘，程式不會。

### (6) 誤讀工具結果（尤其是錯誤）

- **症狀**：工具回了錯誤或空結果，模型卻當成成功繼續；或把一個格式混亂的結果讀錯。
- **根因**：工具結果格式不清、錯誤沒明確標記、把資料和狀態混在一起（Ch 20）。
- **修**：**結果設計**（Ch 20）——錯誤明確標 `is_error`、狀態與資料分開、格式一致可解析；別回一坨讓模型猜的自由文字。

### (7) 錯誤恢復卡死（retry 風暴）

- **症狀**：某個工具一直失敗（如網路逾時、權限不足），模型一直用同樣方式重試，或反覆道歉但不改做法。
- **根因**：錯誤訊息沒給「可行的下一步」、或模型沒意識到「同樣做法不會成功」。
- **修**：錯誤訊息**要可行動**（Ch 20：說清為什麼失敗、建議怎麼改）；harness 層對「同一錯誤重複 N 次」設斷路器，把「這條路不通」這個事實明確餵回去。

### (8) Context 爆掉 → 截斷 → 失憶

- **症狀**：長任務跑到後面，agent「忘了」前面的目標或已做的事、行為變得語無倫次；或請求送不出去、或回應在生成途中被 context 上限截斷。
- **根因**：要分三種，trace 上長得不一樣，別混。① **harness 自己裁掉了輸入歷史**——你的壓縮/裁剪邏輯（Ch 13/16）把舊訊息摘掉或丟掉，模型於是「讀不到」早期目標（注意：API/模型**不會**默默幫你丟早期訊息，會被丟一定是你的 harness 動的手）。② **輸入就超過視窗**——整包 messages 的 input tokens 超過模型 context window，這通常是 **request/API error 或 token 預檢失敗**（送出前就該用 token counting 算出來、由 harness 預裁），不是一個 `stop_reason`。③ **生成途中撞到上限**——回應本身是成功的，但生成時碰到 context window 限制而截斷，`stop_reason` 會是 `model_context_window_exceeded`（這是「有效回應但被截斷」，跟 ② 的「請求根本送不出去」是兩回事）；輸出端的 `max_tokens` 截斷也屬這類。
- **修**：**監控 context 大小**（Ch 35）、送出前 **token counting** 在逼近上限前就動作；**壓縮**（Ch 13）把舊過程摘要成短結論、**裁剪**肥大的舊工具結果（Ch 16），但壓縮策略本身要保住「長期目標、已完成事項」這類關鍵資訊（壓壞了就是上面①的失憶）；把長期目標寫進 memory（Ch 14）而不是只靠對話歷史扛；**分別處理「輸入超限的 request error」與「生成截斷的 `model_context_window_exceeded`」**，而不是讓它們變成沉默的失敗。

### (9) 過度積極做危險動作

- **症狀**：沒問就刪檔、force push、寄信、改了不該改的東西。
- **根因**：缺乏 permission 閘、或 prompt 沒講清「哪些動作要先確認」。
- **修**：**permission 閘**（Ch 25）攔不可逆/高波及的動作；這也是 prompt injection 的防線（Ch 36）——是 bug 還是攻擊，閘都擋。

### (10) 工具協定/訊息形狀錯誤

- **症狀**：API 直接報錯或行為詭異，但**不是模型決定錯**——`tool_use` 沒有對應的 `tool_result`、`tool_use_id` 對不上、`tool_result` 後面又多塞了文字、平行工具呼叫只回了一部分、或 `tool_use` 被 `max_tokens` 截斷成不完整的 JSON。
- **根因**：這是**純 harness 的協定處理 bug**（不是 prompt、不是模型）：你的工具迴圈組訊息時漏配、順序錯、或沒處理截斷。
- **修**：嚴格遵守工具協定（[Ch 5](./05-tool-calling-protocol.md)）——每個 `tool_use` 都要回一個 `tool_use_id` 相符的 `tool_result`、平行呼叫要全部回齊、收到 `max_tokens` 截斷的 `tool_use` 要重發而非硬送；在 harness 層加 assertion 檢查訊息形狀，壞在送出前就攔下。

### (11) 結構化輸出 / 最終答案驗證迴圈

- **症狀**：要求模型回 JSON（或某 schema），它回的 parse 不過；harness 把錯誤回去要它重修，但**修正訊息堆進 context 反而把它帶歪**，或反覆修都修不對、燒一堆 token。
- **根因**：輸出沒用結構化保證（Ch 32）、驗證回饋訊息太模糊（只說「格式錯」沒說錯在哪）、或 JSON 是被 `max_tokens` 截斷的（不是模型不會，是被切斷）。
- **修**：用 provider 的結構化輸出/工具強制（Ch 32）從源頭保證形狀；驗證失敗的回饋要**具體**（指出哪個欄位、期望什麼）；先排除「是不是 `max_tokens` 截斷」（看 `stop_reason`）再怪模型；修正迴圈設次數上限，別讓它無限堆 context（連到(3)context 中毒）。

### (12) 副作用重複 / 狀態漂移（idempotency 缺失）

- **症狀**：同一個有副作用的動作被執行兩次——重複寫入、重複寄信、重複扣款；或重試/replay 之後，外部狀態跟 trace 對不上（state drift）。常在 retry（(7)）、resume、或「執行了工具但結果還沒記錄就中斷」時爆發。
- **根因**：工具**不冪等**、且沒有去重鍵（idempotency key），所以「做一次」和「做兩次」效果不同；harness 在「副作用完成」和「結果寫回 context」之間若中斷重跑，就會重做。
- **修**：讓有副作用的工具**冪等或可去重**（同樣輸入跑兩次等於跑一次、或用 idempotency key 讓工具端跳過做過的）；把「執行+記錄結果」放進同一個可恢復邊界；這也是 replay 能不能安全重放、resume 安不安全的前提——**Ch 39 會專門講**。

## 三、歸因：四類根因，對應四種修法

把上面的修法收斂——agent 的 bug 幾乎都歸到這四類，**修法完全不同，所以歸對類最省時**：

| 根因類別 | 典型症狀 | 往哪修 | 對應章 |
|---|---|---|---|
| **Prompt 問題** | 忽略指令、不知道「完成」標準、行為飄 | 改 system/任務 prompt、講清約束與目標 | Ch 11 |
| **工具問題** | 選錯工具、幻覺參數、誤讀結果 | 改 schema、工具描述、結果格式 | Ch 18-20, 32 |
| **Context 問題** | 失憶、lost-in-the-middle、context 中毒 | 壓縮、裁剪、memory、監控大小 | Ch 10,13,16 |
| **模型問題** | 換模型後某類退化、推理力不足 | 換/升模型、加驗證步驟、分解任務 | Ch 34, 37 |

實務上一個 bug 可能跨類（例如 context 太長 → 忽略指令），但**先歸主因**：問「如果這一步它的 context 完整且正確、工具描述清楚、prompt 講明了，它還會錯嗎？」——能消掉的就不是根因。

> **別對著症狀修**：看到迴圈就只加回合上限（治標），但根因可能是工具結果沒回報狀態（治本）。回合上限是該加的安全網，但若不修根因，它只是把「無限迴圈」變成「跑到上限才失敗」。**安全網 + 根因修，兩個都要。**

## 四、處理非確定：怎麼 debug「偶爾才壞」

最惱人的一類：跑 10 次壞 1 次。先搞清楚**「偶發」的來源不只模型取樣**：模型的隨機性（temperature 取樣）只是其中一種，環境/harness 的非確定同樣會造成偶發——不穩的外部 API、工具逾時、權限或檔案狀態在兩次跑之間變了、race condition、rate limit、快取、時間相依（今天跟昨天回不一樣）。debug 手段：

- **提高重現率**：多跑（`runs_per_case` 拉高，Ch 34），把壞的那次的 trace 抓下來——你需要的是**壞掉那一次**的完整記錄，不是一個「平均」。重現時**連環境一起記**：外部回應、工具延遲/錯誤、相依版本、有沒有 side effect 改了狀態——不然你以為在追模型，其實是環境在搗蛋。
- **固定隨機源**：debug 時把 temperature 設低/設 0、固定能固定的東西（Ch 39），縮小**模型端**的行為空間，讓問題更容易穩定重現（但注意：這固定不了環境端的非確定）。
- **二分定位**：壞的 trace 拿到後，找「最後一個還正確的 span」和「第一個明顯錯的 span」之間那一步——根因通常就在那。**嚴格說只有「可重放」時才是真的二分**（能用 prefix/checkpoint 重跑、能隔離單一 span 重試）；只有單一條 trace 時，你做的是「標出分岔點」而非反覆對半測試。
- **比對好/壞兩條 trace**：同任務一條成功、一條失敗，diff 它們在「哪一步開始分岔」——分岔點的 context 差異是**最該先看的線索**，但別當鐵證：context 一模一樣也可能因為取樣、外部工具非確定、或隱藏狀態而分岔。把它當「下一步往哪查」的指引，再回去驗證。

> **非確定不是「沒法 debug」的藉口**：它只是要求你**先把問題固定下來**（多跑抓到、降隨機性），再用 trace 取證。降低非確定性本身是 Ch 39 的主題。

## 對比與取捨

| 場景 | 直覺做法 | 更好的做法 | 為什麼 |
|---|---|---|---|
| agent 結果不對 | 重跑看看、改 prompt 試試 | **先看 trace 定位到出錯的 span** | 瞎改是賭博；trace 讓你對著真正出錯處下手 |
| 在 trace 裡找根因 | 從頭讀整段 | **二分：找好→壞的分岔點** | 省時，直接框出問題步 |
| 無限迴圈 | 只加回合上限 | **回合上限（網）＋ 修工具結果（根）** | 上限治標；不回報狀態才是根因 |
| 一直選錯工具 | 改 harness 程式邏輯 | **多半先查工具描述/schema** | 通常是「決定」錯（描述含糊）；但也要核對 tool registry / `tool_choice` / 動態工具清單是否對得上 |
| 偶爾才壞 | 「我這邊不重現」放著 | **多跑抓壞 trace + 降隨機性** | 非確定要先固定再查 |
| 修好了 | 收工 | **回灌成 eval 案例（Ch 34）** | 不回灌就會復發或被未來改動破壞 |

## 踩雷集錦

1. **沒有 trace 就硬 debug**：靠重跑和猜，非確定性會把你耍得團團轉。先有 observability（Ch 35），debug 才有依據。
2. **對著症狀修、不找根因**：迴圈只加上限、忽略指令只是把指令再講一遍大聲一點——治標不治本，換個輸入又壞。
3. **把「模型問題」當「harness 問題」修（反之亦然）**：選錯工具去改程式、工具拋例外去改 prompt——方向錯，白忙。先用 trace 分清是「決定錯」還是「執行錯」。
4. **單次重跑就下結論**：「重跑一次好了」不代表修好了，可能只是這次沒踩到。非確定 bug 要多跑驗證。
5. **忽略 context 中毒的傳播**：只看「結果錯的那一步」，沒回溯到「錯誤最早進 context 的那一步」——根因在很前面。
6. **debug 完不回灌 eval**：最常見的浪費。修好的 bug 沒變成回歸測試，遲早復發。
7. **用 print 大海撈針**：在非確定多步系統裡灑 print，輸出一坨還對不上是哪次跑。要結構化 trace + run_id（Ch 35）。
8. **改太多東西一次**：一次同時改 prompt、schema、模型，壞的修好了也不知道是哪招生效、好的搞壞了也找不到兇手。一次改一個變因。
9. **debug 時不降隨機性**：用預設 temperature 追一個偶發 bug，行為空間太大很難穩定重現。先降溫固定（Ch 39）。

## 進階：再往深一層

- **trajectory 級的自動偵測**：把常見失敗模式寫成對 trace 的自動檢查（連續相同 tool_use → 迴圈、出現不存在的工具名 → 幻覺、context size 超閾 → 爆掉風險）。這把「人工看 trace」升級成「系統自動標可疑軌跡」——接 Ch 34 的 trajectory eval。
- **multi-agent 的 debug 更難（Ch 27）**：失敗可能在「orchestrator 拆題拆爛」「某個 subagent 退化」「彙整漏掉衝突」。要能**分層看 trace**（每個 subagent 自己的 span 樹），不然只知道「整體變差」卻定位不到是哪一層、哪個 worker。
- **「它為什麼這樣決定」有時要問它**：在 debug（非生產）情境，可以讓模型把推理講出來（thinking / 要它解釋選擇），幫你理解它的決策——但記得這是**事後合理化、不一定是真實成因**，當線索不當證據。
- **錯誤注入測試（chaos）**：主動讓工具回錯誤/空值/畸形資料，看 agent 的恢復行為——很多失敗模式（誤讀錯誤、retry 風暴、過早放棄）只有在錯誤路徑上才暴露，happy path 測不到。
- **回歸的根源常是「沉默的依賴」**：你改了 A（升模型、調 prompt），B 默默退化——這正是 Ch 34 eval + Ch 35 trace 合體的價值：eval 抓到「B 變差了」，trace 告訴你「因為 B 那步現在的決定變了」。
- **區分「bug」與「能力上限」**：有些「失敗」不是 bug，是任務超出模型能力（需要它做不到的長程推理）。這時修 prompt/工具沒用，要**分解任務**（Ch 28）、降低單步難度，或升模型。先判斷是「設計問題」還是「能力問題」。

## 動手練習

1. **造一個無限迴圈再抓它**：拿 Practice C 的檔案 agent，把某個工具的結果改成「永遠不回報狀態變化」（例如 write 後回空字串），餵一個任務看它會不會重複呼叫。用 trace 認出迴圈，然後用「回合上限 + 結果回報狀態」兩招修掉。
2. **幻覺參數**：把一個工具的 schema 放鬆（拿掉 `required`/`enum`），給一個「它沒有足夠資訊」的任務，觀察它是否編造參數值。用 trace 確認，然後收緊 schema（Ch 32）修掉。**但要體會 schema 的極限**：`enum`/`required` 只能擋「形狀與值域」（少了欄位、值不在允許清單），擋不了「形狀對但內容是編的」——例如它填一個格式正確卻根本不存在的檔名/ID。truthfulness 要靠**先查再填**（流程逼它取得真實值）、或**工具端驗證**（收到參數後查一次、查不到就回 `is_error`），schema 管不到。
3. **二分定位**：找一個你的 agent 會做錯的任務，用 Ch 35 的 trace 跑一次，標出「最後一個正確 span」和「第一個錯誤 span」，寫下你判斷的根因屬於哪一類（prompt/工具/context/模型）。
4. **好壞 trace diff**：同一個偶發失敗的任務跑到一次成功、一次失敗，把兩條 trace 並排，找出分岔的那一步和它們 context 的差異。
5. **回灌 eval**：把上面任一個你修好的 bug，寫成一個 `EvalCase`（Ch 34），故意把修法還原確認 eval 會紅、修法加回確認變綠——體會「bug → 回歸測試」的閉環。

## 本章重點整理

- agent 的 bug **常不只在程式裡，也在模型的決定或「模型↔harness 邊界」上**：沒有 stack trace、常是語意失敗（看起來成功其實錯）、非確定難重現、且會**傳播**（早期小錯被一路放大）。
- debug 是**取證式**的，靠 trace（Ch 35）逐步回放——**沒有 observability 就只能瞎猜重跑**。
- 四步迴圈：**重現（多跑看頻率）→ 定位（trace 找走偏的 span）→ 歸因（四類根因）→ 修 + 回灌 eval（Ch 34）**。
- 定位先問**「模型問題還是 harness 問題」**：決定錯 vs 執行錯，修法完全不同。
- 失敗模式圖鑑：迴圈、幻覺工具/參數、context 中毒、過早放棄、忽略指令、誤讀結果、retry 風暴、context 爆掉、過度積極、工具協定錯誤、結構化輸出驗證迴圈、副作用重複/狀態漂移——每個都有「trace 怎麼認 + 往哪修」。
- 四類根因對應四種修法：**Prompt（Ch 11）/ 工具（Ch 18-20,32）/ Context（Ch 10,13,16）/ 模型（Ch 34,37）**。**對根因修，別只貼症狀（安全網 + 根因修都要）。**
- 非確定 bug：**多跑抓到壞 trace、降隨機性（Ch 39）、二分定位、好壞 trace diff**。
- **每個修好的 bug 都回灌成 eval 案例**——不回灌就會復發。
