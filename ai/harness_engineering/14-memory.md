# Ch 14 — Memory：短期 vs 長期

> **目標**：實作 Ch 12 選單裡的「策略三：外移到 memory」。讀完你能分清楚短期記憶（in-context）與長期記憶（external store）、用檔案式 memory 讓 agent 把該長期記住的東西寫到 context 之外、設計「何時寫、何時讀」、並理解 memory 跟壓縮（Ch 13）、RAG（Ch 15）各自的分工。

> **環境**：Python 3.11、`anthropic` Python SDK（最新版），延續前面的 `Agent`。memory 用本地檔案實作。

## 為什麼壓縮還不夠，需要 memory

Ch 13 的壓縮解決了「歷史太長」，但它有個根本限制：**被壓縮的東西會逐漸模糊、甚至消失**。多層遞迴壓縮後，早期的關鍵事實可能被稀釋掉（Ch 13 的踩雷第 6 點）。而且壓縮是「對話內」的——一旦這段對話結束（程式重啟、使用者開新 session），所有東西都沒了。

但有些東西你**不希望它被壓縮模糊、也不希望它隨對話消失**：

- 使用者的長期偏好（「我都用 TypeScript、不要給我 Python 範例」）
- 跨任務的關鍵事實（「這個專案的資料庫是 PostgreSQL 15」）
- agent 自己歸納出的、之後還要用的結論（「我已經確認模組 A 的 bug 在第 42 行」）

這些東西的正確歸宿不是「塞進會被壓縮的對話歷史」，而是**寫到 context 之外的一個持久儲存，需要時再撈回來**。這就是 memory。一句話分工：**壓縮是「把當前對話變短」，memory 是「把該長期記住的搬到對話之外」。**

## 先建立直覺：短期記憶 vs 長期記憶

人的記憶有兩層：**工作記憶**（現在腦子裡正在想的，容量小、會忘）和**長期記憶**（寫在筆記本、存在腦海深處的，需要時回想起來）。agent 的記憶完全對應：

```
   短期記憶（working memory）            長期記憶（long-term memory）
   ─────────────────────────            ─────────────────────────
   = 當前 context（messages）            = context 之外的持久儲存
   容量 = context window（有限）          容量 = 幾乎無限（檔案/DB）
   每輪都送、佔 token、會被壓縮            不佔 context，除非主動撈回來
   對話結束就沒了                         跨對話、跨 session 存活
   模型「直接看得到」                      模型要「主動讀」才看得到
```

關鍵差異在最後一行：**長期記憶（這裡指 pull-based 的外部記憶）不會自動出現在模型眼前**。它存在外面，模型必須透過工具（讀 memory）把需要的部分撈進 context，才「想得起來」。這跟人一樣——你筆記本上寫的東西，要翻開來看才記得。（補充：有些產品會在 session 啟動時**自動載入**一份記憶摘要或索引——例如 `CLAUDE.md`——那種是 push-based，啟動時就佔了 context。本章做的是 pull-based 的版本：要用才撈。）

這帶出 memory 的核心設計問題：**什麼時候寫進去、什麼時候撈出來？** 寫太多會變成另一個雜亂的大倉庫；撈錯了等於沒記。

## 一、最簡單的 memory：一個檔案

memory 不需要花俏的基礎設施。最簡單、也意外地好用的版本，就是**一個 agent 能讀能寫的檔案**。給 agent 兩個工具：

```python
import os

MEMORY_PATH = "agent_memory.md"

def read_memory() -> str:
    """讀取 agent 的長期記憶筆記。"""
    if not os.path.exists(MEMORY_PATH):
        return "（目前沒有任何長期記憶）"
    with open(MEMORY_PATH, "r", encoding="utf-8") as f:
        return f.read()

def write_memory(content: str) -> str:
    """把一條重要資訊追加進長期記憶。content 應該是精煉、具體的一條事實或偏好。"""
    with open(MEMORY_PATH, "a", encoding="utf-8") as f:
        f.write(content.rstrip() + "\n")
    return "已寫入長期記憶。"
```

把這兩個工具加進你的工具註冊表（Ch 4），並在 system prompt（Ch 11）告訴 agent 怎麼用它們：

```
## 長期記憶
你有一份跨對話保存的長期記憶筆記。
- 在對話開始時，先讀取 read_memory 了解使用者的既有偏好與重要背景。
- 當使用者表達一個長期偏好、或出現一個之後還會用到的關鍵事實時，用 write_memory 記下來。
- 只記「未來的你會需要、且不會變的」資訊；不要把一次性的對話內容塞進去。
```

就這樣。agent 現在能跨對話記住東西了——它在對話開頭讀筆記、在遇到值得記的東西時寫筆記。**這個「agent 讀寫一個筆記檔」屬於和 Claude Code 同一家族的核心模式。** 要稍微區分：`CLAUDE.md` 比較像「每次啟動自動載入、通常由人維護的持久指令檔」，而「agent 自己讀寫、自己決定記什麼」的那種，更接近 Claude Code 的自動記憶機制。本章做的是後者。但它們共享同一個本質——用一個持久檔案承載跨對話的記憶。簡單到你可能不信，但它有效，因為它把「記什麼、什麼時候記」的判斷交給了最適合判斷的角色——模型自己。

## 二、agentic memory：讓模型決定記什麼

上面的設計有個重要特徵：**是模型自己決定要寫什麼、什麼時候寫**，不是你用程式碼寫死規則。這叫 **agentic memory**——記憶的管理本身也交給 agent 的判斷。

為什麼這樣比「寫死規則」好？因為「什麼值得長期記住」是個高度依賴語境的判斷。你很難用 `if` 寫出「使用者這句話算不算長期偏好」。但模型讀完上下文，通常能判斷得不錯——前提是你在 system prompt 給了好的**準則**（Ch 11 的 altitude）：記「相對穩定、未來會用」的（注意是「相對穩定」不是「永遠不變」——使用者偏好、專案狀態都會演化，這類該記、但要能更新），別記一次性的。

```
   ❌ 寫死規則（脆弱）                    ✅ agentic（給準則，模型判斷）
   if "我喜歡" in user_msg:              system prompt:
       write_memory(user_msg)             "當使用者表達長期偏好、或出現
   # 抓不到「以後都用 X」這種變體            之後會用到的關鍵事實時，記下來"
   # 也會誤記「我喜歡今天的天氣」           → 模型判斷「這是長期偏好嗎」
```

這跟 Ch 11 的「職位說明書 vs 腳本」是同一個哲學：給原則、信任判斷，而不是窮舉規則。

> 代價要誠實講：交給模型判斷，代表它**有時會判斷錯**——記了不該記的、或漏記該記的。所以 memory 不是「設好就忘」，需要觀察與調整（system prompt 的準則、甚至偶爾人工清理）。但相比「寫死規則」的脆弱與盲點，agentic 通常是更好的起點。

## 三、結構化你的 memory，別讓它變垃圾場

一個檔案能跑，但隨著 agent 一直 append，它會變成一坨雜亂的流水帳——然後你 `read_memory` 撈回來的就是一大坨低訊噪比的東西塞進 context，違反 Ch 10 的精神。所以 memory 需要**結構**：

```markdown
# Agent 長期記憶

## 使用者偏好
- 慣用語言：TypeScript，不要給 Python 範例
- 回答風格：簡潔，先給結論

## 專案事實
- 資料庫：PostgreSQL 15
- 部署環境：AWS ECS

## 已確認的結論
- [2026-06-01] 模組 A 的 bug 在 utils.ts:42，已修復
```

分類（偏好 / 事實 / 結論）讓 memory 可維護、可選擇性讀取（之後你可以只撈「使用者偏好」那段，而不是整個檔案）。更進階的做法是**用多個檔案或目錄**（一個主題一個檔），讓 agent 能「只讀它現在需要的那塊」，而不是每次都把整個記憶倒進 context。

> 這呼應 Ch 6/Ch 12 的「儲存 ≠ 餵給模型」：你的 memory store 可以很大很完整，但每次只**選擇性地**撈相關的一小塊進 context。memory 的價值不只在「存得下」，更在「能精準撈出當下需要的那一條」。

## 四、memory vs 壓縮 vs RAG：三者的分工

這三個東西很容易混，這裡一次釐清（RAG 是下一章，先建立分野）：

| | 解決什麼 | 資料來源 | 何時用 |
|---|---|---|---|
| **壓縮（Ch 13）** | 當前對話太長 | 對話歷史本身 | 歷史逼近 context 上限 |
| **Memory（本章）** | 跨對話/跨時間記住關鍵事實 | agent 自己寫下的筆記 | 有「不該忘、不該被壓糊」的東西 |
| **RAG（Ch 15）** | 讓 agent 取用大量外部知識 | 外部文件庫（你預先準備的） | 知識量遠超 context、且非 agent 自己產生 |

一句話區分：

- **壓縮**處理「對話內部」的肥大。
- **memory** 是 agent **自己**累積的筆記（它寫、它讀）。
- **RAG** 是取用**外部既有**的大知識庫（別人準備的，agent 通常只讀不寫）。

它們**協同工作**：一個成熟 agent 可能同時——壓縮當前對話、把關鍵結論寫進 memory、需要背景知識時用 RAG 撈。別把它們當成三選一。

## 五、何時讀、何時寫：時機設計

memory 有用沒用，全看時機抓得準不準：

**寫的時機**：
- 使用者明確表達偏好時（「以後都…」「我比較喜歡…」）。
- agent 得出一個之後還會用到的結論時（「確認了 X」）。
- 一個任務告一段落、有值得保留的成果時（常常配合 Ch 13 的壓縮一起做——壓縮前先把關鍵事實寫進 memory，這樣即使壓縮模糊了對話，事實仍在 memory 裡）。

**讀的時機**：
- 對話/session 開始時，讀一次相關 memory 進 context（建立背景）。
- 遇到需要回憶的問題時，主動讀（「我之前是不是處理過這個？」）。

> **壓縮前先寫 memory** 是個關鍵的協同技巧，值得單獨強調：Ch 13 說「真正關鍵的東西別賭它在多層摘要後還活著」——具體做法就是在觸發壓縮**之前**，讓 agent 把那段歷史裡的關鍵事實先 `write_memory`。這樣壓縮可以放心地把對話濃縮掉，因為精華已經安全地存在 memory 外部了。memory 和壓縮在這裡是黃金搭檔。

## 失敗示範：memory 變成什麼都記的垃圾場

看一個「有 memory 卻幫倒忙」的例子。system prompt 寫得太鬆：

```
## 記憶
把對話中任何可能有用的資訊都記到 memory。
```

agent 很「盡責」地把每句話都記下來。幾天後 `agent_memory.md` 長這樣：

```
使用者說你好
使用者問了天氣
使用者覺得今天有點累
使用者問了 2+2
使用者說謝謝
... (五百行流水帳) ...
```

災難在於：每次 `read_memory` 都把這五百行倒進 context，**低訊噪比、佔大量 token、還可能觸發 context rot**（Ch 10）。memory 本來是要「精準保留關鍵」，現在卻變成另一個比對話歷史更糟的垃圾場——因為它還跨對話累積，只會越來越肥。

**問題不在 memory 機制，在準則太鬆。** 正確的 system prompt 要明確：只記「不會變、未來會用」的；一次性的、寒暄的、能重新查到的，都不該進 memory。memory 的價值在**選擇性**，不在「記得多」。這跟 Ch 10「高訊噪比優於塞滿」是同一條原則，只是搬到了 context 之外。

## 踩雷集錦

1. **memory 準則太鬆，變垃圾場**：「把有用的都記下來」會讓 agent 記一堆流水帳，read 回來低訊噪比又佔 token。準則要嚴：只記「相對穩定、未來會用」的（且要能更新，不是只追加）。
2. **每次把整個 memory 倒進 context**：memory 大了之後，無差別全讀違反「儲存≠餵給模型」。要結構化、選擇性讀取（按分類、按主題檔）。
3. **把 memory 跟壓縮搞混**：壓縮處理當前對話的肥大；memory 是跨對話的關鍵事實外存。兩者協同，不是替代。
4. **壓縮後才想到要記**：關鍵事實要在**壓縮前**就 `write_memory`，否則壓縮把它模糊掉就晚了。
5. **用寫死規則管理 memory**：「if 出現某關鍵字就記」抓不到語境變體、又會誤記。給準則、讓模型判斷（agentic memory），但要觀察校正。
6. **memory 寫入沒有去重/更新機制**：使用者偏好改了（「其實我現在改用 Rust」），舊的偏好還留在 memory 裡造成矛盾。進階的 memory 要能更新/覆蓋，不只 append。

## 進階：再往深一層

- **Anthropic 的 memory 工具**：Anthropic 定義了一個標準化的 memory tool **介面**，讓 agent 能用一致的方式跨對話讀寫記憶。要釐清：它**不是「Anthropic 幫你代管儲存」**——實際的 backend（本地檔案、資料庫、雲端、加密檔…）由**你自己實作或配置**，檔案式只是最常見的範例。本章手刻的 `read_memory`/`write_memory` 就是這個範式的最小版——自己刻過，你會懂這個標準介面在規範什麼、以及你仍要自己負責 backend 那一端。用到時看官方 memory tool 文件。
- **memory 的「更新」比「追加」難**：append 很簡單，但真實 memory 需要**更新與淘汰**——偏好變了要覆蓋、過期的事實要刪、矛盾的要調和。這通常需要更結構化的儲存（每條 memory 有 id、類別、時間戳，像本課這個 repo 的 `MEMORY.md` 索引 + 單檔的設計），讓 agent 能「找到舊的那條並改它」，而不只是一直往後加。
- **memory 與 context rot 的張力**：memory 解決「跨時間記住」，但如果讀回太多，它自己就變成 context rot 的來源。好的 memory 系統永遠在平衡「記得夠」與「讀得精」——這跟 RAG 的檢索品質問題（Ch 15）本質相同：**重點從來不是「存了多少」，而是「能不能在對的時機撈出對的那一小塊」**。
- **多 agent 共享 memory**：當你有多個 agent（Part 4），它們可以共享一個 memory store 來協作（一個 agent 的發現，另一個讀得到）。但共享也帶來一致性問題（同時寫怎麼辦）。這是 multi-agent 的進階主題，Ch 27 會碰。

## 動手練習

1. 給你的 mini-agent 加上 `read_memory`/`write_memory` 兩個工具與對應的 system prompt 準則。跑兩段**獨立**的對話：第一段告訴它「我都用 TypeScript」，第二段（重啟程式後）問它「給我一個範例」，看它有沒有從 memory 記得你的偏好、給 TS 而非其他語言。
2. 故意用「把有用的都記下來」這種鬆準則，跑一段閒聊，看 `agent_memory.md` 變多亂——重現垃圾場失敗示範。再換成嚴格準則，對比。
3. 實作「壓縮前先寫 memory」的協同：在你的 `compact`（Ch 13）觸發前，先讓 agent 把關鍵事實 `write_memory`，壓縮後問一個需要那個事實的問題，確認它能從 memory 撈回來（而不是依賴被壓糊的摘要）。
4. （進階）把單一檔案改成「分類 + 選擇性讀取」：read_memory 接受一個類別參數（偏好/事實/結論），只回那一類。觀察撈回來的 context 變精簡多少。
5. （設計題）想想你的 memory 要怎麼支援「更新」而非只「追加」——使用者改了偏好時，怎麼讓 agent 找到舊那條並覆蓋？寫下你的設計。

## 本章重點整理

- 短期記憶 = 當前 context（有限、會被壓縮、對話結束就沒）；長期記憶 = context 之外的持久儲存（近乎無限、跨對話、但要主動讀才看得到）。
- 最簡單有效的 memory 就是「agent 能讀能寫的檔案」——這是 Claude Code `CLAUDE.md` 等機制的本質。
- agentic memory：讓模型自己判斷記什麼（給準則、信任判斷），比寫死規則好，但要觀察校正。
- memory 要結構化、選擇性讀取，否則會變成比對話歷史更糟的垃圾場（低訊噪比 + 跨對話累積）。
- 三者分工：壓縮處理當前對話肥大、memory 是 agent 自己的跨對話筆記、RAG 取用外部既有知識庫——協同而非三選一。
- 黃金搭檔：**壓縮前先把關鍵事實寫進 memory**，這樣壓縮模糊了對話也不怕。
