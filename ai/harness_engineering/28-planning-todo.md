# Ch 28 — Planning 與 todo 管理

> **目標**：前面教你 agent 怎麼跑迴圈（Part 1）、怎麼管 context（Part 2）、怎麼用工具與派 subagent（Part 3-4）。本章補上長任務的關鍵一塊：**規劃與進度追蹤**。讀完你能說出為什麼長多步任務需要「先想清楚再做 / 邊做邊記做到哪」、plan（計畫）與 todo（待辦清單）兩者的分工、為什麼 todo list 要進到 context 裡（它就是 agent 的「外部短期記憶」對抗第 13 章的 context 漂移）、「先規劃後執行」相對「邊想邊做」的取捨、以及 plan mode（唯讀規劃、人類核可後才動手）這種安全閥為什麼存在。

> **環境**：Python + Anthropic SDK，延續前面各章的 agent 迴圈。本章的主角不是某個新 API，而是一種**用工具實作出來的工作習慣**——你正在用的這個 session 就帶著一個 `TodoWrite` 工具和一個 plan mode，本章會直接把它們當第一手教材拆解（會標明哪些是這個 harness 的特定設計、哪些是通用原則）。

## 為什麼需要這個？長任務會「迷路」

回想 Ch 7 的 agent 迴圈：模型看 context → 決定下一步 → 呼叫工具 → 看結果 → 再決定……一步接一步。短任務這樣很好。但任務一長（十幾二十步、跨多檔、要先查再改再驗），三個問題就冒出來：

1. **沒有全局，只有下一步**。迴圈天生是「貪心」的——它每次只看當下決定下一動作，很容易做著做著就鑽進一條岔路，忘了原本的大目標。
2. **做到哪了會忘**。隨著對話變長、context 被壓縮（Ch 13），早期「我打算做 A、B、C、D」的宣告可能被擠出視窗或稀釋，模型於是重做已做過的事、或漏掉還沒做的。
3. **使用者看不到進度**。一個 agent 默默跑五分鐘、中途才發現方向錯了，使用者既無從中途修正、也不知道它到底在幹嘛。

人類做大專案怎麼解決？**先列計畫，再邊做邊勾待辦清單。** Agent 需要的是同一招的工程化版本：

- **Planning（規劃）**：動手前，先把大任務拆成有順序、有依賴的步驟，形成一份計畫。這對抗的是「只有下一步、沒有全局」。
- **Todo 管理（進度追蹤）**：把計畫變成一份**活的待辦清單**，放進 context，每完成一項就更新狀態。這對抗的是「做到哪了會忘」和「使用者看不到進度」。

關鍵心態：**plan 與 todo 不是給人看的文件，是 agent 自己的工作記憶。** 把它們放進 context，等於給那個健忘、貪心的迴圈一個隨時看得到的「我要做什麼、做到哪了」的錨點。

## 先建立直覺：todo list 是「貼在螢幕邊的便利貼」

想像你在做一個多步驟任務，但每隔幾分鐘就會短暫失憶一次（這正是 context 壓縮對 agent 做的事）。你會怎麼自保？**把待辦清單寫在一張便利貼上，貼在螢幕邊**——每次「醒來」第一件事就是看那張便利貼：哪些打勾了、現在該做哪一項、後面還有什麼。

```
        ┌─ 規劃（一次性，動手前）─────────────┐
        │  大任務 → 拆成有序步驟 → 一份計畫       │
        └──────────────┬──────────────────────┘
                       ▼
   ┌─ todo list（活的，全程貼在 context 裡）──────────┐
   │  [x] 1. 找到登入流程相關檔案        ← 已完成        │
   │  [>] 2. 定位 token 過期的 bug       ← 進行中（唯一） │
   │  [ ] 3. 寫修正                                     │
   │  [ ] 4. 跑測試驗證                                 │
   └───────────────────────────────────────────────────┘
        每完成一項 → 更新清單 → 清單回到 context
        → 模型下一回合「一眼看到」全局與進度，不迷路
```

便利貼有三個要點，正好對應 todo 工具的設計：

- **它在你眼前**：todo list 寫進 context（不是存在某個你看不到的地方），模型每回合都讀得到。
- **同時最多一件「進行中」**：你不會同時動手做五件事；清單上**最多一項**標記為進行中，逼出專注與順序（開工前、全部做完後、或暫停時可以是零項——「最多一項」才精確，不是「永遠剛好一項」）。
- **完成就立刻劃掉**：不是做完五件才一次更新——每完成一項馬上更新，清單才反映真實進度，使用者也即時看到。

> **這個 session 就帶著這張便利貼**：我（這個 agent）有一個 `TodoWrite` 工具。每個 todo 有 `content`（要做什麼）、`activeForm`（進行中時顯示的字樣）、`status`（`pending` / `in_progress` / `completed`），而且規則是**任何時候最多一項 `in_progress`**。我寫課程時就是一章一個 todo、寫完一章標 completed、把下一章標 in_progress——你在這個 session 看到的進度更新，就是這張便利貼在運作。這是本 harness 的特定工具（工具的確切名稱與形態會隨版本變——較新的 Claude Code/Agent SDK 已改用 `TaskCreate`/`TaskUpdate`/`TaskList` 這組任務工具，`TodoWrite` 成了相容用的舊介面），但「把活的待辦清單放進 context」是不變的通用原則。

## 一、規劃：動手前先把路想清楚

規劃就是**在第一次呼叫工具之前，先讓模型產出一份步驟計畫**。最樸素的做法是一次純文字呼叫：把大任務丟給模型，要它輸出「要做哪些步驟、什麼順序、彼此怎麼依賴」，不准它現在動手。

```python
def make_plan(big_task: str) -> str:
    """規劃階段：只想、不動手。產出一份步驟計畫（純文字或結構化）。"""
    resp = client.messages.create(
        model="claude-opus-4-8", max_tokens=1024,
        system=(
            "你是規劃者。把使用者的大任務拆成有序、有依賴關係的步驟。"
            "只輸出計畫，【不要】現在執行任何步驟、不要呼叫工具。"
            "每步寫清楚：要做什麼、為什麼、產出是什麼。"
        ),
        messages=[{"role": "user", "content": big_task}],
    )
    return "".join(b.text for b in resp.content if b.type == "text")
```

這份計畫接下來有兩種用法：(a) **餵回執行階段的 context**，當作 agent 的「總綱」；(b) 更結構化地，把它**轉成一份 todo list**（下一節）讓進度可被追蹤。

為什麼「先規劃」值得單獨花一次呼叫？因為它把「想」和「做」分開了。在還沒動任何工具、還沒產生任何副作用之前，先逼模型把整條路講清楚——這時候發現「啊這任務其實要先做 X 才能做 Y」幾乎零成本；等做到一半才發現順序錯了，可能已經改壞了檔案。**規劃是最便宜的一次「想清楚」。**

> **規劃可以更結構化**：與其讓計畫是一段自由文字，不如要模型輸出**結構化的步驟清單**（例如 JSON 陣列，每項有 `step` / `depends_on` / `output`）。這樣計畫能被程式直接讀、直接轉成 todo、直接檢查依賴。這需要 Ch 32 的 structured output——本章先用純文字建立直覺。

## 二、Todo 管理：把計畫變成一份「活的」待辦清單

計畫是靜態的快照；真正對抗「做到哪了會忘」的是一份**會隨進度更新、且始終在 context 裡**的 todo list。實作上它就是一個工具，讓 agent 能「寫入/覆寫整份清單」，而每次寫入後，清單的最新狀態都會回到 context。

```python
# 一份極簡 todo 工具：agent 用它覆寫整份清單；harness 把清單狀態保存並回灌 context
# 註：ToolResult 沿用 Ch 21 / Practice C 的那個 dataclass（欄位 content + is_error），
#     harness 在回傳前會把它轉成 Messages API 的 tool_result content block（Ch 20）。
TODO_STATE: list[dict] = []   # 進程內保存目前清單（真實 harness 可能更講究）

TODO_SCHEMA = {
    "name": "write_todos",
    "description": (
        "建立或更新待辦清單。傳入完整清單（會整份覆寫）。"
        "用它在開始多步任務前列出步驟、並在每完成一步後更新狀態。"
        "規則：任何時候【最多一項】status 為 in_progress。完成一項就立刻標 completed。"
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "todos": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "content": {"type": "string", "description": "這一步要做什麼"},
                        "status": {
                            "type": "string",
                            "enum": ["pending", "in_progress", "completed"],
                        },
                    },
                    "required": ["content", "status"],
                    "additionalProperties": False,   # Ch 18：收緊 schema，不收計畫外的欄位
                },
            }
        },
        "required": ["todos"],
        "additionalProperties": False,
    },
}

def write_todos(todos: list[dict]) -> ToolResult:
    # harness 端強制不變條件：最多一項 in_progress（Ch 25 的精神——規則由 harness 守，不靠模型自律）
    in_progress = [t for t in todos if t["status"] == "in_progress"]
    if len(in_progress) > 1:
        return ToolResult(
            f"錯誤：同時有 {len(in_progress)} 項 in_progress，最多只能一項。請修正後重送。",
            is_error=True,
        )
    TODO_STATE[:] = todos                       # 整份覆寫
    rendered = render_todos(TODO_STATE)         # 把清單渲染成人看得懂的字串
    return ToolResult(rendered)                 # 回灌：清單最新狀態回到 context

def render_todos(todos: list[dict]) -> str:
    mark = {"completed": "[x]", "in_progress": "[>]", "pending": "[ ]"}
    return "\n".join(f"{mark[t['status']]} {t['content']}" for t in todos)
```

幾個設計要點，每個都呼應前面學過的原理：

- **整份覆寫，不是逐項 patch**。模型每次傳完整清單、harness 整份換掉。這比「改第 3 項的狀態」這種增量操作更不容易出錯，也讓「目前完整清單」永遠是單一事實來源。
- **不變條件由 harness 守**（Ch 25 的精神）。「最多一項 in_progress」這條規則，不是寫在 prompt 裡求模型自律，而是 harness 在 `write_todos` 裡**強制檢查**：違反就回 `is_error` 要它重送。模型自我約束會漂移，harness 強制不會。
- **工具回傳值要回灌 context**。`write_todos` 回傳渲染後的清單字串，這個 ToolResult 進到下一回合的 context——這就是「便利貼一直在眼前」的機制。如果寫完清單卻不回灌，模型下一回合照樣失憶。
- **描述（description）就是用法教學**(Ch 19)。schema 的 `description` 直接告訴模型「開始多步任務前列步驟、每完成一步更新、最多一項 in_progress」——工具描述是 prompt 的一部分，行為規範寫在這裡最有效。

> **這個 harness 的 TodoWrite 多了 `activeForm`**：除了 `content`（命令式，如「修正 token 過期 bug」），還有 `activeForm`（進行中字樣，如「正在修正 token 過期 bug」），讓進行中的項目顯示更自然。這是該 harness 的人性化設計細節，不是通用必需——核心仍是 content + status + 「最多一項 in_progress」。

## 三、Plan mode：唯讀規劃、人類核可後才動手

規劃還有一種更強的形態：**plan mode（計畫模式）**。它不只是「先想再做」，而是把「想」這個階段**用 harness 強制成唯讀**——agent 在 plan mode 裡可以讀檔、搜尋、跑唯讀的探索指令、產出計畫，但**不能執行任何有副作用的動作**（寫檔、改設定、跑會改變狀態的命令），直到把計畫呈給人類、人類核可後，才退出 plan mode 開始動手。換句話說：唯讀的「調查」放行，有副作用的「執行」被擋。

這是 Ch 25 權限模型的一個漂亮應用：

```
   使用者下達複雜/高風險任務
        │
        ▼
   ┌─ plan mode（harness 強制唯讀）──────────────────┐
   │  agent 可以：讀檔、grep、查資料、跑唯讀指令、想  │
   │  agent 不能：寫檔、改設定、任何有副作用的動作    │  ← 權限閘門擋住寫入類工具
   │  產出：一份計畫，呈給人類                        │
   └──────────────┬──────────────────────────────────┘
                  ▼
        人類審查計畫 ──→ 核可？
                  │             │
              否（修正）      是（核可）
                  │             ▼
                  └──────  退出 plan mode，開始執行
```

為什麼值得有這個模式？因為**對高風險或大型任務，「動手前讓人看一眼計畫」是最便宜的把關**。它在 Ch 25 「危險動作要人類核可」之上多加了一道**策略層的關卡**：人類先審「整個方案對不對」，而不是一上來就被一連串「可以寫這個檔嗎？」的瑣碎確認轟炸。注意這是「多一道把關」，不是「取代後面的把關」——核可計畫後，你仍可以選擇讓執行階段維持逐動作確認、或切到自動模式，顆粒度由你決定。而 harness 強制唯讀這點很關鍵：它保證 agent 在規劃期間**不可能**手滑改了東西，再多話的「我保證只看不改」prompt 都不如一道硬閘門。

> **你正在用的 session 就有 plan mode**：當任務複雜時，我可以進入 plan mode 做純調查、產出計畫、用 `ExitPlanMode` 把計畫呈給你核可，得到同意後才開始改東西。規劃期間我即使想寫檔也會被擋下。這是本 harness 把「先規劃後執行」做成一道安全閥的具體例子。

## 四、規劃 × 執行 × 委派：把本章接回前面

plan 和 todo 不是孤立的新東西，它們是把前面所有積木串起來的「指揮層」：

- **接 Ch 7（迴圈與停止條件）**：todo list 給貪心的迴圈一個全局錨點。「所有 todo 都 completed」也可以當成一種**停止條件**——清單清空，任務就完成了。
- **接 Ch 13（context 壓縮）**：todo list 是對抗 context 漂移的主力。即使早期對話被壓縮，「目前清單 + 哪項進行中」這個高密度摘要還在 context 裡，模型就不會忘記大局。某種意義上，一份好的 todo list 就是任務狀態的**抗壓縮摘要**。
- **接 Ch 26-27（subagent 與編排）**：計畫拆出來的步驟，正是可以**委派**出去的單位。「步驟 2、3、4 彼此獨立」就對應「fan-out 給三個 worker 並行跑」（Ch 27）。orchestrator-workers 的「拆解」動作，本質就是本章的「規劃」；它拆出的子任務清單，本質就是一份分給多個 worker 的 todo。**規劃決定了什麼能並行委派。**

一句話收束：**規劃決定「做什麼、什麼順序、什麼能並行」；todo 管理確保「做的過程中不迷路、進度看得見」；plan mode 確保「高風險任務動手前有人把關」。** 三者合起來，才讓 agent 撐得起長多步任務。

## 對比與取捨

| 設計選擇 | 選項 A | 選項 B | 怎麼選 |
|---|---|---|---|
| 何時規劃 | **先規劃後執行**（plan-then-act） | 邊想邊做（ReAct 式，不預先規劃） | 任務長/多步/高風險 → 先規劃；短任務 → 直接做，別過度規劃 |
| todo 放哪 | **放進 context（回灌）** | 存在外部、模型看不到 | 一定要回灌 context，否則模型下一回合就忘 |
| todo 更新 | **每完成一項立刻更新** | 做完一批再一次更新 | 立刻更新：進度才真實、使用者才即時看到 |
| 「最多一項進行中」由誰守 | **harness 強制** | prompt 求模型自律 | harness 強制（Ch 25 精神），自律會漂移 |
| 規劃格式 | 純文字計畫 | **結構化（可被程式讀）** | 要轉 todo / 檢查依賴 / 委派 → 結構化（Ch 32） |
| 高風險任務 | 直接動手、逐動作確認 | **plan mode：先核可整個計畫** | 大型/高風險 → plan mode 審策略，比逐動作確認省事又安全 |

## 踩雷集錦

1. **todo list 不回灌 context**：寫了清單卻不把最新狀態放回 context，模型下一回合照樣失憶、重做或漏做。便利貼要貼在眼前才有用。
2. **不更新或批次更新**：做完五件才一次性更新清單。中間若被中斷或壓縮，進度就對不上；使用者也看不到即時進展。**完成一項立刻標 completed。**
3. **同時多項 in_progress**：失去「專注一件、有順序」的意義，清單變成一團糊。靠 harness 強制「最多一項」，別靠模型自律。
4. **過度規劃小任務**：兩步就做完的事還先列六步計畫，純粹增加延遲與 token。規劃是給長/多步/高風險任務的，短任務直接做。
5. **計畫做完就丟、不追蹤**：規劃和執行脫節——列了漂亮計畫，執行時卻不照著、也不更新。計畫要變成活的 todo，才有意義。
6. **plan mode 名為唯讀、實際能寫**：如果 plan mode 沒有真正用權限閘門擋住寫入類工具，那它只是個 prompt 提醒，模型一樣可能手滑改東西。唯讀必須由 harness 硬性保證。
7. **把 todo list 當成給人看的報告**：堆一堆冗長描述、進度註解。它的首要讀者是**模型自己**——要短、要高密度、要一眼看出全局與當前項。

## 進階：再往深一層

- **計畫會變，要能改 plan**：執行到一半發現原計畫錯了（少了一步、順序要調），好的 agent 要能**更新計畫/todo**，而不是硬著頭皮照舊。這也是為什麼 todo 工具設計成「整份覆寫」——重新規劃就是重寫整份清單。把 replanning 當常態，不是例外。
- **巢狀 todo / 子任務分解**：大步驟底下還能再拆小步驟（樹狀）。但小心別過度——多數任務一層平面清單就夠，巢狀太深反而難追蹤。需要時才拆，且通常一層子清單就好。
- **todo 作為委派邊界**：當某個 todo 項夠大、夠獨立，它就是一個適合丟給 subagent 的單位（Ch 26）。「規劃 → 哪些 todo 可獨立 → fan-out」這條鏈，把本章和 Ch 27 直接縫起來。
- **plan mode 的退出契約**：plan mode 的核可是一個明確的「人類在迴圈裡」的關卡（human-in-the-loop）。進階做法是讓人類不只「核可/拒絕」，還能**編輯計畫**再核可——把人的判斷直接寫進 agent 的執行藍圖。
- **規劃品質可被評估**：一份計畫好不好（步驟完整嗎？順序對嗎？依賴抓對了嗎？）本身可以拿去評估甚至用另一個 agent 批評（evaluator-optimizer，Ch 27）。長任務的成敗，常常在第一份計畫就決定了——值得投資在「規劃得好」上。

## 動手練習

1. 實作第一節的 `make_plan`，給它一個多步任務（例如「為一個現有函式補上測試」），看它產出的步驟計畫。再把 `system` 改成「請直接開始執行」對照——體會「先想再做」和「邊想邊做」的差別。
2. 把第二節的 `write_todos` 工具接進你之前章節的 agent 迴圈。給一個 3-4 步的任務，觀察 agent 是否：開頭就列清單、每做一步更新、最後全部 completed。
3. **驗證不變條件**：故意讓模型送出兩項 `in_progress` 的清單（或手動構造），確認 `write_todos` 回 `is_error` 並要求重送。體會「規則由 harness 守」。
4. **不回灌的後果**：把 `write_todos` 改成不回傳清單內容（回個空字串），在長一點的任務上觀察模型是否開始重做或漏做步驟。親身感受「便利貼不在眼前」的失憶。
5. （概念）為一個你做過的真實任務，設計一個 plan mode 流程：列出「規劃期間只准用哪些唯讀工具」「計畫要呈現哪些資訊給人核可」「核可後才解鎖哪些寫入工具」。

## 本章重點整理

- 長多步任務有三個天敵：**只有下一步沒全局、做到哪會忘、使用者看不到進度**。規劃對付第一個，todo 管理對付後兩個。
- **規劃 = 動手前把大任務拆成有序、有依賴的步驟**。它是最便宜的一次「想清楚」，在產生任何副作用前先發現順序/依賴問題。
- **todo list 是 agent 的外部短期記憶**：必須**回灌 context**、**每完成一項立刻更新**、**最多一項 in_progress**（由 harness 強制）。它是對抗 Ch 13 context 漂移的抗壓縮任務摘要。
- **整份覆寫優於逐項 patch**；不變條件由 **harness 強制**（Ch 25 精神），不靠模型自律；工具 **description 就是用法教學**（Ch 19）。
- **plan mode = harness 強制唯讀的規劃階段 + 人類核可才動手**。對高風險/大型任務，審「整個策略」比被「逐動作確認」轟炸更省事也更安全。
- 規劃決定**什麼能並行委派**（接 Ch 26-27）；「所有 todo completed」可當**停止條件**（接 Ch 7）。短任務別過度規劃。
