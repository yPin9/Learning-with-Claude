# Ch 3 — 心智模型：loop + context + tools + policy

> **目標**：把前三章的觀察收斂成一個能套用到**任何** agent 系統的心智模型。讀完你拿到一張「拆解任何 harness 的座標圖」——看到任何 agent 框架、任何產品、任何 bug，你都能定位「這是 loop 的問題、context 的問題、tool 的問題、還是 policy 的問題」。

## 為什麼需要一個心智模型

Ch 0–2 你看了很多具體東西：API 欄位、tool_use、tool_result、stop_reason。但具體知識的問題是**會散**——下次你打開 LangGraph 或 Claude Agent SDK，欄位名稱全變了，你可能又覺得在學新東西。

好的心智模型是壓縮器：它把一堆具體現象壓成幾個一定存在的「角色」，之後不管外殼怎麼變，你都能一眼認出「喔，這是那個角色」。這章給你的模型是：

> **本課討論的這類 agent harness（會用工具、會自己迴圈的那種），幾乎都能用四格來分析：loop、context、tools、policy。**

說「幾乎都能」而不是「一定」：真實系統有的沒有明確的工具、有的 policy 是隱含在外部治理裡、有的 workflow 也有 context/tools 卻不算 agent。這張圖是**分析用的座標**，不是宇宙定律——它的價值在於「拿來拆解和定位問題很好用」，不在於「無一例外」。這四個詞會貫穿剩下 38 章，每一章本質上都在深化其中一塊。先把這張圖刻進腦子，後面所有內容都有地方可以掛。

## 先建立直覺：四個元件是一台「決策機器」的四個部位

把 harness 想成一台會自己幹活的機器。一台典型的這類機器，運轉時會用到四個部位：

```
            ┌─────────────────────────────────────────┐
            │                 HARNESS                   │
            │                                           │
            │   ┌─────────┐         ┌──────────────┐   │
   輸入 ───▶│   │ CONTEXT │ ──餵──▶ │     LOOP      │   │
            │   │ 該讓模型 │         │ 反覆呼叫模型  │   │
            │   │ 看到什麼 │ ◀─塞回─ │ 直到完成      │   │
            │   └─────────┘         └──────┬───────┘   │
            │        ▲                     │ 模型要工具  │
            │        │              ┌──────▼───────┐   │
            │        └──結果──────── │    TOOLS      │   │
            │                       │ 模型能做的事   │   │
            │                       └──────────────┘   │
            │   ┌───────────────────────────────────┐ │
            │   │ POLICY：什麼能做、要不要問人、安不安全 │ │ ← 罩在全部之上
            │   └───────────────────────────────────┘ │
            └───────────────────────────────────────────┘
```

- **LOOP** 是引擎：它讓「呼叫一次模型」變成「反覆呼叫直到任務完成」。沒有 loop，你只有 Ch 0 那種一問一答，不是 agent。
- **CONTEXT** 是它的視野：每次呼叫模型前，決定「這一輪要讓模型看到哪些東西」。視野決定判斷品質。
- **TOOLS** 是它的手腳：模型能請求的動作集合，以及這些動作的真實實作。
- **POLICY** 是它的價值觀與煞車：哪些事能自己做、哪些要先問人、怎麼防止被帶壞、怎麼知道它在正常運作。

接下來逐一拆，並把它對應回你已經在 Ch 0–2 看過的東西。

## 元件一：LOOP（引擎）

**它解決的問題**：模型一次 inference 只能走一步（Ch 1），但真實任務要走很多步（Ch 2 那個查天氣就走了兩回合，修 bug 走了五回合）。loop 負責把「一步」變成「一直走到完成」。

最小骨架其實短到驚人，就是一個 while：

```
while True:
    回應 = 呼叫模型(context)
    if 回應說「我做完了」(end_turn):
        break
    if 回應說「我要用工具」(tool_use):
        執行工具，把結果加進 context
    # 回到迴圈頂，帶著變長的 context 再問一次
```

你在 Ch 2 已經**手動**跑過這個迴圈的一圈半了——只是當時是你親手 append、親手再呼叫。Ch 4 我們把它寫成真的 `while`。

**loop 的工程深度在哪**：骨架很短，但要讓它在真實世界穩定，得回答一串問題——什麼時候該停（不能無限跑下去，Ch 7）？模型回應到一半斷線怎麼辦（Ch 9）？要不要邊跑邊把輸出串流給使用者看（Ch 8）？這些是 Part 1 的內容。

## 元件二：CONTEXT（視野）

**它解決的問題**：模型無狀態（Ch 1），所以每一輪你都得從零幫它組一份「它現在該知道的一切」。這份東西就是 context——它包含 system prompt、對話歷史、工具清單、工具結果、可能還有外部撈進來的資料。Ch 2 那份「不斷變長的 messages」就是 context 最核心的部分。

**為什麼這是整個 Part 2、是 harness 工程最難的一塊**：因為 context 有上限（context window），但任務產生的資訊會無止盡增長。於是每一輪都是一道取捨題：

```
   想塞進 context 的東西（永遠在膨脹）
   ┌──────────────────────────────────┐
   │ system prompt                     │
   │ 完整對話歷史（越來越長）           │ ──┐
   │ 每個工具的完整輸出（可能很巨大）   │   │ 塞不下！
   │ 撈進來的參考資料                  │   │ 必須取捨：
   │ 之前的工具結果（還需要嗎？）      │ ──┘ 壓縮？丟棄？摘要？
   └──────────────────────────────────┘
              │
              ▼  必須壓進這個固定大小的框
   ┌──────────────────────┐
   │   context window      │
   └──────────────────────┘
```

「給太少」模型缺資訊亂答，「給太多」又貴又慢、還可能讓模型抓不到重點（context 不是越多越好，這在 Part 2 會反覆出現）。怎麼在每一輪都組出「剛好夠用」的 context——壓縮歷史（Ch 13）、用 memory 把該記的存到 context 之外（Ch 14）、裁剪工具結果（Ch 16）——這就是 **context engineering**，Part 2 的全部。

> 你常聽到的「prompt engineering」——把指令寫好、組織範例、把工具描述寫清楚——在 agent 場景下，是「管理一份動態 context」的其中一個面向（system prompt 在 Ch 11、工具描述在 Ch 19）。但 agent 真正更大的挑戰，是「一份會隨時間長大、會撞上限的動態 context 怎麼管」，所以業界越來越用 **context engineering** 這個更大的詞，把 prompt engineering 視為它的一部分。

## 元件三：TOOLS（手腳）

**它解決的問題**：模型只會寫「我想做 X」（Ch 1、Ch 2 的 tool_use）。tools 這塊定義了「X 有哪些可能」（工具清單與其 schema），以及「模型要求時，怎麼真的把 X 做出來」（執行與分派）。

Ch 2 你已經看過一個工具的兩面：

```
   宣告面（給模型看的說明書）          執行面（harness 真的做的事）
   ┌────────────────────────┐         ┌──────────────────────────┐
   │ name: get_weather       │         │ def get_weather(city):    │
   │ description: 查天氣...   │  ◀對應▶ │     ... 真的去查 ...       │
   │ input_schema: {city}    │         │     return 結果            │
   └────────────────────────┘         └──────────────────────────┘
       模型靠這面決定要不要用、傳什麼      模型要求後 harness 跑這面
```

**為什麼這塊深到要一整個 Part 3**：工具的「宣告面」其實是寫給模型看的 prompt——`description` 寫得爛，模型就不會用、或用錯（Ch 19）。工具該回傳什麼、回多少（Ch 20）；檔案、shell 這些高頻工具怎麼設計（Ch 21–22）；工具多到模型挑不動時怎麼辦（Ch 23）；怎麼接別人寫好的工具（MCP，Ch 24）——全是 tool 設計的工程。一句話：**在很多產品化場景，工具設計的品質比換一個更強的模型，更能決定 agent 聰不聰明。**

## 元件四：POLICY（價值觀與煞車）

**它解決的問題**：前三個元件讓 agent「能動」，policy 決定「該不該這樣動」。一個能讀檔、能跑 shell、能自己迴圈的 agent，如果沒有 policy，等於一把沒有保險的槍。

policy 不是單一個地方，它**橫切**在另外三個元件之上：

| policy 的面向 | 它管什麼 | 在哪一章 |
|---|---|---|
| Permission（權限） | 哪些工具能自己用、哪些要先問人類核准 | Ch 25 |
| 安全 | 怎麼防 prompt injection、惡意工具結果把 agent 帶歪 | Ch 36 |
| 停止與上限 | 最多跑幾輪、花多少 token 就該收手 | Ch 7、Ch 37 |
| 可觀測與評估 | 怎麼知道它有沒有正常運作、改了之後變好還變壞 | Ch 34、Ch 35 |

注意 policy 不只是「安全」——它涵蓋所有「該不該、值不值、好不好」的治理面：成本上限（別讓一個任務燒掉幾十塊美金）、品質把關（怎麼知道改了之後變好還變壞）、可觀測（出事能不能追查）、產品邊界（這個 agent 該不該碰這件事），安全只是其中之一。

**為什麼初學者最容易漏掉這塊**：因為前三塊不做，agent 根本跑不起來，你被迫面對；但 policy 不做，agent 「看起來」也會動——直到它在生產環境刪錯檔、悄悄燒掉大筆 token、把 API key 印進 log、被一段惡意網頁內容騙去做壞事，而你連發生了什麼都查不到。policy 是「平常感覺不到、缺了它遲早出事」的那種東西。好的 harness 工程師從一開始就把它放在心上，這也是為什麼這門課 Part 5 整個在談可靠性、成本與安全。

## 用這張圖回看 Ch 2

驗證一下這個模型有沒有用。把 Ch 2 那次查天氣的執行，用四元件重新標一遍：

- **LOOP**：你手動跑的「送請求 → 看 stop_reason → 執行 → 再送」就是 loop 的一圈半。
- **CONTEXT**：那份不斷 append、越來越長的 `messages`，加上每次都帶的 `tools`。
- **TOOLS**：`get_weather` 的 schema（宣告面）＋ 那個回傳假資料的 Python 函式（執行面）。
- **POLICY**：Ch 2 **幾乎沒有** policy——我們無條件執行了模型要求的工具，沒問過任何人、沒設上限。在「查天氣」這種無害情境沒差，但如果工具是 `delete_file`，你就會立刻想要 policy。這個「缺了什麼」的感覺，正是 Part 3、Part 5 要補的。

能這樣四個一一對上，代表這個心智模型你拿到了。

## 對比：這個模型和你聽過的其他講法

市面上對 agent 的拆法很多，這裡澄清它們和本課模型的關係，免得你混淆：

| 別處的講法 | 對應到本課的哪塊 | 說明 |
|---|---|---|
| 「Agent = LLM + memory + tools + planning」 | memory→context、tools→tools、planning→loop + context | 大同小異。planning（規劃下一步）主要靠 loop 的控制策略，並由 context/prompt 承載；本課額外把 **policy** 獨立出來，因為它正是這類拆法最常漏掉的治理面 |
| ReAct（Reason + Act + Observe） | 是 LOOP 的一種常見 **pattern** | ReAct 不只是個 while——它規定模型要交錯產生推理（reason）與動作（act），並把工具觀察（observe）回填進 context 影響後續推理。所以它同時牽涉 loop 的節奏與 context 的軌跡格式，是 loop 這格裡一個成熟的選擇 |
| 「Prompt engineering」 | 偏 CONTEXT 的一部分 | prompt engineering 是「寫好並組織給模型的指令／範例／工具描述」；在 agent 場景，這只是「管理一份動態 context」的一個面向。context 比它大得多（見下方說明） |

重點不是哪個拆法「對」，而是**有一個你用得順、能拿來定位問題的模型**。本課用 loop / context / tools / policy，是因為它正好對應到你 debug 時會問的四個問題：「迴圈轉對了嗎？模型看到對的東西了嗎？工具給對了嗎？它被允許這樣做嗎？」

## 踩雷集錦

1. **把四元件當成四個獨立模組**：它們會互相滲透。例如「工具回傳太多東西」既是 tool 設計問題（Ch 20），也立刻變成 context 問題（Ch 16 要裁剪它）。這個模型是**分析用的座標**，不是程式碼的資料夾結構。別硬把它對應成四個 class。
2. **以為 loop 很簡單所以不重要**：骨架簡單 ≠ 不重要。loop 是其他三塊的時間軸——context 在每一圈被重組、tool 在每一圈被呼叫、policy 在每一圈被檢查。它簡單，但它是節拍器。
3. **太晚才想 policy**：「先做出能動的，安全之後再加」是最常見也最危險的順序。等 agent 已經能跑 shell 了才想權限，往往要打掉重練。哪怕第一版只是「危險工具先全部停下來問我」，也比沒有強。
4. **以為 context 就是 prompt engineering**：prompt engineering 偏靜態（把一段指示寫好）；agent 的 context 是動態的、每輪在變的、會撞上限的。用舊的 prompt engineering 直覺去想 agent context，會低估它的難度。
5. **「換更強的模型就能解決」**：換模型確實會影響行為——更強的模型通常更會利用 context、更會挑對工具、更守規矩。但它**不會自動修好** harness 在 context、tool、loop、policy 上的設計問題：如果你工具描述寫得爛、context 組得亂、loop 沒正確處理 stop_reason，再強的模型也施展不開，甚至可能放大你的設計缺陷。先用這張圖定位問題出在哪一格，再決定要不要動模型——很多時候，改 harness 比換模型有效得多。

## 進階：再往深一層

- **這個模型怎麼擴展到 multi-agent**：當你有多個 agent（Part 4），每個 agent 各自有自己的 loop / context / tools / policy。在「協調者本身也是一個 model-owned agent」的情況下，它的「tools」就是「呼叫其他 agent」——這時 multi-agent 常可視為這張圖的**遞迴套疊**。但不是所有 multi-agent 都長這樣：有些是固定路徑的 workflow（協調者其實是你寫死的程式，不是 agent，例如 Anthropic 講的 orchestrator-workers）、有些把子 agent 當成一個外部服務而非工具。先記住「遞迴套疊」這個好用的視角，Ch 26、Ch 27 會把這幾種型態分清楚。
- **框架其實是在「四格」上做選擇**：之後你看任何 agent 框架，可以直接問：它的 loop 長怎樣、能不能自訂？它怎麼管 context、有沒有自動壓縮？它的 tool 怎麼註冊？它的 policy（權限、安全）給了哪些 hook？Ch 40 的框架對比就是照這四格逐一比。先有這張表，你看框架文件會快非常多。

## 動手練習

不用寫 code：

1. 拿一個你用過的 agent 產品（Claude Code、Cursor、某個 chatbot 都行），試著把它的行為拆進四格：它的 loop 大概怎麼跑？它怎麼決定讓模型看到什麼（context）？它有哪些工具？你有沒有觀察到任何 policy（例如它做危險操作前會問你）？
2. 回想你用 agent 時遇過的一次「它表現很爛」的經驗，用這張圖判斷：那比較像 loop、context、tool、還是 policy 的問題？
3. 不看本章，把四個元件各用一句話寫下來，並各舉一個 Ch 2 裡的具體對應。寫得出來，Part 0 就畢業了。

## 本章重點整理

- 任何 agent harness 都能拆成四格：**LOOP**（反覆呼叫模型的引擎）、**CONTEXT**（每輪讓模型看到什麼）、**TOOLS**（模型能請求的動作及其執行）、**POLICY**（能不能做、要不要問人、安不安全）。
- 這四格正好對應本課四個 Part，也對應你 debug agent 時該問的四個問題。
- 它們互相滲透，是分析用的座標，不是程式的資料夾。
- 換模型會影響行為，但不會自動修好 context / tool / loop / policy 的設計問題；多數 agent 瓶頸在這些設計上，不在模型本身。
