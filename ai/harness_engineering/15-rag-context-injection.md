# Ch 15 — RAG 與 context 注入

> **目標**：搞懂 RAG（Retrieval-Augmented Generation，檢索增強生成）在 harness 裡到底是什麼、解決什麼、怎麼把檢索到的內容注入 context。讀完你能說出 RAG 的「檢索 → 注入」骨架、embedding 檢索的直覺、chunk 怎麼切、注入該放哪、為什麼「檢索品質」遠比「塞得多」重要，以及 RAG、長 context、agentic search 三者怎麼選。

> **環境**：Python 3.11。本章概念為主，向量檢索用簡化示意；重點是「在 harness 裡怎麼用 RAG」，不是手刻一個 production 向量資料庫。

## 為什麼 agent 需要 RAG

Ch 14 解決了「agent 自己累積的筆記」。但有一類東西不是 agent 自己產生的，而是**一大批你預先準備好的外部知識**——公司的內部文件、產品手冊、一整個 codebase、法規條文、知識庫。它們有兩個特徵讓 agent 沒辦法「直接知道」：

1. **模型沒被訓練過**：這些是你私有的、或比模型訓練資料更新的內容，模型本身不知道。
2. **量遠超 context window**：可能是幾千份文件、幾百萬字——Ch 10 講過，全部塞進 context 既不可能（撐爆）也不該（context rot、貴）。

RAG 的核心想法很簡單：**不要把整個知識庫塞給模型，而是在需要時「檢索」出最相關的一小撮片段，只把那一小撮「注入」進 context。** 就像你不會把整個圖書館搬到書桌上，而是查目錄、抽出相關的幾本、翻到相關的幾頁。

## 先建立直覺：RAG = 開卷考試的「先翻書再作答」

把模型想成一個聰明但記性有限的考生。閉卷考（沒有 RAG）時，它只能靠腦中記得的（訓練知識）作答，碰到沒讀過的私有知識就會瞎掰（幻覺）。RAG 把它變成開卷考：

```
   使用者問題：「我們公司的退費政策是幾天？」
        │
        ▼
   ① 檢索（retrieve）：拿問題去知識庫找最相關的片段
        │   找到：退費政策文件第 3 段「…自購買日起 14 天內…」
        ▼
   ② 注入（inject）：把找到的片段放進 context
        │   context 現在包含：問題 + 那段政策原文
        ▼
   ③ 生成（generate）：模型根據「翻到的那頁」回答
        │
        ▼
   「根據退費政策，自購買日起 14 天內可申請退費。」
```

關鍵洞察：**模型的「智能」沒變，變的是它手邊有沒有對的資料**。RAG 不讓模型更聰明，它讓模型**有據可查**——把「靠記憶瞎猜」換成「翻到正確的那頁再回答」。這在「檢索正確、注入邊界清楚」時能降低幻覺：模型答的是它眼前的片段，不是腦中模糊的記憶。但要誠實說——這是有條件的：如果檢索撈回的是**錯的或無關的**片段，RAG 反而可能讓幻覺**更糟**（模型很有自信地引用了錯誤的素材）。所以「RAG 降低幻覺」的前提，是後面會反覆強調的檢索品質。

## 一、檢索：怎麼從一大堆文件裡找到「相關的」

「檢索」的難點是：使用者問「退費幾天」，但文件裡寫的是「自購買日起 14 日內得申請退款」——**字面不一樣，意思一樣**。傳統關鍵字搜尋（找「退費」這個詞）會漏掉寫成「退款」的那段。RAG 主流用 **embedding（嵌入）+ 向量檢索**來解決這個「意思相近但字面不同」的問題。

直覺：embedding 是把一段文字轉成一個**座標**（一個高維向量），讓「意思相近的文字」在座標空間裡**靠得近**。

```
   把每段文字變成空間中的一個點（語意相近 → 距離近）

        「退款 14 日」 ●
                       ● 「退費政策」      ← 這幾個擠在一起（語意相近）
        「purchase refund」 ●
                                          ● 「今天天氣」  ← 離很遠（語意無關）
```

檢索流程因此變成：

```python
# 概念示意（非完整實作）
# --- 準備階段（一次性，離線做）---
for chunk in 所有文件切成的片段:
    vector = embed(chunk)          # 把每個片段轉成向量
    vector_db.store(chunk, vector) # 存進向量資料庫

# --- 查詢階段（每次使用者提問）---
def retrieve(query, top_k=5):
    q_vector = embed(query)                    # 把問題也轉成向量
    return vector_db.search(q_vector, top_k)   # 找座標最近的 top_k 個片段
```

`embed()` 是呼叫一個 embedding 模型——注意 **Anthropic 沒有自家的 embedding 模型**，官方文件建議用第三方（例如 Voyage AI，以及 OpenAI、Cohere、開源的 sentence-transformers 等都可以）。所以別期待「Claude embeddings」這種東西，embedding 這一塊你會接外部供應商。`vector_db` 則是專門的向量資料庫（Pinecone、Weaviate、pgvector、Chroma…）。**你幾乎不會自己刻這兩塊**——重點是理解「文字 → 向量 → 找最近鄰」這個流程在做什麼，這樣你才知道檢索為什麼有時找錯、怎麼調。

> 純向量檢索不是萬靈丹。它擅長「語意相近」，但對「精確匹配」（產品型號、錯誤碼、人名）有時反而不如關鍵字搜尋。所以實務上常用 **hybrid search**（向量 + 關鍵字混合），兼顧語意與精確。知道有這回事，遇到「向量檢索老是找不到某個精確詞」時就知道往這想。

## 二、chunk：怎麼把文件切成片段

檢索的單位是「片段（chunk）」，不是整份文件——因為你要注入的是「相關的那一小段」，不是整份手冊。怎麼切，直接影響檢索品質：

- **切太大**（例如整章當一個 chunk）：檢索回來的片段裡，相關的句子被一堆無關內容稀釋，注入後低訊噪比（Ch 10 的 context rot 又來了）。
- **切太小**（例如每句一個 chunk）：可能切斷了語意——一個完整的說明被拆成幾片，每片單獨看都不完整，檢索回來缺乏脈絡。
- **剛好**：通常以「語意完整的段落」為單位，常見做法是固定大小（例如幾百 token）+ 重疊（overlap，相鄰 chunk 共享一小段，避免邊界切斷語意）。

```
   文件：[==================== 一大段 ====================]

   切成有重疊的 chunk：
   [chunk1======]
            [chunk2======]     ← 相鄰 chunk 有重疊（overlap），
                     [chunk3======]  避免關鍵句剛好被切在邊界

```

沒有萬用的 chunk 大小——它取決於你的文件結構和查詢類型。但原則和 Ch 10 一致：**目標是讓每個檢索回來的 chunk 訊噪比高**，相關的密、無關的少。

## 三、注入：檢索到的內容放進 context 的哪裡

檢索回來的片段，要放進 context 才有用。放哪裡、怎麼包裝，是 harness 的決定：

```
   常見的注入位置：

   做法 A：放進當前 user 訊息（最常見）
   user: "根據以下參考資料回答問題。
          [參考資料]
          <檢索到的 chunk 1>
          <檢索到的 chunk 2>
          [問題] 我們的退費政策幾天？"

   做法 B：作為一個「檢索工具」的 tool_result（agentic RAG）
   模型自己決定「我需要查資料」→ 呼叫 search 工具 → 結果以 tool_result 注入
```

兩種做法對應兩種架構哲學：

- **做法 A（檢索前置）**：harness 在呼叫模型**之前**就先檢索、把結果塞進 prompt。模型被動接收。簡單、可控，適合「每個問題都需要查知識庫」的場景（如客服問答）。
- **做法 B（agentic RAG）**：把「檢索」做成一個工具（Ch 4–5），**讓模型自己決定何時查、查什麼**。模型可能查一次不夠再查、或換個查詢詞重查。更靈活、更接近 agent 的精神，但較複雜、較貴（多幾輪）。

注入時的幾個要點：

- **標示清楚這是「參考資料」**：用 `[參考資料]` 之類的標記框起來，讓模型知道「這是我查到的、可以引用的素材」，而不是使用者的指令（呼應 Ch 13 的邊界標記、Ch 36 的注入防護）。
- **附上來源**：每個 chunk 註明它來自哪份文件/哪一段。這讓模型能在回答裡**引用出處**（citation），使用者就能驗證、也降低你對幻覺的疑慮。
- **別注入太多**：檢索回 5 個 chunk 不代表 5 個都要注入——這就是下一節。

## 四、檢索品質 >> 注入數量（這章最重要的一句）

新手做 RAG 最常見的錯誤，是以為「檢索回來越多片段，模型答得越好」，於是 `top_k=50`，把一大堆片段全塞進 context。這幾乎總是錯的，理由就是 Ch 10 講過的：

- 塞太多 → 貴、慢、context rot，相關的那一兩段被淹沒在一堆「也許相關」的片段裡。
- 而且檢索是有雜訊的——`top_k=50` 裡可能只有前 3 個真正相關，後 47 個是噪音，注入它們只會干擾模型。

**正確心態：RAG 的成敗在「檢索的精準度」，不在「注入的數量」。** 與其塞 50 個普通相關的，不如想辦法讓最相關的少數幾個排在最前面、只注入那幾個。提升檢索精準度的手段（hybrid search、rerank、更好的 chunking）比「多塞幾個」有效太多。

要注意「注入幾個」**沒有萬用的魔術數字**——它該由 eval（Ch 34）決定，依你的資料、chunk 大小、查詢類型而定。事實上 Anthropic 的 Contextual Retrieval 實驗裡，注入到前 20 個 chunk 在他們的設定下表現最好；但同一篇也警告「更多 chunk 會分散注意力」。所以重點不是記住某個數字，而是記住**方向**：寧可精排出最相關的，也不要無腦塞一大堆——具體幾個，量出來。

```
   ❌ 大力出奇蹟              ✅ 精準打擊
   top_k 開很大，全注入       多撈一些候選 → rerank 重排 → 只注入最相關的前幾個（數量靠 eval 定）
   貴、慢、訊號被淹沒          便宜、快、訊噪比高
```

> **rerank（重排）** 是個值得知道的進階手段：向量檢索先撈回較多候選（例如 20 個），再用一個更精準（但較慢）的 rerank 模型把它們重新排序，只取最頂端的幾個注入。「先粗篩、再精排」是提升檢索品質的常見兩段式做法。

## 五、RAG vs 長 context vs agentic search：怎麼選

現在模型的 context window 越來越大，有人問：「window 這麼大了，我直接把所有文件塞進去不就好了，幹嘛還要 RAG？」這是個好問題，答案是「看情況」：

| 方法 | 怎麼做 | 適合 | 不適合 |
|---|---|---|---|
| **長 context（全塞）** | 把所有相關文件直接放進 context | 文件總量不大（塞得下且不貴）、需要跨全文推理 | 知識庫巨大、成本敏感、訊噪比低 |
| **RAG（檢索注入）** | 檢索相關片段再注入 | 知識庫遠超 context、要控成本、答案集中在少數片段 | 答案需要綜合大量分散片段、檢索品質難保證 |
| **Agentic search** | 給 agent 搜尋工具，讓它自己反覆查 | 任務開放、需要多步探索、查詢條件要動態調整 | 簡單問答（殺雞用牛刀、貴） |

幾個判斷原則：

- **量**：知識庫塞得進 context 且不貴 → 可以考慮全塞（省去 RAG 的複雜度與檢索風險）。塞不下 → RAG 或 agentic search。
- **訊噪比**：就算塞得下，如果裡面只有一小段相關、其餘是噪音，RAG 的「只注入相關」反而讓模型表現更好（Ch 10）。「塞得下」不等於「該全塞」。
- **互動性**：答案藏在哪不確定、要邊查邊調整 → agentic search（做法 B）比一次性檢索（做法 A）強。

實務上這三者也會混用。重點是別把 RAG 當成唯一解或過時技術——它和長 context 是**互補的工具**，依「量 × 訊噪比 × 互動性」三軸選擇。

## 失敗示範：把整個知識庫塞進去，或檢索回一堆噪音

**失敗一：仗著 context 大，全塞。**

```python
# 反例：把 200 份文件全塞進 context
all_docs = load_all_200_documents()   # 假設剛好塞得下
messages = [{"role": "user", "content": f"{all_docs}\n\n問題：退費幾天？"}]
```

就算塞得下、錢也付得起，結果常常是：模型在 200 份文件裡**找不準**那一句退費政策，被無關內容干擾，答得比「只注入相關那一段」還差（context rot，Ch 10）。而且每次提問都重送 200 份文件，貴得離譜。**「塞得下」是能力問題，「該不該全塞」是品質與成本問題，兩者不一樣。**

**失敗二：檢索品質差，注入一堆噪音。**

`top_k=30` 但檢索器很爛，撈回來的 30 段裡只有 2 段相關。模型被 28 段噪音帶偏，答案東拼西湊甚至幻覺。**這時該先修的是「檢索精準度」（chunking、hybrid、rerank、甚至換更好的 embedding 模型），而不是第一步就去換生成模型或在 prompt 上瞎調。** 很多人 RAG 效果差，根因在檢索那一端——當然，檢索修好之後，更好的 reranker 或生成模型也可能再加分；但順序是「先確認檢索餵對東西，再談生成端」。方向別反了。

## 踩雷集錦

1. **以為注入越多越好**：`top_k` 開很大全塞，貴、慢、訊號被噪音淹沒。RAG 成敗在檢索精準度，不在注入數量。
2. **chunk 切太大或太小**：太大訊噪比低，太小切斷語意。以語意完整段落為單位、適度重疊。
3. **純向量檢索碰精確匹配就瞎**：型號、錯誤碼、人名這種精確詞，向量檢索可能漏。用 hybrid（向量 + 關鍵字）。
4. **不標來源、不框參考資料**：注入的片段沒標 `[參考資料]` 邊界，模型可能誤當指令（注入風險，Ch 36）；不附來源，模型無法引用、你無法驗證。
5. **把 RAG 和 memory 搞混**：memory 是 agent 自己寫的筆記（Ch 14）；RAG 是取用外部既有的大知識庫。一個是「我記下的」，一個是「我查到的」。
6. **RAG 效果差就怪模型**：多數 RAG 問題的根因在檢索端（chunking、檢索器、rerank），不在生成端。先量檢索回來的東西對不對，再動模型和 prompt。
7. **盲目相信「context 夠大就不用 RAG」**：window 大不代表該全塞——訊噪比和成本仍然重要。依「量 × 訊噪比 × 互動性」選。

## 進階：再往深一層

- **評估檢索品質，而不只是最終答案**：RAG 系統要分兩段評估——「檢索」對不對（撈回來的片段含不含正確答案？）和「生成」對不對（給了正確片段後模型答得對嗎？）。把這兩段分開量，你才知道問題出在哪端。常用指標如檢索的 recall/precision。這是 Ch 34（eval）在 RAG 上的具體化。
- **agentic RAG 的威力**：做法 B（讓模型自己查）能做到做法 A 做不到的事——模型查了一次發現不夠，**改寫查詢詞再查**、或根據第一次結果決定下一步查什麼。這把「檢索」從一次性動作變成 agent 的一個能力，特別適合複雜研究型任務（Part 4 的 multi-agent research 大量用這個）。代價是多輪、較貴。
- **RAG 與 Anthropic 的相關能力**：Anthropic 提供了一些跟「讓模型取用外部資料」相關的能力，其中 **Citations** 最呼應本章「附上來源」的主張。但要講精確：citations 不是「對 prompt 裡任意文字或工具輸出施魔法自動標引用」——它是當你把來源以**支援的 document / search-result 區塊**傳入、並開啟 `citations.enabled` 時，模型能在回答裡標注「這句話引用了那份來源的哪個位置」。也就是說，可驗證是建立在「你用正確格式把來源餵進去」之上的。用到時看官方 citations 文件的格式要求。
- **「檢索」不一定要向量**：別被「RAG = 向量資料庫」綁死。對結構化資料，最好的「檢索」可能是一句 SQL；對 codebase，可能是 grep / 符號搜尋。把「檢索」理解成「用對的方式找出相關片段」這個抽象，工具按資料型態選——這跟 Part 3 的工具設計直接相關。

## 動手練習

1. （概念）拿一個你熟悉的問答情境（公司 FAQ、產品手冊），畫出它的 RAG 流程：知識庫是什麼、怎麼 chunk、使用者問題怎麼檢索、注入到哪、模型怎麼答。不寫 code，先把資料流想清楚。
2. 用任一個現成的 embedding 函式庫（如 sentence-transformers）+ 一個小文件集，做一個最小檢索：把問題和文件都 embed，算餘弦相似度，看「語意相近但字面不同」的問題能不能撈到對的段落。
3. 故意做「失敗二」：把 `top_k` 開很大、混入一堆無關文件，觀察注入噪音後答案怎麼變差。再縮小 top_k、只留最相關的，對比。
4. 把做法 A（檢索前置）改成做法 B（agentic RAG）：把檢索包成一個 `search_docs` 工具（Ch 4–5）給 agent，讓它自己決定何時查、查什麼，觀察它會不會「查一次不夠再查一次」。
5. （設計題）給你的場景判斷該用長 context、RAG、還是 agentic search？用「量 × 訊噪比 × 互動性」三軸論證你的選擇。

## 本章重點整理

- RAG = 不把整個知識庫塞給模型，而是「檢索」最相關的片段、只「注入」那一小撮——開卷考的「先翻書再作答」。
- 檢索主流用 embedding + 向量檢索（語意相近 → 座標相近）；精確匹配場景要搭 hybrid（向量 + 關鍵字）。
- chunk 大小影響檢索品質：以語意完整段落為單位、適度重疊，目標是高訊噪比。
- 注入要標 `[參考資料]` 邊界、附來源（可引用、可驗證）；放當前 user 訊息（前置）或做成檢索工具（agentic RAG）。
- **這章最重要的一句**：RAG 成敗在「檢索精準度」，不在「注入數量」——與其無腦塞一大堆，不如精排出最相關的少數幾個（具體幾個靠 eval 定，沒有魔術數字）。
- RAG / 長 context / agentic search 是互補工具，依「量 × 訊噪比 × 互動性」選；window 大不代表該全塞。
- RAG（查外部既有知識）與 memory（agent 自己的筆記）是不同東西，別混。
