# Ch 12 — 訊息歷史的成長與成本

> **目標**：把「歷史會長大」這個 Ch 6 看到、Ch 10 量化過的問題，做一次徹底的**解剖**。讀完你能：instrument 一段真實對話、按訊息類型拆出 token 佔比、指認出成長的真正元兇、並看懂管理歷史的四種策略各自的取捨——為 Ch 13 動手壓縮做好準備。

> **環境**：Python 3.11、`anthropic` Python SDK（最新版），延續前面的 `Agent` 與 `count_tokens`（Ch 10）。

## 為什麼要先解剖，而不是直接壓縮

很多人一聽到「歷史太長」就想「那就砍掉舊訊息」。這往往砍錯地方。真實情況是：歷史裡不同類型的內容，**成長速度和可丟棄性天差地遠**。沒先量過就動手砍，你可能砍掉了模型還需要的關鍵指令，卻留著一坨早就沒用的巨大工具輸出。

這章不寫壓縮演算法（那是 Ch 13）。它教你先當**法醫**：把一段膨脹的歷史攤開，量出「到底是誰在長、長多快、哪些其實可以丟」。有了這份解剖，Ch 13 的壓縮才是「精準手術」而不是「亂砍一通」。這呼應 Ch 10 的核心精神——**先量化，再決策**。

## 先建立直覺：歷史是「會自己長大的帳本」

回到 Ch 6 的等式：agent 的記憶 = messages 這個 list。Ch 10 告訴你它的成本是 O(N²)。把這兩件事合起來，歷史就像一本**每筆交易都會被重新抄寫一次的帳本**——每多一輪，整本帳要重抄重送一遍。

但帳本裡的「條目」不是均質的。有的條目小（使用者一句話）、有的條目巨大（一個讀檔工具吐回整份文件）。膨脹的元兇通常不是「條目變多」，而是「某幾條特別肥的條目」。

```
   一段跑了幾輪、用了工具的歷史，按 token 拆開大概長這樣：

   user: "幫我分析這個 log 檔"        ▓ 12 tokens
   assistant: "我來讀檔" + tool_use   ▓▓ 30 tokens
   user: tool_result（整個 log 檔！）  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 8000 tokens ← 元兇
   assistant: "我看到 3 個錯誤..."     ▓▓▓ 120 tokens
   user: "第二個怎麼修"                ▓ 8 tokens
   assistant: ... + tool_use          ▓▓ 40 tokens
   user: tool_result（又一個大檔）     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 5000 tokens ← 元兇
   ...
```

肉眼就看得出：那兩個 `tool_result` 佔了絕大部分。**在許多會讀檔、查資料、呼叫 API 的 tool-using agent 裡，工具結果常常是歷史膨脹的頭號元兇。** 但這不是鐵律——別的 harness 裡，元兇也可能是使用者貼進來的長文件、RAG 撈回的大段參考資料、囉嗦的模型輸出、或龐大的工具 schema / system prompt。所以別只憑直覺假設，我們來量——量完才知道你這個 agent 的肥肉到底在哪。

## 一、instrument：把歷史按類型拆開量

寫一個小工具，走過 `messages`，按「訊息類型」分類統計 token。這是你 debug context 問題時最常用的一招：

```python
from anthropic import Anthropic

client = Anthropic()
MODEL = "claude-opus-4-8"

def _count(content) -> int:
    """用 count_tokens 量一小段內容的 token（粗略但夠用於分析）。"""
    # 把單一訊息包成一個合法 messages 去量；實務上也可用本地 tokenizer 估
    return client.messages.count_tokens(
        model=MODEL,
        messages=[{"role": "user", "content": content if isinstance(content, str) else content}],
    ).input_tokens

def analyze_history(messages) -> dict:
    """按類型統計歷史的 token 佔比。"""
    buckets = {"user_text": 0, "assistant_text": 0, "tool_use": 0, "tool_result": 0}
    for m in messages:
        content = m["content"]
        if isinstance(content, str):
            key = "user_text" if m["role"] == "user" else "assistant_text"
            buckets[key] += _count(content)
            continue
        for block in content:
            btype = block["type"] if isinstance(block, dict) else block.type
            if btype == "text":
                key = "user_text" if m["role"] == "user" else "assistant_text"
                buckets[key] += _count(_text_of(block))
            elif btype == "tool_use":
                buckets["tool_use"] += _count(_json_of(block))
            elif btype == "tool_result":
                buckets["tool_result"] += _count(_content_of(block))
    return buckets
```

（`_text_of` / `_json_of` / `_content_of` 是把 block 取出**可量的實際內容**的小幫手，依你存 dict 還是 SDK 物件而定。特別注意 `_content_of(tool_result)` 要取出工具回傳的那段 payload 去量，**不要**直接 `str(整個 block)`——後者可能夾帶 SDK 物件的 metadata、或漏掉巢狀內容，量出來的數字會失真。重點是分類邏輯與「量對東西」，不是這幾個 helper 怎麼寫。）

**先講清楚這個工具的定位**：它是**歸因（attribution）**用的——回答「token 大致花在哪一類」，幫你找肥肉。它**不是**精確會計：逐則呼叫 `count_tokens` 並不可加（每次呼叫都含訊息/包裝的固定 overhead），而且為了量測方便把每段都包成 user 訊息去算，對 assistant 文字、`tool_use` 區塊、`tool_result` 的 wrapper（含 `tool_use_id`）等都只是近似。所以各 bucket 加起來**不會**等於對整份請求做一次 `count_tokens` 的精確值。要的是「比例、誰最肥」，不是「分毫不差的帳」。

跑在一段真實對話上，你會得到類似：

```
{'user_text': 180, 'assistant_text': 920, 'tool_use': 240, 'tool_result': 13500}
```

在這個例子裡數字會說話：`tool_result` 佔了 90% 以上。**那就是你該動手的地方**，而不是去砍那些加起來才幾百 token 的使用者問句和模型回答。（換個 agent，元兇可能換人——重點是你量過、知道是誰。）

> 為什麼要分這麼細？因為不同類型對應**不同的處理策略**（下一節）。使用者的問題通常要保留（連貫性）、模型的關鍵結論要保留、但工具結果在「被用過、結論已經產出」之後，往往可以大幅裁剪或丟棄。先分類，才能差別對待。

## 二、歷史裡的「住戶」與它們的成長性

把 Ch 6 那張「住戶表」加上「成長性」這個維度，你就有了一張決策地圖：

| 住戶 | 單筆大小 | 成長性 | 之後的價值 | 處理傾向 |
|---|---|---|---|---|
| 使用者問題 | 小 | 隨輪數線性 | 高（後續可能引用） | 通常保留 |
| 模型回應文字 | 中 | 隨輪數線性 | 中高（連貫性、結論） | 保留結論，中間思考可摘要 |
| tool_use 請求 | 小 | 隨工具呼叫數 | 中（要跟 result 配對） | 跟對應 result 一起處理 |
| **tool_result** | **常常巨大** | **隨工具呼叫數，且單筆可能很大** | **用過後常驟降** | **裁剪/摘要/丟棄的頭號目標** |

關鍵洞察集中在最後一行：**tool_result 的「當下價值」和「事後價值」落差最大**。一個讀檔工具回傳的 8000-token 內容，在模型「讀它、得出結論」的那一輪價值極高；但結論產出之後，那 8000 token 原文留在歷史裡，後續每一輪都要重送、卻幾乎不再被用到。這個「高當下價值、低事後價值」的特性，讓它成為壓縮的首要目標——你不是在丟有用的東西，是在丟「已經榨乾價值的東西」。

## 三、管理歷史的四種策略（選單，不是演算法）

知道了「該動 tool_result、以及部分中間內容」之後，有哪些手段？這裡先給**策略選單**與各自取捨，具體實作分散在後面幾章：

```
   策略一：截斷（truncate）
   做法：直接丟掉最舊的 N 則（或最舊的若干 token）
   優點：實作最簡單
   缺點：粗暴——可能丟掉舊但重要的指令；要小心別破壞 tool_use/result 配對與角色交替（Ch 6）
   適合：對「久遠歷史不重要」的場景（如純閒聊）

   策略二：摘要（summarize / compaction）   ← Ch 13 主題
   做法：把一段舊歷史交給模型濃縮成一則短摘要，用摘要取代原文
   優點：保留語意、大幅縮小；不像截斷那樣硬丟資訊
   缺點：摘要本身要花一次 API 呼叫；摘要可能漏掉之後才需要的細節
   適合：長對話、長任務——這是 agent 最主流的做法

   策略三：外移（offload to memory）         ← Ch 14 主題
   做法：把該記的東西寫到 context 之外（檔案/DB），需要時再撈回來
   優點：context 保持輕，資訊不真的遺失（存在外部）
   缺點：要設計「什麼時候寫、什麼時候撈」；撈錯就沒幫到
   適合：需要跨很長時間、甚至跨 session 記憶的 agent

   策略四：裁剪工具結果（prune tool results） ← Ch 16 主題
   做法：工具結果一進來就只留「模型需要的部分」，或事後把舊的大結果替換成精簡版
   優點：直接打擊頭號元兇；針對性強
   缺點：要判斷「哪部分需要」——裁過頭模型會缺資訊
   適合：幾乎所有會用工具的 agent
```

這四種**不是互斥的，實務上會組合使用**：例如「工具結果進來就裁剪（策略四）+ 對話太長時把舊段落摘要（策略二）+ 關鍵事實外移到 memory（策略三）」。Ch 13–16 會把它們一個個做出來。本章你要帶走的是這張**選單與取捨**——知道有哪些牌、各自的代價，下決策時才不會只會「砍最舊的」這一招。

## 四、什麼時候該觸發管理？

不是每輪都要壓縮（壓縮本身有成本）。常見的觸發方式：

- **門檻觸發**：監看歷史的 token 數（用 Ch 10 的估計或 `count_tokens`），超過 context window 的某個比例（例如 70%）就觸發壓縮。這是最常見的做法——平時不動，逼近上限才出手。
- **回合觸發**：每 N 輪做一次摘要。簡單但較鈍。
- **事件觸發**：某個大工具結果一進來就立刻裁剪它（策略四），不等門檻。

實務常見的組合是「**工具結果即時裁剪 + 總量逼近門檻時做一次摘要壓縮**」。關鍵原則：**留緩衝**。別等 context 撐到 99% 才壓縮——壓縮本身（呼叫模型做摘要）也要佔空間，而且你得替接下來的 output 留位置（Ch 10）。在 70–80% 就動手，留出操作空間。

> 一個容易忽略的點：壓縮會**讓 prompt cache 失效**。更精確地說：你改寫了歷史的某一段，那麼從那個被改動的點**往後**的快取前綴就命中不了了（在那個改動點**之前**的穩定前綴，視快取邊界設定通常還能保留）。所以壓縮不是免費的——它省下未來的 token，但當下要付「重建被改動部分之後的快取」的代價。這是另一個「別太頻繁壓縮」的理由。Ch 13、Ch 17 會把這個取捨講清楚。

## 失敗示範：用「砍最舊」破壞了 tool 配對

看一個「沒解剖就亂砍」的典型翻車。一個 agent 為了省空間，無腦砍掉最舊的兩則訊息：

```python
# 反例！不看內容、不顧結構地砍最舊
if len(agent.messages) > 20:
    agent.messages = agent.messages[2:]   # 砍掉最前面兩則
```

兩個災難：

1. **可能砍到 tool_use 卻留下它的 tool_result**（或反之），破壞 Ch 5/Ch 6 的成對規則——這個跨平台都會直接 400。（順帶一提，slice 也可能弄出連續同角色而破壞交替；如 Ch 6 所述，這在 native API 不一定 400，但仍是你該維持的不變量。）
2. **可能砍掉的不是肥肉**——最舊的兩則也許是使用者最初的關鍵需求（小但重要），而真正的肥肉（中段那個 8000-token 工具結果）紋風不動。你付了「破壞結構 + 丟失關鍵指令」的代價，卻幾乎沒省到 token。

這正是為什麼要先解剖：**量過你就知道，該動的是中段那個巨大的 tool_result，而且動它的時候要連同它配對的 tool_use 一起、用摘要替換而非直接刪、並維持角色交替。** 這些 Ch 13 會做對。本章的任務是讓你**永遠不會再寫出上面這種無腦砍法**。

## 踩雷集錦

1. **沒量就砍**：憑感覺砍「最舊的」，常常砍錯地方——丟了小而重要的舊指令，留著大而無用的工具結果。先用 `analyze_history` 之類的工具量出元兇。
2. **以為「條目變多」是元兇**：通常不是。元兇是「某幾條特別肥的 tool_result」。成長的關鍵在單筆大小，不只在筆數。
3. **砍歷史時破壞結構**：直接 slice 掉訊息，可能拆散 tool_use/tool_result 配對、或破壞角色交替（Ch 6），導致 400。任何刪改都要維持這兩個不變量。
4. **每輪都壓縮**：壓縮有成本（API 呼叫 + 破壞快取），不該每輪做。用門檻觸發，平時別動。
5. **壓到 99% 才動手**：沒留緩衝給「壓縮操作本身」和「output 空間」。在 70–80% 就觸發。
6. **忘了壓縮會破壞快取**：改寫歷史會讓原本命中的快取前綴失效。這是「別太頻繁壓縮」的隱藏成本，Ch 17 會量化。

## 進階：再往深一層

- **不同住戶的「半衰期」不同**：可以給歷史內容一個「重要性會隨時間衰減」的心智模型——工具結果半衰期很短（用過就快速貶值）、使用者的核心需求半衰期很長（整個任務都可能要參照）。好的壓縮策略會**差別對待不同半衰期**的內容，而不是一刀切按時間砍。這個視角會幫你在 Ch 13 設計更聰明的壓縮。
- **「儲存」與「餵給模型」徹底分離**（Ch 6 進階區的延伸）：解剖之後你會更認同這件事——你可以**完整保存**整段原始歷史（給稽核、給 debug、給之後可能的 RAG 檢索），但**送進模型的**是經過裁剪/摘要的精簡版。這兩份東西的分離，是 Part 2 所有策略的共同地基。Ch 14 的 memory 會把它發揮到極致。
- **量測本身要便宜**：`analyze_history` 用 `count_tokens` 精算很準，但對長歷史會慢、且每段都打一次 API 不划算。生產上你會用**本地 tokenizer**（或累加每輪 `usage` 推算各段大小）來做這種分析，只在關鍵決策點才用 `count_tokens` 確認。把 Ch 10 的「估計 vs 精算分層」用在這裡。

## 動手練習

1. 拿你練習 A 的 mini-agent，跑一個會讀大檔的任務，然後寫一個 `analyze_history` 印出各類型的 token 佔比。親眼確認 `tool_result` 是不是元兇。
2. 把同一段歷史，分別用 Ch 10 的「字元數 / 4」估計和 `count_tokens` 精算，比較兩者對「哪類最肥」的判斷有沒有差——體會什麼時候估計就夠、什麼時候要精算。
3. （設計題）針對你那個 mini-agent，從四種策略裡選出你覺得最適合的組合，寫下「什麼時候觸發、動哪些住戶、怎麼維持結構不壞」。先在紙上想清楚，Ch 13 你就照這個藍圖實作。
4. 重現失敗示範：故意 `messages = messages[2:]` 砍掉一段含 tool_use 的歷史，跑下一輪，撞出那個 400，再對照「如果改成砍中段的大 tool_result 並維持配對」會多安全。

## 本章重點整理

- 先解剖再壓縮：沒量過就砍，常常砍錯地方（丟小而重要的、留大而無用的）。
- 用 instrument（按訊息類型統計 token）找出元兇——在會用工具的 agent 裡，元兇幾乎總是 **tool_result**。
- tool_result 的特性是「高當下價值、低事後價值」，是壓縮的首要目標：你丟的是已榨乾價值的東西。
- 四種管理策略：截斷、摘要（Ch 13）、外移 memory（Ch 14）、裁剪工具結果（Ch 16），實務上組合使用。
- 用門檻觸發（逼近 70–80% 就動手、留緩衝），別每輪壓、別壓到 99% 才動；並記得壓縮會破壞快取。
