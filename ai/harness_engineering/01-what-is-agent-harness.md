# Ch 1 — 什麼是 agent harness？

> **目標**：把「LLM」「agent」「harness」這三個常被混為一談的詞徹底分開。讀完你能精確說出：模型本身做什麼、harness 在外面補了什麼、為什麼少了 harness 一個再強的模型也只是個聊天框。

## 為什麼需要先搞清楚這件事

「我用 Claude 做了一個會自己讀檔、改 code、跑測試的 agent。」——這句話裡，**Claude 其實只做了一小部分**。讀檔、改 code、跑測試，沒有任何一件是模型做的。模型從頭到尾只做了一件事：根據你給它的文字，產生一段輸出。這段輸出可能是給人看的文字，也可能是「我想用 `read_file` 這個工具」這種結構化的請求——但無論是哪種，它都只是**輸出的內容**，模型本身不會產生任何外部副作用（不會真的開檔、不會真的執行）。其他全是外面那層程式幹的。

那層程式就是 **harness**（執行框架／鷹架）。這門課要教的就是它。所以第一步，得先把模型的能力邊界畫清楚——你才知道剩下的「魔法」全都是工程，而工程是可以學、可以自己寫的。

很多人對 agent 的誤解，源頭都在這裡：把模型不會做的事，當成模型會做。於是模型升級了卻發現 agent 沒變強，或者 agent 出包了卻怪模型笨。分清楚這條線，是看懂整個領域的前提。

## 先建立直覺：模型是一顆「只會接話的大腦」

想像一個能力極強、但被關在密閉房間裡的人。他沒有手、沒有眼睛、沒有記憶、沒有時鐘。你從門縫塞一張紙進去，上面寫滿文字；他讀完，在紙的末尾續寫一段，再從門縫塞回來。**就這樣，沒別的互動管道。**

```
   你 ──塞一張寫滿字的紙進去──▶ ┌─────────────┐
                                │  房間裡的人  │  讀完整張紙
   你 ◀──他在末尾續寫後塞回來── │ (LLM 模型)   │  在末尾續寫
                                └─────────────┘
```

這個人就是 LLM。關鍵在於這幾個「沒有」：

- **沒有記憶**：他讀完一張紙就忘了。下次你塞新紙進去，他完全不記得上一張寫過什麼——除非你把上次的內容**再抄一遍**放進新紙裡。
- **沒有手腳**：他不能開檔案、不能上網、不能執行任何指令。他唯一能做的就是「在紙上寫字」。
- **沒有時間感**：他不知道現在幾點，不知道距離上次過了多久，不知道外面世界發生了什麼。
- **一次只做一件事**：塞紙進去 → 他寫 → 塞回來。這叫一次 **inference（推論）**，對應 Ch 0 那一行 `client.messages.create(...)`。

如果這個比喻你接受了，那一個殘酷的事實就浮現了：**LLM 自己什麼事都「做」不了**。它連「呼叫一個函式」都做不到——它只能在紙上寫下「我想呼叫這個函式」這幾個字，然後等門外的人替它去做。

## 那 agent 是什麼？harness 又是什麼？

承上。如果模型只會在紙上寫字，那「會讀檔、會跑指令的 agent」是怎麼來的？答案是：**門外有一個勤勞的助手**。

這個助手做四件事，週而復始：

1. 準備一張紙（決定要塞什麼文字給模型）
2. 塞進門縫（呼叫 API）
3. 讀模型寫回來的字
4. **如果模型寫的是「我想讀 config.json」，助手就真的去把 config.json 讀出來，貼到下一張紙上，再塞回去**

```
┌──────────────────────────────────────────────────┐
│                  harness（門外的助手）              │
│                                                    │
│   ① 組裝 context ──▶ ② 呼叫模型 ──▶ ③ 讀回應       │
│        ▲                                  │         │
│        │                                  ▼         │
│   ⑤ 把結果貼回      ◀──  ④ 模型說要用工具？         │
│      下一張紙            真的去執行那個工具          │
│        └──────────────（迴圈，直到模型說「做完了」）  │
└──────────────────────────────────────────────────┘
```

- **agent** 是這整套東西運轉起來表現出來的「行為」——一個看起來會自己讀檔、思考、行動的東西。
- **harness** 是讓這個行為成立的那層**程式碼基礎建設**：那個門外的助手。

換句話說：**agent = LLM + harness**。模型提供「判斷下一步該做什麼」的智能，harness 提供「真的把那一步做出來、並把結果餵回去」的手腳與記憶。這門課教的就是怎麼當好那個助手。

## 一個具體例子：「幫我看看為什麼測試掛了」

把抽象講法落地。使用者對一個 coding agent 說：「跑一下測試，看看為什麼掛了，修好它。」底下實際發生的事：

| 輪次 | 模型在「紙上」寫了什麼 | harness 實際做了什麼 |
|---|---|---|
| 1 | 「我需要先跑測試。呼叫 `run_shell("pytest")`」 | harness 真的執行 `pytest`，抓到輸出（一段 traceback） |
| 2 | （harness 把 traceback 貼進新紙）模型讀完：「錯誤在 `utils.py:42`，我要看那個檔」→ `read_file("utils.py")` | harness 讀出 utils.py 的內容，貼回去 |
| 3 | 模型：「第 42 行少了 None 檢查，我要改」→ `edit_file(...)` | harness 真的把檔案改掉 |
| 4 | 模型：「再跑一次測試確認」→ `run_shell("pytest")` | harness 再跑一次，這次過了 |
| 5 | 模型：「測試通過了，修好了。」（沒有要求用工具） | harness 看到模型不再要求工具，**結束迴圈**，把這句話回給使用者 |

整個過程裡，模型一行 code 都沒「執行」過。它只是反覆地「讀情況 → 決定下一步 → 用文字表達那一步」。**所有的執行、檔案存取、迴圈控制、何時停止，全是 harness 的職責。** 這張表你看懂了，這門課的骨架就建立起來了。

## harness 到底補了哪些東西？

把上面那個助手的工作拆細，就是這門課接下來各 Part 的內容。先看全貌：

```
                 ┌─────────────────────────────┐
   使用者輸入 ──▶│  harness                     │
                 │                              │
                 │  ┌────────┐                  │
                 │  │ Loop   │ 反覆呼叫模型      │ ← Part 1
                 │  └────────┘ 直到任務完成      │
                 │  ┌────────┐                  │
                 │  │Context │ 決定每次塞什麼進  │ ← Part 2
                 │  │ 管理   │ 紙、塞不下時壓縮  │
                 │  └────────┘                  │
                 │  ┌────────┐                  │
                 │  │ Tools  │ 模型能呼叫的能力  │ ← Part 3
                 │  └────────┘ 集，與其執行      │
                 │  ┌────────┐                  │
                 │  │ Policy │ 權限、安全、何時  │ ← Part 3/5
                 │  └────────┘ 該停、該不該問人  │
                 └─────────────────────────────┘
```

- **Loop（迴圈）**：模型一次只能寫一張紙，但任務常常要好幾步。harness 負責「塞紙 → 執行 → 再塞紙」轉到任務完成，並判斷何時該停（Part 1）。
- **Context（上下文）管理**：模型沒記憶，每一輪都要把「相關的過去」重新塞進紙裡。但紙的大小有上限（context window），塞不下時要壓縮、要取捨。這是整個 Part 2。
- **Tools（工具）**：模型只會寫「我想做 X」，harness 要事先告訴它「你可以做哪些 X」（工具清單），並在它要求時真的去做。工具設計的好壞，直接決定 agent 聰不聰明（Part 3）。
- **Policy（策略 / 治理）**：哪些事可以讓模型自己做、哪些要先問人、怎麼防止它被惡意輸入帶壞、怎麼知道它有沒有變笨。這散落在 Part 3 的 permission 和 Part 5 的安全與 eval。

這四塊，就是 Ch 3 會給你的心智模型：**harness = loop + context + tools + policy**。本章先讓你看到它們為什麼存在。

## 對比：workflow 還是 agent？

不是所有「用 LLM 自動化」的東西都需要完整的 agent harness。Anthropic 在〈Building Effective Agents〉裡做過一個很有用的區分，值得現在就建立：

| | Workflow（工作流） | Agent |
|---|---|---|
| 控制流程 | **由你寫死**：步驟一、步驟二、步驟三，路徑固定 | **由模型決定**：下一步做什麼是模型當場判斷的 |
| 模型的角色 | 在固定流程的某幾格裡填空（分類、抽取、改寫） | 自己開車，決定要不要用工具、用哪個、用幾次 |
| 適合什麼 | 任務結構清楚、步驟可預先列出 | 任務開放、步驟數量與順序事先不知道 |
| 例子 | 「把這封信分類 → 若是投訴就轉客服」 | 「想辦法把這個 bug 修好」 |

**關鍵判準**：這個流程的**控制結構由誰擁有**？

- **由你（開發者）擁有**＝ workflow：路徑是你寫死的程式碼骨架。注意「寫死」不代表「死板」——即使中間某一格讓模型動態決定（例如 Anthropic 講的 `orchestrator-workers`：一個 LLM 當協調者、當場把任務拆成子任務再分派），只要**整體的控制骨架是你定義的、有界的**，它仍然是 workflow。
- **由模型擁有**＝ agent：沒有預先寫死的步驟骨架，「下一步做什麼、還要不要繼續」是模型在一個開放式迴圈裡自己決定的，harness 只負責執行與把結果餵回去。

能用前者解決就用前者，更可控、更便宜、更好 debug。只有當你**無法事先定義出有界的控制骨架**——任務開放到連「大概會經過哪些階段」都說不準——才需要 agent，也才需要這門課教的這套 model-owned loop。

很多生產事故是因為「明明 workflow 就夠了，卻硬上 agent」，結果不可控又貴。所以一個好的 harness 工程師，第一個本事是**判斷該不該用 agent**，而不是無腦套。這門課雖然教 harness，但這個判斷力要從第一章就開始建立。

## 為什麼不直接用現成框架就好？

你可能會問：LangChain、LlamaIndex、CrewAI、Claude Agent SDK 都把 harness 寫好了，我為什麼要懂底層、甚至自己刻？

三個理由：

1. **debug**：框架把 loop 和 context 組裝藏起來了。當 agent 行為詭異（不呼叫工具、context 爆掉、無限迴圈），你若不知道底層在組什麼，只能改 prompt 碰運氣。懂底層的人能直接看「到底送了什麼進模型」。
2. **掌控力**：真實產品幾乎都會碰到框架沒覆蓋的需求——特殊的壓縮策略、自訂的 permission 流程、跟既有系統整合。這時你要嘛改框架、要嘛繞過它，兩者都需要懂它在做什麼。
3. **判斷力**：懂底層，你才評估得出「這個框架幫我省了什麼、又綁住了我什麼」。Ch 40 我們會正面比較幾個主流框架——但那個比較要有意義，前提是你先自己走過一遍。

所以本課的路線是：**先自己刻一個能跑的最小 harness（Part 1），理解每一塊為什麼存在，再決定哪些交給框架。** 自己刻過一次，你看任何框架的文件都會「秒懂」，因為你知道它在解決的是哪個你親手碰過的問題。

## 踩雷集錦

1. **「模型會自己呼叫工具」**：在本課的 **client-side tool**（由你的 harness 執行的工具）模型裡——不會。模型只會在輸出裡**表達**它想呼叫某個工具（這在 API 裡是一個 `tool_use` 區塊），真正去執行的是 harness；模型連自己呼叫過的工具結果都看不到，除非 harness 把結果塞回去。（補充：Anthropic 也提供一類 **server-side tools**，例如 web search，其執行是在 Anthropic 那端完成、不經過你的 harness。本課專注在 client-side 工具，因為那才是「harness 工程」真正要處理的部分；Ch 5 會看到 client tool 的完整協議。）
2. **「模型記得我們之前聊過的」**：就 Messages API 本身而言——不記得。模型每一次 inference 都是**全新的**，所謂「記得」是 harness（或產品的應用層）每次把歷史對話重新塞進 context 製造出來的錯覺。一旦沒人把它塞進去（或塞不下了），「記憶」立刻消失。你可能會說「可是 ChatGPT / Claude 的產品版好像會記得我跨對話講過的事」——對，那是**產品在應用層**做了 memory 功能（把該記的東西存起來、下次主動撈出來塞進 context），不是模型自己記得。這個「應用層怎麼幫模型製造記憶」正是 Part 2（尤其 Ch 14 memory）的核心。
3. **「agent 越自主越好」**：不一定。自主代表不可控與更高成本。能用 workflow 解的就別上 agent。「該不該用 agent」本身是個設計決策，不是預設值。
4. **「換更強的模型，agent 自然變強」**：只對一半。模型變強會讓「判斷下一步」更準，但如果 harness 給的工具爛、context 組得差、loop 設計有問題，再強的模型也施展不開。很多 agent 的瓶頸在 harness，不在模型。
5. **「harness 只是個 while 迴圈，沒什麼好學的」**：最小骨架確實是個迴圈（Ch 4 你會看到它真的很短）。但讓它在真實任務下穩定、省錢、安全、可 debug——context 怎麼壓、工具怎麼設計、出錯怎麼重試、怎麼防注入——這些才是這門課剩下 40 章在處理的工程深度。

## 進階：再往深一層

- **「模型其實也不是完全無狀態」的細節**：嚴格說，prompt caching（Ch 17）會在伺服器端暫存你送過的 context 前綴，讓重複的部分算得更快更便宜。但這是**效能優化**，不是「記憶」——快取會過期，而且它不改變模型的邏輯行為：同樣的輸入，有沒有命中快取，模型的回應內容是一樣的，差別只在速度與成本。所以「模型無狀態」這個心智模型基本上一直成立，prompt caching 不是它的例外，只是底層多了一層快取。Ch 17 會把這件事說清楚。
- **agentic 程度是一條光譜**：workflow 和 agent 不是非黑即白。實務上有很多中間態——固定流程裡嵌一小段讓模型自由發揮、或 agent 但限制它最多跑 N 步。〈Building Effective Agents〉裡的 prompt chaining / routing / orchestrator-workers 等 pattern，就是在這條光譜上的不同點。讀那篇時，把它們對照到「控制流程由誰決定」這個軸去理解。

## 動手練習

不用寫 code，用你自己的話完成：

1. 拿 Ch 0 你跑過的 `hello.py`，指出裡面**哪一行**是「模型唯一做的事」，其餘的（讀環境變數、印出結果）屬於誰的職責。
2. 想一個你最近用過的 AI 功能（任何產品都行），判斷它比較像 workflow 還是 agent，並說出你的判準。
3. 用「房間裡的人」這個比喻，向一個完全不懂的朋友解釋：當你直接打 LLM 的 API、且沒有自己保存歷史時，為什麼它「記不住」上一輪講過的話。能講清楚這個「裸 API」的情況，你就抓到 Part 2 的核心動機了——而產品版之所以「好像記得」，正是因為有人在外面替它補了這一塊。

## 本章重點整理

- LLM 只會做一件事：讀一段文字、產生一段輸出（一次 inference）。輸出可能是文字，也可能是結構化的工具請求（`tool_use`），但兩者都只是「內容」——模型本身沒有記憶、沒有手腳、無外部副作用。
- agent = LLM + harness。讀檔、跑指令、迴圈、記憶、停止判斷，全是 harness 的職責，不是模型的。
- harness 補的四塊：loop、context 管理、tools、policy——對應本課四個 Part。
- 不是所有任務都該用 agent；能畫成固定流程圖的，用 workflow 更好。判斷「該不該用 agent」是 harness 工程師的第一個本事。
