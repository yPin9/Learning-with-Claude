# Ch 31 — 背景任務與長時間執行

> **目標**：agent 迴圈天生是「呼叫工具 → 等它回來 → 再決定下一步」。但有些工具會跑很久——編譯、測試、起 dev server、一個花兩分鐘的 subagent 調查。如果同步傻等，agent 就**整個卡住**，什麼別的都做不了。本章談 **背景任務（background tasks）**：怎麼把一個耗時工作「丟到背景、拿一個把手（handle）、繼續做別的、之後再回來收結果」。讀完你能說出同步阻塞為什麼是長任務的大敵、背景任務的生命週期（啟動 → 取得 handle → 輪詢/被通知 → 收集輸出 → 清理）、為什麼「別 sleep 空轉等」而要靠「完成時通知」、長駐型背景程序（dev server、watcher）跟一次性背景任務的差別、以及背景任務對 context 的衝擊（別把整片 log 灌回來）。也會把它跟 Ch 27 的執行緒並行、Ch 22 的行程控制接起來——**背景任務常常是「可被 kill 的獨立行程」，這正補上 Ch 27 那個「執行緒殺不掉」的洞**。

> **環境**：背景任務主要是 **harness 層的能力**——harness 提供「以背景模式啟動某工具、之後查它輸出」的機制。在 Claude Code / Agent SDK 的公開文件裡，可穩定引用的是這組：`Bash(run_in_background=true)` 啟動後回一個 shell 把手（`shellId`），`BashOutput` 用該把手讀「自上次查詢以來新增」的輸出並回 `status`（running/completed/failed），`KillBash` 用把手終止。**你正在用的這個 session 還另外有** `PowerShell`、`Agent` 的 `run_in_background`，以及一個 `Monitor` 串流工具——這些是本 harness 的工具，不一定每個 Claude Code 版本都叫同樣名字。本章拿它們當第一手教材，並標明哪些是具體實作、哪些是通用原則。

## 為什麼需要這個？同步等待會凍住整個 agent

回想 Ch 7 的迴圈：工具呼叫是**同步**的——模型送出 `run_tests()`，harness 跑它，**跑完才**把結果回給模型，模型才能繼續。短工具（讀個檔、查個 API）這樣完全沒問題，毫秒級就回來了。

但工具一旦耗時，同步就變成災難：

- **跑一次完整測試要 3 分鐘** → agent 卡住 3 分鐘，這期間它沒辦法「先去看別的檔」「先準備下一步」。
- **起一個 dev server** → dev server **永遠不會「結束」**（它就是要一直跑著）。同步等？agent 永遠卡在這裡，迴圈再也回不來。
- **派一個花 2 分鐘的 subagent 調查**（Ch 26） → 主 agent 乾等 2 分鐘，完全閒置。

問題的本質：**同步工具呼叫把「啟動一件事」和「拿到它的結果」綁死在同一個阻塞點上。** 對耗時或長駐的工作，這兩件事應該**拆開**：先啟動（馬上返回），之後再收結果（需要時才去拿）。

**背景任務就是這個拆分：啟動工作 → harness 立刻回一個「把手」（process id / task id）→ agent 繼續做別的 → 之後用那個把手去查狀態或收輸出。** dev server 在背景一直跑著、測試在背景算著，agent 同時還能讀程式碼、改別的檔——不再被一個耗時工具凍住。

關鍵心態：**把「耗時」和「長駐」的工作從迴圈的同步路徑上挪開。** 迴圈本身要保持「快速一問一答」的節奏，耗時的東西丟背景、用把手非同步地管理。

## 先建立直覺：背景任務是「把鍋放上爐子，去切菜」

你不會站在爐子前盯著水煮開才開始切菜——你**開火（啟動）、轉身去切菜（做別的）、聽到水滾的聲音（被通知）才回來下麵（收結果）**。背景任務就是給 agent 這個能力：

```
   同步（阻塞）：                    背景（非阻塞）：
   ┌──────────────┐                 ┌──────────────┐
   │ 啟動測試      │                 │ 啟動測試 →handle│  立刻返回
   │   ⏳ 等…      │  3 分鐘什麼      │ 去讀程式碼     │  ← 同時做別的
   │   ⏳ 等…      │  都不能做        │ 去改別的檔     │
   │ 拿到結果      │                 │ （測試在背景跑）│
   └──────────────┘                 │ ←被通知：測試完 │  完成才回來收
                                     │ 讀取輸出 + 清理 │
                                     └──────────────┘
```

切菜的人需要三樣東西：**一個爐子的把手**（知道哪鍋是哪鍋）、**一個「水滾了」的訊號**（不必每三秒回頭看一次）、**最後把鍋端走/關火**（清理）。背景任務也對應這三件事：handle（識別任務）、completion notification（完成通知，而不是空轉輪詢）、cleanup（收尾，別留下孤兒程序）。

> **這個 session 正是這樣運作的**：當我跑一個長指令，我可以用 `Bash(run_in_background=true)` 啟動它、立刻拿到一個背景 task 的把手、繼續處理你的其他需求；它跑完時系統會**通知**我（我不必 sleep 空等），我再回去讀它的輸出。派長時間的 `Agent` 調查也一樣可以丟背景。本章談的就是這層機制——而且工具說明還特別叮嚀我「**別用 sleep 輪詢、完成時你會被通知**」。

## 一、背景任務的生命週期：啟動 → handle → 輪詢/通知 → 收集 → 清理

把一個背景任務從生到死走一遍（五個階段，每個都有工程要點）：

**1. 啟動（launch）**：以背景模式發動工具。harness **不等它跑完**，立刻返回一個**把手**（process id、task id 之類）。這一步的關鍵是「啟動即返回」——迴圈馬上能繼續。

**2. 取得 handle**：那個把手是你之後一切操作的依據——查狀態、讀輸出、終止，都靠它。把它記住（Ch「context 管理」：重要的把手要寫下來，免得被壓縮掉）。

**3. 輪詢或被通知（poll / notify）**：怎麼知道任務好了？看 harness 提供什麼，但原則是**別空轉等**：
   - ❌ **sleep 空轉輪詢**：`while not done: sleep(3)`——浪費迴圈回合、燒 token、還可能 sleep 太久或太短。這是最該避免的。
   - ✅ **若 harness 支援完成通知**：啟動後就去做別的，任務完成時 harness **主動通知**你回來收。這是最理想的姿勢。
   - 🟡 **否則用「有節制的狀態查詢 / 串流」**：有些 harness 是用把手**拉**狀態（如 `BashOutput` 回 `status` 與新增輸出），沒有明文的「完成通知」API。這時就在「有理由認為它差不多好了」時查一次，或用串流持續接新輸出——而不是固定每 N 秒盲查。

**4. 收集輸出（collect）**：任務好了，用把手去讀它的輸出。**這裡要管好 context**：一個跑了三分鐘的測試可能吐出幾萬行 log，**別整片灌回 context**——用工具提供的過濾能力（如 `BashOutput` 的 regex `filter`、只讀「自上次以來新增」的增量輸出），或在命令端自己 `tail`/grep/摘要化後再讀（接 Ch 20 工具結果設計、Ch 13 context 壓縮）。

**5. 清理（cleanup）**：任務結束（或你不要它了），要確保它**真的停掉、不留孤兒**。一次性任務跑完自然結束；長駐程序（dev server）要顯式終止。背景程序若沒清理，會累積成吃資源的孤兒（接 Ch 22 行程控制）。

這五步就是背景任務的骨架。新手最常漏掉的是第 3 步（用 sleep 空轉而非等通知）和第 5 步（忘了清理，留一堆 dev server 在背景）。

## 二、一次性任務 vs 長駐程序：兩種背景，管法不同

「背景任務」其實涵蓋兩種很不一樣的東西，分清楚才知道怎麼管：

| | 一次性背景任務 | 長駐背景程序 |
|---|---|---|
| 例子 | 跑一次完整測試、編譯、長 subagent 調查 | dev server、檔案 watcher、`tail -f` 日誌 |
| 會自己結束嗎 | **會**（跑完就退出） | **不會**（要你顯式停掉） |
| 主要關心 | 「完成了嗎？結果是什麼？」 | 「它還活著嗎？有沒有新輸出？」 |
| 收尾 | 跑完自然清理 | **必須顯式終止**，否則變孤兒 |
| 典型互動 | 啟動 → 等通知 → 收結果 → 結束 | 啟動 → 持續監看輸出 → 任務全程都用著 → 最後關掉 |

**一次性任務**的重點是「完成 + 結果」：啟動、等通知、收摘要、結束。**長駐程序**的重點是「持續可用 + 監看」：你起一個 dev server 是為了**整段任務期間都用它**（對著它測 UI、看它的錯誤輸出），它不該結束，但你得能**邊跑邊看它的新輸出**（例如 server 報的錯），且**任務做完一定要記得關掉它**。

> **這個 session 的 `Monitor` 工具就是給長駐程序用的**：它能**串流**一個背景程序的輸出（每行 stdout 當一則通知），讓我邊做別的、邊看 dev server 或長指令吐出的新內容——而不是反覆去「讀一次完整輸出」。這對應上表「長駐程序：持續監看」那一欄。

## 三、背景任務 vs 執行緒並行（接 Ch 27）：層次不同

Ch 27 用 `ThreadPoolExecutor` 並行跑多個 subagent。那也是「同時做很多事」，跟背景任務有什麼不同？層次不一樣：

- **Ch 27 的執行緒並行**：發生在**單一工具呼叫內部**——`orchestrate()` 這一個工具，內部開執行緒同時跑 5 個 worker，全部收齊了才把彙整結果回給模型。從**模型的視角**，它還是一次同步呼叫（送出 → 等 → 拿到彙整結果）。並行是「工具內部的實作細節」。
- **本章的背景任務**：發生在**迴圈層級**——模型送出「啟動」就拿回把手、繼續跑迴圈、之後再回來收。並行的是「**迴圈在做別的** vs **背景任務在跑**」。

一句話：**Ch 27 是「一個工具內部並行做多件事」，本章是「把一件耗時的事挪出迴圈的同步路徑、讓迴圈能同時做別的」。** 兩者可以疊加——你大可在背景啟動一個「內部又並行跑多 worker」的 orchestrate。

更關鍵的是，背景任務補上了 Ch 27 留的那個洞：

> **背景任務常常是「可被 kill 的獨立行程」——這正是 Ch 27 缺的東西。** Ch 27 講過：Python **執行緒殺不掉**（`ThreadPoolExecutor` / `Future.cancel()` 取消不了一個**已經在跑**的 callable，`timeout` 只能讓你「不再等」，那個 worker 仍在背景燒）。但如果耗時工作是用**獨立行程**跑在背景（像 `Bash(run_in_background)` 起的子行程），它就**真的能被終止**（拿把手去 `terminate()`/`kill()`，Ch 22 的行程控制）。所以「要能硬性中斷一個失控的長任務」時，背景**行程** + kill 是可靠解，背景**執行緒**不是。
>
> **但 kill 行程有個 process-tree 的坑**：`terminate()`/`kill()` 殺的是你手上那個把手指向的行程。如果它（例如一個 shell 或 dev server）又 spawn 了**子行程**，只殺父行程可能留下一堆孤兒子行程還在跑。所以長駐服務的可靠終止要殺**整個 process group / job object（行程樹）**，而不只是單一 PID。（`asyncio.create_subprocess_shell` 尤其要注意：它的 `pid` 是那個 shell 的 PID，不是 shell 裡那條命令的。）這是本章和 Ch 22、Ch 27 的交會點。

## 四、背景任務對 context 的衝擊：別把海量輸出灌回來

背景任務最容易被忽略的坑，是它跟 context 的關係。一個跑很久的任務，往往**產出也很多**：

- 一次完整測試可能吐幾萬行 → 全讀進 context，瞬間吃掉大半視窗，還把重要資訊稀釋掉。
- dev server 跑一小時的 log → 你要的只是「有沒有報錯」，不是那一小時的每一行。

所以收集背景輸出時，要套 Ch 20（工具結果設計）和 Ch 13（context 管理）的原則：

- **只拉你需要的切片**：最後 N 行、grep 出的錯誤行、結構化的「通過/失敗 + 失敗摘要」，而不是整片 raw log。
- **讓「讀背景輸出」這個動作本身可以帶過濾條件**：好的背景輸出工具應該支援「給我含 ERROR 的行」「給我最後 50 行」，而不是只有「給我全部」。
- **長駐程序用串流式監看**：與其反覆「讀一次完整 log」（每次都把愈來愈長的 log 重灌一遍），不如用串流（每次只拿到「新增的那幾行」，像本 session 的 `Monitor`）。

核心原則：**背景任務的「跑多久」和「它的輸出佔多少 context」是兩件事，要分別管。** 別讓一個三分鐘的任務用三萬行 log 撐爆你的視窗。

## 對比與取捨

| 設計選擇 | 選項 A | 選項 B | 怎麼選 |
|---|---|---|---|
| 耗時工具怎麼跑 | 同步阻塞等 | **背景啟動 + 拿 handle** | 耗時/長駐 → 背景；毫秒級 → 同步沒差 |
| 怎麼知道完成 | sleep 空轉輪詢 | **等完成通知** | 通知：不浪費回合、不燒 token、不猜 sleep 長度 |
| 長駐程序的輸出 | 反覆讀完整 log | **串流式監看（只拿新增）** | 串流：避免重複灌、即時看到新錯誤 |
| 收集輸出 | 整片 raw log 回 context | **只拉摘要/最後 N 行/grep 結果** | 過濾：保護 context（Ch 13/20） |
| 要能硬中斷長任務 | 背景執行緒 | **背景獨立行程 + kill** | 行程可 kill，執行緒不行（Ch 22/27） |
| 長駐程序收尾 | 忘了它 | **任務做完顯式終止** | 顯式清理：否則留孤兒程序吃資源 |

## 踩雷集錦

1. **同步等一個長駐程序**：對 dev server 同步呼叫，迴圈永遠回不來。長駐的東西一定要背景啟動。
2. **用 sleep 空轉輪詢**：`while not done: sleep(3)`——浪費迴圈回合、燒 token，sleep 太短狂查、太長又拖慢。要靠完成通知。（本 session 的工具甚至明文禁止無謂的 sleep。）
3. **忘了清理長駐程序**：起了一堆 dev server / watcher 沒關，背景累積孤兒程序，吃光埠口與資源。任務完成要顯式終止。
4. **把整片背景輸出灌回 context**：三萬行測試 log 全讀進來，撐爆視窗。只拉摘要/失敗行/最後 N 行。
5. **弄丟 handle**：啟動了背景任務卻沒記住把手，之後查不到狀態、也 kill 不掉。重要把手要記下（context 管理）。
6. **以為背景執行緒能被 kill**：想中斷一個失控的長任務卻用了執行緒——殺不掉（Ch 27）。要能硬中斷得用獨立行程（Ch 22）。
7. **背景任務靜默失敗沒人發現**：丟到背景就不管了，它早就崩了你還在等。要在收集階段檢查它的結束狀態/錯誤，別假設它一定成功（接 Ch 27 容錯）。

## 進階：再往深一層

- **串流回報給使用者**：長背景任務跑著時，別讓使用者盯著轉圈。可以把「目前進度 / 已完成的部分」串流回報（Ch 8 串流）。多 agent 研究任務尤其需要——讓使用者看到「worker 2 已回來、worker 4 還在查」，而不是黑箱等 90 秒（呼應 Ch 27 進階）。
- **排程與喚醒（scheduling / wake-up）**：有些 harness 提供「過 N 秒後再回來看」「到某時間點觸發」的排程能力（本 session 就有按時喚醒與 cron 類機制）。這讓 agent 能「先睡一下、到時被叫醒繼續」，適合「等一個一定要過幾分鐘才會好的東西」——但仍是「被叫醒」而非「空轉等」。
- **背景任務的把手要能跨回合存活**：把手（process id / task id）必須在多個迴圈回合間保持有效，且最好能在 context 壓縮（Ch 13）後還找得回來。實作上常把活躍背景任務的清單存在 harness 狀態裡，而不只是塞在對話裡。
- **資源與並發上限**：背景任務不是免費的——每個都佔行程/記憶體/埠口。要設「同時最多幾個背景任務」的上限，並在啟動前檢查資源，否則 agent 可能無意間起一堆背景程序拖垮機器。
- **和 sandbox 的關係**：背景行程一樣要在 sandbox 的約束內（Ch 22）——它能碰什麼檔、連什麼網路、用多少資源，都該受限。一個失控的背景任務若沒沙箱，破壞力比同步的更大（它在背景默默跑）。
- **這是 Claude Code 的背景執行能力**：`Bash(run_in_background=true)` + 讀背景輸出的工具、`Agent(run_in_background=true)`、`Monitor` 串流、按時喚醒，都是這個 harness 的具體實作。不同 harness 細節各異，但「啟動即返回 + 把手 + 通知 + 清理」的核心模型是通用的。

## 動手練習

1. 在 Claude Code 裡用 `Bash(run_in_background=true)` 起一個會跑一陣子的指令（例如一個 sleep 後印東西的腳本），確認它**立刻返回**、你能繼續做別的，完成時**被通知**而非空等。
2. **起一個 dev server**（長駐程序）到背景，邊讓它跑、邊用監看工具看它的輸出，最後**記得顯式關掉它**。體會一次性任務和長駐程序在「收尾」上的差別。
3. **對照實驗**：把同一個耗時指令分別用同步、背景兩種方式跑，觀察同步時迴圈是怎麼被凍住、背景時你能在它跑的同時做別的。
4. **context 保護**：故意跑一個會吐大量輸出的背景指令，練習「只拉最後 N 行 / grep 出關鍵行」而不是全讀，對照兩者吃掉的 context 量。
5. （概念，接 Ch 22/27）設計一個「可硬中斷的長任務」方案：用獨立**行程**在背景跑，記住它的 pid，並寫出「超過時限就 kill 它」的邏輯。想想為什麼這用執行緒做不到。

## 本章重點整理

- 同步工具呼叫把「啟動」和「拿結果」綁在同一個阻塞點，對**耗時/長駐**的工作是災難（凍住迴圈、長駐程序永遠回不來）。
- **背景任務 = 啟動即返回（拿 handle）→ 繼續做別的 → 等通知 → 收集輸出 → 清理。** 把耗時的東西挪出迴圈的同步路徑。
- **別 sleep 空轉輪詢，要等完成通知**——省回合、省 token、不必猜 sleep 長度。
- **一次性任務 vs 長駐程序**：前者關心「完成+結果」、跑完自清；後者關心「持續可用+監看」、**必須顯式終止**否則留孤兒。長駐程序用**串流監看**只拿新增輸出。
- **層次區分**：Ch 27 是「一個工具內部並行」，本章是「把一件事挪出迴圈讓迴圈能同時做別的」。背景**行程**可被 kill，補上 Ch 27「執行緒殺不掉」的洞（接 Ch 22）。
- **背景輸出要管 context**：跑多久 ≠ 輸出該佔多少視窗。只拉摘要/失敗行/最後 N 行，別整片灌回（Ch 13/20）。
