# Ch 42 — 漸進式落地：從輔助到自主的信任階梯

> **目標**：學會把「agent 該多自主」當成一條可以一格一格往上爬、也能往下降的滑桿，而不是上線時的一次性賭注；能用 eval 通過率、影子模式、金絲雀等客觀證據決定何時放權，並設計好停損與回退。

> **環境**：本章的自主層級閘工具用 Python 3.11，純標準庫，複製即跑。其餘是落地方法，與語言無關。

## 為什麼需要這個？

[Ch 41](./41-when-to-agentify.md) 幫你選出了「值得交給 agent」的任務。但選對任務之後，最常見的下一個錯誤是：**一上線就讓它全自主**。

agent 會做出你沒預期的動作，而且是統計性的——同一個任務跑十次不會十次都對。你**還沒有證據**證明它在真實情況下夠可靠，就把執行權交出去，等於拿生產環境當測試場。反過來，有些團隊被這個風險嚇到，乾脆讓 agent 永遠停在「給建議、人全部手動執行」——那又把 agent 的價值（速度、規模）全砍掉了。

正解是中間的一條路：**信任要靠證據累積，自主程度跟著證據一格一格放**。這章教你把「多自主」設計成一條可往上爬、也**必須能往下降**的階梯，以及每一格之間用什麼客觀門檻來決定能不能升級。

## 先建立直覺：你不會第一天就給新人簽大額支票的權限

```
              自主程度低                          自主程度高
              可控、慢、需人力                    快、可 scale、風險高
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │ L0 影子模式    │ L1 人在迴圈裡  │ L2 人在迴圈上  │ L3 全自主      │
  │ shadow        │ in-the-loop   │ on-the-loop   │ autonomous    │
  ├──────────────┼──────────────┼──────────────┼──────────────┤
  │ agent 跑但    │ 每個有副作用   │ agent 自己    │ agent 自己跑  │
  │ 輸出不生效，   │ 的動作都要人   │ 執行，人在旁   │ 與執行，只在  │
  │ 只記錄拿來跟   │ 逐一核可才執行 │ 監看、可隨時   │ 出界/異常時   │
  │ 人的決策比對   │ （= gate ask）│ 否決、事後抽查 │ 才通報        │
  └──────────────┴──────────────┴──────────────┴──────────────┘
      ↑ 拿證據          ↑ 人擋在出口     ↑ 人盯著但不擋    ↑ 完全放手
      └──── 往上爬要靠客觀證據；發現退步要能往下降（雙向滑桿）────┘
```

你帶一個新進員工，不會第一天就給他動公司帳戶的權限。你先讓他做不會出事的事、看他的判斷、慢慢給更大的權限——而且如果他出了包，你會把權限收回去。**agent 的自主程度就該這樣管**：用真實表現換信任，信任換權限，出問題收回權限。

> 這條階梯的每一格，本質上是 [Ch 25](./25-permission-model.md) permission gate 的 `allow / ask / deny` 在「整個 agent」層級的放大版。L1「人在迴圈裡」就是把有副作用的工具全設成 `ask`；往上爬就是把越來越多動作從 `ask` 放成 `allow`。如果你對 gate 的三態還不熟，先回看 Ch 25。

## 四個自主層級，逐格拆解

### L0 — 影子模式（shadow mode）：跑，但不算數

agent 在真實輸入上跑，但**輸出完全不生效**——只寫進 trace（[Ch 35](./35-observability.md)），拿來跟「人實際做的決策」並排比對。這是**業務副作用近零的證據收集**：在不改變任何使用者可見結果的前提下，回答「如果當初讓 agent 做，它會做對嗎？」（注意「不生效」不等於「完全無成本」——它仍會花 token、產生 log，碰真實資料時還有隱私／合規與系統負載要顧。）

影子模式的關鍵是**要有人類的真實決策當對照組**。例如客服分類：人照常分類（生效的是人的），agent 同時也分類（不生效），事後比對兩者一致率。一致率夠高、夠久，你才有底氣往上爬一格。

### L1 — 人在迴圈裡（human-in-the-loop）：每個動作都要批准

agent 規劃並產出動作，但**每個有副作用的動作都要人按下確認才真的執行**。唯讀動作（讀檔、查詢）可以放行，有副作用的（寫檔、跑 shell、發請求）一律 `ask`。這是大多數 agent 上線的**第一個會生效的層級**——agent 開始真的做事，但人擋在每個出口。

代價是 scale 受限於人的核可速度；好處是 blast radius 被人鎖死，agent 跑歪也出不了事。

### L2 — 人在迴圈上（human-on-the-loop）：自己做，人盯著

agent **自己執行**，不再逐一等核可，但人**即時監看、可隨時喊停下一步、回滾或否決尚未送出的動作**，且事後對輸出抽查。注意這裡的「否決」是針對**後續或排隊中**的動作——已經執行的動作只能靠回滾／補救，不是事前否決；若你需要的是「每個動作執行前都要人點頭」，那其實是 L1，不是 L2。這一格是 scale 的轉折點——人從「每個都批」變成「盯著儀表板、異常才出手」。

要爬到這格，前提是你已經有：可靠的 eval 證明通過率夠高、完整的 trace 讓人看得懂 agent 在幹嘛、以及**能即時喊停的機制**（下面講的 kill switch）。

### L3 — 全自主（autonomous）：只在出界時通報

agent 自己跑、自己執行，人不再盯著每一次，只在它**撞到預設邊界或異常**時被通報。這是自主程度的頂點，也只有少數**高頻、可逆、可驗證、低 blast radius**（回看 Ch 41 五維）的任務值得爬到這裡。即使到了 L3，硬性的安全邊界（預算上限、blast radius 限制、出界即停）依然要在，只是日常不需要人逐一介入。

> 認識論誠實：這四層是一個**實用的劃分，不是業界統一標準**。不同團隊、不同文獻會把光譜切成三層或五層、用不同的名字。重點不是「剛好四層」，而是**「自主是一條連續光譜、要用證據逐步移動」**這個觀念。你可以按自己的場景增減層級。

## 升級的客觀門檻：用 eval 通過率，不用「感覺差不多了」

從一格爬到下一格，**不能靠「跑了一陣子覺得還行」**。要有客觀門檻，而你手上正好有現成的工具：eval（[Ch 34](./34-eval.md)）的通過率，加上 baseline 回歸偵測（[練習 E](./practice-e-eval-tracing.md)）。

升級門檻的設計原則：

- **看通過率而非單次**：LLM 是統計性的，跑 N 次看 pass-rate（Ch 34）。一次成功不算數。
- **要夠高的樣本量**：3 次裡對 3 次（100%）不能跟 100 次裡對 98 次（98%）相提並論。樣本太小的「100%」是假象。
- **沒有顯著回歸**：跟上一次的 baseline 比，退步不能超過你設定的容忍區間（`PROMOTION_BAR` 裡的 `max_regression`，Practice E 的回歸偵測）。低容錯任務可以把容忍設成 0，但對一般任務「一點波動都不准」並不實際——重點是訂出明確的容忍上限，而不是假裝沒有雜訊。
- **影子/金絲雀期夠長**：在真實流量上（而非只在 eval fixture 上）觀察夠久，因為真實輸入的分布比你的測試案例野。

把這套規則寫成一個可跑的「自主層級閘」：

```python
# autonomy_gate.py — 根據 eval 證據決定能不能把 agent 升到下一個自主層級。
# 純標準庫，複製即跑。資料是寫死的範例，真實使用時從你的 eval/trace 餵進來。
from dataclasses import dataclass

LEVELS = ["L0_shadow", "L1_in_the_loop", "L2_on_the_loop", "L3_autonomous"]

@dataclass
class Evidence:
    pass_rate: float        # 最近一輪 eval 通過率（0..1）
    n_runs: int             # 樣本數——太小的高通過率是假象
    baseline_pass_rate: float  # 上一次的 baseline，用來抓回歸
    shadow_days: int        # 已在真實流量上觀察的天數

# 每一格「往上爬」的門檻。越高的層級門檻越嚴。
PROMOTION_BAR = {
    "L0_shadow":      dict(min_pass=0.80, min_runs=30,  max_regression=0.05, min_shadow_days=7),
    "L1_in_the_loop": dict(min_pass=0.90, min_runs=100, max_regression=0.03, min_shadow_days=7),
    "L2_on_the_loop": dict(min_pass=0.95, min_runs=300, max_regression=0.02, min_shadow_days=14),
    # L3 是頂層，沒有「再往上」
}

def can_promote(current: str, ev: Evidence) -> tuple[bool, list[str]]:
    if current == "L3_autonomous":
        return False, ["已在最高層級，沒有可升級的下一格。"]
    bar = PROMOTION_BAR[current]
    reasons = []
    if ev.pass_rate < bar["min_pass"]:
        reasons.append(f"通過率 {ev.pass_rate:.0%} < 門檻 {bar['min_pass']:.0%}")
    if ev.n_runs < bar["min_runs"]:
        reasons.append(f"樣本數 {ev.n_runs} < {bar['min_runs']}（樣本太小，高通過率不可信）")
    regression = ev.baseline_pass_rate - ev.pass_rate
    if regression > bar["max_regression"]:
        reasons.append(f"相對 baseline 退步 {regression:.0%} > 容許 {bar['max_regression']:.0%}（回歸）")
    if ev.shadow_days < bar["min_shadow_days"]:
        reasons.append(f"真實流量觀察 {ev.shadow_days} 天 < {bar['min_shadow_days']} 天")
    return (len(reasons) == 0), reasons

def next_level(current: str) -> str:
    return LEVELS[LEVELS.index(current) + 1]

if __name__ == "__main__":
    # 案例一：證據充足，可從 L1 升到 L2
    ev1 = Evidence(pass_rate=0.96, n_runs=320, baseline_pass_rate=0.95, shadow_days=20)
    ok, why = can_promote("L1_in_the_loop", ev1)
    print(f"L1→L2? {ok}  {next_level('L1_in_the_loop') if ok else why}")

    # 案例二：通過率高，但樣本太少 + 觀察不夠久 → 擋下
    ev2 = Evidence(pass_rate=1.00, n_runs=12, baseline_pass_rate=0.0, shadow_days=2)
    ok, why = can_promote("L0_shadow", ev2)
    print(f"L0→L1? {ok}  {why}")

    # 案例三：通過率達標、樣本與觀察都夠，但相對 baseline 退步（這次 0.96 < baseline 0.99）→ 不只擋升級，更該考慮「降級」
    ev3 = Evidence(pass_rate=0.96, n_runs=300, baseline_pass_rate=0.99, shadow_days=30)
    ok, why = can_promote("L2_on_the_loop", ev3)
    print(f"L2→L3? {ok}  {why}")
```

跑起來：

```
L1→L2? True  L2_on_the_loop
L0→L1? False  ['樣本數 12 < 30（樣本太小，高通過率不可信）', '真實流量觀察 2 天 < 7 天']
L2→L3? False  ['相對 baseline 退步 3% > 容許 2%（回歸）']
```

案例二是關鍵教學點：**通過率 100% 卻被擋下**，因為只跑了 12 次。「12 次全對」不是沒意義，而是**樣本太小、不足以支持放權**——用信賴區間看，真實成功率仍可能明顯低於 100%。這正是 Ch 34 強調「看通過率也要看樣本量」的具體落地。案例三則示範：`can_promote` 偵測到回歸，至少證明**不該升級**；它同時是一個強烈的**降級警訊**——但「要不要真的降一格」該由獨立的維持門檻決定（見下節與練習 2），而不是擋升級就自動降。

> 這些門檻數字（80%、100 次、7 天…）是**示意值，不是業界標準**。真實門檻取決於你的任務容錯度（Ch 41 維度四）：修測試這種高容錯的可以鬆一點，動錢的低容錯任務要嚴得多，甚至 L2/L3 永遠不開放。別照抄這些數字，照抄的是「升級要有客觀、含樣本量、含回歸的門檻」這個結構。

## 降級與停損：信任是雙向的

爬上去的階梯，**一定要能爬下來**。模型換版會讓行為飄（[Ch 39](./39-determinism-resume.md)）、真實輸入分布會漂移、上游 API 會變——任何一個都可能讓一個原本可靠的 agent 突然變差。所以放權之後，監看不能停，而且要有明確的**降級觸發條件**：eval 通過率掉破門檻、線上錯誤率上升、出現新的失敗模式（[Ch 38](./38-failure-modes-debugging.md)）——觸發就自動降回更受控的層級。

除了「逐步降級」，還要有**硬性停損**，這些在**任何層級都該存在**，不是高層級才加：

- **Kill switch**：一個能立刻把 agent 切到「只建議不執行」或完全停掉的開關。出事時你需要的是「現在就停」，不是「改 code 重部署」。
- **預算上限**（[Ch 37](./37-cost-latency-optimization.md)）：單次 run 與單位時間的 token／呼叫次數上限。撞到就停，防止跑飛的 agent 燒錢。
- **Blast radius 限制**：把 agent 能碰的範圍鎖死——工作目錄（`safe_path`，Ch 25）、能呼叫的工具白名單、單筆操作的金額上限。讓「最壞情況」本身就很小。
- **可恢復**（Ch 39）：checkpoint + resume，讓你能安全地中斷一個跑到一半的 agent 而不留下半套狀態，停下來檢查、修正、再續或回退。

> 把停損和「層級」分開想：**層級控制「日常要不要人介入」，停損控制「最壞情況的天花板」。** 即使是 L3 全自主，預算上限和 blast radius 限制依然要在——全自主指的是「日常不用人逐一批」，不是「拿掉所有安全網」。

## 對比與取捨

| 層級 | 何時用 | 人力負擔 | scale | blast radius 控制 |
|---|---|---|---|---|
| **L0 影子** | 還沒有真實表現證據、想零風險收集 | 低（事後比對） | 不適用（不生效） | 無風險（輸出不生效） |
| **L1 人在迴圈裡** | 剛開始生效、低容錯、不可逆動作 | 高（逐一核可） | 受限於人的核可速度 | 最強（人擋每個出口） |
| **L2 人在迴圈上** | eval 證明夠可靠、要 scale 但仍要人盯 | 中（監看 + 抽查） | 高 | 靠 kill switch + 邊界 |
| **L3 全自主** | 高頻、可逆、可驗、低 blast radius | 最低（只處理異常） | 最高 | 全靠硬性邊界與通報 |

沒有哪一層「最好」——選哪層是任務的容錯度與可逆性（Ch 41）跟你累積的證據共同決定的。**同一個 agent 在不同任務、甚至不同工具上可以處在不同層級**（見進階）。

## 踩雷集錦

1. **「跑了一陣子覺得穩，就放成全自主」**：用「感覺」放權是事故的開端。升級要有客觀門檻——含**樣本量**和**回歸偵測**的 eval 通過率，不是個人印象。「跑一個月沒出事」可能只是還沒遇到那個會出事的輸入。
2. **「100% 通過率就能放手」**：樣本量沒到，高通過率撐不起放權的信心。12 次全對不是無意義，而是樣本太小、不足以支持升級（見 autonomy_gate 案例二）。先問「跑了幾次」，再看通過率。
3. **「階梯只能往上爬」**：信任是雙向的。模型換版、輸入漂移、API 變更都會讓 agent 變差，放權後若沒有降級觸發條件和持續監看，你會在它已經退步之後才從事故裡發現。能升要能降。
4. **「全自主＝拿掉所有安全網」**：混淆了「層級」和「停損」。層級控制日常要不要人介入；預算上限、blast radius 限制、kill switch 是天花板，任何層級都要在，L3 也不例外。
5. **「影子模式不用對照組，跑了看 log 就好」**：影子模式的價值在**跟人的真實決策並排比對**算一致率。沒有對照組，你只是收集了一堆「agent 自己覺得它做了什麼」，回答不了「它做得對不對」。

## 進階：再往深一層

- **同一個 agent，不同工具不同層級**：自主程度不必是整個 agent 一個數字。常見且務實的做法是**按工具分級**——`read_file`、`list_directory` 這類唯讀工具可以 L3 全自主（`allow`，前提是讀到的結果本身不含敏感資料外洩風險、也沒有高額查詢成本），但 `run_shell`、寫 production 的工具永遠停在 L1（`ask`，人逐一核可）。這正是 Ch 25 gate 逐工具決策的延伸：把「整個 agent 多自主」拆成「每個工具多自主」，你能在放手 scale 的同時，把真正危險的那幾個動作牢牢鎖在人手上。
- **金絲雀（canary）放量**：升級不必一次切全部流量。先讓**一小比例**的真實流量走新層級（例如 5%），其餘維持舊層級當對照，比較兩者的結果與錯誤率，沒問題再逐步放大。這借用了傳統部署的金絲雀概念，把「升級」本身也變成可回退的漸進過程。
- **信任會因環境變化而需要重證**：你在模型 A 上爬到 L3 的 agent，換到模型 B（或同模型新 snapshot）後，過去的 eval 證據**不自動繼承**——行為可能飄（Ch 39）。負責任的做法是換版時自動降級回 L1/L0，重跑 eval、重新累積證據再往上爬。把「換版即重證」做成流程，而不是靠人記得。

## 動手練習

1. 跑 `autonomy_gate.py`，然後改 `PROMOTION_BAR` 的數字模擬一個「低容錯任務」（把 `min_pass` 拉到 0.99、`min_runs` 拉到 1000），看同樣的證據在嚴格門檻下會不會被擋。體會「門檻該由任務容錯度決定」。
2. 把案例三（出現回歸）改寫成一個 `should_demote(current, ev)` 函式：當通過率掉破「當前層級的維持門檻」時回傳該降到哪一層。想清楚「升級門檻」和「維持門檻」為什麼不該是同一個數字（提示：避免在門檻邊緣反覆升降的抖動）。
3. 為你 Ch 41 練習選的那個任務，畫出它的信任階梯：每一格要看什麼證據才放行？哪些工具該永遠停在 L1？它的 kill switch 和預算上限長什麼樣？

## 本章重點整理

- agent 的自主程度是一條可往上爬、也**必須能往下降**的滑桿，不是上線時的一次性選擇。
- 四個參考層級：L0 影子（不生效、收集證據）→ L1 人在迴圈裡（逐一核可）→ L2 人在迴圈上（自己做、人盯）→ L3 全自主（只在出界時通報）。它是光譜的劃分，不是業界統一標準。
- 升級要靠客觀門檻：含樣本量與回歸偵測的 eval 通過率（Ch 34 / 練習 E），不是「感覺穩了」。100% 通過率若樣本太小是假象。
- 停損與層級是兩回事：kill switch、預算上限、blast radius 限制在**任何層級**都要在，L3 也不例外。信任要雙向，發現退步要能自動降級。
