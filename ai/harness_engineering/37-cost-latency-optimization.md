# Ch 37 — 成本與延遲優化

> **目標**：你的 agent 能跑、夠安全了——但一個任務要花 $0.4、跑 90 秒，量大起來就養不起、也沒人想等。本章談怎麼把 agent 從「能跑」做到「划算地跑」。讀完你能說出：agent 的成本為什麼會**隨回合數膨脹**（每回合都重送整段歷史，token 是疊加的）、四個輸入/輸出費率為什麼差到 50 倍、省成本的幾根主要槓桿（prompt caching、模型分級/路由、context 管理、限制輸出、減少回合、批次）、壓延遲的幾根槓桿（streaming、並行、快取也降 TTFT、用快模型、少回合），以及**成本 / 延遲 / 品質是個三角**——優化任何一角都在動另外兩角。核心心態：**先量再調**（沒有 Ch 35 的數據，優化都是瞎猜），而且**優化要對著瓶頸下手**，不是把每招都用一遍。

> **環境**：Python + Anthropic SDK。大量回頭用前面的工具：prompt caching（[Ch 17](./17-prompt-caching.md)）、context 壓縮與裁剪（[Ch 13](./13-context-compaction.md)、[Ch 16](./16-tool-result-pruning.md)）、streaming（[Ch 8](./08-streaming.md)）、subagent/並行（[Ch 27](./27-multi-agent-orchestration.md)、[Ch 31](./31-background-tasks.md)）、以及 observability（[Ch 35](./35-observability.md)）——成本/延遲的數據從那裡來。本章的具體費率、TTL、批次折扣等數字**會隨模型與方案調整，以官方 pricing 為準**；重點在「哪根槓桿動哪個成本」的模型。

## 為什麼需要這個？agent 的成本會「隨回合膨脹」

先算一筆帳，戳破一個常見誤解：「一次 LLM 呼叫沒幾分錢，agent 能貴到哪去？」

關鍵在於 **agent 是多回合的，而每一回合都要把「到目前為止的整段對話」重新送進模型**（Ch 6 講過：API 無狀態，歷史是你每次重送的）。所以一個 10 回合的 agent，它的 input token 不是付 1 份，而是接近付了 **1+2+3+…+10 份**——歷史像滾雪球，越後面的回合，每回合送進去的 context 越大：

```
   回合 1：[sys+tools] + msg1                    ← 送 ~5k token
   回合 2：[sys+tools] + msg1 + result1 + msg2   ← 送 ~7k token
   回合 3：[sys+tools] + msg1..result2 + msg3    ← 送 ~9k token
     ⋮                                              （每回合都含前面全部）
   回合 10： …………………………………………………  ← 送 ~25k token
   ───────────────────────────────────────────
   總 input ≈ 各回合相加，跟「回合數 × 平均 context」成正比 → 接近回合數的平方
```

這就是為什麼**一個會「多繞幾圈」的 agent 特別燒錢**：每多一個回合，不只多一次呼叫，還把**之前累積的整個 context 又付了一次**。延遲同理——每回合都要重新處理那一大段 input，回合越多、context 越大，使用者等越久。

> **「接近平方」要加兩個但書**：上面的雪球只描述**會不斷增長的那部分**（messages 歷史）——當每回合新增量大致固定、且歷史每次都未快取地重送，這部分的累積成本約是 `1+2+…+n`，接近回合數平方。但實務上有兩個拉平的因素：(1)固定的 system+tools 是**線性項**（每回合一份，不隨歷史長），(2)**prompt caching 會把穩定前綴改成 ~0.1× 的快取讀取**，大幅壓低重送的單價。所以真實曲線介於線性與平方之間，取決於你的快取命中率與歷史增長速度——但「回合越多、單位成本越糟」這個方向不變。

所以 agent 的成本/延遲優化，跟單次呼叫優化**重點不同**：單次呼叫你想「這次 prompt 能不能短一點」；agent 你要想「**怎麼讓累積的 context 不要爆、怎麼讓回合數不要失控、怎麼讓重複的前綴不要每次重算**」。這正好把前面幾章（caching、壓縮、裁剪、少回合的工具設計）串成一條經濟學主線。

## 先建立直覺：四種 token 費率，差到數十倍

優化前先看清「錢花在哪」。一次呼叫的 `usage`（Ch 35）裡有四種 token，**費率天差地別**（以下用 opus-4-8 的相對比例示意，實際數字以官方為準）：

```
   token 種類              相對單價（以「未快取輸入」=1 為基準）
   ─────────────────────────────────────────────
   cache 命中的輸入         ~0.1×     ← 最便宜！快取讀取
   未快取的輸入             1×        ← 基準
   cache 寫入（建快取）     ~1.25×    ← 比一般輸入貴一點點
   輸出（output）           ~5×       ← 最貴！
```

兩個直覺：

1. **輸出最貴**（這裡約是輸入的 5 倍，且跨模型常見輸出單價遠高於輸入）。所以「讓模型少廢話、限制 `max_tokens`、別叫它把整個檔案抄一遍」直接省錢。
2. **快取命中的輸入只要約 1/10**。agent 有一大段每回合都一樣的前綴（system + tools），這段如果每次都「未快取」地重付，就是在燒錢——caching 把它打到一折（Ch 17）。

> **先量再調**：上面的比例是示意；你**自己 agent** 的錢花在哪，要從 Ch 35 的 cost 數據看。可能是「輸出太長」、可能是「回合太多」、可能是「快取沒命中」——三種的解法完全不同。**對著最大那塊下手，別把每招都做一遍。**

## 一、省成本槓桿一：prompt caching（最高槓桿，幾乎必做）

agent 的 system + 工具定義是「每回合都一樣的大前綴」，這正是 prompt caching 的理想對象（Ch 17 整章在講）。命中時這段輸入只要約 1/10 價、而且**不用重新處理 → 同時降延遲**。

```python
# 在穩定的大前綴（tools / system）尾端設 cache 斷點
resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": LONG_STABLE_SYSTEM_PROMPT,
        "cache_control": {"type": "ephemeral"},      # ← 這段之前的前綴會被快取
    }],
    tools=TOOLS,
    messages=conversation,
)
# 驗收：第一次呼叫看 usage.cache_creation_input_tokens > 0（這次在「建」快取，付 ~1.25× 寫入價）；
#       TTL 內、同前綴的後續呼叫才看 usage.cache_read_input_tokens > 0（命中、付 ~0.1× 讀取價）。
```

重點回顧（細節見 Ch 17）：

- **快取獎勵穩定前綴、懲罰任何對前段的改動**。system 裡塞動態值（時間戳、隨機 ID）會讓快取每次失效——這是「設了 cache_control 卻沒省到」的頭號原因。
- **壓縮/裁剪可能破壞快取**（Ch 13/16）：快取階層是 `tools → system → messages`，**改寫某一層，只會讓「那一層及其之後」的快取失效**。所以改寫歷史中段，只會讓那之後的前綴重算——若你的斷點只設在 `tools/system`，動 messages 後段不會打到前段那塊大快取。重點是「壓縮省未來 token」和「保住命中省當下」之間要權衡，並把壓縮點設在快取斷點之後，別一有點長就把前段也動了。
- **用 `usage.cache_read_input_tokens` 監控命中率**（Ch 35）。命中率掉了通常代表前綴不小心變動了。

## 二、省成本槓桿二：模型分級與路由（讓貴模型只做該它做的事）

不是每一步都需要最聰明（最貴）的模型。一個任務裡，「判斷該用哪個工具」「分類一段文字」「總結一個檔案」這種簡單步驟，用便宜的小模型（如 haiku）就夠；只有「需要深度推理、規劃、寫關鍵程式碼」才動用大模型（opus）。

```python
def pick_model(step_kind: str) -> str:
    # 簡單/高頻的步驟用便宜模型，難的才上貴模型
    if step_kind in ("classify", "extract", "summarize", "route"):
        return "claude-haiku-4-5-20251001"     # 便宜、快
    return "claude-opus-4-8"                    # 貴、強，留給真正難的推理
```

兩個常見的分級模式：

- **路由（routing）**：用一個便宜模型先判斷「這個請求難不難」，簡單的直接讓小模型答完，難的才轉給大模型。省下「大模型回答簡單問題」的浪費。
- **orchestrator-worker 的成本分層（Ch 27）**：orchestrator（規劃、彙整）用 opus，fan-out 出去的 worker subagent 用 haiku。worker 數量多、又是相對機械的檢索/抽取，用便宜模型省最多——這在 Practice D 的多 agent 研究工作流就用過。

> **分級的前提是有 eval（Ch 34）**：換小模型省了錢，但某類任務可能默默退化。**換完一定跑 eval 比成功率**——便宜但做錯不算省，那是把成本轉嫁成「重試」和「使用者不爽」。

## 三、省成本槓桿三：管住 context 大小與回合數

回到開頭那條「成本 ∝ 回合數 × context 大小」。這兩個因子都能壓：

- **壓縮歷史（Ch 13）**：對話長到一定程度，把舊的中間過程摘要成短結論，砍掉重送的 token。代價是破壞快取（見上），所以**逼近門檻再壓**，不是一長就壓。
- **裁剪工具結果（Ch 16）**：一個 `read_file` 回傳 5000 行、其中只有 20 行相關——把龐大的舊工具結果裁掉或摘要，別讓它在後續每回合都被重送。工具結果常是 context 膨脹的最大來源。
- **減少回合數**：每個多餘回合都是「一次呼叫 + 重付整段 context」。減少回合的手段其實在前面：**好的工具設計（Ch 18-20）**讓模型一次就拿到需要的東西、不用反覆試；**清楚的工具描述（Ch 19）**減少選錯工具的來回；**planning（Ch 28）**讓它別亂繞。一個「平均 6 回合辦完」的 agent 比「平均 12 回合」的便宜也快一倍——**減回合常是 CP 值最高的優化**。

## 四、省成本槓桿四：限制輸出 + 批次

- **限制輸出（output 最貴）**：設合理的 `max_tokens` 上限；prompt 裡明確要求「簡潔」「只回 X」；別叫模型把整個檔案/整段內容原封不動抄回來（要它回「改哪幾行」就好）。結構化輸出（Ch 32）也有幫助——回一個精簡的 JSON 比回一大段散文省。
- **批次（Batch API）**：如果你的任務**不需要即時**（離線跑 eval、批量處理一堆文件、夜間任務），用 Anthropic 的 **Message Batches API** 可拿到約 **50% 折扣**，代價是非同步、有結果延遲（通常數分鐘到小時級）。**這是「離線吞吐」場景最大的一根省錢槓桿**——但對「使用者在等」的互動式 agent 不適用。

## 五、延遲是另一回事：壓延遲的槓桿

成本和延遲常一起談，但**它們不是同一件事**——有些招省錢不一定變快，有些招變快不一定省錢。壓延遲的主要槓桿：

- **streaming（Ch 8）**：不改變總時間，但讓使用者**馬上看到字一個個冒出來**，把「等待」變「在看」。對互動式 agent 是體感延遲的最大改善——優先做。
- **prompt caching 也降延遲**：命中的前綴不用重新處理，**首 token 時間（TTFT）明顯變短**。所以 caching 是「同時省錢又變快」的少數招——優先做。
- **並行（Ch 27 / 31）**：彼此獨立的子任務同時跑，而不是排隊。orchestrator fan-out 出 5 個 subagent 並行檢索，總延遲接近「最慢的那一個」而不是「五個相加」。模型一個回合內回多個 `tool_use`、harness 並行執行它們，也是同理。
- **用快模型做延遲敏感的步驟**：小模型（haiku）通常比大模型快。延遲敏感、又不需要深推理的步驟用它。
- **減少回合數**：每個回合都是一次「送 context → 等模型 → 跑工具」的往返。少一個回合就少一個完整往返的延遲——又是它。

> **延遲要看分位數，不是平均（Ch 35）**：p50 看起來很好、p95/p99 慢到爆，是 agent 常態（偶爾某次多繞好幾圈）。優化延遲時盯著**尾巴（p95/p99）**，因為那才是使用者真正抱怨的「怎麼這次卡住了」。

## 六、成本 / 延遲 / 品質：一個三角

沒有「全都要」的免費午餐。大多數調整是在這三者間取捨：

```
                品質（成功率、答得好不好）
                       ▲
                      ╱ ╲
                     ╱   ╲
                    ╱     ╲
            成本 ◀─────────▶ 延遲
```

- 換小模型省成本、常也變快，但**可能掉品質**。
- 多跑幾次取最好（self-consistency）、加 verification 步驟，**提升品質但更貴更慢**。
- 並行省延遲，但**不省成本**（一樣的 token，只是同時付）。
- 壓縮 context 省成本省延遲，但壓太狠**丟資訊、掉品質**。

所以優化前先問：**這個 agent 的瓶頸是哪一角？** 給開發者用的 coding agent，延遲容忍度高、品質至上；給終端使用者的客服 agent，延遲和成本都很要命。**沒有通用最佳解，只有「對這個場景，該往哪一角讓步」。** 而要回答「現在卡在哪一角」，你需要 Ch 35 的數據——這就是為什麼「先量再調」是本章的核心心態。

## 對比與取捨

| 優化招 | 省成本 | 降延遲 | 風險/代價 | 什麼時候用 |
|---|---|---|---|---|
| **prompt caching**（Ch 17） | ✓✓（前綴打一折） | ✓（TTFT↓） | 前綴一變就失效 | 幾乎必做：穩定大前綴的 agent |
| **模型分級/路由** | ✓✓ | ✓（小模型快） | 可能掉品質 | 簡單步驟多時；換完必跑 eval |
| **壓縮/裁剪 context**（Ch 13/16） | ✓✓ | ✓ | 破壞快取、可能丟資訊 | context 快爆時，逼近門檻再做 |
| **減少回合數**（好工具/prompt） | ✓✓ | ✓✓ | 要花工夫設計工具 | CP 值最高，優先投資 |
| **限制輸出 max_tokens** | ✓（輸出最貴） | ✓ | 砍太狠會截斷 | 模型愛廢話/愛抄全文時 |
| **Batch API** | ✓✓（~50% off） | ✗（非同步變慢） | 不即時 | 離線/批量/夜間任務 |
| **streaming**（Ch 8） | ✗ | ✓✓（體感） | 無 | 互動式 agent，優先做 |
| **並行**（Ch 27/31） | ✗（token 不變） | ✓✓ | 複雜度↑、瞬時 rate limit | 有獨立子任務時 |

> 一眼看出兩個「最接近免費午餐」的招：**caching**（省錢又降 TTFT）和**減回合**（省錢又降延遲）——這兩個是**低風險、該優先檢查**的槓桿。但別當成零成本：caching 有最小 token 門檻、首次寫入溢價、TTL/命中率要顧；減回合若砍掉了必要的驗證步驟也可能掉品質。優先做，但一樣要量測與跑 eval 確認。其餘的招取捨更明顯。

## 踩雷集錦

1. **沒量就調**：不知道錢花在輸出、回合、還是沒命中快取，就開始亂優化——白費力氣。先看 Ch 35 的 cost/latency 數據，對著最大那塊下手。
2. **忽略「context 隨回合膨脹」**：以為 agent 貴在「呼叫次數」，其實大頭常是「每回合重送的累積 context」。減回合 + 管 context 才是治本。
3. **設了 cache_control 卻沒省**：前綴裡有動態值（時間戳）、或請求間隔超過 TTL、或壓縮把前綴改了——快取根本沒命中。用 `cache_read_input_tokens` 驗。
4. **為了省錢無腦換小模型、不跑 eval**：某類任務默默退化，重試/錯誤反而更貴。換模型必須跟 eval 綁在一起（Ch 34）。
5. **把成本和延遲當同一件事**：並行省延遲但不省成本；batch 省成本但更慢。搞清楚你要的是哪個。
6. **只看平均延遲**：p50 漂亮、p95 爛掉。使用者抱怨的是尾巴，盯 p95/p99。
7. **讓模型抄全文**：要它「輸出完整修改後的檔案」而不是「只說改哪幾行」——輸出最貴，這是純浪費。
8. **過度並行撞 rate limit**：一次 fan-out 50 個 subagent，瞬時 token/請求速率爆表反而被限流、整體更慢。並行要有上限（Ch 27/31）。
9. **為了快取/省錢犧牲正確性**：不敢更新該更新的 system、壓縮壓到丟關鍵資訊。**先做對，再省錢**——錯的便宜答案沒有價值。
10. **過早優化**：還在驗證 agent 能不能把任務做對時，就忙著省那幾分錢。先讓它「做對」，量出真實成本後再針對瓶頸優化。

## 進階：再往深一層

- **快取的經濟學就是 context engineering 的經濟學（Ch 17）**：縮小 context（省未來 token）vs 保住快取前綴（省當下）是同一個張力的兩面。理解這個，你才知道「該不該壓、何時壓」。
- **成本歸因（cost attribution）**：在 multi-agent / 多步系統裡，把成本拆到「哪個 subagent、哪類步驟、哪個工具」最花錢（用 Ch 35 的 trace + tag 分群）。常會發現 80% 成本來自某一類步驟——那才是該優化的點。
- **推測式與預取（speculative / prefetch）**：在等使用者輸入或某個慢工具時，先把很可能要做的下一步算起來。能降體感延遲，但算錯就是浪費——適合「下一步高度可預測」的場景。
- **快取感知的壓縮策略**：壓縮時只動 messages 後段、別碰前面 tools/system 的早期斷點，就能「省未來 token」又「保住前段快取」（Ch 13/17）。設計壓縮點時把快取斷點一起考慮進去。
- **長 TTL 快取**：間隔較久才會再打的 agent，可用 1 小時 TTL 的快取（寫入貴一點、但跨越更長間隔仍命中）。要算清楚「寫入溢價 vs 命中省下的」划不划算。
- **品質省下的隱形成本**：一個更準的 agent，回合更少、重試更少、人工介入更少——**品質本身就是省錢**。別把「優化」窄化成「砍 token」，把成功率拉高常是更大的省。

## 動手練習

1. **量出成本結構**：拿你的 agent（或 Practice C/D），用 Ch 35 的 `cost_usd` 記每回合四種 token，跑一個真實任務。畫出「輸入/快取讀/快取寫/輸出」各佔多少錢——找出最大那塊。
2. **開快取看差異**：對同一個任務，關快取跑一次、開快取（system+tools 設斷點）跑一次。比較總成本和 TTFT，確認 `cache_read_input_tokens` 有命中。
3. **模型分級**：把一個「簡單步驟（如總結檔案）用 haiku、難步驟用 opus」的路由加進去，跑 eval（Ch 34）比成功率與成本。確認省了錢且沒掉品質。
4. **減回合實驗**：找一個你的 agent「常多繞幾圈」的任務，改進一個工具的描述或結果格式（Ch 19/20），看平均回合數和成本掉多少。
5. **延遲 vs 成本**：把一個有 3 個獨立子查詢的任務，從「序列跑」改成「並行跑」（Ch 27）。記錄總延遲和總成本——驗證延遲降了、但成本（token）幾乎沒變。
6. **batch 省錢**：把一批 50 個離線分類任務，分別用即時 API 和 Message Batches API 跑，比較總價與完成時間，體會「用延遲換錢」。

## 本章重點整理

- **agent 成本會隨回合膨脹**：每回合重送整段累積 context，會增長的歷史部分累積成本接近回合數的平方（固定的 system+tools 是線性項、快取又會壓低重送單價，所以真實曲線在線性與平方之間）。方向不變：減回合 + 管 context 是治本。
- 四種 token **費率差到數十倍**：cache 讀 ~0.1× < 未快取輸入 1× < cache 寫 ~1.25× ≪ **輸出最貴**。先量出錢花在哪，對最大那塊下手。
- **省成本槓桿**：prompt caching（Ch 17，最高槓桿）、模型分級/路由（小模型做簡單步驟）、壓縮/裁剪 context（Ch 13/16）、減回合（好工具/prompt，CP 值最高）、限制輸出、Batch API（離線 ~50% off）。
- **降延遲槓桿**：streaming（體感，Ch 8）、caching（降 TTFT）、並行（Ch 27/31）、快模型、減回合。**streaming、caching、減回合是反作用最小、該優先檢查的低風險槓桿（仍需量測驗證，不是零成本）。**
- **成本 ≠ 延遲**：並行省延遲不省成本；batch 省成本但更慢。搞清楚你優化的是哪個。
- **成本 / 延遲 / 品質是三角**：優化一角會動另兩角。先確認你的 agent 瓶頸在哪角（要靠 Ch 35 數據），再決定往哪讓步。
- **先量再調、別過早優化、換模型必跑 eval**：沒數據的優化是瞎猜；錯的便宜答案不是省，是把成本轉嫁。
