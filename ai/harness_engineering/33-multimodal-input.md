# Ch 33 — 多模態輸入

> **目標**：到目前為止，agent 看到的世界都是文字。但很多真實任務需要它**看圖**：讀一張錯誤截圖來除錯、看設計稿產對應的前端程式碼、解析 PDF 報表、看圖表抓趨勢、做瀏覽器自動化（截圖 → 判斷 → 下一步）。本章談**多模態輸入**——怎麼把圖片、PDF 等非文字內容餵給模型。讀完你能說出多模態訊息的結構（content 是一個**混合 text 與 image block 的清單**）、圖片從哪來（base64 / URL / 檔案）、圖片在 token 與成本上的代價（圖片**不便宜**，而且代價跟解析度相關）、最關鍵的 agent 接法——**工具結果本身可以回傳圖片 block**（截圖工具讓 agent「看到」畫面，接 Ch 20）、以及多模態的限制（讀不準小字、數不準數量、空間定位有限，別過度依賴）。

> **環境**：Python + Anthropic SDK。多模態是 **Messages API 的原生能力**——你已經熟的 `messages` 結構直接支援圖片，只是 content block 多了 `image`/`document` 型別。**你正在用的這個 session 就是多模態的**：我是個多模態 LLM，`Read` 工具能直接「看」圖片檔（PNG/JPG…），系統也明說「使用者常請我讀截圖」。本章拿這個當第一手教材，並標明哪些是 API 規格、哪些是 harness 的工具設計。

## 為什麼需要這個？有些資訊天生不是文字

純文字 agent 有一整類任務做不了，因為**關鍵資訊根本不在文字裡**：

- **「這個畫面壞了，幫我看看」**——使用者貼一張截圖。錯誤訊息、版面跑掉、按鈕位置，全在圖裡。你不可能要使用者把整個畫面「描述成文字」。
- **「照這個設計稿做出前端」**——設計稿是一張圖。間距、顏色、層次，要模型**看著**它產 code。
- **「這份 PDF 報表的第 3 季數字是多少」**——數字在表格、在圖表裡，可能還是掃描的影像。
- **瀏覽器/桌面自動化**——agent 要操作 GUI，就得**看著當前畫面**決定「點哪裡、下一步做什麼」，再截一張圖看結果。這是一個「看 → 動作 → 再看」的多模態迴圈。

問題的本質：**現實世界有大量資訊以視覺形式存在**，硬要轉成文字要嘛不可能、要嘛丟失關鍵（版面、配色、空間關係）。要讓 agent 處理這些任務，它就得能**直接吃圖**。

**多模態輸入就是這個能力：把圖片（或 PDF）跟文字一起放進訊息，讓模型同時「讀」文字和「看」圖。** 在 Anthropic API 裡，這不是另一個端點或另一套機制——就是你熟悉的 `messages`，只是某個 message 的 `content` 從「一段字串」變成「一個清單，裡面混著文字 block 和圖片 block」。

關鍵心態：**多模態不是一個新世界，是既有訊息結構的自然延伸。** 你已經會組 messages 了，多模態只是多學一種 content block。

## 先建立直覺：content 是「圖文並茂的一頁」，不是「純文字」

把一則 user message 的 content 想成一頁文件。純文字 agent 的那頁只有字；多模態的那頁可以**圖文穿插**——一段字、一張圖、再一段字。模型「讀」這一頁時，圖和字它都看得到。

```
   純文字 message：                      多模態 message：
   content = "這段程式碼為什麼錯？"        content = [
                                            {type:"text",  text:"這個畫面為什麼壞了？"},
                                            {type:"image", source:{...截圖...}},
                                            {type:"text",  text:"我預期按鈕在右邊"},
                                          ]
        ↑ 一個字串                            ↑ 一個 block 清單，圖文混排
```

要點：**content 從「字串」升級成「block 清單」後，文字和圖片是平等的 block**，可以任意順序穿插。你可以「先給指示、再貼圖、再補充」，模型按順序理解。（小撇步：官方觀察到**圖片放在文字之前**通常效果略好，沒特殊需求時不妨先放圖、再放問題。）這跟 tool use 的 content（也是 block 清單，含 `tool_use`/`tool_result`）是同一套機制——**Anthropic 的訊息內容一直都是 block 清單**，你只是現在用到 `image` 這種 block。

> **這個 session 天天在做**：當你給我一張截圖的路徑，我的 `Read` 工具會把那張圖**當成視覺內容**呈現給我（系統提示說得很明白：「Read 工具能讀圖片，內容會以視覺方式呈現」）。於是我能「看到」你的畫面、讀出上面的錯誤、指出版面問題。這就是多模態輸入在運作——只是 harness 把「讀檔 → 變成 image block」這步包成了 `Read` 工具。

## 一、怎麼把圖片放進訊息：三種來源

一個 `image` content block 的核心是 `source`——告訴 API「圖在哪、什麼格式」。常見三種來源：

```python
import base64
from anthropic import Anthropic

client = Anthropic()

# 來源 A：base64（最通用——本地檔案讀進來、編碼、塞進 block）
with open("screenshot.png", "rb") as f:
    img_b64 = base64.standard_b64encode(f.read()).decode("utf-8")

resp = client.messages.create(
    model="claude-opus-4-8", max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "這個畫面為什麼壞了？錯誤訊息是什麼？"},
            {
                "type": "image",
                "source": {
                    "type": "base64",
                    "media_type": "image/png",      # 要跟實際格式相符
                    "data": img_b64,
                },
            },
        ],
    }],
)
print(resp.content[0].text)
```

三種來源：

- **base64（來源 A，最通用）**：把圖片位元組 base64 編碼後直接內嵌進 block。本地檔案、剛截的圖、動態產生的圖都適用。代價是訊息體積變大（base64 比原始位元組大約 1/3）。
- **URL**：給一個公開可取的圖片網址，由 API 去抓。省去編碼與內嵌，但圖必須是 API 抓得到的 URL。
- **Files API / 檔案參照**：先把圖片上傳取得一個 file id，之後用 `source` 直接參照（block 形狀是 `source: {"type": "file", "file_id": "..."}`，目前走 beta Files API，呼叫要帶對應的 beta 旗標）。適合重複使用同一張圖，省得每次重傳。

實作要點：

- **`media_type` 要對**：`image/png`、`image/jpeg`、`image/gif`、`image/webp` 等。填錯格式會出問題。
- **支援的格式有限**：常見的 PNG/JPEG/GIF/WebP。其他格式（含很多 RAW、TIFF）要先轉檔。注意 **GIF 只取第一幀**，不能拿來分析動畫。
- **一則訊息可放多張圖**：content 清單裡放多個 image block 即可（「比較這兩張設計稿」）。但每張都要算成本（下一節）。

## 二、圖片的成本：它不便宜，而且跟解析度相關

這是多模態最該記住的工程現實：**圖片消耗的 token 比你想像的多，而且跟圖的尺寸（像素）成正比。**

Anthropic 的大致規則（**確切公式與上限以官方文件為準**，這裡給數量級直覺）：

- 一張圖消耗的 token **約等於 `(寬 × 高) / 750`**（像素數除以約 750）。所以一張 1000×1000 的圖 ≈ 1300+ tokens——抵得上一大段文字。
- 太大的圖會被**自動縮放**到某個上限（長邊與總像素都有限制）。**上限跟模型有關**：一般模型大約是長邊 1568px、約一百多萬像素（≈1600 image tokens 量級）；而原生視覺較強的模型（如 Opus 4.7/4.8）上限更高（長邊約 2576px、image tokens 上限更大）。**確切數字以你用的模型在官方文件上的規格為準。** 超過上限的高解析度圖，多花的位元組不會換來更多細節，只是浪費頻寬。

由此導出幾條實務原則：

- **送之前先縮放到「夠用就好」的解析度**。把一張 4K 截圖縮到模型上限附近（例如一般模型的 1568px 長邊），token 省一大截，而模型能讀到的資訊幾乎不變（因為它本來就會縮）。**別把超大原圖直接塞進去。**（縮的目標值看你用哪個模型——高解析模型可以留更大。）
- **裁切到相關區域**。只關心錯誤對話框？裁出那塊，而不是送整個 4K 桌面。又省 token、又讓模型聚焦。
- **圖片吃 context 也吃錢**。在 agent 迴圈裡（尤其每步都截圖的自動化），圖片會**快速堆積** context 與成本。要有意識地管理——舊截圖該不該留在 context？（接 Ch 13 壓縮、Ch 20 工具結果設計。）
- **多張圖時尤其要克制**。「比較 10 張設計稿」= 10 張圖的 token 疊加，可能瞬間吃掉大半視窗。

核心原則：**圖片是「高 token 密度」的輸入，要像管預算一樣管它**——縮放、裁切、只留需要的、用完考慮移除。

## 三、agent 接法：工具結果可以回傳圖片（最關鍵的一招）

前面是「使用者在訊息裡貼圖」。但在 **agent** 裡，更強大的用法是：**工具執行後，把圖片當成 `tool_result` 的內容回給模型**。這讓 agent 能「主動去看」東西——截一張圖、然後在迴圈裡看到它。

回想 Ch 20：`tool_result` 的 content 也是一個 block 清單。**它可以包含 `image` block**，不只是文字。於是你可以做一個「截圖工具」：

```python
# 一個截圖工具：執行後回傳「圖片 block」當 tool_result，讓 agent 在迴圈裡「看到」畫面
def take_screenshot_tool_result(tool_use_id: str) -> dict:
    png_bytes = capture_screen()                      # 你的截圖實作（瀏覽器/桌面）
    img_b64 = base64.standard_b64encode(png_bytes).decode("utf-8")
    return {
        "type": "tool_result",
        "tool_use_id": tool_use_id,
        "content": [
            {"type": "text", "text": "目前畫面截圖如下："},
            {"type": "image",
             "source": {"type": "base64", "media_type": "image/png", "data": img_b64}},
        ],
    }
```

這解鎖了一整類 agent：

- **瀏覽器/GUI 自動化**：`截圖 → 模型看畫面決定點哪 → 點擊工具 → 再截圖看結果` 的「看-動作-看」迴圈。模型靠視覺判斷下一步，就像人操作 GUI。
- **視覺驗證**：agent 改完前端，截圖看「長得對不對」，不對再改（接 Ch 28 的完成標準、Ch 30 的 Stop hook 可以強制「截圖驗證過才算完成」）。
- **讀視覺化資料**：跑出一張圖表後，agent 截圖「看」趨勢，而不是只看原始數字。

> **這個 session 的 `Read` 讀圖就是這個機制的一種**：harness 把「讀一個圖片檔」做成工具，工具結果就是視覺內容，於是迴圈裡的我「看得到」那張圖。把它推廣到「截當前螢幕」，就是 GUI 自動化 agent 的核心。

但要注意成本與 context 的放大效應：**「看-動作-看」迴圈每一步都產生一張圖**，而圖很貴（第二節）。一個跑 20 步的自動化任務 = 20 張截圖堆進 context。所以這類 agent 特別需要：縮放/裁切每張截圖、考慮只保留**最近幾張**而非全部歷史截圖（舊的截圖對「現在該做什麼」往往沒用了）。

## 四、PDF 與文件：不只是圖

除了圖片，Anthropic 也支援把 **PDF 當文件輸入**（`document` 類型的 block）。它跟單純圖片不同的地方在於：模型同時拿到 PDF 的**文字層**和**每頁的視覺**——所以它既能「讀」文字，也能「看」版面、表格、圖表。

這讓 agent 能處理「文字 + 視覺混合」的真實文件：

- 讀一份有表格和圖表的財報，問裡面的數字。
- 解析一張掃描的發票（沒有文字層，純影像）——靠視覺 OCR-like 能力讀出欄位。
- 看一份有流程圖的設計文件，理解架構。

成本同理要注意：PDF 的每一頁都帶視覺，**頁數多 = token 多**。長 PDF 要考慮只送相關頁、或先用便宜方式定位再細看（呼應 Ch 26 抽取型 subagent：派個便宜模型先掃出「答案在第幾頁」）。

> **確切的 PDF 支援細節（頁數上限、大小上限、計費方式）以官方文件為準**，且會隨版本演進。本章要你記住：**PDF 是「文字 + 每頁影像」的混合輸入，按頁累積成本**。

## 五、多模態的限制：別把它當完美的眼睛

視覺能力很強，但有明確的弱點，過度依賴會出事：

- **小字 / 低解析度讀不準**：截圖裡的小字、被壓縮糊掉的文字，模型可能讀錯。關鍵文字（錯誤碼、數字）若能用文字形式提供，就別只靠圖。
- **精確計數不可靠**：「圖裡有幾個紅點」「表格有幾列」——模型對精確數量常常數錯。需要精確 count 的別只靠看圖。
- **空間定位有限**：「那個按鈕的精確像素座標」——模型能大致知道位置，但給不出可靠的精確座標。GUI 自動化要靠這個時，常需搭配其他定位手段（無障礙樹、DOM、元素標註）。
- **會「腦補」**：跟文字一樣，模型看圖也可能產生看似合理但不存在的細節（幻覺）。關鍵判斷要交叉驗證。
- **有些用途官方明確不建議**：不要拿它來**辨識/指認圖中的人物身分**、不要靠它判斷一張圖**是不是 AI 生成**、醫療影像也**不可當診斷依據**。這些是準確度與責任上的紅線，不只是「讀不準」而已。

實務上的對策：**圖文並用**。能用文字精確表達的（錯誤訊息全文、DOM、座標）就用文字補上，圖片用來提供文字給不了的（版面、配色、整體狀態）。**圖是補充視覺脈絡的，不是用來取代精確的文字/結構化資料。**

核心原則：**多模態給 agent「大致看懂一個畫面」的能力，不是「像素級精確讀取」的能力。** 設計任務時，把需要精確的部分留給文字/結構化輸入（Ch 32），把需要視覺理解的部分交給圖。

## 對比與取捨

| 設計選擇 | 選項 A | 選項 B | 怎麼選 |
|---|---|---|---|
| 圖片來源 | URL | **base64 內嵌** | 本地/動態圖用 base64；公開可取網址用 URL；重複用同張圖考慮 Files API |
| 送圖解析度 | 直接送原始 4K 大圖 | **先縮放/裁切到夠用** | 一律縮裁：模型本來就會縮，原圖只是浪費 token |
| agent 怎麼「看」 | 只能等使用者貼圖 | **截圖工具回 image tool_result** | 工具回圖：解鎖 GUI 自動化、視覺驗證 |
| 自動化迴圈的歷史截圖 | 全部留在 context | **只留最近幾張** | 只留最近：舊截圖對當下決策沒用、又貴 |
| 精確文字/數字 | 只靠看圖讀 | **同時用文字/結構化提供** | 圖文並用：圖讀不準小字與精確數量 |
| 長 PDF | 整份送進去 | **只送相關頁 / 先定位再細看** | 按頁計費，長文件要先收斂範圍 |

## 踩雷集錦

1. **直接塞 4K 原圖**：token 爆炸，而且 API 本來就會縮到上限——多送的像素純浪費。送前縮放/裁切。
2. **`media_type` 填錯**：跟實際格式不符會出錯。PNG 就寫 `image/png`，別亂填。
3. **自動化迴圈把所有截圖都留著**：每步一張圖，20 步 = 20 張圖堆爆 context 與成本。只留最近幾張。
4. **用看圖做精確計數/讀小字**：模型會數錯、讀錯。需要精確的用文字/結構化資料補。
5. **以為圖能取代結構化資料**：把一張表格截圖丟進去要模型「精確抄出每個數字」——不如直接給 CSV/文字。圖是給視覺脈絡的。
6. **GUI 自動化只靠視覺定位座標**：模型給不出可靠精確座標。搭配 DOM / 無障礙樹 / 元素標註。
7. **忘了圖片也能/也該被快取與管理**：在重複使用同一張圖的場景沒用 prompt caching（Ch 17）或 Files API，重複付費重傳；以及沒把舊圖移出 context（Ch 13）。

## 進階：再往深一層

- **圖片與 prompt caching（Ch 17）**：穩定不變的圖片 block 可以被快取，重複引用同一張圖時省下重複處理的成本。在「同一張設計稿問很多問題」的場景特別有用。
- **「看-動作-看」迴圈是電腦操作 agent 的核心**：Anthropic 的 computer use 就是這個模式——模型看螢幕截圖、決定滑鼠/鍵盤動作、再看新截圖。它把本章的多模態輸入和 Ch 7 的 agent 迴圈、Ch 18 的工具結合成「能操作電腦的 agent」。但它也最吃成本（每步一張圖）與最受「空間定位不精確」之苦，是多模態工程挑戰的集大成者。
- **截圖前的預處理能大幅提升可靠度**：在送圖前對截圖做標註（給可點擊元素編號、畫框、放大關鍵區域），能補上模型「空間定位不準」的弱點——讓模型回「點編號 7」而不是「點座標 (412,389)」。
- **多模態 + 結構化輸出（Ch 32）**：要模型「看圖並回結構化資料」（看發票回 `{廠商,金額,日期}`），就是多模態輸入 + schema 強制輸出的組合——這是「視覺抽取」的標準做法。
- **成本/延遲優化（接 Ch 37）**：視覺任務常可用「便宜模型先粗看定位、貴模型細看」的分層（Ch 26 抽取 subagent 的視覺版）。也可在送圖前用傳統影像處理（裁切、二值化、放大）降低後續 token。
- **這是 Messages API 的原生多模態能力**：`image` / `document` content block、base64/URL/Files 來源、token 與尺寸規則，都是 API 規格。`Read` 讀圖、截圖工具則是 harness 把這能力包成工具的方式。延伸閱讀的官方文件是 token 公式、尺寸上限、支援格式等確切數字的權威來源。

## 動手練習

1. 截一張有錯誤訊息的畫面，用第一節的 base64 方式送給模型，請它讀出錯誤並建議修法。確認它「看得到」圖裡的文字。
2. **成本實驗**：同一張圖，分別送「原始大尺寸」和「縮到 1568px 長邊」兩個版本，比較回應品質差異（多半幾乎沒差）並估算 token 差距。體會「縮放幾乎無損但省很多」。
3. **裁切聚焦**：送一張完整桌面截圖問「對話框寫什麼」，再送只裁出對話框的版本，對照模型回答的準確度與 token。
4. （概念/實作）設計一個「視覺驗證」流程：agent 改完一個前端元件後，截圖、送給模型問「這個按鈕是否置中且為藍色」，不符就再改。想想怎麼用 Ch 30 的 Stop hook 強制「驗證過才算完成」。
5. **多模態 + 結構化**（接 Ch 32）：送一張發票圖，用強制 tool_choice + schema 要模型回 `{廠商, 金額, 日期}`。再對幾個欄位做語意驗證（金額>0、日期合法）。

## 本章重點整理

- 現實有大量資訊以**視覺形式**存在（截圖、設計稿、PDF、圖表），純文字 agent 碰不了。多模態輸入讓 agent 能**同時讀文字、看圖**。
- 多模態不是新機制：**message 的 content 從「字串」變成「混合 text 與 image block 的清單」**，跟 tool use 的 block 清單同源。圖片來源有 base64 / URL / Files API。
- **圖片不便宜**：token ≈ `(寬×高)/750`，且大圖會被縮到上限。**送前縮放、裁切、只留需要的**，在迴圈裡尤其要管 context 與成本。
- **最關鍵的 agent 接法：工具結果可回傳 `image` block**（Ch 20）。截圖工具讓 agent「主動看畫面」，解鎖 GUI 自動化的「看-動作-看」迴圈與視覺驗證。
- **PDF 是「文字 + 每頁影像」的文件輸入**，按頁累積成本；長文件要先收斂範圍。
- **限制**：讀不準小字、數不準數量、空間定位不精確、會腦補。**圖文並用**——精確的東西用文字/結構化（Ch 32），視覺脈絡用圖。
