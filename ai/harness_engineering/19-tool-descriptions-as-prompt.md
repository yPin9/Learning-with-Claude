# Ch 19 — Tool 描述就是 prompt

> **目標**：學會把工具的 `description`（工具說明與參數說明）當成一段 **prompt** 來寫。讀完你能說出 description 要回答模型哪些問題、為什麼「什麼時候**不**該用」常常比「做什麼」更重要、怎麼用 description 化解兩個工具的選擇模糊，並能把一句話的爛描述改寫成讓模型「該用時用、不該用時不亂用」的好描述。

> **環境**：Python 3.11、`anthropic` Python SDK（最新版）。本章接續 [Ch 18 — schema 設計](./18-tool-schema-design.md)：上一章把 schema 的**結構**（型別、enum、required、粒度）設計好，這一章把結構裡的**文字**寫好。兩章合起來才是完整的「好工具」。

## 為什麼需要這個？

上一章我們反覆講「工具的資訊全在 schema 裡」。模型當然不是只看得到 schema——它同時看得到 system prompt 和整段對話 context。但講到「這個工具是什麼、能做什麼」，模型**唯一**的來源就是工具定義裡的那些**文字**——工具的 `description` 和每個參數的 `description`。型別和 enum 約束的是「能填什麼」，文字交代的是「這工具是幹嘛的、我現在該不該用它、該怎麼填」。

回想 [Ch 5](./05-tool-calling-protocol.md) 的比喻：工具 schema 就是給模型看的 **API 文件**，而 description 是文件裡的散文部分。人類工程師看到爛文件會去翻 source code、會猜、會試；**模型看不到你的工具實作**——它只能靠 schema 裡的 `name` / `description` / `input_schema` 加上對話上下文推斷，沒寫到的它只能腦補。所以這段文字的品質，幾乎直接等於模型用這個工具的品質。

而且 description 的影響不只是「填對參數」。它決定一件更前面的事：**模型到底要不要呼叫這個工具**。一個 agent 可能有十幾個工具，每一輪模型都在用各工具的 description 判斷「哪個能解決我現在的問題」。description 寫得模糊，模型就會該用的不用（任務失敗）、不該用的亂用（多餘呼叫甚至闖禍）、或在兩個相似工具間挑錯。這是 prompt engineering 的核心戰場，只是它藏在 schema 裡。

## 先建立直覺：description 是寫給一個「沒有上下文的新人」的工作說明

想像你要把一個工具交給一位**第一天上班、聰明但對你們公司一無所知**的同事。他不知道你們有哪些系統、哪個工具會不會誤刪資料、哪兩個工具長得像但用途不同。你貼在工具上的那張說明，是他**唯一**的依據。

一個只寫「搜尋」的說明，他會問一堆問題：搜什麼？哪個資料庫？要不要錢？跟旁邊那個「查詢」有什麼不同？——但模型不會回頭問你，它直接照自己的猜測動手。所以好的 description 要**主動把這些問題在說明裡答掉**：

```
   一個工具的 description 要回答模型的問題
   ┌──────────────────────────────────────────────┐
   │ Q: 這工具到底做什麼？        → 一句話講清楚功能   │
   │ Q: 我什麼時候該用它？        → 觸發情境           │
   │ Q: 我什麼時候不該用它？      → 反向邊界（最常漏）  │
   │ Q: 用了會發生什麼副作用？    → 會不會改資料/花錢   │
   │ Q: 它跟那個很像的工具差在哪？ → 消歧義             │
   │ Q: 每個參數到底要填什麼？    → 參數級描述         │
   └──────────────────────────────────────────────┘
```

整章心法一句話：**description 不是「描述工具」，是「指揮模型怎麼決策」**。你在寫的不是 API reference，是一段給模型讀的 prompt。

## 一、工具 description：要回答的六個問題

先看一個只回答了「做什麼」的描述，再看一個六題全答的：

```python
# ❌ 只說了「做什麼」，模型在選擇時缺一大半資訊
{
    "name": "send_email",
    "description": "寄送 email。",
}

# ✅ 把模型決策需要的資訊都交代清楚
{
    "name": "send_email",
    "description": (
        "寄送一封 email 給指定收件人。"                       # ① 做什麼
        "當使用者明確要求『寄信／通知某人／把這個寄給 X』時使用。"  # ② 何時用
        "不要用它來儲存草稿或提醒自己——那是 create_note 的工作。" # ③ 何時不用 + 消歧義
        "注意：這會真的送出信件、無法撤回，寄出前若資訊不全應先向使用者確認。" # ④ 副作用
    ),
}
```

六個問題裡，新手最常只寫①、最常漏③和④：

- **① 做什麼**：一句話講清楚功能。動詞開頭，講具體（「在內部文件庫搜尋」而非「搜尋」）。
- **② 何時用（觸發情境）**：描述什麼樣的使用者意圖或任務狀態該觸發這個工具。模型靠這句把「當前情境」對應到「這個工具」。
- **③ 何時**不**用（反向邊界）**：這是最被低估的一句。明確講「這些情況別用我」「那種需求請用另一個工具」，能擋掉大量誤呼叫。沒有反向邊界的工具，模型容易在不該用時硬用。
- **④ 副作用與成本**：會不會改變狀態（寫入、刪除、送出）？可不可逆？要不要花錢、要不要授權？危險操作一定要在 description 裡標明，模型才會謹慎、才會在動手前先跟使用者確認。
- **⑤ 與相似工具的關係（消歧義）**：見第三節。
- **⑥ 參數怎麼填**：見第二節（參數級 description）。

> 這裡有個和 [Ch 11 — system prompt 設計](./11-system-prompt-design.md) 的分工：**單一工具的邊界與參數語意（怎麼用、何時用、何時不用）屬於它自己的 description**；**全域的工具使用政策、傾向、跨工具流程順序（例如「回答前一律先用 search_documents 查證」）才放 system prompt**。注意別在 system prompt 重抄一份工具清單或參數細節——模型已經從 `tools` 參數看到所有工具定義了，重抄只會造成兩邊不同步。各司其職：description 管「這一個工具」，system prompt 管「跨工具的策略」。

## 二、參數 description：每個欄位都要自我解釋

工具層的 description 講「要不要用、整體怎麼用」；**參數層**的 description 講「這一格到底填什麼」。每個 `properties` 底下的欄位都該有自己的 `description`，把 schema 的型別約束補上語意：

```python
"input_schema": {
    "type": "object",
    "properties": {
        "to": {
            "type": "string",
            "description": "收件人 email 地址，需為完整格式如 'alice@example.com'；不接受人名",
        },
        "limit": {
            "type": "integer",
            # 型別只說「是整數」，description 補上「範圍」與「省略時的預設」
            "description": "回傳筆數，介於 1-20；省略則預設 5",
        },
        "send_at": {
            "type": "string",
            # 格式約束寫清楚，否則模型會用各種日期寫法
            "description": "排程寄送時間，ISO 8601 格式如 '2026-06-05T09:00:00Z'；省略則立即寄出",
        },
    },
    "required": ["to"],
}
```

參數 description 要做到三件事：

1. **講格式**：尤其字串。`to` 要 email 不要人名、`send_at` 要 ISO 8601——不講，模型就用它猜的格式，於是你收到各種變體。
2. **講範圍與單位**：`limit` 的 1-20、`timeout` 的單位是秒還毫秒。型別說不了這些（Ch 18 提過，這類語意約束 schema 不強制），全靠文字。
3. **講選填項省略時的預設**：上一章原則 2 講過——選填參數一定要寫「省略則…」，模型才敢省略，而不是硬塞或瞎填。

一個好用的自我檢查：把每個參數的 description 單獨抽出來，問「光看這一句，一個沒看過我系統的人填得對嗎？」填不對就是寫得不夠。

## 三、消歧義：當兩個工具長得很像

agent 工具一多，最容易出包的不是「沒有工具可用」，而是**有兩個相似的工具，模型挑錯**。例如同時有 `search_documents`（搜內部文件）和 `search_web`（搜公開網路）。如果兩個的 description 都只寫「搜尋相關內容」，模型只能擲骰子。

解法是在**各自的 description 裡明確劃界、甚至直接點名對方**：

```python
search_documents = {
    "name": "search_documents",
    "description": (
        "在公司**內部**文件庫搜尋（規章、過往報告、內部 spec）。"
        "當問題關於公司自己的資料、政策、歷史紀錄時用這個。"
        "若需要**外部／公開**資訊（新聞、第三方文件、即時資料），改用 search_web。"  # 點名對方
    ),
    # ... input_schema
}

search_web = {
    "name": "search_web",
    "description": (
        "搜尋**公開網路**取得即時或外部資訊。"
        "當問題需要公司資料庫以外的知識（最新新聞、第三方產品文件）時用這個。"
        "若問題是關於公司內部的政策或紀錄，改用 search_documents。"  # 點名對方
    ),
    # ... input_schema
}
```

劃界的訣竅：**用「對立軸」描述**。內部 vs 外部、即時 vs 歷史、唯讀 vs 會寫入——找出兩個工具真正的分界軸，在雙方描述裡都講同一條軸的兩端。模型一旦抓到這條軸，就能穩定地分類當前任務該往哪邊走。

## 四、在 description 裡放範例（few-shot）

當一個工具的「何時用」很難用抽象規則講清楚時，**舉例**比解釋更有效——這其實就是把 few-shot prompting 放進 description：

```python
{
    "name": "create_calendar_event",
    "description": (
        "建立行事曆事件。當使用者表達想安排、預約、提醒某個有明確時間的活動時使用。\n"
        "例如：\n"
        "- 『幫我約禮拜五下午三點跟 Bob 開會』→ 用這個工具\n"
        "- 『我下週應該找時間運動』→ 太模糊、沒有明確時間，先問清楚再決定，不要直接建立\n"
        "- 『我上禮拜開了什麼會？』→ 這是查詢過去，用 list_events，不是這個"
    ),
    # ... input_schema
}
```

範例特別擅長傳達「**邊界**」：哪種講法該觸發、哪種太模糊該先問、哪種其實是別的工具的活。比起寫一條抽象規則，給模型三個對照例子，它更能 generalize 到沒見過的講法。代價是 token——範例會撐大 description，所以只在「規則難以言傳」的關鍵工具上用，不要每個工具都塞。

要分清楚兩種「範例」放哪裡：

- **「何時觸發 / 怎麼判斷」的決策範例**（上面那種口語對照）放 `description`——它要影響的是模型「要不要用、用哪個」的判斷。
- **「輸入物件長什麼樣」的格式範例**（尤其參數是複雜巢狀物件、格式敏感）優先用工具定義頂層的 **`input_examples`** 欄位。這是 Anthropic 官方提供的選填欄位，放進去的範例會對照 schema 驗證，比塞在 description 裡更不容易跟 schema 脫節。

## 五、失敗示範：三種「描述沒寫好」的翻車

description 寫不好，會以三種典型方式翻車。逐一看：

**翻車一：該用卻不用（描述太窄或太抽象）**

```python
# ❌ 模型看不出這跟使用者的口語需求有什麼關係
{"name": "lookup_order", "description": "查詢訂單實體。"}
```

使用者問「我上禮拜買的那雙鞋到哪了？」——模型可能不會把這句口語對應到「訂單實體」這種術語化、太窄的描述，於是放著工具不用、直接瞎掰一個答案。**修法**：用使用者會用的語言描述觸發情境——「查詢訂單狀態與物流進度。當使用者問『我的東西到了沒／訂單狀態／什麼時候到貨』時使用」。

**翻車二：不該用卻亂用（缺反向邊界）**

```python
# ❌ 沒講「什麼時候不要用」，模型把它當萬能搜尋
{"name": "search_web", "description": "搜尋網路取得資訊。"}
```

使用者問「1 加 1 等於多少？」——模型可能也去搜網路，浪費一次呼叫和延遲。**修法**：加反向邊界——「僅在需要你的知識以外、或需要即時/外部資訊時使用；常識性問題、簡單計算請直接回答，不要呼叫本工具」。

**翻車三：填錯參數（參數描述含糊）**

```python
# ❌ date 沒講格式，模型每次用不同寫法
{"name": "get_report", "input_schema": {"properties": {
    "date": {"type": "string", "description": "日期"}}}}
```

模型一下填 `"2026-06-05"`、一下填 `"June 5"`、一下填 `"昨天"`，你的後端解析炸掉。**修法**：`"description": "報表日期，格式 YYYY-MM-DD，例如 '2026-06-05'"`。

三種翻車的共通根因都一樣：**description 把某個模型需要的資訊省略了**，模型只好用猜的。

## 對比與取捨

| 維度 | 寫太少 | 寫太多 | 怎麼拿捏 |
|---|---|---|---|
| 工具用途 | 模型不知何時用、亂猜 | 長篇大論稀釋重點、撐大快取前綴 | 功能一句、觸發情境一兩句、反向邊界一句 |
| 反向邊界（何時不用） | **最常漏**，導致誤呼叫 | 列一堆不相干的「別用於…」反而噪音 | 只列模型**真的會搞混**的那幾種情況 |
| few-shot 範例 | 邊界難言傳時模型抓不到 | 每個工具都塞、token 爆炸 | 只在「規則難講」的關鍵工具上放 2-3 例 |
| 消歧義 | 相似工具模型挑錯 | — | 找出對立軸，雙方描述都點名對方 |
| 參數說明 | 格式/範圍/預設靠猜 | 把工具用途又抄一遍 | 每參數講格式+範圍+省略預設，不重複工具層 |

核心取捨是 **token/注意力成本 vs 決策資訊量**。description 越長，每輪重送的固定成本越高（Ch 17 的快取前綴）、也越可能稀釋模型注意力；但寫太省模型就猜。原則：**把直接影響「用不用、怎麼填」的資訊寫足，其餘砍掉**。

## 踩雷集錦

1. **只寫「做什麼」，不寫「何時不用」**：反向邊界是最高 CP 值卻最常漏的一句。沒有它，模型會在不該用的時候硬用。把「常識題直接答、別呼叫我」這種話寫進去。
2. **用內部術語而非使用者語言描述觸發情境**：「查詢訂單實體」模型對不上「我的鞋到了沒」。觸發情境要用**使用者會講的話**，不是你資料庫的 schema 名。
3. **相似工具描述各寫各的、不互相點名**：兩個 search 都寫「搜尋相關內容」，模型只能擲骰子。要在雙方描述裡沿同一條對立軸劃界。
4. **危險/不可逆操作不在描述裡標明**：`delete`、`send`、花錢的操作若沒講「不可撤回／會真的送出」，模型不會謹慎、也不會先跟使用者確認。副作用一定要寫。
5. **參數 description 重抄工具用途**：參數層該講「這一格填什麼格式/範圍/預設」，不是再把工具幹嘛講一遍。重複只會浪費 token 又稀釋重點。
6. **description 跟實際行為不同步**：改了工具實作卻沒改 description，模型照舊描述用、結果對不上。description 是契約，行為變了它要一起變。
7. **把 description 當成人類文件寫**：寫給工程師讀的文件可以假設讀者會翻 source、會推論慣例；模型不會。對人類「不言而喻」的，對模型都要明寫。

## 進階：再往深一層

- **description 也算進快取前綴成本**：工具定義（含所有 description 文字）排在快取前綴最前面（Ch 17 的 tools→system→messages）。所以 description 不是越長越好——前提是你有啟用 prompt caching、且達到該模型的最低可快取 token 門檻：此時每多一句，每輪未命中（首次寫入）時的固定成本就多一點，命中時雖然便宜但仍有 cache-read 成本；而改任何一字都會讓整個前綴失效、要重新寫入。把「寫足決策資訊」和「別長篇大論」這對張力，當成 token 預算問題來權衡。
- **description 是可以被 eval 出來的**：別憑感覺寫。準備一組「該觸發 / 不該觸發 / 容易選錯」的測試任務，改一版 description 就跑一遍，看模型的工具選擇正確率有沒有變好。description 是 prompt，prompt 就該被 A/B 測——這正是 [Ch 34 — Eval](./34-eval.md) 的主題。
- **錯誤訊息也是「事後的 description」**：當模型用錯工具/填錯參數，你透過 `tool_result`（設 `is_error: true`）回給它的訊息，等於是「即時補一段 description」教它怎麼改。寫得好的錯誤訊息（「`date` 需要 YYYY-MM-DD，你給的是 'June 5'」）能讓模型下一輪自己修正——別只回一個 opaque 的 error code 或整段 traceback。協議上要記得：`tool_result` 必須放在 user 訊息、緊接對應的 `tool_use`，且排在該則訊息任何 text 之前（Ch 5 講過）。這條和 description 是一體兩面，[Ch 20 — Tool 結果設計](./20-tool-result-design.md) 會專門談。
- **工具一多，光靠 description 不夠**：當工具上到幾十個，再好的 description 也擋不住「全部塞進前綴稀釋注意力」的問題。這時要靠動態揭露/檢索工具的機制——見 [Ch 23 — Tool search / deferred tools](./23-tool-search-deferred.md)。本章先把「單一工具的描述」寫到位。

## 動手練習

1. 拿練習 A 的 `read_text_file` 工具，把它的 description 從一句話擴寫成「六個問題」版本（做什麼、何時用、何時不用、有沒有副作用、跟誰像、參數怎麼填）。對比改前改後，模型在邊界任務上的表現。
2. 故意製造一組會打架的工具：`get_weather` 和 `search_web`，兩者都先寫成「取得資訊」。跑「今天台北天氣？」這個任務，觀察模型選哪個、選錯沒。然後用「對立軸」改寫雙方描述、再跑一次。
3. 寫一個 `delete_file` 工具，比較「description 有標明不可逆」和「沒標明」兩版，看模型在動手前會不會主動跟使用者確認。
4. 給 `create_calendar_event` 的 description 加上第四節那種 few-shot 範例，餵幾個模糊講法（「我下週想運動」），看模型會不會照範例先問清楚而非硬建立事件。

## 本章重點整理

- description 是工具 schema 裡真正「跟模型講話」的部分——它不是描述工具，是**指揮模型決策**。它決定模型「要不要用、用哪個、怎麼填」。
- 工具層 description 要答六個問題，其中**「何時不用」（反向邊界）和「副作用」最常被漏**，卻最影響誤呼叫與安全。
- 參數層 description 負責格式、範圍、單位、選填預設——型別約束說不了的，全靠文字。
- 相似工具用「對立軸」劃界、互相點名，化解模型挑錯。
- description 算進快取前綴成本、且可被 eval——把它當 prompt 一樣權衡長度、一樣 A/B 測。
