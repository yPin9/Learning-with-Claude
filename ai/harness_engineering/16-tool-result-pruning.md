# Ch 16 — Tool 結果的裁剪與格式化

> **目標**：實作 Ch 12 選單裡的「策略四：裁剪工具結果」——直擊歷史膨脹的頭號元兇。讀完你能：從源頭讓工具少回一點、把大輸出在進 context 前裁剪/摘要、用 handle 引用大資料、並把工具結果格式化成「給模型好讀」的樣子。這是 context engineering 裡 CP 值最高的一塊。

> **環境**：Python 3.11、`anthropic` Python SDK（最新版），延續前面的 `Agent`、工具系統（Ch 4–5）、`analyze_history`（Ch 12）。

## 為什麼這章 CP 值最高

Ch 12 量化過：在會用工具的 agent 裡，`tool_result` 通常是歷史膨脹的頭號元兇。Ch 13 的壓縮、Ch 14 的 memory 都是「事後補救」——等東西已經塞進去了再想辦法縮。而本章是**源頭治理**：工具結果一進來，甚至還沒進來，就先把它變小。

源頭治理永遠比事後補救划算。一個讀檔工具如果直接回傳整份 5000 行的檔，那 5000 行會：(1) 立刻佔滿這輪 context，(2) 之後每輪都被重送（Ch 10 的 O(N²)），(3) 逼你更早觸發壓縮（Ch 13 的成本）。但如果這個工具一開始就只回「模型真正需要的那 20 行」，上面三個問題**全都不會發生**。**最好的 context 管理，是讓不該進 context 的東西根本別進來。**

## 先建立直覺：工具結果是「給模型的簡報」，不是「資料庫 dump」

新手寫工具，常常讓它「把拿到的東西原封不動全回傳」——API 回什麼 JSON 就回什麼 JSON、檔案多大就回多大。這是把工具當成「資料管道」。

換個心智模型：工具結果是**寫給模型看的一份簡報**。簡報的目的是讓讀者（模型）**做出下一步決策**，不是把所有原始資料倒給他。一個好的下屬不會把整個資料庫 dump 給老闆，他會說「我查了，重點是這三項」。工具也該這樣。

```
   ❌ 資料庫 dump（工具當管道）          ✅ 簡報（工具當分析師）
   ┌──────────────────────────┐       ┌──────────────────────────┐
   │ {完整 API 回應，含 200 個    │       │ 找到 3 筆符合的訂單：       │
   │  欄位、巢狀物件、metadata、 │  →    │ #1234 (已出貨)             │
   │  分頁資訊、5000 行...}       │       │ #1235 (處理中)             │
   │                            │       │ #1238 (已取消)             │
   └──────────────────────────┘       └──────────────────────────┘
      模型要自己從垃圾裡淘金              模型一眼看到該看的
```

這個視角會貫穿整章：**每次設計工具回傳什麼，問自己「模型做下一步決策，到底需要哪些？」** 其餘的，別回。

## 一、源頭：讓工具一開始就少回一點

最好的裁剪是「根本不產生多餘的東西」。在工具的**實作**層就控制回傳量：

```python
# ❌ 把整個 API 回應原樣丟回去
def search_orders(query: str) -> str:
    resp = orders_api.search(query)     # 回傳含分頁、metadata、每筆 50 個欄位的巨物
    return json.dumps(resp)             # 全部塞給模型

# ✅ 只挑模型需要的欄位，整理成精煉的格式
def search_orders(query: str) -> str:
    resp = orders_api.search(query)
    lines = []
    for order in resp["results"][:10]:          # 限制筆數
        lines.append(f"#{order['id']} {order['status']} ${order['total']}")  # 只留關鍵欄位
    more = resp["total"] - len(resp["results"][:10])
    out = "\n".join(lines)
    if more > 0:
        out += f"\n（還有 {more} 筆未顯示，可縮小查詢範圍）"  # 告知有截斷，但不全倒
    return out
```

幾個源頭治理的通用手法：

- **挑欄位**：API 回 50 個欄位，模型只需要 3 個，就只回那 3 個。
- **限筆數**：搜尋結果不要全回，回前 N 筆 + 「還有幾筆」的提示。
- **去 metadata**：分頁資訊、request id、時間戳這種模型不需要的 metadata，別回。
- **告知截斷**：截斷時明確告訴模型「有東西沒顯示、以及怎麼拿更多」——讓模型知道這不是全部，必要時能縮小查詢再查。

> 這直接呼應 Ch 19（工具描述）和 Ch 20（工具結果設計）：工具回什麼是個**設計決策**，不是「API 給什麼就給什麼」。本章先建立「源頭少回」的意識，Ch 20 會更系統地談工具結果設計。

## 二、進場裁剪：大輸出在進 context 前先處理

有些工具你沒法在源頭控制（例如「讀任意檔案」「跑任意 shell」——你事先不知道輸出多大）。這時在**工具結果進 context 之前**做一層裁剪。常見手法：

### 截斷 + 提示

最簡單：超過某長度就截斷，並告訴模型被截斷了：

```python
MAX_TOOL_RESULT_CHARS = 4000   # 注意：這是「字元」預算，不是 token 預算（見下方說明）

def clip(text: str) -> str:
    if len(text) <= MAX_TOOL_RESULT_CHARS:
        return text
    head = text[:MAX_TOOL_RESULT_CHARS]
    return head + f"\n\n…（輸出過長，已截斷，原始長度 {len(text)} 字元。如需更多，請縮小範圍或指定要看的部分）"
```

> 這裡用「字元數」當門檻，是為了簡單——它是個**字元預算**，不是精確的 token 預算（Ch 10 講過字元和 token 不是 1:1，中文/符號尤其）。對「保底別爆」這個目的，字元門檻夠用且零成本。若你要更精準地控 token，可改用 tokenizer 計數，但通常保底關卡用字元就好。

放進 `run_tool_uses`（Ch 4），所有工具結果進 context 前都過這關。截斷比不截好，但它很笨——可能正好切掉了重要的尾段（例如錯誤訊息常在最後）。所以對「結構已知」的輸出，有更聰明的做法。

### 抽取關鍵段（針對結構已知的輸出）

如果你知道輸出的結構（例如 `pytest` 的輸出、編譯錯誤），可以只抽模型需要的部分：

```python
def clip_test_output(raw: str) -> str:
    """pytest 輸出常常很長，但模型通常只需要失敗摘要與錯誤。"""
    lines = raw.splitlines()
    keywords = ("FAILED", "ERROR", "Error", "Traceback", "assert", "Exception", "passed", "failed")
    relevant = [l for l in lines if any(k in l for k in keywords)]
    # 再保留最後幾行（pytest 的總結摘要通常在尾段）
    tail = lines[-15:]
    merged = relevant + ["…", "（輸出尾段）"] + tail if relevant else tail
    # 即使抽完，行數可能仍多，最後一定再過一次通用 clip 保底
    return clip("\n".join(merged)) if relevant or len(raw) > MAX_TOOL_RESULT_CHARS else raw
```

這比無腦截斷聰明——它保留「訊號」（FAILED / ERROR / traceback / 例外行）+ 尾段摘要、丟掉「雜訊」（一堆通過測試的細節），完全是 Ch 10 訊噪比精神的應用。注意最後**仍然過一次 `clip`**：因為若符合關鍵字的行本身就很多（例如幾百個 FAILED），抽完還是可能很大，保底截斷不能省。這也是個提醒——「聰明抽取」和「保底截斷」要疊著用，不是二選一。

### 摘要進場（針對大量非結構化文字）

如果輸出是一大段非結構化文字（例如抓了一個網頁），可以像 Ch 13 那樣**用一個便宜模型把它摘要**後再注入。代價是多一次 API 呼叫，但對「網頁正文這種又大又雜」的輸出值得。

## 三、handle 模式：大資料不進 context，用「引用」代替

有時工具拿到的資料又大又可能後續要用（例如一個大檔、一份完整報告），裁剪掉怕之後要用、全注入又太肥。**handle 模式**（也叫 reference / pointer 模式）解這個兩難：

```
   工具拿到大資料 → 存到 context 之外（檔案/暫存）→ 只回一個「handle」+ 摘要
        │
   tool_result: "已讀取 report.pdf（32 頁，約 4 萬字）。摘要：本季營收成長 12%…
                 完整內容已存為 handle: doc_a1b2。需要細節可用 read_chunk(doc_a1b2, page=N)。"
        │
   模型若需要某部分 → 呼叫 read_chunk(handle, ...) → 只把那一塊撈進來
```

精髓：**大資料留在 context 外，context 裡只放「一個引用 + 夠用的摘要」**。模型需要細節時，再用 handle 配合另一個工具，**按需**把特定部分撈進來。這其實就是 Ch 15 的 RAG 思想用在「工具產生的大資料」上——不全塞，要才撈。

handle 模式特別適合：

- 大檔、長報告、完整 API 回應這種「整體很大、但每次只需要一小部分」的資料。
- 需要在多輪間反覆參照同一份大資料、但不想每輪都重送全文的情況。

代價是複雜度（要管理「context 外的儲存」和「按需撈取的工具」），所以不是每個工具都該這樣——只對真正大的資料用。

## 四、格式化：同樣的資訊，怎麼擺模型更好讀

裁剪是「給多少」，格式化是「怎麼擺」。同一份資訊，格式好壞會明顯影響模型能不能用好它、以及佔多少 token：

- **結構化但精簡 > 冗長 JSON**：模型讀得懂 JSON，但原始 API 的 JSON 常有大量巢狀和冗餘。整理成精簡的條列或表格，往往更省 token 又更好讀。
- **給標籤/欄位名**：`#1234 已出貨 $500` 比 `1234 shipped 500` 好——讓模型知道每個值是什麼。但別過度（不需要把整個 verbose JSON schema 也貼上）。
- **一致的格式**：同一個工具每次回傳用一致的結構，模型更容易學會解讀它。
- **錯誤要清楚**：工具失敗時（Ch 4 的 `is_error`），錯誤訊息要具體可行動（「檔案 X 不存在」而非「Error 2」），讓模型能據此修正。

> 一個常見的取捨：JSON vs 自然語言。對「模型只是要讀懂」的結果，精簡的自然語言/條列通常最省、最好讀。對「模型之後要把它當結構化資料精確處理」的結果，保留必要的結構（精簡 JSON）比較好。沒有絕對答案，依「模型拿這個結果要做什麼」決定。

## 五、把裁剪接進 harness

把上面的手法收進 `run_tool_uses`（Ch 4），讓所有工具結果都過裁剪這關（注意這仍是 Ch 4 那個**文字工具的簡化版**——`str(func(...))` 會把結構化/圖片/文件型的結果壓成字串；真要回傳 image/document block 時，裁剪邏輯要改成不破壞那些 block，見 Ch 5、Ch 33）：

```python
def run_tool_uses(content_blocks):
    results = []
    for block in content_blocks:
        if block.type != "tool_use":
            continue
        func = TOOL_FUNCTIONS.get(block.name)
        try:
            raw = str(func(**block.input)) if func else f"未知工具 {block.name}"
            is_error = func is None
        except Exception as e:
            raw, is_error = f"工具執行失敗：{e}", True

        # ← 統一裁剪關卡：所有工具結果進 context 前都過這裡
        clipped = clip(raw)                  # 通用截斷（個別工具可在自己實作裡做更聰明的裁剪）

        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": clipped,
            "is_error": is_error,
        })
    return {"role": "user", "content": results}
```

分層的設計原則：

- **harness 層**放「通用、保底」的裁剪（如 `clip` 的硬截斷）——確保**任何**工具都不會回傳一個撐爆 context 的巨物。這是安全網。
- **個別工具**在自己的實作裡做「聰明、針對性」的裁剪（挑欄位、抽關鍵段、handle）——因為只有工具自己知道它的輸出結構。

兩層配合：工具盡量在源頭做對，harness 的保底關卡接住漏網的。

## 六、別裁過頭：訊噪比是雙向的

裁剪的反面風險是**裁掉了模型需要的東西**。一個過度激進的截斷（`MAX=200`）可能把錯誤訊息最關鍵的那行切掉，模型看不到真正的原因，反而要多花幾輪試錯——省了 token，賠了正確性與回合數。

所以裁剪要**保留訊號、只砍雜訊**，而不是「一律砍到某長度」。判斷準則還是 Ch 10 那句：目標是高訊噪比。具體做法：

- 截斷時優先保留「結構上重要的部分」（錯誤訊息的尾段、摘要行），而非機械地砍尾巴。
- 截斷時**明確告知模型「有東西被砍了、怎麼拿更多」**——這樣模型缺資訊時能主動再查，而不是基於殘缺資訊瞎猜。
- 用 eval（Ch 34）驗證：裁剪前後，agent 完成任務的正確率有沒有下降？如果裁太狠害它變笨，就放寬。

## 失敗示範：把整份 API 回應原樣塞回去

看 Ch 12 那個 13500-token 元兇是怎麼來的。一個查訂單的工具，圖方便：

```python
# 反例！原樣 dump
def search_orders(query: str) -> str:
    return json.dumps(orders_api.search(query))   # 回了含 200 筆、每筆 50 欄位的巨物
```

連鎖災難：(1) 這一輪 context 瞬間爆 13500 token；(2) 之後每輪重送（O(N²)）；(3) 模型要從 200 筆 × 50 欄位裡自己找那 3 筆相關的，訊噪比極低、容易找錯（context rot）；(4) 逼你提早觸發壓縮。**一個圖方便的 `json.dumps`，引發了後面四章要處理的所有問題。**

修法就是本章第一節：挑欄位、限筆數、去 metadata、告知截斷。同樣是「查訂單」，回傳從 13500 token 降到 100 token，而且模型答得**更準**（因為訊噪比高）。這就是源頭治理 CP 值最高的證明——一個好工具，省下後面一連串補救。

## 踩雷集錦

1. **工具原樣 dump API 回應/檔案**：頭號元兇。工具是「簡報」不是「資料管道」——挑模型需要的，別全回。
2. **只在 harness 做硬截斷、不在工具源頭治理**：硬截斷是保底安全網，但很笨（可能切掉關鍵尾段）。源頭挑欄位/抽關鍵段才是上策，兩者要配合。
3. **截斷不告知模型**：默默切掉一半，模型以為那就是全部，基於殘缺資訊瞎答。截斷一定要附「被截斷了、怎麼拿更多」。
4. **裁過頭、砍掉訊號**：為省 token 砍掉錯誤訊息關鍵行，模型反而多花回合試錯。保留訊號、只砍雜訊，並用 eval 驗證沒裁過頭。
5. **大資料硬塞或硬丟二選一**：又大又可能後續要用的資料，別在「全塞」和「全丟」間二選一——用 handle 模式（存外面、回引用+摘要、按需撈）。
6. **冗長 JSON 當預設格式**：原始 API 的 JSON 常有大量冗餘巢狀。整理成精簡條列/表格通常更省又更好讀；只在模型需要精確結構時才保留 JSON。

## 進階：再往深一層

- **裁剪 vs 壓縮 vs context editing 的協同**：本章的「進場裁剪」是**工具結果剛產生時**就處理；Ch 13 的壓縮是**事後**對整段歷史做語意摘要；Anthropic 的 context editing（Ch 13 進階）是**自動清除**舊的（server-side）tool use/result 或 thinking block——它是 clearing，不是語意壓縮，也不是 client-side 裁剪的替代品。三者層次不同：源頭裁剪 → 事後壓縮 → 自動清除，從早到晚層層把關。**大型/長任務的 agent 常會組合使用**；但小 agent 可能光靠源頭裁剪就夠了，別為了用滿三種而過度設計。
- **「舊工具結果」的特殊性**：Ch 12 講過 tool_result 半衰期短。一個進階技巧是**對歷史裡的舊工具結果做二次裁剪**——一個工具結果在它那輪很重要，但幾輪之後模型早就用過了，這時可以把歷史裡那則巨大的舊結果換成精簡佔位字串。但這裡有兩個一定要守住的細節：
  - **只改那個 `tool_result` 區塊裡的 `content`**，把它換成精簡字串即可。**絕對不要**因此刪掉配對的 assistant `tool_use`、不要把它變成一則普通 user 文字訊息、要保留原本的 `tool_use_id`、保留它緊接在 tool_use 之後、且 tool_result 仍排在 content 最前（Ch 5/Ch 6 的配對與格式規則一條都不能破）。換句話說，是「**替換內容、保留骨架**」，不是「刪除」。
  - 佔位字串若寫「需要可重讀」，**只有在那個工具是確定性的、或你有穩定的 handle/快照**時才成立。對 search / API / shell 這種**易變**的工具，重跑未必拿得到當初那個結果——這種情況佔位字串別承諾「可重讀」，或乾脆在裁剪前把該留的精華先抽出來保在佔位字串裡。

  這是「裁剪」用在時間維度上，跟 context editing 的自動清除是同一個想法的手動版。
- **handle 模式就是 agent 版的「指標」**：把大資料存外面、context 裡只放引用——這在系統設計裡就是「指標 / 參照」的概念。理解這個類比，你會發現很多 context 問題本質是「值傳遞 vs 參照傳遞」的選擇：小東西值傳遞（直接放 context），大東西參照傳遞（放 handle）。
- **多模態結果的裁剪更棘手**：當工具回傳圖片（Ch 5 的 image block、Ch 33），「裁剪」的意義不同——圖片佔的 token 跟解析度有關，你可能要降解析度而非「截斷」。不同模態有不同的「變小」手法，到 Ch 33 會碰。

## 動手練習

1. 拿你 mini-agent 的 `read_text_file`（練習 A），它現在原樣回整個檔。加上 `clip`（硬截斷 + 截斷提示），讀一個大檔，用 `analyze_history`（Ch 12）對比裁剪前後 `tool_result` 的 token——親眼看到源頭治理的效果。
2. 寫一個「聰明裁剪」版本：對某種結構已知的輸出（例如你自己造一段假的 pytest 輸出），只抽失敗摘要與錯誤行，丟掉通過細節。對比硬截斷，看哪個保留的訊號多。
3. 實作一個迷你 handle 模式：`read_large_doc` 把大文件存進一個 dict（key 是 handle）、只回 handle + 前幾行摘要；再寫 `read_doc_section(handle, start, end)` 讓模型按需撈。觀察 context 省了多少。
4. 故意「裁過頭」：把 `MAX_TOOL_RESULT_CHARS` 設成 50，讓 agent 處理一個需要看完整錯誤訊息的任務，觀察它因為看不到關鍵資訊而多繞幾輪——體會踩雷第 4 點。
5. （進階）實作「舊工具結果二次裁剪」：在 compact（Ch 13）之外，加一個邏輯——把歷史裡 N 輪之前的大 tool_result 替換成精簡佔位字串（維持結構合法）。

## 本章重點整理

- 裁剪工具結果是 context 管理 CP 值最高的一塊：源頭治理勝過事後補救，因為它同時解掉「佔當前 context、被重送、逼早壓縮」三個問題。
- 心智模型：工具結果是「給模型的簡報」（幫它做下一步決策），不是「資料庫 dump」。
- 源頭少回：挑欄位、限筆數、去 metadata、告知截斷——工具回什麼是設計決策。
- 進場裁剪：硬截斷（保底）、抽關鍵段（結構已知）、摘要進場（大量非結構化）。
- handle 模式：又大又可能後續要用的資料，存 context 外、只回「引用 + 摘要」、按需撈——agent 版的「參照傳遞」。
- 分層：harness 放通用保底裁剪，個別工具做聰明針對性裁剪，兩層配合。
- 別裁過頭：保留訊號、只砍雜訊、截斷要告知、用 eval 驗證沒害 agent 變笨。
