# Ch 23 — AI 安全政策撰寫

> 目標：知道 AI 安全政策的四個核心模組是什麼、各自要寫什麼，以及政策落地失敗的原因——這是面試中「你如何在組織內推動 AI 安全」的標準答案框架。

---

## 為什麼需要 AI 安全政策

技術控制（guardrails、RBAC、data masking）是必要的，但不夠。

```
沒有政策的問題：
  - 開發者不知道哪些 AI 工具可以用
  - 沒有人知道遇到 prompt injection 事件要聯絡誰
  - 業務部門自己跑去用未審核的 ChatGPT plugins
  - 發生事故後沒有紀錄，無法稽核，也無法改善

政策的作用：
  讓「AI 能做什麼、不能做什麼、誰負責、出事怎麼辦」
  變成組織所有人都知道的明確規則
```

政策不是技術問題，但沒有政策，技術再好也守不住。

---

## 四層文件架構（面試加分）

先理解文件層次，知道政策在哪個位置：

```
政策（Policy）
  --> 原則性宣示：「公司禁止將客戶個資餵入未審核的 LLM」
  --> 對象：全員，包含非技術人員
  --> 不寫實作細節

    標準（Standard）
      --> 量化要求：「所有外部 LLM API 必須使用 TLS 1.2+」
      --> 對象：IT / 開發團隊
      --> 把政策具體化為可量測的指標

        程序（Procedure）
          --> 步驟說明：「新 AI 工具審核的 SOP，含 5 個步驟」
          --> 對象：執行者（工程師、採購）
          --> 告訴人怎麼做

            指引（Guideline）
              --> 建議做法：「建議使用 Presidio 做 PII 遮蔽」
              --> 對象：自願參考
              --> 不強制，但提供最佳實踐
```

面試被問「政策和標準有什麼差別？」就用這個架構回答。

## 四個核心模組

### 模組 1：Acceptable Use Policy（可接受使用政策）

**目的**：明確哪些 AI 工具可用、哪些禁止、使用限制是什麼。

範本片段：

```
AI 工具使用政策 v1.0

1. 核准工具清單
   以下 AI 工具經資安審查，員工可直接使用：
   - Microsoft Copilot（企業版，資料不出租戶）
   - 公司內部部署的 LLM（InternalBot）

2. 禁止行為
   - 將客戶個人資料（姓名、身分證、電話、帳號）
     輸入任何未經審核的 AI 系統
   - 使用 AI 產生的程式碼直接部署上線，未經 code review
   - 將公司機密文件（C3 以上等級）上傳至任何雲端 AI 服務

3. 未列在核准清單的工具
   需透過 IT 提交審核申請，審核週期 5 個工作日。
   等待期間不得使用。
```

### 模組 2：Risk Assessment Procedure（風險評估程序）

**目的**：部署新 AI 之前要走的評估流程，不能自行決定就上線。

範本片段：

```
新 AI 系統部署前風險評估程序 v1.0

觸發條件：以下情況須執行此程序：
  a. 導入新的 AI 模型或服務
  b. 現有 AI 系統的訓練資料或核心模型更換
  c. AI 系統存取範圍擴大（新增資料來源或使用者群）

步驟：
  1. 填寫 AI 系統描述表（附件 A）
     包含：用途、資料來源、使用者族群、第三方元件清單

  2. 執行 AI 影響評估（AIIA）
     參考 ISO 42001 條款 8.2 格式
     評估對象：安全性、隱私、公平性、可靠性

  3. 威脅建模（STRIDE）
     由資安團隊或授權的資安工程師執行
     輸出：威脅清單 + 風險矩陣

  4. 取得核准
     低風險（DREAD 平均 < 4）：部門主管核准
     中風險（4-6）：CISO 或指定代理人核准
     高風險（> 6）：需要 CTO + CISO 聯合核准

  5. 記錄歸檔
     評估文件保存於 AI 系統登錄表，保存期限 3 年
```

### 模組 3：Data Classification for AI（AI 資料分類）

**目的**：明確哪類資料不能餵給 LLM，哪類可以有條件使用。

範本片段：

```
AI 資料使用分類政策 v1.0

資料等級定義：

C1 公開資訊
  定義：已公開或無機密性的資訊
  AI 使用限制：無限制，可使用任何核准工具
  範例：官網內容、公開新聞稿

C2 內部資訊
  定義：公司內部使用，洩漏影響有限
  AI 使用限制：僅可使用企業版工具（資料不出租戶）
  範例：內部流程文件、會議紀錄

C3 機密資訊
  定義：洩漏會造成競爭劣勢或法律責任
  AI 使用限制：僅可使用公司自架 LLM，禁止使用任何雲端 API
  範例：客戶合約、未公開財報、薪資資料

C4 絕密資訊
  定義：洩漏造成嚴重損害
  AI 使用限制：禁止任何 AI 處理
  範例：未公開 M&A 資料、安全漏洞細節
```

### 模組 4：Incident Response for AI（AI 事件回應）

**目的**：發現 prompt injection、資料洩漏、AI 產生有害內容時怎麼處理。

範本片段：

```
AI 安全事件回應程序 v1.0

事件分類：

P1 嚴重（4 小時內回應）
  - 確認客戶 PII 透過 AI 洩漏
  - AI Agent 執行了未授權的操作（刪除資料、外部 API 呼叫）
  - 知識庫遭到資料污染攻擊

P2 高（24 小時內回應）
  - 懷疑 prompt injection 但尚未確認損失
  - AI 系統持續產生有害或錯誤資訊
  - 異常查詢模式（疑似知識庫探測攻擊）

P3 中（5 個工作日內）
  - System prompt 洩漏（低機密性）
  - 單次幻覺事件（無財務損失）

回應步驟：
  1. 偵測與通報：發現者立即通報 Security Hotline
  2. 初步評估：值班資安工程師 15 分鐘內評估等級
  3. 隔離：P1 事件立即下線受影響的 AI 系統
  4. 調查：保存 logs，分析攻擊向量
  5. 通報：P1 事件 24 小時內通報主管機關（如有法規要求）
  6. 修復與驗證
  7. 事後檢討報告（P1/P2 事件強制執行）
```

## 政策落地的常見失敗原因

| 失敗原因 | 說明 |
|---|---|
| 太抽象 | 「確保 AI 安全使用」是口號，不是政策 |
| 沒有技術配套 | 政策寫「禁止輸入 PII」但沒有 Presidio 擋，員工不知道怎麼做 |
| 沒有稽核機制 | 政策存在，但從來沒人查是否遵守 |
| 更新頻率太低 | AI 技術一年一大變，三年沒更新的政策等於沒有政策 |
| 只有技術人員看得懂 | 政策文件充滿術語，業務部門讀不懂 |
| 沒有處罰機制 | 違反政策沒有後果，等於虛設 |

## 稽核清單（12 個檢查點）

定期審查 AI 系統是否符合政策：

- [ ] 1. 所有上線的 AI 系統都在 AI 系統登錄表中
- [ ] 2. 每個 AI 系統有對應的 AIIA 文件，且在 12 個月內更新
- [ ] 3. 威脅建模文件存在，且涵蓋 STRIDE 六個類別
- [ ] 4. 所有外部 LLM API 連線使用 TLS
- [ ] 5. 向量 DB 啟用認證，未使用預設密碼
- [ ] 6. RAG 系統有 metadata filter 存取控制
- [ ] 7. PII 遮蔽機制在 indexing 和 query 兩個層次都有實作
- [ ] 8. LLM API key 存放在 Secrets Manager，不在程式碼或環境變數檔案
- [ ] 9. AI 系統的存取日誌（audit log）保存至少 90 天
- [ ] 10. 有 AI 安全事件回應 runbook，且有人知道在哪裡
- [ ] 11. 開發人員在過去 12 個月接受過 AI 安全訓練
- [ ] 12. 高風險 AI 系統有自動化監控告警（異常查詢、高錯誤率）
