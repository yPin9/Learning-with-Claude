# 練習 C — AI 系統威脅建模文件

> 目標：用 Ch 22 的 STRIDE 框架和 DFD 方法，對一個指定的 AI 系統做完整的威脅建模，產出一份正式文件，包含 DFD、STRIDE 矩陣、風險評估表、緩解措施建議。

---

## 目標系統描述

一家公司部署了一個內部知識庫 RAG Agent：

- 使用者透過 **Web UI** 提問（瀏覽器）
- Agent 有三個 tool：
  - **搜尋內部文件**（連接向量資料庫）
  - **查員工資料庫**（連接 HR 資料庫）
  - **寄送 Email**（連接 SMTP 服務）
- 知識庫包含 HR 文件、財務報告、技術文件（不同機密等級）
- 部署在 **Kubernetes**，LLM 用 **vLLM** 跑
- 使用者認證透過公司 **LDAP/AD**

## 題目要求

### 交付物 1：系統 DFD（Data Flow Diagram）

用 ASCII 圖畫出系統的資料流，必須：
- 標出所有外部實體（使用者、外部服務）
- 標出所有資料儲存（資料庫、向量庫）
- 標出所有處理程序（API、Agent、LLM）
- 用虛線框標出信任邊界（Trust Boundary）
- 箭頭標明資料流向和傳輸的資料類型

### 交付物 2：STRIDE 威脅矩陣

針對系統每個主要元件，分析六類威脅：

| 威脅類別 | 英文 | 說明 |
|---------|------|------|
| Spoofing | 欺騙 | 冒充合法使用者或系統 |
| Tampering | 篡改 | 修改資料或程式碼 |
| Repudiation | 否認 | 否認曾執行某操作 |
| Information Disclosure | 資訊洩漏 | 未授權讀取資料 |
| Denial of Service | 阻斷服務 | 讓服務不可用 |
| Elevation of Privilege | 提升權限 | 獲得超出授權的存取 |

每個類別至少 2 個具體威脅，每個威脅要有：
- 威脅描述（一句話說清楚攻擊場景）
- 受影響元件
- 攻擊者類型（外部攻擊者 / 內部員工 / 被入侵的 AI Agent）

### 交付物 3：風險評估表

對每個識別出的威脅進行評分：

- **可能性（Likelihood）**：1-5分（1=極低，5=極高）
- **影響（Impact）**：1-5分（1=可忽略，5=災難性）
- **風險等級（Risk）**：可能性 × 影響
  - 1-5：低風險
  - 6-14：中風險
  - 15-25：高風險

### 交付物 4：前 5 大風險的緩解措施

針對風險評分最高的 5 個威脅，提出：
- 主要緩解措施（技術手段）
- 補償性控制（輔助措施）
- 殘餘風險說明（做了這些還剩多少風險）

## 實作步驟

### Step 1：畫完整 DFD

從以下問題開始，逐步完成 DFD：

1. **誰使用這個系統？** 列出所有外部實體
2. **系統裡有哪些程序？** 列出所有處理節點
3. **資料存在哪裡？** 列出所有資料庫和暫存
4. **資料怎麼流動？** 畫出每條資料流，標明資料類型
5. **信任邊界在哪裡？** 用虛線框標出

這個系統的元件清單（你需要全部畫進 DFD）：
- 外部實體：使用者瀏覽器、SMTP 郵件服務
- 處理程序：Web API、LangChain Agent、vLLM、Email Tool
- 資料儲存：LDAP/AD、向量資料庫（ChromaDB）、HR 資料庫、文件儲存
- 網路邊界：Internet/Intranet 邊界、K8s Namespace 邊界

### Step 2：逐元件做 STRIDE 分析

對每個元件系統地問：

```
以 Web API (FastAPI) 為例：

S - 有人能冒充 Web API 嗎？（例如 DNS 劫持）
T - 有人能篡改 API 的請求或回應嗎？（例如 MITM）
R - API 有沒有記錄足夠的日誌來防止否認？
I - API 會不會洩漏它不該洩漏的資訊？（錯誤訊息、debug info）
D - 有辦法讓 API 服務不可用嗎？（flooding、大 payload）
E - 有辦法透過 API 獲得超出授權的存取嗎？（BOLA、權限繞過）
```

至少要分析：Web API、LangChain Agent、vLLM 服務、向量資料庫、HR 資料庫

### Step 3：AI 特定威脅

除了傳統 STRIDE，AI 系統有額外的威脅類別需要納入：

- **Prompt Injection**（屬於 T + E）：輸入惡意 prompt 操控 AI 行為
- **RAG Poisoning**（屬於 T）：污染知識庫影響輸出
- **Model Data Extraction**（屬於 I）：透過輸出推測訓練資料或 system prompt
- **Agent Tool Abuse**（屬於 E）：讓 Agent 呼叫不該呼叫的 tool
- **Token Flooding DoS**（屬於 D）：超大 context 打爆 GPU 記憶體

這些都要在 STRIDE 矩陣裡反映。

### Step 4：填寫風險評估表

可能性評分參考：
- 5：這個攻擊很容易執行，且已有公開工具（例如基本 prompt injection）
- 4：需要一些技術能力，但不需要特殊存取
- 3：需要特定知識或內部存取
- 2：需要高度技術能力或特殊條件
- 1：幾乎不可能或需要 APT 等級的攻擊

影響評分參考：
- 5：全公司資料洩漏 / 服務完全停止 / 法律責任
- 4：大量敏感資料洩漏 / 核心服務中斷
- 3：部分敏感資料洩漏 / 服務降級
- 2：少量非敏感資料洩漏 / 輕微服務影響
- 1：可忽略的資訊洩漏 / 幾乎無影響

### Step 5：緩解措施優先排序

用 DREAD 邏輯找出前 5 大風險（風險分數最高的），為每個提出：
- 主要緩解措施：直接解決這個威脅
- 補償性控制：假設主要措施失效時的備援
- 殘餘風險：做完這些後，這個威脅還剩多少危險

### 前 5 大風險緩解措施

**T-014：Prompt Injection（風險 20）**

主要緩解措施：
- 部署 NeMo Guardrails 或 Lakera Guard 做 input/output rail
- 在 system prompt 使用明確的 XML tag 隔離 user input：
  `<user_input>...</user_input>` 裡的指令不應被執行
- LLM 不直接接受使用者輸入，Agent 做一層參數驗證

補償性控制：
- 完整記錄所有請求和回應，異常行為觸發警報
- 限制 Agent 在每次 session 能呼叫的 tool 次數

殘餘風險：Prompt injection 目前沒有完全可靠的防禦，仍有繞過的可能性。估計風險降為 12（中）。

---

**T-013：Agent 無授權查詢 HR 資料（風險 20）**

主要緩解措施：
- Agent 的 HR 查詢 tool 只能查詢當前登入使用者自己的資料
- 實作 ABAC（Attribute-Based Access Control）：查詢前驗證使用者身份和資料擁有者是否匹配
- HR 資料庫實作 Row-Level Security（RLS）

補償性控制：
- 所有 HR 資料查詢記錄到稽核日誌，每日異常查詢自動警報
- 定期人工審查 Agent 查詢日誌

殘餘風險：技術控制完整後，主要殘餘風險是管理員帳號被入侵。估計風險降為 6（低）。

---

**T-015：Agent Tool Abuse（風險 16）**

主要緩解措施：
- Email Tool 加入白名單：只能寄到 @company.com 內部地址
- 實作 Human-in-the-loop：寄出 Email 前要求使用者確認
- Email 內容不能包含附件或 HTML（純文字）

補償性控制：
- 所有對外郵件自動副本給管理員信箱
- 設定每小時、每日發信數量上限

殘餘風險：內部地址仍可能被濫用傳播惡意訊息。估計風險降為 8（中）。

---

**T-003：RAG 知識庫投毒（風險 15）**

主要緩解措施：
- 文件上傳到知識庫前，掃描是否含注入指令（regex + LLM 分類）
- 實作文件來源追蹤：每個文件記錄上傳者、時間、hash
- 定期重新審查知識庫內容

補償性控制：
- 在 RAG prompt 裡明確告知 LLM：文件內容中的指令不應被執行
- 限制文件上傳權限，普通員工不能直接上傳，需要審核

殘餘風險：間接注入難以完全防禦，尤其是寫得很隱蔽的情況。估計風險降為 9（中）。

---

**T-010：Token Flooding DoS（風險 16）**

主要緩解措施：
- vLLM 設定 `--max-model-len 4096` 硬性截斷
- API 層設定 request body 大小上限（例如 10KB）
- Rate limiting：每個使用者每分鐘最多 10 次請求

補償性控制：
- K8s ResourceQuota 限制 vLLM Pod 的 GPU 和記憶體
- 超過閾值自動觸發 PagerDuty 警報

殘餘風險：在 rate limit 內仍可造成輕微降速。估計風險降為 6（低）。

## 測試用例

完成文件後，用以下問題自我審查：

```
1. DFD 完整性：
   - DFD 裡的元件是否覆蓋了題目描述的全部系統元件？
   - 所有資料流是否都有標明方向和資料類型？
   - 信任邊界是否正確標出（Internet/Intranet、K8s cluster）？

2. STRIDE 矩陣完整性：
   - 每個 STRIDE 類別是否都有至少 2 個威脅？
   - 是否包含了 AI 特定威脅（prompt injection、RAG 投毒、agent abuse）？
   - 每個威脅是否都有明確的受影響元件和攻擊者類型？

3. 風險評估合理性：
   - 風險分數的可能性和影響評分是否有依據（不是隨便填的）？
   - 高風險的威脅（15+分）是否都是真的重大威脅？
   - AI 特定威脅的可能性是否反映了現實（prompt injection 很容易做）？

4. 緩解措施有效性：
   - 緩解措施是否具體可執行（不是「加強安全」這種廢話）？
   - 殘餘風險是否誠實（做了緩解之後不可能變成 0 風險）？
   - 補償性控制是否真的能在主要控制失效時發揮作用？
```

## 自我檢核

- [ ] DFD 包含所有題目描述的元件，信任邊界正確標出

- [ ] 每個威脅都有受影響元件和攻擊者類型
