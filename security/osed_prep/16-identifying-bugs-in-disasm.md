# Ch 16 — 從反組譯辨識 bug：unsafe copy、長度檢查缺陷

> **目標**：在組語（與 Hex-Rays 虛擬碼）裡認出常見漏洞樣式——危險函式呼叫、固定大小 stack 緩衝區後接無長度檢查的複製迴圈、看似有檢查但比錯的長度判斷、整數問題導致的過小配置。看完這一章,你應該能在陌生 handler 裡「一眼認出可疑段落」,而不是逐行瞪著組語等靈感。

> **環境**：Win10 x64 + IDA Free 9.x/IDA Pro。本章反組譯片段為**教學示意**，未在真實 binary 上逐一驗證位址；示意片段標注清楚,驗證法見文末。

## 為什麼需要這一章

Ch 15 教你逆出協定、找到每個指令的 handler。但找到 handler 不等於找到漏洞——大部分 handler 其實是安全的,只有少數會把使用者可控的資料,複製進一個不夠大的緩衝區。你需要的是一套**模式辨識**的能力:看到特定的組語形狀,直接反應出「這裡可能溢位」,而不是每次都要完整模擬執行過程才能判斷。

這和 Linux pwn 找洞的直覺是共通的——在原始碼層級你一眼認得出 `strcpy(buf, user_input)` 很危險；這一章要把同樣的敏感度,移植到組語層級,因為考場不會給你原始碼。

## 先建立直覺：漏洞在反組譯裡的「形狀」

絕大多數 stack overflow 類漏洞的反組譯,長這個樣子的疊構:

```
┌─────────────────────────────┐
│ 1. 函式開頭配置固定大小的      │   sub esp, 0x200
│    stack 緩衝區               │   (buf 佔用 0x200 bytes)
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 2. 某個複製動作把「使用者可控   │   call strcpy / rep movsb / 手寫迴圈
│    長度的資料」寫進這個緩衝區   │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 3. (可能有，也可能沒有)        │   cmp ecx, 0x200 之類的比較
│    長度檢查                   │   —— 問題在：有沒有做？做對了嗎？
└─────────────────────────────┘
```

你要練的,就是認出第 1 步的緩衝區大小、第 2 步的複製方式、第 3 步的檢查是否存在且正確。三者對不上,就是一個候選漏洞。

## 危險函式清單與語意

先把老朋友的語意釘死(Linux pwn 熟悉的那套,在 Windows CRT 裡一樣危險):

- **`strcpy(dst, src)`**：複製 `src` 直到遇到 `\0`,**不管 `dst` 多大**。`src` 若是使用者可控且夠長,必定溢位 `dst`。
- **`strcat(dst, src)`**：把 `src` 接到 `dst` 現有字串後面,同樣不檢查 `dst` 剩餘空間。
- **`sprintf(dst, fmt, ...)`**：依 `fmt` 展開寫入 `dst`,不檢查 `dst` 大小。`fmt` 裡有 `%s` 且參數是使用者可控字串時特別危險。
- **`gets(dst)`**：從標準輸入讀一行寫進 `dst`,完全沒有長度界限——網路服務少用（這是給本機輸入的函式），但手寫的「讀一行網路資料」邏輯常常自己重造一個等價物,一樣危險。
- **`memcpy(dst, src, n)` / Win32 的 `CopyMemory`（本質是同一個東西）**：複製 `n` bytes,`n` 本身沒有危險,**危險的是 `n` 從哪來**——如果 `n` 是使用者可控的值（例如直接取自網路封包裡的一個長度欄位,未經檢查）,就等於攻擊者自己決定溢位多少 bytes。

在反組譯裡,這些函式會以 `call strcpy`、`call memcpy` 等形式出現（有 import 符號時),或在最佳化/inline 後變成一段手寫的複製迴圈（見下段)。按 `X` 看呼叫處,核對傳入的 `src`/`n` 是否可追溯到 `recv` 緩衝區——能追溯到,就是候選。

## 組語徵兵：手寫複製迴圈

編譯器有時會把短的複製 inline 成組語迴圈,不透過 `call`。常見兩種形式:

**(a) `rep movsb` / `rep movsd`**——x86 的字串複製指令,`ecx` 給長度,`esi`→`edi` 複製:

```
; 示意:典型的 inline 複製，ecx 從哪來是關鍵
mov  ecx, [ebp+recv_len]    ; ← 這個長度是 recv() 回傳的實際收到的 byte 數
mov  esi, [ebp+recv_buf]
lea  edi, [ebp+local_200]    ; 目的地：一個 0x200 bytes 的 stack 緩衝區
rep  movsb                   ; 複製 ecx bytes，從 esi 到 edi，不檢查 edi 的容量
```

如果 `ecx`（這裡是 `recv_len`,直接來自網路輸入的實際長度）沒有在複製前被限制在 `0x200` 以內,攻擊者送多少 bytes 就複製多少 bytes 進這個固定大小的緩衝區——**典型 stack overflow**。

**(b) 手寫的位元組/字元迴圈**：

```
; 示意:逐字元複製直到碰到結束符，等價於手刻的 strcpy
xor  ecx, ecx
copy_loop:
mov  al, [esi+ecx]
mov  [edi+ecx], al
inc  ecx
test al, al
jnz  copy_loop               ; 持續複製直到遇到 0 結束符，edi 多大完全不檢查
```

這段邏輯看起來不像在「呼叫危險函式」,但語意上跟 `strcpy` 一模一樣——這是為什麼只盯著 import 清單裡有沒有 `strcpy` 字樣是不夠的,組語形狀本身要認得出來。

## 長度檢查缺陷：有檢查,但檢查錯了

比起完全沒檢查,更隱蔽的漏洞是**檢查存在但邏輯錯**。常見三種:

**比較用錯運算元或方向**（示意）:

```
; 示意:檢查寫反，變成「只要小於緩衝區大小才拒絕」
cmp  ecx, 0x200
jl   reject_too_long          ; 本意應該是 jg/jge（太長才拒絕），寫反成太短才拒絕
; 正常複製邏輯接在這裡，長度 >= 0x200 的輸入反而被允許通過
```

**有號/無號比較混用**：x86 的 `cmp` 本身只是減法設旗標,真正決定「怎麼解讀結果」的是接在後面的跳轉指令——`jl`/`jg`（有號,signed）vs `jb`/`ja`（無號,unsigned）。如果長度變數的型別原本該當無號處理（長度不該是負的）,但組語用了 `jl`/`jg` 這組有號跳轉,一個刻意構造出「看起來是負數」的長度值（高位 bit 被設起來的大數字）就能騙過檢查:

```
; 示意：假設 ecx 存使用者傳入的長度，本意應視為 unsigned
cmp  ecx, 0x200
jg   reject                   ; jg 是有號比較！若 ecx 高位 bit=1(即 unsigned 下是個巨大值)
                               ; 有號解讀下反而是「負數」，負數 < 0x200，不會跳到 reject
; 複製邏輯照跑，用一個 unsigned 巨大值當長度 → 大溢位或錯誤行為
```

**Off-by-one**：邊界用 `<=` 還是 `<` 寫錯,導致剛好在邊界的那一個 byte 多寫或少檢查:

```
; 示意：迴圈條件 <= 而非 <，多跑一次
cmp  ecx, 0x200
jle  copy_loop                 ; 本意 jl（< 0x200），寫成 jle（<= 0x200）多算一個 byte
```

Off-by-one 單獨看起來影響很小（一個 byte）,但在某些佈局下足以覆寫到關鍵的 byte（例如 saved frame pointer 的最低位元組,或緊鄰緩衝區後的某個旗標),效果可能遠大於字面上的「一個位元組」。

## 整數問題導致的過小配置

另一類比較隱蔽:長度**計算**本身就錯,而不是比較錯。常見在動態配置緩衝區時:

```
; 示意：長度欄位相減得到負值，轉成 unsigned 後變巨大值，或反過來造成配置過小
mov  eax, [ebp+total_len]
sub  eax, [ebp+header_len]    ; 本意算出 payload 長度
push eax
call malloc                   ; 若 total_len < header_len，eax 下溢成一個巨大的 unsigned 值
                               ; malloc 可能失敗，或配置到一個極小/極大、非預期的大小
```

這類問題的核心是**有號/無號的語意在運算過程中被混用或忽略**,造成配置出來的緩衝區大小和後面實際寫入的資料量不匹配——配置太小,後面寫入時溢位；配置失敗沒檢查回傳值,後面對一個無效指標寫入直接當掉或變成可控寫入,視情況而定。

## 對比取捨：三種漏洞樣式怎麼分辨優先序

| 樣式 | 辨識難度 | 可利用性(典型) | 辨識線索 |
|---|---|---|---|
| 完全沒有長度檢查（直接 `strcpy`/無界迴圈） | 低，一眼可見 | 高,通常直接 EIP 控制 | 固定大小緩衝區後直接接複製,複製前後找不到任何 `cmp`/跳轉 |
| 檢查存在但方向/有號無號寫錯 | 中，需要讀懂跳轉指令語意 | 高,效果等同沒檢查但更隱蔽 | 有 `cmp`+跳轉,但跳轉指令（`jl` vs `jb` 等）和變數的預期語意不符 |
| Off-by-one / 整數下溢導致配置錯 | 高，需要追溯長度變數的計算來源 | 視佈局,可能只能溢位極小範圍或造成間接問題 | 邊界用 `<=`,或配置大小由減法/乘法運算得出而沒檢查中間結果 |

逆向時先掃過一遍找「低辨識難度」的樣式——這些往往是教學靶和部分考場目標的主要漏洞。找不到再往複雜的樣式深挖。

## 踩雷集錦

1. **錯誤直覺：看到 `memcpy` 就是漏洞** → **正確**：`memcpy` 本身是中性的,危險與否取決於第三個參數（長度）是否可被攻擊者控制且未受限制。先追長度變數的來源,再下判斷。
2. **錯誤直覺：有 `cmp` 加跳轉就代表長度檢查是對的** → **正確**：要讀懂比較用的是哪組跳轉指令（有號 vs 無號）、方向對不對、邊界是 `<` 還是 `<=`。檢查「存在」和檢查「正確」是兩件事。
3. **錯誤直覺：固定大小緩衝區（`sub esp, 0x200`）本身就是漏洞訊號** → **正確**：固定大小緩衝區到處都是,正常情況下配合正確的長度檢查完全安全。危險的是「固定大小 + 無界或錯誤檢查的複製」這個**組合**,缺一不可。
4. **錯誤直覺：只要函式裡沒有危險函式呼叫（`strcpy` 等）就安全** → **正確**：編譯器可能把複製 inline 成 `rep movsb` 或手寫迴圈,不會留下任何「危險函式」的 import 呼叫痕跡,一定要認得組語層級的複製形狀,不能只靠搜函式名。
5. **錯誤直覺：找到一個漏洞就代表這個 handler 逆完了** → **正確**：同一個 handler 常常不只一個問題,或同一支服務的不同 handler 各藏一個。Practice C 會特別練「找出第二個漏洞」這個習慣。

## 進階：再往深一層

- **Stack cookie（`/GS`）對這些樣式的影響**：有 `/GS` 保護的函式,溢位 stack 緩衝區可能先觸發 cookie 檢查失敗而當掉,而不是直接讓你控制 EIP。識別 `/GS` 的痕跡（函式開頭存一份 `security_cookie` 到 stack,結尾核對)是進階辨識的一部分,`windows_pwn` 課程對現代緩解有更深入的處理,OSED 範圍內的教學靶通常刻意關閉或較舊,但考場目標不保證。
- **Hex-Rays 虛擬碼下的同一套樣式**：有 `F5` 時,上面這些組語形狀在虛擬碼裡會呈現得更直白——`strcpy(v4, a2)`、`memcpy(&buf, a2, v3)` 這種類 C 呼叫,配合變數宣告直接看出緩衝區大小（例如 `char buf[512]`）。但虛擬碼有時會把長度檢查的邏輯重新排列得不直覺,懷疑結果時回去對組語確認。

## 本章重點整理

- 漏洞的反組譯「形狀」三件套：固定大小緩衝區配置 → 複製動作 → （有或沒有/對或錯的）長度檢查。三者對不上即是候選。
- 危險函式語意：`strcpy`/`strcat`/`sprintf`/`gets` 無長度界限；`memcpy`/`CopyMemory` 本身中性,危險看第三參數來源。
- 複製不一定透過函式呼叫，`rep movsb` 與手寫迴圈是同樣危險的 inline 形式,必須認得組語樣貌。
- 長度檢查缺陷三型：方向寫反、有號/無號混用、off-by-one；三者都讓「看起來有檢查」實際上形同沒檢查。
- 整數下溢/上溢可能導致配置的緩衝區本身就比預期小,追問題要追溯到長度**計算**,不只是**比較**。
