# Final Project — 48 小時 OSED 模擬考

> **目標**：用一場完整模擬考，驗收本課 70% 以上的核心概念——逆向找洞、SEH/stack overflow、egghunter、DEP/ASLR bypass、手寫 shellcode、format string——同時練一次 OSED 真實考試的節奏：有限時間、多題並行、要交可重現 exploit 與一份 OffSec 風格報告。這不是另一篇教學，是給你自己打的一場考試。

> **環境**：三個 assignment 全部建議在你自己的隔離 VM 裡架設（延續 Ch 0 的拓撲：攻擊機 + 偵錯/靶機兩台，或單機 `127.0.0.1` 互打）。本專案不提供任何靶程式的下載連結或原始碼（避免在教材裡散布可執行檔），改以「用什麼現成靶 + 怎麼自己出題」的方式描述，你需要自行準備目標。所有「預期行為」若未在你自己環境實測，標注為**未實測，理論預期**，並附上你應該怎麼驗證。全程只在你擁有完整授權的機器上進行。

## 為什麼要有這個 Final Project

OSED 的實際考試是 48 小時：拿到三個獨立的 assignment，各自需要你完成逆向找洞、構造 exploit、取得 code execution 的證明，然後在額外時間內寫出一份 OffSec 格式的報告。這個節奏和你前面逐章練習的方式完全不同——每一章你專注一個技法，Final Project 要你**在時間壓力下，自己判斷一個陌生目標該用哪一套技法、卡住了怎麼換路、什麼時候該放棄這條路線換下一題**。

這份文件不教新技法，它的任務是：
1. 給你三個涵蓋本課主要 Part 的 assignment 設計（題意、交付要求、評分配分）；
2. 給你每題「卡住了怎麼辦」的提示階梯（不是答案，是讓你自己往下想的引導）；
3. 給你整體時間分配建議與 OffSec 風格報告模板；
4. 給你一套自我評分 rubric，讓你知道「打到這個程度算不算準備好了」。

参考解法思路放在每題結尾的 `<details>` 摺疊區塊——那裡給的是方法論與關鍵步驟，不是逐行 code。你應該先自己打完（或打到卡死）才展開看。

### 三題分別驗收哪些 Part

這場模擬考不是隨便拼三個題目，是刻意設計成讓每一題各自整合本課不同 Part 的技能組合，合起來覆蓋課程的大部分內容：

| 題目 | 整合的 Part | 核心驗收能力 |
|---|---|---|
| 題 1：自訂 x86 網路服務 | Part 4（逆向找洞）+ Part 2（stack overflow）+ Part 7（DEP）+ Part 8（ASLR）+ Part 6（shellcode） | 從零逆向陌生目標、找到可利用的 bug、疊加繞過兩種緩解 |
| 題 2：SEH + 空間受限 | Part 3（SEH overflow）+ Part 5（egghunter） | SEH chain 的理解與操作、在極度受限空間下仍能插入 full shellcode |
| 題 3：Format string | Part 9（format string） | 讀寫原語的精確計算，以及把「讀寫記憶體」轉成「控制程式邏輯」的思維 |

三題合起來，你會用到本課 Part 2、3、4、5、6、7、8、9——總共八個 Part 裡的七個（Part 1 的基礎貫穿全部題目，Part 10 的 PE 後門技法則不在這次模擬考範圍內，因為它和控制流劫持是不同的攻擊類型）。這個覆蓋率對應題目要求的「70% 以上核心概念」。

### 為什麼設計成三題獨立、而不是一題涵蓋全部

OSED 真實考試採用的就是「三個獨立 assignment」的結構，而不是一個需要你把所有技法串在一條鏈上的超級題目。這個設計有意義：它測試的是你能不能在不同的漏洞類型之間**快速切換思維模式**——題 1 要你用「控制流劫持 + 繞過緩解」的思路，題 2 要你用「空間受限下的巧妙構造」思路，題 3 要你用「讀寫原語的精確計算」思路。三種思路的肌肉記憶不同，這正是本課 Part 2–9 分開教、而不是合併成一條大 pipeline 的原因，也是這份模擬考照樣分三題的原因。

### 自己出題的建議靶組合

本課沒有提供現成的三個靶程式（避免在教材裡散布漏洞程式），你可以用以下組合自己架設：

- **題 1（stack overflow + DEP + ASLR）**：用 vulnserver（Ch 0 介紹過）的某個尚未在前面練習裡用過的指令（README 列出 `TRUN`/`GMON`/`GTER`/`KSTET` 等，選一個你還沒打過的），**手動關閉它的 ASLR 保護模組來源**——例如自己寫一個小的 C 程式用 `/DYNAMICBASE:NO` 編譯（mingw: `-Wl,--disable-dynamicbase`）當作「非隨機化模組」，模擬 Ch 31 教的場景；或直接找一個公開、OSED 社群常用來練習的老舊 32-bit 第三方軟體（本身未開 ASLR 的歷史版本）。
- **題 2（SEH + 空間受限）**：vulnserver 裡有專門設計成 SEH-based 漏洞的指令（Ch 12 已經用過其中一個），這次選一個不同的指令，並**自行限制 payload 可用空間**（例如只允許覆寫後剩下 100 bytes 可用，逼自己用 egghunter）。
- **題 3（format string）**：用 Ch 34–36 練習過的自訂 format string 靶程式架構（一個會把使用者輸入直接傳進 `printf`/`wsprintf` 類函式的小型網路服務），自己寫一個新版本、换一個觸發點與緩解設定（例如關掉編譯器的 format string 警告、確保 `%n` 真的能被解析執行）。

### 自己出題的具體做法（三題各一段可操作的設置說明）

**題 1 的非隨機化模組設置**：如果你想重現「某個模組未開 ASLR」這個情境,最簡單的做法是自己寫一個極簡的 C 動態連結庫（內容無關緊要，重點是編譯設定），用 mingw 編譯時明確關閉 `DYNAMICBASE`：

```bash
gcc -shared -o helper.dll helper.c -Wl,--disable-dynamicbase -Wl,--disable-nxcompat
```

把這個 DLL 放進你的靶程式目錄,讓靶程式啟動時載入它（例如用 `LoadLibrary` 或直接作為它的依賴）。用 `dumpbin /headers helper.dll` 確認 `DllCharacteristics` 沒有 `DYNAMIC_BASE` 位元,再用 WinDbg 重啟服務兩次，確認這個模組的載入位址（`lm` 指令）兩次完全相同——這就是你題 1 要找的跳板來源。

**題 2 的空間限制設置**：直接在你自訂的靶程式協定設計裡,讓某個指令的處理函式只分配一個小的 stack buffer（例如 `char buf[80]`），但協定本身允許送更長的輸入（例如 300 bytes）。覆寫超出 80 bytes 的部分會蓋到 SEH chain,而「蓋到 SEH chain 之後、到連線協定允許的總長度上限之間」的那一段，就是你题目設計上刻意要限制的可用空間——調整這個總長度上限（協定層面的 buffer 大小），就能控制題目的難度（可用空間越小，越逼近真實 egghunter 場景）。

**題 3 的 `%n` 啟用設置**：如果你用 MSVC 編譯你的 format string 練習靶,在 `main` 函式最開始加上：

```c
#include <stdio.h>
int main(void) {
    _set_printf_count_output(1);  // 沒這行，%n 在新版 MSVC CRT 下不會執行寫入
    /* ... 你的網路服務邏輯 ... */
}
```

如果你用 mingw 編譯（本課預設工具鏈），mingw 的 CRT（走 `msvcrt.dll` 或 `ucrtbase.dll`，依連結設定）對 `%n` 的處理方式需要你自己先寫一個三行的最小範例驗證：

```c
#include <stdio.h>
int main(void) {
    int n = 0;
    printf("test%n\n", &n);
    printf("n = %d\n", n);  // 預期輸出 4（"test" 的長度）
    return 0;
}
```

跑一次看 `n` 有沒有被正確寫成 4——如果這個最小範例都不工作，你的題 3 目標從根本上不成立，必須先解決這個前提，再去設計完整的靶程式。

> **關於 `%n` 的啟用前提**：Visual C++ 從 VS2005 起，CRT 的 `printf` 家族函式**預設停用 `%n`**（行為被 `_set_printf_count_output` 控制，預設值是關閉），直接呼叫 `printf("%n", ...)` 在新版 MSVC CRT 下不會生效（甚至可能觸發 CRT 自己的例外）。要讓題 3 的 `%n` write primitive 真實可用，你必須在自己架設的靶程式裡**明確呼叫 `_set_printf_count_output(1)`**，或者改用舊版 CRT / mingw 的 `printf`（mingw 的 `printf` 實作走的是不同的 CRT，`%n` 的行為需要你自行驗證是否受限）。這是出題時最容易漏掉、導致題 3 整題打不穿的前提條件，務必在出題階段先驗證 `%n` 確實會執行寫入,再進入解題流程。
>
> **未實測，理論預期**：`_set_printf_count_output` 的行為依 Microsoft CRT 文件整理，mingw CRT 的 `%n` 支援狀況需要你自己在目標編譯環境裡用一個最小範例（`printf("test%n", &var)` 配合 `_set_printf_count_output(1)`）驗證過，才能確認題 3 的攻擊面成立。

## 題 1：自訂 x86 網路服務——逆向找洞 + DEP/ASLR 雙重 bypass

### 情境描述

你拿到一個陌生的 32-bit Windows 網路服務（二進位，無原始碼），它監聽一個 TCP port，接受若干文字指令。題目不告訴你哪個指令有漏洞，也不告訴你是什麼型態的漏洞——這是刻意的，OSED 真實考試的 assignment 1 經常就是這樣的設定。目標環境已知：DEP 開啟，ASLR 開啟（但目標進程載入的某個第三方模組未隨機化，或你能找到一個 info leak），無 CFG/CET（維持 OSED 考試環境的乾淨假設）。

你的任務：
1. 用 IDA 逆向這個服務，找出哪個指令存在 stack-based buffer overflow；
2. 用 fuzzing/手動測試觸發 crash，在 WinDbg 裡確認控制了 EIP；
3. 找到繞過 ASLR 的方法（非隨機化模組，或你自己在逆向過程中發現的 info leak 原語）；
4. 手工打造一條 ROP chain，呼叫 `VirtualProtect`（或 `VirtualAlloc`）繞過 DEP；
5. 接上一段壞字元安全的 shellcode（手寫或 msfvenom 生成皆可），取得 reverse shell。

### 協定與環境假設（出題/解題時的參考基準）

為了讓這題有明確的成功判準，建議（或若你是出題者，請明訂）以下假設：

```
- 目標協定：文字型 TCP 指令，格式類似 "COMMAND <data>\r\n"（仿 vulnserver 風格）
- 已知壞字元（出題時先用 mona bytearray 測過，解題時你需要自己重新驗證一次,
  不要直接信任這份清單）：0x00（null terminator）、0x0a/0x0d（行結尾，
  協定層面會截斷）、0x25（若協定本身用 % 做某種轉譯，需另行確認）
- 連線行為：服務崩潰後需要手動重啟（沒有自動重啟機制）——這意味著你的
  exploit 開發過程中，每次 crash 測試都要重啟一次,務必把重啟步驟腳本化
```

> 這份假設是給你出題與自我練習用的參考基準,不是惟一答案——你自己架設的靶，壞字元清單必須自己重新跑一次 mona 驗證，不能照抄這裡列的範例值。

### 交付要求

- 一個**可重現**的 Python exploit script（純 `socket`，不依賴 pwntools），從頭到尾跑一次就能拿到 shell，不需要手動介入。
- 截圖清單（至少含）：
  1. IDA 裡標出漏洞函式與關鍵指令的截圖
  2. WinDbg 裡 crash 瞬間，EIP 被你控制的截圖（暫存器視窗）
  3. 定位非隨機化模組或 info leak 的證明（例如該模組的 base address 每次重啟都相同的對比截圖，或 leak 出的位址）
  4. ROP chain 執行後，DEP 繞過成功、記憶體頁變成可執行的證明（例如在 WinDbg 裡 `!vprot` 顯示頁屬性變化前後對比）
  5. 最終取得 reverse shell 的截圖（攻擊機 `nc` 收到 shell，且在靶機上執行一個確認指令如 `whoami`）

### 如果卡住了：提示階梯

1. **找不到漏洞指令**：回到 Ch 15–18 的方法論——先列出服務支援的所有指令（通常協定裡有類似 `HELP` 的指令會列出來），對每個指令送一個異常長的輸入做初篩，再用 IDA 鎖定送長輸入後哪個函式呼叫了不檢查長度的複製函式（`strcpy`/`memcpy` 配固定/使用者可控長度）。
2. **crash 了但 EIP 不是你控制的值**：先確認你覆寫的範圍對不對——用 Ch 8 的 cyclic pattern（mona `pattern_create`）重新定位精確 offset，別假設你的 `"A"*N` 長度剛好落在 EIP 上。
3. **ASLR 繞不過去**：檢查目標進程載入的所有模組（WinDbg `lm`），找有沒有一個模組的 base address **每次重啟服務都相同**（通常是舊的、沒加 `/DYNAMICBASE` 編譯的第三方 DLL）。如果真的沒有，回頭檢查漏洞本身是否能順便洩漏一個位址（例如回應封包裡原樣回傳了某段記憶體內容）。
4. **ROP chain 排好了但執行到一半 crash**：先確認壞字元分析有沒有漏掉——ROP chain 裡每個 gadget 位址本身也要過壞字元檢查（這是初學者最容易忘記的一步，Ch 8 的壞字元表不只用在 shellcode，也要套用在你的 gadget 位址上）。
5. **VirtualProtect 呼叫完但 shellcode 沒執行**：確認 `lpAddress` 參數指向的位址，和你實際放 shellcode 的位址一致——常見錯誤是把要改保護屬性的頁算錯（算成 shellcode 所在頁的上一頁或下一頁）。

| DEP bypass（ROP chain）正確且可重現 | 25 |
| 完整 exploit 一次執行到取得 shell | 20 |
| 報告清晰度（截圖齊全、步驟可被第三方重現） | 5 |

<details>
<summary>參考解法思路（先自己打，卡死才展開）</summary>

**找洞**：這類題目的典型根因是一個指令處理函式裡用固定大小的 stack buffer（例如 `char buf[2000]`）接收網路輸入，用 `strcpy` 或等價的無界複製函式填入，沒有檢查輸入長度。IDA 裡的辨識特徵是：看到 `call strcpy`（或等價的 `rep movsb` 內聯展開）之前，沒有任何對輸入長度的比較/截斷指令。Ch 16 教的「不安全複製模式」辨識清單在這裡直接適用。

**控 EIP**：標準流程——cyclic pattern 定位 offset，確認 `EIP = 下一個 4 bytes`，接著做完整壞字元分析（mona `bytearray` + `compare`）。

**ASLR**：如果目標環境有意安排一個非隨機化模組（出題時故意用沒開 `/DYNAMICBASE` 編的 DLL），直接在 WinDbg `lm` 裡確認重啟後 base 不變,從這個模組裡找 `jmp esp` 或 ROP gadget。如果沒有這種模組（出題時刻意不給），要回頭看漏洞本身——很多網路服務的某個回應路徑會「原樣回傳部分輸入或部分記憶體」，這類題目的 info leak 往往藏在不起眼的、乍看和主漏洞無關的另一個指令裡。

**DEP**：Ch 29 的標準 VirtualProtect ROP chain 構造法——四個參數 `lpAddress`、`dwSize`、`flNewProtect=PAGE_EXECUTE_READWRITE(0x40)`、`lpflOldProtect`（指向一塊可寫記憶體）,全部透過 `pop eax/ebx/ecx/edx; ret` 類 gadget 排進 stack,最後 `ret` 進 `VirtualProtect`，return address 設成 shellcode 起點。

**shellcode**：壞字元安全的 reverse shell，可以用 Ch 25 教的手寫版本，也可以用 `msfvenom -p windows/shell_reverse_tcp -b '\x00...'`（指定壞字元清單）生成,兩種都合法,重點是驗證生成的 shellcode 真的不含你分析出的壞字元。
</details>

## 題 2：SEH Overflow + 空間受限 Egghunter

### 情境描述

另一個 32-bit 網路服務，這次的漏洞是透過 SEH 觸發（即：overflow 蓋到的是 SEH chain 上的 `Next SEH`/`SEH Handler`，不是直接蓋 return address）。而且這題刻意**限制了你能塞進去的 payload 空間**——覆寫點之後只有不到 150 bytes 可用，不夠放一個完整的 reverse shell shellcode，逼你必須先放一個小的 egghunter，再把完整 shellcode 放在封包的別處（egghunter 負責在記憶體裡掃到它再跳過去執行）。

目標環境：未開 SafeSEH（或你需要找一個未受 SafeSEH 保護的模組作為跳板來源），DEP 關閉（這題專注在 SEH + 空間限制，不疊加 DEP，維持題目的單一焦點，符合 OSED assignment 常見的「每題聚焦不同技能組合」設計）。空間限制的具體設計建議：overflow 點之後（蓋掉 Next SEH 之後的區域）只保留約 100–150 bytes 可用，其餘空間被協定本身的其他欄位佔用或直接截斷——這個數字刻意小於大多數壞字元安全 reverse shell shellcode 的長度（通常 300–400 bytes 以上），逼你必須走 egghunter 這條路，而不能像題 1 一樣直接塞完整 shellcode。

### 這題為什麼刻意不疊加 DEP

你可能注意到題 2 沒有像題 1 一樣要求同時繞過 DEP。這不是偷懶，是刻意的教學設計：SEH overflow 配合空間受限、再疊加 DEP bypass，三件事放在一起的複雜度會蓋過「SEH exploit 流程」和「egghunter 構造」這兩個本題真正要驗收的核心技能，讓你分不清自己到底卡在哪一層。OSED 真實考試裡，確實有 assignment 會把 SEH 和 DEP 疊在一起考，但作為模擬考的第一輪練習，先把變數控制住，確認這兩個技能本身紮實，之後再自己加一層 DEP 作為進階挑戰（見本題結尾的「進階挑戰」）。

你的任務：
1. 觸發 SEH-based overflow，在 WinDbg 裡觀察 SEH chain 被竄改；
2. 用 POP POP RET 技法找到跳板，完成短跳（short jump）+ 長跳（long jump）的標準流程；
3. 構造一個客製的 egghunter（四字節 tag，記得避開壞字元），塞進有限空間；
4. 把完整的壞字元安全 shellcode 放在封包的另一個區段（egghunter 掃描範圍內），驗證 egghunter 正確找到並跳轉執行。

### 交付要求

- 可重現的 Python exploit script。
- 截圖清單：
  1. WinDbg 裡觀察到的 SEH chain，標出被覆寫的 `Next`/`Handler` 欄位
  2. POP POP RET 跳板位址的確認（反組譯截圖，標出這三個指令）
  3. 短跳/長跳執行過程的單步除錯截圖（展示控制流如何從 SEH handler 跳到你的 egghunter）
  4. egghunter 在記憶體裡掃描、命中 egg tag 的過程（WinDbg 單步或記憶體視窗對比）
  5. 最終 shell 的截圖

### 如果卡住了：提示階梯

1. **找不到 POP POP RET**：先確認你要找的是「跳過 SEH 的 4-byte Next SEH 欄位，落到下一個可控位置」這個目的，不是隨便找 POP POP RET——mona 的 `!mona seh` 可以直接列出候選。如果候選都在受 SafeSEH 保護的模組裡，檢查目標進程有沒有載入一個舊的、未受保護的第三方模組（Ch 13 的核心主題）。
2. **短跳距離算錯**：短跳通常是 `EB XX`（2 bytes 的相對跳轉），你的 `XX` 要能跳過 4-byte 的 Next SEH 欄位落到長跳的位置——這個距離的計算錯誤是本題最常見的卡點,用 WinDbg 單步執行（`t`）盯著每一步 EIP 的位置，比憑算的更可靠。

   具體算法參考：`EB` 之後的 `XX` 是**相對於短跳指令執行完畢後的下一條指令位址**的有符號位移。假設短跳指令本身佔用 `Next SEH` 欄位的前 2 bytes（位址設為 `A`），你要跳到的長跳指令位於 `A + 6`（跳過 Next SEH 剩下的 2 bytes，加上 Handler 欄位的 4 bytes）,則：
   ```
   位移 = 目標位址 - (短跳指令位址 + 2)
        = (A + 6) - (A + 2)
        = 4
   因此短跳的 opcode 是 EB 04
   ```
   這個算法要套用到你實際的欄位佈局上重算一次，不要照抄 `EB 04` 這個數字——不同的協定封包佈局，Next SEH 和 Handler 之間的實際 byte 距離可能不同。
3. **egghunter 寫好了但一直找不到 tag**：確認 egghunter 用的 syscall（檢查記憶體頁是否可讀，常用 `NtAccessCheckAndAuditAlarm` 或等價技巧）本身有沒有壞字元問題；也確認你放置的「完整 shellcode」前面真的加上了兩次 egg tag（egghunter 通常要連續比對兩次 tag 才算命中，避免誤判）。
4. **shellcode 放的位置 egghunter 掃不到**：egghunter 是從某個起始位址往高位（或你設計的方向）線性掃描，如果完整 shellcode 被放在比 egghunter 起始掃描點更低的位址，就永遠掃不到——檢查你的封包佈局，shellcode 要放在 egghunter 掃描方向能到達的地方。

### 評分配分（滿分 100）

| 項目 | 配分 |
|---|---|
| 正確識別 SEH-based 漏洞與觀察 SEH chain 被覆寫 | 15 |
| POP POP RET 跳板選擇正確（含 SafeSEH 規避理由） | 15 |
| 短跳/長跳流程正確執行 | 15 |
| Egghunter 構造正確（壞字元安全、tag 設計合理） | 20 |
| 完整 shellcode 透過 egghunter 正確執行 | 25 |
| 報告清晰度 | 10 |

<details>
<summary>參考解法思路</summary>

**SEH 觸發與觀察**：送一個刻意設計長度的 overflow payload，在 WinDbg 裡用 `!exchain`（若有 mona/pykd）或手動走 `fs:[0]` 鏈，觀察到 `Next SEH`/`Handler` 兩個欄位被你的資料取代。

**POP POP RET**：核心原理是——例外發生時，系統把一個指向 `EXCEPTION_REGISTRATION_RECORD` 的指標傳給 handler,這個指標在呼叫 handler 前的 stack 佈局裡,"POP POP RET" 三個指令的效果恰好是把 stack 往上彈兩層，然後 `ret` 到彈出後的新頂端——這個新頂端如果就是你控制的 `Next SEH` 欄位，就等於把控制流導向你放在那裡的短跳指令。`!mona seh` 會自動掃描符合這個 pattern、且不在 SafeSEH 保護模組裡的候選位址。

**短跳+長跳**：`Next SEH`（4 bytes）塞不下完整跳轉邏輯，標準做法是先放一個 2-byte 短跳（`EB 06` 之類）跳過緊接著的 `Handler` 欄位（4 bytes，被 POP POP RET 的目標位址佔用），落到 `Handler` 之後的記憶體，那裡放一個完整的長跳（`E9 ...` 或等價），跳到你真正的 payload（本題是 egghunter）起點。

**Egghunter**：Ch 20–21 教的標準構造——選一個不常見的 4-byte tag（避開壞字元），egghunter 本體用合法的方式（不觸發 access violation 當機）逐頁檢查記憶體是否可讀，讀到之後比對是否連續兩次出現 tag，命中就跳轉執行 tag 後面的內容（也就是你放在封包其他地方的完整 shellcode）。
</details>

### 進階挑戰（可選，給打完基礎版還有餘力的人）

把題 2 的目標改成同時開 DEP：egghunter 本身可以正常放（egghunter 不需要執行額外的頁，只是掃描 + 跳轉），但它最終跳去執行的「完整 shellcode」現在會因為 DEP 而無法執行。這逼你要在 egghunter 找到 shellcode 之後，先讓一條小型 ROP chain 執行 `VirtualProtect`，再跳回 shellcode——等於把題 1 的 DEP bypass 技法和題 2 的 SEH + egghunter 技法疊在一起，這正是 OSED 真實考試裡較難的 assignment 常見的組合方式。不強制作為本次模擬考的交付要求，但如果你有餘力，這是檢驗「能不能把兩種技法自己串起來」的好練習。

## 題 3：Format String Leak + Write 導向 Code Execution

### 情境描述

第三個目標是一個會把使用者可控字串直接傳進 `printf` 家族函式（而非當作格式化模板的第一個固定字串使用）的網路服務——典型的 format string 漏洞根因：`printf(user_input)` 而非 `printf("%s", user_input)`。目標進程已確認 `%n` 可用（出題時已呼叫 `_set_printf_count_output(1)`，或使用不受此限制的 CRT/編譯器）。

你的任務：
1. 確認 format string 漏洞存在，用 `%x`/`%p` 序列驗證你能讀到 stack 上的任意內容；
2. 用讀取能力（arbitrary read）洩漏出足夠的資訊繞過 ASLR（例如洩漏一個模組內的位址，推算出模組 base）；
3. 用 `%n` 系列（`%n`/`%hn`/`%hhn`）構造 arbitrary write，把一個你選定的目標（例如一個函式指標、或者一個會在後續被呼叫的位址）改寫成你控制的值；
4. 透過後續的程式邏輯觸發這個被改寫的值，取得程式碼執行。

### 交付要求

- 可重現的 Python exploit script，分階段清楚標出「leak 階段」和「write 階段」。
- 截圖清單：
  1. 用 `%x`/`%p` 確認 format string 漏洞存在的截圖（送入 payload 前後的回應對比）
  2. 成功 leak 出一個已知含義的位址（例如某個模組 base）的證明，並附上你怎麼驗證這個位址的正確性（例如和 WinDbg 裡 `lm` 顯示的實際 base 對比）
  3. `%n` write 的計算過程（你怎麼算出要送多少個字元才能讓寫入值正確，建議附上你的計算腳本或手算過程）
  4. 寫入成功後，WinDbg 裡確認目標記憶體位置的值確實被改成你要的值
  5. 觸發 code execution 的最終截圖

### 如果卡住了：提示階梯

1. **送 `%x` 沒有觀察到任何異常，程式正常回應**：先確認你送的輸入真的是走到有漏洞的那條程式路徑——有些服務對不同指令走不同的字串處理函式，先用簡單的指令列舉（類似題 1 的 `HELP`）確認漏洞所在的具體指令。
2. **能讀但不知道怎麼定位到「有意義」的位址**：先送大量 `%p`（比 stack 深度更多次），把整段輸出記錄下來，再用已知值反查——例如你知道自己送的 payload 裡某個固定字串的長度，去輸出裡找有沒有看起來像指向你輸入 buffer 本身的位址（format string 漏洞很常見的現象是：你送的字串本身的位址，也會出現在 `%p` 掃出來的某個位置裡，這是絕佳的自我參照錨點）。
3. **`%n` 寫入的數值不對**：`%n` 系列寫入的值，是「到目前為止這個格式化字串已經輸出了多少個字元」。要精確控制寫入值，標準做法是用一串 `%x` 墊出指定寬度的輸出（例如 `%08x` 墊出固定 8 字元），再用寬度欄位（`%<width>x`）精確湊出你要的數字——這一步幾乎一定要寫一個小腳本幫你算，不要手算大數字，容易算錯導致寫入錯誤的值。

   **具體計算示範**（用 `%hn` 寫 2 bytes 為例）：假設你要讓某個記憶體位置被寫入值 `0x1234`（十進位 4660），而格式化字串在到達這個 `%n` 之前，已經自然輸出了 20 個字元（例如前面幾個 `%x`/位址參數造成的輸出長度）。你需要再墊出 `4660 - 20 = 4640` 個字元，才能讓 `%n` 寫入的累計字元數恰好是 4660。做法是用 `%4640x`（寬度欄位設為 4640，配合一個值很小的參數，讓輸出被空白字元墊到 4640 寬）接上 `%hn`。這個計算必須寫成一個小函式——先統計「已知會自然輸出的字元數」，再推算還差多少，寬度欄位的數字才不會憑感覺亂湊。

   ```python
   # 示範：算出要墊的寬度（概念程式碼，非完整 exploit）
   def width_for_target(target_value, chars_already_output):
       pad = (target_value - chars_already_output) % 65536  # %hn 寫 2 bytes，mod 0x10000
       return pad
   ```
   實際 exploit 裡通常要分別對高 2 bytes 和低 2 bytes 各算一次寬度，而且因為同一個格式化字串裡輸出是累加的，後面算的那個寬度要再扣掉前面已經墊出的量——這是 format string write 裡最容易算錯、也最值得耐心重算一次的環節。
4. **`%hn`/`%hhn` 和 `%n` 的差異搞混**：`%n` 寫 4 bytes（完整 `int`），`%hn` 寫 2 bytes（`short`），`%hhn` 寫 1 byte（`char`）。如果你只需要改寫一個位址的低位幾個 byte（部分覆寫，常見於只需要改到同一頁內跳轉），用 `%hn`/`%hhn` 分段寫，比一次用 `%n` 寫整個 4 bytes 更容易控制精確度,也更不容易因為數值過大導致 payload 長度暴增。
5. **寫入成功但程式沒有執行你預期的東西**：確認你選的「被改寫目標」真的會在之後被程式**主動讀取並使用**（例如一個稍後會被呼叫的函式指標，或是一個會影響分支判斷的旗標），不是一個寫完就沒人再碰的死記憶體——format string write 的價值完全取決於「寫完之後，程式自己會不會用到它」。

### 評分配分（滿分 100）

| 項目 | 配分 |
|---|---|
| 正確確認 format string 漏洞與根因 | 15 |
| Arbitrary read：成功 leak 出有意義的位址 | 20 |
| Arbitrary write：`%n` 系列精確寫入目標值 | 30 |
| 正確選定被改寫目標並觸發後續執行 | 25 |
| 報告清晰度（尤其是 `%n` 計算過程的可重現性） | 10 |

<details>
<summary>參考解法思路</summary>

**確認漏洞**：送 `%x %x %x %x %x`（或更多），觀察回應裡是否出現看起來像記憶體內容/位址的十六進位數字，而不是你預期的正常回應——這代表格式化字串在讀取本不該讀的 stack 資料（因為對應的實際參數根本沒被傳入，`printf` 照樣照著格式串往 stack 上層讀）。

**Arbitrary read**：有系統地送連續的 `%p`（比預期 stack 深度更多次），記錄每個位置輸出的值，再和已知錨點比對（上面提到的「你自己輸入字串的位址會自我出現」技巧）,定位出第幾個 `%p` 對應到你想要的那塊記憶體。一旦能用這個位置精確讀出模組內某個已知函式的位址，減去已知的 offset（該函式在模組裡的相對位置，可以從沒開 ASLR 的本機副本逆向得出），就能推算出模組的真實 base，完成 ASLR bypass。

**Arbitrary write 的計算**：`%n` 寫入值 = 目前已輸出字元數。要讓這個數字等於你要寫的任意值（例如一個位址的某個部分），標準技巧是用型如 `%<N>x` 的寬度欄位墊出剛好 N 個字元的輸出，再接 `%n`。對於要寫一個完整 4-byte 位址，通常拆成 `%hn` 分兩次各寫 2 bytes（高位、低位分開算,因為一次性墊出一個大數字對應的字元數常常大到不現實，payload 長度會爆炸),這是 format string exploit 裡最耗費耐心的手算/腳本輔助步驟,Ch 36 有完整的分段寫入計算方法。

**選定寫入目標**：常見選擇是一個稍後會被呼叫的函式指標（例如某個回呼函式表裡的一項），或者一個在程式邏輯裡控制「要不要執行某段程式碼」的旗標變數。寫完之後，讓程式走到會讀取這個值的路徑（通常只需要再送一個正常的後續指令，觸發程式自己的邏輯），完成控制流劫持。
</details>

```
  驗證穩定性（重跑 3 次）    10% T   ← 容易被跳過，但報告的可重現性全靠這一步
```

**一個實務建議**：如果某一題在「逆向/定位漏洞」階段超過該題總時間的 50%，先暫停，切到下一題，把剩下的時間留給你更有把握的題目——48 小時制的考試裡，**三題部分完成的分數，通常高於一題完美、兩題空白**。這是 Ch 39（考試作戰）反覆強調的策略，在這次模擬考裡親自驗證一次。

## OffSec 風格報告模板

以下是給三題各自用的報告段落骨架（markdown），寫報告時直接照這個結構填：

```markdown
# Exploit Report — [目標名稱 / 指令名稱]

## 1. Summary（摘要）
- 目標：[服務名稱、版本、監聽 port]
- 漏洞類型：[Stack-based buffer overflow / SEH overflow / Format string]
- 影響：[遠端程式碼執行 / 資訊洩漏，CVSS 風格的嚴重度描述可選]
- 一句話結論：[例如「TRUN 指令未檢查輸入長度，導致可控的 stack overflow，
  配合手工 ROP chain 繞過 DEP，達成遠端程式碼執行」]

## 2. Discovery（發現過程）
- 使用工具：[IDA / WinDbg / fuzzing 腳本名稱]
- 定位過程：[簡述你怎麼從「列舉指令」到「鎖定漏洞函式」]
- 關鍵反組譯片段：[貼出 IDA 截圖或關鍵組語，標出問題所在]

## 3. Exploitation（利用過程）
### 3.1 Crash 分析
- [offset 定位方法、crash 時暫存器狀態]
### 3.2 繞過的緩解機制
- [ASLR bypass 方法 / SafeSEH 規避方法 / 其他]
### 3.3 Payload 構造
- [ROP chain 佈局 / egghunter 設計 / %n 計算過程，附關鍵程式碼片段]
### 3.4 完整 exploit 流程
- [標號列出從發送 payload 到取得 shell 的每一步]

## 4. Proof of Concept
- 完整 exploit script：[附檔或貼全文]
- 執行截圖：[按交付要求清單附上]

## 5. Remediation（修復建議）
- [針對這個具體漏洞類型的修復建議：輸入長度檢查 / 使用安全函式 /
  升級到有 ASLR+DEP+CFG+CET 保護的編譯設定等]

## 6. Timeline（可選，若要模擬完整考試報告格式）
- [漏洞發現時間 / exploit 完成時間]
```

三題各寫一份，最後再寫一份**整合 Executive Summary**（給「非技術讀者」看的一頁摘要，OffSec 正式報告要求的格式之一）：三個漏洞分別是什麼、整體風險等級、最高優先修復建議。

### 填寫範例：Discovery 段落的具體寫法對照

報告最容易寫得空洞的段落是 Discovery（發現過程）——很多人會寫成「我用 IDA 看了一下，找到了漏洞」,這種寫法在真實 OffSec 報告評審裡會被扣分,因為它無法讓第三方（評審、團隊成員）重現你的發現過程。對照一下空洞寫法和及格寫法的差異：

```markdown
✗ 空洞寫法（不及格）：
  用 IDA 打開 target.exe，找到處理 TRUN 指令的函式，發現有 overflow。

✓ 及格寫法：
  1. 用 netcat 連上 target.exe 的 9999 port，送 HELP 指令，取得支援的指令列表：
     TRUN, GMON, GTER, KSTET, GTER2, ...
  2. 對每個指令送長度 5000 bytes 的 "A" 字串做初篩，觀察哪個指令導致連線中斷
     （服務崩潰的徵兆）——確認是 TRUN 指令。
  3. 用 IDA 打開 target.exe，在 Strings 視窗搜尋 "TRUN"，從字串的 xref 找到
     處理這個指令的函式 sub_401500。
  4. 在 sub_401500 的反組譯裡看到：
       call strcpy  （位於 0x401532）
     呼叫前，目標 buffer 宣告在 stack 上固定大小 2000 bytes（[ebp-0x7D0]），
     來源是直接來自 recv() 的網路輸入，中間沒有任何長度檢查指令。
  5. 這確認了根因：TRUN 指令處理函式用 strcpy 把使用者可控、長度不受限的
     輸入複製進固定 2000 bytes 的 stack buffer，造成 stack-based buffer overflow。
```

及格寫法的關鍵差異：**每一步都可以被第三方照著重做一次，得到一樣的結論**。這是 OffSec 報告評分的核心標準，也是你寫這次模擬考三份報告時該自我要求的標準。

## 分項技能自我檢核（彙總本課 Part 2–9）

除了每題各自的評分配分，用以下清單對照你在整場模擬考裡，每個 Part 的技能是否真的用上了、用得紮實。這份清單橫跨三題，是對本課「70% 以上核心概念」驗收要求的具體化：

**Part 2 — Stack Overflow 方法論**
- [ ] 能自己從「送異常輸入」走到「確認 offset」，不需要查筆記回想 cyclic pattern 的用法
- [ ] 壞字元分析這次是自己重做的（不是沿用之前練習靶的結果）

**Part 3 — SEH Overflow**
- [ ] 能分辨一個 crash 是「直接蓋 return address」還是「蓋到 SEH chain」（從 WinDbg 的例外資訊判斷）
- [ ] 能解釋為什麼這次用的 POP POP RET 位址沒有被 SafeSEH 擋下來

**Part 4 — IDA 逆向找洞**
- [ ] 題 1 的漏洞函式是自己從 Graph view / Strings 逆向定位出來的，不是靠猜測指令名稱
- [ ] 能講出根因（哪個函式呼叫、為什麼沒做長度檢查），不只是「它 overflow 了」

**Part 5 — Egghunter**
- [ ] 能解釋自己選的 egg tag 為什麼這麼選（避開了哪些壞字元）
- [ ] 能解釋 egghunter 掃描方向和放置 shellcode 位置的對應關係，不是試出來的

**Part 6 — 手寫 Shellcode**
- [ ] 至少一題的 shellcode 是自己手寫（或至少理解每個片段在做什麼），不是全部直接套 msfvenom 輸出
- [ ] 清楚自己的 shellcode 完整避開了這次目標的壞字元清單

**Part 7 — DEP Bypass**
- [ ] ROP chain 裡每個 gadget 的來源模組都能講出來（不是盲目複製 mona 的輸出）
- [ ] 能解釋 shadow space／對齊（若在 x86 題目中不適用可略過，但要能說明為什麼 x86 不需要）

**Part 8 — ASLR Bypass**
- [ ] 能清楚講出這次用的是「非隨機化模組」還是「info leak」路線，以及為什麼選這條路
- [ ] 若走 info leak 路線，能講出 leak 出的位址是怎麼被驗證為正確的

**Part 9 — Format String**
- [ ] `%n` 系列的寬度計算是自己手算或自己寫腳本算出來的，不是複製別人範例的數字
- [ ] 能解釋為什麼選定的「被改寫目標」真的會被程式後續使用

如果某個 Part 的檢查項目你打了勾卻心裡沒底（「好像是這樣，但我不確定能不能講清楚」），回頭對應章節重讀一次該章的「自我檢核」小節,比急著進到下一次模擬考更有效益。

### 跨題共通檢查清單（打完三題後逐項確認）

不管三題各自打得順不順，用以下清單檢查你的整體準備度，這些是跨題型、容易被忽略的共通項目：

- [ ] 每一條 exploit script 都能**從乾淨狀態重跑一次**成功（重啟靶程式、重新連線），不依賴「上一次殘留的狀態」
- [ ] 每一題都在 WinDbg 裡**親眼確認**過關鍵的中間結果（offset、壞字元清單、對齊狀態），不是只憑計算假設它對
- [ ] 三份報告的 Discovery 段落，都寫到「第三方能照著重現」的程度（見上面的填寫範例對照）
- [ ] 三題的壞字元分析都各自重做過一次（不同的目標、不同的輸入路徑，壞字元表不保證一樣）
- [ ] 截圖清單裡的每一張，檔名或標題能讓人一眼看出對應交付要求裡的哪一項，不是一堆沒有標註的螢幕截圖堆在一起

### 常見失分模式（對照 Ch 39 的考試作戰經驗）

這些是本課 Ch 39（OSED 考試作戰）討論過的常見失分模式，在這次模擬考裡刻意對照檢查一次，看自己有沒有犯：

1. **exploit 能跑，但只跑過一次**——第二次重跑失敗（通常是因為某個 heap/stack 狀態依賴了第一次執行殘留的副作用，而不是乾淨的初始狀態）。評審標準要求「可重現」，不是「曾經跑成功過」。
2. **報告裡的截圖和敘述對不上**——例如敘述寫「EIP 被覆寫成 0x41414141」，但附的截圖裡暫存器視窗顯示的是完全不同的值（可能是截圖截早了或截晚了）。每次要附截圖前，先確認截圖內容和你敘述的那一刻完全對應。
3. **省略了「為什麼」，只寫了「怎麼做」**——例如只寫「我用了 `pop pop ret` 在 0x7c1234 這個位址」，沒寫「為什麼選這個位址（它在哪個模組、為什麼沒有 SafeSEH 保護、為什麼能用來跳過 Next SEH 欄位）」。報告的評分同時看操作正確性和理解深度。
4. **低估了驗證穩定性要花的時間**——很多人把全部時間花在「讓 exploit 第一次跑成功」，完全沒留時間重跑驗證,結果交付的 exploit 其實有十分之一的機率失敗（例如依賴一個稍微不穩定的 timing）。回頭看本文件前面的「整體時間分配建議」，驗證穩定性那 10% 的時間預留不是可選項。

## 重打一次：難度調整建議

如果這次模擬考打完，自我評分落在「準備充分」區間，想再找一次挑戰，或者這次沒打完想降低難度重來一次，以下是具體的調整旋鈕：

**調降難度（適合第一次接觸 Final Project 形式的人）**：
- 題 1：直接提供非隨機化模組清單（不要求自己找 info leak）
- 題 2：放寬可用空間到 200 bytes 以上（egghunter 構造本身還是要做，但排版壓力變小）
- 題 3：先給定「被改寫目標」是什麼（例如明確告知是某個函式指標），只練 `%n` 計算本身

**調升難度（適合評分落在「準備充分」區間、想逼近真實考試壓力的人）**：
- 題 1：疊加題 2 的 egghunter（空間也受限，逼你把 Part 5 和 Part 7/8 一起用上）
- 題 2：套用本題結尾提到的「進階挑戰」（疊加 DEP）
- 題 3：把目標改成需要連續兩次 `%n` 寫入（例如先寫一個指標，再用這個指標間接寫到另一個位置——這更貼近某些真實 format string CVE 的複雜度）
- 全部三題：把時限從 48 小時壓縮到 24 小時，逼自己重新排優先序

**最有效的重打方式**：不要原封不動重打同一個靶（你已經知道答案，練習價值會大幅下降）。換一個 vulnserver 的其他指令、換一個不同的自訂目標、或者請同學／學習夥伴幫你改一版協定佈局——新鮮感帶來的「真的不知道哪裡有洞」才是這份模擬考最重要的訓練價值。

## 結語

從 Ch 0 的環境搭建，到這裡的三題模擬考，你走過的是 OffSec 設計給 OSED 的同一條路——逆向找洞、控制流劫持、繞過緩解、手寫底層原語、整合成可重現的 exploit，最後用一份經得起第三方檢驗的報告收尾。這條路練的不是某個工具的按鍵順序，是「每個 byte 都知道為什麼在那裡」的底層直覺,這個直覺不會因為換了考試、換了目標架構就失效。

如果這份模擬考讓你發現自己在 x64 或現代緩解（CFG/CET）面前還不夠篤定，那正是這次練習該帶給你的收穫——回頭看 Ch 40–41，再往本 repo 的 [`windows_pwn`](../windows_pwn/README.md) 走下去，把同一套直覺搬到 64-bit、搬到 Win11 的現代緩解戰場。

回到本課一開始（README）的定位：這門課要把你從「Linux ROP 很熟、一碰 Windows exploit dev 就卡」帶到「能獨立逆向一支陌生服務、寫出完整 exploit、交出一份經得起檢驗的報告」。打完這場模擬考，不管分數落在哪個區間，你已經實際走過這條生產線一次——這比任何一張證書本身更值得記住。
