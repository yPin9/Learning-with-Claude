# Ch 17 — 靜態逆向 + 動態驗證雙軌（IDA ↔ WinDbg）

> **目標**：學會把 IDA 裡靜態推理出的「可疑函式」,接到 WinDbg 裡實際下斷點驗證——包括 IDA 位址（ImageBase 相對）和 WinDbg 位址（實際載入基址,ASLR 下會變）之間的換算。看完這一章,你應該能把一個「我猜這裡會溢位」的假設,變成「我在偵錯器裡親眼看到它溢位」的證實。

> **環境**：Win10 x64 + IDA Free 9.x/IDA Pro + WinDbg（2026）。所有 WinDbg 操作步驟與輸出標**未實測，理論預期**；驗證法見文末。

## 為什麼需要這一章

Ch 16 教你在反組譯裡認出「這裡看起來會溢位」的樣式——但這終究是**靜態推理**,是你讀程式碼腦內模擬執行的結果。靜態推理會錯：你可能誤判了某個檢查的語意、漏看了前面還有一層過濾、或者這段程式碼其實根本沒被你以為的那條路徑執行到。

OSED 要求的不是「我覺得這裡有洞」,而是「我證明了這裡有洞」。證明的方法只有一個：**動態驗證**——實際送觸發輸入,在偵錯器裡觀察程式真的做了什麼。這一章把 Ch 14-16 的靜態工作（IDA）和 Ch 4-5 學過的動態工具（WinDbg）接起來,形成一個可以反覆跑的「假設 → 驗證」迴圈——這個迴圈正是 Ch 18 案例研究要完整走一次的核心流程。

## 先建立直覺：兩軌工作流長什麼樣

```
┌─────────────────────────┐          ┌─────────────────────────┐
│   靜態軌（IDA）            │          │   動態軌（WinDbg）        │
│                           │          │                           │
│  1. 逆出 handler 位址      │          │                           │
│     (IDA 顯示的是 RVA,     │          │                           │
│      即相對 ImageBase)     │  位址換算  │                           │
│  2. 看出可疑的複製/檢查     │ ───────► │  3. bp <實際載入位址>       │
│     邏輯                   │          │  4. 送觸發輸入              │
│                           │          │  5. 命中斷點，看暫存器/stack │
│                           │  結果回饋  │     驗證「真的溢位了嗎？」   │
│  6. 根據動態結果，回頭修正   │ ◄─────── │                           │
│     靜態假設（offset、      │          │                           │
│     有效 payload 長度等）   │          │                           │
└─────────────────────────┘          └─────────────────────────┘
```

這不是走一次就結束的線性流程,是個**迴圈**：動態驗證常常會打破你的靜態假設（例如你以為溢位從第 100 byte 開始,實測發現是第 108 byte,因為你漏算了某個對齊 padding），這時回頭修正對 IDA 裡那段邏輯的理解,再驗證一次。

## 第一步：在 IDA 裡記下可疑函式的位址

打開 Ch 16 找到的可疑 handler,把游標停在你要下斷點的那一行（例如 `rep movsb` 那一行,或複製迴圈的起點）,IDA 左側或狀態列會顯示這個指令的位址,格式像 `.text:00401234`。

**關鍵認知**：IDA 預設顯示的位址,是這支 binary 的 **ImageBase**（PE header 裡宣告的「理想載入位址」,常見預設是 `0x00400000`）加上這個函式在檔案裡的**相對位移**（RVA, Relative Virtual Address）算出來的。如果這支 binary 在你的系統上實際載入到的位址,恰好就是它宣告的 ImageBase（沒有重定位、沒開 ASLR 的舊式 exe 常如此）,那麼 IDA 顯示的位址就是你在記憶體裡會看到的真實位址,直接拿去用沒問題。

但如果開了 **ASLR**（Address Space Layout Randomization,位址空間配置隨機化）,這個模組每次執行載入的基址都不同,IDA 顯示的位址只是「假設從 ImageBase 載入」時的位址,跟實際跑起來在記憶體裡的位址**不一樣**,直接拿 IDA 看到的位址去 WinDbg 下斷點會下到錯的地方（或者 WinDbg 直接告訴你那個位址沒有有效的程式碼)。

## 位址換算：RVA + 實際載入基址

正確的做法是分兩步:

**(a) 算出 RVA**：IDA 顯示的位址減掉 ImageBase,就是 RVA。

```
RVA = IDA 顯示的位址 - ImageBase
```

ImageBase 可以在 IDA 裡看 PE header（`File → Load file → ...` 的屬性,或直接查 IDA 的 segment 設定),也可以用 `dumpbin /headers` 之類的工具查原始 PE 檔。很多教學靶、未開 ASLR 的舊式 exe,ImageBase 就是 `0x00400000`,IDA 顯示的位址扣掉這個數字就是 RVA。

**(b) 在 WinDbg 裡查這個模組實際載入到哪裡**，用 `lm`（list modules）：

```
0:000> lm m vulnserver
```

未實測，理論預期輸出類似：

```
start    end        module name
00400000 0041a000   vulnserver   (no symbols)
```

這裡的 `start` 就是這個模組**這次執行**實際載入的基址（如果沒開 ASLR,通常就等於 ImageBase,跟 IDA 算的一樣；如果開了 ASLR 或這是個 DLL,這個值每次執行可能不同)。

**(c) 真正要下斷點的位址**：

```
實際位址 = WinDbg 查到的實際載入基址 + RVA
```

WinDbg 讓你直接用**模組名+RVA（用十六進位）**的語法下斷點,不用自己手算加法——這是最保險、最不容易算錯的方式：

```
0:000> bp vulnserver+0x1234
```

這裡 `0x1234` 就是上面算出的 RVA。WinDbg 會自動幫你把它加上這個模組實際載入的基址。只要你确定 RVA 算對了（IDA 位址減 ImageBase),這條命令在 ASLR 開或關的情況下都正確——這是**比自己手算絕對位址更建議的做法**,因為它天然對 ASLR 免疫。

## 完整流程走一遍

未實測，理論預期的步驟:

1. **IDA**：找到可疑的 `rep movsb` 位於 `.text:004012A0`。確認 ImageBase 是 `0x00400000`。RVA = `0x004012A0 - 0x00400000 = 0x12A0`。
2. **WinDbg**：Attach 到目標行程（Ch 4 教過的流程）。確認模組名：`lm` 列出模組清單,確認目標程式的模組名稱（通常就是 exe 檔名,不含副檔名)。
3. 下斷點：`bp vulnserver+0x12A0`。
4. `g` 讓程式繼續跑。
5. **攻擊機**送出 Ch 15 逆出的觸發指令格式（例如 `TRUN .` 加一段夠長的字串）。
6. WinDbg 應該**命中斷點**,程式停在 `vulnserver+0x12A0`。如果沒命中,代表這個函式這次沒被執行到——回頭檢查你送的指令是否真的符合觸發這個 handler 的條件（Ch 15 逆出的協定格式是否正確)。
7. 命中後,用 `r` 看暫存器、`dd esp`（或類似指令）看 stack 內容,核對：負責長度的暫存器（例如上一章示意的 `ecx`）此刻的值是多少？是否等於你送的資料長度，還是被某個檢查限制住了？緩衝區起始位址（`edi` 或類似）加上這個長度,算出來的結束位址有沒有超出緩衝區宣告的大小？
8. 讓它繼續跑（`g` 或單步 `p`/`t`),觀察複製完成後,緊鄰緩衝區的記憶體（例如 saved return address 所在位置）是否真的被覆寫成你送的資料——這一步直接證實「能控制多少、控制到哪」,不再是靜態猜測。

## 畫出雙軌工作流的完整樣貌

```
   [IDA 靜態分析]
        │ 1. 找到可疑 handler, RVA = addr - ImageBase
        ▼
   [算出 RVA]
        │ 2. RVA 帶進 WinDbg
        ▼
   [WinDbg: bp module+RVA]
        │ 3. g 繼續執行
        ▼
   [攻擊機送觸發輸入] ──────────────┐
        │ 4. 命中斷點?              │ 否：回頭檢查協定/路徑假設
        ▼ 是                       │
   [r / dd 檢視暫存器與記憶體]       │
        │ 5. 真的會溢位嗎?           │
        ▼ 是                   否──┘ (靜態推理有誤，回 IDA 重新檢視)
   [證實漏洞，記錄溢位 offset/可控範圍]
        │
        ▼
   回到 IDA，核對這個 offset 在原始邏輯裡對應什麼意義
   (例如：第幾個參數、哪個 recv 迴圈的第幾輪)
```

## 對比取捨：下斷點用「絕對位址」vs「模組+RVA」

| 方式 | 寫法 | 對 ASLR 的穩健性 | 適用場景 |
|---|---|---|---|
| 絕對位址 | `bp 004012A0` | 差——ASLR 開啟或模組重載入位址改變時,直接失效 | 確定沒開 ASLR、且這次 session 不會重啟目標的快速測試 |
| 模組+RVA | `bp vulnserver+0x12A0` | 好——WinDbg 自動用模組**當前**實際載入位址換算 | 預設做法,幾乎所有情境都該用這個 |

本課全程建議用模組+RVA 的寫法,養成習慣——即使現在練習的教學靶常常沒開 ASLR,養成這個習慣在考場遇到開了 ASLR 的目標時不會手忙腳亂。

## 踩雷集錦

1. **錯誤直覺：IDA 顯示的位址就是程式實際跑起來時的位址** → **正確**：只有在 ImageBase == 實際載入基址時才成立（常見於沒開 ASLR 的舊式 exe）。穩健做法永遠是算 RVA,再用 `module+RVA` 語法下斷點,不要直接複製 IDA 的絕對位址去 WinDbg。
2. **錯誤直覺：斷點沒命中就代表這段程式碼有問題（邏輯不對）** → **正確**：更常見的原因是你送的觸發輸入沒有真正走到這條路徑——協定格式理解錯、指令關鍵字拼錯、或前面某個條件判斷把你導向了別的分支。先懷疑輸入,再懷疑位址算錯,最後才懷疑函式本身邏輯理解錯。
3. **錯誤直覺：靜態推理出的 offset（例如「第 100 byte 開始溢位」）一定準確** → **正確**：編譯器可能插入 padding、對齊、額外的 saved 暫存器,實際的 offset 常常和靜態粗估有出入。動態驗證的目的正是要精確定出真實 offset,不是用來「確認一下」靜態猜測——它是權威來源。
4. **錯誤直覺：這支程式每次重新啟動,模組基址都一樣** → **正確**：開了 ASLR 的模組每次啟動基址都會變,即使是同一支 exe。這也是為什麼 `bp module+RVA` 比寫死絕對位址更重要——每次重啟目標後,直接重下同一條 `bp` 指令,WinDbg 會自動對應到新的基址,不用你重算。
5. **錯誤直覺：動態驗證一次通過就代表漏洞穩定可用** → **正確**：這一步只證實「存在性」。溢位的穩定性（換一台機器、換一次重啟是否行為一致）、能否真正拿來控制 EIP、壞字元有沒有干擾——這些還要後續章節（Ch 7-8 的方法論搬到這裡重跑一次）才能確認。動態驗證是「有洞」的證明,不是「exploit 可用」的證明。

## 進階：再往深一層

- **符號化模組名**：如果目標程式有 PDB 符號檔（開發者自己編譯、帶 debug info 的 build),WinDbg 能直接用函式名下斷點（`bp vulnserver!handle_TRUN`),比算 RVA 更方便。考場目標通常是 release build 沒有符號,RVA 換算這套功夫才真正用得上。
- **條件斷點**：WinDbg 支援在斷點上加條件（例如只在 `ecx` 大於某個值時才真正停下),對反覆觸發同一函式但只想在特定輸入長度時中斷很有用。Ch 4-5 的 WinDbg 進階指令可以配合這裡用。
- **Time Travel Debugging（TTD）**：如果你的 WinDbg 版本支援 TTD,可以錄下整段執行再回放,對「這個斷點命中前,資料是怎麼一步步被處理成這樣」的回溯分析非常有力,比反覆重跑觸發輸入更有效率。Ch 0 與 Ch 41 有更多提及。

## 本章重點整理

- 靜態推理（IDA）永遠需要動態驗證（WinDbg）確認——這是個反覆的「假設 → 驗證 → 修正」迴圈,不是單向的線性流程。
- IDA 顯示的位址是 ImageBase 相對；真正下斷點要換算 **RVA = IDA 位址 - ImageBase**,再用 `bp module+RVA` 語法,讓 WinDbg 自動對應到實際載入基址——這個寫法天然抵抗 ASLR。
- 斷點沒命中,先懷疑觸發輸入/協定理解有誤,再懷疑位址算錯,最後才懷疑邏輯理解錯。
- 動態驗證的產出是精確的 offset 與可控範圍,這些數字通常和靜態粗估有出入,動態結果才是權威。
