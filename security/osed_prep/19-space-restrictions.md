# Ch 19 — 空間限制：shellcode 放不下怎麼辦

> **目標**：搞懂「buffer 太小塞不下完整 shellcode」這個 OSED 常見卡關，掌握四種解法的取捨，並建立「為什麼 egghunter 常是最佳答案」的直覺，為 Ch 20 的 egghunter 實作鋪路。

> **環境**：Win10 x64 + WinDbg（2026）+ mona v3 + Python 3

## 為什麼需要這一章

Ch 10、Ch 12 你已經寫出完整的 exploit：控制 EIP、跳進 `jmp esp`，然後整支 reverse shell shellcode（常規手寫版本動輒 **350 bytes 以上**，若走 `WinExec` 類路徑也常破百）就塞在 buffer 裡等著被執行。那一版的前提是：**溢位之後你能控制的那段連續記憶體，大到足以塞下整支 shellcode**。

但 OSED 考試和真實世界的漏洞常常不給你這個奢侈條件。典型情況：

- **SEH overflow（Ch 11–13）**：nSEH 只有 4 bytes，真正能放東西的常常是 nSEH 之後、到下一個結構之前的一小段，可能只有幾十到一兩百 bytes——塞不下 350+ bytes 的 reverse shell。
- **短緩衝溢位**：某些函式的輸入上限被程式內部檢查卡住，你能溢位的欄位本身就很短（例如一個固定 64 bytes 的欄位），根本放不了完整 payload。
- **多重跳轉後剩餘空間不足**：你靠 short jump 繞過某個檢查或跳過垃圾資料之後，實際可寫、可控、且會被執行到的空間已經被切得很碎。

這一章要處理的問題只有一個：**可控空間 < shellcode 大小時，怎麼讓 shellcode 還能跑起來？**

## 先建立直覺

把問題畫成空間不夠用的畫面：

```
記憶體（可控、會被執行的那段）
┌────────────────────────┐
│  能放的空間：~60 bytes   │   ← 完整 reverse shell shellcode 要 350+ bytes
│  (nSEH 後到下個結構前)    │      放不下！
└────────────────────────┘
```

四種解法分別在解決「哪裡找到更多空間」這個子問題：

```
(a) 跳到別處的大緩衝        (b) 分段 / 多階             (c) egghunter                (d) 往回跳 (negative jump)

┌────┐  jmp   ┌────────┐   ┌────┐ stage1  ┌────┐        ┌────┐  jmp    ┌─────────┐  ┌────────┐ jmp back ┌────┐
│小空間│ ────► │另一欄位 │   │小空间│ ───►   │再收更多│       │小 egg-  │ ────►   │ 掃描整個  │  │大空間在前 │ ◄──────  │小空间│
│(控EIP)│      │殘留資料 │   │(控EIP)│      │stage2 │       │hunter  │  找到egg │ 行程記憶體│  │面(先送的  │          │(控EIP)│
└────┘      │大shellcode│  └────┘      │大shellcode│      │(~32B)  │          │找大shellcode│ │封包殘留)  │          └────┘
            └────────┘                └────┘             └────┘          └─────────┘  └────────┘
```

四條路線的共同邏輯：**小空間裝不下的東西，換個方式間接抵達大空間**。差別在於「大空間在哪」「怎麼找到它」「要不要先送額外資料」。

## 核心：四種解法逐一拆解

### (a) 跳到別的更大緩衝

如果某個更早送出的欄位、或協定裡的另一個參數，會被伺服器收下並留在記憶體裡（沒有被覆寫、沒有被釋放），而且它比目前控制 EIP 的這段空間大很多，你可以：

1. 把完整 reverse shell shellcode 塞進那個「大欄位」裡發送出去（它會被正常接收、存進某塊記憶體，位址通常可預測或可用 WinDbg 找出來）。
2. 讓控制 EIP 之後能執行的那一小段空間，裝一條 **直接跳轉**（`jmp` 到絕對位址，或相對跳轉）指令，跳去大欄位的位址。

**前提**：你必須先用 WinDbg 確認那塊大欄位的資料真的還在記憶體裡（沒被後續處理覆寫），而且位址穩定（跨重啟/跨連線一致，或至少可被 info leak / 固定模組基址推算）。這在 OSED 的 SEH 題型裡常見——某個先送的封包內容原封不動留在 heap 或 stack 深處。

### (b) 分段 / 多階 shellcode（staged payload）

邏輯類似 Linux pwn 的 stage1/stage2：小空間先放一段**極短**的 shellcode，它的唯一工作是「去接收更多資料，存到別處，再跳過去執行」。典型做法：

- stage1（幾十 bytes）：呼叫 `recv()` 再收一批資料，存到某個固定或可推算的記憶體位置（例如堆疊上更深處、或剛才已知的某塊可寫記憶體）。
- stage1 收完後 `jmp` 到剛存好的位置，執行 stage2（完整 reverse shell shellcode）。

**代價**：stage1 本身也要手寫、也要避壞字元，而且需要目標服務的協定允許你「再送一次資料」且該連線/狀態還活著——不是所有服務都配合。

### (c) egghunter（小搜尋器找大 shellcode）

這是 OSED 最常考、也是本課接下來兩章的重點：寫一段**極小**（約 32 bytes）的 stub，塞進那個小空間裡。它不做任何 exploit 邏輯，只做一件事——**在整個行程的虛擬位址空間裡逐頁掃描，找一個你事先選定的 8-byte 標記（"egg"）**，找到後跳到 egg 後面立刻執行那裡的完整 shellcode。

完整 shellcode 放哪？通常就塞進前面提到的「另一個欄位」或「先送的封包」留在記憶體裡的位置——**不需要知道它的確切位址**，只需要它前面貼著那個 8-byte egg 標記，egghunter 會自己找到它。

這跟 (a) 的差別是：(a) 需要你**精確算出**大緩衝的位址再寫絕對跳轉；egghunter 則是**不需要知道位址**，只要大 shellcode 存在於行程記憶體某處、前面有 egg 標記即可，大幅降低對位址穩定性的依賴。

### (d) 往回跳（negative jump）

如果控制 EIP 的那個點**之前**（在記憶體位址上更低、或是程式流程上先經過）的那段空間反而比較大——例如 buffer 的前半段還留著你一開始送的資料、尚未被用掉或覆寫——可以用一個**負偏移的相對跳轉**（`jmp` 到一個負的 offset，往回跳）跳回那裡執行。

這其實是 (a) 的特例：目標空間本來就在你自己送出的同一包資料裡，只是位置在「控制流到達點」的前面而不是後面。常見手法是在短跳/長跳（short jump + long jump）結構裡，先 short jump 跳過某個會壞事的位元組，再從那裡往回跳一大段到前面藏好的 shellcode。

## 多範例：同一個洞，四種解法各自怎麼接

假設一個虛構的 vulnserver 風格指令 `VULN`，溢位後你量出的狀況是：

- 控制 EIP 之後能用的連續空間只有 **48 bytes**（夾在 SEH 記錄和下一塊資料之間）。
- 同一個連線裡，更早送出的 `GMON` 參數內容會被存進一塊固定位址的全域緩衝區，**大小 1024 bytes，內容不會被後續處理覆寫**（你用 WinDbg 下 breakpoint 在 crash 前後各看一次那塊記憶體內容，兩次一致，證實了這點）。
- 這塊全域緩衝區的位址在這次連線裡是 `0x006F5000`（可用 `!address` 或直接 `d 0x006F5000` 驗證），而且因為該模組沒有啟用 ASLR（Ch 13 SafeSEH/ASLR 模組選擇的延伸），這個位址每次重啟都一樣。

四種解法在這個具體場景下分別長這樣：

**(a) 跳到別處大緩衝**：48 bytes 裡放一條 `jmp 0x006F5000`（或等價的相對跳轉），`GMON` 參數裡放完整 reverse shell shellcode。優點是最簡單、一條指令；**前提是位址 `0x006F5000` 真的固定**——上面特別強調「沒有 ASLR」就是因為一旦該模組重新導入基址會變，整條 exploit 直接失效。

**(b) 分段**：48 bytes 放一段迷你 stub：呼叫 `recv()` 把攻擊機再送來的第二批資料存到棧上某個已知位置，再跳過去執行。這個做法**不依賴 `GMON` 殘留資料**，但要求協定允許你在同一個 crash 觸發前，先讓服務再吃一次 `recv()`——如果觸發點是在收完整個請求後才處理（像很多單次請求單次回應的服務），根本沒有「再收一次」的機會，這條路直接判死。

**(c) egghunter**：48 bytes 放一段約 32 bytes 的 egghunter stub（還有餘裕塞 NOP 墊一下）。`GMON` 參數裡放 `egg + egg + 完整 shellcode`（例如 `w00tw00t` 重複一次再接 shellcode）。這個做法**完全不需要知道 `0x006F5000` 這個位址**——即使它會漂移、即使你根本沒去驗證過，只要 shellcode 真的進了行程記憶體，egghunter 掃描到就會執行。這正是為什麼它比 (a) 穩健：少了一個「位址要準」的失敗點。

**(d) 往回跳**：如果 48 bytes 這段「之前」（記憶體位址更低處）還留有一段你自己送的、尚未被覆寫的資料，且空間夠大，可以在這 48 bytes 裡放一條負偏移的 `jmp`，跳回去執行藏在那裡的 shellcode。這個場景下如果溢位點前方本身空間就很擠（常見於 nSEH 前面只是填充資料，沒地方藏），這條路也不可行。

這個例子想說明的是：**四種解法不是同時都可行**，實際能不能用，取決於你對目標程式記憶體佈局的觀察結果——這也是為什麼 Ch 16–18 的逆向功夫扎實,直接決定你在 Part 5 能不能選對解法。

### 邊界情況：找不到任何殘留大緩衝怎麼辦

如果 WinDbg 驗證後發現：沒有任何欄位留下可用的大緩衝、服務也不給你二次 `recv()` 的機會、溢位點前後都擠得一滴空間都沒有——egghunter 仍然有解，因為它不要求「大 shellcode」放在某個特定欄位裡。只要**任何**能送進這個服務、會被接收並留在行程記憶體裡的資料（哪怕是協定裡一個看起來無關的欄位、甚至是 TCP 層面上還沒被處理掉的 socket buffer 殘留），前面貼上 egg 標記，egghunter 掃過去就能找到。這也是為什麼它常是「其他三條路都被堵死」時的最後手段，也是 OSED 教材花最大力氣講它的原因。

## 底層機制：為什麼"小空間"會發生

```
溢位時記憶體的實際佈局（以 SEH 為例）：

  [... 填充 ...][nSEH: 4B][SEH: 4B][...往後，可能馬上碰到下一個 SEH 記錄 / 不可控資料...]
                  ↑                  ↑
              你能寫但極小        控制 EIP 落點之後
                                 真正"安全"可執行的空間
                                 可能只有幾十 bytes
```

空間限制的根因通常是：

1. **結構本身就小**：nSEH 固定 4 bytes，是結構設計決定的，不是你能改的。
2. **後面緊接著別的合法資料**：溢位點之後很快就碰到程式自己要用的下一塊結構（下一個 SEH 記錄、下一個 heap chunk header），寫過去會讓程式在你的 shellcode 執行**之前**就先壞掉或行為異常。
3. **前置檢查卡住輸入長度**：某些函式會在複製前做長度檢查，只是檢查邏輯本身有缺陷（允許你剛好溢位一點點），能溢位的量被這個缺陷的大小精確框住。

## 對比取捨

| 解法 | 需要的額外條件 | 位址穩定性要求 | 複雜度 | OSED 出現頻率 |
|---|---|---|---|---|
| (a) 跳到別處大緩衝 | 另一欄位/封包內容真的留在記憶體裡 | 高（要算準或可推算位址） | 低（一條 jmp） | 中 |
| (b) 分段/多階 | 服務允許你再收一次資料、連線存活 | 中（stage2 存放位置要可控） | 中（要再寫 stage1） | 低 |
| (c) egghunter | 完整 shellcode 能以任何方式進入行程記憶體 | **低**（不需知道確切位址） | 中高（egghunter 本身要正確處理不可讀頁面） | **高，OSED 主力** |
| (d) 往回跳 | 溢位點前方確實有未用到的可控空間 | 中（offset 要算對） | 低（一條負向 jmp） | 中（常與短跳結合） |

egghunter 之所以是 OSED 最常考的答案，原因是它把「空間限制」和「位址不確定」**一次解決**：你不需要精確算出大 shellcode 落在哪裡，只要它存在、前面貼著 egg 標記，egghunter 掃描到就會跳過去。這在 ASLR 存在、或你根本無法預測某塊記憶體位址時，是四個解法裡最穩健的一個——也因此是 OSED 課程花最大篇幅教的技巧。

## 踩雷

1. **誤判「空間不夠」**：先用 mona 的 pattern（Ch 8 的技巧）精確量出可控空間的實際大小，別憑感覺猜。有時看起來小，其實把前後幾個欄位串起來還夠用（例如方案 (d)）。
2. **用了 (a) 但位址其實不穩定**：「另一個欄位的內容留在記憶體裡」不保證它的**位址**每次都一樣——heap 分配、ASLR、甚至同一服務不同次連線都可能讓它漂移。沒驗證就硬編位址的 jmp，常常是 exploit 「本機測試成功、換一輪就當」的元兇。
3. **忽略了"小空間"裡還塞了別的必要指令**：方案 (c)/(d) 常常要先塞一個 short jump 去跳過某些不能覆寫的 bytes（像 SEH 的下一個指標），egghunter/跳轉指令本身還要在這個已經很擠的空間裡再擠一次——別忘了算進去。
4. **分段方案忘了處理 bad chars**：stage1 本身一樣要過壞字元分析（Ch 8），很多人只顧著 stage2 的完整 shellcode 過濾壞字元，忘了 stage1 也是手寫機械碼，一樣會踩雷。
5. **選 egghunter 卻沒先確認大 shellcode 真的會進入記憶體**：egghunter 掃描的前提是「完整 shellcode 以某種方式先被送進行程記憶體」——沒有送過去，egghunter 永遠掃不到東西，會一直循環或最後踩到不可讀頁面而掛掉。
6. **把方案 (a)/(d) 的「位址沒 ASLR 所以固定」誤推到有 ASLR 的模組上**：同一個行程裡不同模組的 ASLR 狀態可能不一樣（某些舊 DLL 沒重新編譯過，沒有 `/DYNAMICBASE`，Ch 31 會細講），誤把「這次剛好沒變」當成「這個位址永遠固定」，是考場上常見的運氣型通過、下一輪就翻車。

## 進階：再往深一層

實務上這四種解法不是互斥選項，考試現場常常是組合拳：短跳避開不可寫的 SEH 指標 → 長跳 → 落到一個放了小小 egghunter stub 的位置 → egghunter 掃到位於另一個先送封包裡的大 shellcode。理解每一段各自在解決哪個子問題，比死記「SEH 就用方案 X」更重要。

另一個值得先建立的直覺：egghunter 的「穩健」是用**速度**換來的。掃描整個虛擬位址空間（32-bit 行程理論上限是 4GB，實際可用空間常小得多，但仍可能是數百 MB 到數 GB 的掃描範圍）不是瞬間完成的事，逐頁探測有明確的額外執行時間；相較之下方案 (a) 的一條 `jmp` 幾乎零延遲。如果你已經能百分之百確認位址穩定，方案 (a) 其實是更「乾淨」的解——egghunter 的優先度建立在「位址不確定或不可信」這個前提上，不是無條件的萬能解。下一章開始拆 egghunter 本身怎麼做到「安全地掃描」。

## 本章重點整理

- 空間限制問題的本質：可控且會被執行的連續記憶體 < 完整 shellcode 大小。
- 四種解法：(a) 跳到別處更大緩衝、(b) 分段/多階、(c) egghunter、(d) 往回跳，核心邏輯都是「間接抵達別處的大空間」。
- egghunter 最大優勢：不需要預先知道大 shellcode 的確切位址，只需要它存在、前面貼著 egg 標記。
- 空間限制常見於 SEH overflow（nSEH 僅 4 bytes）與被長度檢查卡住的短緩衝。
