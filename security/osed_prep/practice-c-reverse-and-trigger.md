# 練習 C — 逆向自訂網路服務找出並觸發漏洞

> **目標**：不給你 offset、不給你漏洞位置,獨立對一支陌生的 32-bit Windows TCP 服務跑完 Ch 14-18 的完整逆向生產線——recon、逆協定、在反組譯裡找出 unsafe handler、靜態推測、WinDbg 動態驗證控制 `EIP`。這是 OSED 真正的核心能力:自己找洞,不是改 PoC。

> **環境**：Win10 x64 + IDA Free 9.x/IDA Pro + WinDbg（2026）。假設你已完成 Ch 14-18。

## 背景與動機

Part 2-3 的練習(A、B)都是對 vulnserver 下手——這是個**已知**靶,網路上一查就有別人逆好的答案,公開資料已經告訴你哪個指令有洞、offset 多少。這個練習故意反過來:**不告訴你答案在哪**。你可以選擇用 vulnserver 裡一個你完全沒碰過的指令(偽裝成「未知」,自己逼自己不查答案),或者如果你手邊有其他公開的逆向練習靶(例如簡單的自訂 CTF pwn 靶、OSED 社群分享的練習二進位),直接拿那個練更貼近考場的「真的沒人告訴過你答案」情境。

這個練習的重點不是「找到一個 offset 數字」,是驗證你是否真的把 Ch 14-18 的循環內化成肌肉記憶——拿到一支完全陌生的 binary,你知道第一步看哪裡、第二步看哪裡、卡住的時候怎麼退一步重新假設。

## 任務規格

1. **選定目標**:
   - 選項一(建議新手)：vulnserver 裡一個你在 Part 2-3 都沒碰過的指令(`HELP` 列出的指令裡,排除你已經打穿的那幾個),當它是「陌生 binary」,自己不查任何公開 writeup,完全照本練習的步驟走。
   - 選項二(進階,更貼近考場)：找一支公開的、沒有附帶詳細漏洞說明的 32-bit Windows 練習二進位(例如社群分享的 OSED 練習靶、简单的自寫 TCP echo/命令服務)——嚴禁下載來路不明的二進位執行,只在你自己隔離 VM 裡跑,且只挑你能確認合法用於學習目的的練習素材。
2. **靜態 recon**:用 IDA 載入目標,走 Ch 14-15 的流程——Imports 找 Winsock API、Strings 找可疑指令關鍵字、順著 `recv` 往下追,逆出協定格式(指令關鍵字、分隔符、參數結構)。寫下你的協定推論。
3. **找出漏洞 handler**:逐一檢視每個指令對應的 handler,用 Ch 16 教的樣式辨識(unsafe 函式、inline 複製迴圈、長度檢查缺陷),找出至少一個候選漏洞點。記下可疑指令位置,並說明你判斷它可疑的具體依據(是什麼樣式讓你起疑)。
4. **靜態推測**:粗估可能的溢位 offset 範圍(不要求精確,只要有合理依據的估計)。
5. **動態驗證**:用 Ch 17 教的 RVA 換算方式在 WinDbg 下斷點,送觸發輸入,證實這個 handler 真的會被執行到、真的會溢位,並精確定出讓 `EIP` 被你完全控制的 offset(用 cyclic pattern,Ch 8 教過的方法)。
6. 全程記錄每一次「假設 → 驗證 → 修正」的循環——卡住過幾次、怎麼調整假設,這份記錄比最終的 offset 數字更重要。

## 期望輸出

- 一份你自己寫的**協定規格**文件(指令清單、格式、哪個 handler 對應哪個指令)。
- 明確指出哪個 handler 有漏洞、漏洞類型(unsafe copy / 長度檢查缺陷,依 Ch 16 分類)、你的判斷依據(反組譯的哪一段讓你起疑)。
- WinDbg 裡實際命中斷點、`EIP` 被覆寫的證明(螢幕截圖、暫存器輸出紀錄,或至少清楚寫下你預期會看到什麼、怎麼驗證——若環境限制下只能寫「理論預期」,要說明你會怎麼在自己環境操作驗證)。
- 精確 offset 值,以及你怎麼從粗估值走到精確值的過程紀錄。

## 如果卡住:提示

1. **完全不知道從哪裡開始**：回到 Ch 14-15,先別想漏洞,純粹把協定逆出來——Imports 看 `recv`,Strings 看指令字串,xref 兜起來,先把「這支程式怎麼跟外界說話」搞懂,漏洞分析是下一步,不要跳著做。
2. **每個 handler 看起來都正常,找不到明顯的 unsafe copy**：回頭檢查是不是漏看了 inline 的手寫複製迴圈(`rep movsb` 或逐字元迴圈),這些不會以「呼叫危險函式」的形式出現,只搜尋 `strcpy`/`memcpy` 這類函式名會漏掉它們。也檢查「有檢查但檢查錯」的三種缺陷(方向寫反、有號無號混用、off-by-one)——別只看「有沒有 cmp」,要看 cmp 後面接的跳轉對不對。
3. **送觸發輸入,斷點完全沒命中**：先懷疑協定格式理解錯(是不是漏了分隔符、關鍵字大小寫錯、結束符 `\r\n` 沒加),再懷疑 RVA 算錯(重新核對 ImageBase 和 IDA 顯示位址的減法),最後才懷疑這段邏輯真的沒被執行到(換一個 handler)。
4. **命中斷點但 `EIP` 沒有被覆寫成預期的值**：你送的測試資料長度可能不夠長,沒真正碰到 saved return address;或者這個 handler 的溢位路徑比想像複雜(中間有別的欄位、別的檢查先擋下來)。先送一個明顯超量的測試值排除「不夠長」這個可能性,再用 cyclic pattern 精確定位。
5. **找到的 offset 在不同次測試之間不穩定**：可能這支服務是多執行緒(每個連線獨立 thread),不同連線的 stack 佈局有微小差異;也可能緩衝區前後有未初始化的雜訊資料影響了你的觀察。多測幾次、記錄每次的差異,確認到底是真的不穩定還是你的量測方式有誤。

## 實作步驟

1. **選定目標、架好環境**:vulnserver(或你選的練習靶)在偵錯/靶機上跑起來,WinDbg 準備好附掛,IDA 開好 binary 跑完自動分析。
2. **靜態 recon**:Imports/Strings/`recv` 的 xref,逆出協定規格,寫成文件。
3. **逐一檢視 handler**:每個指令對應的處理函式都讀一遍,標記看起來正常的和看起來可疑的,用 `N`/`;` 留下你的推理痕跡。
4. **鎖定候選漏洞,靜態推 offset**:針對最可疑的 handler,算出大致的緩衝區大小和可能的溢位範圍。
5. **WinDbg 動態驗證**:算 RVA,`bp module+RVA`,送明顯超量的觸發輸入,確認斷點命中、確認 `EIP` 被覆寫。
6. **精確定位**:用 cyclic pattern 找出精確 offset,`BBBB` 二次驗證。
7. **(延伸)找第二個漏洞**:回頭檢視其餘 handler,看能不能用同一套方法找出第二個問題。

## 參考解答

<details>
<summary>完整參考解答（先自己動手，卡住 15 分鐘以上才展開）</summary>

以下以 vulnserver 的 `KSTET` 指令為範例路徑示範**完整的逆向思路**(**未實測,理論預期**——`KSTET` 是否真有漏洞、具體 offset 與行為,請自己在環境裡依下列思路實測確認,不要把下面的數值當成現成答案抄用。若你選的目標不是 `KSTET`,思路一樣適用,只是把每一步換成你自己目標的實際發現):

**(1) 靜態 recon**：IDA 載入 `vulnserver.exe`。Imports 裡看到 `ws2_32.dll` 的 `recv`、`send`、`accept`。對 `recv` 按 `X`,找到主連線處理函式(命名為 `handle_connection`)。Strings window 掃過,看到 `"KSTET"`、`"TRUN "`、`"GMON "` 等字串,對 `"KSTET"` 按 `X`,跳到 dispatch 邏輯裡對應的比較分支,循線找到它呼叫的 handler(命名為 `handle_KSTET`)。

**(2) 檢視 handler**：

```
; 教學示意，非真實逆向輸出，具體位址/大小請以你自己環境逆向結果為準
handle_KSTET:
sub  esp, 0x3F0            ; 配置約 1008 bytes 的 stack 緩衝區
mov  esi, [ebp+arg_ptr]     ; 指向 "KSTET " 後面的參數
lea  edi, [esp+0x8]
call strcpy                 ; 直接呼叫 strcpy，無任何長度檢查
```

看到 `call strcpy` 且前後找不到任何限制 `esi` 指向字串長度的 `cmp`/跳轉——符合 Ch 16 教的「完全沒有長度檢查」樣式,辨識難度低,是優先候選。

**(3) 靜態推 offset**：緩衝區 `0x3F0` (1008) bytes,加上這個函式 frame 裡其他區域變數佔用的空間,粗估「大概 1010-1030 bytes 左右會碰到 saved return address」——這只是起點,不當最終答案。

**(4) 動態驗證**：IDA 記下 `handle_KSTET` 入口,算出 RVA(假設是 `0x2310`,未實測)。WinDbg attach 到跑著的 vulnserver,`lm m vulnserver` 確認基址。`bp vulnserver+0x2310`,`g`。攻擊機送:

```python
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("192.168.x.x", 9999))
s.recv(1024)
s.send(b"KSTET " + b"A" * 1500 + b"\r\n")   # 明顯超量，排除「剛好不夠長」
s.close()
```

斷點命中後放行,觀察是否 access violation、`EIP` 是否變成 `0x41414141`。若命中且 `EIP` 被覆寫,證實漏洞存在。

**(5) 精確定位**：用 mona(或等價的 cyclic pattern 工具)產生 1500 bytes 的 pattern,送出去,`EIP` 崩潰時記下那 4 bytes 的值,`!mona pattern_offset <值>` 查出精確 offset,再送 `offset 個 A + BBBB` 驗證 `EIP` 精確等於 `0x42424242`。

> 參考解答示範的是**思路骨架**：recon → 找 handler → 辨識樣式 → 粗估 → 動態驗證 → 精確定位。具體位址、offset、甚至這個指令是否真有這個漏洞,都必須你自己在環境裡重新確認——這正是這個練習要你做的事。

## 測試用例表

| 測試情境 | 預期行為 | 如何驗證 |
|---|---|---|
| 對目標服務送正常格式的已知指令 | 正常回應,服務不崩潰 | nc 手動連線測試,確認基準行為正常 |
| 對選定的候選漏洞指令送小量參數 | 正常回應或正常的錯誤訊息,不崩潰 | nc 手動測試,排除「隨便送就崩潰」的誤判 |
| 送明顯超量(遠大於粗估緩衝區大小)的參數 | 服務崩潰,WinDbg 中斷顯示 access violation | WinDbg attach + 中斷觀察 |
| 送 cyclic pattern 後查 offset | `EIP` 處的 4 bytes 能在 pattern 的合法範圍內查到唯一 offset | mona `pattern_offset` 或等價工具 |
| 用查到的精確 offset 送 `BBBB` | `EIP` 精確等於 `0x42424242` | WinDbg 暫存器視窗 |
| 在非漏洞 handler 用同樣方式測試 | 不崩潰或崩潰原因不同(用來對照,確認你找到的才是真正的漏洞點) | 對照組測試,排除誤判 |

## 延伸挑戰

1. **找出同一程式的第二個漏洞**：vulnserver(或你選的目標)通常不只一個指令有問題。重複本練習的流程,對另一個還沒測過的指令跑一次,記錄它的漏洞類型是否和第一個相同(同樣是無檢查的 `strcpy`,還是長度檢查缺陷的變形)。
2. **比較兩個漏洞的可控範圍**：哪一個溢位的字元數更多?哪一個對壞字元更敏感?如果要在考場時間有限的情況下只能選一個深挖,你會選哪個,為什麼。
3. **對找到的漏洞,追問「這個長度檢查缺陷是故意設計的教學案例,還是真實世界常見的錯誤模式」**——回頭對照 Ch 16 的三種檢查缺陷分類,你找到的屬於哪一種,並思考在真實程式碼審查裡,這種模式有多容易被看漏。
