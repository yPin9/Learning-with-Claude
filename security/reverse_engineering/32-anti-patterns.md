# Ch 32 — 常見誤區與反模式

> **目標**：把全課的教訓反過來濃縮成一份「反模式清單」。逆向者卡住、逆錯、白費三倍時間，幾乎都是踩了下面這十條的某幾條。每條的結構固定：**反模式（你正在做的錯事）→ 為什麼錯（它讓你付出什麼代價）→ 正確做法（連回對應章）**。這章不教新技巧，教你認出自己什麼時候在做蠢事——這往往比多學一個工具更能提速。

## 為什麼需要專門講反模式？

技巧是「該做什麼」，反模式是「別做什麼」。兩者不對稱：學會一個新技巧讓你**多一種選項**，改掉一個反模式讓你**少走一整段冤枉路**。逆向特別吃反模式，因為它有兩個放大器：

1. **沒有標準答案兜著**：讀 source 讀錯了，編譯器/測試會糾正你；逆向逆錯了，binary 不會抗議。**自信地逆錯**是這行最貴的失敗，而它幾乎都源於某個反模式（不做 ground-truth、只信反編譯器、不動態驗證）。
2. **搜尋空間巨大**：一個中型 binary 幾萬條指令，走錯方向的成本是幾小時。反模式讓你把時間花在錯的地方（鑽 libc、逆整個 binary、瞪靜態）。

所以這章是「省時間」的一章。下面每一條，我都見過（也犯過）它讓一次本該一小時的攻堅拖成一整天。這是 [`reading_code` Ch 37 反模式](../../soft_skills/reading_code/README.md) 的 binary 鏡像——那邊講讀 source 的壞習慣，這邊講逆 binary 的壞習慣，很多是同一個病在不同介質上的變體。

## 反模式 1：一上來就鑽 asm 細節，不先建地圖

**你在做**：拿到 binary，`objdump -d` 整個 dump 出來，從 entry point 第一條指令開始逐行讀，想「讀著讀著就懂了」。

**為什麼錯**：一個 strip binary 有幾千到幾萬條指令，其中八成是 libc 啟動樁、PLT stub、編譯器生成的 boilerplate、和你目標無關的函式。從第一條逐行讀，你會在 `_start`、`__libc_csu_init`、`frame_dummy` 這些**你根本不需要懂**的東西上耗掉半小時，還沒碰到真正的邏輯。這等於拿到一本一千頁的書從版權頁開始一個字一個字讀。逐行讀 asm 也讓你只見樹不見林——看得懂每條指令，卻拼不出「這個函式在做什麼」。

**正確做法**：**先偵察建地圖，再鑽細節**。順序是 `file`/`readelf`（骨架）→ `strings`（線索）→ import 表（它會用哪些能力）→ 定位 main / 目標函式 → **只逆你需要的那一小塊**。Ch 31 的攻堅裡，import 表一秒就告訴我「沒 crypto、自訂編碼」，`strings` 的 `%02x` 告訴我輸出結構——這些讓我直接跳到那一條迴圈，跳過所有 boilerplate。逆向是**定向攻擊不是通讀**（Ch 3 偵察、Ch 5 認控制流建骨架）。

## 反模式 2：無條件相信反編譯器的輸出

**你在做**：Ghidra / IDA 按 F5，pseudocode 出來讀著很像 C，就當它是真相——它說這是 `int`，你就當 `int`；它掰出一個 `local_38` 變數，你就當真有這變數。

**為什麼錯**：**反編譯器是在猜**。它會猜錯型別（把 `char*` 猜成 `long`、把一個 struct 拆成散落的 offset）、掰出不存在的變數、把 `rol` 還原成看不懂的 `(x<<3)|(x>>5)` 甚至還原錯、把編譯器的優化「反優化」成似是而非的邏輯。反編譯器版本不同輸出還不一樣。你信了它的謊，整條逆向就建在流沙上——而且錯得很有說服力，因為它長得像正確的 C。

舉個具體的：Ch 31 那條 `rol $0x3,%bl`（左旋 3 bits），反編譯器很可能還原成 `(x << 3) | (x >> 5)`——**數學上對，但它把「rotate」這個高階意圖拆成了兩個 shift 加一個 or**，你讀到會以為原 code 真的寫了兩個 shift。更糟的版本會把 `%bl` 的寬度搞錯，還原成對 32-bit 值做 `>> 5`（少了 `& 0xFF` 的截斷），你照抄就對拍不上。反編譯器也常把 `-O2` 的 strength reduction「反優化」成似是而非的東西：把 `+= 7` 的累加器猜成一個迴圈變數 `* 7`，型別猜錯把 `unsigned char` 當 `int`——每一個都長得很有道理，錯得很有說服力。

**正確做法**：**反編譯器是輔助不是真相，卡住或存疑時回去讀 asm**（Ch 8 專講它怎麼騙你）。Ch 31 裡我用 r2 的 `pdc`，但把它當**第三個獨立證人**——手讀 asm、gdb 觀測、反編譯器三方一致我才下結論。任何反編譯器給的關鍵斷言（型別、常數、運算），都用 asm 或動態執行對一次。特別是**位元操作（rotate/shift/mask）、整數寬度、優化過的算術**這三類最容易被反編譯器說謊，看到就回 asm。反編譯器幫你快速看骨架，細節去 asm 求證。

## 反模式 3：忽略優化等級，拿 -O0 直覺套 -O2 binary

**你在做**：教材/教學看的都是 `-O0` 的乾淨對照，於是逆真實 binary 時預期「一個 source 變數對一個 stack slot、一個運算對一條指令」。看到 `-O2` 的 binary「怎麼完全對不上」就慌了。

**為什麼錯**：真實 release binary 幾乎都 `-O2`/`-O3`。優化會：inline 函式（`secret` 整個消失，Ch 0）、常數摺疊（整段迴圈算成一個常數）、strength reduction（`i*7` 變 `+=7`、`x*10` 變 `lea`、`/2` 變 `sar`）、把變數全塞暫存器（不落 stack）、向量化（一條 SIMD 抵八個 byte）。你拿「一對一」的 `-O0` 心智模型去讀，會覺得 binary 面目全非、到處對不上，甚至誤判邏輯。

具體看一次。Ch 31 那個 `enc` 的 source 有 `k = i*7 + 0x5A`。同一行在兩個等級下差多遠——`-O0`（真跑 objdump，照抄）：

```asm
    1261:  mov    -0x18(%rbp),%rax      ; 從 stack 讀 i
    1265:  mov    %eax,%edx
    1269:  shl    $0x3,%eax             ; ┐ i*7 = 8i - i：
    126c:  sub    %edx,%eax             ; ┘   shl 3 得 8i、sub 減回一個 i
    126e:  add    $0x5a,%eax            ; + 0x5a
    1271:  mov    %al,-0x19(%rbp)       ; k 存回 stack
```

`-O0` 連 `i` 和 `k` 都往 `-0x??(%rbp)` 的 stack slot 存讀（每個變數一個 slot，一對一），`i*7` 用 `shl 3; sub`（8i-i）算。`-O2` 呢？整個變成迴圈裡一條 `add $0x7,%r12d`——**`i*7` 連算都不算了**，編譯器把「每輪的 k 比上一輪多 7」這件事變成一個累加暫存器（strength reduction），變數 `i`/`k` 根本沒有獨立存在。同一行 source，`-O0` 是 6 條含 stack 存取的指令、`-O2` 是迴圈裡增量的一條——**你拿 `-O0` 的「一個變數一個 slot」心智模型去讀 `-O2`，會找不到 `i` 也找不到 `k`，以為自己看漏了什麼。**

**正確做法**：**先確認你在看哪個優化等級，並知道每個等級的變形指紋**。Ch 31 的 target 是 `-O2`，我一看到 `keystream += 7` 就知道原 source 多半是 `i*step`（strength reduction 的指紋），沒被它嚇到。判斷等級的快招：`-O0` 大量 `mov` 進出 `-0x??(%rbp)`、幾乎每個 C 變數對一個 stack slot、算術逐條展開；`-O2`+ 值多在暫存器、迴圈被展開/向量化、函式被 inline。用 godbolt 對照同一段 source 在 `-O0`/`-O2`/`-O3` 的差異，把「優化會做哪些變形」內化成字典（Ch 2 講編譯器做了什麼、Ch 10 idiom）。看到反直覺的形狀，第一反應是「編譯器優化成這樣」而不是「我看錯了」。

## 反模式 4：不做 ground-truth 就硬逆無答案的目標

**你在做**：初學就直接找一個沒有 source 的真實 binary（別人的 crackme、真 malware）硬啃，逆出一套邏輯，覺得「應該是這樣」就收工。

**為什麼錯**：你**沒有辦法知道自己逆對了**。逆向最危險的不是讀不懂，是自信地讀錯——你腦補一條邏輯，看起來合理，其實不是原意，而 binary 不會糾正你。沒有 ground-truth，你連「我這個假設是對是錯」都無法驗證，練了半天可能一直在強化錯誤直覺。

**正確做法**：**練功階段一律用有標準答案的 target**——寫一小段 C、`gcc` 編、`strip`、逆回去、對照原始碼（Ch 0 的 ground-truth 迴圈，本課靈魂）。逆錯了當場抓到：「我以為這是乘法，其實是編譯器把除法優化成乘法了。」Ch 31 全程就是這個迴圈——我逆完寫等價實作，用 500 組隨機輸入對拍，通過了才敢說逆對。**先在有答案的 binary 上把直覺練準，再上無答案的真實目標**（那時你已經有對拍/動態驗證的習慣兜底）。

## 反模式 5：純靜態瞪到死，就是不肯跑它

**你在做**：一個函式邏輯繞、`rol` 方向拿不準、某個暫存器跨迭代累積搞不清累積什麼——你選擇繼續盯著 asm 硬推，推十五分鐘還在原地。

**為什麼錯**：有些東西靜態**本來就難確定**：間接跳轉的目標、某分支實際會不會走到、跨迭代的 feedback 到底 feed 什麼值、某個 magic number 是輸入還是常數。你瞪十分鐘的東西，`gdb` 下個斷點 `print` 一下五秒就知道。純靜態閱讀在這種點上是負投資——你在用最慢的方法求一個最快能觀測到的事實。

哪些東西靜態**先天**吃力、動態一秒破解，值得記一張「該切動態」清單：

- **間接跳轉/呼叫的目標**（`jmp *%rax`、`call *%rdx`）：靜態不知道 `%rax` 是什麼，動態一斷點就看到實際跳去哪（Ch 31 的 VM 示範裡 jump table 就是這種）。
- **跨迭代累積的暫存器 feed 什麼值**：Ch 31 的 `prev` 到底是「上一個輸入」還是「上一個輸出」，靜態容易看反，gdb 第二輪印一次就對。
- **某分支實際會不會走到**：靜態看得到分支存在，看不到真實輸入下走哪條——餵個輸入下斷點就知道。
- **某 magic number 是輸入還是常數**：靜態看是個立即數，但它可能來自環境/檔案；動態看它執行時的實際值。

**正確做法**：**觀察勝於推理，靜態卡住就跑它**（Ch 12 動態心法、Ch 13 gdb 工作流）。Ch 31 裡我對 `rol` 方向、`prev` 餵哪個值這兩個疑點，沒有硬推——直接 gdb 下斷點看真實中間值，`prev=0x81` 一出來假設立刻釘死。設一個時間盒：**同一段靜態推超過 10 分鐘沒進展，就是該上動態的信號**。動態不是靜態的替代，是靜態卡住時的破局器——靜態產生假設、動態釘死假設（Ch 17）。

## 反模式 6：不外化，全靠腦子記

**你在做**：逆的過程中，哪個暫存器是什麼、哪個位址是哪個函式、當前假設是什麼——全記在腦子裡，不寫下來。連反編譯器裡的變數也懶得重命名。

**為什麼錯**：逆向的工作記憶負擔極重——你同時要追蹤十幾個「`%r12d` 是 keystream、`%rbp` 是輸入指標、`0x10c0` 是 main、當前假設是加→XOR→旋轉」。人腦扛不住這個量，於是你不斷「這個暫存器剛剛是幹嘛的來著」回頭重讀，效率崩盤。更糟的是假設不寫下來就會漂移——你以為你在驗假設 A，追著追著偷換成假設 B 都沒發覺。

**正確做法**：**全程外化**——把逆出的東西寫進筆記、把暫存器/函式在反編譯器裡重命名、把假設列成清單、複雜控制流畫 ASCII 圖（Ch 25 逆向筆記與外化）。Ch 31 裡我一路把 `%r12d` 命名 `keystream`、`0xab` 命名 `IV`、把假設寫成一張卡再逐條驗。外化不是額外功夫，是**把工作記憶卸載到紙上**讓腦子專心推理。strip 拿走了所有名字，外化就是你把名字一個個補回去的過程——這本身就是「重建意圖」。

## 反模式 7：想逆懂整個 binary，不收斂到目標

**你在做**：任務只是「搞懂授權檢查邏輯」，你卻從 main 開始想把每個函式都逆懂，覺得「先全懂了再看目標比較踏實」。

**為什麼錯**：一個中型 binary 有幾百個函式，全逆懂要幾週，而你的任務可能只碰其中三個。想「全懂」是完美主義偽裝成嚴謹，實際是**逃避收斂的決策**——因為決定「只追這條、其他當黑盒」需要判斷力，而無腦全逆感覺比較安全。結果你在無關函式上耗掉所有精力，真正的目標反而沒時間深挖。

**正確做法**：**界定任務、收斂到目標、其餘當黑盒**。動手前先寫任務三欄，尤其是「不需要懂」那欄（Ch 31 階段 0）——我明確宣告「libc 內部、ELF 載入、PLT/GOT 不追」，就把攻擊面從整個 binary 縮到一條迴圈。追蹤時遇到一個函式，先問「它在我的目標路徑上嗎」，不在就當黑盒（名字/行為推得出就夠）繼續。逆向是**定向的**——你要的是「回答一個問題」不是「理解一切」（Ch 31 的收斂節奏、reading_code 的目標驅動 SOP）。

## 反模式 8：忽略字串、import、符號這些免費線索

**你在做**：直接進 asm，不看 `strings`、不看 import 表、不看有沒有殘留符號、不看 section 名——覺得「那些是花邊，真東西在指令裡」。

**為什麼錯**：這些是**最高性價比的情報**，一秒可得，卻常常直接告訴你答案的一半。`strings` 裡的 `usage:`/格式字串/錯誤訊息/URL/檔名，勾勒出程式在做什麼、輸出長怎樣。import 表告訴你它會用哪些能力——**沒有 crypto import 就不可能是標準加密**，有 `socket`/`connect` 就是網路程式，有 `fopen` 就碰檔案。忽略它們，你等於蒙著眼從 asm 硬推那些線索本來白送你的結論，慢十倍還容易猜錯方向。

**正確做法**：**偵察階段把免費線索撿滿再進 asm**（Ch 5、Ch 11 認標準庫指紋）。Ch 31 裡 `strings` 的 `%02x` 給了輸出結構、import 表的「有 strlen/printf 無 crypto」直接定調「自訂 per-byte 編碼」——這兩條讓我跳過所有 boilerplate 直奔那條迴圈。就算 binary strip 了，動態符號（`.dynsym` 裡的 import）也 strip 不掉——那是免費且可靠的地圖。**先問 binary「你用了什麼、說了什麼」，它會回答一大半。**

## 反模式 9：被混淆/packer 嚇退，不動態

**你在做**：`objdump` 出來一堆看不懂的東西——大量間接跳轉、自修改 code、entropy 高得像亂數、`.text` 小得可疑——你判定「這被混淆/加殼了，逆不動」就放棄，或繼續在靜態 dump 上硬瞪。

**為什麼錯**：混淆和加殼**針對的正是靜態分析**——packer 把真正的 code 壓縮/加密，執行時才在記憶體解開；混淆器製造靜態難以跟蹤的間接跳轉、opaque predicate、控制流平坦化。你在**靜態** dump 上瞪一個設計來擊敗靜態的東西，當然瞪不動。但這些技巧幾乎都有一個共同弱點：**code 終究要在記憶體裡以真面目執行**，不然 CPU 跑不了。

**正確做法**：**混淆是動態分析的信號，不是放棄的信號**（Ch 23 對抗混淆）。加殼的：讓它跑，在記憶體裡 dump 出解開後的 code（unpacking）。控制流平坦化/間接跳轉密集的：gdb/DBI 動態記錄實際走過的路徑，把「靜態看不出的跳轉目標」用執行填出來（Ch 15 DBI）。看到高 entropy 的 `.text`、看到 `mprotect` 改權限、看到 `.text` 很小——這些是「該切動態」的指紋，不是「該收工」的判決。**混淆抬高的是靜態成本，動態往往繞過它。**

## 反模式 10：認不出標準庫函式，浪費時間逆 libc

**你在做**：靜態連結的大 binary 裡，你逆到一個函式，一行一行讀它在做記憶體複製/字串比較/排序，逆得很辛苦——其實那是 `memcpy`/`strcmp`/`qsort` 被靜態連結進來、strip 掉名字了。

**為什麼錯**：靜態連結 + strip 後，libc/libstdc++ 的函式和程式自己的函式混在一起、都沒名字。你花二十分鐘逆懂一個函式，最後發現那是 `memcpy` 的 SIMD 優化版——這二十分鐘完全白費，因為那個函式**跟程式的邏輯毫無關係**，它是標準庫。這是靜態連結大 binary 最大的時間黑洞：把精力花在逆你早就知道的標準庫。

怎麼認出「這是標準庫」？幾個指紋：`memcpy`/`memset` 的優化版有一段一段的 SIMD 搬移（`movdqu`/`movaps` 對齊處理 + 尾端零頭）；`strlen` 有 word-at-a-time 的位元魔術（一次讀 8 byte，用 `(x-0x0101…) & ~x & 0x8080…` 這種常數偵測零 byte）；`printf` 家族有巨大的格式解析狀態機；`malloc` 有對 arena/bin 的特定操作。這些常數和樣板一旦看熟，一眼就能貼標籤。反過來，程式自己的邏輯通常小、直接、用到你在 `strings`/import 看到的那些線索——兩者風格差很多。

**正確做法**：**先認出並排除標準庫函式，只逆程式自己的邏輯**（Ch 11 認標準庫指紋、Ch 22 逆靜態連結大 binary）。手段：用 FLIRT（IDA）/ Ghidra 的函式 ID / `sigkit` 這類**函式指紋庫**自動標記已知的 libc 函式（它們比對已知庫的位元組樣板，自動把 `memcpy`/`strcmp` 標好名）；認上面那些 idiom；看呼叫慣例和常數（`qsort` 有 comparator callback、`bsearch` 有二分的位移）。**看到一個函式先問「這是不是標準庫」**——是的話貼標籤跳過，把時間留給程式真正的邏輯（Ch 28 函式指紋）。

## 踩雷集錦（反模式的反模式：矯枉過正）

改反模式時容易擺盪到另一個極端，這裡校準：

1. **錯誤直覺**：「反模式 5 說靜態卡住要跑它，那我乾脆全靠動態、不讀 asm。」→ **正確**：動態只告訴你「這次執行走了什麼」，覆蓋不到的分支、輸入依賴的路徑它看不到。**靜態給全貌、動態給實況**，兩者互補（Ch 17）。純動態會漏掉沒觸發的邏輯。

2. **錯誤直覺**：「反模式 7 說要收斂，那我把所有函式都當黑盒最省事。」→ **正確**：目標路徑上的核心函式該深挖就得深挖，「收斂」是砍**無關**的枝節不是砍該追的主幹。判斷「這函式在不在目標路徑上」才是重點，不是無腦全黑盒。

3. **錯誤直覺**：「反模式 2 說別信反編譯器，那我完全不用它、只讀 asm。」→ **正確**：反編譯器快速看骨架的價值極高，該用。要改的是「無條件信」——用它導航，關鍵斷言回 asm/動態求證。因噎廢食比盲信更慢。

## 一次「反模式 vs 正確做法」的對照劇本

抽象講十條不如看它們串成一場戲。同一個 target（一個 strip 的授權檢查工具），兩個人攻，一個踩滿反模式、一個照正確做法：

**踩坑者的一小時**：`objdump -d` 全 dump，從 entry 第一條開始逐行讀（反 1），在 `_start`/`frame_dummy`/PLT stub 上耗了二十分鐘還沒到邏輯。終於摸到一個函式，按 F5 看 pseudocode，反編譯器說有個 `int local_c`，他當真（反 2），照著推邏輯。推到一個 `rol` 被還原成 `(x<<5)|(x>>3)`，方向他沒細想（反 2+3）。卡在一個間接跳轉，瞪了十五分鐘硬推（反 5），假設沒寫下來，追著追著忘了自己在驗哪個假設（反 6）。最後「覺得」邏輯是 XOR 一個常數，沒對拍就收工（反 4）——結果那常數是他把反編譯器猜錯的型別當真、算出來的錯值。**一小時，結論是錯的，而他不知道。**

**照 SOP 者的一小時**：先 `file`/`strings`/`readelf --dyn-syms`（正 1、8），`strings` 撈到 `"Access denied"`、import 有 `strcmp` 無 crypto——「授權檢查 + 字串比較、無標準加密」方向立刻定。反查 `"Access denied"` 位址在哪被 load，直接跳到檢查函式（正 8）。讀 asm 認出 `strcmp` 的呼叫（正 10，沒去逆 `strcmp` 本體），把暫存器命名、假設寫成清單（正 6）。看到一個 `rol`，不確定方向，gdb 斷點看真實中間值秒確認（正 5）。逆出「拿輸入和一個由某常數變換出的字串比對」，寫等價 keygen，對拍 500 組全過（正 4）。**一小時，結論可對拍證明是對的。**

差別不在誰聰明，在**流程**。踩坑者每一步都選了「感覺比較安全」的懶路（全 dump、信 F5、硬瞪、不對拍），結果全是負投資。這就是為什麼認出反模式比多學一個工具更能提速。

## 進階：把反模式變成 checklist

老手不是不犯這些錯，是**犯了能很快自覺**。方法是把反模式做成一張「我是不是又在犯蠢」的自檢卡，卡住時掃一遍：

```
卡住 / 覺得慢時，自問：
[ ] 我是不是還沒偵察就在鑽 asm？（反1,8）
[ ] 我是不是在信反編譯器一個沒求證的斷言？（反2）
[ ] 這 binary 是 -O 幾？我的預期符合這個等級嗎？（反3）
[ ] 我這個假設，有 ground-truth / 對拍能驗嗎？（反4）
[ ] 我瞪這段靜態超過 10 分鐘了嗎？該 gdb 了嗎？（反5）
[ ] 我的假設寫下來了嗎？暫存器命名了嗎？（反6）
[ ] 這個函式在我的目標路徑上嗎？還是我在逆整個 binary？（反7）
[ ] 這是不是標準庫函式？我在逆 libc 嗎？（反10）
```

Ch 33 會把這張卡和正向的攻堅流程合成一份完整的個人 SOP。

## 本章重點整理

- 逆向卡住/逆錯，幾乎都是踩了十條反模式的某幾條——改掉一個反模式往往比多學一個工具更能提速。
- 逆向對反模式特別敏感，因為**沒有標準答案兜著**（自信地逆錯是最貴的失敗）+ **搜尋空間巨大**（走錯方向成本以小時計）。
- 十條的骨幹：偵察先行（1,8）、別盲信反編譯器（2）、認優化等級（3）、練功用 ground-truth（4）、卡住就動態（5）、全程外化（6）、收斂到目標（7）、混淆=動態信號（9）、排除標準庫（10）。
- 矯枉過正也是坑：別因為「該動態」就純動態、別因為「該收斂」就全黑盒、別因為「別信反編譯器」就完全不用——都是互補不是取代。
- 老手的差別不是不犯錯，是**犯了很快自覺**——把反模式做成自檢卡，卡住時掃一遍。
