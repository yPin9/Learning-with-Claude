# Ch 17 — 靜動結合：假設驅動逆向

> **目標**：把 Part 1 的靜態技術和 Part 2 的動態武器綁成一套完整方法——**假設驅動逆向**：靜態建假設（「這函式好像在檢查長度」）→ 動態驗證（下斷點看真實資料確認或推翻）→ 修正假設 → 收斂到真相。走一個完整小案例：一段靜態看不懂、動態一跑就懂的 code，示範這個循環怎麼運轉。真跑貫穿。

> **環境**：WSL2 / Linux x86-64，gcc + objdump + gdb + ltrace。本章 objdump/ltrace/gdb 輸出全是真跑貼上的。

Part 1 你學了純靜態、Part 2 你學了純動態。但逆向高手從不「純」任何一種——他們在兩者之間**來回跳**，而且跳得很有紀律。這一章把那個紀律講清楚：它叫**假設驅動逆向（hypothesis-driven reversing）**，是 `reading_code` 讀 source SOP 的鏡像（那門課教你對陌生 source 建假設、讀碼驗證；這裡對陌生 binary 建假設、跑它驗證）。

## 為什麼需要這個？

前面每一章都在教「怎麼觀察」——怎麼讀 asm、怎麼下斷點、怎麼 trace、怎麼追資料流。但「觀察什麼」「什麼時候該從靜態切到動態」沒人告訴你。沒有方法，逆向會退化成兩種失敗模式：

- **純靜態硬啃**：從第一條指令讀到最後一條，想在腦裡把整個程式模擬出來。遇到間接跳轉、inline hash、混淆就卡死，還會自信地腦補錯（Ch 0 最致命的陷阱）。
- **純動態亂試**：拿 gdb 到處下斷點、瞎 stepi，沒有目標地看一堆值，看完不知道拼成什麼。

假設驅動逆向是這兩種失敗的解藥。它給逆向一個**方向**：不是「讀懂全部」，而是「**對關鍵處提出一個可證偽的猜測，然後用最省力的方式證實或推翻它**」。靜態負責便宜地生假設，動態負責精準地驗假設——各用所長。

## 先建立直覺：逆向是科學方法

假設驅動逆向本質是把科學方法搬到 binary 上：

```
   ┌─────────────────────────────────────────────────┐
   │                                                   │
   │   ① 觀察（靜態）      ② 假設          ③ 實驗（動態）│
   │   objdump 看骨架  →  「這好像在  →  下斷點/trace  │
   │   strings/strace     檢查長度」     看真實資料     │
   │        ▲                               │          │
   │        │                               ▼          │
   │        │            ④ 對照結果：假設對嗎？        │
   │        │         對 → 記下、推進到下個問題          │
   │        └─────────  錯 → 修正假設，回 ①            │
   │                                                   │
   └──────────────────── 收斂 ─────────────────────────┘
                    直到重建出完整意圖
```

四個關鍵紀律：

1. **假設要可證偽**：「這函式好像很重要」不是假設（無法驗證）。「這函式在檢查輸入長度是否為 8」是假設（一跑就知道對不對）。
2. **用最省力的方式驗證**：能 ltrace 一行看出來的，別開 gdb 慢慢 stepi。驗證成本要低於「繼續靜態硬讀」。
3. **推翻比證實更有價值**：假設被推翻時，你學到最多——「原來不是 strcmp，是自己寫的 hash」。別執著於證明自己對。
4. **一次一個問題，收斂**：不要同時追五條線。鎖定一個關鍵決策點，驗證，記下，再推進。這是 `reading_code` 收斂精神的鏡像。

## 完整案例：一段靜態看不懂、動態一跑就懂的 code

用一個 ground-truth 目標走完整個循環。這是一個「保險箱」程式，source 是**標準答案，我們假裝沒看過**（真實逆向就是這樣）：

```c
// vault.c — 逆的時候把這份蓋起來！
#include <stdio.h>
#include <string.h>
static int stage2(const char*s){ int x=0; for(int i=0;s[i];i++) x=(x<<4)^s[i]; return x; }
int main(int argc,char**argv){
    if(argc<2){ printf("usage\n"); return 1; }
    if((int)strlen(argv[1]) != 8){ printf("bad length\n"); return 1; }
    int code = stage2(argv[1]);
    if(code == 0x1a8b7f95){ printf("UNLOCKED\n"); return 0; }
    printf("locked (0x%x)\n", code); return 1;
}
```

```bash
$ gcc -O0 -o vault vault.c
$ cp vault vault_stripped && strip vault_stripped
```

我們手上只有 `vault_stripped`。目標：**找出讓它印 `UNLOCKED` 的輸入。** 開始跑循環。

### 循環 1：偵察——先看大局（靜態 + 動態各一眼）

還沒建假設前，花 30 秒摸清「這東西大概在幹嘛」。先 `strings`：

```bash
$ strings vault_stripped | grep -iE 'lock|pass|key'
UNLOCKED
locked (0x%x)
```

有 `UNLOCKED` 和 `locked (0x%x)`——這是個「成功/失敗」二元判斷的程式，失敗時還會印一個 hex 值。再跑一次拿真實行為：

```bash
$ ./vault_stripped hello
bad length              ← "hello"(5 字元) → bad length
$ ./vault_stripped WRONGpwd
locked (0x26ba0714)     ← 8 字元 → 過了長度檢查，但 lock，印出一個 code
```

**偵察就給了兩個線索**：(1) 輸入要先過某種**長度檢查**（"hello" 被擋成 bad length，"WRONGpwd" 沒有）；(2) 過長度後會算出一個 **code**（0x26ba0714），跟某個目標比。這比通讀 asm 快得多——這正是 Ch 14 trace 的「快速定位」和 `reading_code` 偵察階段的鏡像。

### 循環 2：假設「有一個長度檢查」→ 靜態定位 → 動態確認

**假設 1**：程式先檢查輸入長度，不對就 `bad length`。可證偽——找出檢查值，改輸入長度看反應。

靜態定位。objdump 找 `strlen` 附近（真跑，節選）：

```asm
    1222:  call   1080 <strlen@plt>
    1227:  cmp    $0x8,%eax             ; ★ strlen 結果 cmp 8
    ...（不等就跳去印 bad length）
```

`call strlen` 緊接著 `cmp $0x8,%eax`——**長度要等於 8**。假設 1 確認，而且順便得到具體值：**長度必須是 8**。用 ltrace 再交叉驗證（Ch 14），真跑：

```bash
$ ltrace ./vault_stripped WRONGpwd
strlen("WRONGpwd")                    = 8
printf("locked (0x%x)\n", 0x26ba0714) = 20
locked (0x26ba0714)
```

ltrace 清楚顯示 `strlen("WRONGpwd") = 8`——長度過了，然後直接 `printf` 印 locked。**但注意 ltrace 到此為止就沒別的了**——它看不到「算出 0x26ba0714 的那個運算」。為什麼？因為那個運算是**inline 的自寫 code**，不是 libc 函式呼叫（Ch 14 講的 ltrace 天花板）。ltrace 一片安靜正是「關鍵邏輯被 inline、該切靜態/gdb」的訊號。假設 1 收工，推進。

### 循環 3：假設「算出的 code 拿去跟一個 magic 比」→ 靜態找 magic

**假設 2**：過長度後，程式對輸入算出一個 code，跟某個寫死的 magic 比，相等就 UNLOCKED。偵察時看到失敗印 `locked (0x26ba0714)`，強烈暗示有這麼個比較。

靜態找那個比較（真跑，objdump 節選）：

```asm
    11a8:  shl    $0x4,%eax              ; ┐ x = x << 4
    11c0:  xor    %ecx,%eax              ; ┘   x = (x<<4) ^ 某個 byte   ← inline hash！
    ...
    1258:  cmpl   $0x1a8b7f95,-0x4(%rbp) ; ★ 拿算出的 code 跟 0x1a8b7f95 比
    ...（相等 → UNLOCKED）
```

假設 2 大幅確認，而且挖到兩個關鍵事實：

1. **目標 magic 是 `0x1a8b7f95`**（`cmpl $0x1a8b7f95,-0x4(%rbp)`）。
2. **hash 演算法是 `x = (x<<4) ^ byte`**（`shl $0x4; xor`）——這就是 ltrace 看不到的 inline 運算，靜態一眼認出。

這是靜動結合的漂亮之處：ltrace（動態）告訴我們「這裡有個算不出來的東西」，objdump（靜態）補上「那個東西是 `(x<<4)^c`」。**動態指出盲點的位置，靜態填補盲點的內容。**

### 循環 4：動態確認我讀對了演算法

靜態讀出「hash = `(x<<4)^c` 迴圈，比 `0x1a8b7f95`」——但我**確定**讀對了嗎？Ch 0 最大的陷阱是「自信地讀錯」。用動態驗證：斷在那個 `cmp`（`0x1258`），餵一個已知輸入，看 gdb 算出的 code 是否符合我對演算法的預測。

先算：對 `"WRONGXYZ"`，我預測 `(x<<4)^c` 迴圈的結果。真跑 gdb 讀真實值：

```bash
$ gdb -q -batch \
    -ex "set disable-randomization on" \
    -ex "break *(0x555555554000+0x1258)" \
    -ex "run WRONGXYZ" \
    -ex 'printf "computed code = 0x%x, wants 0x1a8b7f95\n", *(int*)($rbp-0x4)' \
    ./vault_stripped WRONGXYZ

Breakpoint 1, 0x0000555555555258 in ?? ()
computed code = 0x26ba2dca, wants 0x1a8b7f95
```

gdb 在比較的那一刻讀出：`"WRONGXYZ"` 算出 `0x26ba2dca`，目標是 `0x1a8b7f95`。我拿手算（或寫個 Python 跑 `(x<<4)^c`）對照 `0x26ba2dca`——如果吻合，就**證實我對演算法的理解正確**；不吻合，代表我靜態讀錯了某步（可能漏了 mask、搞錯移位量），得回循環 3 修正。這一步是循環的靈魂：**動態當靜態理解的裁判。**

### 循環 5：反推輸入——收斂到答案

假設全部確認，理解完整：**8 字元、`(x<<4)^c` 迴圈算出的值 == `0x1a8b7f95`**。現在解輸入。因為演算法已知，寫個 Python 反算/搜尋（或用符號執行，Ch 16 末尾）。這裡我知道答案是 `UNLOCKME`（因為我是出題者），驗證：

```bash
$ ./vault UNLOCKME
UNLOCKED               ← 逆對了，真正的輸入
```

`UNLOCKME` 讓它 `UNLOCKED`——沒 patch、沒改記憶體，binary 自己認。完整閉環：偵察定位 → 假設長度檢查（動態確認）→ 假設 magic 比較（靜態挖出 magic 和演算法）→ 動態驗證演算法讀對了 → 反推輸入 → 真跑驗證。

> **對照 source 驗證**：現在打開 `vault.c` 對答案。長度檢查 `strlen != 8`（✓ 我們的假設 1）、`stage2` 的 `x=(x<<4)^s[i]`（✓ 我們讀的 hash）、`code == 0x1a8b7f95`（✓ 我們挖的 magic）。三個假設全對——這就是 ground-truth 迴圈：逆完打開答案，確認沒腦補錯。

## 靜動如何分工：一張速查表

案例走完，把「什麼問題該用靜態還是動態」固化成表：

| 逆向問題 | 先靜態還是動態 | 為什麼 |
|---|---|---|
| 這程式大概在幹嘛 | 動態（strings/strace/跑一次） | 偵察最快 |
| 這裡有個檢查，門檻值多少 | 靜態（找 cmp 的常數） | 常數寫在指令裡 |
| 算出的中間值是多少 | 動態（斷點讀值） | 讀值 << 手算 |
| 這段 inline 運算是什麼演算法 | 靜態（讀 shl/xor/imul pattern） | ltrace 看不到 inline |
| 我讀的演算法對不對 | 動態（斷點對照預測值） | 動態當裁判防腦補 |
| 間接呼叫 `call *%rax` 跳去哪 | 動態（斷點讀 rax） | 目的地執行期才定 |
| 要輸入什麼才能過 | 靜態理解 + 反推/符號執行 | 動態幫不了「解方程」 |

核心分工一句話：**靜態便宜地生假設與挖常數/演算法，動態精準地驗假設與讀中間值。** 兩者交替，不要偏食。

## 對比與取捨：假設驅動 vs 兩種失敗模式

| 面向 | 純靜態硬啃 | 純動態亂試 | 假設驅動（靜動結合） |
|---|---|---|---|
| 方向感 | 想讀懂全部，易迷失 | 到處看值，拼不起來 | 一次一個可證偽假設，收斂 |
| 防腦補 | 差（自信讀錯不自知） | 中 | 好（動態當裁判） |
| 效率 | 低（卡在編譯器細節） | 低（無目標） | 高（各用所長） |
| 對混淆/inline | 卡死 | 盲目 | 靜態指出、動態穿透，互補 |

## 踩雷集錦

1. **假設不可證偽**：「這函式很重要」「這裡有點可疑」——這些沒法驗證，只會讓你原地打轉。逼自己把假設寫成「X 在做 Y，我可以用 Z 驗證」。不會寫，代表你還沒真的形成假設。
2. **證實偏誤：只找支持假設的證據**：你認定某段是 strcmp，就腦補每個細節去符合。動態一跑發現參數根本不是兩個字串——**主動找能推翻假設的實驗**，別只找能證實的。推翻時學最多。
3. **驗證成本比硬讀還高**：為驗一個小假設架半天 Frida、寫一堆 gdb script，不如直接靜態讀完。選**最省力**的驗證手段——ltrace 一行能看的別開 gdb。
4. **一次追太多假設**：同時懷疑長度檢查、hash、比較、還有那個間接呼叫，五條線並行，腦子爆掉。鎖定一個關鍵決策點，驗完再下一個。收斂是紀律。
5. **動態確認演算法時用了會退化的輸入**：驗 `(x<<4)^c` 時餵全 `\0` 或空字串，迴圈根本沒跑，值恆為初始，看不出演算法對錯。用一個**會觸發完整運算**的代表性輸入（本案例用 8 個雜字元）。
6. **忘了最後對照 source**：ground-truth 練習逆完不打開答案對照，等於放棄了「當場抓到腦補錯」的機會——這門課最核心的回饋迴圈。逆完一定對答案。

## 進階：再往深一層

- **假設驅動的鏡像根**：這整套是你 [`reading_code`](../../soft_skills/reading_code/README.md) 課「假設驅動讀碼」的 binary 版。讀 source 時你用「跳到定義、grep 呼叫者」驗假設；逆 binary 時你用「下斷點、trace」驗假設。同一個 SOP，換了驗證工具。兩門對照讀，方法論會通透。
- **符號執行——假設驅動的自動化**：循環 5 的「反推輸入」我們手動搜。符號執行（`angr`，`symex_taint` 課）把「要輸入什麼才能讓 `cmp` 成立」變成自動求解——你甚至不用完全讀懂 hash，把路徑條件丟給 SMT solver 直接解。這是假設驅動逆向裡「解方程」那一步的引擎。
- **外化你的假設**：逆一個大 binary 時，假設多到記不住。把「函式 A = 長度檢查（已確認）、函式 B = hash（假設 `(x<<4)^c`，待驗）」寫進筆記/資料庫——這是 Ch 25「逆向筆記與外化」的主題，也是 `reading_code` 外化精神的鏡像。假設驅動 + 外化，才撐得起大目標。

## 本章重點整理

- **假設驅動逆向**把科學方法搬到 binary 上：靜態建可證偽假設 → 動態驗證 → 修正 → 收斂。是 `reading_code` 讀碼 SOP 的鏡像。
- 四紀律：假設可證偽、用最省力方式驗、推翻比證實有價值、一次一個問題收斂。
- 核心分工：**靜態便宜地生假設、挖常數與演算法（ltrace 看不到的 inline）；動態精準地驗假設、讀中間值、當防腦補的裁判。** 動態指出盲點位置，靜態填補盲點內容。
- 完整循環（本章案例真跑）：偵察定位 → 假設長度檢查（動態確認）→ 假設 magic 比較（靜態挖 magic + 演算法）→ 動態驗證演算法讀對 → 反推輸入 → 真跑 + 對照 source 驗證。
