# Ch 11 — 例外處理架構 I：x86 SEH chain

> **目標**：徹底搞清楚 x86 Windows 的 Structured Exception Handling 如何把 `EXCEPTION_REGISTRATION_RECORD` 串在 stack 上、OS 怎麼走這條鏈分發例外，以及為什麼「SEH record 在 stack 上、handler 是可被 overflow 蓋掉的函式指標」這個設計決策，正是 Ch 21 SEH overwrite 攻擊的根本原因。

---

## 為什麼需要這個？

Linux 的例外處理——`SIGSEGV`、`SIGILL`、`SIGFPE`——是 kernel 對 process 發 signal，signal handler 是個全域的 per-thread 函式指標，和 stack frame 完全分離。C++ exception 則是另一套（`libunwind` / DWARF），走 `.eh_frame` 表。兩套系統完全不同，但有個共同點：**例外處理的控制流資訊不存在於普通的執行 stack 上**，不容易被 stack buffer overflow 直接蓋掉。

Windows x86 的選擇截然不同。

Windows NT 設計時，Intel 的段選擇器（segment selector）機制還是主要工具，FS 段寄存器（在使用者態）特別指向 TEB（Thread Environment Block）。設計師的決定是：把每個函式的例外處理「框（frame）」直接**推入執行 stack**，並把鏈頭指標存在 `FS:[0]`。這樣的好處是實作簡單、不需要額外的 per-function 表、動態建立/拆除 handler 很直覺。代價呢？**handler 指標和 stack 資料住在同一塊記憶體裡。** 一旦有 stack buffer overflow 能往高位址方向覆寫（x86 stack 往低位址長），攻擊者就能蓋掉 handler，在發生例外時把 EIP 指到任意地方。

這章建立機制，不講利用。Ch 21 會讓你親手打這個漏洞。但如果不先把這裡弄透，你在 Ch 21 只是照步驟抄，不是真的懂。

## 先建立直覺：SEH 是 Windows 的一級公民

在 Linux，C++ `try/catch` 是語言層功能，作業系統對它完全不知情。在 Windows，`__try/__except/__finally` 是**作業系統直接支援的機制**，從 NT 3.1 就有，比 C++ 標準例外早。Win32 API 裡一堆地方預設用 SEH，kernel 也用（kernel-mode SEH 的結構和 user-mode 類似但略有差異，這裡聚焦 user-mode）。

幾個關鍵角色先認識：

| 角色 | 實體 | 職責 |
|---|---|---|
| `EXCEPTION_REGISTRATION_RECORD` | stack 上的一個結構 | 一個「例外處理框」，含下一個框的指標和 handler 函式指標 |
| `FS:[0]` / `TEB.NtTib.ExceptionList` | 存在 TEB 裡的指標 | 指向 SEH chain 的**鏈頭**（最新/最深的那個 frame） |
| exception handler | 函式指標，型別 `EXCEPTION_DISPOSITION (*)(...)` | 被呼叫時決定「繼續執行」或「繼續搜尋下一個 handler」 |
| `KiUserExceptionDispatcher` | ntdll 裡的函式 | 從 kernel 回到 user-mode 後，負責走 SEH chain 的起點 |
| `RtlUnwind` | ntdll 裡的函式 | 在找到 handler 之後，反向走鏈執行 `__finally` 清理（unwinding） |

## `EXCEPTION_REGISTRATION_RECORD` 的結構

這個結構只有兩個欄位，極其簡單：

```c
/* winnt.h 定義 */
typedef struct _EXCEPTION_REGISTRATION_RECORD {
    struct _EXCEPTION_REGISTRATION_RECORD *Next;  /* 指向上一個（更舊的）record */
    PEXCEPTION_ROUTINE                     Handler; /* 這個 frame 的例外處理函式 */
} EXCEPTION_REGISTRATION_RECORD, *PEXCEPTION_REGISTRATION_RECORD;
```

`Next` 指向 chain 裡的前一個（更靠近 stack bottom 的那個）record。最後一個 record 的 `Next` 是 `0xFFFFFFFF`（sentinel），代表鏈結束。

`Handler` 的完整簽名是：

```c
EXCEPTION_DISPOSITION Handler(
    struct _EXCEPTION_RECORD    *ExceptionRecord,  /* 例外資訊（code、address…） */
    void                        *EstablisherFrame, /* 這個 SEH frame 的 stack 位址 */
    struct _CONTEXT             *ContextRecord,    /* 例外發生時的完整暫存器狀態 */
    void                        *DispatcherContext /* 內部用 */
);
```

回傳值是一個 enum，常用的兩個：
- `ExceptionContinueExecution`（0）：handler 處理好了，從例外點繼續執行
- `ExceptionContinueSearch`（1）：我不管這個，往下一個 handler 找

## Stack 上的 SEH chain 圖解

假設有這段 C 程式（x86，用 MSVC `__try`）：

```c
void level2(void) {
    __try {
        *(int*)0 = 0;  /* 故意 crash */
    } __except(EXCEPTION_EXECUTE_HANDLER) {
        /* handler */
    }
}

void level1(void) {
    __try {
        level2();
    } __except(EXCEPTION_CONTINUE_SEARCH) {
        /* 不處理，往上傳 */
    }
}

int main(void) {
    level1();
    return 0;
}
```

執行到 `*(int*)0 = 0` 的那一刻，stack 和 SEH chain 長這樣：

```
高位址（stack bottom / 舊的 stack frame）
┌──────────────────────────────────────────────────────┐
│  main 的 stack frame                                  │
│  ...（local vars）                                    │
│                                                      │
│  FS:[0] ─────────────────────────────────────────┐   │
│           （TEB.NtTib.ExceptionList 指向鏈頭）     │   │
└──────────────────────────────────────────────────┼───┘
                                                   │
┌──────────────────────────────────────────────────▼───┐
│  level1 的 stack frame                                │
│  ...（local vars）                                    │
│  ┌──────────────────────────────────────────────┐    │
│  │ EXCEPTION_REGISTRATION_RECORD  [level1 frame] │    │
│  │  +0x00  Next    ──────────────────────────────┼────┼──┐
│  │  +0x04  Handler ─→ level1 的 filter 函式      │    │  │
│  └──────────────────────────────────────────────┘    │  │
└─────────────────────────────────────────────────────┘  │
                                                          │
┌─────────────────────────────────────────────────────────▼┐
│  level2 的 stack frame                                    │
│  ...（local vars）                                        │
│  ┌────────────────────────────────────────────────────┐  │
│  │ EXCEPTION_REGISTRATION_RECORD  [level2 frame]      │  │
│  │  +0x00  Next    ─→ 0xFFFFFFFF  （sentinel, 鏈尾）   │  │
│  │  +0x04  Handler ─→ level2 的 filter 函式           │  │
│  └────────────────────────────────────────────────────┘  │
│  ← ESP 大約在這附近                                       │
│  [觸發 AV 的 *(int*)0 = 0 在這個 frame 裡執行]           │
└───────────────────────────────────────────────────────────┘
低位址（stack top / 新的 stack frame）
```

鏈的方向：`FS:[0]` → `level1 的 record` → `level2 的 record` → `0xFFFFFFFF`

注意方向：**最新（最深）的 frame 在 chain 開頭**（FS:[0] 指向它），最舊的在鏈尾。這和你直覺可能預期的相反，但有道理：函式呼叫時新的 `EXCEPTION_REGISTRATION_RECORD` 被 push 成新的鏈頭，函式返回時再把它 pop 掉（恢復 `FS:[0]` 到原來的值）。

## `__try/__except/__finally` 是如何翻譯成 SEH 的

`__try/__except/__finally` 是 MSVC 編譯器關鍵字（Microsoft 擴充，不是 C 標準）。GCC/mingw **不支援** `__try`，x86 的 `__try` 程式只能用 MSVC 編。這點很重要：本章的 MSVC 程式碼範例標為「未實測，理論預期」，因為本機 MSVC C++ workload 尚未就位。

MSVC 遇到 `__try` 時，會在 stack frame 裡多插入一個（或更複雜版本的）`EXCEPTION_REGISTRATION_RECORD`，並在函式 prologue 把它 push 進 `FS:[0]` 的鏈頭，在 epilogue 把它移除。實際上 MSVC 用的是更豐富的 `SCOPETABLE_ENTRY` 機制（`EH4` 版本的 SEH）來支援多層 `__try` 巢狀和 scope table，但骨架結構不變。

> **未實測，理論預期**：用 MSVC 編一個含 `__try` 的 x86 程式，用 WinDbg 在例外觸發前停下，`dt ntdll!_EXCEPTION_REGISTRATION_RECORD @esp` 可以印出 stack 上的 record。讀者裝好 MSVC + cdb 後，試試用 `cdb -c "bp main;g;dd fs:0 L4;q" target.exe` 看 FS:[0] 鏈。

### `__try/__except` 的流程

```
__try {
    /* 可能觸發例外的程式碼 */
} __except ( filter_expr ) {
    /* exception handler body */
}
```

`filter_expr` 的三種值：
- `EXCEPTION_EXECUTE_HANDLER`（+1）：我要處理，執行 `__except` 的 body，然後繼續執行（unwinding 發生）
- `EXCEPTION_CONTINUE_SEARCH`（0）：不管，往下一個 handler 繼續搜尋
- `EXCEPTION_CONTINUE_EXECUTION`（-1）：修好了，從例外點重新執行（慎用）

### `__try/__finally` 的流程

```
__try {
    /* 正常程式碼 */
} __finally {
    /* 不管正常返回還是例外，一定執行 */
}
```

`__finally` 不是 exception handler，它是一個 **termination handler**。在 unwinding 過程中（找到 handler 開始往回拆 frame 時），MSVC 的 SEH 實作會在拆每個 frame 前呼叫對應的 `__finally` block。這就是 RAII 在 C 語言的 SEH 版本。

## 例外分發流程：從硬體到 handler

這是整個機制最重要的部分。以 Access Violation 為例，從 CPU 觸發到 handler 被呼叫的完整路徑：

```
1. CPU 執行到壞指令（例如：mov [0xDEADBEEF], eax）

2. CPU 的 Page Fault 處理：
   IDT[0x0E] → kernel 的 #PF handler
   ↓
   KiTrap0E（在 ntoskrnl.exe 裡）
   - 嘗試修復（copy-on-write、demand paging…）
   - 修不了 → 決定這是個要往上回報的例外
   ↓
3. 建立 EXCEPTION_RECORD + CONTEXT
   EXCEPTION_RECORD {
     ExceptionCode    = STATUS_ACCESS_VIOLATION (0xC0000005)
     ExceptionFlags   = 0
     ExceptionAddress = 觸發 AV 的指令位址
     NumberParameters = 2
     ExceptionInformation[0] = 1 (write access)
     ExceptionInformation[1] = 0xDEADBEEF (fault address)
   }

4. 回到 user-mode：
   kernel 把執行流轉到 ntdll!KiUserExceptionDispatcher
   （透過 KUSER_EXCEPTION_STACK 機制 / APC-like 注入）
   
   此時 user-mode stack 的頂端有：EXCEPTION_RECORD + CONTEXT
   
5. KiUserExceptionDispatcher 呼叫：
   ntdll!RtlDispatchException(ExceptionRecord, ContextRecord)
   
6. RtlDispatchException 走 SEH chain：
   
   pRegistration = NtCurrentTeb()->NtTib.ExceptionList;  /* = FS:[0] */
   
   while (pRegistration != EXCEPTION_CHAIN_END) {      /* 0xFFFFFFFF */
       
       /* 安全檢查（如果有 SEHOP）省略先 */
       
       result = pRegistration->Handler(
                    ExceptionRecord,
                    pRegistration,      /* EstablisherFrame */
                    ContextRecord,
                    &DispatcherContext
               );
       
       if (result == ExceptionContinueExecution)
           NtContinue(ContextRecord, FALSE);  /* 修復，繼續執行 */
       
       if (result == ExceptionContinueSearch) {
           pRegistration = pRegistration->Next;  /* 往下走 */
           continue;
       }
       
       /* result == ExceptionNestedException 等其他情況略 */
   }
   
   /* 走到鏈尾還沒人處理 → UnhandledExceptionFilter → 通常是崩潰 */

7. 如果某個 handler 決定「我要執行 __except body」：
   handler 內部呼叫 RtlUnwind(pRegistration, …)
   ↓
   RtlUnwind 從鏈頭再走一次，對每個 frame 呼叫 Handler（UNWIND 旗標 set）
   被呼叫到的 handler 執行對應的 __finally block
   ↓
   完成 unwind 後，跳到 __except body 執行
```

整個流程的 ASCII 時序圖：

```
CPU fault
   │
   ▼
[kernel: KiTrap0E]
  建立 EXCEPTION_RECORD + CONTEXT
   │
   ▼
[ntdll: KiUserExceptionDispatcher]
  在 user-mode stack 上設置例外資訊
   │
   ▼
[ntdll: RtlDispatchException]
  FS:[0] ──► [frame_N.Handler()] ──► ExceptionContinueSearch
                     │
                     ▼ (Next)
             [frame_N-1.Handler()] ──► ExceptionContinueSearch  
                     │
                     ▼ (Next)
             [frame_1.Handler()]  ──► ExceptionExecuteHandler
                     │
                     ▼
             [ntdll: RtlUnwind]
              反向走鏈，呼叫 __finally
                     │
                     ▼
             跳到 __except body
```

## `FS:[0]`、TEB、NtTib 的關係

```
FS:[0x00]  = TEB.NtTib.ExceptionList  ← SEH chain 鏈頭
FS:[0x04]  = TEB.NtTib.StackBase      ← stack 最高位址（bottom）
FS:[0x08]  = TEB.NtTib.StackLimit     ← stack 最低位址（top，可擴展的限制）
FS:[0x18]  = TEB 自身的位址
FS:[0x20]  = TEB.EnvironmentPointer
FS:[0x24]  = TEB.ClientId.UniqueProcess
FS:[0x28]  = TEB.ClientId.UniqueThread
FS:[0x30]  = TEB.ActiveRpcHandle
FS:[0x34]  = TEB.ThreadLocalStoragePointer
FS:[0x38]  = TEB.ProcessEnvironmentBlock  ← PEB 指標（x86 PEB 在這）
```

`NT_TIB`（NT Thread Information Block）是 TEB 的前幾個欄位，用來和舊的 OS/2 保持相容性的一個「公開」前綴。`ExceptionList` 就是 `NT_TIB` 的第一個欄位，所以 `FS:[0]` 就直接是 chain 鏈頭。

> **以你環境的 dt 為準**：若有 cdb，`dt ntdll!_TEB @$teb NtTib.ExceptionList` 可印出實際的鏈頭位址。`dt ntdll!_NT_TIB` 可看完整偏移表。

## 關鍵安全含義：為什麼 handler 可以被 overflow 蓋掉

現在把機制和安全性接起來。考慮這段虛擬碼（x86，假設 stack layout）：

```
stack frame:
┌─────────────────────────────────────────────────────┐
│  char buf[64]                ← overflow 的目標      │
│  ...（其他 local vars）                             │
│  EXCEPTION_REGISTRATION_RECORD:                    │
│    +0x00  Next    = 0xFFFFFFFF                      │
│    +0x04  Handler = 0x00401234  ← 合法 handler addr │
└─────────────────────────────────────────────────────┘
     ↑ ESP（stack top，低位址）
```

當 `buf[64]` 被超過 72 bytes 的資料覆寫（具體 offset 看編譯結果），`Handler` 欄位就會被攻擊者控制的值蓋掉。

接下來，如果攻擊者能觸發一個例外（最常見：故意存取壞位址，或直接讓 overflow 本身觸發 stack 損毀相關例外），SEH 分發流程就會呼叫被蓋掉的 `Handler`——EIP 跳到攻擊者指定的地方。

**這正是 Ch 21「SEH overwrite」攻擊的根因**：
1. `EXCEPTION_REGISTRATION_RECORD` 和 `buf` 住在同一個 stack frame
2. `Handler` 是一個普通的記憶體指標，沒有簽章、沒有加密
3. `KiUserExceptionDispatcher` 呼叫它之前，幾乎沒有驗證（在 SEHOP 出現前）

這章的任務是把機制說清楚；Ch 22 講 SEHOP 怎麼防；Ch 21 講怎麼打。

## Unwinding 的意義與流程

Unwinding 在 SEH 的語境有特定意思：找到願意處理例外的 handler 之後，系統把 SEH chain 從鏈頭**往回拆**到那個 handler 所在的 frame，沿途每個 frame 的 `__finally` block 都會被執行。這保證了 C 的 RAII 語意（或說是它的前身）——打開的檔案、拿到的鎖，在例外發生時依然能被清理。

`RtlUnwind(TargetFrame, ReturnValue, ExceptionRecord, ReturnValue2)` 的核心邏輯：

```
pReg = FS:[0]   (鏈頭)

while (pReg != TargetFrame) {
    /* 對每個 frame，以 UNWIND flag 呼叫 handler */
    pReg->Handler(record, pReg, context, &dc);  /* flag: EH_UNWINDING */
    /* 移除這個 frame：FS:[0] = pReg->Next */
    FS:[0] = pReg->Next;
    pReg = pReg->Next;
}
/* TargetFrame 對應的 __except body 接管執行 */
```

Unwind 和 dispatch 的關鍵差別：dispatch 是**由新到舊**走鏈尋找 handler；unwind 是**從新到舊**清理（在找到 handler 後，再走一次）。對同一個 handler 來說，兩次都會被呼叫——第一次（dispatch）是詢問「你要處理嗎？」，第二次（unwind）是通知「你已被選中，現在清理你的 frame」。

## 例外記錄：EXCEPTION_RECORD 結構

每次例外發生，kernel 建立一個 `EXCEPTION_RECORD` 描述這次例外，傳給每個 handler 作為第一個參數：

```c
typedef struct _EXCEPTION_RECORD {
    DWORD                    ExceptionCode;        /* 0xC0000005 = STATUS_ACCESS_VIOLATION */
    DWORD                    ExceptionFlags;       /* EXCEPTION_NONCONTINUABLE 等 */
    struct _EXCEPTION_RECORD *ExceptionRecord;     /* 嵌套例外時的上一個記錄（可為 NULL） */
    PVOID                    ExceptionAddress;     /* 觸發例外的指令位址 */
    DWORD                    NumberParameters;     /* ExceptionInformation 的有效項數 */
    ULONG_PTR                ExceptionInformation[EXCEPTION_MAXIMUM_PARAMETERS]; /* 15 項 */
} EXCEPTION_RECORD;
```

對 Access Violation（`0xC0000005`），`ExceptionInformation[0]` 是存取類型（0=讀, 1=寫, 8=DEP 執行），`ExceptionInformation[1]` 是觸發 AV 的記憶體位址。這兩個值在 exploit 開發裡很有用：

- 觸發 AV 後，handler 裡的 `ExceptionInformation[1]` 告訴你「哪個位址引發的 AV」——可以確認 overflow 覆寫到哪裡了
- 如果 `ExceptionInformation[0] == 8`（DEP 阻擋執行），你知道是 DEP 在作用，不是單純的 bad pointer

其他常見 exception code（對應 Linux signal）：

| Windows ExceptionCode | 值 | Linux 對應 |
|---|---|---|
| STATUS_ACCESS_VIOLATION | 0xC0000005 | SIGSEGV |
| STATUS_ILLEGAL_INSTRUCTION | 0xC000001D | SIGILL |
| STATUS_INTEGER_DIVIDE_BY_ZERO | 0xC0000094 | SIGFPE |
| STATUS_BREAKPOINT | 0x80000003 | SIGTRAP |
| STATUS_STACK_OVERFLOW | 0xC00000FD | SIGSEGV（通常） |
| STATUS_CPP_EXCEPTION | 0xE06D7363 | — （C++ throw 在 x86 走 SEH） |

`STATUS_CPP_EXCEPTION`（`0xE06D7363`，「msc」的 ASCII）是 MSVC C++ `throw` 生成的 exception code，由 `_CxxThrowException` 呼叫 `RaiseException` 觸發，然後走 SEH chain 找到 C++ 的 `__CxxFrameHandler3` 處理。這意味著 x86 上的 C++ exception 和 `__try/__except` 走同一條 SEH 分發路徑。

## CONTEXT 結構：handler 拿到的暫存器快照

`KiUserExceptionDispatcher` 傳給每個 handler 的第三個參數是 `CONTEXT` 結構——例外發生瞬間的完整 CPU 暫存器狀態（x86 版本）：

```c
/* 簡化版，只列 exploit 常用欄位 */
typedef struct _CONTEXT {
    /* x86 segment regs */
    DWORD SegGs, SegFs, SegEs, SegDs;
    /* x86 integer regs */
    DWORD Edi, Esi, Ebx, Edx, Ecx, Eax;
    /* x86 control regs */
    DWORD Ebp, Eip, SegCs, EFlags, Esp, SegSs;
    /* ...浮點、擴充狀態... */
} CONTEXT;
```

`CONTEXT.Eip` 是例外發生時的指令指標。在 `EXCEPTION_CONTINUE_EXECUTION` 路徑上，handler 可以修改 `CONTEXT.Eip` 然後回傳，讓 `NtContinue` 以修改後的 `Eip` 繼續執行——這是一個「從任意地址繼續執行」的原語。某些高級利用技法用這個方式在 handler 裡更改 EIP 而不是傳統的 `call [esp+8]` 跳轉。

`CONTEXT.Esp` 也可被修改：如果攻擊者控制了 handler 並能修改 `ContextRecord->Esp`，就能做到 stack pivot（在 ROP chain 裡很有用）。

> **未實測，理論預期**：在 WinDbg 裡，`.exr -1`（顯示最近一次例外的 EXCEPTION_RECORD）和 `.ecxr`（切換到例外的 CONTEXT）是 exploit 分析的標準起手動作。

## 對比：x86 SEH vs Linux signal/DWARF

| 面向 | Windows x86 SEH | Linux signal | Linux C++ (DWARF unwinding) |
|---|---|---|---|
| 控制流資訊存在哪 | **stack 上**（`EXCEPTION_REGISTRATION_RECORD`） | 獨立的 `sigaction` 表 | `.eh_frame` / `.gcc_except_table`（唯讀 section） |
| 可被 stack overflow 蓋掉嗎 | **是**（這是 SEH overwrite 的根因） | 不行（不在 stack 上） | 不行（在唯讀段裡） |
| OS 支援程度 | OS 一級公民，kernel 直接分發 | OS signal，但 C++ 例外是 libc 層 | libc 層（`libunwind`/`libgcc`） |
| 效能 | 幾乎零 overhead（不觸發就沒有掃表成本） | 有 sigaction lookup | 有 table lookup，但 zero-cost 在 happy path |
| 巢狀 try 支援 | 是（scope table） | 透過 sigaltstack | C++ 標準支援 |
| x64 是否繼續用 | 否（改成 table-based） | 是 | 是 |

## 安全機制預告：SafeSEH 和 SEHOP 的位置

本章只建立機制，但你需要知道 Windows 在哪裡嘗試修補這個設計缺陷，這樣你在 Ch 21–22 不會措手不及：

**SafeSEH**（`/SAFESEH` 連結器旗標，MSVC only）：在 PE 的 Load Config 目錄裡加入一個「已知合法 SEH handler」的位址陣列。`RtlIsValidHandler` 在呼叫 handler 前檢查：handler 位址必須在這個白名單裡。如果被 overflow 蓋的 handler 指向白名單以外的位址（例如 shellcode 或 gadget），`RtlIsValidHandler` 會拒絕它，轉而走終止流程。

繞過條件：目標 binary 或被利用的模組（handler 跳轉目標所在的模組）沒有 `/SAFESEH`，或者跳轉目標是一個沒有 SEH handler 表（因而視為不受 SafeSEH 保護）的模組。在 x86 時代，找一個「non-SafeSEH 的模組裡的 `call [esp+8]` gadget」是標準繞過策略。

**SEHOP**（Structured Exception Handler Overwrite Protection，Windows Vista SP1 起在 server edition 預設開啟）：在分發每個例外前，`RtlIsValidHandler` 走整條 SEH chain，驗證：
1. 每個 `Next` 指標都指向比目前 frame 更高的 stack 位址（向 stack bottom 方向）
2. 鏈最終以 `ntdll!FinalExceptionHandlerPad` 結尾（OS 安裝時在 TEB 裡注入的 sentinel handler）

如果 chain 被 overflow 破壞（一個 record 的 `Next` 指向 stack 以外），SEHOP 偵測到鏈的完整性被破壞，直接終止程式，不呼叫任何 handler。Ch 22 詳講 SEHOP 的繞過思路。

```
SafeSEH  保護的是：handler 指標本身必須合法
SEHOP    保護的是：整條 SEH chain 的完整性（Next 指標的走向）
兩者互補，但都只在 x86；x64 用 table-based 從根本上避開了這個問題
```

## 底層機制：MSVC 的 `__except_handler3` / `__except_handler4`

實際上 MSVC 在 x86 mode 用的不是原始的兩欄 record，而是擴充版：

```c
/* MSVC x86 SEH frame（簡化）*/
typedef struct _EH3_EXCEPTION_REGISTRATION {
    struct _EH3_EXCEPTION_REGISTRATION *Next;     /* 標準 Next */
    PEXCEPTION_ROUTINE                  Handler;  /* 標準 Handler（指向 __except_handler3） */
    PSCOPETABLE_ENTRY                   ScopeTable; /* MSVC 專屬：scope table 指標 */
    DWORD                               TryLevel;   /* 目前在第幾層 __try 裡 */
    /* （後面還有儲存的 EBP 等，確切 layout 看版本）*/
} EH3_EXCEPTION_REGISTRATION;
```

`__except_handler3`（或新版的 `__except_handler4`）是 MSVC CRT 提供的一個通用 handler 函式。所有用 `__try/__except` 的函式，其 `Handler` 指標都指向這同一個函式。真正的 filter 邏輯和 handler body 在 `ScopeTable` 裡，`__except_handler3` 根據 `TryLevel` 查表決定實際行為。

這個設計的安全含義：攻擊者不必找到「正確的 handler 函式」，只要把 `Handler` 改成任何有用的地址就夠了——因為 SEH dispatch 無論如何都會呼叫它。

> **未實測，理論預期**：在 WinDbg 裡，`!exchain` 命令可以印出目前執行緒的 SEH chain，包含每個 frame 的地址和 handler 指標。這是確認 SEH 狀態最直接的方法。

## 完整的 SEH chain 生命週期：從 push 到 pop

把 SEH record 推入鏈和彈出鏈的操作，在 x86 assembly 層面很清楚。MSVC 在有 `__try` 的函式 prologue/epilogue 裡插入這些指令（理論預期，MSVC 編譯才會有）：

**Prologue（建立 SEH frame，push 進鏈頭）**：
```nasm
; 函式進入時
push  offset __except_handler3   ; 壓入 Handler 指標
push  dword ptr fs:[0]           ; 壓入舊的 FS:[0]（即新 record 的 Next）
mov   dword ptr fs:[0], esp      ; FS:[0] 指向新 record（stack 頂端）
; 此時 esp 指向新的 EXCEPTION_REGISTRATION_RECORD
;   [esp+0]  = Next（舊的 FS:[0]）
;   [esp+4]  = Handler（__except_handler3 的位址）
; MSVC 實際上還會再 push ScopeTable 和 TryLevel
```

**Epilogue（函式返回，從鏈頭 pop）**：
```nasm
; 函式返回前
mov   eax, dword ptr [esp]       ; 取回 Next（舊的 FS:[0]）
mov   dword ptr fs:[0], eax      ; 恢復 FS:[0] 為舊值
add   esp, 8                     ; 清掉 Next + Handler
```

這個 push/pop 對是隱含的——你不會在 C 原始碼裡看到它，是 MSVC 自動插入的。理解這個是為什麼「函式返回後，SEH chain 自動被清理」的原因：不是 OS 來做的，是 MSVC 的 epilogue 做的。

從 exploit 角度看，這個機制讓 `Handler` 在 stack 上的位置可以精確計算：它總是在 `Next` 後面 4 bytes（在 `EXCEPTION_REGISTRATION_RECORD` 的 +0x04 位置）。當你知道 buffer 相對於 `esp` 的偏移，就能算出要覆蓋多少 bytes 才能蓋到 `Handler`。這就是 Corelan SEH exploit 教程裡「找 offset to nSEH」的計算目標。

> **名詞說明**：Corelan 的教程用 **nSEH**（next SEH）指 `EXCEPTION_REGISTRATION_RECORD.Next` 欄位，用 **SEH**（SEH handler）指 `Handler` 欄位。在利用的過程中，`nSEH` 通常被填成一個 short jump，讓執行流在 `Handler`（gadget）把 ESP 調整後跳回 payload；`Handler` 被填成一個 `call [esp+8]` 的 gadget（跳到 nSEH 位置），形成一個兩步的執行轉移。Ch 21 會詳講這個雙欄位利用流程。

## 踩雷集錦

1. **「GCC/mingw 也支援 `__try`」**：x64 的 mingw 不支援 `__try`，x86 的也視版本而定。本課 SEH 的 C 範例都是 MSVC 路線；要用 mingw 觀察 SEH 行為得改用 `SetUnhandledExceptionFilter` 或 VEH（下一章）。不要在 mingw 上試圖編 `__try` 的程式然後懷疑機制。

2. **「FS:[0] 的 sentinel 是 NULL」**：x86 的 chain 尾端是 `0xFFFFFFFF`（即 `-1`/`EXCEPTION_CHAIN_END`），不是 NULL。x64 的 `GS:[0]`（NtTib.ExceptionList）在 mingw runtime 下是 NULL，在 MSVC runtime 下是 `0xFFFFFFFFFFFFFFFF`——但意義完全不同（x64 根本不用這條鏈，詳見 Ch 12）。不要混淆。

3. **「Dispatch 和 Unwind 是同一件事」**：dispatch 是找誰來處理（由新到舊走鏈），unwind 是找到後再走一次執行清理（由新到舊，但這次是 `UNWIND` flag）。許多資料把兩者混用，導致你搞不清楚「handler 被呼叫幾次」。記住：如果你的 frame 被選中作為 handler，它的 Handler 函式**總共被呼叫兩次**（dispatch 時問、unwind 時執行）。

4. **「`__finally` 一定在例外時執行」**：準確說法是「`__finally` 在 unwind 時執行」。如果是正常的函式返回（沒有例外），`__finally` 也會執行——MSVC 在 function epilogue 呼叫它。所以 `__finally` 不是「例外清理」，是「離開 try block 時的清理」，正常返回也算。

5. **「Stack 上的 record 被 frame 按順序擺放」**：MSVC 把 `EXCEPTION_REGISTRATION_RECORD` 放在哪個 stack offset，取決於優化級別和其他 local var 的 layout。你在利用時要用 `!exchain` 或計算 offset 來確認，不能假設固定在某個 EBP 偏移。不同版本 MSVC、不同優化設定，offset 可能差到數十 bytes。

## 進階：再往深一層

### EH4：cookie 保護的 scope table

`__except_handler4` 是 MSVC `/GS` 和 SEH 結合的版本，在 `EH3_EXCEPTION_REGISTRATION` 基礎上加了對 `ScopeTable` 指標的 XOR 加密（用 stack cookie 當 key）。如果攻擊者能蓋掉 `Handler`，它指向 `__except_handler4`，呼叫時 `__except_handler4` 試著用 XOR 解密 `ScopeTable` 指標，但因為 ScopeTable 也被蓋壞了，解密出來的是個亂值，接著跳進去就崩潰——比直接 control flow hijack 難了一點。這是過渡性防護；SEHOP 是更完整的答案（Ch 22）。

### C++ exception 和 SEH 的交織

MSVC 的 C++ `try/catch` 在 x86 下**用 SEH 實作**。`throw` 最終會呼叫 `RaiseException(STATUS_CPP_EXCEPTION, …)`，讓 SEH 分發流程走 C++ 的 `__CxxFrameHandler3`。這意味著：在 x86 Windows 上，SEH overwrite 可以同時攻擊用 `__try/__except` 的程式**和**用 C++ `try/catch` 的程式——只要 SEH chain 存在。

### 面試題：為什麼 x64 拋棄 stack-based SEH？

因為 stack-based SEH 根本上有安全問題（handler 可被 overflow 蓋），加上 x64 有 DEP/NX，不能在 stack 上執行 shellcode，但 SEH overwrite + 跳到 ROP gadget 還是可以做。Microsoft 在設計 x64 ABI 時，選擇了 table-based 方案：把 handler 資訊放在 PE 的唯讀 section（`.pdata`/`.xdata`），stack overflow 蓋不到那裡。Ch 12 詳講。

## `RaiseException`：手動觸發 SEH 的方式

SEH 不只是被動接收硬體例外——程式可以用 `RaiseException` 主動觸發一個 SEH 例外：

```c
VOID RaiseException(
    DWORD      dwExceptionCode,   /* 你自訂的 exception code，或系統定義的 STATUS_* */
    DWORD      dwExceptionFlags,  /* 0 或 EXCEPTION_NONCONTINUABLE */
    DWORD      nNumberOfArguments, /* ExceptionInformation 的項數 */
    const ULONG_PTR *lpArguments  /* 傳給 handler 的額外資訊 */
);
```

C++ 的 `throw` 實際上就呼叫 `RaiseException(0xE06D7363, EXCEPTION_NONCONTINUABLE, 3, args)`，`args` 包含 exception object 的指標和 throw info。

在安全研究裡，`RaiseException` 有幾個用途：
1. 測試 SEH chain：直接觸發一個你知道不會被處理的例外（例如自訂 code），觀察 chain 走向
2. 反除錯技法：`RaiseException(EXCEPTION_BREAKPOINT, …)` 用程式法發出 `INT 3` 訊號，如果有除錯器掛著就會被攔截，否則走 SEH chain
3. 把 C 程式碼的錯誤碼轉成 SEH 流程（模擬 C++ exception 語意）

從 exploit 角度：`RaiseException` 被攻擊者控制時（例如 format string 能控制參數），可以用來強制走 SEH chain 並讓 handler 被呼叫——這在某些「需要例外但 overflow 本身不會觸發 AV」的場景下有用。

## 動手練習

> **環境**：需要 MSVC（`cl.exe`）x86 模式 + WinDbg/cdb。

1. 寫一個最小的 x86 C 程式，用 `__try/__except` 包住一個 `*(int*)0 = 0`。
2. 用 MSVC 編成 x86（`cl /O0 /Zi target.c /link /SUBSYSTEM:CONSOLE`），加上 `/Oy-`（關 frame pointer 省略）。
3. 在 WinDbg（x86 模式）裡執行，在例外前用 `!exchain` 看 SEH chain。
4. 畫出 stack 上 `EXCEPTION_REGISTRATION_RECORD` 的實際位址和 `Handler` 的值。
5. 確認 `Handler` 指向 `__except_handler3` 或 `__except_handler4`。
6. 繼續執行，讓例外分發發生，在 handler 入口處下 breakpoint，驗證 `EstablisherFrame` 參數確實是 stack 上那個 record 的位址。

## 本章重點整理

- x86 Windows SEH 把 `EXCEPTION_REGISTRATION_RECORD {Next, Handler}` 串在執行 stack 上，鏈頭在 `FS:[0]`（TEB.NtTib.ExceptionList）。
- 例外發生時：CPU → kernel `KiTrap0E` → `ntdll!KiUserExceptionDispatcher` → `RtlDispatchException` 走鏈呼叫每個 `Handler` 直到有人接手，再由 `RtlUnwind` 反向清理 `__finally`。
- `Handler` 指標和 local buffer 同在一個 stack frame 裡，stack buffer overflow 可以直接蓋掉它——這是 SEH overwrite 攻擊的根本原因（Ch 21 的靶心）。
- Linux 的例外處理（signal/DWARF）把控制流資訊存在 stack 以外的地方；x86 Windows 的這個設計選擇在 x64 被拋棄，改成 table-based（Ch 12）。
