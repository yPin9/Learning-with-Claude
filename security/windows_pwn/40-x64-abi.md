# Ch 40 — x64 ABI / calling convention 對 exploit 的影響

> **目標**：徹底掌握 Windows x64 calling convention 與 System V AMD64（Linux）的具體差異——暫存器分工、shadow space 的必要性、對齊規則——並把這些差異轉化為 ROP chain 建構的具體知識：要湊哪些 gadget、chain 裡哪裡要留洞、對齊錯了會在哪裡 crash。學完能解釋為什麼 x64 ROP 比 x86 難，並在 mingw 反組譯輸出裡指出 shadow space 分配的位置。

> **環境**：mingw-w64 GCC 14.2（`C:\msys64\ucrt64\bin`）。反組譯用 `objdump -d -M intel`。所有 `objdump` 輸出為本機實跑結果。

---

## 為什麼需要這個？

你已經在 Ch 23 建構過 Windows x64 ROP chain，也知道 VirtualProtect 要四個參數。但那一章把 calling convention 當作前提帶過了——「第一個參數放 RCX，記得留 shadow space」。

這樣的理解在練習靶上夠用，但到了真實 CVE 就會撞牆：

- gadget 搜尋器找不到 `pop rcx` 但找得到 `pop rdi`——你知道在 Linux 用 `rdi` 傳第一個參數，在 Windows 這樣做對嗎？
- ROP chain 跑到 `VirtualProtect` 前 crash，backtrace 指在某個 SSE 指令——是哪裡沒對齊？
- 要呼叫一個六個參數的 API，第五、六個參數放在哪？
- x64 call 之前一定要 `sub rsp, 0x28`，為什麼？不做的後果？

這些問題的答案全在 x64 ABI 的細節裡。這章把它講清楚，對照 Linux 你熟的那套，把每個差異落地到 exploit 場景。

---

## 先建立直覺：兩套不同的電話禮儀

把函式呼叫想成打電話。「呼叫者」要把訊息傳給「被呼叫者」，雙方需要事先約好：

1. **訊息放哪裡**（參數在哪個暫存器 / stack 的哪個位置）
2. **誰要保護現場**（哪些暫存器呼叫後還能用，哪些可能被改掉）
3. **電話前要準備什麼**（stack 對齊、為被呼叫者預留的空間）

System V AMD64（Linux 慣例）和 Microsoft x64 是兩套不同的電話禮儀，寫在 ABI 規格裡。它們在 x86-64 的物理層（CPU 暫存器）上跑，但**協議不同**。

ROP chain 本質上是你作為攻擊者扮演「呼叫者」——你要負責把這套禮儀做完，才能讓被你呼叫的 API 正常工作。禮儀沒做好，不是 API 算錯，就是因為 stack misaligned 在 SSE 指令 crash，或在 epilogue 的 `ret` 跳到錯誤位址。

## 參數傳遞：暫存器對照

這是兩套 ABI 最醒目的差異，用對照表看最清楚。

### 整數 / 指標參數

| 參數順序 | System V AMD64（Linux） | Microsoft x64（Windows） |
|---|---|---|
| 第 1 個 | `RDI` | `RCX` |
| 第 2 個 | `RSI` | `RDX` |
| 第 3 個 | `RDX` | `R8` |
| 第 4 個 | `RCX` | `R9` |
| 第 5 個 | `R8` | `[RSP+0x20]`（stack，call 後的位址） |
| 第 6 個 | `R9` | `[RSP+0x28]` |
| 第 7 個以後 | stack（右到左壓） | `[RSP+0x30]`、`[RSP+0x38]`... |
| 返回值 | `RAX`（整數 / 指標） | `RAX`（整數 / 指標） |

**關鍵觀察**：

- Linux 用 6 個暫存器傳參；Windows 只用 4 個，第 5 個起就上 stack。
- 前四個的暫存器**完全不同**（`RDI/RSI` 在 Linux 傳一二，在 Windows 這兩個是 callee-saved，跟參數無關）。
- 兩套的 `RDX` 都參與（Linux 傳第 3、Windows 傳第 2），但 `RCX` 在 Linux 傳第 4、在 Windows 傳第 1——**直接對換**。
- 返回值都是 `RAX`，這一點相同。

這對 ROP 的意義：**你在 Windows 找到的 Linux ROP writeup 裡的所有 `pop rdi` gadget，在 Windows 要換成 `pop rcx`**。把別人 Linux exploit 移植到 Windows 時，這是第一個要批量換掉的東西。

### 浮點 / SIMD 參數

前四個浮點參數走 `XMM0`–`XMM3`，而不是整數暫存器。

```
Windows x64 浮點傳參：
  第 1 個 float/double → XMM0
  第 2 個              → XMM1
  第 3 個              → XMM2
  第 4 個              → XMM3
```

**混合整數 + 浮點的「位置佔位」規則**：這是 Windows x64 的一個特殊設計。如果函式簽名是 `void f(int a, double b, int c)`，那麼：
- `a` → `RCX`（第 1 位整數）
- `b` → `XMM1`（第 2 位，浮點，但佔第 2 個 slot，所以 `RDX` 被跳過）
- `c` → `R8`（第 3 位整數，`XMM2` 被跳過）

換句話說，Windows x64 按**位置（slot）**分配，整數和浮點共用位置計數器。Linux 的規則不同（整數和浮點分開計）。

對 ROP 的實際影響：通常 API 呼叫是純整數參數，浮點問題不常見。但如果你要呼叫某些媒體 / 圖形 API，要注意。

## Shadow Space（最重要的差異）

這個機制在 System V AMD64 裡**完全不存在**。它是 Windows x64 最讓 Linux pwn 老手踩雷的地方。

### 什麼是 shadow space？

**呼叫者**在發出 `call` 指令之前，必須在 stack 上「預留」32 bytes（4 × 8 bytes），緊接在 `call` 的返回位址之上。這 32 bytes 叫做 **shadow space**（也叫 home space 或 spill space）。

```
呼叫前後的 stack 佈局（以 call 發生為分界）：

   高位址（呼叫者 stack 方向）
   ┌──────────────────────────────────────────┐
   │  ...呼叫者的 local vars...               │
   ├──────────────────────────────────────────┤
   │  arg6（若有）    ← [RSP+0x28] after call │
   ├──────────────────────────────────────────┤
   │  arg5（若有）    ← [RSP+0x20] after call │
   ├──────────────────────────────────────────┤  ─── shadow space 上緣
   │  R9 slot（shadow[3]）  [RSP+0x18] a.c.  │
   ├──────────────────────────────────────────┤
   │  R8 slot（shadow[2]）  [RSP+0x10] a.c.  │  32 bytes
   ├──────────────────────────────────────────┤  shadow space
   │  RDX slot（shadow[1]） [RSP+0x08] a.c.  │  呼叫者預留
   ├──────────────────────────────────────────┤
   │  RCX slot（shadow[0]） [RSP+0x00] a.c.  │ ─── shadow space 下緣
   ├──────────────────────────────────────────┤
   │  返回位址        ← call 壓入，RSP 在此   │
   ├──────────────────────────────────────────┤
   │  被呼叫者的 stack frame...               │
   低位址
```

（a.c. = after call，指 call 剛執行後的偏移）

被呼叫者可以把暫存器裡的參數 spill（倒出）到這 32 bytes，或者完全不用（取決於編譯器是否需要）。shadow space 就是**呼叫者給被呼叫者留的後門**，不管用不用都必須留。

### 為什麼存在 shadow space？

微軟的設計動機是**除錯器友好性**：被呼叫者的 prologue 可以把 `RCX/RDX/R8/R9` spill 到這裡，之後任何時刻除錯器都能從 stack 上重建出呼叫時的參數值，即使暫存器已被函式覆蓋。

相比 Linux 的 System V——Linux 完全靠除錯符號（DWARF 的 location expression）還原參數——Windows 的 shadow space 讓沒有符號的函式也可能保有參數的 stack 副本。代價是**每次呼叫都要在 stack 上多吃 32 bytes**。

### 真實反組譯：shadow space 的兩個現身位置

**位置 1：呼叫者分配（本機實跑，mingw GCC 14.2 -O0）**

原始 C：

```c
int leaf(int a, int b, int c, int d) { return a + b + c + d; }
int main(void) { return leaf(10, 20, 30, 40); }
```

`main` 的反組譯（`shadow_check.exe`，本機實跑）：

```asm
0000000140001456 <main>:
   140001456:  55                      push   rbp
   140001457:  48 89 e5                mov    rbp,rsp
   14000145a:  48 83 ec 20             sub    rsp,0x20        ← shadow space 32 bytes
   14000145e:  e8 fd 00 00 00          call   140001560 <__main>
   140001463:  41 b9 28 00 00 00       mov    r9d,0x28        ← arg4 = 40 (0x28)
   140001469:  41 b8 1e 00 00 00       mov    r8d,0x1e        ← arg3 = 30 (0x1e)
   14000146f:  ba 14 00 00 00          mov    edx,0x14        ← arg2 = 20 (0x14)
   140001474:  b9 0a 00 00 00          mov    ecx,0xa         ← arg1 = 10 (0xa)
   140001479:  e8 b2 ff ff ff          call   140001430 <leaf>
   14000147e:  48 83 c4 20             add    rsp,0x20        ← 釋放 shadow space
   140001482:  5d                      pop    rbp
   140001483:  c3                      ret
```

`sub rsp,0x20` 就是分配 32 bytes shadow space。`add rsp,0x20` 在 epilogue 回收。注意：`__main`（mingw 初始化函式）和 `leaf` **共用**這 32 bytes——shadow space 屬於「某次呼叫期間」，下一次呼叫覆寫就行。

**位置 2：被呼叫者把參數 spill 進 shadow space（本機實跑）**

原始 C（`shadow_demo.exe`，`add_four(int a,int b,int c,int d)`）：

```asm
0000000140001430 <add_four>:
   140001430:  55                      push   rbp
   140001431:  48 89 e5                mov    rbp,rsp
   140001434:  89 4d 10                mov    DWORD PTR [rbp+0x10],ecx   ← spill RCX→shadow[0]
   140001437:  89 55 18                mov    DWORD PTR [rbp+0x18],edx   ← spill RDX→shadow[1]
   14000143a:  44 89 45 20             mov    DWORD PTR [rbp+0x20],r8d   ← spill R8→shadow[2]
   14000143e:  44 89 4d 28             mov    DWORD PTR [rbp+0x28],r9d   ← spill R9→shadow[3]
   140001442:  8b 55 10                mov    edx,DWORD PTR [rbp+0x10]
   140001445:  8b 45 18                mov    eax,DWORD PTR [rbp+0x18]
   ...
   140001455:  c3                      ret
```

`[rbp+0x10]`~`[rbp+0x28]` 就是呼叫者預留的 shadow space 四個 slot。`push rbp` 之後 rbp = 呼叫前的 RSP，所以 `[rbp+0x08]` 是返回位址，`[rbp+0x10]` 起是 shadow。

**第 5、6 個參數（本機實跑，`main` 呼叫 `add_six(1,2,3,4,5,6)`）**：

```asm
   1400014df:  c7 44 24 28 06 00 00    mov    DWORD PTR [rsp+0x28],0x6   ← arg6=6 on stack
   1400014e7:  c7 44 24 20 05 00 00    mov    DWORD PTR [rsp+0x20],0x5   ← arg5=5 on stack
   1400014ef:  41 b9 04 00 00 00       mov    r9d,0x4
   1400014f5:  41 b8 03 00 00 00       mov    r8d,0x3
   1400014fb:  ba 02 00 00 00          mov    edx,0x2
   140001500:  b9 01 00 00 00          mov    ecx,0x1
   140001505:  e8 4c ff ff ff          call   140001456 <add_six>
```

`[rsp+0x20]` 是 shadow space 之後的第一個 stack slot（shadow 四格：+0x00、+0x08、+0x10、+0x18，call 後加返回位址就是 +0x08~+0x28）。arg5 在 `[rsp+0x20]`、arg6 在 `[rsp+0x28]`——這是 call 之前呼叫者視角的 RSP 偏移。

## Stack 對齊

### 規則

`call` 指令執行**之前**，RSP 必須 16-byte 對齊（`RSP % 16 == 0`）。

`call` 執行時壓入 8 bytes 返回位址，所以**被呼叫者進入時** `RSP % 16 == 8`。被呼叫者的 prologue（`push rbp`）再減 8，回到 0。

時間線：

```
程序起始（loader 保證 RSP 對齊 16）：
  RSP % 16 == 0

呼叫者做完 sub rsp, 0x20（shadow）：
  0x20 是 16 的倍數 → RSP 仍然 % 16 == 0

call 指令執行（壓入 8 bytes 返回位址）：
  RSP % 16 == 8       ← 被呼叫者進入時的狀態

被呼叫者 prologue: push rbp（-8）：
  RSP % 16 == 0

被呼叫者 prologue: sub rsp, N（N 必須是 16 的倍數）：
  RSP % 16 == 0       ← 保持對齊，才能用 MOVAPS 等指令
```

### 對齊不對會怎樣？

`MOVAPS`（Move Aligned Packed Single）、`MOVAPD`、`MOVDQA` 等 SSE/SSE2 指令要求記憶體位址 16-byte 對齊；存取 misaligned 位址觸發 `#GP`（General Protection Fault），Windows 把它轉成 `EXCEPTION_ACCESS_VIOLATION`（`0xC0000005`）。

Windows API 函式（`ntdll`、`kernel32`、`kernelbase`）的實作裡可能有這類 SSE 指令，**就算你根本沒傳浮點參數**。以 `RtlCopyMemory`（即 `memcpy`）為例，MSVC 的最佳化版本使用 `MOVAPS [rsp+XX], xmm0` 備份 XMM 暫存器——這一行在 RSP misaligned 時直接 crash。

對 ROP chain 的影響：

```
你的 ROP chain 裡每個 ret 跳轉都在操控 RSP（+8）。
當你的 chain 準備進入 API 時，
進入點之前 RSP 是否 16-byte 對齊——
這必須人工計算，不能假設。
```

最常用的修補方法：在 chain 裡插入一個 `ret` gadget（只有 `ret` 這一條指令，沒有 pop 任何東西）。`ret` 讓 RSP+8，把對齊從 8 mod 16 翻成 0 mod 16（或反之），讓對齊復位。這個 gadget 有時叫 **alignment gadget** 或 **stack alignment fix**。

## Caller / Callee-saved 暫存器差異

### 對照表

| 類別 | System V AMD64（Linux） | Microsoft x64（Windows） |
|---|---|---|
| **Caller-saved（volatile，callee 可以隨便改）** | RAX, RCX, RDX, RSI, RDI, R8–R11, XMM0–XMM7 | RAX, RCX, RDX, R8–R11, XMM0–XMM5 |
| **Callee-saved（non-volatile，callee 必須恢復）** | RBX, RBP, RSP, R12–R15 | RBX, RBP, **RSI, RDI**, R12–R15, **XMM6–XMM15** |

**最大的差異**（加粗）：

- **`RSI` 和 `RDI`** 在 Linux 是 caller-saved（傳參用完就行），在 Windows 是 callee-saved（函式必須保存並恢復）。
- **`XMM6–XMM15`** 在 Windows 是 callee-saved。Linux 的 XMM 全部都是 caller-saved。

### 對 ROP gadget 的影響

這個差異在 ROP 的影響：

1. **Windows 函式的 prologue 會 push RSI/RDI/RBX/R12–R15**（若用到）。這些 push 改動 RSP，讓你的 chain 計算 offset 時要考慮它們（尤其是你跳進函式中間某個 gadget 時）。
2. 當你控制某個 gadget 讀 RSI/RDI 的值，在 Linux 這兩個暫存器是 caller-saved（函式用完就改），在 Windows 這兩個是保護的——但這是對**合法函式**的約束，對 ROP gadget 本身沒有直接約束（gadget 不是完整函式）。
3. 你在 Windows 裡找到 `pop rdi; ret` 或 `pop rsi; ret`，這些 gadget 本身可以用來設值（任何暫存器都可以作為 gadget 的輸入），只是 `RDI`/`RSI` 的值不會成為傳給 API 的參數——它們在 API prologue 會被 save/restore。

## 底層機制：Stack Frame 全景圖

以下是 Windows x64 標準 stack frame 的完整結構（函式有 local vars、有 push callee-saved、有 shadow space）：

```
進入被呼叫者，prologue 完成後的 stack 全景：

高位址（呼叫者方向）
┌──────────────────────────────────────────────┐
│  arg7（若有）                  [rbp+0x38]    │ ← 超過 4 個的 stack 參數
│  arg6（若有）                  [rbp+0x30]    │
│  arg5（若有）                  [rbp+0x28]    │
├──────────────────────────────────────────────┤
│  shadow[3] ← R9 spill slot    [rbp+0x20]    │ ← shadow space（32 bytes）
│  shadow[2] ← R8 spill slot    [rbp+0x18]    │   呼叫者分配
│  shadow[1] ← RDX spill slot   [rbp+0x10]    │   被呼叫者可以 spill 或不用
│  shadow[0] ← RCX spill slot   [rbp+0x08]    │   (以上均呼叫前 RSP 視角 +0x00..+0x18)
├──────────────────────────────────────────────┤
│  返回位址                      [rbp+0x08]    │ ← call 壓入
├──────────────────────────────────────────────┤
│  saved RBP                     [rbp+0x00]    │ ← push rbp
├──────────────────────────────────────────────┤ ← RBP 指向這裡
│  saved RBX                     [rbp-0x08]    │ ← push rbx（若用到）
│  saved RSI                     [rbp-0x10]    │ ← push rsi（若用到）
│  saved RDI                     [rbp-0x18]    │ ← push rdi（若用到）
│  local vars                    ...           │
│  padding（to 16-byte align）   ...           │
├──────────────────────────────────────────────┤
│ ← RSP 指向這裡（epilogue 時往上回收）         │
低位址（stack 增長方向）
```

## 對 ROP Chain 建構的影響（回扣 Ch 23）

### 1. 湊「設參數」gadget 更難

x86（32 位元）傳參全靠 stack push，gadget 只要 `pop eax; ret` 這種通用 pop，拿到值之後 push 進 stack 就行。

x64 Windows 傳參靠暫存器（前四個），你要有**明確**的 `pop rcx; ret`、`pop rdx; ret`、`pop r8; ret`、`pop r9; ret`。這四個 gadget 的組合不一定都在同一個 DLL 裡，有時得跨 DLL 拼。

Encoding 對比（gadget 搜索時的 byte pattern）：

| gadget | encoding（x64） | 常見度 |
|---|---|---|
| `pop rax; ret` | `58 c3` | 極多 |
| `pop rcx; ret` | `59 c3` | 多 |
| `pop rdx; ret` | `5a c3` | 多 |
| `pop rbx; ret` | `5b c3` | 多 |
| `pop rsi; ret` | `5e c3` | 多 |
| `pop rdi; ret` | `5f c3` | 多 |
| `pop r8; ret`  | `41 58 c3` | 較少（REX.B prefix） |
| `pop r9; ret`  | `41 59 c3` | 較少 |
| `pop r10; ret` | `41 5a c3` | 較少 |

### 2. Shadow Space 要在 chain 裡手動留

你在 ROP chain 裡「呼叫」API 不是用真正的 `call` 指令（那需要可執行的 stack），而是把 API 位址放進 chain，讓最後的 `ret` 跳進去。但這樣的話，shadow space 沒有呼叫者分配——**被呼叫者在 prologue 存取 shadow 區域時，那裡是你 chain 剩下的 gadget 位址**。

解法是在 chain 裡、API 位址**之前**插一個 `sub rsp, 0x28; ret` 或類似 gadget：

```
ROP Chain 佈局示意（call VirtualProtect via ROP）：

   [RSP+0x00] → addr of: pop rcx; ret
   [RSP+0x08] → lpAddress（要改成 RWX 的頁起始）
   [RSP+0x10] → addr of: pop rdx; ret
   [RSP+0x18] → dwSize（頁大小）
   [RSP+0x20] → addr of: pop r8; ret
   [RSP+0x28] → PAGE_EXECUTE_READWRITE (0x40)
   [RSP+0x30] → addr of: pop r9; ret
   [RSP+0x38] → &oldProtect（可寫的記憶體位址）
   [RSP+0x40] → addr of: sub rsp, 0x28; ret   ← 手動分配 shadow+對齊
   [RSP+0x48] → VirtualProtect 位址            ← 進入時上方 0x28 bytes 是 shadow
   [RSP+0x50] → shellcode addr                  ← VirtualProtect ret 後跳這裡
```

如果跳過 shadow space 這步，`VirtualProtect` prologue 的 `mov [rsp+0x08], rcx`（spill 第一個參數）會把你的 gadget 位址覆蓋掉，chain 後續就爆。

### 3. 對齊計算

每次 `ret` 讓 RSP+8。要在 chain 裡 call API 之前確認 RSP 是 16-byte 對齊。

典型的計算流程：

```
1. 從 overflow 點算起，RSP 目前對齊狀態是什麼？
   （例如：overflow 覆蓋 saved RBP 和返回位址，RSP after overflow = X）

2. 每個 gadget「pop N; ret」讓 RSP += (N+1)*8
   （pop 一個暫存器 = RSP+8，ret = RSP+8，共 +16；但 gadget 本身被取用時 RSP 已在下一格）

3. 到 API 入口之前，RSP mod 16 必須 == 0

4. 若差 8，在 chain 某處插入一個 `ret` gadget（只有 ret）
```

### 4. 為什麼 x64 比 x86 難（總結）

| 面向 | x86（32 位元） | Windows x64 |
|---|---|---|
| **參數傳法** | 全 push 到 stack，gadget 通用 | 前 4 個要特定暫存器，gadget 要指名 RCX/RDX/R8/R9 |
| **gadget 稀缺度** | `pop eax; ret` 到處都是 | `pop r8; ret`（`41 58 c3`）稀有 |
| **shadow space** | 無 | 每次呼叫要留 32 bytes，ROP 要手動模擬 |
| **對齊要求** | 4-byte 對齊，寬容 | 16-byte 對齊，SSE 用錯就 crash |
| **位址空間** | 4GB，gadget 位址可能不含 null | 64-bit 虛擬位址高位常為 null，stack 溢位場景截斷問題更嚴重 |

## 可變參數（Variadic Functions）

`printf`、`wsprintfW` 等可變參數函式在 Windows x64 有額外規則：

- 固定參數仍然走 RCX/RDX/R8/R9；
- 可變部分從第 5 個 slot 開始，上 stack；
- **所有**浮點參數同時要放進對應的整數暫存器（`RCX/RDX/R8/R9`），因為 `va_arg` 從整數暫存器讀（Windows x64 的 variadic convention 要求這樣）；
- 這和 Linux System V 不同（Linux 有 `AL` 暫存器計數 XMM 用量，浮點和整數分開計）。

對 exploit 的影響：如果你要 ROP 呼叫 `printf` 做 format string chain（不常見但存在於某些題目），格式串放 RCX，第一個 `%s`/`%x` 的值要放 RDX，第二個放 R8，第三個放 R9，第四個以後 stack。

## 對比與取捨

| 面向 | System V AMD64 | Microsoft x64 |
|---|---|---|
| **整數參數暫存器** | RDI, RSI, RDX, RCX, R8, R9（6 個） | RCX, RDX, R8, R9（4 個） |
| **RSI/RDI 的角色** | 傳參（caller-saved） | callee-saved，跟參數無關 |
| **Shadow space** | 無 | 有，32 bytes，呼叫者強制分配 |
| **XMM 保護** | 全 caller-saved | XMM6–XMM15 是 callee-saved |
| **對齊保證** | call 前 RSP 對齊 16 | 相同 |
| **除錯友好性** | 參數在 frame 裡不保證 | shadow space 讓除錯器可還原參數 |
| **移植 Linux exploit** | 原生 | 要換暫存器、加 shadow、重算對齊 |

## 踩雷集錦

1. **「pop rdi; ret 就能設第一個參數」**：在 Linux 是對的，在 Windows 不行。Windows 第一個參數是 `RCX`，`RDI` 是 callee-saved 跟傳參無關。把 Linux exploit 移植到 Windows 時，`pop rdi` 要換 `pop rcx`，`pop rsi` 換 `pop rdx`，`pop rdx` 換 `pop r8`，`pop rcx` 換 `pop r9`——整個表格對換。

2. **「Shadow space 是被呼叫者分配的」**：錯，是**呼叫者**分配的。被呼叫者只是可以用那 32 bytes，但空間在 `call` 之前由呼叫者 `sub rsp, 0x20`（或更多）預留。在 ROP chain 裡你是呼叫者，你得負責。記憶法：`sub rsp, 0x20` 出現在 `call` 之**前**，那 0x20 就是 shadow。

3. **「對齊 16 bytes 只有浮點呼叫才需要」**：錯。Windows API 內部大量使用 `MOVAPS` 等 aligned SSE 指令，就算你在呼叫 `VirtualProtect`（純整數參數），對齊錯了一樣 crash。規則就是：進入任何 API 時 RSP 必須對齊 16。

4. **「sub rsp, 0x20 就夠了」**：有時需要 `sub rsp, 0x28`。如果在插入 shadow 之前 RSP mod 16 == 0，`sub rsp, 0x20`（0x20 是 16 的倍數）讓它保持 0；但如果這個 `sub rsp` 之後還有一個 `call`（call 壓 8 bytes），那 call 之前必須是對齊的，call 後就是 8。總之每條 chain 要個別計算，沒有萬用公式。

5. **「pop r8 到處都有」**：`pop r8` 的 encoding 是 `41 58`（REX.B prefix），`pop r9` 是 `41 59`。許多搜尋器在大型 DLL 裡能找到，但在小型 EXE 或被 strip 的模組裡就稀少。要驗證 gadget 位址是否含 null byte（例如 `0x00007FF8...` 高位的零），並視情況找備用 DLL（`ntdll`、`kernelbase` 通常夠大）。

## 進階：再往深一層

### 找 R8/R9 gadget 的替代策略

`pop r8; ret` 稀少時的備案：

1. **`xchg r8, rax; ret`** + 先用 `pop rax; ret` 設值——`xchg` 的 encoding 常見。
2. **`mov r8, rcx; ret`** 類的 move gadget——設好 RCX 後複製過來。
3. **`mov r8d, eax; ret`**（只設低 32 bit，對整數參數夠用，因為 MOV to 32-bit reg 自動零擴展 64-bit）。
4. 換目標 DLL：`ntdll.dll`、`kernelbase.dll`、`ucrtbase.dll`（mingw 程式）的 gadget 庫各有側重，跨庫搜。

### `__fastcall` 的歷史來源

32-bit 時代 Windows 有 `__fastcall`（`ECX`、`EDX` 傳前兩個參數，其餘 stack），這是 x64 慣例的歷史前身。x64 只有一套慣例（沒有修飾詞），所有函式都是同一套規則。你在 x86 disassembly 裡看到 `__fastcall`（`thiscall` 也類似，`this` 指標用 `ECX`），到了 x64 它自動就是標準慣例，不用特別標注。

### 用 `mona.py` 產生 chain 草稿

> **未實測，理論預期（需 WinDbg + mona.py 環境）**

```
!mona rop -m "ntdll,kernelbase" -n
```

mona 會為 `VirtualProtect`、`VirtualAlloc`、`WriteProcessMemory` 各產一條 ROP chain 草稿，自動挑 gadget、自動插 shadow space 和對齊 gadget。草稿出來之後**必須手動驗證**對齊計算是否正確（mona 的對齊計算在複雜 prologue 情境下有時不準）。用法詳見 Ch 23。

## 動手練習

用本機 mingw 確認 shadow space 分配，並計算一個假設 chain 的對齊：

**步驟 1**：複製以下 C，存成 `abi_demo.c`，編譯：

```c
#include <stdio.h>
#include <windows.h>

__attribute__((noinline)) int callee(int a, int b, int c, int d, int e, int f) {
    return a + b + c + d + e + f;
}

int main(void) {
    int r = callee(1, 2, 3, 4, 5, 6);
    printf("%d\n", r);
    return 0;
}
```

```bash
gcc -O0 -o abi_demo.exe abi_demo.c
objdump -d -M intel abi_demo.exe | grep -A 40 '<main>:'
```

**步驟 2**：在 `main` 的 disassembly 裡找：
- `sub rsp, 0xXX`：記下 XX，這就是 shadow space 大小（對只有四個參數的呼叫應該是 `0x20`）
- `mov DWORD PTR [rsp+0x20], ...` 和 `mov DWORD PTR [rsp+0x28], ...`：這是 arg5、arg6 的 stack 位置

**步驟 3**：算對齊。假設：
- overflow 後 saved return addr 被覆蓋，此時 RSP 指向你的 chain 開頭
- chain 開頭 = `pop rcx; ret`，RSP 此時 mod 16 = 0（假設）
- 走完 pop rcx（RSP+8）、ret（RSP+8）= RSP+16，mod 16 = 0
- 繼續 pop rdx、pop r8、pop r9，各 +16
- 最後一個 gadget `sub rsp, 0x28; ret`：ret 讓 RSP+8，mod 16 = 8；進入 API 時 RSP mod 16 = 8——需要在 chain 插 `ret` gadget 修正

目標：**在紙上或腳本裡把整條 chain 的 RSP 偏移追蹤一遍，確認進 API 之前 mod 16 == 0**。

## 本章重點整理

- Windows x64 前四個整數參數走 `RCX/RDX/R8/R9`（不是 Linux 的 `RDI/RSI/RDX/RCX`）；`RSI/RDI` 在 Windows 是 callee-saved，跟傳參無關；第五個起 stack。
- **Shadow space**（32 bytes）由呼叫者在 `call` 前以 `sub rsp, 0x20`（以上）預留；被呼叫者可以把暫存器 spill 進去；ROP chain 必須手動模擬這個步驟，否則 API 的 spill 操作會破壞 chain。
- **16-byte 對齊**是絕對要求，尤其是 API 內有 `MOVAPS`/`MOVAPD`——misalign 直接 access violation。在 chain 裡插 `ret` gadget 可以翻轉 8-byte 對齊。
- x64 ROP 比 x86 難的核心原因：暫存器傳參要特定 gadget（`pop rcx/rdx/r8/r9`，其中 `r8/r9` 稀有）、要模擬 shadow space、要維護 16-byte 對齊——三道關卡疊加。
