# Ch 2 — V8 架構全圖：Parser → Ignition → TurboFan → GC

> **目標**：把一段 JS 從原始碼到 CPU 執行，在 V8 裡走過的每個階段認清楚——Parser、Ignition（bytecode 直譯器）、Sparkplug/Maglev/TurboFan（三層 JIT）、GC。理解「V8 為了快而分層」這件事**本身就是攻擊面的地圖**：知道每個 bug 大類住在哪一層，你才知道 Part 4 的 type confusion 為什麼幾乎都在 TurboFan/Maglev。

> **環境**：V8 15.3.0（commit `ab2cad06`），`out/x64.release`。下面所有 bytecode 與 tiering 輸出都是在這顆 d8 上真跑出來的。

## 為什麼需要這個？

你在 `binary_exploitation` 打的 C 程式，從原始碼到執行只有一步：編譯器把它變成機器碼，執行時就是那份機器碼。**V8 不是這樣**——它同一段 JS 會用**好幾種不同的方式**跑：一開始用直譯器慢慢跑、發現這函式很熱之後偷偷叫優化編譯器把它重編成快速機器碼、萬一優化時押的賭注錯了再退回直譯器。

這種「多層執行、動態切換」的設計是 V8 快的原因，也是它**最肥的洞的來源**。優化編譯器為了快，會對你的 JS 做一堆「假設」；只要你能讓某個假設在它背後偷偷失效，就是一個 type confusion。你不先搞懂這條管線，看 Part 4 的漏洞會像看天書——不知道那個 bug 到底發生在哪一層、為什麼那層會犯這種錯。

這章是全課的骨架圖。之後每學一個漏洞，你都要能指著這張圖說「它在這裡」。

## 先建立直覺：一個會自我觀察、然後找槍手的直譯器

想像你在餐廳當服務生（直譯器 Ignition）。有道菜（某個 function）你今晚已經送了一萬次，你發現每次都一模一樣。與其每次都照著食譜一步步做，你去請一個廚神（優化編譯器 TurboFan）幫你把這道菜「預先做成一鍵出餐」——但廚神有個條件：他**賭**這道菜的食材永遠是牛肉。他把「檢查是不是牛肉」這步省掉，直接照牛肉的做法一鍵完成，所以超快。

問題來了：如果哪天客人（攻擊者）偷偷把食材換成豆腐，而廚神那份「一鍵出餐」還在照牛肉做——他會拿切牛肉的力道去切豆腐，**廚房就爆炸了**（type confusion → 記憶體破壞）。

```
   源碼  ──► Parser ──► AST ──► Ignition（直譯器，邊跑邊記錄「食材都是什麼」）
                                    │
                     函式變熱 ───────┤ 收集到的「食材紀錄」= feedback
                                    ▼
                          Sparkplug / Maglev / TurboFan
                          （優化編譯器：基於 feedback「賭」食材不變，
                           省掉檢查，編成飛快的機器碼）
                                    │
                     賭錯了（食材真的變了）───► Deopt：退回 Ignition 重跑
```

整門課後半在做的事，一句話：**想辦法讓「食材」在廚神背後悄悄改變，而他那份省了檢查的機器碼還在照舊食材做。**

## 這條管線的每一站

### 站 1：Parser → AST

V8 拿到 JS 原始碼，先做**詞法/語法分析**，產生抽象語法樹（AST）。V8 這裡有個效能招數叫 **lazy parsing（惰性解析）**：對還沒被呼叫的 function，只做輕量的 pre-parse（確認語法沒錯、記下它的範圍），等真的被呼叫才完整解析。這對利用大多不是主戰場，但偶爾有 parser 的歷史 bug（見 Ch 25）。

### 站 2：Ignition — bytecode 直譯器

AST 不直接執行，先被編成 **bytecode**（位元組碼），由 **Ignition** 這個直譯器一條一條跑。看實際的 bytecode——一個最簡單的加法函式：

```
$ d8 --print-bytecode --print-bytecode-filter=add -e 'function add(a,b){return a+b;} add(1,2); add(3,4);'
[generated bytecode for function: add (0x1e780101e2b5 <SharedFunctionInfo add>)]
Bytecode length: 6
Parameter count 3
Register count 0
Frame size 0
         0x116601000110 @    0 : 0b 04             Ldar a1
         0x116601000112 @    2 : 42 03 00          Add a0, EmbeddedFeedback[0]
         0x116601000115 @    5 : b9                Return
Constant pool (size = 0)
```

逐行讀（這是你這門課要習慣的事）：

- **`Parameter count 3`**：`add` 只宣告 `(a, b)` 兩個參數，為什麼是 3？因為隱藏的 `this`（receiver）也算一個。這種「隱藏 receiver」之後看 bytecode 常遇到。
- **`Ldar a1`**：Load Accumulator from Register——把參數 `b`（`a1`）載入累加器。Ignition 是**累加器架構**，一個特殊的 accumulator 暫存中間值。
- **`Add a0, EmbeddedFeedback[0]`**：把 `a`（`a0`）加到累加器。關鍵是後面的 **`EmbeddedFeedback[0]`**——這條 `Add` 綁著一個 **feedback slot**。Ignition 每次執行這條加法，會把「這次 `a`、`b` 是什麼型別」記到這個 slot 裡。這就是前面比喻的「食材紀錄」。
- **`Return`**：回傳累加器的值。

**feedback 是整個攻擊模型的核心**。Ignition 邊跑邊填的這份 feedback（存在一個叫 **feedback vector** 的結構裡），就是之後 TurboFan「押賭注」的依據。攻擊者操弄 feedback 讓優化器產生錯誤假設，是 type confusion 的常見起手式（Part 4 反覆用到）。

### 站 3：三層 JIT — Sparkplug、Maglev、TurboFan

一個 function 被呼叫夠多次（變「熱」），V8 就不甘心一直用直譯器跑它，開始往上「升級」（tiering up）。現代 V8（15.3）有**多個層級**，速度與編譯成本各不同：

| Tier | 名字 | 做什麼 | 特性 |
|---|---|---|---|
| 0 | **Ignition** | bytecode 直譯 | 啟動快、跑得慢、收集 feedback |
| 1 | **Sparkplug** | baseline JIT | 把 bytecode 幾乎 1:1 翻成機器碼，**不做優化**、不押賭注。純粹省掉直譯 overhead |
| 2 | **Maglev** | mid-tier 優化 JIT | 較新（2023+）。做**中等程度**的優化，基於 feedback 押賭注，但編譯比 TurboFan 快 |
| 3 | **TurboFan** | top-tier 優化 JIT | 最激進的優化，sea-of-nodes IR。押最多賭注、跑最快、編最慢 |

親眼看 tiering 發生——跑一個熱迴圈並開 `--trace-opt`：

```
$ d8 --trace-opt hot.js     # hot.js 裡 add() 被呼叫十萬次
[marking 0x..<JSFunction add> for optimization to MAGLEV, ConcurrencyMode::kConcurrent, reason: hot and stable]
[compiling method 0x..<JSFunction add> (target MAGLEV), mode: ConcurrencyMode::kConcurrent]
[completed compiling 0x..<JSFunction add> (target MAGLEV) - took 0.000, 0.231, 0.001 ms]
[compiling method 0x..<JSFunction> (target TURBOFAN_JS) OSR, mode: ConcurrencyMode::kConcurrent]
```

看到了嗎？`add` 先被標記升級到 **MAGLEV**（原因：`hot and stable`——夠熱、型別夠穩定），編完之後迴圈本身又被升到 **TURBOFAN_JS**。而且注意 `ConcurrencyMode::kConcurrent`：**優化是在背景執行緒併發做的**，不擋主執行緒。這個「併發優化」的設計本身就是一類攻擊面的來源——主執行緒可能在優化器背景編譯的空檔改變了世界（Part 4 的 side-effect 類漏洞）。

> **踩雷**：很多 2019、2020 的 V8 exploit writeup 只講「Ignition → TurboFan 兩層」。那是舊架構。現在中間多了 Sparkplug 和 Maglev，你在 `--trace-opt` 看到 `MAGLEV` 不要驚慌，那是正常的中間層。Maglev 自己也會有 type confusion（和 TurboFan 同源的病），Part 4 會提。

### 站 4：Deoptimization — 賭錯了怎麼辦

優化編譯器押的賭注（「這變數一定是整數」「這陣列的 map 不變」）萬一在執行時被打破，機器碼裡埋的檢查會觸發 **deoptimization（deopt）**：丟掉這份優化過的機器碼，把執行狀態「翻譯」回 Ignition 的 bytecode 層，繼續用直譯器慢慢跑。

deopt 是**正常且必要**的機制——它是優化器敢於押賭注的安全網。但它也是攻擊面：如果攻擊者能製造一個「優化器以為不可能、所以沒放 deopt 檢查」的狀態，那份機器碼就會帶著錯誤假設繼續執行，不 deopt——這正是型別混淆的本質。[Ch 12](./12-speculation-deopt.md) 專章拆解 speculation 與 deopt。

### 站 5：GC — 記憶體從哪來、往哪去

所有 JS 物件都活在 V8 的**堆（heap）**上，由 **GC（垃圾回收器，代號 Orinoco）**管理生死。它是分代式的：新物件在 young generation（Scavenger 快速回收），活得久的晉升到 old generation。GC 對利用的影響很實際：

- 物件在記憶體裡的**相對佈局**受 GC 影響——你 spray 一堆物件想讓它們相鄰，得懂 GC 怎麼擺放。
- GC 會**搬動**物件（compaction），所以你不能假設一個物件的位址永遠不變。
- pointer compression（下一章）和 GC 的設計緊密耦合。

[Ch 13](./13-garbage-collection.md) 會深入 GC 對利用的影響。

## 攻擊面地圖：每一層住著什麼 bug

把上面五站攤平，標出各層的攻擊面密度——這是你這門課的「礦脈圖」：

```
   Parser        ░░ 稀少（偶有語法邊界 bug，Ch 25 帶過）
   Ignition      ░░ 較少（bytecode handler bug 罕見）
   Builtins      ▓▓ 中（Torque/CSA 寫的內建函式，Array/RegExp/JSON，Ch 21/25）
   ┌───────────────────────────────────────────────┐
   │ Maglev       ████ 高                            │  ← Part 4
   │ TurboFan     ██████ 最高（type confusion 主礦） │  ← Part 4 重頭戲
   └───────────────────────────────────────────────┘
   GC / 物件模型  ▓▓▓ 中（佈局、UAF-ish、Ch 8/13）
```

為什麼 TurboFan/Maglev 是主礦？因為它們是**唯一「為了快而主動省略安全檢查」的地方**。直譯器每次都乖乖檢查型別，慢但安全；優化器賭型別不變、省掉檢查，快但只要賭注被騙就爆。攻擊面的密度和「省了多少檢查」成正比。這也解釋了本課的重心分配：Part 4 花 7 章在 TurboFan 一類的漏洞上。

## 容器：Isolate、Context、Heap

最後補三個你會一直看到的名詞，先建立粗略印象（細節散在後面）：

- **Isolate**：一個獨立的 V8 執行個體，有自己的堆、自己的 GC。一個 Isolate 同一時間只被一個執行緒用。你在 `%DebugPrint` 看到的位址都是相對某個 isolate 的。
- **Context**：一個 JS 執行環境（大致對應一個 global object / 一個網頁的 realm）。一個 Isolate 裡可以有多個 Context。
- **Heap**：Isolate 的物件堆，分 young/old space、read-only space、code space 等。pointer compression（Ch 4）就是在這個堆上做的。

CTF 的 d8 通常一個 Isolate 一個 Context，單純；真實 Chrome 一個 renderer 進程可能有多個。現在知道這幾個字代表什麼容器即可。

## 對比：V8 的多層執行 vs 傳統 AOT 編譯

| 面向 | 傳統 C（AOT 編譯） | V8（多層 JIT） |
|---|---|---|
| 原始碼到執行 | 一次編成機器碼，跑那份 | 直譯 → 熱了才編 → 可退回 |
| 對輸入的假設 | 編譯期固定 | 執行期基於 feedback 動態押注 |
| 出錯的代價 | 編譯期就定型 | 賭錯 → deopt（正常）或 type confusion（漏洞） |
| 攻擊面 | 記憶體破壞在你的邏輯裡 | **額外多了「優化器的錯誤假設」這整類** |

這張表點出 V8 pwn 和 userland pwn 最根本的差異：你不只是在找「程式邏輯的記憶體 bug」，你是在找「優化編譯器對 JS 語意的錯誤推理」。這是一個全新的、更抽象的 bug 類別，也是為什麼 V8 pwn 被放在天梯頂端。

## 踩雷集錦

1. **以為 V8 只有「Ignition → TurboFan」兩層**：舊 writeup 的說法。現代 V8 是四層階梯（Ignition → Sparkplug → Maglev → TurboFan），你在 `--trace-opt` 看到 MAGLEV 是正常的。
2. **把 feedback 當成無關緊要的效能細節**：feedback vector 是 type confusion 的命脈。優化器信任 feedback，攻擊者操弄 feedback 誤導優化器——不懂 feedback 就不懂 Part 4。
3. **以為 deopt 是「錯誤」**：deopt 是正常機制、是優化器的安全網。漏洞不是「發生了 deopt」，而是「該 deopt 卻沒 deopt」——優化器以為某狀態不可能而沒放檢查。
4. **忽略優化是併發的**：`ConcurrencyMode::kConcurrent` 意味主執行緒和背景優化執行緒並行，中間的時間窗是一類 side-effect 漏洞的溫床。
5. **假設物件位址固定**：GC 會搬物件（compaction）。exploit 裡要即時 `%DebugPrint` 或 leak 當下的位址，不能寫死。

## 進階：再往深一層

- **Torque 與 CodeStubAssembler（CSA）**：V8 的內建函式（`Array.prototype.push`、`JSON.parse`…）很多是用一種叫 **Torque** 的 DSL 或更底層的 CSA 寫的，會編成 bytecode handler 或 builtin。這些內建的實作 bug 是 Builtins 攻擊面（Ch 21/25）。想深入可讀 V8 的 `src/builtins/*.tq`。
- **OSR（On-Stack Replacement）**：上面 trace 裡的 `OSR` 是指「一個正在執行的長迴圈，中途被換成優化版本」——不用等函式下次被呼叫。這對「一個大迴圈的 exploit trigger」很關鍵，因為它決定你的觸發碼何時被優化。
- **`--trace-turbo` 與 turbolizer**：想看 TurboFan 內部把你的函式優化成什麼樣的 sea-of-nodes IR，`--trace-turbo` 產生 JSON，用 `tools/turbolizer` 圖形化。[Ch 10](./10-turbofan-overview.md) 會實際用它看一個 bug 怎麼在 IR 上長出來。
- **Maglev vs TurboFan 的取捨**：Maglev 是為了填補「Sparkplug 太笨、TurboFan 太貴」的中間地帶而生。理解它的存在動機（啟動延遲 vs 峰值效能）能幫你判斷一個 bug 在哪一層更容易觸發。

## 動手練習

1. 用 `--print-bytecode` 看幾個不同函式的 bytecode：一個有 if、一個有 for 迴圈、一個呼叫別的函式。觀察 `Ldar`/`Star`/`Add`/`JumpIfFalse`/`CallProperty` 這些 opcode，試著把 bytecode「翻譯」回原始邏輯。不用全懂，建立「bytecode 長怎樣」的手感。
2. 寫一個熱迴圈跑十萬次，用 `--trace-opt` 觀察你的函式升到哪一層。改變迴圈內容（讓型別忽而整數忽而字串），看 `--trace-opt` 有沒有出現 deopt（`--trace-deopt` 更清楚）。你剛剛就親手觸發了一次「賭注被打破」。
3. 不看本章，畫出從源碼到執行的五站管線，並在每一站標註「這裡的攻擊面密度高還是低、為什麼」。

## 本章重點整理

- V8 用**多層執行**（Ignition 直譯 → Sparkplug/Maglev/TurboFan 逐層優化）換速度；每層省掉的檢查越多，攻擊面越肥。
- **feedback vector** 是優化器押賭注的依據，也是 type confusion 的命脈：操弄 feedback → 誤導優化器。
- **TurboFan/Maglev 是主礦脈**，因為它們是唯一「主動省略安全檢查」的層；Part 4 的重心在此。
- **deopt** 是安全網不是 bug；漏洞是「該 deopt 卻沒 deopt」。
- GC 會搬動物件、決定佈局，影響 spray 與位址穩定性。
