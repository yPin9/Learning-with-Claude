# Ch 9 — Parser 與 Ignition bytecode

> **目標**：把管線的最前兩站——Parser 與 Ignition——從 [Ch 2](./02-v8-architecture.md) 的「一句話帶過」升級成「能逐格讀」。這章結束你要能：解釋 lazy parsing 為什麼存在、看懂一段 bytecode 的每個 opcode、指出 accumulator 和 register 各自的角色，尤其是把 **feedback vector** 從一個名詞變成一個你能在 `%DebugPrint` 裡看到欄位的具體結構。因為 feedback 是後面 TurboFan「押賭注」的唯一依據，也就是 Part 4 type confusion 的第一張骨牌。

> **環境**：V8 15.3.0（candidate、commit `ab2cad06`）、`~/v8build/v8/out/x64.release/d8`（`object_print`/`disassembler`/`sandbox`/`pointer_compression` 全開）。本章所有 bytecode 與 `%DebugPrint` 輸出都是在這顆 d8 上真跑出來的，位址（`0x...`）每次跑會變，看結構不看數字。

## 為什麼需要這個？

[Ch 2](./02-v8-architecture.md) 給了你管線的鳥瞰圖，也貼過一段 `add` 的 bytecode。但那只是讓你「看過長相」。真正打 V8 時你會反覆做兩件事：

1. **讀 bytecode**，確認你的觸發碼被編成什麼、哪條指令綁著哪個 feedback slot。
2. **讀 feedback vector**，確認你成功把某個 slot 從「以為是整數」污染成「以為是別的東西」——這是很多 type confusion 的第一步。

Ignition 這一層本身**極少有可直接利用的 bug**（bytecode handler 是 V8 最保守、最少改動的部分）。它在攻擊模型裡的地位不是「靶」，而是「情報來源」：它邊跑邊記錄的型別紀錄（feedback），就是優化器將來要信任的那份資料。你在這一層做的事，是**佈置**——讓優化器將來讀到你想讓它讀到的假設。所以這章不教你怎麼打 Ignition，教你怎麼**讀懂 Ignition 在替優化器記什麼帳**。

## 先建立直覺：一個邊做菜邊寫食材筆記的直譯器

回到 [Ch 2](./02-v8-architecture.md) 的餐廳比喻。Ignition 是那個親手做菜的服務生，慢但穩。但它做菜時多做一件事：**每上一道菜，就在旁邊的筆記本上記一筆「這次用的食材是什麼」**。

這本筆記本就是 **feedback vector**。筆記本上有固定數量的格子（slot），每個格子綁定原始碼裡某一個「會因型別而異」的操作——一次加法、一次屬性讀取、一次函式呼叫。服務生每執行到那個操作，就更新對應格子：「這次加法是兩個整數」「這次讀 `.x` 的物件長這個樣（這個 Map）」。

```
   源碼: function add(a,b){ return a+b; }
                              │
                              ▼ Ignition 執行 Add 這條 bytecode
   ┌──────────────────────────────────────────────┐
   │ feedback vector（筆記本）                     │
   │  slot[0]  (Add 的紀錄): "看過的都是 SMI"      │  ← 廚神將來讀這格決定賭什麼
   │  slot[1]  ...                                 │
   └──────────────────────────────────────────────┘
                              │
              函式變熱 ───────┤ 廚神(TurboFan) 讀筆記本，賭「永遠是 SMI」
                              ▼
                     省掉型別檢查的快速機器碼
```

整個攻擊模型的種子就在這：**如果你能讓筆記本上寫的和實際端上桌的不一致，廚神就會照錯的筆記做菜**。這章教你讀懂這本筆記本。

## 站 1：Parser — 而且它很懶

V8 拿到 JS 原始碼，先做詞法/語法分析產生 AST（抽象語法樹）。這部分的機制和你在 `compilers/compiler_frontend` 學的 lexer/parser 一樣，不重複。V8 這裡真正值得講的是一個效能招數：**lazy parsing（惰性解析）**。

### eager parse vs pre-parse

一個網頁動輒載入幾 MB 的 JS，但頁面初始化時真正會跑到的函式可能只有一小部分。V8 不想在啟動時就把每個函式都完整解析、編成 bytecode——那太慢。所以它對函式分兩種待遇：

- **eager parse（完整解析）**：立刻被呼叫的、或在頂層作用域的程式碼，完整解析、產生 AST、編成 bytecode。
- **pre-parse（預解析）**：包在函式裡、還沒被呼叫的內層函式，只做輕量掃描——確認**語法沒錯**、記下它的**位元組範圍**（從哪個字元到哪個字元）、記下它引用了外層哪些變數。**不產生完整 AST，不編 bytecode**。等它第一次真的被呼叫，才「回頭」完整解析。

```
function outer() {
  function neverCalled(a, b, c) { return a*b + c - 999; }  // ← 只被 pre-parse
  return 1;                                                 //   語法檢查過，但沒編 bytecode
}
outer();   // neverCalled 從頭到尾沒被呼叫 → 永遠停在 pre-parse 狀態
```

`neverCalled` 只被掃過一眼確認「語法合法」，V8 沒替它產生 bytecode。這省下的啟動時間在真實網頁上很可觀。

### 為什麼利用者要在意 parser

三個理由，密度由低到高：

1. **一般情況下 parser 不是主戰場**。它太成熟、太保守，直接的 memory bug 罕見。
2. **但 lazy parsing 有過歷史 bug**。「pre-parse 時漏判某個語法邊界、eager parse 時才發現不一致」這種狀態機錯誤，歷史上出過（例如某些 `arguments`/箭頭函式/解構賦值的邊界）。這類在 [Ch 25](./25-regexp-json-builtins.md) 帶過。
3. **pre-parse / eager 的切換會影響你的觸發碼何時被編**。如果你的 exploit 依賴某個函式在特定時機被優化，你得知道它什麼時候才第一次被完整編譯。這在寫穩定 trigger 時偶爾咬人。

現在你只要記住：**parser 是懶的，函式在被呼叫前只是「語法檢查過的一段字元範圍」，還沒有 bytecode**。這也解釋了為什麼你 `%DebugPrint` 一個剛定義、還沒呼叫的函式，看到的 `bytecode` 欄位可能還沒實體化。

## 站 2：Ignition — accumulator 架構的 bytecode 直譯器

AST 不直接執行，先被編成 **bytecode**，交給 **Ignition** 這個直譯器一條一條跑。看最簡單的例子——一個加法函式（真跑輸出）：

```
$ d8 --print-bytecode --print-bytecode-filter=add \
     -e 'function add(a,b){return a+b;} add(1,2); add(3,4);'

[generated bytecode for function: add (0x02f70101e2b5 <SharedFunctionInfo add>)]
Bytecode length: 6
Parameter count 3
Register count 0
Frame size 0
         0x237f01000110 @    0 : 0b 04             Ldar a1
         0x237f01000112 @    2 : 42 03 00          Add a0, EmbeddedFeedback[0]
         0x237f01000115 @    5 : b9                Return
Constant pool (size = 0)
Handler Table (size = 0)
Source Position Table (size = 0)
```

逐格拆解，這是你這門課要練成反射的技能：

### header 三行

- **`Parameter count 3`**：`add` 只宣告 `(a, b)`，為什麼是 3？因為隱藏的 `this`（receiver）也佔一個參數槽。所以參數暫存器編號從 receiver 算起：`a0` = 第一個顯式參數 `a`，`a1` = `b`。**「參數數量 = 顯式參數 + 1」是常態**，看 bytecode 常遇到。
- **`Register count 0`**：這函式不需要額外的本地暫存器（register）。複雜函式會 > 0，見下面的 `loopSum`。
- **`Frame size 0`**：這函式的堆疊 frame 大小（register count × 指標大小），這裡不需要 register 所以是 0。

### accumulator 是什麼

Ignition 是**累加器架構（accumulator machine）**。不像 x86 那種「任意暫存器對任意暫存器」的設計，Ignition 有**一個特殊的、隱形的暫存器叫 accumulator**，幾乎每條算術/邏輯指令都隱含地拿它當「其中一個運算元 + 結果的去處」。這讓 bytecode 更短（少編碼一個運算元）。

opcode 名字裡的 `a`（accumulator）和 `r`（register）就是這個意思：

- **`Ldar a1`** = **Ld**（Load）**a**（into Accumulator）**r**（from Register）`a1`：把參數 `b`（`a1`）**載入 accumulator**。
- **`Add a0, EmbeddedFeedback[0]`**：把 `a`（`a0`）**加到 accumulator**（accumulator 現在是 `b`，加上 `a` 變成 `a+b`），結果留在 accumulator。注意 `Add` 只寫了一個運算元 `a0`——另一個運算元（accumulator）是隱含的。
- **`Return`**：回傳 accumulator 的值。

一句話：**accumulator 是「當前手上正在算的那個值」，register（`r0`、`r1`、`a0`…）是「暫存到旁邊的值」**。`Ldar` 把 register 搬進手上，`Star`（Store Accumulator to Register）把手上的搬到旁邊。

### 那個 `EmbeddedFeedback[0]` 才是重點

`Add a0, EmbeddedFeedback[0]` 後面那個 **`EmbeddedFeedback[0]`** 就是本章的核心。這條 `Add` 綁定了 **feedback vector 的第 0 號 slot**。Ignition 每次執行這條加法，就更新 slot[0]：「這次 `a`、`b` 是什麼型別」。

**為什麼加法需要記型別？** 因為 JS 的 `+` 是多型的：`1+2` 是整數加法、`1.5+2.5` 是浮點加法、`"a"+"b"` 是字串串接、`{}+[]` 是一坨型別轉換惡夢。Ignition 每次都重新判斷（慢但安全）。但它把「歷來看過的型別」記進 slot[0]，好讓將來的優化器可以賭「這裡永遠是整數加法」而省掉判斷。

**這就是 [Ch 2](./02-v8-architecture.md) 比喻裡「食材紀錄」的實體**。記住這個字：**feedback slot**。Part 4 你會反覆想辦法污染它。

## 讀一段更真實的 bytecode：帶迴圈與屬性讀取

`add` 太簡單。看一個有迴圈、有陣列存取、有屬性讀取的函式（真跑輸出）：

```
$ d8 --print-bytecode --print-bytecode-filter=loopSum -e \
  'function loopSum(arr){let s=0;for(let i=0;i<arr.length;i++){s+=arr[i];}return s;} loopSum([1,2,3]);'

[generated bytecode for function: loopSum]
Parameter count 2
Register count 3
Frame size 24
   @    0 : 0c                LdaZero
   @    1 : d5                Star0
   @    2 : 0c                LdaZero
   @    3 : d4                Star1
   @    4 : 33 03 00 00       GetNamedProperty a0, [0:"length"], FBV[0]
   @    8 : 79 f8 00          TestLessThan r1, EmbeddedFeedback[0]
   @   11 : a8 17             JumpIfFalse [23] (@ 34)
   @   13 : 0b f8             Ldar r1
   @   15 : 35 03 02          GetKeyedProperty a0, FBV[2]
   @   18 : 42 f9 00          Add r0, EmbeddedFeedback[0]
   @   21 : 1b f9 f7          Mov r0, r2
   @   24 : d5                Star0
   @   25 : 0b f8             Ldar r1
   @   27 : 5b 04             Inc FBV[4]
   @   29 : d4                Star1
   @   30 : 97 1a 00 05       JumpLoop [26], [0], FBV[5] (@ 4)
   @   34 : 0b f9             Ldar r0
   @   36 : b9                Return
Constant pool (size = 1)
   0: <String[6]: #length>
```

慢慢讀，把它翻回原始邏輯：

- **`LdaZero` / `Star0`**：把 0 載入 accumulator、存到 `r0`。`r0` 就是本地變數 `s`（`let s=0`）。
- **`LdaZero` / `Star1`**：`r1` 就是 `i`（`let i=0`）。
- **`GetNamedProperty a0, [0:"length"], FBV[0]`**：讀 `arr.length`（`arr` = `a0`，屬性名 `"length"` 在常數池索引 0）。**這條也綁 feedback**——`FBV[0]` 記錄「`arr` 是什麼 Map、`.length` 這次怎麼讀到的」。屬性讀取的 feedback 記的是 **Map（隱藏類別）**，這就是 [Ch 5](./05-map-hidden-class.md) 的 inline cache，下面詳談。
- **`TestLessThan r1, ...`**：比較 `i < (accumulator=length)`。
- **`JumpIfFalse [23]`**：迴圈條件不成立就跳出到 `@34`。
- **`GetKeyedProperty a0, FBV[2]`**：讀 `arr[i]`（索引在 accumulator）。**keyed（用變數當索引）的存取也綁 feedback**——`FBV[2]` 記「`arr` 的 elements kind 是什麼」（[Ch 7](./07-jsarray-elements-kind.md) 的 `PACKED_SMI_ELEMENTS` 之類）。**這個 feedback 是 Part 4 陣列 type confusion 的關鍵**：優化器賭「elements kind 不變」而省掉檢查，你想辦法在背後變它。
- **`Add r0, ...` / `Star0`**：`s += arr[i]`，結果存回 `r0`。
- **`Inc FBV[4]` / `Star1`**：`i++`。連 `Inc` 都綁 feedback（記「`i` 是不是一直是小整數、有沒有溢位」）。
- **`JumpLoop [26], [0], FBV[5]`**：跳回迴圈開頭 `@4`。`JumpLoop` 綁 `FBV[5]` 是給 **OSR（On-Stack Replacement）**用的——[Ch 2](./02-v8-architecture.md) 提過，一個長迴圈可以在執行到一半時被換成優化版本，這個 slot 記錄迴圈跑了多少圈、該不該觸發 OSR。

看到重點沒有？**幾乎每一條「型別會影響行為」的指令都綁著一個 feedback slot**：`Add`、`GetNamedProperty`、`GetKeyedProperty`、`Inc`、`TestLessThan`、`JumpLoop`。這本筆記本記得非常細。優化器將來就是拿這整本筆記去押賭注。

## feedback vector 到底長什麼樣

前面一直說「筆記本」，現在把它 dump 出來看實體。用 `%DebugPrint`。有個坑要先講：**feedback vector 不是函式一定義就存在的**。V8 為了省記憶體，函式剛開始只有一個空的 `ClosureFeedbackCellArray`；要等函式被呼叫夠多次、或你手動 `%PrepareFunctionForOptimization`，才真的配置 feedback vector。這解釋了為什麼直接 `%DebugPrint` 一個新函式，會看到：

```
 - feedback vector: No feedback vector, but we have a closure feedback cell array
```

先 `%PrepareFunctionForOptimization(add)`（這儀式的完整意義留到 [Ch 12](./12-speculation-deopt.md)），再看（真跑輸出，節錄）：

```
$ d8 --allow-natives-syntax -e \
  'function add(a,b){return a+b;} %PrepareFunctionForOptimization(add); add(1,2); add(3,4); %DebugPrint(add);'

DebugPrint: 0x34e80101e385: [Function] in OldSpace
 - map: 0x34e8010050fd <Map[32](HOLEY_ELEMENTS)> [FastProperties]
 - shared_info: 0x34e80101e2f9 <SharedFunctionInfo add>
 - builtin: InterpreterEntryTrampoline          ← 目前用直譯器入口（還沒優化）
 - formal_parameter_count: 3
 - interpreted
 - bytecode: 0x36bd010000fd <BytecodeArray[6]>   ← bytecode 實體化了
 - source code: (a, b) { return a + b; }
 - feedback vector: 0x34e80101e439: [FeedbackVector] in OldSpace   ← 有 FV 了
 - map: 0x34e800000895 <Map(FEEDBACK_VECTOR_TYPE)>
 - length: 0 (empty)
```

幾個要你認得的欄位：

- **`shared_info: <SharedFunctionInfo add>`**：**SharedFunctionInfo（SFI）**是「同一個函式定義」共享的部分（bytecode、原始碼範圍、參數數量）。一個函式定義所有 closure 共用一份 SFI。
- **`bytecode: <BytecodeArray[6]>`**：Ignition 要跑的 bytecode 陣列，長度 6 對應前面 `Bytecode length: 6`。
- **`builtin: InterpreterEntryTrampoline`**：這個 closure 目前的執行入口是**直譯器入口**——代表它還沒被優化。等它升到 TurboFan，這欄會變成指向優化過的機器碼。**這一欄是你判斷「函式優化了沒」的其中一個線索**。
- **`feedback vector: <FeedbackVector>`**：筆記本本體。這裡 `length: 0` 是因為 `add` 這種簡單函式的 slot 在這個版本被收斂了；換成上面 `loopSum` 那種有多個型別敏感操作的函式，FV 會有多個 slot，每個 slot 存著「這個操作看過的型別集合 + 相關的 Map 指標」。

### feedback 記的三種狀態（型別金字塔）

feedback 每個 slot 有個「見多識廣程度」的狀態，這決定優化器敢不敢賭：

```
   uninitialized  →  尚未執行過，什麼都沒看過
        │
        ▼
   monomorphic    →  只看過「一種」Map / 型別  ← 優化器最愛，賭得最爽
        │  看到第二種
        ▼
   polymorphic    →  看過少數幾種（通常 ≤4）    ← 優化器賭「就這幾種之一」
        │  看到太多種
        ▼
   megamorphic    →  看過太多種，放棄記錄       ← 優化器不敢賭，退回泛型慢路
```

這個金字塔是 Part 4 的操盤面板：

- 你想讓某個操作是 **monomorphic**（優化器賭得最激進、省最多檢查），才好製造「賭錯」的空間。
- 「型別污染」攻擊的一種手法就是**在優化前把 feedback 餵成你要的形狀**（例如讓它 monomorphic 在某個 Map），優化後再偷偷換掉實際物件的 Map。
- 有些防禦/緩解會讓某操作變 megamorphic（放棄優化），那條路就打不通。

**inline cache（IC）**這個詞你會一直看到：它就是「屬性讀取的 feedback」的別名。`GetNamedProperty a0, [0:"length"], FBV[0]` 這條，第一次執行是慢的（要走完整的屬性查找），但它把「`arr` 這個 Map 的 `.length` 在哪個 offset」快取進 `FBV[0]`；下次同樣 Map 就直接讀那個 offset，這叫「命中 inline cache」。IC 從 monomorphic 惡化到 megamorphic 的過程，就是上面那個金字塔。細節 [Ch 5](./05-map-hidden-class.md) 講 Map 時已鋪過，這裡只要把「IC = 屬性存取的 feedback slot」這個等號記牢。

## 怎麼讀 bytecode（實用清單）

你不需要背全部 200 多個 opcode。認得下面這批就能讀懂九成觸發碼：

| opcode | 意思 | 綁 feedback？ |
|---|---|---|
| `Ldar r` / `Star r` | Load/Store accumulator ↔ register | 否 |
| `LdaZero` / `LdaSmi [n]` / `LdaConstant [i]` | 載入常數到 accumulator | 否 |
| `Mov r_from, r_to` | register 間搬移 | 否 |
| `Add` / `Sub` / `Mul` / `Inc` / `Dec` | 算術（accumulator 為隱含運算元） | **是** |
| `TestLessThan` / `TestEqual` / `TestGreaterThan` | 比較 | **是** |
| `GetNamedProperty o, [name], FBV[n]` | 讀 `o.name` | **是（IC）** |
| `GetKeyedProperty o, FBV[n]` | 讀 `o[key]`（key 在 accumulator） | **是** |
| `SetNamedProperty` / `SetKeyedProperty` | 寫屬性 | **是** |
| `CallProperty` / `CallUndefinedReceiver` | 呼叫函式 | **是** |
| `JumpIfFalse [Δ]` / `JumpIfTrue` / `Jump` | 條件/無條件跳轉 | 否 |
| `JumpLoop [Δ], [depth], FBV[n]` | 迴圈回跳（帶 OSR feedback） | **是** |
| `Return` | 回傳 accumulator | 否 |
| `CreateObjectLiteral` / `CreateArrayLiteral` | 建物件/陣列字面量 | **是** |

讀 bytecode 的訣竅：**盯著 accumulator 的內容流動**。從上往下,每條指令問自己「這條把什麼放進 accumulator / 從 accumulator 拿走什麼」,就能把 bytecode 逆回原始邏輯。凡是行尾有 `FBV[n]` / `EmbeddedFeedback[n]` 的,就在心裡標一顆星:「這裡優化器會押賭注」。

## 對比：Ignition bytecode vs 傳統機器碼 vs Java bytecode

| 面向 | x86 機器碼 | Java bytecode（JVM） | Ignition bytecode |
|---|---|---|---|
| 暫存器模型 | 多個通用暫存器 | 運算元堆疊（stack machine） | **單一 accumulator + register 檔** |
| 型別資訊 | 無（型別在編譯期消失） | 有（bytecode 帶型別） | 弱型別，型別靠 **feedback 執行期收集** |
| 誰執行它 | CPU 直接 | JVM 直譯 + JIT | Ignition 直譯 + 三層 JIT |
| 對利用的意義 | 邏輯 bug | 沙箱逃逸類 | **feedback 是型別混淆的種子** |

accumulator 架構是 Ignition 的招牌選擇（相對 JVM 的 stack machine）：bytecode 更緊湊、直譯器的 dispatch loop 更好寫。對你，重點是**認得 `a`/`r` 後綴、知道 accumulator 是隱形運算元**。

## 踩雷集錦

1. **錯誤直覺：「參數 `a` 就是 `a0`、`b` 就是 `a1`，數字對得上」**。正確：因為隱藏的 `this` receiver 佔第 0 個參數槽，`Parameter count` 會比你宣告的多 1。但**顯式參數的暫存器編號 `a0`/`a1` 仍從第一個顯式參數算起**（receiver 另有其位）。看到 `Parameter count 3` 而你只宣告兩個參數，別以為 bytecode 印錯了。

2. **錯誤直覺：「feedback vector 函式一定義就有」**。正確：新函式只有空的 `ClosureFeedbackCellArray`,要被呼叫夠多次或 `%PrepareFunctionForOptimization` 才配置真正的 FV。直接 `%DebugPrint` 新函式看到 "No feedback vector" 不是壞掉。

3. **錯誤直覺：「bytecode 是最終要跑的東西,優化就是把 bytecode 跑快」**。正確:bytecode 是**直譯器**跑的;優化器（TurboFan）不「跑 bytecode 快一點」,它把 bytecode **重新編譯成完全不同的機器碼**,過程中大量參考 feedback。優化過的機器碼和 bytecode 幾乎沒有一對一關係。

4. **錯誤直覺：「lazy parsing 只是效能細節,和利用無關」**。正確:大多時候是,但 pre-parse/eager 的狀態機不一致出過真 bug,且它影響你的觸發碼何時被完整編譯——寫穩定 trigger 時會咬人。

5. **錯誤直覺：「IC（inline cache）和 feedback vector 是兩個東西」**。正確:IC 就是「屬性存取那類操作的 feedback slot」的俗名,兩者是同一本筆記本的不同欄位。monomorphic/polymorphic/megamorphic 講的就是某個 IC slot 的狀態。

## 進階：再往深一層

- **BytecodeGraphBuilder**：TurboFan 優化一個函式時,不是從 AST 開始,而是**從 bytecode + feedback vector 重建出一張圖（sea-of-nodes）**。這個階段叫 `BytecodeGraphBuilder`（下一章 [Ch 10](./10-turbofan-overview.md) 的 `--trace-turbo` 輸出第一個 phase 就是它 `V8.TFBytecodeGraphBuilder`）。也就是說 **bytecode + feedback 是優化器的輸入**,你這章讀的東西正是優化器讀的東西。
- **bytecode handler**：每條 opcode 的實際行為由一段用 Torque/CSA 寫的「handler」實現,Ignition 的 dispatch loop 就是不斷「取下一條 opcode → 跳到對應 handler」。handler 的 bug 極罕見但存在,屬 [Ch 25](./25-regexp-json-builtins.md) 的 Builtins 攻擊面。
- **`--print-bytecode-filter`**：只印你關心的函式,免得被一堆內建函式的 bytecode 淹沒。配合 `--print-bytecode` 用。
- **SharedFunctionInfo vs JSFunction**：一個函式定義一份 SFI（含 bytecode）,但每次 closure 建立產生一個新的 JSFunction（含各自的 feedback vector）。搞懂這個 split 對理解「同一段程式碼的不同 closure 為什麼 feedback 不同」很關鍵——你 spray 大量 closure 時,它們共享 bytecode 但各有 feedback。

## 動手練習

1. 用 `--print-bytecode` 印出三個函式：一個純算術、一個有 `if/else`、一個有 `for` 迴圈呼叫別的函式。對每一條指令,在旁邊註明「它動了 accumulator 嗎/它綁 feedback 嗎」。把 bytecode 逆回原始邏輯,不對照原始碼。
2. 寫一個 `function get(o){return o.x;}`,先 `%PrepareFunctionForOptimization` 再餵它**同一種**物件幾次,`%DebugPrint` 看它的 feedback。再餵它**三四種不同 shape** 的物件,重新 `%DebugPrint`。你能不能從輸出判斷這個 IC 現在是 monomorphic 還是 polymorphic？（提示:看 feedback 裡記了幾個 Map。）
3. 寫一個內層函式從不被呼叫的 `outer`,用 `--print-bytecode` 確認 V8 沒替內層函式產生 bytecode(找不到它的 bytecode 輸出)。再讓內層函式被呼叫一次,重跑,確認 bytecode 出現了。你剛觀察到 lazy → eager 的轉換。

## 本章重點整理

- **Parser 是懶的**：未被呼叫的內層函式只做 pre-parse（語法檢查 + 記範圍）,不產生 bytecode;第一次呼叫才 eager parse。
- **Ignition 是 accumulator 架構**：一個隱形的 accumulator 當多數指令的隱含運算元 + 結果去處;`a`/`r` 後綴區分 register 來源;`Ldar`/`Star` 在 accumulator 和 register 間搬值。
- **幾乎每條型別敏感的 bytecode 都綁一個 feedback slot**（`Add`、`GetNamedProperty`、`GetKeyedProperty`、`JumpLoop`…）,Ignition 邊跑邊把「看過的型別/Map」記進去。
- **feedback vector 是優化器唯一的情報來源**,狀態走 uninitialized → monomorphic → polymorphic → megamorphic;**這是 Part 4 type confusion 的第一張骨牌**——污染 feedback = 誤導優化器。
- **IC（inline cache）= 屬性存取的 feedback slot**,不是另一個東西。
