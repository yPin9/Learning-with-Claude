# Ch 41 — 審計反模式

> **目標**：把整門課的教訓反過來講。前面 40 章教你「該怎麼做」，這一章專門收集「怎麼做會搞砸」——那些讓資深 auditor 也一再翻車的失敗模式。每一條反模式我們拆成三段：**症狀**（你會怎麼表現出來）→ **為什麼有害**（它讓你漏了什麼、浪費了什麼）→ **怎麼改**（換成什麼行為）。你讀完之後，該對照的不是「別人怎麼審」，而是「我上一次審計，中了哪幾條」。

## 反模式為什麼比正確做法更值得專門講

正確的方法論你已經學了一整門課：漏斗（見 [Ch 35](./35-funnel-combining-tools.md)）、誤報分級（見 [Ch 12](./12-false-positive-triage.md)）、CVE→query（見 [Ch 26](./26-codeql-cve-to-query.md)）、靜態接動態（見 [Ch 37](./37-static-plus-dynamic.md)）。但真正決定你一場審計成不成的，往往不是你**知不知道**正確做法，而是你**有沒有在壓力下滑進某個熟悉的壞習慣**。

反模式的可怕之處在於：它們每一個都**在當下看起來很合理**。工具沒報 → 「那應該沒事」很合理。誤報太多 → 「把這條規則關掉」很合理。時間不夠 → 「先掃一遍再說」很合理。每一步單看都是理性的局部決策，合起來卻讓你系統性地漏掉真 bug。這章要做的，就是把這些「看起來合理的滑坡」拉出來標記清楚，讓你下次滑的時候至少**知道自己在滑**。

先給一張全景圖，把九個反模式按「它主要傷害你哪一環」排列：

```
   審計流程環節              對應的反模式
   ──────────              ────────────
   選工具 / 信工具    →     工具依賴症、盲信近似結果、sound-washing
   寫 query           →     pattern 過擬合單一 CVE、只廣不深 / 只深不廣
   triage 命中        →     誤報疲勞、不記錄 triage 理由
   定 severity        →     把 severity 當 exploitability
   選 bug 追          →     追新奇忽略無聊
```

九條反模式，一條條拆。

## 反模式 1：工具依賴症——工具沒報就當安全

**症狀**：你跑完 CodeQL 的 `cpp-security-and-quality` query pack，0 命中，於是在報告寫「未發現記憶體安全問題」，收工。你把「工具沒報」直接翻譯成「沒有 bug」。

**為什麼有害**：這是把**工具的能力邊界**誤當成**程式的安全邊界**。靜態分析永遠在漏報與誤報之間取捨（原理見 [Ch 2](./02-static-analysis-landscape.md) 的 sound/complete），任何實務工具為了不淹死你，都選擇犧牲一部分 completeness——也就是**主動接受漏報**。CodeQL 沒報，可能是因為：這條 query 根本不覆蓋這種 CWE；資料流在某個 sanitizer 建模處被切斷了（可能是誤切）；source/sink 沒建模到這個 codebase 特有的 API；或者跨了一層 macro / 函式指標 / 反射，工具的 points-to（見 [Ch 6](./06-points-to-analysis.md)）追不過去。「工具沒報」承載的資訊量遠比你以為的少——它只說「在我建模的範圍內、以我設定的精度、我沒找到符合我 query 形狀的東西」。這句話跟「這裡沒有 bug」中間隔著一整個銀河系。

**怎麼改**：把工具的 0 命中當成**一個需要解釋的現象**，不是一個結論。問三個問題：(1) 我的 query 到底覆蓋了哪些 CWE、漏了哪些？(2) 這個 target 的攻擊面（見 [Ch 10](./10-attack-surface-modeling.md)）裡，有哪些 source/sink 是我的 query 根本沒建模的？(3) 高風險區域（parser、反序列化、特權邊界）我有沒有**手讀**過至少一遍？工具是覆蓋率的地板，不是天花板。真正的 auditor 用工具掃完之後，會拿工具**掃不到的地方**當作手讀的優先清單。

## 反模式 2：誤報疲勞——被淹沒後亂關規則

**症狀**：你跑一條新 query，出來 800 條命中。你點開前 15 條全是誤報，火大，直接把整條規則停用，或把整個檔案 / 整個目錄加進 ignore list。「反正都是噪音。」

**為什麼有害**：這是拿**噪音比例**當**價值判斷**，兩者無關。一條 800 命中裡有 795 條誤報的 query，可能那 5 條真陽性正是全 repo 最嚴重的 RCE。你憑「前 15 條是誤報」就整條關掉，等於用抽樣的頭部誤報率去推斷你根本沒看的尾部——而真 bug 常常就藏在尾部（因為它們形狀特殊，才會沒被一眼看穿）。更糟的是「關整個目錄」這種粗暴 suppress：你以為在降噪，其實是在**永久性地把一整塊 code 移出視野**，下次別人（或未來的你）掃這個 repo，會以為那塊已經審過了。

**怎麼改**：誤報疲勞的解法不是**關規則**，是**排序命中**和**修 query**（這是 [Ch 12](./12-false-positive-triage.md) 誤報分級與 [Ch 36](./36-false-positive-governance.md) 誤報治理的整個主題）。三個具體動作：(1) 先按可信度排序，把最可能真的排前面看，而不是照工具給的順序硬啃；(2) 誤報如果**集中在某一種模式**（例如全是某個已知安全的 wrapper），那該做的是給 query 加一個 sanitizer / barrier 把這種模式建模掉，讓 query 變準——這是把你的 triage 勞動**沉澱回 query**，下次不用再看；(3) 真要 suppress，suppress 到**單一命中**的粒度並寫明理由，絕不 suppress 整個檔案 / 目錄。關規則是投降，修 query 是進步。

## 反模式 3：sound-washing——用「掃過了」當免責

**症狀**：專案要出貨 / 過稽核，你跑了一輪掃描器，產出一份「已執行靜態分析、無高危發現」的報告，蓋章放行。這份報告的真正功能是**免責**——出事了可以說「我們掃過了」。

**為什麼有害**：這是把靜態分析從一個**尋找 bug 的工具**降格成一個**風險轉移的儀式**。「sound-washing」這個詞我們借來指：拿工具的（假想的）soundness 給一個其實很淺的審計流程貼金，讓它看起來比實際嚴謹。問題是絕大多數實務工具**根本不 sound**（它們接受漏報以換取可用性），所以「掃過了無發現」這句話的保證強度接近於零。更陰險的是這會制度性地**扼殺真正的審計**：一旦組織接受「掃過即合規」，就沒有人有動機再花時間手讀、建模攻擊面、寫客製 query——因為那些不會讓報告更好看，只會拖慢出貨。這正是**反模式 1（工具依賴症）的組織版**：個人層次的「工具沒報就當安全」被制度固化成流程。

**怎麼改**：分清楚兩件本質不同的事——**合規性掃描（compliance scan）**和**安全審計（security audit）**。前者證明「我們有跑工具」，後者證明「我們認真找過 bug」。你可以兩者都做，但**絕不能拿前者冒充後者**。如果你的角色是做真審計，報告裡要誠實寫清楚：掃了哪些 CWE、覆蓋率邊界在哪、哪些高風險區域是**手動**審過的、哪些地方因為時間 / 工具限制**沒審到**（見 [Ch 39](./39-sarif-ecosystem.md) 談報告與覆蓋率的呈現）。一份誠實標明「這些地方我沒看」的報告，比一份「無發現」的漂亮報告有價值一百倍——因為它讓下一個人知道該從哪接手。

## 反模式 4：pattern 過擬合單一 CVE——抓不到變體

**症狀**：你拿到一個 CVE，讀了它的 patch，寫了一條 query 精準命中**那一行 code 修改前的樣子**。query 跑原 repo，命中了那一處（已經修了），其他地方 0 命中，你宣告「變體分析完成，無其他變體」。

**為什麼有害**：這是把**變體分析**做成了**變更檢測**。你的 query 過擬合（overfit）到那個 CVE 的**表面特徵**——同樣的函式名、同樣的變數名、同樣的呼叫順序——而不是它的**抽象 root cause**。但變體的定義就是「同型但長得不一樣」（見 [Ch 1](./01-reading-to-auditing.md) 與 [Ch 26](./26-codeql-cve-to-query.md)）：同一個團隊的同一個盲點，會在不同函式、用不同變數名、經過不同中間層，寫出**形狀相同但字面不同**的 bug。你的 query 綁死表面特徵，就只認得出那一個雙胞胎，認不出那七個表兄弟。過擬合的 query 給你的 0 命中，是**最危險的一種 0 命中**——它讓你誤以為找乾淨了，其實你只是把搜尋範圍縮到只剩原案本身。

**怎麼改**：抽 pattern 時要刻意往上**抽象一層**，抽到 root cause 而非表面。具體做法（[Ch 26](./26-codeql-cve-to-query.md) 是整章在教這個）：問「這個 bug 的**本質**是什麼？」——是「某類 user 可控的 source，流到某類危險 sink，中間缺了某類檢查」。把 query 寫成描述這三者的**抽象性質**，而不是描述那一行 code 的具體長相。抽完之後做一個關鍵驗證：**故意用不同寫法重寫一遍那個 bug**（改函式名、拆多行、繞一層 wrapper），看你的 query 還抓不抓得到。抓得到，才叫抽對了。抓不到，你就是過擬合了。校準的方向永遠是「寧可抽太寬產生誤報（可以 triage 掉），也不要抽太窄漏掉變體（你根本不知道漏了）」——因為誤報你看得見，漏報你看不見。

## 反模式 5：只廣不深 / 只深不廣

**症狀（只廣不深）**：你什麼都掃，CodeQL 全 query pack、Semgrep 全 registry、每個 target 都跑一遍，但每條命中你只瞄一眼就 pass 到下一條，從不對任何一個可疑點追到底構造 PoC。你的審計是一公里寬、一公分深。

**症狀（只深不廣）**：你逮到一個有趣的函式，一頭栽進去手讀三天，把它每個分支每個 corner case 都搞懂了，寫了漂亮的分析。但整個 repo 你只碰了這一個檔案，攻擊面的其他 90% 從沒建模過。你的審計是一公分寬、一公里深。

**為什麼有害**：這兩個是同一枚硬幣的兩面，都是**廣度與深度失衡**。只廣不深讓你有覆蓋率的假象——你「掃過」了所有東西，但因為從不深入，你連一個真 bug 都驗證不出來，命中全停在「可疑」狀態，等於沒交付。只深不廣讓你有深度的假象——你對那一個檔案的理解無懈可擊，但攻擊者不會只攻你精讀的那個檔案，他攻的是你**沒看**的那 90%。兩種失衡的共同結局是：你花了大量時間，卻在真正重要的維度上是空的。

**怎麼改**：正確的形狀是**先廣後深、且深要深在對的地方**——這正是漏斗（[Ch 35](./35-funnel-combining-tools.md)）的核心。廣度階段（weggli / Semgrep 快篩）目的是**縮面**，把攻擊面從整個 repo 收斂到少數高風險候選；深度階段（CodeQL 深查 + 手讀 + 動態驗證）目的是把候選**追到底**，追出可利用性。關鍵在於深度資源要**分配給廣度篩出來的高價值目標**，而不是隨機一頭栽進第一個看起來有趣的函式。時間盒（下一章 [Ch 42](./42-your-audit-sop.md) 詳談）幫你強制平衡：給廣度掃描設一個上限，給每個深挖目標設一個「追不出來就記錄下來換下一個」的止損點。

## 反模式 6：不記錄 triage 理由

**症狀**：你 triage 了 200 條命中，逐條在腦子裡判斷「這條是誤報因為 xxx」「這條真的但不可達」，然後把它們 dismiss 掉，**什麼都沒寫下來**。三週後你（或同事）重跑 query，同樣 200 條又冒出來，你得**從頭再判斷一遍**。

**為什麼有害**：triage 的判斷是這門課裡**最昂貴的勞動**——它需要你手讀、理解語意、推可達性，一條可能花你半小時。不記錄理由，等於每次重掃都把這筆昂貴勞動**歸零重來**。而且問題會複利：query 迭代一次、依賴升級一次、程式碼重構一次，命中集合就變一次，你就得重 triage 一次。沒有記錄的團隊會陷入一個荒謬循環——同一條誤報被同一個團隊反覆判定為誤報幾十次，因為沒人記得上次為什麼判它誤報。更嚴重的是**無法審計你的審計**：出了漏，沒人能回答「這個 bug 當初 triage 時被誰、以什麼理由判成安全」，你連自己哪裡判錯都復盤不了。

**怎麼改**：triage 的**理由**跟結論一樣重要，甚至更重要（[Ch 36](./36-false-positive-governance.md) 誤報治理的核心論點）。每條 dismiss 都要留下：判成什麼（真陽 / 誤報 / 真但不可達）、**憑什麼這樣判**（哪個 sanitizer 切斷了、哪個前置條件不成立、哪個 source 其實不可控）、以及**這個判斷在什麼條件下會失效**（例如「假設 `validate_input()` 有做長度檢查——如果那個函式被改了，這條要重看」）。落地方式：CodeQL 的 SARIF suppression 帶 justification、Semgrep 的 `nosemgrep` 帶說明、或一份 triage 台帳。把 triage 理由沉澱下來，你的每一次判斷才會**累積**成資產，而不是蒸發成空氣。

## 反模式 7：盲信工具的近似結果

**症狀**：CodeQL 報了一條「tainted data flows to sink」，你看到那條漂亮的 data flow path 高亮，直接寫進報告當真 bug，不去驗證那條 path 在真實執行下**跑不跑得通**。反過來也一樣：工具說「這裡有 sanitizer，安全」，你就信了，不去看那個 sanitizer 到底 sanitize 了什麼。

**為什麼有害**：靜態分析的每一個結果都建立在一整疊**近似**之上——points-to 分析是近似的（見 [Ch 6](./06-points-to-analysis.md)）、路徑條件通常被忽略（工具多半 path-insensitive，不解 `if` 條件的可滿足性）、sanitizer 是**人建模**的（建模對不對是另一回事）、跨函式的 summary 是近似的。工具給你一條 data flow path，它保證的是「在我的抽象裡，taint 可以這樣傳」，**不保證**「這條 path 在真實輸入下可達」。那條 path 可能經過一個 `if (never_true)` 分支（path-insensitive 看不出）、可能中間其實有個工具沒建模的檢查、可能 source 其實不可控。反過來，工具信誓旦旦的「有 sanitizer」也可能是誤判——那個「sanitizer」也許只擋了部分字元、只在部分路徑生效、或建模者根本搞錯了它的語意（見 [Ch 9](./09-source-sink-sanitizer.md)）。盲信任一方向，都是把工具的**近似**當成**事實**。

**怎麼改**：對工具結果保持**結構性懷疑**——不是不信，是知道每個結果背後有哪些近似、哪些近似最可能出錯。對**真陽方向**：拿到一條 flow path，逐段驗證它的可達性，能上動態就上動態（fuzzer / symbolic execution 驗可達，見 [Ch 37](./37-static-plus-dynamic.md) 與 [`symex_taint`](../symex_taint/README.md)）——動態驗證是靜態近似的解毒劑。對**安全方向**：工具說安全的地方，若落在高風險攻擊面上，**不能只憑工具的 sanitizer 判定就放過**，要親眼看那個 sanitizer 做了什麼。核心心法：**工具的「有 bug」和「沒 bug」，都只是需要你驗證的假設，不是可以直接抄的結論。**

## 反模式 8：把 severity 當 exploitability

**症狀**：你按 CVSS 分數或工具給的 severity 標籤排序命中——所有 CRITICAL 優先追，LOW 的直接不看。你把「這個 CWE 類別理論上多嚴重」當成「這個具體命中在這個具體程式裡有多能打」。

**為什麼有害**：severity 和 exploitability 是**兩個不同的軸**，混為一談會讓你既追錯目標又漏掉真 bug。**severity** 是類別層次的、脫離語境的——「buffer overflow 是 CRITICAL」講的是這**類**漏洞一般有多嚴重。**exploitability** 是實例層次的、深度依賴語境的——這個**具體**的 overflow，攻擊者搆得到嗎（可達性）？可控程度多高（overflow 的量、方向、目標）？有沒有緩解措施擋著（stack canary、ASLR、CFI）？現實是：一個標 CRITICAL 的 heap overflow，如果 source 根本不可達、或 overflow 只有 1 byte 且落在 padding 上，它的 exploitability 趨近於零；一個標 MEDIUM 的邏輯錯誤，如果它讓你繞過整個認證，它的 exploitability 是滿分。照 severity 排序，你會把時間砸在**高分但打不動**的命中上，同時略過**低分但致命**的。這對 offensive research 尤其毒——你要的是「能寫出 PoC 的洞」，不是「CVSS 好看的洞」。

**怎麼改**：排序命中要用 **exploitability**，不是 severity。severity 只能當**初始的粗篩**（把明顯是 informational 的降權），真正決定追不追的是你對這個具體命中的可利用性評估：source 可達嗎、可控嗎、緩解措施繞不繞得過、能不能連成一條到達有意義後果的鏈。這需要你懂**利用**——你的 pwn / RE 背景在這裡就是核心資產，它讓你能看穿「CVSS CRITICAL 但實際打不動」和「CVSS MEDIUM 但是條乾淨的 primitive」的差別。offensive 審計的排序準則是一句話：**這個命中能不能，以及多容易，變成一個能打的 PoC。**

## 反模式 9：追新奇 bug 忽略無聊但真的 bug

**症狀**：你放著一堆平凡的 `sprintf` overflow、path traversal、命令注入不管，因為它們「太無聊」，一頭鑽進某個需要三個條件同時成立、繞過兩層緩解、用到某個冷門 primitive 的精妙利用鏈——因為那個**有趣**、值得寫 blog。

**為什麼有害**：這是讓**審美**凌駕**價值**。新奇的 bug 有智力上的吸引力（我們都懂那種爽感），但審計的目的是**找到並消除真實風險 / 找到能用的洞**，不是收集炫技案例。無聊的 bug 之所以無聊，往往正是因為它**經典、直接、好利用**——一個直白的命令注入比一條需要天時地利人和的精妙鏈**更能打**、更可能真的被攻擊者利用。把注意力全押在追新奇上，你會系統性地漏掉那些「一眼就懂所以懶得追」的 bug，而這些恰恰是投報率最高的。這個反模式在有經驗的 auditor 身上特別常見——越熟練的人越容易嫌棄無聊 bug，越容易被新奇陷阱吸走時間。

**怎麼改**：把「無聊」從一個貶義詞改成一個**中性描述**。排序時，無聊但可達、可控、好利用的 bug，優先級要**高於**新奇但條件苛刻的 bug。判準還是回到 exploitability（反模式 8）：不是「這個 bug 有多聰明」，是「這個 bug 有多能打、多好打」。新奇的鏈當然可以追——但要在你先把無聊但真的 bug 收割乾淨、時間有餘之後，當作 bonus，而不是主菜。研究者的虛榮心是條要主動管理的偏差，不是能力的證明。

## 三個「反模式害你漏 bug / 浪費幾週」的具體情境

抽象講完，看三個把反模式串起來的真實形狀的情境（形狀真實、細節為教學擬真）。

### 情境 A：0 命中的假安全（反模式 1 + 3 + 7）

一個團隊要對某 C 網路服務出貨前做安全審計。auditor 跑了 CodeQL 標準 C/C++ query pack，**0 命中**，報告寫「未發現記憶體安全問題」，放行（**反模式 1 工具依賴 + 反模式 3 sound-washing**）。

三個月後，外部研究者在該服務的一個 protocol handler 裡找到一個 stack overflow。回頭復盤：那個 handler 收 user 長度後，經過一個**自訂的 `copy_field()` wrapper** 呼叫 `memcpy`。CodeQL 標準 query 的 sink 建模認得 `memcpy`，但**不認得** `copy_field()` 這個專案特有的 wrapper——taint 追到 wrapper 邊界就斷了（工具的近似邊界，**反模式 7**）。0 命中的真正意思是「我的 query 沒建模你這個 codebase 的自訂寫入原語」，但 auditor 把它讀成了「沒有 bug」。

**如果沒中反模式**：auditor 會問「這個 codebase 有沒有自訂的記憶體操作 wrapper？」——盤點攻擊面時（[Ch 10](./10-attack-surface-modeling.md)）就會發現 `copy_field()` 這類函式，把它們加進 sink 建模（[Ch 9](./09-source-sink-sanitizer.md)），重跑就會命中。代價：多花半天建模，省下三個月後被公開打臉。

### 情境 B：過擬合的變體分析（反模式 4 + 5）

一個研究者拿到某影像解析庫的一個 heap overflow CVE，讀了 patch：某函式在算 chunk 大小時 `width * height * bpp` 整數溢位，patch 加了溢位檢查。研究者寫了一條 CodeQL query，精準匹配「`width * height * bpp` 這三個變數名相乘後傳給 `malloc`」（**反模式 4 過擬合**）。query 跑全 repo，命中原案（已修）+ 0 個其他，宣告無變體，收工（順帶**反模式 5 只深不廣**——只盯這一個 CVE 的一種寫法）。

半年後另一個研究者在**同一個庫**找到兩個同型溢位：一個用的是 `w * h * channels`（變數名不同），一個先算 `pixels = w * h` 再 `pixels * bpp`（拆成兩步）。第一個 auditor 的 query 兩個都抓不到，因為它綁死了字面形狀，抓的是雙胞胎不是同型 bug。

**如果沒中反模式**：把 pattern 抽到 root cause——「任何**多個 user 可控的維度相乘**、結果**未經溢位檢查**就流進 allocation size」——用 CodeQL 的 taint + 溢位建模（[Ch 22](./22-codeql-global-taint.md)、[Ch 24](./24-codeql-cpp-memory-safety.md)）表達這個抽象性質，並用「換寫法重寫測試」驗證 query 抓得到變種。代價：抽象化多花一兩小時、多幾條要 triage 的誤報；回報：撈到那兩個真變體。

### 情境 C：誤報疲勞埋掉真 bug（反模式 2 + 6）

一個 auditor 對一個大型 web 後端跑 Semgrep 的 SSRF taint 規則，出來 **300 命中**。前 20 條全是誤報——都是打到內部固定 URL 的請求，source 其實不可控。auditor 火大，把整條 SSRF 規則從 CI 裡停用（**反模式 2 亂關規則**），而且沒記錄為什麼關、也沒記那 20 條為什麼是誤報（**反模式 6 不記錄理由**）。

那 300 條裡，第 147 條是真的：一個 admin 面板的 webhook 設定功能，直接拿 user 填的 URL 去發請求，是條乾淨的 SSRF。它被埋在 auditor 從沒看到的尾部。規則一關，這條 bug 在 CI 裡永久隱形。更糟的是三個月後新人接手，看到 CI 沒有 SSRF 規則、也沒任何記錄說明為什麼，以為這個 repo 從沒考慮過 SSRF，重新加規則又撞上同樣 300 條誤報，同樣的痛苦重來一遍。

**如果沒中反模式**：(1) 那 20 條誤報**集中在同一個模式**（固定內部 URL），該做的是給規則加一個 barrier 把「常數 / 固定 URL」排除掉（[Ch 14](./14-semgrep-taint-mode.md)、[Ch 36](./36-false-positive-governance.md)），一次修好、噪音大降，而不是關規則；(2) 就算要暫時降權，也記錄「因誤報率高暫時降為 warning，待 barrier 補上」，讓下一個人接得住。代價：修規則多花一小時；回報：那條真 SSRF 不會被埋，且團隊的判斷會累積而非蒸發。

## 踩雷集錦（元層次：把方法論本身變成反模式）

前面九條講的是「怎麼審會搞砸」。這一節升一層，講**怎麼看待這門課的方法論本身會搞砸**——這些是讀完一整門課後最容易犯的元錯誤。

**錯誤直覺：「這 42 章的方法論是一套要照著跑的固定流程。」**
正確認識：方法論是**思考的鷹架**，不是**填空的表單**。把 SOP 當教條照抄（下一章 [Ch 42](./42-your-audit-sop.md) 會反覆強調這點），是最諷刺的反模式——你用一套「幫你避免思考盲點」的工具，把自己變成了不思考。每個 target 都不一樣：有的沒法 build（CodeQL 就用不了，跳到 Joern）、有的太小（建 database 的成本高過手讀）、有的你早就有 corpus（直接上 fuzzer 比靜態划算）。方法論告訴你**有哪些刀、各適合什麼**，選哪把、要不要全走一遍，永遠是當下的判斷。

**錯誤直覺：「反模式清單就是拿來檢查別人的。」**
正確認識：讀反模式最大的價值是**照鏡子**，不是**拿放大鏡看同事**。你讀「追新奇忽略無聊」時心裡想的如果是「對啊某某人就這樣」，你就白讀了——因為每一條反模式，最資深的人也照樣中，包括你。真正的用法是每次審計**復盤**時，拿這九條逐項自問「我這次中了哪幾條」。反模式不會因為你知道它存在就消失，它們是重力，你只能持續對抗。

**錯誤直覺：「避開所有反模式，我的審計就對了。」**
正確認識：反模式是**必要非充分**——避開它們讓你不搞砸，但不保證你找得到 bug。找 bug 終究靠的是攻擊面直覺、對 root cause 的抽象能力、和把命中追成 PoC 的硬功夫。這章能幫你的是「別把自己絆倒」，能不能贏還是看你跑得多快。別把「沒犯錯」誤當成「做對了」——不犯反模式的平庸審計，依然是平庸審計。

## 進階延伸

- **反模式的組織版**：本章大多從個人視角講，但每一條在團隊 / 組織層次都有放大版——工具依賴變成「合規即安全」的流程、不記錄理由變成「沒有機構記憶」的知識蒸發、誤報疲勞變成「大家都學會忽略掃描器」的告警盲。組織版反模式更難改，因為它們被流程和 KPI 固化。[Ch 36](./36-false-positive-governance.md) 的誤報治理其實有一半是在對抗這些組織版反模式。
- **反模式與認知偏誤的對應**：把九條反模式對回心理學的認知偏誤會很有啟發——工具依賴 ≈ automation bias（過度信任自動化）、追新奇 ≈ 新奇偏好 + 沉沒成本、把 severity 當 exploitability ≈ 用現成標籤代替獨立判斷的 anchoring。理解偏誤的機制，你才知道為什麼這些反模式**在當下總是感覺合理**——因為它們搭的是大腦的節能捷徑。
- **反向操作——刻意練習抗反模式**：每條反模式都可以設計成一個練習。例如對抗過擬合：拿一個你寫過的 query，故意用五種不同寫法重寫同一個 bug，看你的 query 漏了幾種。對抗誤報疲勞：規定自己看命中時**從尾部往前看**一次，破除「頭部誤報率代表全體」的錯覺。把抗反模式變成可練習的動作，比單純「知道有這回事」有用得多。

## 本章重點整理

- **反模式的可怕在於「當下看起來合理」**——工具沒報→沒事、誤報多→關規則、時間少→掃一遍，每步局部理性，合起來系統性漏 bug。
- **九條反模式**：(1) 工具依賴（沒報當安全）、(2) 誤報疲勞（亂關規則）、(3) sound-washing（掃過當免責）、(4) 過擬合單一 CVE（抓不到變體）、(5) 只廣不深 / 只深不廣、(6) 不記錄 triage 理由、(7) 盲信工具近似、(8) 把 severity 當 exploitability、(9) 追新奇忽略無聊。
- **反覆出現的主線**：工具給的（0 命中、有 bug、有 sanitizer、severity 標籤）全是**需要驗證的假設**，不是可以直接抄的結論。
- **triage 的理由跟結論一樣是資產**——不記錄，昂貴的判斷勞動每次重掃就蒸發歸零。
- **offensive 審計的排序準則是 exploitability，不是 severity**：能不能、多容易變成能打的 PoC。無聊但可達好利用的 bug，優先於新奇但條件苛刻的。
- **元層次**：方法論是鷹架不是教條；反模式清單拿來照鏡子復盤，不是檢查別人；避開反模式是必要非充分——它讓你不絆倒，不保證你贏。
