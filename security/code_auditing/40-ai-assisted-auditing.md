# Ch 40 — AI 輔助審計

> **目標**：冷靜拆解 LLM 在審計流程的**正確用法與陷阱**。你會學到哪些事 LLM 真能加速（產 query 初稿、解釋陌生碼、triage 輔助、補 sink model、生 PoC 骨架），哪些會坑你（幻覺 API/CVE、把似是而非說成真、query 看似對其實漏報），以及一條核心紀律——**LLM 說的一律要能用工具驗**。本章真跑一個「LLM 產的 query 怎麼驗」的閉環。
> **環境**：WSL、semgrep 1.172.0、python3。靶在 `~/audit-lab/ch40/`。LLM API 部分標「未實測，理論預期」附步驟。

AI 輔助審計是當下最熱、也最容易被濫用的題目。作為低階安全研究者，你對這件事的態度應該和你對任何工具一樣：**它是加速器，不是判官**。LLM 能把你「寫 query 初稿」「讀懂陌生碼」「初篩一堆命中」的速度拉高幾倍——但它產出的**每一個具體斷言**（這個 API 存在、這個 CVE 是這樣、這個命中是真的、這條 query 對）都可能是幻覺，且它會用一樣自信的語氣說對的和錯的。

所以本章的骨架不是「LLM 能做什麼」，而是「**LLM 說的怎麼驗**」。你的技術判斷力是這一章的主角，LLM 只是配角。

---

## 為什麼是「加速器不是判官」

先講清楚 LLM 的本質侷限，這決定了它能被信任到什麼程度：

- **它產生的是「看起來對」的文字**，不是「驗證過對」的結論。它沒有執行你的碼、沒有跑你的 query、沒有查 CVE 資料庫——它是在預測「一個懂這題的人會怎麼寫」。多數時候這個預測很準，但**它不知道自己哪次不準**。
- **它的錯誤最危險的形態是「自信的錯」**：幻覺出一個不存在的函式、編一個不存在的 CVE 編號、把一個 infeasible 的 flow 講得像鐵證。因為語氣一致，你很難從輸出本身分辨對錯。
- **它不可重現**：同一個問題問兩次可能給不同答案。這對審計是硬傷——審計要的是可複現的證據鏈，「LLM 這樣說」不是證據。

結論很直接：**LLM 的輸出是「待驗證的假設」，不是「結論」**。凡是它給的具體斷言，都要能落到一個工具能驗的形式（跑 query、編譯 PoC、查真實文件/CVE DB）。驗得過才採信，驗不過就丟。這條紀律貫穿整章。

## 有效用法（每個都配「怎麼驗」）

### 1. 產 query 初稿（自然語言 → CodeQL/Semgrep）

LLM 最實用的用法之一：你用自然語言描述想找的 pattern（「找 memcpy 的長度來自外部且沒 bound check 的」），它產一條 Semgrep/CodeQL query 初稿。這省掉你查語法、想 metavariable 的時間。

**但初稿幾乎不能直接用**——語法可能對、語意常有微妙偏差（過度具體漏報、過度寬鬆誤報）。驗法：**在已知答案的靶上跑它**（見範例一）。

### 2. triage 輔助（解釋命中、初篩）

面對一個命中，LLM 能快速幫你**解釋**它為什麼被報（讀 codeFlow 講「len 從這裡流到那裡」）、給一個「這像不像真的」的初步意見。這對量大時做粗分很有用。

**但它的「這是真/假」不能當判定**——它沒跑動態驗證、沒查你的 sanitizer。驗法：把它的意見當**排序訊號**（優先看它說「像真的」的），真偽仍走 Ch 12 三角 + Ch 37 動態驗證。

### 3. 補 sink model（列某 framework 的 source/sink）

「Django 有哪些會產生 SQL 的 sink？」「這個 RPC framework 的 request handler 入口有哪些？」——LLM 對常見 framework 的 source/sink 清單記得不錯，能快速幫你補 Ch 9/11 的模型。

**但它會漏、會編**——漏掉冷門 sink、或編一個聽起來合理但不存在的 API。驗法：每一條**回查官方文件**、或 grep 該 framework 原始碼確認 API 真存在。

### 4. 解釋陌生碼（接 reading_code）

丟一段沒看過的碼給 LLM，它能快速給你「這大概在做什麼」的摘要，加速讀碼（接 reading_code 課的技能）。

**但它會腦補**——把碼裡沒有的邏輯講得像有、誤解 control flow。驗法：拿它的摘要當**閱讀地圖**，關鍵結論（尤其安全相關的「這裡有沒有檢查」）一定回去讀原碼確認。

### 5. 生成 PoC 骨架

「幫我寫一個觸發這個 memcpy OOB 的 harness/輸入」——LLM 能產 PoC 骨架，省掉樣板碼。

**但骨架常有 off-by-one、格式錯、觸發條件搞錯**。驗法：**編譯跑它、看 ASan 有沒有真的 crash**（Ch 37 的閉環）。跑不出 crash 就是骨架沒對，不是沒 bug。

## 範例一：LLM 產的 query 怎麼驗（真跑，核心紀律）

這是本章最重要的實作——**永遠不要相信 LLM 的 query 對，要跑給你看**。我們模擬一個常見情境：你請 LLM 產一條「找變數長度的 memcpy」的 Semgrep 規則，它給了這個（`llm_rule_v1.yaml`）：

```yaml
rules:
  - id: llm-memcpy-len
    languages: [c]
    severity: ERROR
    message: memcpy with variable len (LLM draft).
    pattern: memcpy($DST, $SRC, len);      # <- LLM 把長度變數寫死成 "len"
```

**在原始靶 `vuln.c` 上跑（那裡的變數剛好叫 `len`）**：

```bash
cd ~/audit-lab/ch40
semgrep --config llm_rule_v1.yaml vuln.c -q
```

```
   ❯❯❱ llm-memcpy-len
           12┆ memcpy(buf, data, len);           // sink: OOB write, len unchecked
```

**它命中了！** 如果你只在這個靶上測，會下結論「LLM 的 query 對」。這正是陷阱——LLM 把長度變數**寫死成識別字 `len`**，而這個靶剛好用了 `len`。這條 query 其實是**過度具體**的，它只匹配變數叫 `len` 的 memcpy。

**在一個變數叫 `n` 的變體 `variant.c` 上跑**：

```c
void copy(char *dst, char *src, int n){ char b[64]; memcpy(b, src, n); }
```

```bash
semgrep --config llm_rule_v1.yaml variant.c --json -q | \
  python3 -c 'import json,sys;print("hits:", len(json.load(sys.stdin)["results"]))'
# hits: 0
```

**漏報！** 同樣的 OOB memcpy，只因變數叫 `n` 不叫 `len`，LLM 的 query 完全看不到。如果你信了 LLM「這 query 對」、拿去掃真專案，所有變數不叫 `len` 的同類 bug 全部漏掉——而你毫不知情，因為它在你測的那個檔上「看起來對」。**這就是 LLM query 最陰險的失敗：看似對，其實系統性漏報。**

**正確的 query 用 metavariable 抓長度、排除 sizeof**（`correct_rule.yaml`）：

```yaml
rules:
  - id: memcpy-nonconst-len
    patterns:
      - pattern: memcpy($DST, $SRC, $N)      # <- metavar，不寫死變數名
      - pattern-not: memcpy($DST, $SRC, sizeof($X))
    message: memcpy with non-constant length.
    languages: [c]
    severity: ERROR
```

```bash
for f in vuln.c variant.c; do
  h=$(semgrep --config correct_rule.yaml $f --json -q | \
      python3 -c 'import json,sys;print(len(json.load(sys.stdin)["results"]))')
  echo "$f -> $h hit(s)"
done
# vuln.c    -> 1 hit(s)
# variant.c -> 1 hit(s)
```

修正後**兩個都抓到**。

這個真跑閉環就是本章的核心紀律：**LLM 產的 query 一律要在「正例 + 反例/變體」上跑，看它抓對正例、不漏變體、不誤報負例**。只在一個檔上「看起來對」什麼都證明不了。你要拿已知答案的靶主動去**證偽**它——這正是把安全研究者的懷疑本能用在 LLM 上。

## 陷阱（本章重點）

### 幻覺出不存在的 API/CVE

LLM 會用完全自信的語氣說「這個 bug 是 CVE-2023-XXXXX」或「用 `secure_memcpy_checked()` 就安全了」——而那個 CVE 編號、那個函式**根本不存在**。它是在生成「聽起來像真的」的東西。

**紀律**：任何 LLM 給的 CVE 編號**回查 NVD/官方 advisory**；任何 API **回查官方文件或 grep 原始碼**。查不到就是幻覺，不管它講得多肯定。

### 把似是而非的命中說成真

給 LLM 一個命中問「這是不是真 bug」，它常給一個聽起來很有道理的「是的，因為 len 可控且沒檢查」——但它沒跑動態驗證、沒看到上游其實有 clamp。**它把「看起來像」講成「確認是」**。

**紀律**：LLM 的真偽意見只當排序訊號，判定走 Ch 37 動態驗證。

### query 看似對其實漏報（範例一已示範）

最陰險的一類。LLM 的 query 在你手邊的例子上命中了，你就信了，但它有系統性漏報（過度具體）。你以為在掃，其實漏了一大類。

**紀律**：範例一的「正例+變體」驗證法，永遠做。

### over-trust 與不可重現

用久了會產生「它通常對，這次應該也對」的鬆懈——這是 over-trust。加上 LLM 不可重現，你今天基於它的答案做的判斷，明天可能重現不出來。

**紀律**：LLM 的產出全部要落成**可重現的工件**（跑得出來的 query、編得過的 PoC、查得到的文件連結），審計報告裡不能有「LLM 說」當證據。

## 前沿：LLM-based / ML-based 找洞的現狀（誠實評估）

有人問：能不能直接讓 LLM 讀碼找洞（跳過寫 query）？誠實的現狀是——**目前不可靠，誤報高，別當主力**：

- **誤報極高**：LLM「讀碼找洞」會把大量安全的碼說成有洞（尤其它腦補了不存在的執行路徑）。在真實大 codebase 上，訊噪比差到難以用。
- **漏報也嚴重且不可預測**：它可能漏掉明顯的洞、卻對一段安全的碼言之鑿鑿。而且你無法預測它哪次會漏——沒有 sound/complete 的保證，連「近似」的方向都不穩定。
- **不可重現、不可審計**：同一段碼問兩次結論可能不同，且它給不出可驗證的推理鏈。這和審計要的「可複現證據」根本衝突。
- **它適合的是「輔助」不是「取代」**：當上面那些**有明確驗證閉環**的用法（產 query 初稿 → 跑驗、生 PoC → 編譯驗），LLM 是有效加速器。當「無驗證的自主找洞判官」，它現在不合格。

措辭要謹慎：這領域在快速演進，未來可能改變。但**以現在（本課寫作時）而論**，把 LLM 當自主漏洞偵測器會給你一堆你分不清真假的東西，反而拖慢審計。正確姿勢是把它嵌進**有工具驗證閉環**的環節，讓每個 LLM 斷言都被一個能跑的工具檢查。

## LLM API 整合（未實測，理論預期）

若要把 LLM 接進審計腳本（例如自動對每個命中產一段解釋、或自然語言轉 query），流程大致是：

```python
# 未實測，理論預期——需 LLM API key
# 1. 把命中的 code snippet + codeFlow 塞進 prompt
# 2. 要求輸出「結構化」的東西（一條 query、一個 JSON 判定），不要自由文字
# 3. 關鍵：對輸出做程式化驗證——
#    - 產的是 query -> 立刻對已知靶跑（範例一的正例+變體）
#    - 產的是 CVE -> 立刻對 NVD API 查編號是否存在
#    - 產的是 API 名 -> 立刻 grep 原始碼確認存在
# 4. 驗不過就丟棄或標「LLM 未驗證，人工複查」
```

> 這段標**未實測，理論預期**——需要 LLM API 帳號與 key。步驟：用官方 SDK 送 prompt、取回輸出後，**務必**接一個程式化驗證步驟（上面第 3 點）才採信。核心設計原則：**讓 LLM 產「可被工具驗證的東西」**（query、CVE 編號、API 名），而非「無法驗證的自由判斷」。可驗證性是安全地用 LLM 的前提。若你要接 Anthropic 的 Claude API 做這件事，SDK 用法、模型選擇、結構化輸出（tool use / JSON mode）等請以官方 API 文件為準。

## 對比：LLM 用在「有驗證閉環」vs「無驗證」的環節

```
                    有驗證閉環（推薦）              無驗證（危險）
產 query            產初稿 → 對已知靶跑驗           產 query 直接拿去掃真專案
CVE/API 查詢        LLM 給編號 → 回查 NVD/文件      直接信 LLM 給的 CVE/API
triage             LLM 意見當排序 → 動態驗證真偽    LLM 說是真 bug 就當確認
讀陌生碼            LLM 摘要當地圖 → 關鍵處讀原碼    信 LLM 摘要不看原碼
自主找洞            —（現階段不當主力）             讓 LLM 讀碼直接判洞
共同紀律            每個斷言都落到工具能驗的形式      把 LLM 輸出當結論
```

規律很清楚：**LLM 用得好的環節，都有一個「工具驗證」把它的輸出接住**。沒有這個接住的環節，LLM 就從加速器變成噪音源。

## 踩雷集錦

**錯誤直覺一：LLM 產的 query 在我的例子上命中了，那就是對的。**
→ 正確認識：在一個例子上命中什麼都不證明——LLM 常產「過度具體」的 query（把變數名/常數寫死），它在你手邊的例子上剛好對，卻系統性漏掉變體（範例一：變數叫 `n` 就漏）。必須在**正例 + 反例 + 變體**上跑，看它抓對、不漏、不誤報。只測一個檔等於沒測。

**錯誤直覺二：LLM 說這是 CVE-2023-XXXXX / 用這個 API 就安全，那就寫進報告。**
→ 正確認識：LLM 會用一樣自信的語氣**編造**不存在的 CVE 編號和 API。任何 LLM 給的具體 CVE **回查 NVD**、任何 API **回查官方文件或 grep 原始碼**。查不到就是幻覺。把未查證的 LLM 斷言寫進審計報告，是砸自己招牌的最快方式。

**錯誤直覺三：LLM 說這個命中是真 bug，那就當確認了，省得動態驗證。**
→ 正確認識：LLM 沒跑你的碼、沒看你的 sanitizer、沒做可達性分析——它的「是真的」是文字預測不是驗證。它的意見最多當**排序訊號**（優先看它覺得像真的），真偽判定仍走 Ch 12 三角 + Ch 37 ASan。用 LLM 取代動態驗證等於用「聽起來像」取代「證明是」。

**錯誤直覺四：現在 LLM 很強了，直接讓它讀碼找洞就好。**
→ 正確認識：以現階段（本課寫作時）而論，LLM 自主找洞誤報極高、漏報不可預測、不可重現、給不出可驗證推理鏈——在真實大 codebase 上訊噪比差到拖慢審計。它適合的是有明確驗證閉環的**輔助**環節（產 query→驗、生 PoC→編譯驗），不是無驗證的自主判官。這領域在演進，但別現在就把它當主力找洞器。

**錯誤直覺五：LLM 通常對，這次應該也對，不用每次都驗。**
→ 正確認識：這是 over-trust，加上 LLM 不可重現，是複合風險。「通常對」正是它偶爾錯時最坑你的原因——你放鬆了驗證。紀律必須是**無例外**：每個 LLM 斷言都落到工具能驗的形式，不因為它「最近都對」就跳過。安全研究者對工具的懷疑本能，對 LLM 要開到最大。

## 進階延伸

- **結構化輸出 + 程式化驗證是安全用 LLM 的關鍵設計**：與其讓 LLM 產自由文字（難驗證），不如強制它產**結構化、可驗證的東西**——一條完整 query（可立刻跑）、一個 CVE 編號（可立刻查 NVD）、一個 JSON 判定（可 schema 檢查）。這讓「驗證 LLM 輸出」從「人工讀一段話判斷」變成「跑一個自動檢查」。可驗證性應該是你設計任何 LLM 輔助環節的第一原則，而不是事後補的。
- **LLM 當「query 語法轉譯器」比當「漏洞判斷器」可靠得多**：LLM 在「把自然語言意圖轉成 Semgrep/CodeQL 語法」這種**有客觀對錯、可立即驗證**的任務上，可靠度遠高於「這段碼有沒有洞」這種需要深層語意推理、無法立即驗證的任務。把 LLM 的用途往「轉譯/樣板/摘要」（可驗證）推、往「判斷/找洞」（難驗證）縮，是最大化它價值、最小化它風險的策略。
- **LLM 輔助 triage 的「盲測」評估**：若你真要在流程裡用 LLM 做 triage 初篩，該像評估任何分類器一樣**盲測它**——拿一批你已知真偽的命中（來自過去的 triage 紀錄，Ch 36），讓 LLM 判，算它的 precision/recall。別憑感覺信它「篩得不錯」。這也讓你知道該不該信它某一類命中的判斷（它可能對某類準、對另一類爛）。接 Ch 36 的規則 precision 度量思路，只是把度量對象換成 LLM。

## 本章重點整理

- LLM 在審計是**加速器不是判官**：它產「看起來對」的文字不是「驗證過」的結論，最危險的錯是「自信的錯」（幻覺 API/CVE），且不可重現。
- 核心紀律：**LLM 的每個具體斷言都是待驗證假設，要落到工具能驗的形式**（跑 query、編譯 PoC、查 NVD/文件）——驗過才採信。
- 有效用法都配驗法：產 query 初稿→對已知靶跑、triage 意見→當排序訊號 + 動態驗證、補 sink model→回查文件、解釋碼→當地圖再讀原碼、生 PoC→編譯看 ASan。
- 真跑核心：LLM 產的 `memcpy(...,len)` query 在變數叫 `len` 的靶上「看似對」，卻**系統性漏掉**變數叫 `n` 的變體——必須在正例+變體上跑才抓得出這種陰險漏報。
- LLM 自主找洞現階段不可靠（誤報高、漏報不可測、不可重現、無可驗證推理鏈），適合有驗證閉環的輔助環節，不適合當無驗證的判官。這領域在演進，措辭謹慎。

## 自我檢核

- 為什麼說 LLM 是「加速器不是判官」？它輸出的本質是什麼、最危險的錯誤形態是什麼？
- 範例一的 LLM query 在 `vuln.c` 上命中了，為什麼「命中」不能證明它對？它在 `variant.c` 上出了什麼問題、根因是什麼？正確 query 怎麼修？
- 給「產 query 初稿」「補 sink model」「生 PoC」三個用法，各寫出對應的「怎麼驗」動作。共同的紀律是什麼？
- LLM 給你一個 CVE 編號和一個「安全 API」名，你在採信前各做什麼動作？查不到代表什麼？
- 為什麼 LLM 自主找洞現階段不當主力？列出至少三個具體理由（跟審計要的「可複現證據」怎麼衝突）。

## 延伸閱讀

- **你要用的 LLM 供應商官方 API 文件（模型、結構化輸出/tool use、限制）**——本章 API 整合標未實測那段的實作依據，尤其「怎麼強制結構化輸出」是可驗證性的關鍵。用法：接 LLM 進審計腳本前，先搞懂怎麼讓它產 JSON/query 而非自由文字。前提：本章的「結構化+驗證」原則。若用 Claude，以 Anthropic 官方 API 文件為準。
- **reading_code 課程（讀碼方法論）**——本章「LLM 解釋陌生碼」的正確用法建立在你**自己**有讀碼能力之上——LLM 的摘要是地圖，你要能回去核對原碼。用法：把 LLM 摘要和那門課的讀碼技巧配著用，摘要定位、原碼定案。前提：本章；那門課給你「不被摘要牽著走」的底氣。
- **各家 SAST 廠商關於「AI-assisted / autofix」功能的技術部落格（讀時保持懷疑）**——看業界怎麼宣稱、怎麼實際整合 LLM 進 SAST。用法：對照本章的「有驗證閉環 vs 無驗證」框架，判斷某個 AI 功能是把 LLM 接在驗證閉環裡（可信）還是當無驗證判官（存疑）。前提：本章；讀行銷語言要打折。
- **關於 LLM 幻覺與可靠性的綜述性資料（保持時效意識）**——理解 LLM 為什麼會自信地錯、幻覺的機制。用法：想從「知道它會幻覺」深入到「為什麼、什麼時候更容易幻覺」時讀，幫你預判哪些審計任務 LLM 特別不可靠。前提：本章；此領域演進快，注意資料時效。
