# Ch 35 — 組合拳漏斗

> **目標**：把全課的工具觀收束成一句話——**四把刀不是競爭，是漏斗的不同層級**。你已經一把把學過 rg、weggli、ast-grep/comby、Semgrep、CodeQL、Joern；這章教你怎麼把它們**接力**成一條流程：便宜的快工具在頂端秒級砍掉 99%，昂貴的深工具只花在最可疑的 1%。我們會對真實 repo（libgit2）跑一遍「找 unchecked memcpy」的前兩層漏斗、貼真實過濾數字，讓你看到 287 個 memcpy 怎麼一路收斂到 2 個值得深查的點。
> **環境**：weggli 0.2.4，WSL Ubuntu 22.04；ast-grep/comby/CodeQL 深查層以「理論預期/接續章節」標示。

前面兩章你集滿了刀。但工具會用不等於會審計——新手最典型的失敗是**選錯層級的刀**：對整 repo 一上來就開 CodeQL（慢死、淹沒），或全程只用 grep（漏掉所有要 flow 才看得出的 bug）。這章給你的是**組合的章法**：哪把刀在哪一層、每層砍掉多少、為什麼方向必須是「快而粗 → 慢而精」。

## 漏斗全景

把審計想成一個漏斗。上寬下窄：頂端是幾百萬行原始碼，底端是幾個確認的真 bug。每一層用一把「比上一層貴、但比上一層精」的刀，把候選數量砍一個數量級：

```
        幾百萬～幾千萬行原始碼
   ┌─────────────────────────────────┐
   │  L0  rg / grep                   │  純文字正則，毫秒級
   │      「危險函式全 repo 用在哪」    │  → 幾千～幾萬個文字命中
   └────────────┬────────────────────┘
                │  砍掉：非目標函式、明顯不相關
   ┌────────────▼────────────────────┐
   │  L1  weggli / ast-grep           │  單函式 AST 結構，秒級
   │      「結構長得像 bug 的」         │  → 幾百～幾千個結構候選
   └────────────┬────────────────────┘
                │  砍掉：結構安全的（size 是常數、有本地 guard）
   ┌────────────▼────────────────────┐
   │  L2  Semgrep / Joern             │  輕量 taint / 語意，分鐘級
   │      「加一點來源語意」            │  → 幾十～幾百個
   └────────────┬────────────────────┘
                │  砍掉：來源不可控、路徑不可達
   ┌────────────▼────────────────────┐
   │  L3  CodeQL                      │  跨函式 global taint，分鐘～十幾分
   │      「size 真的來自不可信 source」│  → 幾個～幾十個高可信命中
   └────────────┬────────────────────┘
                │  砍掉：工具沒建模的 sanitizer、infeasible path
   ┌────────────▼────────────────────┐
   │  L4  手讀 + 動態驗證（PoC/fuzz）  │  人時最貴，逐個確認
   │      「確認可觸發、寫得出 PoC」    │  → 真 bug（可報）
   └─────────────────────────────────┘
```

每往下一層，**單位成本上升一個數量級，候選數量下降一個數量級**。這個「成本與數量反向」的結構就是漏斗能省時間的原因：貴的刀永遠只砍前面便宜刀留下的少數。

## 每層的過濾率與成本

把上面的圖量化。數字是量級估計（實際隨 repo 與 pattern 變動很大），但**相對關係是穩的**：

| 層 | 工具 | 單次成本 | 輸入量級 | 輸出量級 | 過濾率 | 產出性質 |
|---|---|---|---|---|---|---|
| L0 | rg / grep | 毫秒 | 10^6~10^7 行 | 10^3~10^4 命中 | ~99% | 文字命中（含雜訊） |
| L1 | weggli / ast-grep | 秒 | 10^3~10^4 | 10^2~10^3 | ~90% | 結構候選 |
| L2 | Semgrep / Joern | 分鐘 | 10^2~10^3 | 10^1~10^2 | ~80% | 帶輕量語意/taint |
| L3 | CodeQL | 分鐘~十幾分 | 10^1~10^2 | 10^0~10^1 | ~80% | 跨函式 flow 確認 |
| L4 | 人 + 動態 | 小時/命中 | 10^0~10^1 | 真 bug | — | 可報漏洞 + PoC |

關鍵讀法：**L0 一次砍掉的量最大、成本最低**（毫秒砍 99%），越往下每次砍的比例遞減但單位成本暴增。所以你**絕不能跳過上層**——把 CodeQL（分鐘級/命中）直接開在 10^6 行上，等於用每命中幾分鐘的刀去處理幾萬個候選，跑到天荒地老還淹死在輸出裡。

## 具體走查：在 libgit2 找 unchecked memcpy

抽象講完，真跑一遍。目標：**在 libgit2 找「size 是變數、dst 是固定 stack buffer」的 memcpy**——這是 stack overflow 的結構候選。我對 `/tmp/libgit2`（`src/` 204 個 `.c`、約 12.7 萬行）真跑前幾層漏斗。

### L0 — rg 粗篩：有沒有、幾個

```
$ cd /tmp/libgit2
$ rg -c 'memcpy\(' src | awk -F: '{s+=$2} END{print s}'
287
```

**287 個 memcpy 文字命中，毫秒級。** 這是漏斗入口——先確認「這個 repo 確實大量用 memcpy，值得往下查」。rg 這層也會命中註解裡的、字串裡的假 memcpy（Ch 34 看過），但沒關係，下一層的結構工具會濾掉。L0 的任務只是**確認有、給個量級**。

### L1 — weggli 結構縮面：size 是奇怪變數的

上 weggli，加第一個結構約束：**size 引數的名字不是 `size`**（叫 `size` 的多半是刻意算好的長度，不可疑）：

```
$ time weggli -R 's!=^size$' '{ memcpy(_,_,$s); }' src | grep -c '^/tmp'
99
real    0m0.425s
```

**287 → 99，0.4 秒。** 三分之二的 memcpy（size 叫 `size` 的那些）被砍掉。注意 weggli 這裡順便把 rg 的雜訊（註解、多行誤判）也自動濾掉了——因為它懂 AST。

### L2（本例併入 weggli）— 再加結構約束：dst 是固定 stack buffer

繼續收緊。真正危險的是「size 是變數 **且** dst 是同函式內的固定大小陣列」——這是 stack 溢位的典型結構。加 `char $b[_]` 約束 dst：

```
$ time weggli '{ char $b[_]; memcpy($b,_,$s); }' src | grep '^/tmp'
/tmp/libgit2/src/util/util.c:709
/tmp/libgit2/src/libgit2/transports/smart_pkt.c:525
real    0m0.088s
```

**99 → 2，0.088 秒。** 整個 repo 只剩兩個點：memcpy 的 dst 是本函式宣告的固定陣列、size 是變數。**這就是漏斗的威力**——12.7 萬行、287 個 memcpy，用兩條秒級 weggli 收斂到 2 個值得人眼看的結構候選。

### L4 — 人眼 triage 這 2 個

看這兩個到底是不是 bug（這步是人時，但只花在 2 個點上）：

**點 1：`src/util/util.c:709`**
```c
static void swap(uint8_t *a, uint8_t *b, size_t elsize)
{
    char tmp[256];
    while (elsize) {
        size_t n = elsize < sizeof(tmp) ? elsize : sizeof(tmp);  // n 被 clamp 到 <= 256
        memcpy(tmp, a + elsize - n, n);
        ...
    }
}
```
四問（Ch 12）：dst 是 `tmp[256]`、size 是 `n`——但 `n = elsize < sizeof(tmp) ? elsize : sizeof(tmp)` **把 n clamp 到最多 256**。sanitizer 那問「否」（有本地 guard）→ **誤報**。這是 weggli 看不到的：它只知道「size 是變數 `n`」，不知道 `n` 前一行被 clamp 了。**這正是為什麼漏斗底層要人讀或 CodeQL**——結構工具到這裡就止步。

**點 2：`src/libgit2/transports/smart_pkt.c:525`**
```c
static int parse_len(size_t *out, const char *line, size_t linelen)
{
    char num[PKT_LEN_SIZE + 1];
    if (linelen < PKT_LEN_SIZE) return GIT_EBUFS;   // 有長度前檢查
    memcpy(num, line, PKT_LEN_SIZE);                 // size 是常數 PKT_LEN_SIZE
    num[PKT_LEN_SIZE] = '\0';
    ...
}
```
這裡 size 其實是常數 `PKT_LEN_SIZE`（weggli 把它綁進了 `$s` 因為它是個識別子），dst `num[PKT_LEN_SIZE+1]` 剛好夠、前面還有 `linelen` 檢查——**也是誤報**（結構像但實際安全）。

兩個都是誤報——但**這正是預期且健康的結果**：漏斗的職責是把「值得花人時看的點」從 287 壓到 2，而不是保證那 2 個都是 bug。你花在 triage 的人時從「讀 287 個」降到「讀 2 個」，這就是全部的價值。真有 bug 的 repo，這 2 個裡就會有真陽。

### L3 — CodeQL 深查（接續章節，理論說明）

上面的例子在 L1/L2 就收斂到 2 個、人眼直接能判，沒動用 CodeQL。但當 L2 後還剩幾十個、且判定卡在「size 到底可不可控」時，就輪到 CodeQL：**對這批 weggli 候選點，寫一條 global taint query，問「哪些 memcpy 的 size 是從網路 read / 檔案解析等不可信 source 流過來的」**（你在 Ch 22 學過）。CodeQL 把「size 是變數」升級成「size 來自污染源、且中間無 sanitizer」——這是 weggli 給不了的跨函式判斷。做法是把 weggli 找到的 sink 位置當 CodeQL query 的 sink 集合，只在這幾十個點上追 taint，而不是對全 repo 盲追。

### L4 — 動態驗證（接 Ch 37）

CodeQL 確認「size 可控 + 無 sanitizer」的高可信命中，最後用**動態**收尾：構造輸入實際觸發、寫 PoC，或丟給 fuzzer 讓它自己撞出 crash（Ch 37 靜態+動態）。到這步才叫「確認的漏洞」。靜態全程給的都是「候選/高可信候選」，動態才給「可觸發的證明」。

## 為什麼方向是「快而粗 → 慢而精」

漏斗方向不能反。理由是**經濟學**，不是偏好：

- **便宜工具砍掉的絕對數量最大**：rg 毫秒砍掉 99%（287→…其實 L0 是入口，真正的大砍在 L1：287→99），把幾百萬行壓到幾百個。這幾百萬行如果留給 CodeQL，光跑就是天文數字的機時。
- **貴工具的成本只該花在最可疑的少數**：CodeQL 每命中幾分鐘的 flow 分析，只有在候選已經被砍到幾十個時才划算。在幾萬個候選上跑 = 浪費 + 輸出淹沒（你 triage 不完）。
- **雜訊要在便宜的地方濾掉**：rg 的雜訊（註解命中）讓 weggli 濾（秒級）；weggli 的結構誤報（有本地 guard）讓人眼/CodeQL 濾（分鐘級）。**每種雜訊都在「能最便宜濾掉它」的那一層濾掉**。把雜訊帶到下游 = 用貴刀砍便宜刀該砍的東西。

一句話：**先用便宜工具砍掉 99%，貴工具只花在最可疑的 1%**。反過來（一上來就 CodeQL 全掃）是把最貴的資源鋪在最寬的面上，必然又慢又淹。

## 每層記錄，避免重工

漏斗每一層都要**記下輸入/輸出/砍掉的理由**（接 Ch 12 triage 記錄）。原因：

- **可重跑**：pattern 改一版重跑，有紀錄就能 diff「這版新增的候選」，只看新的，不用從 287 重來。
- **可交接**：隊友接手看你的漏斗紀錄，知道每層砍了什麼、為什麼，不用重推。
- **可回溯**：L4 發現漏了個真 bug，回頭查是哪一層的 pattern 太緊把它砍掉了——沒紀錄就查不出。

最低限度：一個表格記「層 / 工具 / pattern / 輸入數 / 輸出數 / 砍掉理由」。上面的 libgit2 走查就是這種紀錄的雛形（287→99→2，每步理由都寫了）。這直接接 Ch 42 的 audit SOP——SOP 就是把這套漏斗流程 + 記錄固化成你每次審計都跑的標準程序。

## 踩雷集錦

**錯誤直覺：「repo 到手，直接對整個 tree 開 CodeQL 最徹底。」**
正確認識：這是新手頭號浪費。整 repo 建 database 幾分鐘、一條 global taint query 在幾百萬行上跑幾十分鐘甚至更久，回你**幾千個命中**——你既跑得慢、又 triage 不完、真 bug 淹在雜訊裡。正確是**先漏斗**：rg/weggli 秒級把面砍到幾十個候選，只對這幾十個點開 CodeQL 追 taint。CodeQL 是精密手術刀，不是推土機。徹底 ≠ 一開始就用最重的刀。

**錯誤直覺：「漏斗中間那層可以跳過，直接從 rg 跳到 CodeQL 深查。」**
正確認識：跳層會讓貴工具吃到本該被上層砍掉的量。rg 直接餵給 CodeQL = CodeQL 在幾千個文字命中（含註解雜訊）上跑 flow，慢且雜。weggli/ast-grep 這層的作用就是**用秒級結構匹配把「幾千」變「幾十」再交棒**。每一層都在為下一層減負，跳掉就是把減負的活推給更貴的刀。

**錯誤直覺：「每層不用記，反正工具能重跑。」**
正確認識：能重跑不等於不用記。不記錄的代價是：pattern 改一版，287 個候選又從頭 triage 一遍（上次判過的全混進來）；隊友接手從零推你的思路；漏了真 bug 回溯不出是哪層砍掉的。一個「層/pattern/輸入輸出/理由」的表就解決這些。這也是規模化（Ch 36 誤報治理的 baseline/diff）的地基——沒紀錄就沒 baseline。

**錯誤直覺：「一定有一把刀最強，學會它就夠了。」**
正確認識：沒有全能刀。CodeQL 深但慢且要建庫、weggli 快但只 C/C++ 且不追 flow、rg 最快但不懂結構、comby 能改寫但語意淺。**每把刀都是某個「深度 vs 成本 vs 廣度」取捨點**，漏斗的意義正是讓每把刀只做它最划算的那一層。指望一把刀包辦 = 要嘛在寬面上用貴刀（慢），要嘛在深問題上用淺刀（漏）。工具觀的成熟標誌就是「不再找最強的刀，而是排最省的接力」。

**錯誤直覺：「漏斗底端剩的都該是真 bug，全是誤報代表流程失敗。」**
正確認識：漏斗的職責是**把人時集中到最可疑的少數**，不是保證那少數全真。我們在 libgit2 收斂到的 2 個都是誤報（有 clamp、有前置檢查）——這**完全正常**：結構工具看不到本地 guard，人眼/CodeQL 才補得上。價值在於你只讀了 2 個而非 287 個。誤報率高的是你的 pattern 該收緊的信號（Ch 12 批砍、Ch 36 治理），不是漏斗失敗。

## 進階延伸

- **漏斗是可調的，不是固定五層**：層數與工具依目標調整。目標是 C/C++ 記憶體 bug，可能 rg→weggli→CodeQL 三層就夠；目標是多語言注入，可能 rg→ast-grep→Semgrep taint→手讀。核心不變的是「快而粗→慢而精、每層砍一個數量級、雜訊在最便宜處濾掉」。把它當方法論而非固定 pipeline。
- **反向漏斗（bug-first / variant hunting）**：另一種玩法不是從「全 repo」往下收，而是從「一個已知 bug」往外擴——把 bug 的危險結構抽成 weggli/CodeQL pattern，掃全 repo 找變體（Ch 43）。方向相反，但同樣是「便宜工具先鋪面、貴工具確認」的經濟學。
- **層間介面的自動化**：成熟團隊會把「上層輸出 → 下層輸入」自動化——weggli 的命中位置自動轉成 CodeQL query 的 sink 集合、SARIF 串各層結果（Ch 39）。手動接力能跑，但規模化要讓漏斗變 pipeline（接 Ch 42 SOP、Ch 17/39 CI 與 SARIF）。
- **漏斗的過濾率是 repo 的指紋**：同一組 pattern 在不同 repo 的收斂數字（287→99→2）反映該 repo 的編碼風格與防禦習慣——某 repo 的 memcpy 大量帶本地 clamp，某 repo 幾乎裸奔。記錄這些數字久了，你會對「哪類 repo 值得深挖」有量化直覺。

## 本章重點整理

- 四把刀不是競爭是**漏斗層級**：L0 rg（毫秒、文字粗篩）→ L1 weggli/ast-grep（秒、結構縮面）→ L2 Semgrep/Joern（分鐘、輕量語意/taint）→ L3 CodeQL（分鐘~十幾分、跨函式 global taint）→ L4 人 + 動態（PoC/fuzz、確認）。
- **每往下一層：成本升一個數量級、候選降一個數量級**。便宜工具砍絕對量最大、雜訊在能最便宜濾掉它的那層濾掉。
- 真跑證據（libgit2、12.7 萬行）：rg 撈 287 個 memcpy → weggli `-R 's!=^size$'` 砍到 99（0.4s）→ 加 `char $b[_]` 約束 dst 砍到 **2**（0.088s）。人眼只 triage 這 2 個（都誤報，但那正是漏斗把人時從 287 壓到 2 的價值）。
- **方向必須「快而粗→慢而精」**：貴工具只花在便宜工具留下的少數，這是經濟學不是偏好。跳層/一上來開 CodeQL 全掃 = 把最貴資源鋪最寬面，又慢又淹。
- **每層記錄**（層/pattern/輸入輸出/理由）避免重工、可交接、可回溯漏砍，是規模化（Ch 36）與 SOP（Ch 42）的地基。
- 沒有全能刀，工具觀成熟 = 不找最強的刀，而是排最省的接力。

- 畫出五層漏斗，標出每層的工具、成本量級、過濾率。為什麼成本與候選數量必須反向？
- 用 libgit2 的 287→99→2，說明每一步砍掉的是哪一類、用什麼約束砍的。為什麼最後 2 個是誤報卻不代表流程失敗？
- 為什麼「repo 到手直接對整 tree 開 CodeQL」是浪費？把 CodeQL 放對層級後，它的輸入應該是什麼、由哪一層產生？
- 漏斗某層 pattern 太緊，把一個真 bug 砍掉了——沒有每層記錄的話，你事後查得出是哪層砍的嗎？記錄該包含哪些欄位？
- weggli 找到「size 是變數 `n`」的 memcpy，但你在 libgit2 看到 `n` 前一行被 clamp 成 `<= sizeof(tmp)`——這說明結構工具的什麼根本限制？這個判斷要靠哪一層補上？
