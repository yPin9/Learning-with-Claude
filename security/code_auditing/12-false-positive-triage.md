# Ch 12 — 誤報三角與可信度分級

> **目標**：審計真正難的不是讓工具吐出命中，是從幾百上千個命中裡篩出真的那幾個。這章建立一套 **triage（分流判定）方法論**：一個命中怎麼快速判真假、怎麼按可信度分級、怎麼批次砍掉一整類誤報、怎麼記錄理由避免重工。這是全課裡最不性感但最值錢的技能——會寫 query 的人很多，能在一千個命中裡穩定挖出真 bug 的人很少。

前面三章讓你能大量產出 candidate。現在殘酷的現實來了：你對一個真實 codebase 跑一條 memcpy taint query，可能回來 800 個命中，其中 795 個是誤報。**逐個從頭讀是必死的路**——讀到第 50 個你就麻木了，第 780 個那個真 bug 會被你當雜訊劃掉。triage 的全部意義是：**用結構化的判定順序，讓你在正確的命中上花時間，在明顯的誤報上花三秒**。

## 誤報三角：一個命中可能假在哪

一個 taint 命中 = 「source → sink，中間無有效 sanitizer」。它是誤報，只可能是這條鏈的某一環站不住。我把它畫成一個三角，triage 就是逐角檢查：

```
                  ┌─────────────┐
                  │   SOURCE    │  這個 source 真的攻擊者可控嗎？
                  │  真的可控？  │  （還是其實被上游固定/內部產生）
                  └──────┬──────┘
                         │
        ┌────────────────┼────────────────┐
        │                                  │
 ┌──────▼──────┐                    ┌──────▼──────┐
 │    SINK     │                    │    PATH     │
 │ 真的危險？   │                    │  真的可達？  │
 │（危險維度對嗎）│                   │（&有效 sanitizer嗎）│
 └─────────────┘                    └─────────────┘
```

四個判定問題，任何一個答「否」，這個命中就是誤報：

1. **source 真的攻擊者可控嗎？** 工具標的 source 可能其實被上游寫死、被前面的邏輯固定成安全集合、或根本是內部產生的常數。
2. **sink 真的危險嗎（危險維度對嗎）？** 命中的 sink 可能在這個上下文不危險——`memcpy` 的 size 是污染的，但 dst 是動態配置且大小同源（不會溢位）；或污染流到的是 sink 的無害參數。
3. **path 真的可達嗎？** 工具算出的 flow 可能經過一個實際永不成立的 branch（infeasible path），或需要一個矛盾的條件組合。
4. **中間真的沒有有效 sanitizer 嗎？** 最常見——路徑上其實有個工具沒建模的 sanitizer（自訂的檢查、隱含的長度約束、型別限制）把污染擋住了。

**triage 就是對每個命中，用這四問快速定位它假在哪、或確認它四問全過（真陽）**。

## 可信度分級框架

不是每個命中都值得深查。給每個命中打一個粗略的可信度等級，決定投入多少時間：

| 等級 | 判定 | 該做什麼 |
|---|---|---|
| **A / 高可信** | 四問初判全過：source 明顯可控、sink 明顯危險、path 直接、看不到 sanitizer | 立刻深查，往 PoC 走（Ch 37 動態驗證） |
| **B / 中** | 大致成立但有一問不確定（sanitizer 存不存在？path 可達嗎？） | 花幾分鐘查那一問，確認後升 A 或降 C |
| **C / 低** | 明顯某一問不成立，但不是 100% 確定 | 記一句理由，擱置；有餘力再回頭 |
| **FP / 誤報** | 四問中明確有一問「否」 | 記錄「假在哪」，關掉，且**看能不能整批砍同類** |

分級的價值是**時間分配**：A 級可能只有 5 個，你把 80% 的精力給它們；C/FP 級佔 90%，你每個花不超過幾十秒。**麻木讀完 800 個是輸家做法；分級後只深查 5 個 A 是贏家做法**。

## 排序策略：把最可能真的排前面

分級之外，用幾個維度給命中**排序**，讓高價值的浮上來：

- **按 exploitability（可利用性）排**：能到 RCE/提權的排前面，DoS/資訊洩漏其次，理論性問題最後。一個 pre-auth 的 memcpy 溢位 > 一個要 root 才觸發的 off-by-one。
- **按 reachability（可達性）排**：pre-auth、遠端、預設啟用的路徑上的命中優先。這接 Ch 10 的攻擊面地圖——命中落在你標為 ★★★ 的攻擊面上，排最前。
- **按 source 可信度排**：source 是「純網路輸入」的優先於「要先通過認證才餵得進的輸入」。
- **按 sink 嚴重度排**：記憶體寫 > 記憶體讀 > 邏輯問題。但**別只信工具給的 severity**（下面踩雷）。

實務：先分級（A/B/C/FP），A 級內部再按上面排序，從最上面開始查。

## 批次砍誤報：triage 的核心加速

逐個判定會累死。真正的效率來自**認出「一整類」誤報然後一次砍掉**。常見的可批砍模式：

- **同一個假 source**：工具把某個其實不可控的 API 標成 source，於是幾十個命中共用這個假起點。確認這個 source 不可控一次，那幾十個全砍。
- **同一個未建模的 sanitizer**：專案有個自訂 `check_bounds()`，工具不知道它是 sanitizer，於是所有經過它的 flow 都誤報。把它加進 query 的 sanitizer（或 triage 時心裡記住），整批消失。
- **同一個測試/範例目錄**：`tests/`、`examples/`、`third_party/` 裡的命中通常不在攻擊面上，可整目錄降級或排除。
- **同一個 wrapper 模式**：某個 flow 都經過一個安全 wrapper，認出來後同模式全砍。

**批砍的前提是先分類再判定**，不是逐個看。你要主動找「這批命中有什麼共通結構」，而不是把它們當 800 個獨立事件。這也是為什麼 triage 要記錄理由——記下的理由讓你發現「欸這 30 個都是同一個原因」。

## 具體：走三個命中的 triage

假設對某 C 服務跑 memcpy taint query，回來三個命中，逐一走判定。

**命中 1：**
```c
uint32_t len = read_be32(pkt);        // source: 網路封包
char dst[64];
memcpy(dst, pkt->body, len);          // sink
```
四問：source 可控（網路封包，是）✓；sink 危險（固定 64-byte stack buffer，len 來自網路，是）✓；path（直達，可達）✓；sanitizer（memcpy 前**沒有** `if (len > 64)`，無）✓。**四問全過 → A 級真陽**。這是 stack overflow，直接往 PoC。

**命中 2：**
```c
uint32_t len = read_be32(pkt);
if (len > sizeof(dst)) return -1;     // 工具沒認出這是 sanitizer？
memcpy(dst, pkt->body, len);
```
四問：source 可控 ✓；sink 危險 ✓；path ✓；sanitizer——**路徑上有 `if (len > sizeof(dst)) return -1`，這是有效的邊界檢查**，taint 到 sink 時 len 已被 clamp。**sanitizer 這問「否」→ 誤報**。記錄理由：「memcpy 前有 size guard，工具未建模」。而且——**去看還有多少命中是同一個 guard 模式，一起砍**。

**命中 3：**
```c
uint32_t len = get_config_len();      // source? 來自 config
memcpy(dst, src, len);
```
四問：source——`get_config_len` 讀的是 config 檔。**攻擊者控制得了 config 嗎？** 若 config 只有 root 能寫、且威脅模型不含本地 root，這個 source 不可控 → 誤報（在此威脅模型下）。但若 config 能被較低權限方或遠端影響（例如透過某個 CONFIG SET 指令），它就是真 source。**這問要回到 Ch 10 的威脅模型才能定**——所以標 **B 級**，去查 config 的寫入路徑，再定升降。

三個命中，一個真陽（深查）、一個誤報（批砍同類）、一個待查（回威脅模型）。**這就是 triage 的節奏：不是全查，是快速定位每個假在哪或值不值得。**

## 記錄理由：不記等於重工

triage 最容易被跳過、代價最大的一步：**每個判定寫一句為什麼**。

- FP 記「假在哪」（source 不可控 / 有 guard / 測試目錄），下次同 query 重跑、或別人接手，不用重判。
- B 級記「卡在哪一問」，回頭時直接續查那一問，不用從頭。
- A 級記「四問怎麼過的 + flow 摘要」，寫報告時直接用。

不記錄的後果是**重工地獄**：query 改一版重跑，800 個命中裡 795 個上次判過的又混進來，你又從頭看一遍。有紀錄（哪怕是一個 CSV：命中位置 / 等級 / 理由）就能 diff 出「這版新增的命中」，只看新的。這直接接 Ch 36 的誤報治理（規模化、SARIF baseline）和 Ch 38 的 diff-based 審計。

## 踩雷集錦

**錯誤直覺：「命中不多，逐個從頭讀完最穩。」**
正確認識：逐個讀不分類，你會在第 50 個就麻木，把後面的真 bug 當雜訊劃掉——人的判定品質隨疲勞崩塌。而且逐個讀放棄了「批砍同類」這個最大加速。正確做法永遠是**先分級、找共通結構、批砍，再深查少數 A 級**。命中越多，逐個讀越是災難。

**錯誤直覺：「工具標了 high severity，那就是嚴重的真 bug。」**
正確認識：工具的 severity 是**規則作者對「這類 sink 一般多嚴重」的先驗**，不是對**你這個具體命中**的判定。high severity 的命中可能 source 根本不可控（誤報）；low severity 的可能在 pre-auth 路徑上（其實很嚴重）。severity 只是排序的一個弱信號，四問才是判定。只信 severity = 把判斷外包給不了解你威脅模型的工具。

**錯誤直覺：「這個 flow 看起來很像那個經典漏洞，八成是真的。」**
正確認識：「看起來像」不等於「確認是」。像不像是模式匹配，確認要走完四問——特別是「path 真的可達嗎」和「真的沒 sanitizer 嗎」。無數「看起來很像 UAF」的命中，實際上那條 free 路徑和 use 路徑永不同時發生（infeasible）。把「像」當「是」會讓你花幾天寫一個不可能觸發的 PoC。判定靠四問，不靠既視感。

**錯誤直覺：「triage 時心裡有數就好，不用寫下來。」**
正確認識：不記錄 = 保證重工。query 改一版重跑、隔天回來、交接給隊友，沒有紀錄就得全部重判。而且沒紀錄你發現不了「這 30 個是同一原因」的批砍機會。一行紀錄（位置/等級/理由）省下的是下次的幾小時。這也是規模化審計（Ch 36）的地基——沒有 triage 紀錄就沒有 baseline、沒有 diff。

**錯誤直覺：「誤報就是誤報，關掉就好。」**
正確認識：每個誤報都在告訴你「query 哪裡不準」。批量的同類誤報通常意味著**一個該加進 query 的 sanitizer 或該排除的 source**——修 query 比一個個關命中划算得多。triage 不只是篩結果，是 query 的回饋迴路：誤報模式 → 改 query → 下次更乾淨（Ch 15 rule engineering）。

## 進階延伸

- **可達性的自動化**：「path 真的可達嗎」這問，輕則靠讀 code、重則靠符號執行/約束求解判 infeasible path（你在 `symex_taint` 學過）。審計實務多半停在「人工看 branch 條件矛不矛盾」，但知道有工具能自動判很重要（Ch 37 靜態+動態）。
- **ranking 的機器化**：大規模時人工排序不夠，商業 SAST 用 ML/啟發式給命中打分（歷史 FP 率、程式碼熱度、複雜度）。CodeQL 的結果也可帶 `@precision`/`@severity` metadata 供排序。原理仍是本章的四問維度，只是自動化。
- **triage 疲勞與抽樣**：命中上萬時連分級都做不完。策略是分層抽樣——每一類抽幾個判，若整類都 FP 就整類降級；只對高攻擊面區塊做全量 triage。這是 Part 7 規模化的核心權衡。

## 本章重點整理

- 審計的難點在**從一堆命中篩出真的**，不在產出命中。逐個從頭讀是必敗。
- **誤報三角/四問**：source 真可控？sink 真危險？path 真可達？真的無有效 sanitizer？任一「否」即誤報。
- **可信度分級**（A/B/C/FP）決定時間分配：80% 精力給少數 A 級，FP/C 每個花幾十秒。
- **排序**按 exploitability × reachability × source 可信度 × sink 嚴重度，接 Ch 10 攻擊面地圖。
- **批砍同類**是核心加速：找共通結構（假 source、未建模 sanitizer、測試目錄）一次砍一批。
- **記錄理由**避免重工、催生批砍、餵報告，是規模化（Ch 36）與 diff 審計（Ch 38）的地基。

## 自我檢核

- 畫出誤報三角，寫出四個判定問題。給一個命中，示範怎麼用四問定位它假在哪。
- 為什麼「逐個從頭讀完」在命中多時是必敗？triage 的兩個加速（分級、批砍）各解決什麼？
- 工具給一個命中打 high severity，你為什麼不能直接信它是真 bug？severity 在 triage 裡扮演什麼角色？
- 「這 flow 看起來很像 UAF」——你還要查哪兩問才能從「像」到「確認是」？舉一個「像但其實 infeasible」的情境。
- 為什麼 triage 一定要記錄理由？它跟 Ch 36 的誤報治理、Ch 38 的 diff 審計怎麼接？
- 一批 30 個命中都經過某個自訂 `validate_len()`——你會怎麼一次處理它們？這同時給你什麼「改 query」的訊號？

- **《The DevSecOps Playbook》/ 各家 SAST triage 指南中「三角/可信度」章節**——業界對 FP triage 的實務整理。用法：跟本章的四問對照，補充團隊/流程層面的 triage（誰判、怎麼分工）。前提：本章。偏工程流程。
- **`symex_taint` 課程中 infeasible path / 約束求解章節**——「path 真的可達嗎」這問的硬核版。用法：想把「人工看 branch 矛不矛盾」升級成「用 solver 自動判」時讀。前提：符號執行基礎。接 Ch 37。
