# Ch 42 — 打造你的 audit SOP

> **目標**：把整門課的零件——攻擊面建模、四把刀、漏斗、triage、動態驗證、報告——整合成一套**可複製的個人 audit SOP（standard operating procedure，標準作業程序）**。你會拿到一張完整流程圖、一套「什麼 target 用哪把刀」的決策樹、offensive 現實下的時間盒與精力分配建議，和一份可以直接抄去用的 check-list 模板。但先把最重要的一句話放前面：**SOP 是預設路徑，不是鐵軌**——它幫你在陌生 target 前不會呆掉，也讓你有個明確的東西去「刻意偏離」。不會偏離的 SOP，就退化成上一章罵過的教條。

## 為什麼要有 SOP，以及 SOP 不是什麼

沒有 SOP 的審計長這樣：打開 repo，隨便找個看起來有趣的檔案開始讀，讀到一半跳去掃一輪工具，被一堆命中淹沒，隨機點開幾個，累了跑去追一個新奇 bug，時間到了交一份東拼西湊的報告。**每個動作都在做事，合起來卻沒有覆蓋率、沒有優先級、沒有止損。** 這正是 [Ch 41](./41-auditing-antipatterns.md) 那些反模式的溫床。

SOP 解決的是**認知負荷**問題。審計要同時追蹤太多東西——攻擊面在哪、掃到哪了、哪些命中還沒 triage、哪個線索追到一半、時間還剩多少。人腦的工作記憶塞不下這些。SOP 把「下一步該做什麼」這個決策**外包給流程**，讓你的腦力全用在真正需要判斷的地方（這個命中是真的嗎？這個 pattern 該抽多抽象？這條鏈打得通嗎？）。它是**鷹架**——托著你，讓你專心砌真正重要的那幾塊磚。

但 SOP 有兩張臉。好的 SOP 是**預設路徑 + 明確的偏離點**：它告訴你「一般情況這樣走」，同時標清楚「遇到這些情況該跳過哪步、加做哪步」。壞的 SOP 是**無腦全流程**：不管 target 長怎樣，每次都從頭到尾走一遍，攻擊面建模也走、CodeQL database 也建、動態驗證也做——即使這個 target 根本不需要。壞 SOP 比沒 SOP 更糟，因為它給你一種「我很嚴謹」的假象，同時浪費大把時間在對這個 target 沒意義的步驟上。這章要教的是前者。

## 完整流程：從 target 到報告

先給全景 ASCII 流程圖，每個框對回它在哪一章詳講。這是**預設路徑**——之後的決策樹會告訴你哪些框可以跳、哪些要加。

```
┌─────────────────────────────────────────────────────────────────┐
│                      個人 audit SOP（預設路徑）                    │
└─────────────────────────────────────────────────────────────────┘

  ① target 選擇 ─────────────────────────────────► [Ch 10, 本章決策樹]
     選什麼審？攻擊面大不大、build 得起來嗎、
     有沒有已知 CVE 可當變體種子、投報率如何
        │
        ▼
  ② 攻擊面建模 ───────────────────────────────────► [Ch 10]
     entry point 在哪、trust boundary 在哪、
     哪些是 source（user 可控輸入）、
     這個 codebase 特有的 sink / wrapper 有哪些
        │
        ▼
  ③ source / sink / sanitizer 盤點 ────────────────► [Ch 9, Ch 11]
     把攻擊面翻成具體清單：
     source 清單、sink 清單、既有 sanitizer 清單
        │
        ▼
  ④ 選工具 & 跑漏斗 ──────────────────────────────► [Ch 33-35]
     ┌──────────────────────────────────────────┐
     │  weggli / 結構化 grep  ── 縮面（廣、快）  │
     │        │  高風險候選區域                  │
     │        ▼                                  │
     │  Semgrep / Joern  ── 篩（中精度、快迭代） │
     │        │  可疑資料流                      │
     │        ▼                                  │
     │  CodeQL  ── 深挖（跨函式 taint、變體）    │
     └──────────────────────────────────────────┘
        │
        ▼
  ⑤ 寫 / 跑 query ───────────────────────────────► [Ch 13-32, Ch 26]
     從已知 bug 抽 pattern → 寫 query →
     抽象化驗證（換寫法測漏報）→ 跑全 repo / 生態
        │
        ▼
  ⑥ triage & 分級 ───────────────────────────────► [Ch 12, Ch 36]
     按 exploitability（不是 severity）排序 →
     逐條判真陽/誤報/真但不可達 → 記錄理由 →
     誤報集中就修 query（沉澱回 query）
        │
        ▼
  ⑦ 動態驗證 ─────────────────────────────────────► [Ch 37, symex_taint, advanced_fuzzing]
     真陽候選上 fuzzer / symbolic execution
     驗可達性、構造 PoC、把 primitive 追成後果
        │
        ▼
  ⑧ 產出報告 / PR ───────────────────────────────► [Ch 39]
     真 bug → PoC + root cause + 修法 → report / PR
     覆蓋率邊界誠實標明（哪些沒審到）
        │
        └──► 迭代：把新確認的 bug 當新種子，回 ⑤ 抽變體
```

八個步驟，但**兩個關鍵洞察**藏在圖裡：

**其一，這不是一條直線，是一個帶迴圈的漏斗。** 步驟 ④→⑤→⑥ 是主迴圈：你會反覆「篩→深挖→triage→修 query→再深挖」，query 每迭代一次精度就高一點。而步驟 ⑧ 確認一個真 bug 之後，這個 bug 本身變成新的變體種子，把你送回步驟 ⑤——這就是變體分析的複利（見 [Ch 1](./01-reading-to-auditing.md)、[Ch 26](./26-codeql-cve-to-query.md)）。一場好的審計，一個 bug 會滾出一串同型 bug。

**其二，前三步（建模）決定後五步的天花板。** 如果步驟 ②③ 沒把這個 codebase 特有的 `copy_field()` wrapper 盤進 sink 清單（回想 [Ch 41](./41-auditing-antipatterns.md) 情境 A），後面 query 寫得再漂亮也追不到它。建模是投報率最高的一步，也是最多人想跳過直接掃的一步——這是後面踩雷集錦的重點。

## 決策樹：什麼 target 用哪把刀

流程圖是預設路徑，但**選哪把刀、要不要建 CodeQL database、要不要手讀**，全看 target 長怎樣。這棵決策樹是把「[Ch 32](./32-joern-vs-codeql.md) 四工具對比 + [Ch 35](./35-funnel-combining-tools.md) 漏斗」濃縮成可執行的判斷。

```
target 到手，先問四個問題：

Q1. build 得起來嗎？（有沒有完整的編譯環境 / build script）
    ├── build 得起來 ──────────────► CodeQL 可用，深挖主力用它
    └── build 不起來 / 殘缺 source ─► CodeQL 出局，改用 Joern
                                       （不需 build 就能建 CPG，見 Ch 29-32）
                                       + weggli（C/C++ 結構化 grep）

Q2. 語言是什麼？
    ├── C / C++ ───────► weggli 縮面（最快）→ CodeQL/Joern 深挖
    ├── web 語言(JS/Py/
    │   Ruby/Go/Java) ─► Semgrep 快篩（跨語言、registry 現成規則多）
    │                     → CodeQL 深挖跨函式 taint
    └── 混合 / 多語言 ─► Semgrep（跨語言一致）當主篩

Q3. 有沒有已知 CVE / patch 當變體種子？
    ├── 有 ──► CVE→query 路線（Ch 26）：讀 patch、抽 root cause pattern、
    │          寫 query 掃原 repo + 相似專案（MRVA，Ch 27）
    └── 沒有 ► 攻擊面探索路線：先建模（Ch 10）找高風險區，
               手讀開路挖第一個 bug，再回頭抽 pattern

Q4. codebase 多大？投報率如何？
    ├── 小（< 幾千行）─────► 手讀可能比建 database 快，直接讀
    │                        （建 CodeQL db 的固定成本 > 收益）
    ├── 中 ────────────────► 漏斗全上：weggli/Semgrep 縮面 → CodeQL 深挖
    └── 大（十萬行+）──────► CodeQL database 一定值得建，
                             建一次掃無數 query，攤提固定成本
```

三條要記住的判斷法則從這棵樹裡浮出來：

**法則一：build 不起來，CodeQL 就出局，這是硬約束。** CodeQL 需要在編譯過程中觀察程式來建 database（見 [Ch 20](./20-codeql-databases.md)）。拿到一個殘缺的 source dump、或一個你死活 build 不出來的老專案，別浪費半天跟 build 系統搏鬥——直接上 Joern（CPG 不需要 build）和 weggli。這是 Joern 存在的最大理由。

**法則二：CodeQL database 值不值得建，看攤提。** 建 database 是一筆**固定成本**（要 build、要跑 extractor、要等）。這筆成本只有在你**要跑很多條 query**、或 codebase **夠大**時才划算。target 只有幾千行、你只想查一種 pattern——手讀或 Semgrep 快篩可能整體更快。別為了「用上最強的刀」而建一個你只查一次的 database。

**法則三：有 CVE 種子就走變體路線，沒有就先建模開路。** 有已知 bug，你的起點是現成的——讀 patch 抽 pattern（[Ch 26](./26-codeql-cve-to-query.md)）是最高效的入場。沒有種子，你得先靠攻擊面建模 + 手讀挖出第一個 bug，才有 pattern 可抽。兩條路最後匯流到同一個變體迴圈。

## 時間盒與精力分配：offensive 現實

真實審計的核心約束是**時間有限**——一場 CTF 幾小時、一次 bug bounty 一個週末、一個委託幾天到幾週。無限時間下的最優策略（全部手讀 + 全 query 跑遍 + 全命中驗證）在現實裡不存在。所以 SOP 必須內建**時間盒（time-boxing）**：每個階段給一個上限，時間到就**強制往下走或止損**，不管你多想繼續。

時間盒對抗的是兩個致命的時間黑洞：**建模階段的完美主義**（想把攻擊面畫到滴水不漏，結果一天過去還沒開始掃）和**深挖階段的沉沒成本**（一個線索追了三小時追不出來，卻因為「都追這麼久了」不肯放）。時間盒是預先設好的止損線，讓你在情緒上頭前就把規則定好。

一個**一週委託**的粗略精力分配（比例可調，重點是「有明確配額」而非「照著跑」）：

```
   階段                       配額      止損訊號 / 偏離規則
   ────────────────────────  ──────    ──────────────────────
   ①②③ target+攻擊面建模     ~15%      建模夠指出高風險區就停，
                                        別追求完備——邊掃邊補
   ④⑤ 漏斗篩選+寫 query       ~30%      一條 query 迭代到「訊噪比可接受」
                                        就跑，別無限打磨精度
   ⑥ triage                   ~25%      按 exploitability 排序，
                                        從最可能真的看；單條追不動先記
   ⑦ 動態驗證+PoC             ~20%      每個候選給固定時數，
                                        打不出 PoC 就降級為「疑似」記錄
   ⑧ 報告                     ~10%      預留死線前的固定時段，別擠壓
```

三條精力分配的心法：

**其一，建模別追求完備，追求「夠指路」。** 攻擊面建模（步驟 ②）的產出不是一份完美地圖，是一份「先挖哪裡」的優先清單。畫到 80% 就該停手開始掃——剩下的 20% 邊掃邊補。想把建模做完美是最常見的時間黑洞。

**其二，query 打磨到「訊噪比可接受」就跑，別追零誤報。** 一條 query 永遠可以再精一點，但邊際收益遞減。判準是：跑出來的命中，你 triage 得動嗎？50 條裡有 5 條真的，可接受，跑。500 條裡全是噪音，回去修。別在「把誤報從 20 條降到 5 條」上耗掉本該用來 triage 的時間。

**其三，每個深挖候選設「止損時數」。** 動態驗證 / 追 PoC 是最容易掉進沉沒成本的地方。事先規定每個候選「追 N 小時打不出 PoC 就降級記錄、換下一個」。你手上通常有多個候選，把時間平均分配、先廣掃一遍，比把全部時間押在第一個上更可能收割。追不出來的**記下來**（連同你追到哪、卡在哪），不是丟掉——它可能是下次的起點，也是報告裡誠實的「疑似項」。

## 可直接抄的 check-list 模板

下面這份是可以複製去實戰的骨架。它刻意做成**可勾選 + 帶偏離提示**的形式——每一項後面標了「什麼情況跳過 / 加做」。照抄，然後根據你的 target 刪改。

```
═══════════════════════════════════════════════════════════
  AUDIT CHECK-LIST ── target: ____________  日期: ________
═══════════════════════════════════════════════════════════

[① TARGET & 範圍]
  [ ] 明確審計範圍與死線（時間盒總量：____ 小時/天）
  [ ] build 得起來嗎？  是→CodeQL 可用 / 否→Joern+weggli
  [ ] 主要語言：________  → 對應主篩工具：________
  [ ] 有已知 CVE/patch 當種子嗎？ 有→變體路線 / 無→建模開路
  [ ] codebase 規模：____ 行 → 值得建 CodeQL db 嗎？ Y/N

[② 攻擊面建模]  ── 追「夠指路」不追完備
  [ ] entry point 清單（誰把外部輸入送進來）
  [ ] trust boundary（哪裡從不可信變可信）
  [ ] 高風險區優先序（parser/反序列化/特權操作/記憶體操作）
  [ ] 【關鍵】codebase 特有的 wrapper / 自訂 sink（別漏！見 Ch41情境A）

[③ SOURCE / SINK / SANITIZER 盤點]
  [ ] source 清單（user 可控輸入點）
  [ ] sink 清單（危險原語 + 上面盤到的自訂 wrapper）
  [ ] 既有 sanitizer 清單（query 要建模成 barrier）

[④⑤ 漏斗 & QUERY]
  [ ] 縮面：weggli/Semgrep 快篩高風險區
  [ ] 深挖：對候選寫 CodeQL/Joern 跨函式 taint query
  [ ] 【關鍵】query 抽象化驗證：換寫法重寫 bug，query 還抓得到嗎？
  [ ] 跑全 repo（+ 相似專案 MRVA，若走變體路線）

[⑥ TRIAGE]  ── 按 exploitability 排序，不是 severity
  [ ] 命中按「多能打/多好打」排序
  [ ] 逐條判：真陽 / 誤報 / 真但不可達
  [ ] 【關鍵】每條 dismiss 記錄理由 + 失效條件
  [ ] 誤報集中某模式 → 修 query 加 barrier（別關規則）

[⑦ 動態驗證]  ── 每候選設止損時數
  [ ] 真陽候選上 fuzzer/symex 驗可達
  [ ] 構造 PoC，把 primitive 追成有意義後果
  [ ] 追不出 → 降級「疑似」+ 記錄卡在哪（別丟）

[⑧ 報告 / PR]  ── 預留固定時段
  [ ] 每個確認 bug：PoC + root cause + 建議修法
  [ ] 【誠實】覆蓋率邊界：哪些區域沒審到、為什麼
  [ ] 確認的 bug 回填為新種子 → 回 ⑤ 抽變體？

═══════════════════════════════════════════════════════════
  復盤（審計後做）：對照 Ch41 九反模式，我這次中了哪幾條？
═══════════════════════════════════════════════════════════
```

注意那四個標【關鍵】的項目——它們對應 [Ch 41](./41-auditing-antipatterns.md) 裡傷害最大的四個反模式（漏盤自訂 sink、query 過擬合、不記錄 triage、亂關規則）。check-list 的價值不是幫你記得每一步，是幫你**在壓力下不跳過最容易被跳過、代價又最高的那幾步**。

## 踩雷集錦

**錯誤直覺：「SOP 就是照著從頭走到尾，越完整越嚴謹。」**
正確認識：無腦全流程是壞 SOP 的定義（本章開頭就在講）。一個 build 不起來的 target，你花半天硬要建 CodeQL database 就是災難——決策樹早叫你跳到 Joern。一個三千行的小 target，你走完整套攻擊面建模 + database + MRVA，固定成本遠超收益，手讀早讀完了。SOP 的每一步都帶「什麼情況跳過」的偏離規則，**不是**因為偷懶，是因為對這個 target 那步沒有正的投報率。嚴謹體現在「為這個 target 選對步驟」，不是「步驟數量最多」。

**錯誤直覺：「先掃再說，攻擊面建模等有空再補。」**
正確認識：跳過建模直接掃，是把 SOP 攔腰砍斷、也是最常見的翻車。前三步（建模）決定後五步的天花板——你沒盤到的 source/sink，query 再強也追不到（[Ch 41](./41-auditing-antipatterns.md) 情境 A 的 `copy_field()` wrapper 就是這樣漏掉的）。「先掃再說」感覺上是在推進（有命中出來了！），實際上你在用一張殘缺的地圖找路，掃出來的覆蓋率有系統性的洞而你不自知。建模不必完美，但**必須在掃之前先做到「夠指路」**。省這 15% 的時間，換來的是後面 85% 建在流沙上。

**錯誤直覺：「SOP 定好了就固定，每個 target 都同一套。」**
正確認識：SOP 僵化不因 target 調整，是把上一章罵的教條反模式搬到流程層。C 記憶體安全 target、web 反序列化 target、殘缺的韌體 dump——它們的攻擊面、能用的刀、值得深挖的地方**完全不同**。同一套 SOP 硬套，你會在 web target 上找 stack overflow、在韌體上想跑 CodeQL。正確的 SOP 是**一個核心骨架（建模→漏斗→triage→驗證→報告）+ 隨 target 換裝的具體工具與重點**。骨架穩定，血肉隨 target 變。每次審計後用復盤那一行去校準：這套流程對這類 target 哪裡不合身、下次怎麼改。

## 進階延伸

- **把 SOP 部分自動化成 pipeline**：check-list 裡機械性的步驟（跑固定 query pack、產 SARIF、diff 兩次掃描結果）可以固化成 CI / 腳本，讓你的腦力全留給需要判斷的步驟。[Ch 17](./17-semgrep-ci.md)（Semgrep CI）、[Ch 38](./38-diff-based-auditing.md)（diff-based 審計）、[Ch 39](./39-sarif-ecosystem.md)（SARIF 生態）合起來就是把 SOP 的重複部分工程化。目標不是全自動——是把「不需要判斷的事」自動掉，騰出人腦。
- **團隊版 SOP 與知識沉澱**：個人 SOP 放大到團隊，最大的增量價值是**共享的 triage 台帳 + 客製 query 庫**——一個人 triage 過的誤報、抽過的 pattern，變成全隊的資產（正是 [Ch 36](./36-false-positive-governance.md) 誤報治理的主題）。團隊 SOP 的成敗不在流程文件寫得多漂亮，在知識到底有沒有沉澱下來、還是每個人各審各的、每次重來。
- **SOP 的元技能是「知道何時偏離」**：這章給你的骨架，價值上限取決於你偏離它的判斷力。新手照 SOP 走能避免大部分低級錯誤（這已經很值錢）；高手的價值在於一眼看出「這個 target 該跳過哪三步、加做哪一步」。這個判斷力沒有捷徑，靠的是審夠多不同 target、每次復盤校準。SOP 是讓你**快速累積這種經驗**的框架，不是取代它的公式。

## 本章重點整理

- **SOP 是預設路徑 + 明確偏離點，不是無腦全流程鐵軌**。它把「下一步做什麼」外包給流程，騰出腦力給真正需要判斷的地方。壞 SOP（每次全走一遍）比沒 SOP 更糟。
- **八步流程**：target 選擇 → 攻擊面建模 → source/sink/sanitizer 盤點 → 漏斗選工具 → 寫/跑 query → triage 分級 → 動態驗證 → 報告。是帶迴圈的漏斗，不是直線；確認的 bug 回填為新種子。
- **前三步（建模）決定後五步的天花板**——沒盤到的 sink，query 再強也追不到。建模是投報率最高、也最常被跳過的一步。
- **決策樹三法則**：build 不起來 CodeQL 就出局（改 Joern/weggli）；database 值不值得建看攤提（小 target 手讀更快）；有 CVE 種子走變體路線、沒有先建模開路。
- **時間盒對抗兩個黑洞**：建模完美主義、深挖沉沒成本。建模追「夠指路」、query 打磨到訊噪比可接受就跑、每個深挖候選設止損時數。
- **check-list 的四個【關鍵】項**對應 Ch41 傷害最大的四反模式：漏盤自訂 sink、query 過擬合、不記錄 triage、亂關規則。
