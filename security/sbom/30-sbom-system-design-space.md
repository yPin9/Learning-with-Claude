# Ch 30 — 從操作者到設計者：SBOM 系統的架構空間

> **目標**：把「設計一套 SBOM 系統」這件事拆解成三個定位座標，說清楚技術難題集中在哪裡、研究問題集中在哪裡，並給 Part 8 後續章節畫一張地圖。讀完你能用三句話說出一個 SBOM 系統的設計決策樹，以及為什麼「它準不準」和「一個 CVE 可不可利用」是整個領域最難的兩個問題。

## 為什麼需要這個？

前面七個 Part 教你**操作**一套現有的工具鏈：syft 生成、grype 掃描、Dependency-Track 監控、cosign 簽章、SLSA provenance。你知道怎麼按對按鈕。

但如果有人問你：「如果我們公司要自己建一個 SBOM 系統，第一個設計決策是什麼？」——你會從哪裡開始？

操作者和設計者的思維斷層在這裡：操作者處理的問題是**給定工具，怎麼用好**；設計者處理的問題是**給定需求，怎麼分解成可解的子問題，再決定每個子問題怎麼解**。SBOM 這個領域之所以有研究空間，恰恰是因為兩個最核心的子問題——「一個元件到底是什麼」和「一個 CVE 到底影不影響我」——至今沒有普遍可接受的答案。

Part 8 的目的是讓你站到設計者的位置，用研究者的眼光看這個問題空間。這章先畫地圖。

## 先建立直覺：SBOM 系統不是一件事

很多人把「SBOM」想成一個工具或一份文件。但如果你去看真實部署，SBOM 涉及的系統有三個截然不同的角色：

```
     ┌──────────────────────────────────────────────────────────┐
     │              SBOM 系統的三個定位                          │
     │                                                          │
     │  A. 生成引擎          B. 消費/管理平台       C. 組織級架構 │
     │  (Generation Engine)  (Consumption Platform) (Governance) │
     │                                                          │
     │  問：這個軟體         問：有 CVE 影響我嗎？   問：SBOM 從  │
     │  裡有什麼？           哪些真的要修？           哪裡來、誰  │
     │                      版本範圍對不對？          信任它？    │
     │  代表實作：           代表實作：               代表實作：  │
     │  syft, trivy,        Dependency-Track,        SDLC 流程、 │
     │  cdxgen              Grype, OSV-Scanner        簽章/信任鏈 │
     │                                                          │
     │  核心難題：           核心難題：               核心難題：  │
     │  元件識別             漏洞關聯/可達性           治理/法規   │
     │  依賴圖建構           VEX 自動化               交換協議    │
     └──────────────────────────────────────────────────────────┘
                               ↑
                    技術研究熱區在這裡（A+B 交界）
```

**這個三分法是整個 Part 8 的組織原則**。不同章節分別深挖 A（Ch 31–32）、B（Ch 33–34）和 A+B 交界的理論地基（Ch 31）。

## 三個定位的本質差異

### A. 生成引擎：識別問題

生成引擎要回答的根本問題是：**給定一個軟體 artifact（source tree、build output、container image、binary），裡面有哪些元件？**

這個問題比看起來難，原因是「元件」沒有唯一的物理邊界：

- 一個 Go binary 靜態連結了 30 個 library，沒有任何 manifest 記錄這件事。你只能從 binary 裡面找線索。
- 一個 npm package 把它的依賴直接 bundle 進同一個 `.js` 檔，lockfile 消失了。
- 一個 C library 被 vendor 進去（複製到專案目錄），不再有 package manager 記錄。

syft 的 cataloger 架構（Ch 10 已介紹）是回應這個問題的一種設計：用多個專門辨識器各自找「自己認識的跡證」，再把結果合併。但這個設計有一個根本限制：**cataloger 只能找它知道找什麼的東西**。沒有被任何 cataloger 覆蓋的跡證，就是盲點。

生成引擎的研究問題集中在：
- 二進位識別（binary-level identification）——不靠 manifest，從 binary 本身還原元件身份（Ch 32）
- 依賴圖語意——「直接依賴」vs「傳遞依賴」的邊界在哪裡、怎麼表達（Ch 31）
- 識別信心（confidence）——cataloger 給出的 PURL 有多可信

### B. 消費/管理平台：關聯問題

消費平台要回答的根本問題是：**給定這份 SBOM 和一個漏洞資料庫，哪些元件受影響、程度如何？**

這個問題比「比對名字和版本」複雜得多：

- **版本範圍比對**：CVE 說「openssl < 3.2.0 受影響」，你的 SBOM 說版本是 `3.1.8-r1`（Alpine 的 backport 包，實際 patch 了那個 CVE）。純版本比對說「有問題」，但實際沒問題。
- **漏洞可達性**（reachability）：一個 Java 專案引用了 log4j，但它根本沒有讓 log4j 去解析 JNDI 查詢的 code path——JNDI lookup 功能不可達，Log4Shell 在這個特定環境下不可利用。
- **VEX 處理**：元件提供者說「我知道這個 CVE，但我的打包方式不受影響」——消費平台怎麼處理這份宣告？

消費平台的研究問題集中在：
- 版本範圍語意的跨生態統一（每個生態的版本語意不一樣）
- 可達性分析（reachability analysis）——能不能自動判斷一個 CVE 的攻擊向量在這個部署下是否可達（Ch 34）
- VEX 自動化（Ch 34）

### C. 組織級架構：信任與治理問題

組織級架構要回答的問題是：**SBOM 在 SDLC 裡怎麼流動、誰負責產、誰能信任它、失效的時候怎麼辦？**

這個層面更接近流程設計和風險管理，技術難題相對少，但工程挑戰不小：

- 一個大組織有上百個 team、數千個 repo，誰強制每個 repo 產 SBOM？
- 第三方供應商給你一份 SBOM，你怎麼驗證它沒被竄改？（Part 5 的 sigstore/in-toto 答的是這個問題）
- 新 CVE 爆出來，你要能幾分鐘內查清楚「我的哪些產品用了這個元件的哪個版本」——這需要一個持續更新的、可查詢的 SBOM 資料庫，而不是每次重跑掃描

這個層面在 Part 6（Ch 24–29）已介紹，Ch 35–36 從設計者視角補強。

## 技術研究熱區：A+B 交界

最有趣的技術問題發生在 A 和 B 的交界：

```
  SBOM 的準確性直接決定關聯的準確性
  ────────────────────────────────────
  生成引擎的誤差      →    消費平台的放大
  ─────────────────────────────────────────
  元件識別多一個       →   多一個漏洞要評估（假陽性）
  元件識別少一個       →   少一個漏洞（假陰性，更危險）
  版本識別錯           →   版本範圍比對失準
  PURL 格式不對        →   比對資料庫失敗（lookup miss）
  傳遞依賴漏掉         →   間接攻擊路徑看不到
```

這意味著：如果你想讓 Dependency-Track 給你有用的結果，你首先得保證 syft 產出的 SBOM 品質夠高。「品質」在這個脈絡裡有具體的定義：

- **識別完整度**（completeness）：有多少元件被漏掉？
- **識別精確度**（accuracy）：被識別的元件，其 PURL / CPE 有多準？
- **版本精確度**：版本號是 source-level 版本還是 distro-packaged 版本？
- **關係完整度**（relationship）：直接依賴/傳遞依賴/動態載入的區分記錄了嗎？

Ch 37 會看學術界對這些問題的實測結果，劇透是：現有工具的準確度因語言生態差異很大，而且沒有工具能在所有場景下同時達到高完整度和高精確度。

## 「設計一套 SBOM 系統」要回答的根本問題

如果有人叫你設計一套 SBOM 系統，以下清單是你不能繞過的設計決策：

### 第一層：識別什麼粒度？

- 你要識別到 **package** 粒度（`log4j-core@2.14.1`），還是 **file** 粒度（某個 `.class` 檔），還是 **function** 粒度（某個函式是否存在且可達）？
- 粒度越細，生成成本越高、資料量越大，但關聯和可達性分析才有意義。
- 不同用途要不同粒度：法規合規的 SBOM 要 package 粒度就夠；漏洞可達性分析要 function 粒度。

### 第二層：信任誰的識別結果？

- 你信任 manifest 說的（`package.json` 列的就是 dependency）？還是你要從 binary 驗證（manifest 和實際 binary 對得上嗎）？
- 開源元件的 SBOM 你要自己掃，還是信任上游提供的 SBOM？
- 第三方供應商的 SBOM，簽了章才能信嗎？（Part 5 的問題）

### 第三層：要支援多大規模？

- 單一 repo 的 one-shot 掃描 vs 整個組織幾千個 artifact 的持續監控——架構完全不同
- 持續監控的挑戰：新 CVE 每天都來，你要能在「不重跑所有掃描」的情況下知道哪些 artifact 受影響
- Dependency-Track 的設計選擇是：SBOM 入庫後，漏洞 DB 更新時自動重新比對——不需要重掃 artifact 本身，因為 artifact 沒變，只是漏洞知識更新了

### 第四層：關聯有多準？

- 你用的漏洞 DB 覆蓋了哪些生態（NVD/CPE 的覆蓋 vs OSV 的覆蓋不同）？
- 版本範圍比對的語意是否跟漏洞描述的語意對齊？
- VEX 流程是人工評估還是自動化？自動化的依據是什麼？

### 第五層：SBOM 可以合併嗎？

- 你的服務由多個元件組成（OS image + runtime + 你的 code）——這三個 SBOM 可以合成一個完整的 SBOM 嗎？
- 「合併」在技術上需要解決命名衝突、重複元件去重、關係圖的合併——這些不是平凡問題（Ch 36 會討論）
- SPDX 有 relationship 機制、CycloneDX 有 assembly/composition 機制，但兩者的語意不完全對齊

## 踩雷集錦

1. **「SBOM 就是跑一次 syft 然後存著」——錯誤直覺**

   正確認識是：這樣的 SBOM 在幾個月後就過期了（依賴更新了但 SBOM 沒更新），而且只有生成層，沒有消費和信任層。一套完整的 SBOM 系統需要三個層都在運作，而且是持續的。

2. **「準確性問題靠更好的掃描工具解決」——錯誤直覺**

   正確認識是：有些識別問題是結構性的，不是「工具不夠好」。靜態連結的函式庫、vendored 程式碼、動態載入的 plugin——這些在某些語言生態裡根本沒有機器可讀的 manifest，任何工具都面對同樣的資訊缺乏。

3. **「消費平台把 CVE 和元件對起來就是對的」——錯誤直覺**

   正確認識是：「名字對上」不代表「確實受影響」。版本範圍的語意、backport patch、distro 包的上游版本對應，都可能讓「對上的 CVE」在你的環境不實際可利用。漏洞關聯只是第一步，可達性和 VEX 才能縮短到「真正需要修的清單」。

4. **「SBOM 合規就是生成一份 SBOM 文件」——錯誤直覺**

   正確認識是：法規（EO 14028、EU CRA、FDA）要求的不只是「存在一份文件」，而是「持續、可驗證地知道你的軟體裡有什麼」。這是一個流程問題和系統問題，不是一個文件格式問題。

## 進階：再往深一層

設計 SBOM 系統時，有三個「隱藏假設」最容易在設計評審裡被忽略：

**假設一：元件邊界是清晰的。** 實際上，submodule、vendoring、copy-paste 的程式碼片段，在源碼層面根本沒有邊界。生成引擎的設計必須明確宣告它能識別哪種邊界、不能識別哪種。

**假設二：版本是全序的。** 實際上，不同語言生態的版本語意差異很大（PEP 440 vs semver vs npm 範圍語意），跨生態做版本範圍比對時這些差異會製造對齊錯誤。Ch 31 會形式化這個問題。

**假設三：漏洞是靜態的。** 實際上，NVD 的 CVE 記錄會被修改、CVSS score 會被重新評估、影響範圍會被收窄或擴大。消費平台的設計需要能處理「漏洞知識的更新」，而不只是「新漏洞的進入」。

## 動手練習

這章是論理章，練習是設計練習，不需要跑任何工具：

1. **三層分類練習**：翻開你以前用過的 SBOM 相關工具或流程（syft/grype/Trivy/Renovate/Dependabot），把每個工具或步驟歸入 A/B/C 三層。哪一層在你的組織裡缺失？

2. **設計決策清單**：假設你的 team 要為一個中型 SaaS 產品（10 個 micro-service、用 Go + Python）設計一套 SBOM 系統，回答本章「根本問題」清單的五個問題，每個問題寫一個你的暫定答案和你這樣決定的理由。

3. **失敗模式分析**：想一個你曾遇到或聽說過的「掃描出一堆漏洞但大半都不實際影響我」的情況。用本章的框架分析：是生成引擎的識別問題、還是消費平台的關聯問題、還是兩者都有？

## 本章重點整理

- SBOM 系統分三個定位：A 生成引擎（識別問題）、B 消費/管理平台（關聯問題）、C 組織級架構（信任與治理）。
- 技術研究熱區在 A+B 交界：生成的準確性決定了關聯的有效性，而「準確性」有四個維度（識別完整度、識別精確度、版本精確度、關係完整度）。
- 「設計一套 SBOM 系統」要回答五個根本問題：識別什麼粒度、信任誰、規模多大、關聯有多準、可以合併嗎。
- Part 8 後續章節分別深挖三個定位的核心技術難題，以研究者/設計者視角補充前面七個 Part 的操作視角。
