# Ch 37 — SBOM 的實證現況與研究地圖

> **目標**：從「設計者 / 研究者能貢獻什麼」的角度繪製地圖——從業者真實在痛什麼、學界認為哪些問題還沒解、SBOM 品質怎麼量化、哪些硬問題現在還沒有好答案。

## 為什麼需要這個？

Part 8 前面幾章從理論和機制角度談 SBOM 系統設計。這一章的任務是「接地氣」：暫時放下設計美學，看看從業者和研究者各自怎麼看這件事，兩個視角在哪裡吻合、在哪裡分歧。

研究者眼中的「open problem」和從業者眼中的「真實痛點」往往不一樣。研究者在研究 formal reachability analysis 的可擴展性；從業者在苦惱「我要怎麼說服老闆讓我在 CI 加一個跑 10 分鐘的工具」。兩個問題都是真實的，但解決順序和優先級不同。把兩個視角放在一起，才能做出有用的設計。

## 先建立直覺

SBOM 在 2020 年前幾乎只存在於研究文獻和少數安全研究者的討論裡。SolarWinds 事件（2020 年底）和 Log4Shell（2021 年底）在兩年內把它從「好東西但沒人做」推到「政府強制要求」。這種速度的推廣會帶來一個特定的問題：**工具和標準還沒有成熟，法規和期望就已經先到了**。

Xia 等人（ICSE 2023）在 2022 年（EO 14028 發布後第一年）做了第一個系統性的實證研究，訪談 17 名從業者、問卷 65 名、橫跨 15 個國家 5 大洲。他們想知道：「從業者真的是怎麼用 SBOM 的、他們在痛什麼」。這份資料是目前最接近地面真相的學術數據。

## 從業者視角：ICSE 2023 的實證發現

### 研究設計

Xia 等人採用混合研究法：先做 17 個半結構化訪談（qualitative）整理出主題，然後用 65 份問卷（quantitative）驗證這些主題在從業者群體裡的普遍性。受訪者橫跨軟體工程師、資安工程師、工具開發者、法規合規人員。

研究產出了 **26 條陳述（statements）**，組織成 **3 個主題**，以及一個 goal model 描述從業者對 SBOM 的期待和障礙。

### 主題一：SBOM 的理解與認知

從業者對 SBOM 的理解差距很大。在研究進行的時間點，「我知道 SBOM 是什麼」和「我在生產環境裡用過 SBOM」之間有明顯斷層。很多受訪者了解 SBOM 的概念，但沒有實際部署過——主要因為沒有明確的啟動動機（在 EO 14028 之前，沒有「不做會有什麼後果」）。

研究發現一個核心認知問題：很多從業者把 SBOM 理解為一個靜態文件（一份清單，做完就不動），而不是一個需要隨構建更新的動態元件。這個誤解直接導致「一年更新一次 SBOM」的不良實踐——在漏洞快速出現的現代環境裡，一年前的 SBOM 幾乎沒有防禦價值。

### 主題二：SBOM 的生成與品質

生成工具的成熟度問題是最多受訪者提到的技術痛點：

**命名一致性問題**：不同工具對同一個元件的識別結果不一樣。一個 C 函式庫可能在一個工具裡叫 `libssl`、在另一個叫 `openssl`、在 CPE 資料庫裡叫 `openssl:openssl:3.0.1`、在 PURL 裡叫 `pkg:generic/openssl@3.0.1`。這導致跨工具的 SBOM 無法直接合併，漏洞比對也會出現漏報。

**生成完整度問題**：沒有工具能 100% 可靠地識別所有元件，尤其是：
- 靜態鏈入的函式庫（沒有套件管理器記錄）
- 容器裡手動 `curl` 下載的 binary
- 預處理生成的代碼（protobuf/gRPC 生成的代碼算不算一個元件？）

**維護成本問題**：從業者認為 SBOM 的維護比生成更難。初始生成跑一次工具就有了，但後續每次依賴更新、每次構建環境改變，SBOM 都應該更新——這在沒有自動化 CI 整合的情況下是手動負擔。

### 主題三：SBOM 的消費與使用

從業者最頭痛的消費端問題是**誤報（false positive）**。一份 SBOM 吐出 200 個漏洞，掃描工具說其中 180 個 critical，但實際上能被利用的可能只有 5 個。在沒有 reachability 分析和 VEX 降噪的情況下，安全工程師每天面對的是「漏洞海」——最終的結局是報告疲勞，然後忽略所有警報。

**分發與交換信任**：「我收到一份 SBOM，我怎麼知道它是真的、而不是對方隨便跑一個工具生出來的？」這個問題在 SBOM 簽章和 provenance 工具出現之前幾乎沒有好答案。即使有了工具，如何建立跨組織的信任也沒有標準流程。

**可操作性（actionability）**：從業者普遍反映，SBOM 本身不夠 actionable——你知道有一個漏洞組件，但你不知道「我現在能做什麼、不能做什麼、有沒有 workaround」。這正是 VEX 嘗試解決的問題（Ch 16），但 VEX 的自動化生成還遠未成熟。

### Goal Model 的含義

Xia 等人導出的 goal model 把從業者的期待分成幾個層次：
- **基本期待**：能知道軟體裡有什麼（命名準確、完整度可信）
- **進階期待**：能做漏洞管理（比對快速、誤報低、有 reachability 資訊）
- **理想期待**：能自動化整個流程、跨組織交換、法規合規一站搞定

實際上，大多數從業者在 2022 年還在掙扎「基本期待」。這告訴研究者：提升工具易用性和生成品質的工程問題，比研究新的形式化理論更有社會價值。

### 從訪談數據讀出的隱藏訊號

Xia 等人的 17 個訪談資料裡，有幾個值得設計者留意的隱藏訊號（這些不總是直接出現在量化問卷裡，而是質性訪談的特有洞察）：

**組織文化的阻力比技術難度更重要**：多個受訪者說「工具其實可以，但讓組織接受這個新流程才是最難的」。這說明 SBOM 的採用困難不只是技術問題——你設計的系統如果讓工程師覺得是「額外負擔」而不是「有回饋的工具」，再好的技術設計也推不動。這對生成引擎設計有含義：好的生成工具除了精確，還要「整合進現有工作流不需要工程師改習慣」。

**誰來擁有 SBOM 沒有共識**：在多數組織裡，SBOM 落在資安團隊和開發團隊之間的灰色地帶——資安說是開發的責任，開發說是資安的要求。這個責任模糊導致「有人生成 SBOM 但沒有人消費它」的情況，也是 SBOM 作為靜態文件（而非持續更新）的原因之一。設計 SBOM 系統時，要明確「這個系統的 primary user 是誰，他的工作流是什麼」。

**Legal 和 privacy 的考量阻礙了分發**：有受訪者提到，他們擔心公開分享詳細的 SBOM（包含所有第三方元件的版本號）會讓攻擊者知道「這個系統用的是 OpenSSL 1.1.1k，而不是 3.x，所以還有某個漏洞」——換言之，SBOM 本身可能成為攻擊資訊。這個顧慮並不是沒有根據：詳細的 SBOM 確實可以幫助攻擊者做更精準的目標篩選。這是「透明性和安全性之間的矛盾」，在 SBOM 分發設計上（Ch 26 的 tiered sharing）需要明確處理。

## 研究者視角：Williams TOSEM 2025 的研究地圖

### 背景

Williams 等人（TOSEM 2025, vol. 34 issue 5, DOI 10.1145/3714464）的「Research Directions in Software Supply Chain Security」是 NSF S3C2（Secure Software Supply Chain Center）聯盟的綜合成果，來自 8 場峰會、131 位從業者、涵蓋 42 個工業組織和 15 個美國政府機構。它代表了學界試圖回應「業界認為哪些問題需要研究」這個問題的最新嘗試。

### 三大攻擊向量分類

Williams 等人把供應鏈攻擊的根因歸到三個向量：

**1. Code Dependencies（代碼依賴）**：開源和第三方依賴裡的漏洞或惡意代碼，無論是意外引入的還是蓄意注入的。這是最廣泛討論的向量，也是 SBOM 最直接對應的威脅。

**2. Build Infrastructure（構建基礎設施）**：CI/CD 管線被入侵、build 環境被污染、artifact 在傳輸中被替換。SLSA 和 in-toto 主要在防這個向量。

**3. Humans（人）**：針對軟體工程師的社會工程攻擊——釣魚取得 repo 或 registry 帳號、欺騙維護者 merge 惡意 PR、利用離職維護者帳號。這個向量是技術防禦最難覆蓋的。

三個向量的重要性：研究者的注意力傳統上集中在向量 1（工具最容易自動化），向量 3（人）是防禦的最弱環，但也是工具設計最難介入的地方。

### 實踐者與研究者之間的優先級落差

Williams TOSEM 2025 的一個重要貢獻是明確記錄了「業界從業者認為最重要的問題」和「學界論文最多的問題」之間的落差。

從業者最想要的：
1. **更好的漏洞優先排序**（哪個漏洞真的需要我今天修）— 這需要 reachability，但 reachability 規模化還在研究
2. **更低的 SBOM 維護成本**（每次 CI 都自動更新並驗證 SBOM）— 工具成熟但流程設計還沒標準化
3. **更清楚的法規合規路徑**（我要做什麼才算符合 EO 14028？）— 這是文件和培訓問題，不是研究問題

學界最多論文的：
1. **formal vulnerability detection 方法**（符號執行、靜態分析理論）
2. **依賴圖的圖理論分析**（pagerank-like 風險評分）
3. **新的 binary similarity 算法**（比現有算法更精確）

這個落差說明了一個研究者應該知道的設計原則：**技術上困難的問題不一定是業界最急需解決的問題**。從業者用 Dependency-Track + VEX 的人工流程能解決 80% 的問題，研究者在研究的 formal reachability 解決的是剩下 20% 裡最困難的那個——但你要知道自己在做哪種貢獻。

### 學界識別的未解問題

Williams 等人整理了從業者和研究者共同認為「還沒有好答案」的問題（以下按課題分類）：

**依賴管理與 SBOM**：
- 如何可靠地追蹤所有傳遞依賴（尤其是跨語言、跨套件生態的依賴）？
- SBOM 的「精確度」如何測量和比較？
- 如何設計能自動更新的 SBOM（而不是靜態文件）？

**漏洞管理**：
- 可達性分析（reachability analysis）能否規模化到大型 monorepo 或複雜 C/C++ 代碼庫？
- VEX 的自動化生成——「這個漏洞在我的代碼路徑裡不可達」這個判斷，機器能可靠地做嗎？
- 如何處理跨語言的漏洞傳播（Go FFI 呼叫 C 庫，C 庫有漏洞，Go 程式算受影響嗎）？

**信任與驗證**：
- 跨組織的 SBOM 信任交換如何標準化（我信任你的 SBOM，你信任我的，這個信任怎麼建立）？
- SBOM 自身的完整性如何在沒有 PKI 基礎設施的小型組織裡做到？

**人因問題**：
- 如何設計工具讓維護者願意採用 SBOM 和簽章（降低摩擦，不是加負擔）？
- 社會工程攻擊的偵測：有沒有辦法從 commit 行為、PR review 模式裡識別出異常？

## SBOM 品質的量化

從業者說「SBOM 品質」，但「品質」是什麼？目前有幾個量化框架：

### NTIA Minimum Elements

NTIA（美國國家電信和資訊管理局）定義了 SBOM 的最低要素：
- 供應商名稱（Supplier Name）
- 元件名稱（Component Name）
- 元件版本（Component Version）
- 元件的其他識別符（如 PURL 或 CPE）
- 依賴關係
- SBOM 作者
- 時間戳

NTIA minimum elements checker 可以自動驗證一份 SBOM 是否符合這些最低要求。它是合規的最低門檻，不是品質的上限。

### OWASP SCVS（Software Component Verification Standard）

OWASP SCVS 把 SBOM 品質分成三個層次（Level 1/2/3）：
- **Level 1**：能識別所有第一層依賴，有標準識別符（PURL/CPE）
- **Level 2**：完整傳遞依賴清單、有 hash 驗證、來源資訊
- **Level 3**：有 provenance、構建資訊、license 合規資訊、簽章和完整性保護

Level 1 是「合規能過」，Level 3 是「真的有防禦效果」。大多數工具預設生成介於 Level 1 和 Level 2 之間的 SBOM。

### sbomqs：可量化的品質分數

`sbomqs`（Anchore 開發，Ch 12 用過）是目前最具體的 SBOM 品質量化工具，輸出各維度分數：

```
SBOM Quality:                                              Score
 ─────────────────────────────────────────────────────────────
 valid-spdx-license                                         6.0
 components-have-purl                                       8.0
 components-have-supplier                                   0.0
 components-have-cpe                                        2.5
 sbom-has-signature                                         0.0
 components-have-checksums                                 10.0
 sbom-has-creation-timestamp                               10.0
 components-have-licenses                                   7.0
```

這些分數直接對應到防禦能力：`components-have-purl` 低意味著漏洞比對精確度低；`sbom-has-signature` 是 0 意味著下游無法驗 SBOM 完整性。

### 品質量化的限制

目前所有品質量化工具都在測量「SBOM 記錄了多少資訊」，但沒有辦法量化「SBOM 記錄的資訊有多準確」——一份 PURL 全填了的 SBOM，如果 PURL 識別有誤（例如把 `openssl 1.0.1` 識別成 `openssl 1.1.0`），品質分數會很高但實際品質很差。準確性（accuracy）目前沒有自動化量化方法，只能用 ground-truth 對比（人工驗證或用 Ch 32 提到的 binary 指紋比對）。

Xia ICSE 2023 的從業者調查直接確認了這個落差：受訪者認為「生成工具的準確性」是採用 SBOM 的一個核心障礙。工具說它找到了 150 個元件，但工程師不確定還有多少被遺漏——這個不確定性讓 SBOM 在他們眼裡是「可能有用、但不可靠的參考」而不是「可以信賴的清單」。品質量化要真正有用，需要能量化「我遺漏了多少」而不只是「我記錄了多少」，這在學術上是個開放問題。

## 還沒解的硬問題

誠實列出幾個在學術文獻和從業者社群裡都承認「目前沒有滿意答案」的問題：

### 1. 命名對齊（Naming Alignment）

PURL（Package URL）是目前最好的元件識別方案，但它依賴套件管理器的元資料。對於從原始碼靜態鏈入的函式庫、手動複製進來的代碼、或者 vendored dependency，PURL 無法自動生成——你要靠 binary 分析（Ch 32）去猜它是什麼，而 binary 識別的誤差率目前還相當高。

跨生態的 naming 更是難題：npm 的 `uuid` 和 PyPI 的 `uuid`、以及 Go 的 `github.com/google/uuid`，是不是同一個元件的不同版本？CPE 字典的映射不完整、PURL 不跨生態、OSV 的 `aliases` 欄位嘗試解這個但覆蓋率有限。

更深的問題：OSV 用 aliases 連結不同生態的同一個漏洞（例如一個 C 函式庫的 CVE 同時影響多個語言的 binding 套件），但這個連結是人工維護的，不完整且有滯後。Williams TOSEM 2025 把這列為 code dependencies 攻擊向量裡的關鍵開放問題：沒有可靠的 cross-ecosystem alias 機制，就沒有辦法做到「一個 CVE 只需要記錄一次，就能對映到所有受影響的生態系」。

### 2. Reachability 的規模化

靜態 reachability 分析（「這個漏洞函數在我的調用鏈裡嗎」）對小型 Java/Go 專案已有可用工具，但對大型 C/C++ 代碼庫（幾百萬行，複雜的 function pointer 分派、inline assembly）精確 reachability 分析仍是開放問題。GCC callgraph 和 LLVM call graph 都能跑，但精確度在複雜代碼庫下會下降到讓誤報仍然很多的程度。

更深的問題：動態加載的函式庫（`dlopen`）、JVM 的 reflection、Python 的動態 `import` ——靜態分析在這些情況下原則上就無法做到完整的 callgraph，需要動態分析或近似，而動態分析需要代表性的測試覆蓋率。

### 3. VEX 自動化的極限

VEX（Vulnerability Exploitability eXchange，Ch 16）讓供應商能宣告「這個 CVE 在我的產品裡不可被利用」，附帶理由（`not_applicable`、`code_not_present`、`code_not_reachable` 等）。問題是：這個宣告目前幾乎全部是人工產出的——需要安全工程師手動確認每個 CVE 在代碼裡的實際狀態。

自動化 VEX 生成（讓工具自動判斷 `code_not_reachable`）需要可靠的 reachability 分析，而這就繞回了上面的問題。目前沒有任何工具能在生產環境裡可靠地自動生成高精確度的 VEX——所有自動化 VEX 工具的誤報率仍然高到需要人工審核。

### 4. SBOM 品質的準確性量化

如前所述，所有品質指標都在測量「記錄了什麼」，不測量「記錄是否準確」。設計一個能自動測量 SBOM 準確性的方法，需要一個 ground-truth——這只能在有原始碼的情況下透過靜態分析驗證，對 binary-only 的 SBOM 無法做到。

更根本的問題：「哪些元件應該被包含在 SBOM 裡」本身就沒有共識。靜態鏈入的函式庫算嗎？OS 層的共享函式庫算嗎？開發工具（compiler、linter）算嗎？不同場景的答案不同，讓「完整度」的量化標準無法統一。

研究機會在這裡很清楚：需要一個「SBOM scope definition」的標準，讓不同用途（軟體交付給客戶 vs 內部安全管理 vs 法規合規）的 SBOM 能有不同但明確的完整度定義，而不是所有人用同一個「完整」標準但理解完全不同。

### 5. 跨組織的 SBOM 交換信任

我信任你的 SBOM，你信任我的——這個雙邊信任建立起來之後，要怎麼讓它可以傳遞和組合？如果 A 的 SBOM 來自 B、B 的 SBOM 來自 C，A 對 C 的 SBOM 有多少信任？

目前沒有標準的「SBOM 信任聯邦（SBOM trust federation）」協議。每個組織各自決定「我信任哪些 SBOM 來源」，沒有機器可讀的信任政策標準。CISA 的 SBOM sharing guidance 提供了人類可讀的指引，但離機器可執行的信任策略還很遠。

跨組織信任的問題在法規層面已經出現：EU CRA（Cyber Resilience Act）要求製造商向客戶提供 SBOM，但沒有規定信任機制。如果一個歐洲客戶收到中國供應商提供的 SBOM，他怎麼知道這份 SBOM 是可信的？Ch 36 的信任鏈設計（SBOM 簽章 + transparency log）理論上能解這個問題，但大多數供應商目前還沒有部署這套機制。這個落差在未來幾年可能成為法規合規的實際痛點。

### 法規對研究的影響

Williams TOSEM 2025 的一個隱含觀察是：美國政府機構（EO 14028）和歐盟（CRA）的介入讓 SBOM 從「學術和資安先進者的話題」變成「所有軟體廠商都要面對的問題」。這對研究的含義是雙面的：

**正面影響**：有更多真實的 SBOM 在生產環境裡被生成和使用，研究者有更多真實數據可以研究。法規的強制力也讓工具的品質問題從「理論上有問題」變成「實際上有法律責任」，增加了產業對研究成果的採用動機。

**負面影響**：法規要求的最低標準（NTIA minimum elements）有可能成為業界的最高標準——合規了就不再投資品質。如果研究社群不主動推動「合規門檻以上的最佳實踐」，法規反而可能成為 SBOM 品質停滯的原因。

這個觀察告訴研究者：在 SBOM 領域，「技術上正確的研究」和「業界實際採用的做法」之間的鴻溝需要主動去彌合。只發論文是不夠的，讓研究成果進入工具（syft、grype、trivy 等），或者進入標準（SPDX、CycloneDX 的下一個版本），才能真正改變生產環境的現狀。

## 研究者能貢獻什麼

根據上面的分析，幾個有具體影響力的研究方向：

**近期有成果的方向**：
- 改善 binary 元件識別的精確度（Ch 32 的論文已開始，但 C/C++ 的 stripped binary 仍然困難）
- 跨語言 SBOM 合併（VEX 的跨語言傳播規則）
- SBOM diff 算法（兩個版本的 SBOM 之間的最小變更集，用於增量更新）

**中期有機會的方向**：
- 可規模化的 C/C++ reachability 分析（需要研究精確度-效能的取捨）
- SBOM 準確性的地面真相對比方法（可能需要新的評測 benchmark）
- 輕量級 VEX 自動化（不依賴完整 reachability，用語義相似度或統計方法近似）

**長期的困難問題**：
- naming 對齊的生態解法（需要多個套件生態系的協調，不是一個研究組能解決的）
- 人因攻擊的技術對策（比帳號 takeover 的偵測、異常 commit 行為的識別）

### 如何評估「一篇 SBOM 相關論文是否值得讀」

研究地圖的最後一個實用工具：給你一個快速判斷新論文品質的 checklist。SBOM 是個新興領域，論文品質參差不齊，有些只是把舊工具換個包裝、有些做了真正的進展。

**值得深讀的信號**：
1. **有真實的 ground-truth benchmark**：論文有人工標注的「這個 SBOM 應該包含哪些元件」的 ground-truth，而不只是「我的工具比另一個工具找到更多元件」（找更多不等於找得更準）。
2. **有開源的 dataset 和工具**：Ladisa 的 Risk Explorer、Ohm 的 Backstabber dataset 都是公開的。能被重現的結果比不能被重現的更可信。
3. **有誠實的 failure case 分析**：如果論文只報告 precision 高的案例，不報告 recall 低的地方，要小心。好的論文會分析「在什麼情況下我的方法失效」。
4. **benchmark 使用的軟體與你的真實環境有重疊**：很多論文用 Java Maven 專案做 benchmark，如果你主要是 C/C++ 嵌入式系統，這篇論文的數字對你的意義有限。

**可以快速跳過的信號**：
1. 只用合成資料集（沒有真實軟體）
2. 只在一個生態系測試（例如只測 npm），但宣稱跨生態有效
3. 沒有與既有工具（syft、trivy、grype）的對比
4. 所有案例的 precision 都接近 100%（可能是 benchmark 太容易）

Williams TOSEM 2025 的一個隱含建議是：研究者應該更多地採用從業者能實際使用的 benchmark（真實的企業代碼庫樣本），而不只是精心選擇的 GitHub 開源專案。這是一個研究生態的問題，不只是個別論文的問題。

| SBOM 品質量化 | 中 | 低 | 中（sbomqs）|

| 人因攻擊防禦 | 中 | 低 | 低 |

## 踩雷集錦

1. **把學術 benchmark 當成實際生產環境的代表**。多數 SBOM 相關論文用的 benchmark 是精心選擇的開源 Java 或 Python 專案——這些專案有乾淨的套件管理器記錄、沒有 vendored 依賴、沒有 generated code。在 C/C++ 工業代碼庫上直接套用這些結論會得到很不一樣的結果。

2. **SBOM 生成工具的評估結果沒有可比性**。不同論文用不同 benchmark、不同評估指標（precision/recall 的定義各不同）評估同一個工具，得到的結論不一致。在比較兩篇論文的工具評估結果時，先確認他們的 ground-truth 是怎麼定義的、benchmark 是不是可比的。

3. **把「已有工具」等同於「問題已解決」**。sbomqs 有了，不代表 SBOM 品質量化已解決。grype 有了，不代表漏洞管理已解決。工具的存在是第一步，工具的精確度、適用場景、以及跟從業者實際工作流的整合，才是決定「問題有沒有真正解決」的指標。

4. **法規要求的最低標準被當成品質目標**。EO 14028 的 SBOM 要求是 NTIA minimum elements——一個非常低的門檻，設計上是「任何組織都能做到」的起點，而不是「這樣就夠了」的終點。把符合 minimum elements 當成 SBOM 計畫的目標，會讓你在真正有攻擊的時候發現 SBOM 沒用，然後得出「SBOM 沒用」的錯誤結論。

5. **從業者的 adoption 困難被低估**。Xia 等人的研究明確顯示，工具的技術成熟度不是 adoption 的主要障礙——組織內部的變革管理、說服力、以及與現有工作流的整合摩擦才是主因。設計 SBOM 工具時，如果不考慮「這個工具在典型組織裡的 onboarding 流程有多複雜」，再好的技術也推不動。

## 進階：再往深一層

**SBOM 的自動更新機制設計**

Xia 等人指出的「靜態 SBOM」問題是一個設計機會：如果 SBOM 能在每次 CI 構建時自動更新並簽章，從業者的維護負擔就消失了。技術上這已經可以做到（syft 在 CI 裡跑），但設計「SBOM 版本管理系統」（怎麼存、怎麼 diff、怎麼讓下游知道有新版本）還沒有標準化的解法。

**人因攻擊的技術輔助**

Williams 等人把「人」列為第三個攻擊向量，但學界在這個方向的工具研究相對薄弱。有幾個值得探索的研究方向：commit 行為異常偵測（突然大量修改非相關模組的 contributor）、PR review 的社群分析（reviewer 的審查深度統計）、maintainer 帳號的行為基線建立。這些都需要大量歷史數據和隱私保護的平衡，是困難但重要的問題。

**SBOM as a Service 的設計問題**

隨著 SBOM 需求增加，會有越來越多的「SBOM as a Service」方案出現（把生成和管理外包給第三方）。這引入了新的信任問題：你怎麼知道第三方服務生成的 SBOM 是準確的、而不是為了讓你的產品看起來乾淨而偷偷漏掉一些元件？attestation 框架（Ch 36）需要延伸到這個場景。

## 動手練習

1. 用 `sbomqs score <你的 SBOM 檔案>` 對你在前面練習裡生成的 SBOM 打分，找到最低分的維度，查它對應的品質指標是什麼，想想「這個維度低，對哪種攻擊的偵測能力會受影響」。

2. 選一個你熟悉的開源專案，試著回答：這個專案的 SBOM「完整度」有多高？它的直接依賴和傳遞依賴各有幾個？有哪些依賴你懷疑工具識別不到（靜態鏈入的、vendored 的）？

3. 去看 CISA 的「Known Exploited Vulnerabilities Catalog」最近新增的 10 個 CVE，問：「如果我有一份品質良好的 SBOM，我能在多久內知道我是不是受影響？哪些資訊是 SBOM 提供的，哪些還需要其他工具？」

4. 閱讀 Xia ICSE 2023 的 Section 5（goal model），然後對你自己組織目前的 SBOM 採用狀態做一個誠實的評估：你現在在「基本期待 / 進階期待 / 理想期待」哪個層次？你離下一個層次最主要的技術阻礙是什麼？最主要的組織阻礙是什麼？

5. 選 Ch 37「還沒解的硬問題」裡一個你覺得「最值得研究」的問題，搜尋最近 2 年在 IEEE S&P / USENIX Security / CCS / NDSS / ISSTA / ASE 上有沒有相關的進展。用你在本章學到的「評估論文品質的 checklist」評估你找到的論文——它有真實 ground-truth benchmark 嗎？有開源 dataset 嗎？benchmark 和你的真實環境有多高的重疊度？

## 給從業者的實際行動建議

結合兩份論文的發現，對不同角色的從業者，下面是幾個有具體行動力的建議：

**如果你是 SBOM 系統的設計者（工程師或架構師）**：

1. 用 sbomqs 對你目前的 SBOM 做一個基線評分，找到最低分的維度，這就是優先改進的地方。別用總分，看單一維度——`sbom-has-signature` 是 0 意味著下游完全無法驗完整性，這是一個比 `components-have-supplier` 低分更嚴重的問題。

2. 把「SBOM 的什麼維度會讓你無法偵測哪個攻擊向量」記在設計文件裡。Xia 的研究表明從業者最大的問題不是「不知道有問題」，而是「問題沒有被明確記錄，讓下游有錯誤的安全感」。

3. 在你的 CI pipeline 設計一個最小的 SBOM 品質閘道：拒絕沒有完整 PURL 的 SBOM 進入 staging 環境。這不是最高品質要求，但它讓品質問題在早期就被發現，而不是等到消費者抱怨漏洞比對不準確。

**如果你是研究者**：

1. 在你的下一個 SBOM 相關論文裡，用 Williams TOSEM 2025 的三大攻擊向量框架定位你的研究：你的工作在解決哪個向量的哪個具體問題？已有的哪些工作覆蓋了周邊，你的是補缺？這樣的定位讓讀者能評估「這篇論文在更大的地圖裡是什麼位置」。

2. 用 Xia ICSE 2023 的 goal model 作為評估標準：你的研究成果能讓從業者在「基本期待 / 進階期待 / 理想期待」哪個層次上提升？如果你的技術只能改善從業者 2% 的情況，而更簡單的工程改進能改善 30% 的情況，要誠實地說清楚。

3. 開源你的 dataset 和工具。Ladisa 的 Risk Explorer、Ohm 的 Backstabber dataset 都是公開的，這讓研究是可重現的、可比較的。不開源的研究在 SBOM 這個領域的影響力會大幅縮減，因為工具作者（syft、grype 等）需要能重現你的結果才能採用你的方法。

## 本章重點整理

- Xia ICSE 2023 的實證研究（17 訪談 + 65 問卷，15 國）識別出從業者在 SBOM 命名、生成完整度、漏洞誤報、分發信任四個領域的真實痛點；26 條陳述組成 3 個主題。
- Williams TOSEM 2025（131 位從業者，42 工業組織，15 美國政府機構）把供應鏈攻擊的根因歸到三個向量：Code Dependencies、Build Infrastructure、Humans；Humans 是技術防禦最難覆蓋的。
- SBOM 品質量化：NTIA minimum elements 是合規下限、OWASP SCVS Level 1-3 是漸進標準、sbomqs 是可量化的品質分數——但目前所有工具只能測「記錄了多少」，不能測「記錄是否準確」。
- 五個目前沒有好答案的硬問題：naming alignment（跨生態）、reachability 規模化（C/C++）、VEX 自動化精確度、SBOM 準確性量化、跨組織信任交換。

## 一個誠實的評估：SBOM 解決了多少問題？

這門課從 Ch 1 開始就說「Log4Shell 爆發那晚，有 SBOM 的人幾分鐘知道答案，沒有的人翻了三天」。這是真的。但 Xia 和 Williams 兩篇論文合在一起，告訴了我們一個更完整的圖景：

**SBOM 確實解決的問題（有工具支持、從業者認同）**：
- 在已知 CVE 爆發後，快速識別哪些服務用了哪個元件
- 法規合規的基礎層（能知道自己軟體裡有什麼）
- 授權（license）合規的自動化

**SBOM 部分解決的問題（工具存在但仍有重要限制）**：
- 漏洞管理（存在，但 false positive 率高、沒有 reachability 資訊）
- 供應鏈可見性（取決於生成品質，binary 識別仍有誤差）
- 跨組織信任（有 sigstore 但部署不普遍）

**SBOM 還沒解決的問題（工具基本不存在或精確度太低）**：
- 零日漏洞的偵測（SBOM 只能比對已知的 CVE）
- 惡意代碼的識別（惡意套件的 PURL 可能完全合法）
- 人因攻擊（社工讓合法帳號做了惡意操作）
- 自動 reachability 分析的規模化

這個評估告訴你：SBOM 是一個必要的基礎設施，但它不是供應鏈安全的「解法」，而是「讓其他防禦機制能夠工作的前提條件」。沒有 SBOM，你連「我的系統裡有什麼」都不知道，就更談不上漏洞管理、reachability 分析、或信任驗證。有了 SBOM，你才能開始問更深的問題。

## 研究方向的「可解性」評估框架

在研究地圖裡，不是所有「未解問題」都是同樣難的，也不是所有「未解問題」都適合由學術研究解決。以下是一個評估研究問題「可解性」的框架，幫助研究者做更有效的投入判斷：

**技術可解但缺乏工程投入的問題**（研究成果存在，需要工程化）：
- SBOM 簽章和驗章：技術完整（sigstore），缺的是在主流工具（npm、pip）的預設整合
- Build-time SBOM 自動生成：技術成熟（各語言都有工具），缺的是統一的 CI 模板和低摩擦 onboarding

**技術本身需要突破的問題**（適合學術研究）：
- C/C++ stripped binary 的精確元件識別
- 跨語言動態呼叫的 reachability 分析（C 函式庫被 Python FFI 呼叫）
- 大規模 VEX 自動生成（需要能在真實規模下工作的輕量級 reachability 近似）

**需要生態系協作而非技術突破的問題**（學術研究影響有限）：
- Naming alignment（PURL 跨生態對映）——需要 npm、PyPI、GitHub、NIST 等多方協調
- 跨組織 SBOM 信任交換——需要業界標準，學術 prototyping 可以影響標準設計方向

**根本上是組織 / 行為問題的事情**（研究能提供洞察但工具解決不了）：
- 「SBOM 責任不清楚」——這是組織設計問題
- 「工程師認為 SBOM 是負擔」——這是工具 UX 問題，部分是文化問題
- 社會工程攻擊的防禦——技術工具只能輔助，核心是人的判斷

這個框架的使用方式：選定一個研究問題後，先問它屬於哪個類別。如果是「技術可解但缺乏工程投入」，你的研究貢獻可能比做一個「開源、好用、文件完整的工具」更大，而不是又一篇論文。如果是「技術本身需要突破」，這才是值得花大量學術資源的地方。
