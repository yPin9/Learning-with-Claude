# 練習 G — 從 production core dump 還原現場

> **目標**：綜合 Part 7（core dump、backtrace、多執行緒、符號）與前面所有技能，模擬一次真實的「線上服務半夜崩潰、只留下一個 core」的事故調查。你會在不重現、不上線的情況下，從 core 還原當機現場、找出根因、寫出事故報告。這是生產環境 debug 的終極演練。

## 背景與動機

這是最接近真實工作的練習。線上服務崩潰，你手上只有：一個 core dump、對應的 binary、和一份模糊的告警。沒有原始情境、不能重現、不能上線測試——只能靠 core 把現場還原。這正是 SRE/後端工程師處理 production incident 的日常。做完這個練習，你就具備了「拿著 core 就能查線上崩潰」的硬實力。

## 任務規格

### 產生一個「production-like」的崩潰

```c
// server.c — gcc -g -O2 -pthread server.c -o server
// 注意用 -O2！模擬 release build（Ch 32 的難度）
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <pthread.h>
#include <unistd.h>

typedef struct Request {
    int    id;
    char  *url;          // 可能是 NULL
    int    method;
} Request;

typedef struct Worker {
    int       worker_id;
    Request  *current;
} Worker;

static int route(const char *url) {
    return (int)strlen(url);          // url=NULL 時崩潰
}

static void *worker_loop(void *arg) {
    Worker *w = (Worker *)arg;
    for (int i = 0; i < 3; i++) {
        Request r = { .id = w->worker_id * 100 + i, .url = "/api/data", .method = 1 };
        // 第 2 個 worker 的第 2 個 request 故意 url=NULL（模擬上游傳了壞資料）
        if (w->worker_id == 2 && i == 1) r.url = NULL;
        w->current = &r;
        int code = route(r.url);      // url=NULL → strlen(NULL) → SIGSEGV
        printf("worker %d req %d -> %d\n", w->worker_id, r.id, code);
        usleep(1000);
    }
    return NULL;
}

int main(void) {
    pthread_t t[4];
    Worker w[4];
    for (int i = 0; i < 4; i++) {
        w[i].worker_id = i;
        pthread_create(&t[i], NULL, worker_loop, &w[i]);
    }
    for (int i = 0; i < 4; i++) pthread_join(t[i], NULL);
    return 0;
}
```

### 產生 core

```bash
ulimit -c unlimited
gcc -g -O2 -pthread server.c -o server
./server                    # 會崩潰，產生 core
# 找到 core（依 core_pattern / coredumpctl）
```

### 你要做的事

1. 載入 core，找出**哪個 thread** 崩潰、崩在哪、是什麼 signal。
2. 用 backtrace 找出崩潰的呼叫鏈。
3. 找出**根因**：是哪個 worker、處理哪個 request、為什麼 url 是 NULL。
4. 對抗 `-O2` 的難度（`<optimized out>`，Ch 32）——從暫存器/其他 thread 撈出線索。
5. 寫一份事故報告：根因 + 影響 + 修法。

### 驗收標準

- [ ] 找出崩潰 thread 與其他 thread 的狀態（`thread apply all bt`）
- [ ] 確定 signal 與崩潰位置（`route`/`strlen`，url=NULL）
- [ ] 追出是 worker 2 的某 request 的 url=NULL
- [ ] 對抗 `-O2`：即使參數 `<optimized out>`，從 `Worker` 結構或暫存器撈出 worker_id
- [ ] 寫出根因報告（含修法建議）

## 期望輸出範例

```
(gdb) thread apply all bt
Thread 3 (worker 2):
#0  strlen () ...
#1  route (url=0x0) at server.c:18
#2  worker_loop (arg=0x...) at server.c:30
...其他 thread 在 join 或正常結束...

(gdb) thread 3
(gdb) frame 2
(gdb) print *w           # Worker 結構
$1 = {worker_id = 2, current = 0x...}
(gdb) print *w->current  # 那個壞 request
$2 = {id = 201, url = 0x0, method = 1}   # url = NULL！根因
```

## 如果你卡住了

1. **怎麼知道哪個 thread 崩？** 載入 core，GDB 預設 focus 在崩潰的 thread。`info threads`、`thread apply all bt` 看全貌。
2. **`-O2` 讓參數都 `<optimized out>`？** 回 Ch 32：`info registers` 找參數暫存器、看 `Worker` 結構（在記憶體裡，沒被優化掉）、或從別的 frame 撈。
3. **`route` 的 url 看不到？** `route` 被 inline 或參數優化掉。但 `worker_loop` 的 `w`（Worker*）通常還在——`print *w->current` 看那個 request。
4. **strlen 是 libc 沒符號？** 沒關係，看 `route` 那層（你的 code）。配 debuginfod 可看 libc。

## 實作步驟建議

### Step 1：載入與初步定位

```
$ gdb ./server core.server.XXXXX
(gdb) bt                  # 崩潰 thread 的 backtrace
(gdb) print $_siginfo._sifields._sigfault.si_addr   # SIGSEGV 存取的位址（0x0?）
```

子目標：確認 SIGSEGV、存取位址 0x0（NULL 解參）、崩在 `route`/`strlen`。

### Step 2：全 thread 狀態

```
(gdb) info threads
(gdb) thread apply all bt
```

子目標：看到崩潰 thread + 其他 thread 在哪（有的可能正常跑完、有的在 join）。確認是「一個 worker 崩了」。

### Step 3：切到崩潰 thread 找根因

```
(gdb) thread <崩潰的>
(gdb) frame <worker_loop 那層>
(gdb) print *w
(gdb) print *w->current
```

子目標：找到 `worker_id = 2`、`current->url = NULL`、`current->id = 201`。確定是 worker 2 的某 request。

### Step 4：對抗 -O2

子目標：如果 `route` 的 url 是 `<optimized out>`，從 `worker_loop` 的 `w` 撈（Worker 結構在記憶體）；如果連 `w` 都 optimized out，從 `$rdi`（worker_loop 的參數）或暫存器撈。練習 Ch 32 的技能。

### Step 5：寫事故報告

子目標：根因（worker 2 收到 url=NULL 的 request，route→strlen(NULL) 崩潰）+ 影響（單一 request 崩潰整個 process）+ 修法（route 檢查 NULL、上游驗證輸入）。

$ gdb ./server core.server.12345

崩在 strlen，存取位址 0x0 = strlen(NULL)。

### 全 thread 狀態

```
(gdb) thread apply all bt

Thread 4 (LWP 12347):
#0  worker_loop ... (正常跑或結束)
Thread 3 (LWP 12346): ...
Thread 2 (LWP 12348):                # ← 崩潰的
#0  __strlen_avx2 ()
#1  0x... in route (url=0x0) at server.c:18
#2  0x... in worker_loop (arg=0x7fff...) at server.c:30
#3  ... in start_thread ...
Thread 1 (LWP 12345):                # main
#0  ... in pthread_join ...          # main 卡在 join 等 worker
```

崩潰 thread 的鏈：`worker_loop → route(url=0x0) → strlen`。其他 worker 有的跑完、main 在 join。

### 找根因

```
(gdb) thread 2                       # 切到崩潰 thread
(gdb) frame 2                        # worker_loop 那層
#2  worker_loop (arg=0x7fff...) at server.c:30
(gdb) print *(Worker*)arg            # 看 Worker（arg 可能要 cast）
$2 = {worker_id = 2, current = 0x7ffff...}
(gdb) print *((Worker*)arg)->current
$3 = {id = 201, url = 0x0, method = 1}   # 根因！url=NULL, id=201, worker 2
```

確定：worker 2 處理 id=201 的 request，它的 url 是 NULL。對照 code，正是 `if (w->worker_id == 2 && i == 1) r.url = NULL`——模擬上游傳了壞資料。

### 對抗 -O2

`-O2` 下，`route` 的 `url` 參數可能顯示 `<optimized out>`，但 backtrace 仍標 `url=0x0`（GDB 從 strlen 的呼叫慣例或 entry value 推出，Ch 32）。`worker_loop` 的 `arg`（Worker*）通常還在 stack（它被 `w->current = &r` 取址，必須有記憶體位置）。若 `arg` 也 optimized out：

```
(gdb) frame 2
(gdb) info registers                 # 找 worker_loop 入口的 rdi（arg）
(gdb) print *(Worker*)$rdi           # 從暫存器撈（入口處有效）
```

或從崩潰 frame 往回：`route` 的 url 在 `$rdi`（route 的第一參數）= 0x0，已經是答案。

### 事故報告

```
== Incident Report ==
Signal:   SIGSEGV (NULL pointer dereference at 0x0)
Location: route() → strlen(NULL), server.c:18
Thread:   worker 2 (LWP 12348)
Root cause:
  Worker 2 處理 request id=201 時，該 request 的 url 欄位為 NULL。
  route() 直接 strlen(url) 未檢查 NULL，導致 SIGSEGV。
  上游（request 來源）允許了 url=NULL 的 request 進入處理。
Impact:
  單一 malformed request 導致整個 server process 崩潰（所有 worker 一起死）。
  這是可用性風險：一個壞 request 打掛整個服務。
Fix:
  1. route() 加 NULL 檢查：if (!url) return -1;
  2. 上游驗證：拒絕 url=NULL 的 request 進入 worker。
  3. 架構層面：考慮 worker 崩潰隔離（一個 worker 崩不該帶死全部）。
```

**解答說明**：

這個練習濃縮了 production debug 的完整流程：
- **core 分析**（Ch 33）：載入、`$_siginfo` 看 signal/位址。
- **多執行緒**（Ch 16）：`thread apply all bt` 定位崩潰 thread + 看全貌。
- **backtrace + frame**（Ch 10）：切到對的 frame 找變數。
- **-O2 對抗**（Ch 32）：參數 optimized out 時從結構/暫存器撈。
- **根因 + 報告**：不只「崩在 strlen」，而是「worker 2、request 201、url=NULL、上游沒驗證」——可行動的結論。

最重要的軟技能：debug 的終點不是「找到崩在哪」，而是「**找到根因 + 影響 + 修法**」。`strlen(NULL)` 是症狀，「上游允許 url=NULL」才是根因，「一個壞 request 打掛整個 process」才是真正要修的影響。

## 延伸挑戰（加分）

1. **無 debug info 版**：`strip` 掉 binary 重產 core，只靠組語 + 暫存器（Ch 11）+ 部分符號還原——純逆向難度。
2. **配 debuginfod**：開 debuginfod，讓 libc 的 strlen 也有符號/原始碼，看完整 backtrace。
3. **gcore 對照**：用 Ch 33 的 `gcore` 對一個活著的 server 拍快照，對比崩潰 core。
4. **自動化分析腳本**：寫一個 `gdb -batch -x analyze.gdb ./server core` 腳本，自動印 `thread apply all bt` + 崩潰 frame 的關鍵變數——production 自動化分析（呼應 Ch 19 batch）。
5. **Python 自動根因**：用 Part 5 的 Python API 寫一個指令，自動找崩潰 thread、自動 cast 出 Worker/Request、自動印根因——Final Project 的雛形。
6. **多層真實案例**：改 code 製造更深的呼叫鏈（解析器、狀態機），練習在複雜 backtrace 裡定位。
