# Ch 38 — 完整逆向方法論：陌生 App 的 SOP

> **目標**：把 Ch 1 給你的那張骨架 SOP（偵察 → 判斷防護 → 定位目標 → 靜動印證 → 產出）**展開成一套能照著跑的完整方法論**。給你一棵**決策樹**：拿到任何一個陌生 APK，每一步該問什麼問題、看什麼證據、根據答案往哪個分支走。學完這章，面對一個從沒見過的 App，你不會再「開 jadx 亂翻」，而是有一條清楚的路徑：從辨識框架、量測防護等級，到規劃攻擊鏈、決定產出物。

> **環境**：本章是方法論整合，指令片段以 **AVD（Android 13 / API 33）+ apktool 2.9 / jadx 1.4 / Frida 16.x** 為準。凡是用到 unzip/檔案掃描這種本機能跑的，標「**實際輸出**」；需要 AVD/真機才能重現的動態步驟，標「**未實測，理論預期行為**」並給你自己環境的驗證步驟。

## 為什麼需要這個？

前面 37 章給了你一整箱工具：apktool、jadx、Frida、IDA、脫殼器、反反調試腳本。工具會用，不等於會逆向。**逆向的難點從來不是「這個工具怎麼按」，是「現在該用哪個工具、打哪一層、下一步往哪走」**。

我看過太多人的失敗模式長一模一樣：拿到一個帶加固的 App，直接開 jadx，翻到一堆 `com.stub.StubApp`、`libjiagu.so`、名字全是 `a.a.a` 的類，翻了兩小時一無所獲，然後結論是「這 App 太難逆不動」。真相是他連「這是加固殼、真程式碼根本不在靜態 DEX 裡」都沒判斷出來——**方向錯了，努力全白費**。

方法論的價值就在這裡：它讓你在**投入昂貴工具（IDA 逆 native、寫 Frida 腳本、脫殼）之前**，先用便宜的偵察動作把 App 分類、把防護等級量出來、把攻擊路徑規劃好。這是「先想再做」跟「邊做邊撞牆」的差別。真實的安全評估有時效壓力，你不可能每個 App 都從頭亂試——你需要一套**可重複、能交接、有決策依據**的流程。

## 先建立直覺：逆向是一棵決策樹，不是一條直線

Ch 1 的 SOP 是線性的五步，那是為了好記。真實的逆向是**帶回溯的決策樹**：每一步的觀察會把你導向不同分支，某個分支撞牆了就回到上一個決策點換條路。

```
                        拿到陌生 APK
                             │
              ┌──────────────▼──────────────┐
              │  Phase 0: 偵察 (recon)       │
              │  它是什麼？什麼框架？有沒有殼？ │
              └──────────────┬──────────────┘
                             │
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
    原生 Java/Kotlin      Flutter/RN/Unity      有加固殼
    (本課主線)           (換專門工具，見下)     (先脫殼→回 Phase 0)
         │                                        │
         │◀───────────────────────────────────────┘  脫殼拿到真 DEX 後
         ▼                                            重新偵察
    ┌────────────────────────┐
    │ Phase 1: 量測防護等級   │  混淆？反調試？反 Frida？
    │  (決定要帶多重的火力)    │  pinning？完整性校驗？
    └───────────┬────────────┘
                ▼
    ┌────────────────────────┐
    │ Phase 2: 定位目標       │  你到底要找什麼？
    │  (縮小到幾個類/方法/函式) │  登入邏輯/簽名/金鑰/開關
    └───────────┬────────────┘
                ▼
    ┌────────────────────────┐
    │ Phase 3: 靜動印證       │  靜態找 → 動態驗 → 靜態深入
    │  (螺旋，不是單向)        │  卡住就回上一個 Phase
    └───────────┬────────────┘
                ▼
    ┌────────────────────────┐
    │ Phase 4: 產出           │  Frida 腳本/smali patch/
    │                        │  重放 PoC/評估報告
    └────────────────────────┘
```

三個要點刻進腦子：

1. **偵察決定你走哪條主幹**——框架判斷（原生 vs Flutter vs 加固）錯了，後面全錯。
2. **有加固的話，脫殼是一個「回到起點」的動作**——脫完殼你拿到真 DEX，要**重新跑一次 Phase 0 偵察**，因為殼底下的真 App 可能又是另一種形態。
3. **Phase 3 是螺旋不是直線**——靜態縮範圍、動態驗證、發現在 native 就回去逆 `.so`、發現走網路就回去抓包，來回震盪直到目標清晰。

## Phase 0：偵察 —— 在動用重火力之前先分類

偵察的目標是**用最便宜的動作，回答三個問題**：這是什麼 App？什麼框架？有沒有加固？三個問題全靠 `unzip` + 掃檔案 + 讀 Manifest 就能回答，不需要 root、不需要跑起來。

### 動作 1：解開 APK，掃檔案清單

```bash
unzip -l target.apk | sort -k1 -n -r | head -40   # 按大小排，先看大檔
```

你在找的線索：

- **哪些 `.so`？** `lib/*/` 底下的 native 庫名字是框架與加固的最強指紋。
- **`classes*.dex` 的大小與數量**——異常小的主 DEX（幾 KB）配一個大 `.so`，是加固的訊號。
- **`assets/` 裡有什麼**——Flutter 的 `flutter_assets/`、加固殼的加密 blob、第二階段 payload 常藏這（Ch 2 說的金礦）。

### 動作 2：用 `.so` 與檔案指紋判斷框架

這是偵察最關鍵的分岔。**同樣叫「安卓 App」，底層形態差很多，逆向策略完全不同**：

| 看到什麼指紋 | 框架 | 真邏輯在哪 | 你該換的工具/策略 |
|---|---|---|---|
| 只有 `classes*.dex` + 少量業務 `.so` | **原生 Java/Kotlin** | DEX + 自寫 native | 本課主線：jadx/apktool/Frida/IDA |
| `libflutter.so` + `libapp.so` + `flutter_assets/` | **Flutter** | `libapp.so`（Dart AOT，無符號） | reFlutter / blutter；本課只指路 |
| `index.android.bundle` 在 `assets/` | **React Native** | JS bundle | 抽 bundle、`hbc` 反編譯（Hermes）；相對易逆 |
| `libil2cpp.so` + `global-metadata.dat` | **Unity (IL2CPP)** | `libil2cpp.so` | Il2CppDumper 還原符號後逆 |
| `libjiagu.so`/`libshell*.so`/`libDexHelper.so` 等 | **加固殼**（見下表） | 真 DEX 被藏起來（執行期還原） | 先脫殼（Part 5）再回 Phase 0 |

**加固殼的指紋**（看到就知道要走脫殼路線）：

| 殼 `.so` / 特徵 | 加固廠商 | 大致世代 |
|---|---|---|
| `libjiagu.so`, `libjiagu_art.so` | 360 加固保 | 一/二代混合 |
| `libshella-x.x.x.so`, `libshellx-*.so` | 梆梆/愛加密 | 二代 |
| `libDexHelper.so`, `libDexHelper-x86.so` | 娜迦/Bangcle | 二代 |
| `libtprt.so`, `libtup.so`, `libmobisec` | 騰訊樂固/legu | 二代/VMP |
| `libnesec.so`, `libNESec.so` | 網易易盾 | 二代/VMP |
| Application 名為 `com.stub.StubApp` / `s.h.e.l.l` | 通用殼載入器 | — |

> **判斷世代決定策略**（Ch 28 展開）：**一代殼**（整包 DEX 加密後在記憶體整個還原）好脫，記憶體 dump 就有真 DEX；**二代殼**（DEX 抽取成函式級、跑到才還原一個方法）要靠主動調用（FART 那套，練習 E）；**VMP**（把 Dalvik bytecode 轉成自訂 VM 指令）最難，往往只能逐函式硬啃。偵察時認出殼，先查它大概是哪一代，你才知道要帶多重的火力。

### 動作 3：讀 Manifest 定位「這是什麼、從哪起步」

```bash
apktool d target.apk -o target_out       # 把 binary XML 解成可讀
```

Manifest 你要撈的欄位（Ch 2 講過，這裡是偵察清單版）：

- **`package`**：App 身分。也拿去 `frida-ps -U` 對照跑起來的進程名。
- **`<application android:name=...>`**：自訂 Application 類。名字怪（`StubApp`、單字母、混淆）→ **加固強訊號**，殼從這裡開機先跑。
- **入口 `Activity`**（`MAIN`/`LAUNCHER`）：靜態分析的起點。
- **`android:debuggable`**：若為 `true`，不用 root 也能 attach 除錯器——逆向大禮包。
- **權限清單**：`INTERNET`（走網路，要抓包）、`READ_CONTACTS`/`SEND_SMS`（可疑，惡意樣本重點）。

偵察產出：一句話描述「這是一個 **X 框架**、**有/無加固（哪家殼、大概幾代）**、入口在 **Y**、走網路 **是/否** 的 App」。這句話決定你接下來的整條路。

## Phase 1：量測防護等級 —— 決定帶多重的火力

偵察知道「有沒有加固」是粗分類。Phase 1 要細測**這個 App 到底防了幾層**，因為防護等級決定你要投入多少成本。一個裸奔的 App 可能十分鐘 jadx 讀完；一個「加固殼 + native 簽名 + SSL pinning + 反 Frida + 完整性校驗」的 App 是一週的活。**先量出來，才好排程與規劃火力**。

我用這張表當防護等級量表（對逆向者就是「阻力等級」）：

| 防護層 | 怎麼偵測 | 阻力 | 對應繞法（章節） |
|---|---|---|---|
| **DEX 混淆**（名字 `a.b.c`） | jadx 開來看，全是單字母 | 低 | 靠動態印值反推（Ch 8/13） |
| **字串加密** | 看不到明文 URL/key，有 `decrypt()` 包裹 | 低-中 | hook 解密函式印明文（Ch 13） |
| **SSL pinning** | 抓包時 App 報憑證錯、連不上 | 中 | bypass pinning（Ch 17） |
| **加固殼** | Phase 0 的 `.so` 指紋 | 中-高 | 脫殼（Ch 29） |
| **反調試 / 反 Frida** | Frida attach 就閃退/卡死 | 中-高 | 繞反調試（Ch 30） |
| **root / 模擬器檢測** | App 一開就說「環境不安全」退出 | 中 | 繞檢測（Ch 31） |
| **native 化關鍵邏輯** | 簽名/加密在 `.so` 不在 DEX | 高 | 逆 native + hook（Ch 22–25） |
| **完整性校驗** | 改完重打包一裝就閃退 | 中-高 | 繞校驗（Ch 32） |
| **OLLVM / VMP** | IDA 反編譯出來控制流爆炸/看不懂 | 很高 | 去混淆（Ch 27）/ 硬啃 |

**怎麼快速量**——用一個「五分鐘探針」序列：

```
1. jadx 開一下 → 名字混淆嗎？有沒有明文字串？   （測混淆/字串加密）
2. frida-ps -U 能不能 attach 上目標進程？        （測反 Frida，見下）
3. objection/mitmproxy 抓一個請求 → 連得上嗎？    （測 pinning）
4. Phase 0 已知有沒有殼、有沒有業務 .so          （測加固/native 化）
5. apktool 改一個字串重打包裝上去 → 閃退嗎？       （測完整性校驗）
```

> **反 Frida 的探針要小心**：直接 `frida -U -f pkg` spawn，如果 App 有反 Frida，可能一 attach 就閃退，你會誤以為「Frida 壞了」。正確做法是先 attach 一個**什麼都不做的空腳本**觀察是否閃退——閃退代表有反 Frida（Ch 30），這本身就是一條情報，不是你的環境壞了。**未實測（需 AVD/目標 App）**；驗證步驟：`frida -U -f <pkg> -e "console.log('attached')"`，看它是正常印出還是進程秒死。

Phase 1 產出：一張「這個 App 的防護清單」，每一項標好阻力與對應繞法章節。這張清單就是你的作戰地圖。

## Phase 2：定位目標 —— 先問「我到底要找什麼」

**逆向最忌諱漫無目的地讀程式碼**。一個中型 App 有幾萬個方法，你不可能全讀。Phase 2 逼你先把**目標寫成一句具體的話**，再用它反過來縮小搜尋範圍。

目標通常是這幾類之一：

- **某個 API 請求的參數怎麼算的**（如 `sign`/`token`）——最常見，練習 B、final 都是這個。
- **某段加密/解密的演算法與金鑰**——還原協議、解本地資料。
- **某個功能開關的判斷邏輯**（如 VIP 判斷、環境檢測）——要 patch 或繞過的目標。
- **某個本地儲存的敏感資料**（密碼、token）——資料外洩評估。

有了目標，用**關鍵字回溯**縮範圍。搜的順序從「最可能命中」到「最泛」：

```
搜尋優先序（jadx 全域搜 + apktool grep smali）：
1. 業務字串    "sign" "token" "encrypt" "secret" "key" "nonce"
2. URL / API   搜出所有 endpoint，鎖定你關心的那支請求
3. 系統 API    Cipher / Mac / MessageDigest / getBytes / Base64
              （加密一定經過這些，是很強的錨點）
4. JNI 註冊    native 方法宣告、System.loadLibrary（邏輯在 .so 的入口）
5. 反射字串    Class.forName / getMethod（混淆常用反射躲靜態搜）
```

`Cipher`/`Mac`/`MessageDigest` 這幾個是**黃金錨點**：任何 App 做 HMAC、AES、SHA 都得經過 `javax.crypto` 或 `java.security` 這幾個類。就算名字全混淆了，這些**系統 API 類名不會變**（App 不能混淆 framework 的類）。從這裡下 hook，你能直接抓到「它在對什麼資料做什麼加密、用什麼 key」。

Phase 2 產出：把幾萬個方法縮到「這 3-5 個類/方法/native 函式最可疑」。

## Phase 3：靜動印證 —— 螺旋前進

拿到 Phase 2 的可疑清單，開始**靜態看一眼、動態驗一下、再靜態深入**的螺旋。核心心法：**靜態告訴你「程式碼長怎樣」，動態告訴你「執行期真實的值」**，兩者對照才不會被混淆騙。

一條典型的螺旋（以「還原登入請求簽名」為例，串起本課多個 Part）：

```
靜態: jadx 搜 "sign" → 找到 LoginReq.buildSign()，但它呼叫一個 native 方法
  ↓ （Java 層看不到 native 內部）
動態: Frida hook buildSign()，印出它傳進 native 的參數
  ↓ （拿到參數，但簽名怎麼算的還在 .so 裡）
靜態: IDA 逆那個 .so 的 JNI 函式 → 看出是 HMAC-SHA256(排序拼接的參數, key)
  ↓ （演算法懂了，但 key 是動態算的，靜態看不到值）
動態: Frida hook native 的 HMAC 入口 / hook Mac.init → 印出執行期真實的 key
  ↓ （演算法 + key 都有了）
產出: 自己用 Python 重算 sign，寫重放腳本驗證（Phase 4）
```

看到這條鏈跨了 **Ch 17（抓包）→ Ch 13（hook Java）→ Ch 22（逆 .so）→ Ch 14/25（hook native）**——這正是 Ch 1 說的「真實任務串多個攻擊面」。方法論的作用是讓你知道**現在螺旋到哪一圈、下一步該靜還是動**。

**卡住時的回溯規則**（決策樹的精髓）：

- **動態 hook 不到**（函式沒被呼叫/名字對不上）→ 回 Phase 2 確認你鎖的方法對不對，或 App 有反 Frida（回 Phase 1）。
- **靜態看到殼載入器不是真邏輯** → 你漏判了加固，回 Phase 0 重新偵察、走脫殼。
- **native 函式 IDA 反編譯像亂碼** → 可能 OLLVM，回 Phase 1 標記「高阻力」，考慮改用純動態（hook 進出 + Stalker trace）而非硬讀。

## Phase 4：產出 —— 逆向不是讀懂就結束

逆向的價值在**產出物**，不是「我看懂了」。依任務不同，產出是：

| 任務類型 | 產出物 | 對應章節 |
|---|---|---|
| 改 App 行為 | smali patch + 重打包重簽的 APK | Ch 6/10 |
| 持久化修改 | Frida 腳本 / LSPosed 模組 | Ch 13–16 |
| 還原協議 | 協議文件 + Python 重放 PoC | Ch 18 |
| 安全評估 | 逆向報告（漏洞、風險、佐證） | 本 Part |
| 自動化分析 | 可複用 Frida 腳本庫 | Ch 40 |

**產出要能被別人驗證**：報告附上你怎麼得到結論的證據鏈（hook log、抓包截圖、重放腳本跑通的輸出），而不是「我覺得它是 HMAC」。這是安全研究跟「我玩了一下」的分界線。final project 就是逼你把整條鏈走完並產出一份可交付的報告。

## 對比與取捨：什麼時候該停、該換路、該升火力

| 情境 | 該怎麼決策 | 為什麼 |
|---|---|---|
| jadx 一開全明文、沒殼沒混淆 | 直接靜態讀到底，別急著上 Frida | 靜態最快，動態是為了「靜態看不到的值」 |
| 靜態看到 `native` 方法 | 別硬讀 Java，去 hook 它印參數/回值 | Java 層邊界外的值只有動態拿得到 |
| 偵察發現加固殼 | **先脫殼**再談後面，別在殼裡瞎翻 | 殼裡沒有真邏輯，翻了也白翻 |
| IDA 反編譯像亂碼（疑 OLLVM） | 改純動態（hook 進出 + Stalker） | 硬去混淆成本極高，動態繞開它 |
| 目標只要「繞過一個開關」 | patch smali 就好，別逆整個演算法 | 目標導向：夠用就停，別過度分析 |
| 目標要「還原完整協議重放」 | 得逆到演算法+key，動靜全上 | 重放需要精確重算，含糊的理解不夠 |

**核心取捨是「投入 vs 目標」**：逆向可以無限深挖，但你的任務有邊界。方法論幫你在「夠用了該收」與「還沒到得繼續」之間做判斷——別把「繞一個開關」的活做成「重寫整個加密庫」。

## 踩雷集錦

1. **跳過 Phase 0 直接開 jadx**：不判框架、不看殼，對著加固殼的載入器或 Flutter 的空殼 DEX 猛翻，白費半天。**先偵察再動手**是這章的頭號紀律。
2. **把「Frida attach 就閃退」當成環境壞了**：那多半是**反 Frida**（Ch 30），是一條情報不是 bug。先用空腳本 attach 確認，別急著重裝 Frida。
3. **脫殼後忘了重新偵察**：脫出真 DEX 就以為到終點——真 DEX 可能又混淆、又把邏輯搬 native。**脫殼是回到 Phase 0，不是抵達 Phase 4**。
4. **無目標地讀程式碼**：沒先寫下「我要找什麼」就開始翻，讀了三小時不知道自己在找啥。Phase 2 的「一句話目標」是省時間的關鍵。
5. **只信靜態或只信動態**：靜態被字串加密/混淆騙、動態只看到這次跑到的路徑。**兩者互相印證**才可靠——這是 Phase 3 螺旋的意義。
6. **在 x86_64 AVD 上逆到 x86 native 卻以為是 ARM64**：Ch 0 的環境陷阱在方法論階段一樣咬人。要逆真機的 ARM64 `.so`，換 arm64 image 或真機（尤其反模擬器的 App 只能真機，見下）。

## 進階：再往深一層

- **反模擬器 App 逼你上真機**：有些加固/風控 App 會檢測模擬器（讀 `ro.kernel.qemu`、感測器數量、`/proc/cpuinfo` 特徵），在 AVD 上直接拒跑。這類目標的 Phase 1 會很早撞牆，方法論上要及早判斷「這個必須上 arm 真機」，別在 AVD 上耗。**本課環境（x86_64 AVD）對這類 App 有先天限制，誠實標注：需要 root 過的 arm64 真機**。
- **框架的次分類**：Flutter 還分 debug/release、有沒有開 `--split-debug-info`；RN 分 JSC 與 Hermes（Hermes 是 `.hbc` bytecode，要專門反編譯）。偵察精細一點，選工具才準。
- **威脅建模式的偵察**：進階做法是在 Phase 0 就用 OWASP MASTG 的檢查清單系統化跑一遍（儲存、通訊、加密、認證、反竄改、反逆向），把「量測防護」變成有標準的稽核，而不是憑感覺。這也是把個人手藝變成可交接流程的關鍵。
- **自動化偵察**：Phase 0 的偵察動作（掃 `.so` 指紋、讀 Manifest、量防護）高度可腳本化。MobSF 這類工具就是把 Phase 0-1 自動化。Ch 40 會教你自己寫批量偵察腳本，把這章的手動流程變成一鍵報告。

## 動手練習

1. 拿三個你有權分析的 App（自己寫的、開源的、CTF 題各一），只做 **Phase 0**：對每一個寫出那句「這是 X 框架、有/無加固、入口 Y、走網路 是/否」的偵察結論。故意挑一個 Flutter 或 Unity 的，親眼看 `.so` 指紋長什麼樣、跟原生 App 差在哪。
2. 對其中一個原生 App 做 **Phase 1**，用「五分鐘探針」序列量出它的防護清單，每一項標阻力與對應章節。就算探針結果是「什麼防護都沒有」，也把這個結論寫下來——**確認沒有防護本身也是情報**。
3. 選一個目標（例如「找出它某支網路請求的某個參數怎麼來的」），走完 **Phase 2 的關鍵字回溯**，把幾萬個方法縮到你認為最可疑的 3 個。先不求逆出結果，只練「怎麼從一句目標縮到幾個方法」。
4. 把本章的決策樹（Phase 0→4 那張圖）不看筆記自己畫一遍，並在每個決策點標上「觀察到什麼 → 走哪個分支」。畫得出來，方法論才真的進腦。

## 本章重點整理

- 逆向是一棵**帶回溯的決策樹**（偵察 → 量防護 → 定目標 → 靜動印證 → 產出），不是線性流程。
- **Phase 0 偵察**用最便宜的動作（unzip + `.so` 指紋 + Manifest）分類 App：框架判斷與加固判斷錯了，後面全錯。
- **Phase 1 量防護等級**決定帶多重火力；「五分鐘探針」快速量出防護清單，反 Frida 閃退是情報不是 bug。
- **Phase 2 先寫一句話目標**，再用關鍵字回溯縮範圍；`Cipher`/`Mac`/`MessageDigest` 是不會被混淆的黃金錨點。
- **Phase 3 靜動螺旋印證**，卡住就回溯到上一個 Phase；**Phase 4 產出可驗證的成果**才算完成。
- **脫殼是回到 Phase 0 重新偵察，不是抵達終點**；投入永遠對齊任務邊界，夠用就收。
