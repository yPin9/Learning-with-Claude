# Ch 1 — 安卓逆向全貌：攻擊者視角與工作流

> **目標**：在碰任何工具之前，先把整張地圖攤開。一個 App 從原始碼到在螢幕上跑起來，中間經過哪些形態轉換？攻擊者能在哪些點切入？拿到一個陌生 APK，你的 SOP 是什麼？這章給你一個**心智框架**，讓後面 40 章的每個工具都能對號入座——你會知道 apktool 打的是哪一層、Frida 切的是哪一刀、脫殼脫的是什麼。

## 為什麼要先看全貌？

初學逆向最大的陷阱是「工具驅動」：學了 jadx 就到處 jadx，學了 Frida 就什麼都 hook，結果面對一個有加固的 App 完全不知道從哪下手——因為你腦中沒有地圖，不知道「現在卡在哪一層、下一步該換哪個工具」。

逆向的本質是**還原資訊**。開發者從高階原始碼（Java/Kotlin/C++）一路編譯、打包、混淆、加固，每一步都在**丟棄或隱藏資訊**（變數名沒了、控制流被打亂、DEX 被藏起來）。你的工作是逆著這條管線，把資訊一層一層還原回來。所以你必須先懂**這條管線長什麼樣**——知道資訊在哪一步被丟掉，才知道去哪一步把它撈回來。

## 先建立直覺：App 的一生

一個 App 從開發者的鍵盤到你手機的螢幕，經過這條單向管線：

```
   開發者這端（正向：編譯打包）                你這端（逆向：還原）
 ┌──────────────────────────────┐
 │ Java / Kotlin 原始碼          │◀──────── jadx 想還原到這裡（近似）
 │        │ javac / kotlinc      │
 │        ▼                      │
 │ .class (JVM bytecode)         │
 │        │ d8 / r8              │
 │        ▼                      │
 │ classes.dex (Dalvik bytecode) │◀──────── apktool 還原到 smali（一對一）
 │  C/C++ ──ndk──▶ lib*.so       │◀──────── IDA/Ghidra 逆 native
 │        │ aapt2 打包 + 簽名     │
 │        ▼                      │
 │ app.apk  (一個 zip)           │◀──────── 你拿到的通常是這個
 │        │ 有加固的話：加殼      │
 │        ▼                      │
 │ 加固後的 app.apk              │◀──────── 脫殼：把真 DEX 從記憶體撈回來
 └──────────────────────────────┘
              │ 安裝 + 執行
              ▼
   ┌─────────────────────────┐
   │ ART runtime 載入 DEX     │◀──────── Frida 在這裡動態 hook
   │ dex2oat 編成機器碼        │           （執行期，資訊最全）
   └─────────────────────────┘
```

看懂這張圖，你就懂了逆向的兩大策略：

- **靜態分析**：不執行 App，直接對著檔案（APK/DEX/.so）還原。優點是全面、可反覆看；缺點是碰到混淆/加固就卡住，因為你手上的檔案裡資訊已經被藏起來了。
- **動態分析**：讓 App 真的跑起來，在**執行期**觀測。優點是加固殼在執行期一定得把真程式碼還原到記憶體（不然 CPU 沒法執行），所以動態能繞過很多靜態繞不過的東西；缺點是只能看到「這次執行走到的路徑」。

這兩者不是二選一，是**互相補**。Ch 11 會專門講「為什麼動態常常贏」，但真正的高手是兩手都用、互相印證。

## 形態轉換：資訊在每一步怎麼被丟掉

逆向能還原到什麼程度，取決於資訊在哪一步被丟。逐層看：

| 形態 | 長什麼樣 | 逆向工具 | 能還原多少 |
|---|---|---|---|
| Java/Kotlin 原始碼 | 有變數名、註解、型別 | —（原始） | — |
| `.class` JVM bytecode | 保留大量 metadata | —（安卓不直接用） | 幾乎 100% |
| **`classes.dex`** | Dalvik bytecode，暫存器式 | apktool→smali | smali **一對一無損**；反編譯 Java **近似** |
| **`.so`** native | ARM64/x86 機器碼 | IDA/Ghidra | 反組譯無損；反編譯 C **近似** |
| 混淆後 | 名字變 `a`/`b`/`c`、控制流打亂 | 去混淆 | 邏輯在，但可讀性大降 |
| 加固後 | 真 DEX 被加密藏起來 | 脫殼 | 執行期還原 |

兩個關鍵事實要刻進腦子：

1. **DEX → smali 是一對一無損的**。smali 就是 Dalvik bytecode 的文字表示，一條 bytecode 對一條 smali，改 smali 再組回去 100% 對應。所以要**改邏輯重打包**，走 smali（Ch 5/6）。
2. **DEX → Java 是「反編譯」，是猜的**。jadx 把 bytecode 往上推回類 Java 語法，但編譯是有損的（區域變數名早就沒了、`for`/`while` 可能被還原成別的形狀、Kotlin 的協程會變成一坨狀態機）。所以 jadx 的輸出是**給你讀懂用的近似**，不是能重新編譯的原始碼。搞混這兩件事是新手最常見的認知錯誤。

> **一個常見誤解**：「我用 jadx 反編譯出 Java，改一改再編譯回去不就好了？」——不行。jadx 的輸出常常編不過（它產的是給人讀的近似 Java，不保證語法完整），而且就算編過也對不回原本的 DEX。要改邏輯，你改的是 **smali**（apktool），不是 jadx 的 Java。

## 攻擊者視角：這張地圖上有哪些切入點

同一張管線圖，用攻擊者的眼睛重看一遍，每一層都是一個攻擊面：

```
攻擊面                          你想拿到什麼               主要武器
──────────────────────────────────────────────────────────────────
① APK 靜態（DEX/資源）      邏輯、字串、金鑰、API      jadx / apktool
② App 層執行期             跑起來的真實參數/返回值    Frida hook Java
③ 網路流量                 它跟伺服器說什麼            mitmproxy + pinning bypass
④ Native .so              藏在 C 裡的核心演算法       IDA/Ghidra + Frida hook native
⑤ 加固殼                  被藏起來的真 DEX            脫殼（dump/主動調用）
⑥ 儲存/IPC               本地存的密碼、token         objection dump / 逆 IPC
⑦ ART runtime            繞過殼與反調試的最底層       ArtMethod hook / 改 runtime
```

一個真實的分析任務通常要串好幾個攻擊面。舉例：你想還原某 App「登入請求的簽名怎麼算的」——

1. 先 **③ 抓包**看請求長什麼樣，發現有個 `sign=xxxx` 參數（③）。
2. **① jadx** 搜 `sign`，發現簽名邏輯呼叫了一個 native 方法（① → ④）。
3. **④ IDA** 逆那個 `.so`，看懂它是 `HMAC-SHA256(參數排序後拼接, 金鑰)`（④）。
4. 但金鑰是動態算出來的，靜態看不到值——**② Frida hook** 那個 native 函式，印出執行期真正傳進去的金鑰（②）。
5. 拿到金鑰與演算法，自己重算 `sign`，寫個腳本重放請求——**任務完成**。

這就是為什麼你不能只會一個工具。這條鏈（練習 B、練習 C、final 都會走）跨了三個攻擊面。這門課的 Part 2–6 就是把每個攻擊面各自挖深，Part 7 教你怎麼把它們串成一條鏈。

## 拿到陌生 APK 的標準 SOP

給你一個從沒看過的 APK，別急著開 jadx 亂翻。先跑這套偵察流程（Ch 38 會展開成完整方法論，這裡先給骨架）：

```
1. 偵察 (recon)
   ├─ 這是什麼 App？看 AndroidManifest：package、入口 Activity、權限、元件
   ├─ 用了什麼框架？Flutter / React Native / Unity / 原生？（決定逆向策略）
   └─ 有沒有加固？看 DEX 大小異常 / 有沒有殼的特徵 so（libjiagu 之類）

2. 判斷防護等級
   ├─ 沒混淆沒加固 → 直接 jadx 讀，可能十分鐘搞定
   ├─ 有混淆 → 讀得動但慢，配合 Frida 動態確認
   └─ 有加固 → 先脫殼（Part 5），拿到真 DEX 再回到步驟 1

3. 定位目標
   ├─ 你要找什麼？（登入邏輯 / 某個 API 的參數 / 某個開關 / 金鑰）
   ├─ 靜態搜關鍵字：字串、API 名、URL、"sign"/"token"/"encrypt"
   └─ 縮小到幾個可疑類/方法

4. 靜動印證
   ├─ Frida hook 可疑方法，印參數與返回值，確認你猜對了
   ├─ 邏輯在 native？→ 逆 .so + hook native
   └─ 走網路？→ 抓包對照

5. 產出
   └─ 改 smali 重打包 / 寫 Frida 腳本 / 寫重放 PoC / 寫報告
```

**框架判斷**（步驟 1）是個常被忽略但很關鍵的分岔。同樣是「安卓 App」，底層可能差很多：

| 框架 | 邏輯藏在哪 | 逆向重點 |
|---|---|---|
| **原生 Java/Kotlin** | DEX + 少量 .so | 本課主線，jadx/apktool/Frida |
| **Flutter** | `libapp.so`（Dart AOT，無符號） | 難逆，需專門的 Dart 反編譯（reFlutter） |
| **React Native** | JS bundle（`index.android.bundle`） | 逆 JS，相對容易 |
| **Unity** | `libil2cpp.so` + `global-metadata.dat` | 用 Il2CppDumper 還原符號 |

> **這門課聚焦原生 Java/Kotlin + native 的 App**（也就是絕大多數 App 的形態）。Flutter/RN/Unity 各自是獨立的坑，Ch 38 會給指路，但不深入——先把主線練扎實。

## 對比與取捨：靜態 vs 動態，先用哪個？

| 情境 | 先靜態 | 先動態 | 為什麼 |
|---|---|---|---|
| App 沒加固沒混淆 | ✅ | | jadx 直接讀最快 |
| App 有加固 | | ✅ | 靜態看到的是殼，要動態脫殼才有真程式碼 |
| 想確認某函式的執行期參數 | | ✅ | 靜態只看得到程式碼，看不到執行期的值 |
| 想全面理解一個模組 | ✅ | | 靜態能通盤看，動態只看到跑過的路徑 |
| 反調試很兇 | ✅ 先靜態找防護 | | 先靜態定位反調試邏輯，才知道動態要繞什麼 |

實務上是**螺旋前進**：靜態縮小範圍 → 動態確認 → 靜態再深入 → 動態再驗證。不是線性的「先做完靜態再做動態」。

## 踩雷集錦

1. **把 jadx 的 Java 當成能編譯的原始碼**：jadx 輸出是**近似**、常編不過。要改邏輯重打包，改的是 smali（apktool），不是 jadx 的 Java。這是全安卓逆向最根本的認知錯誤，Ch 5–7 會一再強調。
2. **一上來就 jadx 亂翻，沒先偵察**：不看 Manifest、不判斷框架、不確認有沒有加固，直接翻程式碼——結果翻到的是殼的載入器，或翻一個 Flutter App 的空殼 DEX，白費半天。先 recon。
3. **以為加固 App 靜態就徹底沒轍**：加固藏了 DEX，但執行期一定得還原到記憶體（CPU 才能跑），所以動態脫殼幾乎總有辦法。「靜態卡住」不等於「逆不了」，只是要換動態這條腿。
4. **忽略 native 層**：很多人只會 Java 層，碰到「關鍵邏輯搬進 .so」就投降。現代 App 把值錢的東西（簽名、加密、風控）放 native 正是為了擋只會 Java 的人。native 是本課 Part 4 的重點，不能跳。
5. **框架沒判斷就套原生策略**：對 Flutter App 猛翻 DEX 只會看到框架膠水碼，真邏輯在 `libapp.so` 的 Dart AOT 裡。先判斷框架再選策略。

## 進階：再往深一層

- **殼的「一代到 VMP」光譜**：加固不是一個東西，是一個從「整包 DEX 加密」（一代殼，好脫）到「DEX 抽取成函式級」（二代）再到「把 Dalvik bytecode 轉成自訂 VM 指令」（VMP，最難）的光譜。Ch 28 會展開，這裡先知道「殼有強弱之分，策略跟著變」。
- **逆向的合法邊界**：不同司法管轄區對逆向工程的態度不同（研究/互通性豁免 vs DMCA 反規避條款）。做安全研究要清楚：你逆的是不是你有權分析的對象？這門課的所有目標都是自己寫的 crackme、開源 App、CTF 題、或明確授權的評估物件。這不只是道德問題，是保護你自己。
- **對抗是動態的軍備競賽**：你學的每個脫殼/繞過技術，加固廠商都在想辦法擋。所以本課教的不只是「這個工具怎麼用」，更是「這類防護的原理是什麼」——原理不變，具體繞法會隨版本變，Ch 41 從防禦者視角再看一次這場軍備競賽。

## 動手練習

1. 找一個你自己裝的、來源正當的 App（或 AOSP 內建 App），用 Ch 0 學的 `pm path` + `pull` 撈出 APK，把它當成「陌生 APK」，走一遍上面的 SOP 步驟 1（偵察）：看 Manifest 找入口與權限、判斷它是什麼框架。先不求逆出什麼，只練「拿到 APK 先看什麼」。
2. 把同一個 APK 用 apktool 拆出 smali、用 jadx 拆出 Java，隨便找一個方法，兩邊對照著看——親眼感受「smali 是一對一的機器邏輯」vs「Java 是給人讀的近似」的差別。
3. 對著本章的「App 的一生」那張圖，不看筆記，自己畫一遍，並在每個箭頭標上對應的逆向工具。畫得出來，代表地圖進腦了。

## 本章重點整理

- 逆向的本質是**逆著編譯打包管線還原資訊**；懂管線才知道去哪一層撈回被丟掉的資訊。
- **DEX→smali 一對一無損（用來改）**，**DEX→Java 是近似（用來讀）**——這是全課最根本的區分。
- 攻擊面有七層（APK 靜態 / App 執行期 / 網路 / native / 殼 / 儲存 / runtime），真實任務常串多層。
- 拿到陌生 APK 的 SOP：**偵察 → 判斷防護 → 定位目標 → 靜動印證 → 產出**；先判斷框架再選策略。
