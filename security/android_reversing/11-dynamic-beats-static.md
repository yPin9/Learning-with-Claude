# Ch 11 — 為什麼動態贏靜態

> **目標**：把 Ch 1 埋下的「靜態 vs 動態」種子長成一套可操作的直覺。你要能回答：面對一個加固/混淆的 App，為什麼「讓它跑起來、在執行期看」常常比對著檔案硬啃更快、更準？動態的優勢從哪來、限制又在哪？以及最重要的——靜態和動態不是二選一，而是一組互相咬合的螺旋，你要知道每一步該切哪一刀。這章之後（Ch 12 起）我們才正式進 Frida，屆時你會知道自己每個 hook 是在替哪個靜態盲點補位。

## 為什麼需要這個？

因為新手最容易犯的錯，是把「逆向」等同於「用 jadx 把 App 讀完」。這在沒防護的 App 上行得通，一碰到加固、混淆、native、動態解密的真實 App 就撞牆——你打開 jadx，看到的是一坨 `a.a.a()`、一個空殼 `Application`、或乾脆連真 DEX 都不在檔案裡。這時候你需要的不是「更用力地讀」，而是換一條腿：讓 App 自己把它藏起來的東西，在執行期攤在你面前。

想通「為什麼動態贏」不是為了叫你放棄靜態。恰恰相反——只有你懂動態強在哪、弱在哪，你才知道什麼時候該靜態縮範圍、什麼時候該動態捅一刀。這章給你的是**決策框架**，不是某個工具。

## 先建立直覺：靜態是看藍圖，動態是看施工現場

先給你一個貫穿全章的心智模型。假設你要搞懂一棟大樓是怎麼蓋的：

```
   靜態分析（看藍圖）                  動態分析（站在施工現場）
 ┌────────────────────────┐        ┌────────────────────────────┐
 │ 你有全部圖紙            │        │ 你只看得到「今天在蓋的」    │
 │  ✔ 每個房間都畫出來    │        │  ✔ 混凝土真的怎麼灌你看到  │
 │  ✔ 可以反覆翻、慢慢看  │        │  ✔ 藍圖騙人的地方現場穿幫  │
 │  ✘ 圖被塗改（混淆）    │        │  ✘ 沒開工的樓層你看不到    │
 │  ✘ 有些圖故意不給（殼）│        │  ✘ 要親自到場、可能被趕出去│
 └────────────────────────┘        └────────────────────────────┘
        ▲                                    ▲
        │  藍圖說「這裡是牆」                 │  現場發現那面「牆」是活動隔間
        └────────── 互相對照，才不會被單邊騙 ──┘
```

三個要點先刻進去：

- **靜態全面但可被欺騙**。你手上有整包檔案，可以反覆看、通盤看；但檔案裡的資訊是開發者「決定給你看的」——他可以混淆它、加密它、乾脆不放進去（加固殼把真 DEX 藏在執行期才解密的 blob 裡）。你看到的藍圖可能是假的。
- **動態真實但只看得到跑過的路徑**。App 要執行，CPU 就必須拿到**真正的、解密後的**指令與資料——這是物理事實，殼再兇也繞不過。所以執行期的東西是「真的」。代價是你只看得到這次執行實際走到的分支；沒觸發的功能、沒走到的 error path，動態完全看不到。
- **兩者互補，不是對立**。真正的工作流是螺旋：靜態縮小可疑範圍 → 動態捅一刀確認 → 靜態再往深挖 → 動態再驗。

## 底層機制：為什麼「執行期一定有真相」

動態之所以能贏，根植於一個繞不過的事實：**再怎麼加密、加固、混淆的程式碼，最終都得變回 CPU 能執行的形態**。把這條路徑攤開看：

```
   開發者藏東西的手段              執行期發生什麼（動態能截到的點）
 ─────────────────────────────────────────────────────────────────
  DEX 被殼加密藏在 assets   ──▶  ART 載入前，殼必須在記憶體裡解密成
                                  真 DEX 交給 ClassLoader
                                  ↑ 動態：從記憶體 dump 真 DEX（脫殼）

  字串被加密（"aHR0cH…"）   ──▶  用的那一刻，解密函式回傳明文字串
                                  ↑ 動態：hook 解密函式，印回傳值

  簽名金鑰動態拼出來        ──▶  呼叫 native 前，金鑰已在暫存器/記憶體
                                  ↑ 動態：hook 該 native 函式，讀參數

  控制流被 OLLVM 打平       ──▶  CPU 還是得一條一條真的執行下去
                                  ↑ 動態：trace 實際執行序列（Stalker）
 ─────────────────────────────────────────────────────────────────
        關鍵：資訊在「被使用的那一刻」一定是明文/真實的
```

這就是動態的根本優勢來源。靜態面對的是「開發者精心佈置的檔案」，動態面對的是「CPU 不得不執行的真相」。開發者可以讓你**看不懂**檔案，但不能讓 CPU 看不懂——而動態就站在 CPU 這一側。

我們用一個最小例子把這件事講具體。假設一段 Java 邏輯是這樣（開發者把 API 金鑰用 Base64「藏」起來，執行期才解）：

```java
// 開發者的原始碼（示意）
String key = decrypt("k7Hq3nX9...==");   // 靜態只看得到這串密文
callApi(url, sign(params, key));          // 金鑰在這一刻是明文
```

- **靜態視角**：jadx 給你看到的是 `decrypt("k7Hq3nX9...==")`。這串密文對你毫無意義，你還得回頭逆 `decrypt` 的演算法、找它的 key、自己重算——如果 `decrypt` 又在 native 層，你得再開 IDA。這條路走得通，但慢。
- **動態視角**：你根本不管 `decrypt` 怎麼實作的。你 hook 它，讓它照跑，只在它 `return` 的那一刻把回傳值印出來——明文金鑰直接躺在你 log 裡。**你用 App 自己的解密邏輯，幫你解了密。**

這就是「動態贏」最典型的一刀：**不還原演算法，直接偷結果**。

## 三個場景：動態各贏在哪個點

### 場景一：加固殼——靜態看到的根本不是真程式碼

你 jadx 打開一個加固 App，`MainActivity` 只有幾行、真正的邏輯類全部找不到，`Application` 是個叫 `com.stub.StubApp` 的東西。這不是你找錯地方——是**真 DEX 根本不在這個 APK 的 `classes.dex` 裡**，它被殼加密塞在別處（`assets/` 的 blob、`.so` 裡的資料段），開機時由殼在記憶體裡解密、再餵給 ClassLoader。

- **靜態單獨處理**：卡死。你手上的 DEX 是殼的載入器，不是 App。
- **動態的解法**：讓 App 跑起來——殼被迫在記憶體裡把真 DEX 解出來（不然 ART 沒東西可載入）。這時候從記憶體把真 DEX dump 回來（Part 5 的脫殼），你就拿到了「靜態原本拿不到」的東西。

> **邊界**：dump 出來的 DEX 可能是「函式級抽取」的殼——類結構在、但方法體是空的，執行期才逐個回填。這種殼一次 dump 不完整，要主動調用每個方法逼它回填（練習 E 的 mini FART）。所以「動態能脫殼」不代表「一鍵脫乾淨」，殼有強弱之分（Ch 28）。

### 場景二：混淆——名字沒了，但執行期行為騙不了人

一個經過 R8/ProGuard + 字串加密的 App，jadx 裡滿眼 `a.b.c(d, e)`，你連哪個方法是「登入」都認不出來。純靜態你得靠交叉引用、常數、字串殘骸慢慢拼。

- **動態的解法**：你不需要知道方法叫什麼。你在乎的是「按下登入按鈕後，哪些方法被呼叫、參數是什麼」。用 Frida 把可疑範圍內的方法**全部 hook 起來印 call trace**，點一下登入，執行序列直接告訴你 `a.b.c` 收到了你的帳號密碼——名字是假的，行為是真的。

這就是動態對抗混淆的核心思路：**混淆改的是「標識」（名字、控制流形狀），改不了「行為」（誰呼叫誰、傳什麼值）**。動態盯行為，繞開了標識這一整層騙術。

### 場景三：動態產生的值——靜態物理上看不到

有些東西靜態**原理上就不存在於檔案裡**：

- 執行期才從伺服器下發的金鑰、開關
- `System.currentTimeMillis()`、隨機數、裝置 ID 這類 runtime 值
- 多層拼接才算出來的簽名（各段散在不同函式，靜態拼不出最終值）

這些不是「藏得好」，是**檔案裡根本沒有那個值**——它是在執行的那一刻才誕生的。靜態再強也變不出來，只有動態在「值誕生的那一刻」把它截下來。

## 動靜互補的螺旋工作流

看到這你可能覺得「那我全用動態不就好了」。錯。動態有個致命弱點會在下一節講；這裡先把**正確的協作姿勢**建立起來。真實逆向不是「先做完靜態再做動態」的線性流程，是一個螺旋：

```
  ┌─▶ 靜態 recon：jadx 掃字串/API，縮到 3 個可疑方法 ──┐
  │                                                      ▼
  │                                          動態 hook 這 3 個，印參數/返回值
  │                                                      │
  │   靜態回去讀「動態證實有用」的那 1 個 ◀───────────────┘
  │        （只深挖被驗證過的，不浪費時間讀死碼）
  │                    │
  │                    ▼
  └── 發現它呼叫 native → 靜態 IDA 逆 .so + 動態 hook 讀執行期金鑰 …循環
```

Ch 1 那條「還原簽名」的鏈就是這個螺旋的實例：抓包（動）→ jadx 搜 `sign`（靜）→ IDA 逆 .so（靜）→ Frida hook 印金鑰（動）。每一步都是用一邊的結果，餵給另一邊當起點。

**為什麼非螺旋不可**？因為：

- 純靜態會**淹死在死碼裡**——你不知道哪些方法真的會跑，可能花三小時讀一個根本沒被呼叫的分支。動態告訴你「這條路真的走到了」，幫你聚焦。
- 純動態會**瞎子摸象**——你不知道整體結構，只能看到這次點按觸發的片段，容易見樹不見林。靜態給你地圖，讓你知道剛才 hook 到的方法在整個架構裡的位置。

一句話：**靜態給廣度與結構，動態給真實與聚焦。** 缺一邊，你要嘛淹死、要嘛瞎摸。

## 一條螺旋走完：還原一個 `sign` 參數的成本對照

抽象講完，我們把一條真實任務攤開，逐步標「純靜態要花多少力」對「螺旋省了多少」。任務：某 App 登入請求帶一個 `sign=3f9a...` 參數，你要搞懂它怎麼算，好自己重放請求。

```
步驟         純靜態的走法（慢）                螺旋的走法（快）
─────────────────────────────────────────────────────────────────────
① 起點      jadx 全域搜 "sign"，命中 40 處    先抓包（動）：看到 sign 只在
            逐個讀，猜哪個是請求簽名          登入這一支請求出現 → 縮到 1 支 API
─────────────────────────────────────────────────────────────────────
② 定位      順著呼叫鏈讀 20 個混淆方法        hook 那支 API 的組請求方法（動），
            （a.b.c → d.e.f …），人肉追      印 call stack → 直接看到 sign 在
                                             哪個方法被塞進去，跳過 19 個死追
─────────────────────────────────────────────────────────────────────
③ 演算法    逆出它呼叫 native nativeSign()    jadx 確認 nativeSign 是 native（靜），
            → 開 IDA 逆整個 .so 的演算法      IDA 大致看出是 HMAC（靜），但金鑰
            （HMAC-SHA256），再找金鑰         動態算出來 → hook nativeSign 印
                                             執行期真金鑰（動），不逆金鑰生成
─────────────────────────────────────────────────────────────────────
④ 收尾      自己用 Python 重寫 HMAC + 金鑰    要嘛重寫、要嘛更省：直接
                                             NativeFunction 呼叫 App 的
                                             nativeSign 當 oracle（Ch 14）
─────────────────────────────────────────────────────────────────────
成本        數小時～數天，且金鑰是動態的       ①②③ 各被動態砍掉大半，
            靜態可能根本拿不到最終金鑰值       金鑰用 hook 直接偷 → 半天內完成
```

看清楚動態在每一步的角色：它**不是取代**靜態的 IDA/jadx，而是**替靜態剪枝**——把「40 處搜尋結果」剪到 1 支請求、把「追 20 個混淆方法」剪到直接看 call stack、把「逆金鑰生成邏輯」剪成「hook 印出金鑰值」。這就是 Ch 1 那條鏈的成本細節。動態贏，很多時候贏的不是「靜態做不到」，而是「靜態做得到但貴得離譜，動態一刀砍掉九成成本」。

## 動態的限制：只看得到跑過的路徑

現在講那個致命弱點，這是本章最需要你記住的誠實。動態的一切優勢都建立在「App 真的執行了那段程式碼」上——**沒跑到的，動態一無所知**。

```
   App 的所有程式碼路徑
 ┌───────────────────────────────────────┐
 │  ┌──────────┐   你這次觸發的路徑        │
 │  │ 登入成功 │◀── 動態看得到 ✔          │
 │  └──────────┘                           │
 │  ┌──────────┐                           │
 │  │ 登入失敗 │◀── 你沒觸發 → 動態看不到 ✘│
 │  └──────────┘                           │
 │  ┌────────────────┐                     │
 │  │ if(被 root) 自毀 │◀ 你沒踩到條件 → 看不到 ✘
 │  └────────────────┘   （但它存在，靜態看得到）
 └───────────────────────────────────────┘
```

這帶來幾個實際後果：

- **覆蓋率問題**：一個功能你沒點到，它的邏輯動態就是空白。要全面理解一個模組，你得靜態通盤看，或想辦法觸發所有分支（很難）。
- **反調試/反 Frida 的隱藏路徑**：App 可能有「偵測到 Frida 就走另一條路（假資料、閃退、靜默上報）」的邏輯。這條路你「正常操作」時不會走到，但它一偵測到你就啟動——你甚至不知道自己已經被騙了。這正是為什麼 Ch 30 要先**靜態**找出反調試邏輯，才知道動態要繞什麼。
- **觀測即干擾**：你 attach 上去、hook 下去，本身就改變了 App 的執行環境（多了 frida-server 進程、記憶體被改、時序變了）。有防護的 App 會偵測這些。你看到的「執行期真相」有可能是「被你的存在污染後的真相」。

所以動態不是萬能。它強在「看真實跑過的東西」，弱在「看不到沒跑的、且自己會擾動現場」。這正是它需要靜態當搭檔的根本原因——靜態能看到那些「存在但這次沒跑」的分支（那個 `if(被 root) 自毀`），提前告訴你地雷在哪。

## 對比與取捨

| 維度 | 靜態分析 | 動態分析 |
|---|---|---|
| **看到的是** | 開發者決定給你看的檔案 | CPU 不得不執行的真相 |
| **覆蓋範圍** | 全部程式碼（含沒跑的） | 只有這次執行跑過的路徑 |
| **對抗混淆** | 弱（名字/控制流被打亂就慢） | 強（盯行為，繞開標識騙術） |
| **對抗加固** | 弱（真 DEX 不在檔案裡） | 強（執行期殼必須解密，可 dump） |
| **拿執行期值** | 拿不到（檔案裡沒有） | 直接截（值誕生的那一刻） |
| **可反覆性** | 高（檔案不變，隨便看） | 低（要重跑，時序可能不同） |
| **對目標的擾動** | 零（不執行） | 有（進程、記憶體、時序被改） |
| **反調試影響** | 不受影響 | 可能被偵測、被餵假資料 |
| **適合** | 建立結構、通盤理解、找隱藏分支 | 驗證假設、脫殼、偷執行期值、對抗混淆 |

看清楚：兩欄的強弱幾乎是**互補的**——一邊弱的地方正好是另一邊強的地方。這不是巧合，這就是為什麼成熟的逆向永遠兩手都用。

## 踩雷集錦

1. **「動態萬能，靜態可以不學」**：錯。動態看不到沒跑的路徑，也會擾動現場被反調試騙。那個「偵測到 Frida 就自毀」的分支，你只有靜態才提前看得到。動態強，但瞎了一隻眼——靜態是它的另一隻眼。
2. **「靜態卡住 = 這個 App 逆不了」**：錯。靜態卡住多半只代表「資訊被藏在執行期」，換動態這條腿就通了。Ch 1 的踩雷 3 講過，這裡再強調：加固/混淆讓靜態難，不讓動態難。
3. **「我全 hook 起來跑一遍就等於看完了」**：錯。你只看到「這次操作觸發的路徑」。沒點到的功能、沒滿足條件的分支，全是動態盲區。別把「跑過的」當成「全部的」。
4. **「動態看到的一定是真的」**：不完全對。你 attach 的動作本身改變了環境，有防護的 App 會偵測並餵你假資料。動態的「真」，前提是「你沒被發現」。被發現後，你看到的是它想給你看的。
5. **「先把靜態全做完，再開始動態」**：低效。真實工作是螺旋——靜態縮範圍就馬上動態驗，別想著讀完整包 DEX 再動手。你會淹死在死碼裡。

## 進階：再往深一層

- **符號執行填動態的覆蓋率洞**：動態只走一條路，符號執行（symbolic execution，如 angr）能把「輸入當成符號」一次探索多條分支，理論上補上「沒跑到的路徑」這個洞。代價是路徑爆炸、對真實大型 App 常跑不動。它是動靜之外的第三種視角，知道它存在、知道它想解決什麼即可。
- **動態的「觀測代價」是個光譜**：從輕到重——讀記憶體（幾乎無擾動）< hook 單一函式 < 全域 trace（Stalker，Ch 15，時序影響大）< 附加除錯器（最重，最容易被反調試偵測）。防護越兇，你越要往「輕擾動」那端靠。這是 Ch 30 對抗反 Frida 的核心權衡。
- **「動態脫殼 → 回靜態」是螺旋的經典閉環**：加固 App 你先動態脫殼（Part 5）拿到真 DEX，然後**回到靜態**用 jadx 讀那個真 DEX。動態在這裡不是終點，是「幫你把靜態的原料撈回來」的手段。整個 Part 5–6 都在玩這個閉環。

## 動手練習

1. **親眼看動態繞過字串加密**：找一個你自己寫的小 App（或 crackme），把一個字串用 Base64 編碼後在執行期 `decode` 再用。先用 jadx 靜態看——你只看到密文。回頭想：如果 hook 那個 `decode` 方法印回傳值，你會看到什麼？把這個「靜態密文 vs 動態明文」的對比在腦中走一遍（實際 hook 到 Ch 13 就會寫）。
2. **畫覆蓋率盲區**：拿你熟的任一 App，列出它 5 個功能。假設你只點了其中 2 個——畫出「動態看得到的 2 塊」和「動態全黑的 3 塊」。體會「跑過的 ≠ 全部的」。
3. **設計一條螺旋**：給定任務「找出某 App 登入請求裡 `sign` 參數怎麼算」，不看 Ch 1 的答案，自己排出「靜態/動態交替」的步驟序列，標明每步是哪一邊、為什麼這步該用這一邊。排完再回頭對照 Ch 1 的鏈。

## 本章重點整理

- **動態贏的根本原因**：程式碼再怎麼藏，執行期一定得變回 CPU 能執行的真相——動態站在 CPU 這一側，靜態站在「開發者佈置的檔案」那一側。
- **動態最典型的一刀**：不還原演算法，直接 hook 偷結果（用 App 自己的邏輯幫你解密/算簽名）。
- **動態三大主場**：加固殼（執行期必解密可 dump）、混淆（盯行為繞開名字騙術）、執行期值（檔案裡根本沒有）。
- **動態的致命弱點**：只看得到跑過的路徑，且觀測本身會擾動現場、可能被反調試餵假資料。
- **正確姿勢是螺旋**：靜態給廣度與結構、動態給真實與聚焦，交替前進，缺一邊要嘛淹死要嘛瞎摸。
