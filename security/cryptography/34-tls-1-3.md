# Ch 34 — TLS 1.3：一個握手搞定一切

> 目標：能畫出 TLS 1.3 的 1-RTT 握手流程（ClientHello → ServerHello → Finished），理解 HKDF key schedule 如何從一個共享秘密衍生出所有 traffic key，解釋 TLS 1.3 砍掉了什麼（RSA key exchange、CBC mode、renegotiation）以及為什麼砍。

---

## 為什麼需要 TLS 1.3

TLS 1.2 活了十年（2008–2018），累積的問題不是「不能用」而是「太多選擇」：

- **Cipher suite 組合爆炸**：TLS 1.2 允許 300+ 種 cipher suite 組合。每多一種組合，攻擊面就多一塊——ROBOT（RSA padding oracle）、POODLE（CBC padding oracle）、Logjam（512-bit DHE）全是「允許弱組合」的後果
- **握手太慢**：TLS 1.2 的 full handshake 需要 2-RTT——先交換參數，再交換 key，然後才能傳資料。對行動裝置和高延遲連線來說，多一個 RTT 就是多幾百毫秒
- **沒有 forward secrecy 的強制要求**：TLS 1.2 允許 RSA key transport——server 把 pre-master secret 用 RSA 加密直接傳給 client，沒有 ephemeral DH。一旦 server 的 private key 洩漏，所有歷史流量都能解密
- **Renegotiation 和 compression 是攻擊向量**：Triple Handshake attack 和 CRIME attack 分別利用了這兩個功能

TLS 1.3（RFC 8446, 2018）的設計哲學：**砍掉所有已知有問題的功能，強制只留安全的選項**。

## 先建立直覺

把 TLS 1.3 握手想成兩個人在公共場所建立悄悄話頻道：

1. **Alice 先出手**：她在第一則訊息裡同時附上「我支援哪些加密方式」和「這是我的 DH 公鑰」
2. **Bob 回應**：他挑一個加密方式，附上自己的 DH 公鑰——**到這裡雙方已經能算出共享秘密**
3. **Bob 繼續**（在加密通道裡）：傳送自己的身份證明（certificate + 簽章）
4. **Alice 確認**：驗證 Bob 的身份，傳一個 Finished 訊息
5. **開始傳資料**

整個過程只需要 **1-RTT**（Alice 發一趟、Bob 回一趟、Alice 確認一趟就能開始傳資料）。

對比 TLS 1.2：需要 2-RTT（多一趟用來協商參數）。

## 核心概念：1-RTT 握手流程

### 範例一：用 openssl s_client 觀察 TLS 1.3 握手

```bash
# 連到 cloudflare 的 TLS 1.3 server，dump 握手過程
openssl s_client -connect www.cloudflare.com:443 -tls1_3 -msg -debug 2>&1 | head -80

# 更精簡的版本：只看握手訊息
openssl s_client -connect www.cloudflare.com:443 -tls1_3 -tlsextdebug -status
```

你會看到這些訊息（按順序）：

```
>>> TLS 1.3 [ClientHello]
<<< TLS 1.3 [ServerHello]
<<< TLS 1.3 [EncryptedExtensions]
<<< TLS 1.3 [Certificate]
<<< TLS 1.3 [CertificateVerify]
<<< TLS 1.3 [Finished]
>>> TLS 1.3 [Finished]
```

每則訊息的角色：

| 訊息 | 方向 | 功能 |
|------|------|------|
| ClientHello | C → S | 支援的 cipher suite、key_share（DH 公鑰）、signature_algorithms |
| ServerHello | S → C | 選定的 cipher suite、server 的 key_share |
| EncryptedExtensions | S → C | 加密後才傳的 extension（ALPN、server_name 等） |
| Certificate | S → C | Server 的 X.509 憑證鏈 |
| CertificateVerify | S → C | Server 用私鑰對 handshake transcript 簽章 |
| Finished (server) | S → C | HMAC over transcript — 證明 server 看到的和你看到的一樣 |
| Finished (client) | C → S | Client 端的 transcript HMAC |

### 握手流程圖

```
Client                                            Server
──────                                            ──────
ClientHello
  + supported_versions: [TLS 1.3]
  + supported_groups: [x25519, secp256r1]
  + key_share: x25519 公鑰 gᵃ
  + signature_algorithms: [ed25519, ecdsa_secp256r1_sha256]
  + cipher_suites: [TLS_AES_256_GCM_SHA384,
                    TLS_CHACHA20_POLY1305_SHA256]
─────────────────────────────────────────────→

                                            ServerHello
                                              + selected cipher: TLS_AES_256_GCM_SHA384
                                              + key_share: x25519 公鑰 gᵇ
                                            ────────────── 從這裡開始加密 ──────────
                                            {EncryptedExtensions}
                                            {Certificate}
                                            {CertificateVerify}
                                            {Finished}
                                ←─────────────────────────────────────────────

    ◆ 雙方各自算出 shared secret = gᵃᵇ
    ◆ 用 HKDF 從 shared secret 衍生 handshake keys
    ◆ Client 驗證 server certificate + CertificateVerify

{Finished}
─────────────────────────────────────────────→

    ◆ 用 HKDF 衍生 application traffic keys
    ◆ 開始傳加密資料

{Application Data}              ←→            {Application Data}
```

注意幾個關鍵點：

1. **ClientHello 直接帶 key_share**：不需要先協商用哪個 group 再做 DH——Client 猜測 server 最可能接受的 group，直接算好公鑰附上。如果猜錯，server 回 HelloRetryRequest
2. **EncryptedExtensions 在加密後傳**：TLS 1.2 的 extension 全部明文，洩漏了 server 端的資訊。TLS 1.3 只有 ClientHello 和 ServerHello 是明文
3. **CertificateVerify 簽的是整個 handshake transcript**：攻擊者不能把一個合法 handshake 的 Certificate 貼到另一個 handshake 裡——transcript 不同，簽章驗證會失敗

## 底層機制：HKDF Key Schedule

TLS 1.3 的 key schedule 是整個 protocol 最精巧的部分。所有金鑰都從一條鏈上衍生出來。

### HKDF 的兩個操作

| 操作 | 輸入 | 輸出 | 目的 |
|------|------|------|------|
| HKDF-Extract(salt, IKM) | salt + 輸入 key material | PRK（pseudorandom key） | 「濃縮」：把不夠隨機的 input 變成均勻隨機的 PRK |
| HKDF-Expand-Label(PRK, label, context, length) | PRK + label + transcript hash | 衍生 key | 「展開」：從 PRK 衍生出不同用途的 key |

### 三個 Secret 的推導鏈

```
         0 (32 bytes of zeros)
         │
         v
PSK ──→ HKDF-Extract ──→ Early Secret
         │
         ├── Derive-Secret(., "ext binder" | "res binder", "")
         │     → binder_key
         │
         ├── Derive-Secret(., "c e traffic", ClientHello)
         │     → client_early_traffic_secret     ← 0-RTT data key
         │
         v
    Derive-Secret(., "derived", "")
         │
         v
(EC)DHE ──→ HKDF-Extract ──→ Handshake Secret
         │
         ├── Derive-Secret(., "c hs traffic", ClientHello...ServerHello)
         │     → client_handshake_traffic_secret  ← 握手階段 client 加密 key
         │
         ├── Derive-Secret(., "s hs traffic", ClientHello...ServerHello)
         │     → server_handshake_traffic_secret  ← 握手階段 server 加密 key
         │
         v
    Derive-Secret(., "derived", "")
         │
         v
   0 ──→ HKDF-Extract ──→ Master Secret
         │
         ├── Derive-Secret(., "c ap traffic", ClientHello...server Finished)
         │     → client_application_traffic_secret_0  ← Application data key
         │
         ├── Derive-Secret(., "s ap traffic", ClientHello...server Finished)
         │     → server_application_traffic_secret_0  ← Application data key
         │
         ├── Derive-Secret(., "exp master", ClientHello...server Finished)
         │     → exporter_master_secret
         │
         └── Derive-Secret(., "res master", ClientHello...client Finished)
               → resumption_master_secret  ← 下次 PSK 的種子
```

幾個設計重點：

1. **分離方向**：client → server 和 server → client 用不同的 key。攻擊者不能把 client 的封包反射回去假裝是 server 的
2. **分離階段**：handshake 階段和 application data 階段用不同的 key。即使 handshake key 被 compromise，application data 仍然安全
3. **Transcript hash binding**：每個 Derive-Secret 都包含目前為止所有 handshake message 的 hash。改動任何一則訊息，後續所有 key 都會不同
4. **沒有 PSK 時**：PSK 設為 0，Early Secret 的 HKDF-Extract 退化成 `HKDF-Extract(0, 0)`

### Derive-Secret 的展開

```python
# 概念版（不是完整實作）
def Derive_Secret(secret, label, messages):
    return HKDF_Expand_Label(
        secret,
        label=label,
        context=Hash(messages),  # transcript hash
        length=Hash.digest_size
    )
```

### HKDF-Expand-Label 的結構

```
HKDF-Expand-Label(Secret, Label, Context, Length) =
    HKDF-Expand(Secret, HkdfLabel, Length)

HkdfLabel = struct {
    uint16 length;              // 想要的 output 長度
    opaque label<7..255>;       // "tls13 " + Label
    opaque context<0..255>;     // 通常是 transcript hash
}
```

## 進一步用法：用 Python 建 TLS 1.3 Server + Client

### 範例二：Python ssl module 的 TLS 1.3 連線

```python
"""
tls13_demo.py — TLS 1.3 server + client
需要：Python 3.11+, OpenSSL 3.x
"""
import ssl
import socket
import threading
import subprocess
import os

# ── 步驟 0：生成自簽憑證 ──
def generate_self_signed_cert():
    """用 openssl 生成 EC key + 自簽憑證"""
    if os.path.exists("server.crt") and os.path.exists("server.key"):
        return
    subprocess.run([
        "openssl", "req", "-x509", "-newkey", "ec",
        "-pkeyopt", "ec_paramgen_curve:prime256v1",
        "-keyout", "server.key", "-out", "server.crt",
        "-days", "365", "-nodes",
        "-subj", "/CN=localhost"
    ], check=True)
    print("[+] 自簽憑證已生成")

generate_self_signed_cert()

# ── 步驟 1：建 TLS 1.3 server ──
def run_server():
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    context.load_cert_chain("server.crt", "server.key")

    # 強制只用 TLS 1.3
    context.minimum_version = ssl.TLSVersion.TLSv1_3
    context.maximum_version = ssl.TLSVersion.TLSv1_3

    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
        sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        sock.bind(("127.0.0.1", 8443))
        sock.listen(1)
        print("[Server] Listening on :8443")

        conn, addr = sock.accept()
        with context.wrap_socket(conn, server_side=True) as tls_conn:
            print(f"[Server] TLS version: {tls_conn.version()}")
            print(f"[Server] Cipher: {tls_conn.cipher()}")
            data = tls_conn.recv(1024)
            print(f"[Server] Received: {data.decode()}")
            tls_conn.sendall(b"Hello from TLS 1.3 server!")

# ── 步驟 2：建 TLS 1.3 client ──
def run_client():
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    # 因為是自簽憑證，手動載入 CA cert
    context.load_verify_locations("server.crt")

    context.minimum_version = ssl.TLSVersion.TLSv1_3
    context.maximum_version = ssl.TLSVersion.TLSv1_3

    with socket.create_connection(("127.0.0.1", 8443)) as sock:
        with context.wrap_socket(sock, server_hostname="localhost") as tls_conn:
            print(f"[Client] TLS version: {tls_conn.version()}")
            print(f"[Client] Cipher: {tls_conn.cipher()}")
            tls_conn.sendall(b"Hello from TLS 1.3 client!")
            data = tls_conn.recv(1024)
            print(f"[Client] Received: {data.decode()}")

# ── 啟動 ──
import time
server_thread = threading.Thread(target=run_server, daemon=True)
server_thread.start()
time.sleep(0.5)  # 等 server 開始 listen
run_client()
```

執行結果：

```
[+] 自簽憑證已生成
[Server] Listening on :8443
[Client] TLS version: TLSv1.3
[Client] Cipher: ('TLS_AES_256_GCM_SHA384', 'TLSv1.3', 256)
[Server] TLS version: TLSv1.3
[Server] Cipher: ('TLS_AES_256_GCM_SHA384', 'TLSv1.3', 256)
[Server] Received: Hello from TLS 1.3 client!
[Client] Received: Hello from TLS 1.3 server!
```

注意 cipher 是 `TLS_AES_256_GCM_SHA384`——TLS 1.3 的 cipher suite 名字不再包含 key exchange algorithm，因為 **TLS 1.3 只用 ECDHE/DHE**，不需要在 cipher suite 裡指定。

## 0-RTT：速度的誘惑與 Replay 的代價

TLS 1.3 有一個可選功能：**0-RTT（Early Data）**。

如果 client 之前和 server 建過 TLS 1.3 連線，server 會發一個 resumption ticket。下次連線時 client 可以在 ClientHello 裡直接附上加密的 application data——**不需要等 server 回應就開始傳資料**。

```
Client                                         Server
──────                                         ──────
ClientHello
  + early_data
  + key_share
  + pre_shared_key
(Application Data)              ──→              [0-RTT data]
                                ←──
                                            ServerHello
                                            {EncryptedExtensions}
                                              + early_data
                                            {Finished}
{EndOfEarlyData}
{Finished}                      ──→
```

### 0-RTT 的致命問題：Replay Attack

0-RTT data **沒有 server 的貢獻**——它完全由 client 的 PSK 和 ephemeral key 加密。攻擊者可以錄下 0-RTT data，然後重送給 server。

如果 0-RTT data 是一個「轉帳 1000 元」的 HTTP POST：

1. 攻擊者錄下這個 ClientHello + early data
2. 重送 10 次
3. 帳戶被扣 10000 元

**Server 的責任**：必須自己做 replay 防護（例如只接受 idempotent request 的 0-RTT data，或用 anti-replay token）。TLS 1.3 spec 明確說 0-RTT 沒有 replay protection。

### 什麼時候用 0-RTT

| 場景 | 可以用 0-RTT？ | 原因 |
|------|---------------|------|
| HTTP GET（讀取） | 可以 | Idempotent，重送不會改變 state |
| HTTP POST（寫入） | 危險 | 非 idempotent，replay 會造成重複操作 |
| DNS query | 可以 | Idempotent |
| 資料庫寫入 | 絕對不要 | Replay = 重複寫入 |

## TLS 1.3 砍掉了什麼（以及為什麼）

### 砍掉的功能清單

| 被砍的功能 | 存在的漏洞 | TLS 1.3 的替代方案 |
|-----------|-----------|-------------------|
| RSA key transport | 沒有 forward secrecy；ROBOT attack | 只允許 (EC)DHE |
| CBC mode cipher suite | Padding oracle（POODLE, Lucky 13） | 只允許 AEAD（GCM, ChaCha20-Poly1305） |
| RC4 | 統計 bias 可還原 plaintext | 移除 |
| DES / 3DES | Key 太短（56 / 112 bit） | 移除 |
| Static RSA / Static DH | 沒有 forward secrecy | 只允許 ephemeral (EC)DHE |
| Renegotiation | Triple Handshake attack | 移除（用 post-handshake auth 取代） |
| Compression | CRIME attack | 移除 |
| Custom DHE groups | Logjam（weak group downgrade） | 只允許 named groups（x25519, secp256r1 等） |
| ChangeCipherSpec | 增加複雜度、曾有 implementation bug | 移除 |

### 為什麼砍 RSA key transport 最重要

TLS 1.2 的 RSA key transport：

```
Client                          Server
──────                          ──────
                                [有 RSA private key K]
用 server 的 RSA 公鑰
加密 pre_master_secret
  ──→  RSA_Enc(PMS)
                                用 K 解密得到 PMS
```

問題：如果 server 的 RSA private key **在未來**被洩漏（被駭、硬碟被偷、法律強制交出），攻擊者可以用 K 解密**過去錄下的所有流量**。

TLS 1.3 的 (EC)DHE：

```
Client                          Server
──────                          ──────
gᵃ              ──→
                ←──              gᵇ
shared = gᵃᵇ                    shared = gᵃᵇ
```

a 和 b 是 ephemeral（握手完就丟）。即使 server 的 long-term signing key 洩漏，攻擊者也算不出 gᵃᵇ——因為 a 和 b 已經不存在了。這就是 **forward secrecy（前向保密）**。

## 對比與取捨

### TLS 1.2 vs TLS 1.3 完整對比

| 面向 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 標準年份 | 2008 (RFC 5246) | 2018 (RFC 8446) |
| 握手 RTT | 2-RTT（full）/ 1-RTT（resume） | 1-RTT / 0-RTT（resume） |
| Key exchange | RSA / DHE / ECDHE（自選） | 只允許 (EC)DHE |
| Forward secrecy | 可選（只有 (EC)DHE 有） | 強制 |
| Cipher suite 數量 | 300+ | 5 |
| 允許的 cipher mode | CBC / GCM / CCM / stream | 只允許 AEAD |
| Renegotiation | 有（有 Triple Handshake 風險） | 無 |
| Compression | 有（有 CRIME 風險） | 無 |
| Handshake 加密 | 無（全部明文） | ServerHello 之後加密 |
| 0-RTT | 無 | 可選（有 replay 風險） |
| Certificate 傳輸 | 明文 | 加密 |

### TLS 1.3 的五個 cipher suite

TLS 1.3 只定義了五個 cipher suite：

```
TLS_AES_128_GCM_SHA256           (0x1301) — 必須實作
TLS_AES_256_GCM_SHA384           (0x1302) — 必須實作
TLS_CHACHA20_POLY1305_SHA256     (0x1303) — 推薦
TLS_AES_128_CCM_SHA256           (0x1304)
TLS_AES_128_CCM_8_SHA256         (0x1305) — 用於 IoT
```

名字裡沒有 key exchange algorithm——因為 TLS 1.3 的 key exchange 永遠是 (EC)DHE，不需要在 cipher suite 裡選。

## 踩雷集錦

### 踩雷 1：「TLS 1.3 = 絕對安全」

TLS 1.3 的 protocol design 是目前最好的，但安全性取決於三個層面：

- **Protocol design**：TLS 1.3 處理了 ✓
- **Implementation**：OpenSSL、GnuTLS、BoringSSL 的程式碼可能有 bug（Heartbleed 就是 OpenSSL 的 implementation bug）
- **Configuration**：server admin 可能開了不該開的功能（0-RTT 沒有做 anti-replay）、用了過期的 certificate

protocol 是三層之一。另外兩層出問題，protocol 再好也擋不住。

### 踩雷 2：0-RTT 的 Replay 風險被低估

很多 deployment guide 寫「開 0-RTT 可以降低 latency」，但沒有強調 replay 的後果。Cloudflare 的做法：只對 HTTP GET 啟用 0-RTT，POST/PUT/DELETE 的 early data 直接拒收。

### 踩雷 3：Certificate Pinning 在 TLS 1.3 裡已經 deprecated

HTTP Public Key Pinning（HPKP）因為太容易搞壞自己的網站（pin 到錯誤的 key、忘記更新 pin），被 Chrome 在 2018 年移除。TLS 1.3 的生態裡，Certificate Transparency（CT）是替代方案——它不 pin 特定 key，而是要求所有憑證都公開記錄在 CT log 裡，讓任何人都能監控是否有不正當的憑證簽發。

### 踩雷 4：SNI 仍然是明文

TLS 1.3 加密了 Certificate，但 **Server Name Indication（SNI）仍然在 ClientHello 裡以明文傳送**。中間人可以看到 client 要連哪個 domain。Encrypted Client Hello（ECH，RFC 草案）正在嘗試解決這個問題，但截至 2025 年還沒有被廣泛部署。

### 踩雷 5：混淆 TLS record version 和 handshake version

TLS 1.3 的 ClientHello 裡，record layer 的 version 寫的是 `0x0303`（TLS 1.2），而不是 `0x0304`。真正的版本在 `supported_versions` extension 裡。這是為了和中間裝置（middlebox）相容——很多 middlebox 看到未知的 version 就直接斷線。

## 進階

### HelloRetryRequest（HRR）

如果 server 不支援 client 在 key_share 裡提供的 group，server 會回 HelloRetryRequest，要求 client 用指定的 group 重新做一次 ClientHello。這會把 1-RTT 變成 2-RTT。

```
Client                                         Server
──────                                         ──────
ClientHello (key_share: x25519)    ──→
                                   ←──    HelloRetryRequest
                                            (selected_group: secp384r1)
ClientHello (key_share: secp384r1) ──→
                                   ←──    ServerHello + 正常 handshake
```

實務上很少發生——絕大多數 server 支援 x25519 和 secp256r1，而 client 通常至少附上其中一個的 key_share。

### Post-Handshake Authentication

TLS 1.3 砍了 renegotiation，但有些場景需要在連線建立後才要求 client certificate（例如使用者登入後才需要 mutual TLS）。TLS 1.3 用 post-handshake authentication 取代：server 送一個 CertificateRequest，client 回 Certificate + CertificateVerify + Finished。

### Key Update 和 Session Resumption

TLS 1.3 允許任一方在連線中途發 KeyUpdate 訊息，從舊 key 衍生新 key（`HKDF-Expand-Label(old_secret, "traffic upd", "", length)`），限制單一 key 被 compromise 的影響。

Session resumption 改用 PSK（Pre-Shared Key）：server 在 handshake 結束後送 NewSessionTicket，client 下次連線在 `pre_shared_key` extension 附上 PSK identity。PSK 可以和 (EC)DHE 結合（PSK + DHE mode），保留 forward secrecy。

## 動手練習

1. **觀察 handshake 差異**：用 `openssl s_client -tls1_2` 和 `openssl s_client -tls1_3` 分別連同一個 server（例如 `www.google.com:443`），比較兩者的 handshake message 數量和 cipher suite 格式

2. **Cipher suite 計數**：寫一個腳本用 `openssl ciphers -v 'ALL:@STRENGTH'` 列出你的 OpenSSL 支援的所有 TLS 1.2 cipher suite，數有幾個；再用 `openssl ciphers -v -tls1_3` 列出 TLS 1.3 的，數有幾個

3. **HKDF 手動推導**：用 Python 的 `hmac` 和 `hashlib` 模組實作 `HKDF-Extract` 和 `HKDF-Expand-Label`，對一組已知的 test vector（RFC 8448, Section 4）驗證你的 output 是否正確

4. **（挑戰）0-RTT replay 實驗**：修改範例二的程式，讓 server 發 NewSessionTicket，client 下次連線帶 early data。然後用 Wireshark 錄下 ClientHello + early data，觀察 early data 是否在 ServerHello 之前就送出了

---

## 重點整理

1. **TLS 1.3 的核心改進**：1-RTT 握手（快）、強制 (EC)DHE（forward secrecy）、只允許 AEAD cipher（安全）、砍掉所有已知有問題的功能
2. **HKDF key schedule 是核心**：Early Secret → Handshake Secret → Master Secret，每一步都 bind transcript hash，改動任何訊息都會導致 key 不同
3. **0-RTT 有 replay 風險**：TLS 1.3 spec 明確不保證 0-RTT 的 anti-replay——server 必須自己處理
4. **TLS 1.3 砍 RSA key transport 是最重大的安全改進**：強制 forward secrecy，讓「錄流量、未來破解」的攻擊模型失效
5. **只有 5 個 cipher suite**：比 TLS 1.2 的 300+ 個少了兩個數量級，大幅縮小攻擊面
