# Ch 34 — TLS 1.3 握手

> 目標：把 TLS 1.3（RFC 8446）拆透。1-RTT 與 0-RTT 流程、HKDF schedule（早期 secret → 握手 secret → master secret）、為什麼 TLS 1.3 砍掉 RSA key transport / static DH / 大半 cipher suite，TLS 1.2 留下的歷史包袱。

## TLS 1.3 簡史

```
1995  SSL 2.0 (Netscape)，幾月被破
1996  SSL 3.0
1999  TLS 1.0 (RFC 2246)，幾乎等於 SSL 3.0
2006  TLS 1.1
2008  TLS 1.2 — 流行近 10 年
2014  Heartbleed shock，社群開始重新設計
2014  IETF tls-13 working group
2018  TLS 1.3 RFC 8446（4 年 28 個 draft）
```

TLS 1.3 是**從零重新設計**，不是 1.2 的小升級。**砍掉所有不安全 / 過時 cipher 與 mode**，新加 modern feature。

## TLS 1.2 的問題

```
TLS 1.2 cipher suites 像菜單，幾百種：
  TLS_RSA_WITH_AES_128_CBC_SHA
  TLS_DHE_RSA_WITH_AES_256_CBC_SHA256
  TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
  ...
  
每個 suite 包：key exchange + cert sig + cipher + MAC

問題：
  - 太多 → 配置複雜，admin 經常選錯
  - 含 RSA key exchange（沒 forward secrecy）
  - 含 CBC-MAC mode（padding oracle 風險）
  - 含 export-grade weak cipher（Logjam、FREAK）
  - 含 SHA-1 簽章
```

實戰被各種 downgrade attack（FREAK、Logjam、POODLE、ROBOT、CRIME、BREACH）。

## TLS 1.3 的決定

```
砍掉：
  - RSA key exchange（必 ECDHE / DHE）
  - Static DH / static ECDH（必 ephemeral）
  - CBC + HMAC（必 AEAD）
  - SHA-1 簽章
  - DSA、export-grade、anonymous、weak primes
  - 壓縮（CRIME 攻擊）

新增 / 改善：
  - 1-RTT handshake（vs 1.2 的 2-RTT）
  - 0-RTT resumption
  - HKDF-based key schedule（清晰）
  - 早期 encrypted Server Hello
  - 砍 cipher suite 到 5 個
```

## TLS 1.3 cipher suites（總共 5 個）

```
TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256
TLS_AES_128_CCM_8_SHA256
```

實務 99% 用前三個。**極簡化**。

## 1-RTT 完整 handshake

```
Client                                  Server

ClientHello
  + supported_versions: [TLS 1.3]
  + key_share: x25519_pubkey
  + signature_algorithms: [...]
  + supported_groups: [...]
                              ─────────►
                                    ServerHello
                                      + key_share: x25519_pubkey
                                      + selected cipher suite
                                {ServerCertificate}        ← {} 表加密
                                {CertificateVerify}        ← server 簽 transcript
                                {Finished}                 ← MAC of transcript
                              ◄─────────
{Certificate} (optional client cert)
{CertificateVerify} (optional)
{Finished}
                              ─────────►
                                    [Application Data]
                                    [Application Data]
                              ◄ ────────►
```

關鍵 message：

- **ClientHello**：含 client 的 ECDHE pubkey share
- **ServerHello**：含 server 的 ECDHE pubkey share（雙方算 shared）
- **EncryptedExtensions**：server 的其他配置（從這個 message 起一切加密）
- **Certificate**：server cert chain
- **CertificateVerify**：server 用 cert 私鑰簽迄今所有 message 的 transcript
- **Finished**：HMAC over transcript（驗證雙方 transcript 一致）

## Handshake key derivation：HKDF schedule

```
                       PSK or 0
                          │
                          ▼
                       HKDF-Extract
                          │
                          ▼
                    Early Secret
                          │
                          ▼
            HKDF-Expand-Label("derived")
                          │
                          ▼
                    DH secret ──────► HKDF-Extract
                                          │
                                          ▼
                                  Handshake Secret
                                          │
                                          ▼
                          HKDF-Expand-Label
                                  │      ↓
                  ┌───────────────┴──────────────┐
                  ▼                               ▼
           client_handshake_secret      server_handshake_secret
                  │                               │
                  ▼                               ▼
            HKDF-Expand-Label             HKDF-Expand-Label
              (client write key)           (server write key)
              (client write IV)            (server write IV)
                                          ...
                  
    Then: Master Secret derived from Handshake Secret + 0
          → application traffic keys
```

**整個 schedule 很複雜但有結構**：每階段 HKDF-Extract / Expand label，從一個 secret 衍生多個 sub-key。

`HKDF-Expand-Label(secret, label, context, length)`：

```
HKDF-Expand-Label = HKDF-Expand(secret, "tls13 " || label || context || length, length)
```

context 通常是 transcript hash（綁定 handshake state）。

## CertificateVerify

server 簽迄今 transcript：

```
sig_input = "TLS 1.3, server CertificateVerify" || \
            transcript_hash(ClientHello || ServerHello || EncryptedExtensions || Certificate)

signature = sign(server_cert_priv_key, sig_input)
```

client 用 server cert 公鑰驗。**這把 ECDHE 與 cert 綁起來** — MITM 不能改 ECDHE share（會讓簽章無效）。

## Finished

```
finished_key = HKDF-Expand-Label(handshake_secret, "finished")
finished_data = HMAC(finished_key, transcript_hash)
```

兩端各自算，confirm transcript 一致。**最後一道防線**抗未發現的 transcript 攻擊。

## 0-RTT (Early Data)

如果之前連過 → server 給 PSK ticket。下次連可直接：

```
Client                                  Server

ClientHello + early_data + 
  encrypted_application_data
                              ─────────►   (server 立刻可解密 early data)
                                    ServerHello + Finished
                              ◄─────────
{Finished}
                              ─────────►
```

**1 round trip** 就有 application data → 0-RTT。

代價：**no forward secrecy for early data**（用 PSK 加密，PSK 洩漏 → 過去 0-RTT 全洩漏）。**also vulnerable to replay attack**（attacker 重發 0-RTT data）。

實務 0-RTT 只用於 idempotent / safe operation（如 GET request）。寫 / POST 不該 0-RTT。

## Session resumption

兩種：

1. **Session ID**（TLS 1.2 的）：被 1.3 砍
2. **PSK ticket** (Pre-Shared Key)：server 發 ticket（含 encrypted state），client 下次帶 ticket
3. **PSK with key exchange (PSK-DHE)**：仍做 ECDHE 為了 forward secrecy

TLS 1.3 預設用 PSK-DHE。

## TLS 1.3 與 PQC

TLS 1.3 設計時 PQC 還在標準化。現在採用 hybrid key exchange：

```
key_share group: X25519MLKEM768 (CFRG draft, 2024)
  client send X25519_pub || ML-KEM_pub
  server send X25519_pub || ML-KEM_ciphertext
  shared = HKDF(X25519_secret || ML-KEM_secret)
```

Chrome 2024 起預設啟用（對 Cloudflare、Google 等 server）。**production-scale PQC TLS** 已在跑。

## TLS 1.3 wire-level：record layer

```
TLSPlaintext:
  type: handshake / application_data / alert / ...
  legacy_record_version: 0x0303 (compatibility lie)
  length: ...
  fragment: payload

TLSCiphertext:
  opaque_type: 0x17 (always application_data after handshake)
  legacy_record_version: 0x0303
  length: AEAD output length
  encrypted_record: AEAD(... key, nonce_xor_seq, payload || type, additional_data)
```

注意 `opaque_type` 對外都是 0x17（**訊息類型藏在加密內容**），traffic analysis 只看到「TLS application data」。

## 用 OpenSSL 看 TLS 1.3 handshake

```bash
# Server
openssl s_server -cert server.crt -key server.key -tls1_3 -port 4443

# Client
openssl s_client -connect localhost:4443 -tls1_3 -keylogfile keylog.txt

# 用 keylog 在 Wireshark 解密
# Wireshark → preferences → TLS → (Pre)-Master-Secret log filename
```

這個 workflow 對 debug TLS 必備。

## 一個常見誤解

「TLS 1.3 比 TLS 1.2 慢，因為加密強」

**反過來**。TLS 1.3 比 TLS 1.2 **快**：

- 1-RTT vs 1.2 的 2-RTT（少一次 round trip）
- AEAD 比 CBC+HMAC 快
- 0-RTT resumption（1.2 沒有）
- ECDHE 預設（key exchange 比 RSA key transport 快）

**安全 + 快 + 簡單**。TLS 1.3 是工程典範。
