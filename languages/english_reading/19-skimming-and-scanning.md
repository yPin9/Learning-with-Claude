# Ch 19 — 略讀與掃讀：以及它們誠實的極限

> **目標**：講清楚 skimming（略讀，抓大意）與 scanning（掃讀，找特定資訊）到底是什麼、何時該用、怎麼做。同時講一個很多「速讀課」不敢講的**誠實真相：你略讀不了你根本讀不動的東西**——略讀是流暢讀者的工具，不是逃避地基的捷徑。我們會示範讀技術文件的策略性讀法（man page 幾乎沒人從頭讀到尾，怎麼定位需要的段落），並區分「為資訊而讀」與「為學習/樂趣而讀」——這兩者該用完全不同的速度與方法。

---

## 為什麼需要這個？

前面兩章（Ch 17/18）我們示範了精讀：一段四句話的段落，認真走完要 15–20 分鐘。**如果每篇東西都這樣讀，你一天讀不了幾頁，而且你也不需要。** 你讀一份 API 文件，多半只想找「那個函式的參數怎麼傳」；你掃一篇技術部落格，多半只想知道「這篇值不值得我花時間細讀」。這些場景，精讀是浪費——你需要的是**快速定位**或**快速判斷**。

但「快速讀」這件事被市面上的速讀課講壞了。他們賣你「一分鐘讀一千字、理解率不變」的幻覺。**這是假的，且對你這個階段的讀者特別有害。** 因為略讀的前提是「你本來就讀得動這段文字」——略讀是在你已具備流暢閱讀能力之上，**選擇性地跳過**你有把握的部分。如果一段文字你逐字讀都讀不懂，你「略讀」它只是自我安慰，什麼也沒抓到。

這一章要做兩件事：一是誠實地教你 skimming 和 scanning 怎麼用、什麼時候用；二是把**它們的極限**講白——讓你不會把「該補地基」誤當成「該學速讀」。搞混這兩者，你會在錯的方向上白費力氣。

## 先建立直覺

三種讀法，目的完全不同，別混為一談：

```
精讀（intensive / close reading）
  目的：完全讀懂 + 吸收語言/知識
  速度：慢（每字都處理）
  場景：學習材料、關鍵條款、想榨乾的好文章
  → Ch 13/17/18 教的

略讀（skimming）
  目的：抓「整篇大意 / 值不值得細讀」
  速度：快（大量跳過，只看骨幹）
  場景：判斷一篇文章要不要細讀、快速掌握全貌
  → 本章上半

掃讀（scanning）
  目的：找「某個特定資訊」（一個數字、一個函式名、一個日期）
  速度：極快（眼睛掃過大片文字，只等某個目標跳出來）
  場景：查 API 參數、在長文件裡找那一段、查表
  → 本章下半
```

**最關鍵的直覺：略讀和掃讀都不是「讀得更快的精讀」，而是「讀得更少」。** 你不是用更快的速度處理每一個字——你是**大量地不處理**大部分字，只讓眼睛停在少數關鍵位置。速度來自「跳過」，不是來自「加速」。想通這點，你就不會落入「訓練眼球一分鐘掃一千字」的假速讀陷阱。

## Skimming（略讀）：抓大意、判斷值不值得細讀

略讀是**選擇性地只讀「承載最多資訊的位置」**，跳過其餘。承載最多資訊的位置在哪？各種文體有固定套路：

### 略讀新聞

- **標題 + 第一段**：倒金字塔結構（Ch 17）把 5W 全塞在開頭，讀完標題和第一段，大意八成到手。
- **每段第一句**：新聞（和多數說明文）的段落多半「第一句是主題句」，往後是展開。略讀時只讀每段第一句，串起來就是全文骨架。

### 略讀技術文章／部落格

- **標題、小標（headings）**：先讀所有 heading，拼出文章結構地圖——這篇講幾個點、按什麼順序。
- **程式碼區塊、圖表**：技術文的關鍵常在 code 和圖，略讀時眼睛先落在這些。
- **第一段 + 結論段**：作者常在開頭講「這篇要解決什麼」、結論講「所以呢」。
- **粗體字、列表**：作者已經替你標了重點。

### 略讀的正確用途：判斷「要不要精讀」

**略讀最有價值的用途，是當「篩選器」。** 你面前有十篇文章，沒時間全部細讀——略讀每篇兩分鐘，判斷哪一兩篇值得走完精讀 SOP。這是**閱讀的資源分配**：把昂貴的精讀留給值得的材料，其餘用略讀處理掉。Ch 17/18 說「精讀昂貴、要挑值得的」，挑的動作就是靠略讀完成的。

### 略讀怎麼做（步驟）

```
1. 讀標題和所有小標 → 建立結構地圖（這篇講什麼、分幾塊）
2. 讀第一段 + 最後一段 → 抓「問題」與「結論」
3. 掃每段第一句 → 補上中段的論證骨架
4. 眼睛掃過粗體、列表、圖表 code → 撿作者標好的重點
5. 停：問自己「大意抓到了嗎？這篇值得精讀嗎？」
```

全程可能只花兩三分鐘，你就有了「大意 + 是否值得細讀」的判斷。**注意：略讀的產出是「模糊的全貌」，不是「精確的細節」。** 想要細節，就得回頭精讀——別指望略讀給你精確理解，那不是它的工作。

## Scanning（掃讀）：找一個特定資訊

掃讀和略讀不同：略讀要「大意」，掃讀要「一個明確的目標」。你**已經知道要找什麼**（一個函式名、一個錯誤碼、一個日期、一個參數），只是要在大片文字裡定位它。

掃讀時，你的眼睛不是在「讀」，而是在**等某個特定樣式跳出來**——像 Ctrl+F 的人肉版。你腦中鎖定目標的「形狀」（一個大寫的常數名、一個數字、一個特定單字），眼睛快速掃過文字，直到那個形狀出現才停。

### 掃讀怎麼做（步驟）

```
1. 明確定義目標：我到底要找什麼？（一個字？一個數字？一段特定主題？）
2. 用文件結構縮小範圍：目錄、小標、索引 → 先跳到最可能的區塊
3. 用「真的 Ctrl+F」：電子文件別用眼睛掃，直接搜關鍵字（見下）
4. 眼睛掃過候選區塊，鎖定目標的「形狀」，讓它跳出來
5. 找到後，回到「精讀模式」細讀那一小段——因為你要的正是這段的精確意思
```

**第 5 步是關鍵、也是最多人漏掉的**：掃讀的目的是**定位**，一旦定位到你要的段落，就切回精讀——因為你查 API 參數、查錯誤碼，要的正是那句的精確意思，錯不得。**掃讀是快速抵達，不是快速理解。** 抵達之後，該慢還是要慢。

## 讀技術文件的策略性讀法：以 man page 為例

技術文件是 scanning + 局部精讀的主場。**幾乎沒有人從頭到尾讀 man page**——man page 是設計來「查」的，不是「讀」的。它有固定的章節結構，你要學會**直接跳到你需要的那一節**：

```
NAME          → 一句話，這是什麼（略讀時看這行就夠）
SYNOPSIS      → 函式簽名 / 命令用法（查參數順序、型別，最常掃這裡）
DESCRIPTION   → 詳細行為（要理解語意時精讀這段）
RETURN VALUE  → 回傳什麼（Ch 18 精讀過，查回傳值跳這）
ERRORS        → errno 有哪些、各代表什麼（除錯時掃這裡找你的錯誤碼）
EXAMPLES      → 範例（想快速上手，很多人直接跳這）
SEE ALSO      → 相關頁面（追線索用）
```

**實戰讀法**：
- 想知道「這函式參數怎麼傳」→ 直接跳 SYNOPSIS，掃出簽名，可能整頁其他都不看。
- 遇到某個 errno → 直接跳 ERRORS，掃你的錯誤碼，精讀那一條。
- 不確定某個行為（例如 Ch 18 的「讀到的比要求的少算不算錯」）→ 跳 RETURN VALUE 或 DESCRIPTION，精讀相關段。
- 完全沒用過這函式，想上手 → 讀 NAME + SYNOPSIS + EXAMPLES，DESCRIPTION 略讀。

**同一份文件，不同目的用完全不同的讀法和速度。** 這是技術文件閱讀的核心技能：不是「把 man page 讀完」，而是「知道要跳到哪、跳到後用什麼精度讀」。API 文件、RFC、官方文件都是同一套邏輯——先用結構（目錄/小標/索引）定位，再局部精讀。

### 用工具，別用眼球硬掃

電子文件掃讀，**第一步永遠是 Ctrl+F（或 `/` 在 man/less 裡搜尋）**，不是用眼睛掃。人肉掃讀又慢又易漏，工具搜尋秒定位。真正需要眼睛掃讀的場合，是「目標形狀模糊、無法用單一關鍵字搜」時（例如「找那段講效能的部分」——你不知道確切用詞，只好掃小標和段落）。**能用工具就用工具，眼球掃讀是退而求其次。**

## 誠實的極限：你略讀不了你讀不動的東西

現在講這章最重要、也最反市場話術的一點。

**略讀和掃讀，都建立在「你本來就讀得動這段文字」的前提上。** 略讀是你「選擇性跳過有把握的部分」；掃讀是你「快速滑過已能秒懂的文字，等目標跳出」。**兩者都要求：你滑過去的那些字，你是有能力讀懂的，只是選擇不細讀。**

如果一段文字，你**逐字慢讀都讀不懂**（生字太多、句構拆不開），那麼「略讀」它是什麼結果？——你的眼睛滑過去，什麼也沒抓到。你不是「快速抓到大意」，你是「快速地什麼都沒讀懂」，然後騙自己「我略讀過了」。**這是自我安慰，不是閱讀。**

這直接呼應 Ch 1 的**覆蓋率門檻**：一段文字你認識的字若低於某個比例（研究上抓大意約需 95%、獨立流暢閱讀約需 98%），你連逐字讀都撐不住，遑論略讀。**略讀不能替你跨過覆蓋率門檻——它是門檻之上的工具，不是繞過門檻的捷徑。**

所以，市面速讀課賣的「快速讀完任何東西」是危險的誤導，尤其對正在打地基的你：

- 如果你**讀得動**這段：略讀能幫你省時間、掃讀能幫你定位。這時它們是真本事。
- 如果你**讀不動**這段：你需要的是**回去補地基**（詞彙覆蓋率 Ch 1-6、拆句能力 Ch 7-10），不是學速讀。速讀救不了讀不動。

**判斷標準很簡單**：拿一段你想「略讀」的文字，**先逐字慢讀一遍**。如果慢讀能懂，那略讀對你就是有效工具；如果慢讀都不懂，別略讀它——那是精讀（或補地基）的材料，不是略讀的材料。**略讀不是能力的替代品，是能力的延伸。**

## 為資訊而讀 vs 為學習/樂趣而讀

同一個「讀」字，兩種目的，該用**完全不同**的方法與速度。這是很多人沒想清楚、結果用錯讀法的地方。

### 為資訊而讀（reading for information）

你要的是**答案/資料**，讀完就丟。查 API 參數、找錯誤碼、看新聞知道發生什麼、查一個事實。

- **方法**：scanning 為主，找到目標 + 局部精讀，其餘全跳。
- **速度**：快，目標導向。
- **成功標準**：拿到那個資訊。文章其餘部分讀不讀無所謂。
- **不做**：不查生字（除非擋住目標）、不做 Anki、不精讀無關段落。**在這個模式下花時間精讀、做卡是浪費——你不是要學這篇，你是要它的資訊。**

### 為學習/樂趣而讀（reading to learn / for pleasure）

你要的是**把材料變成自己的一部分**——語言吸收、知識內化，或純粹享受。這才是你這門課的終極目標（README 講的「輕鬆讀懂 BBC 與技術原文」）。

- **方法**：精讀（Ch 13/17/18 的 SOP），或大量的「舒服的延伸閱讀」（extensive reading，讀略低於你程度、幾乎不查字的材料，靠量累積）。
- **速度**：精讀慢求吸收；延伸閱讀順順讀求流暢與量。
- **成功標準**：語言/知識留在你腦中，或你讀得開心讀得多。
- **做**：精讀時查高頻字、做 Anki、拆難句；延伸閱讀時放輕鬆、少查字、享受「讀懂」的感覺。

**關鍵取捨**：用錯模式會兩頭空。**為資訊而讀卻拿去精讀** → 慢死、效率低，你只是要個參數卻走完五遍 SOP。**為學習而讀卻用略讀滑過去** → 什麼也沒吸收，還誤以為「我讀了很多」。**讀之前先問自己：我這次是要「資訊」還是要「學習/樂趣」？** 答案決定你該快還是該慢、該不該查字做卡。

## 對比與取捨

| 讀法 | 目的 | 速度 | 處理多少字 | 何時用 | 對你這階段 |
|---|---|---|---|---|---|
| 精讀 | 完全懂 + 吸收 | 慢 | 每個字 | 學習材料、關鍵條款 | **主力**，練能力靠這個 |
| 略讀 | 抓大意 / 篩選 | 快 | 骨幹（標題、首句、粗體） | 判斷值不值得細讀 | 讀得動的材料才有效 |
| 掃讀 | 找特定資訊 | 極快 | 極少（只找目標） | 查文件、查資料 | 隨時可用（配 Ctrl+F） |
| 延伸閱讀 | 累積流暢度 | 中 | 順讀不細究 | 大量讀略低於程度的材料 | **地基期的長期投資** |

**給你這個階段（TOEIC ~480，正在打地基）的直接建議**：你現在的主力應該是**精讀（練能力）+ 延伸閱讀（累積量）**。略讀和掃讀是**工具技能**——該會，但別當成主力，更別拿它當「跳過補地基」的藉口。等你的覆蓋率和拆句能力上來、能「讀得動」大部分材料了，略讀和掃讀才會真正發揮省時間的威力。**現階段，慢讀讀懂，比快讀讀不懂有價值一百倍。**

## 踩雷集錦

**雷 1：把略讀當成「跳過補地基的捷徑」。** 這是最危險的錯。你讀不動的東西略讀不了——略讀是流暢讀者選擇性跳過有把握的部分，不是讀不懂時滑過去自我安慰。**讀不動就回去補覆蓋率和拆句（Ch 1-10），別學速讀。**

**雷 2：相信「一分鐘一千字、理解不變」的速讀話術。** 快是靠「讀得更少（跳過）」，不是「處理每個字更快」。理解率和資訊量是有取捨的——略讀給你模糊全貌，要精確細節就得慢下來。**沒有免費的午餐。**

**雷 3：掃讀找到目標後不切回精讀。** 掃讀的產出是「定位」，不是「理解」。你查到 API 參數那一段，那一段要精讀——你要的正是它的精確意思，掃過去不細看等於白查。**掃讀快速抵達，抵達後該慢還是慢。**

**雷 4：用錯「讀的目的」模式。** 為查個參數卻走完精讀 SOP（浪費），或為學習卻略讀滑過（沒吸收）。**讀之前先定目的：要資訊還是要學習？** 目的決定速度和方法。

**雷 5：電子文件用眼球硬掃，不用 Ctrl+F。** 人肉掃讀又慢又漏。能用工具搜關鍵字就用工具，眼球掃讀是「目標形狀模糊、無法用單一關鍵字搜」時才退而求其次。

**雷 6：略讀完就以為「讀懂了」。** 略讀的產出是「大意 + 是否值得細讀」，不是精確理解。拿略讀的模糊印象去做需要精確的事（寫程式、做決策、答考題），會出錯。**要精確，回頭精讀。**

## 進階：再往深一層——略讀能力其實是精讀練出來的副產品

一個反直覺但重要的事實：**你越會精讀，你就越會略讀——而不是反過來。**

為什麼？因為略讀的本質是「快速判斷哪些部分可以跳過」。而「判斷哪些可跳過」需要你**對文體結構有深刻的直覺**：知道新聞的重點在開頭、知道段落主題句在第一句、知道技術文的規範句和說明句差在哪、知道 man page 哪節放什麼。這些直覺**全部來自大量精讀的累積**——你精讀夠多篇新聞，才會「一眼看出」哪段是背景可跳、哪段是核心要讀。

所以**略讀不是一種「另外學」的技巧，是精讀能力成熟後自然長出的副產品**。這也是為什麼速讀課教「眼球運動訓練」多半沒用——真正讓你能略讀的，不是眼球移動速度，是你對「文字如何組織」的內化直覺。**你這階段該做的，是老老實實精讀（Ch 17/18）、大量閱讀，略讀的能力會隨之而來，不必特地訓練。**

再深一層：**掃讀（找特定資訊）能力也和你的「結構知識」綁定。** 你之所以能在 man page 裡秒跳到 ERRORS、在 RFC 裡秒找到規範章節，是因為你懂這些文件的固定結構。**越熟一種文件的結構，你在裡面掃讀就越快。** 所以「讀技術文件的能力」，很大一部分是「熟悉技術文件的結構慣例」——這也是靠讀多了累積的。工具（Ctrl+F）幫你在區塊內定位，結構知識幫你選對區塊，兩者合起來才是高效的技術文件讀者。

## 動手練習

1. **略讀篩選**：去一個技術新聞站（如 Hacker News）或 BBC，用「略讀步驟」花兩分鐘略讀五篇文章，各寫一句大意，並決定哪一篇值得你精讀。然後真的精讀那一篇。
2. **掃讀 man page**：挑一個你沒用過的系統呼叫（例如 `man 2 openat`），設三個「找特定資訊」的任務（例如：第三個參數是什麼型別？失敗回傳什麼？哪個 errno 表示權限不足？），用 scanning + 局部精讀完成，記錄各花幾秒。
3. **驗證「讀不動就略讀不了」**：找一段你覺得很難的英文（例如一段學術論文摘要），先「略讀」寫下你以為的大意，再「逐字精讀」寫下真正的大意，對比兩者差多少。感受略讀在讀不動的材料上有多不可靠。
4. **分辨讀的目的**：列出你日常會讀的五種英文材料（API 文件、BBC 新聞、技術部落格、GitHub README、規格書），各標「為資訊而讀」還是「為學習而讀」，並寫下各該用哪種讀法和速度。
5. **Ctrl+F 練習**：拿一份長 RFC 或官方文件，設一個「找某個關鍵詞」的任務，比較「用 Ctrl+F」和「用眼睛掃」各花多久、哪個會漏。體會工具的威力。

## 本章重點整理

- **三種讀法目的不同**：精讀（完全懂+吸收，慢）、略讀（抓大意/篩選，快）、掃讀（找特定資訊，極快）。別混為一談。
- **快來自「讀得更少（跳過）」，不是「處理每字更快」**。速讀課的「一分鐘一千字理解不變」是話術。
- **略讀的最佳用途是當篩選器**：判斷一篇值不值得精讀，把昂貴的精讀留給值得的材料。
- **掃讀是快速定位，不是快速理解**：找到目標後要切回精讀，因為你要的正是那段的精確意思。電子文件先用 Ctrl+F。
- **誠實的極限：你略讀不了你讀不動的東西**。略讀是覆蓋率門檻（Ch 1）之上的工具，不是繞過補地基的捷徑。讀不動就回去補詞彙和拆句。
- **技術文件是「跳到需要的節 + 局部精讀」**：man page/RFC/API 文件都靠結構定位，同一份文件不同目的用不同讀法。
- **為資訊而讀 vs 為學習而讀，用完全不同的方法**：前者 scanning 快取答案、不做卡；後者精讀慢吸收或延伸閱讀累積量。讀前先定目的。
- **略讀/掃讀能力是精讀+結構熟悉度的副產品**，不必特地訓練眼球——老實精讀、大量閱讀，它自然長出來。
