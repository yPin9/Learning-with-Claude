# 練習 D — 完整精讀報告

> **目標**：把 Ch 13 的精讀 SOP、Ch 17（新聞示範）、Ch 18（技術示範）學到的整套流程，**用你自己選的真實文章，從頭到尾獨立跑一遍**，各產出一份完整的精讀報告。這是 Part 5 從「看示範」變成「會做」的關鍵一步——**看再多示範都不會讓你變強，親手精讀一篇真文章、寫出報告才會。** 你要自選 1 篇 BBC 新聞 + 1 篇技術文，各自套精讀 SOP，交出兩份含「大意、難句拆解、生字表 + Anki 卡、心得」的報告。

---

## 背景

Ch 17 和 Ch 18 我們用**自造的代表性段落**示範了精讀——那是為了教學方便、涵蓋最多手法。但你的真本事不會從看示範長出來，只會從**在真實、不受控、你沒讀過的文章上獨立操作**長出來。真實文章不會乖乖把每種手法塞在一段裡；它會有無關的段落、意料外的句構、你沒學過的字——這才是你將來面對的現場。

這份練習就是把你推上現場。規則很硬但很重要：**文章必須是你自己找的真文章、你事先沒讀過。** 你不能用 Ch 17/18 的示範段落交差——那已經被拆解過，等於抄答案。你要的是「拿到陌生文章、獨立跑完流程」的經驗，因為那正是你讀 BBC 和技術原文的真實情境。

閱讀是肌肉不是知識（README 講過）。前面所有章節是在你腦中安裝流程，這份練習是第一次讓那套流程**在無人示範、無標準答案的真實材料上**跑起來。做完這份，你就從「知道精讀怎麼做」跨到「能對任何文章做精讀」。

## 任務規格

### 選材要求

**文章一：BBC 新聞**
- 來源：bbc.com/news（或 BBC 其他英文頻道）。
- 長度：**至少 4 段**（不要挑只有兩三句的短訊）。挑一篇你**對主題有點興趣、但事先沒讀過**的。
- 主題不限（政治、科技、環境、文化都行），但避免純數據型（如比分、天氣），那種沒什麼句構可拆。

**文章二：技術文**
- 來源擇一：某個系統呼叫或函式的 man page（man7.org）、一段 RFC（rfc-editor.org）、某官方文件（如語言/框架的 official docs）、或一篇有實質技術內容的工程部落格。
- 長度：**至少 3 段實質內容**（man page 可取 DESCRIPTION + RETURN VALUE + 一段 ERRORS/NOTES；RFC 取含 MUST/SHOULD/MAY 的一節）。
- 挑一個**你領域內、但這篇/這節你沒細讀過**的，讓你能觀察「領域知識在哪幫你、哪幫不上」（Ch 18 的重點）。

### 每篇要產出的四個部分

對**每一篇**，完整走精讀 SOP 並寫成報告，含以下四塊：

1. **大意（第 1 遍產出）**：先只花 1–2 分鐘抓大意，寫下**一段話**（3–5 句）的中文總結。這一塊要**在動手拆句、查字之前**寫，記錄你「第一遍」的理解。

2. **難句拆解（第 2 遍產出）**：從文章中挑**至少 3 個你卡住或覺得結構複雜的句子**，每句做：
   - 抄原句（標出處，如「第 2 段第 1 句」）。
   - 寫**主幹**（Ch 7）。
   - 畫 **ASCII 拆解樹**（Ch 8/9/10 的技巧，掛對層次）。
   - 標**結構類型**（被動 / 關係子句 / 分詞構句 / 名詞化 / attribution / 條件句 / RFC 規範動詞…）。
   - 寫**中文大意**。

3. **生字表 + Anki 卡（第 3 遍產出）**：
   - 列一張**生字表**（至少 5 個），每字標：意思、以及你的**分流決定**（查 / 猜 / 放過）+ 一句理由（用 Ch 1 覆蓋率、Ch 4 高頻的邏輯）。
   - 從中挑**至少 3 個值得做 Anki 的高頻字**，寫成**克漏字（cloze）卡**（Ch 5 的做法：例句挖空 + 背面答案，例句優先用文章原句）。

4. **心得（第 4、5 遍後產出）**：一段話，回答：
   - 這篇用了哪些**文體手法**？（新聞：attribution 態度、被動迴避施事者、headlinese；技術：MUST/SHOULD/MAY、名詞化、被嚴格定義的術語、規範 vs 說明句）
   - 這篇**哪裡卡最久**？為什麼？（是生字、是句構、還是純敘事段落靠不了領域知識？）
   - 對技術文那篇，特別寫：**領域知識在哪幫了你、哪幫不上？**

## 期望輸出範例

下面是**技術文那份報告的一小段示範**（只示範顆粒度，你自己的報告要對你選的真文章做完整四塊）。這裡用一句 RFC 風句子當樣本，讓你看到「合格報告」長什麼樣。

**（節錄自「難句拆解」塊的一句）**

> **原句（假想 RFC，第 2 段第 2 句）**：`If the declared length exceeds the maximum permitted value, the implementation MUST reject the message and SHOULD log the event.`
>
> **主幹**：`the implementation MUST reject [...] and SHOULD log [...]`（實作必須拒絕、應該記錄）
>
> **ASCII 拆解樹**：
> ```
> If the declared length exceeds the maximum permitted value,     ← 條件副詞子句（觸發條件）
> the implementation ── MUST reject the message
>                    └─ and SHOULD log the event                  ← 兩個並列述語，注意規範等級不同
> ```
>
> **結構類型**：條件句（If）、RFC 規範動詞（MUST / SHOULD，兩個不同等級並列）、過去分詞後置修飾（declared length）。
>
> **中文大意**：若宣告的長度超過允許上限，實作**必須**拒絕該訊息，並**應該**記錄此事件。（MUST=硬性要求，SHOULD=強烈建議，兩者刻意分級。）

看到顆粒度了嗎——原句標出處、主幹拎乾淨、樹掛對層、結構標籤齊、大意通順且點出 MUST/SHOULD 的分級。你的兩份報告，每個難句都照這個標準做。

## 如果你卡住了

**卡點 1：「我不知道該挑哪些句子拆。」**
挑「第一遍讀不順、需要回頭再讀一次才懂」的句子——那些就是值得拆的。長句、有多層子句的、被動的、名詞化長主詞的優先。如果整篇都很順（恭喜，但也可能是你選太簡單了），挑最長的 3 句拆。

**卡點 2：「生字太多，不知道哪些該查、哪些該做卡。」**
回 Ch 1 的覆蓋率邏輯 + Ch 18 的分流表。三個問題：(a) 這字擋不擋住大意？擋 → 查。(b) 能不能靠字根/上下文猜到夠用？能 → 猜了往前。(c) 是不是跨領域高頻、以後常見？是 → 做 Anki。**別全查全做卡**——真正進 Anki 的通常只有 3–5 個。

**卡點 3：「技術文那篇我一眼就懂，好像沒東西可拆。」**
這正是 Ch 18 的重點——你的領域知識在「說明句」上幫你飛。這時去找**純敘事的句子**（講動機、歷史、限制、因果的那些，例如 "has been the root cause of..."），那些領域知識幫不上、必須靠語言硬讀，拆那些。找不到純敘事句，就拆名詞化最重的句子。

**卡點 4：「我第一遍抓的大意，和精讀後發現的差很多，是不是我很爛？」**
不是，這正是精讀有價值的證據——**第一遍模糊、精讀後精確，落差就是你這次的收穫**。把落差寫進心得（「我第一遍以為 X，精讀後發現其實是 Y，因為漏讀了 attribution / 看反了 MUST/SHOULD」），這種落差記錄比報告本身還珍貴。

**卡點 5：「新聞的 attribution 手法我看不太出來。」**
盯 attribution 動詞（said / insisted / denied / claimed / suggested / warned…）。問：記者用的是中性的 said，還是帶態度的 insisted/claimed？以及——這句是**事實**、**某方的說法**、還是**作者判斷**？（Ch 17 的核心）把每個「觀點」歸給它的來源。

## 實作步驟

1. **選材**（10 分鐘）：按選材要求，找 1 篇 BBC 新聞 + 1 篇技術文。確認長度夠、你沒讀過、對主題有點興趣。存下連結（報告要附出處）。
2. **第 1 遍抓大意**（各 1–2 分鐘）：**先寫大意塊**，再做任何拆句/查字。這一步務必先做、先寫下來——它是後面「落差記錄」的基準，事後補寫就失真了。
3. **第 2 遍逐句拆**（各 20–40 分鐘）：挑至少 3 句，逐句做主幹 + ASCII 樹 + 結構標籤 + 大意，寫進難句拆解塊。
4. **第 3 遍處理生字**（各 15 分鐘）：列生字表、做分流決定、挑 3+ 個做 Anki 克漏字卡，寫進生字塊。
5. **第 4、5 遍手法辨識 + 重讀**（各 10 分鐘）：辨文體手法、重讀全文驗證理解，寫心得塊（含「第一遍 vs 精讀後的落差」，技術文加寫「領域知識邊界」）。
6. **整理成兩份報告**：用下方模板排版，兩篇各一份。
7. **把 Anki 卡真的建進你的 deck**（練習 A 建的那副）——報告寫完不代表結束，卡片進 deck 開始複習才算把養分吃下去。

## 完整參考範例

<details>
<summary>展開：一份完整的「技術文」精讀報告範例（點開前先自己做完你自己的兩篇）</summary>

> **提醒**：這份範例用的是一段**自造的、貼近 RFC 風格的代表性段落**（同 Ch 18 的誠實聲明），示範一份合格報告的完整長相。你自己的報告要對**你選的真文章**做。別照抄——照抄練不出反射。

**用來示範的段落（RFC 風，假想協定欄位驗證）：**
```
A conforming implementation MUST validate the length field before
allocating the buffer. If the declared length exceeds the maximum
permitted value, the implementation MUST reject the message and
SHOULD log the event. Implementations MAY impose a stricter limit,
provided that the limit is documented. Failure to validate the
length field before allocation has been the root cause of numerous
memory-corruption vulnerabilities.
```

```
========================================
精讀報告：（示範用）某協定的長度欄位驗證規範
出處：（示範用自造段落，真練習請填真實 URL，如 rfc-editor.org/rfc/xxxx）
文體：☑ 技術文（RFC 風）
日期：2026-08-03
========================================

【一、大意】（第 1 遍，動手前寫）
這節在規範實作處理「長度欄位」的規則：配置緩衝區之前必須先驗證長度；
若宣告的長度超過上限，必須拒絕訊息並應記錄；實作可以自訂更嚴格的上限
但要有文件。最後點出：沒在配置前驗證長度，是很多記憶體損毀漏洞的根源。

【二、難句拆解】

── 難句 1 ──
原句（第 1 句）：A conforming implementation MUST validate the length
field before allocating the buffer.
主幹：A conforming implementation MUST validate the length field
ASCII 拆解樹：
  A conforming implementation ── MUST validate ── the length field
                                                    └─ before allocating the buffer   ← 時間條件（先驗證再配置）
結構類型：RFC 規範動詞（MUST，絕對要求）、名詞片語堆疊（conforming implementation）、
         before + 動名詞（時間順序，順序本身是規範的一部分）。
中文大意：符合規範的實作，必須在配置緩衝區之前驗證長度欄位。

── 難句 2 ──
原句（第 2 句）：If the declared length exceeds the maximum permitted
value, the implementation MUST reject the message and SHOULD log the event.
主幹：the implementation MUST reject [...] and SHOULD log [...]
ASCII 拆解樹：
  If the declared length exceeds the maximum permitted value,      ← 條件副詞子句
  the implementation ── MUST reject the message
                     └─ and SHOULD log the event                   ← 並列述語，規範等級不同！
結構類型：條件句（If）、RFC 規範動詞（MUST vs SHOULD 兩個等級並列）、
         過去分詞後置修飾（declared length / permitted value）。
中文大意：若宣告的長度超過允許上限，實作必須拒絕該訊息，並應記錄此事件。
         （MUST=硬性、SHOULD=強烈建議，作者刻意分級。）

── 難句 3 ──
原句（第 4 句）：Failure to validate the length field before allocation
has been the root cause of numerous memory-corruption vulnerabilities.
主幹：Failure ... has been the root cause of ... vulnerabilities
ASCII 拆解樹：
  [Failure to validate the length field before allocation]  ← 名詞化長主詞（把動作壓成名詞）
      └─ 還原成動作：「（實作）沒有在配置前驗證長度欄位」這件事
  ── has been ── the root cause of numerous memory-corruption vulnerabilities
                                    └─ memory-corruption（複合形容詞）修飾 vulnerabilities
結構類型：名詞化（Failure to... 當主詞）、現在完成式、名詞堆疊（memory-corruption vulnerabilities）。
         ★這是純敘事句——講因果/歷史，領域知識只給方向，細節靠語言。
中文大意：「沒有在配置前驗證長度欄位」一直是眾多記憶體損毀漏洞的根本原因。

【三、生字表 + Anki 卡】

生字表：
| 生字            | 意思              | 分流   | 理由 |
|-----------------|-------------------|--------|------|
| conforming      | 符合規範的        | 查     | RFC 高頻限定詞，該熟 |
| declared        | 宣告的（分詞）     | 猜/查  | declare 家族，上下文清楚，但值得確認「對方宣稱」的意涵 |
| exceeds         | 超過              | 該認得 | 高頻學術動詞（Ch 4），若不熟就做卡 |
| impose          | 施加、規定        | 做卡   | 跨領域高頻，技術/新聞都常見 |
| provided that   | 以……為條件        | 查     | 條件連接詞，不能略過，查一次記住 |
| numerous        | 眾多的            | 做卡   | 高頻形容詞，比 many 正式，敘事常見 |
| root cause      | 根本原因          | 做卡   | 技術/工程高頻片語，除錯常用 |

Anki 克漏字卡（例句用原句）：
卡 1｜正面：Implementations MAY ____ a stricter limit, provided that the limit is documented.
      背面：impose（v. 施加、規定）— 施加限制/規則
卡 2｜正面：Failure to validate ... has been the root cause of ____ memory-corruption vulnerabilities.
      背面：numerous（adj. 眾多的）— 比 many 正式
卡 3｜正面：... has been the ____ ____ of numerous vulnerabilities.（兩格）
      背面：root cause（n. 根本原因）— 工程除錯高頻片語

【四、心得】
- 文體手法：MUST/SHOULD/MAY 三個規範等級都出現了（且第 2 句刻意在同句並列 MUST 和
  SHOULD）；名詞化重（第 4 句 Failure to... 當主詞）；被嚴格界定的詞（conforming
  implementation）；前三句是規範句、最後一句是說明句（講漏洞根源）。
- 卡最久的地方：第 4 句。前三句我一眼就懂（規範描述是我熟的），但第 4 句的名詞化
  長主詞讓我頓了一下，得把它還原成「沒在配置前驗證」這個動作才讀順。
- 第一遍 vs 精讀後：第一遍我把 MUST 和 SHOULD 都當「要做」，精讀後才注意到第 2 句
  刻意分級——log 只是 SHOULD（不記不算違規），這是重要差別，第一遍漏了。
- 領域知識邊界：前三句（規範句）我的協定/資安知識幫我飛，幾乎是「認出」不是「讀出」；
  但第 4 句（純敘事講因果）領域知識只讓我「猜到大概在講危險」，真要讀懂「這是 root
  cause、是 numerous 漏洞」的精確宣稱，還是得靠逐字讀。印證 Ch 18 的邊界。
========================================
```

| 卡真的進 deck | Anki 卡已加入你的 deck 開始複習 | □ |

**評分口徑**：
- **10 項全達 = 優秀**：你已能對陌生真文章獨立跑完精讀 SOP，這門課的核心技能到手。
- **7–9 項達 = 及格**：主流程會了，補齊沒達的項（最常漏：大意沒在動手前寫、結構標籤不齊、卡沒進 deck）。
- **6 項以下 = 重做**：多半是「邊看示範邊做/挑太簡單的文章/大意事後補寫」。回頭老實重跑一篇，別將就。

---

## 延伸挑戰

1. **同一篇隔週重讀**：一週後，不看你的報告，重讀同一篇文章。這次順多了嗎？哪些當初的難句現在一眼就懂？把「進步」記下來——這是最有感的正回饋。
2. **加一篇更難的**：BBC 換成 op-ed（評論）或 long read（深度長文），技術文換成一整篇 RFC 的核心章節。難度上一階，感受精讀 SOP 在更硬的材料上還撐不撐得住。
3. **交換批改**：找一個也在學的朋友，交換彼此的報告互相挑錯（他拆的主幹對嗎？結構標籤齊嗎？）。批改別人的報告，會逼你把標準看得更清楚。
4. **累積一個月**：每週各一篇 BBC + 技術文，連做四週，把八份報告的生字卡全進 deck。月底回看第一週的報告，量出你的成長。

## 延伸閱讀

- **[BBC News](https://www.bbc.com/news)** — 新聞那篇的一手選材場。挑一篇你有點興趣、至少 4 段的真報導開刀。
- **[Linux man-pages（man7.org）](https://man7.org/linux/man-pages/)** 與 **[RFC Editor](https://www.rfc-editor.org/)** — 技術文那篇的一手選材場。man page 挑一個沒細讀過的系統呼叫；RFC 挑一節含 MUST/SHOULD/MAY 的規範。
- **[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)** — 若你技術文選了 RFC，隨手把這兩頁放旁邊當「規範動詞字典」。

這份練習做完，你已經證明自己能對真實的 BBC 新聞和技術原文獨立完成完整精讀——這正是這門課設定的核心能力。但精讀是「把單篇榨乾」的深度技能；要真正達到「輕鬆讀懂」的目標，你還需要把精讀（練能力）和大量閱讀（累積流暢度）組成一套**能長期跑下去的閱讀計畫**。這正是最終專案要幫你搭起來的東西。
