# Ch 1 — 一個封包的旅程

> **目標**：建立整門課的全局地圖。跟著「你在瀏覽器打開 example.com」這一個動作，走完背後 10 幾個步驟——DNS 解析、TCP 握手、TLS 協商、HTTP 請求、封包經過路由器和 NAT……每個步驟都對應後面的某一章。讀完你有一張「網路全貌圖」，知道每個後續章節在整體中的位置。

> **環境**：概念章為主，搭配可在本機跑的觀察命令（Ubuntu/Debian）。

## 為什麼從「一個封包的旅程」開始？

網路有太多層、太多協定、太多縮寫（TCP/IP/DNS/TLS/NAT/ARP…），一開始就分層教容易見樹不見林——你學了 TCP 握手卻不知道它什麼時候發生、學了 DNS 卻不知道它在整個流程的哪一步。

所以我們反過來：先看**一個完整的真實流程**——你打開一個網頁，從按 Enter 到畫面出現，背後發生的所有事。這條「主線」串起整門課的每個概念，給你一個掛鉤。之後每學一個協定，你都知道「啊，這是主線上的第 X 步」。這章不求深（細節後面章節會挖），求的是**全貌**和**順序**。

## 先建立直覺:一封信要經過多少手

```
寄一封實體信的類比（幫助理解網路分層）：

  你寫信給遠方朋友：
    1. 查朋友的地址（不知道地址寄不出去）      ← DNS
    2. 把信裝進信封、寫上收件/寄件地址          ← IP 封裝
    3. 信封裝進郵局的郵包、貼上路線標籤          ← TCP/連結層
    4. 信經過多個轉運站，每站決定下一站往哪      ← 路由
    5. 跨國時經過海關/轉換                       ← NAT
    6. 到達後拆郵包、拆信封、朋友讀信             ← 解封裝
        │
  關鍵：每一層只管自己的事
    寫信的人不管郵局怎麼運、郵局不管信的內容
    → 這就是「網路分層」（Ch 2）：每層獨立、各司其職
        │
  而你的資料在網路上，就是這樣被「層層包裝」
  再「層層拆開」的
```

關鍵心智：你的資料在網路上傳輸，像一封信被**層層包裝**（應用資料 → 加 TCP 標頭 → 加 IP 標頭 → 加乙太網標頭）再送出，到對方那層層拆開。每一層只管自己的職責（Ch 2 的分層模型）。一個封包的旅程，就是「打包 → 經過很多中繼站轉送 → 拆包」的過程。

## 完整旅程:從 URL 到網頁

我們把「在瀏覽器打開 `https://example.com`」拆成步驟，每步標出對應章節：

```
你打開 https://example.com 的完整流程：

  ┌─ 步驟 1：解析域名（DNS）────────────────── Ch 9
  │  "example.com" 是給人看的，電腦要 IP 位址
  │  → 問 DNS：example.com 的 IP 是多少？
  │  → 得到 93.184.216.34
  │
  ┌─ 步驟 2：找出「下一跳」往哪送（路由 + ARP）─ Ch 4/5/3
  │  我的電腦查路由表：93.184.216.34 不在本地網段
  │  → 送給「預設閘道」（你家的路由器）
  │  → 用 ARP 問出路由器的 MAC 位址（同網段靠 MAC）
  │
  ┌─ 步驟 3：建立 TCP 連線（三次握手）───────── Ch 6
  │  和 93.184.216.34 的 443 port 建立 TCP 連線
  │  → SYN → SYN-ACK → ACK（三次握手）
  │
  ┌─ 步驟 4：TLS 加密協商（HTTPS 的 S）───────── Ch 11
  │  在 TCP 之上建立加密通道
  │  → ClientHello → ServerHello → 憑證驗證 → 金鑰交換
  │  → 之後的資料都加密
  │
  ┌─ 步驟 5：發 HTTP 請求 ───────────────────── Ch 10
  │  GET / HTTP/1.1, Host: example.com
  │  → （加密後）送出去
  │
  ┌─ 步驟 6：封包穿越網路（路由 + NAT）──────── Ch 4/8
  │  封包經過你家路由器（NAT：私有 IP → 公網 IP）
  │  → 經過 ISP、骨幹網路、多個路由器，一跳跳到目標
  │
  ┌─ 步驟 7：伺服器回應 ─────────────────────── Ch 10
  │  伺服器處理請求，回 HTTP 200 + HTML
  │  → 沿原路（反向）回到你的電腦
  │
  └─ 步驟 8：瀏覽器渲染 ─────────────────────── （非本課）
     解析 HTML、載入 CSS/JS/圖片（每個又是一輪上述流程）
     → 畫面出現
```

> 這張圖是**整門課的骨架**。你會注意到一個動作（打開網頁）牽動了 DNS（Ch 9）、ARP（Ch 3）、IP/路由（Ch 4-5）、TCP（Ch 6）、TLS（Ch 11）、HTTP（Ch 10）、NAT（Ch 8）——幾乎每個核心協定都參與了。後面每一章深挖其中一步。現在不用懂細節，只要記住**這個順序**：先 DNS 拿到 IP，才能建 TCP 連線，TCP 之上才有 TLS，TLS 之內才送 HTTP。這個依賴順序是理解網路的關鍵——上層依賴下層。

## 親眼看這個旅程

別只讀，動手看。我們用工具觀察旅程的幾個步驟：

```bash
# 步驟 1：DNS 解析（Ch 9）—— 看 example.com 變成什麼 IP
dig +short example.com
# 93.184.216.34（或類似）

# 步驟 2：看「下一跳」往哪（路由表）
ip route get 93.184.216.34
# 93.184.216.34 via 192.168.1.1 dev eth0 ...
#   via 192.168.1.1 = 經過你的路由器（預設閘道）

# 步驟 2b：ARP（同網段的 MAC 解析，Ch 3）
ip neigh
# 192.168.1.1 ... lladdr aa:bb:cc:dd:ee:ff（路由器的 MAC）

# 步驟 6：封包經過哪些路由器（Ch 16）
traceroute example.com
#  1  192.168.1.1 (你的路由器)
#  2  <ISP 的路由器>
#  3  ...                  ← 每一跳是一個路由器

# 步驟 3-5：抓封包看整個 TCP+TLS+HTTP（Ch 14，本課核心手法）
sudo tcpdump -i any -n host example.com &     # 背景抓封包
curl -sI https://example.com > /dev/null      # 觸發一次請求
# 在 tcpdump 輸出看到：
#   SYN → SYN-ACK → ACK              (TCP 握手，Ch 6)
#   ... TLS handshake ...            (TLS 協商，Ch 11)
#   ... 加密的 application data ...   (HTTP over TLS)
sudo pkill tcpdump
```

> **這就是本課的學法——每個協定都能用工具「看見」**。`dig` 看 DNS 解析、`ip route get` 看路由決策、`traceroute` 看封包經過的路由器、`tcpdump` 看 TCP/TLS/HTTP 的真實封包。網路不是抽象的——它是真實的 bytes 在線上流動，而這些工具讓你看見它們。建議現在就跑一遍上面的命令，對著「完整旅程」那張圖,把每個命令的輸出對應到旅程的某一步。這種「協定 ↔ 看得見的封包」的連結，是把網路從「背概念」變成「理解」的關鍵。

## 為什麼分這麼多層、這麼多協定？

新手常困惑：為什麼要這麼複雜？一個協定搞定不行嗎？理解「為什麼分層」是理解網路的關鍵：

```
為什麼不用「一個大協定」搞定全部？

  假設有個超級協定「Netall」管所有事：
    定址、可靠傳輸、加密、域名、路由全包
        │
  問題：
    1. 換實體媒介就要重寫（WiFi/光纖/4G 傳輸不同）
    2. 想換加密方式要動到整個協定
    3. 不可靠傳輸的場景（影音）被迫背可靠傳輸的成本
        │
  分層的解法（每層可獨立替換）：
    應用層    HTTP/DNS/SSH...   ← 換應用不影響下層
    傳輸層    TCP/UDP           ← 要可靠用 TCP，要快用 UDP
    網路層    IP                ← 統一定址（不管底下是 WiFi 還光纖）
    連結層    Ethernet/WiFi...  ← 換媒介只換這層
        │
  → 每層只依賴「下一層的服務」，不管它怎麼實作
    IP 不管底下是光纖還 WiFi，HTTP 不管底下是 TCP 怎麼傳的
    這讓每層能獨立演進（如 HTTP/1→2→3、WiFi 4→5→6）
```

> **分層的核心價值是「每層能獨立替換和演進」**。如果網路是一個大協定，換 WiFi 換光纖要重寫、改加密要動全部。分層讓每層只依賴「下層提供的服務」而不管它怎麼實作——IP 層不在乎底下是光纖還是 WiFi（連結層的事）、HTTP 不在乎底下 TCP 怎麼保證可靠傳輸。這讓各層獨立演進：WiFi 從 4 進化到 6、HTTP 從 1.1 到 2 到 3、TLS 從 1.2 到 1.3，都不用其他層配合。這是 1970 年代網路設計最重要的決定，Ch 2 會深入這個分層模型。代價是「分層有開銷」（每層加自己的標頭、有時重複工作如多層都做錯誤檢查）——但可演進性的價值遠超這點開銷。理解分層，後面的一切才有架構。

## 故意弄壞:斷掉旅程的一步看現象

```bash
# 體會「旅程的每一步都不可少」——弄壞一步，整個壞掉

# 弄壞步驟 1（DNS）：把 DNS 指向錯的地方
# （在安全的測試方式：用 curl 指定錯誤的解析）
curl --resolve example.com:443:1.2.3.4 https://example.com --max-time 5
# 連線 timeout / 失敗 —— DNS「對」但 IP 是錯的（1.2.3.4 沒有 example.com）
# → 證明步驟 1（拿到正確 IP）不可少

# 弄壞「路由」：看沒有預設閘道會怎樣（在 netns 裡安全測試，Ch 0）
sudo ip netns add noroute
sudo ip netns exec noroute ip link set lo up
sudo ip netns exec noroute ping -c 2 8.8.8.8
# connect: Network is unreachable —— 沒有路由，封包不知道往哪送
# → 證明步驟 2（路由決策）不可少
sudo ip netns del noroute

# 觀察正常 vs 異常的差別，理解每一步的必要性
```

> 這個練習讓你體會旅程的**依賴性**——每一步都建立在前一步成功之上。DNS 給錯 IP，後面的 TCP 連線就連到錯的地方（timeout）。沒有路由，封包根本送不出去（Network is unreachable）。這種「斷一步、全鏈壞」的特性，是 debug 網路問題的核心思路（Ch 16/練習 B）：當「網頁打不開」時，你要沿著這條旅程**逐步排查**——DNS 解析對嗎？路由通嗎？TCP 連得上嗎？TLS 握手成功嗎？HTTP 有回應嗎？每一步都有對應的工具去驗證。理解了完整旅程，你就有了系統化 debug 的地圖。

## 動手練習

1. 走一遍旅程：對一個你常用的網站，依序跑 `dig`（DNS）、`ip route get <IP>`（路由）、`traceroute`（路徑）、`curl -I`（HTTP），把每個輸出對應到旅程圖的某一步

2. 抓完整封包：`tcpdump` 背景抓 + `curl https://...` 觸發，在輸出裡找出 TCP 握手（SYN/SYN-ACK/ACK）

3. 數路由跳數：對國內網站和國外網站各跑 traceroute，比較經過幾個路由器（跳數），體會「距離」

4. 跑「故意弄壞」：用 `--resolve` 給錯 IP、在 netns 裡測沒路由，看旅程斷在哪一步、報什麼錯

5. 畫你自己的旅程圖：不看本章，憑記憶畫出「打開網頁」的步驟順序，再對照檢查漏了哪步

## 本章重點整理

- 你的資料在網路上像信件被「層層包裝」再送出、層層拆開——這是分層模型（Ch 2）
- 打開一個網頁牽動 DNS→路由/ARP→TCP 握手→TLS→HTTP→NAT 幾乎所有核心協定，有嚴格的依賴順序（上層依賴下層）
- 每個協定都能用工具「看見」：dig（DNS）、ip route（路由）、traceroute（路徑）、tcpdump（封包）——這是本課核心學法
- 分層的價值是「每層獨立演進」（換 WiFi/換加密/HTTP 升級不影響其他層），代價是分層開銷
- debug 網路 = 沿旅程逐步排查（DNS 對嗎？路由通嗎？TCP 連得上嗎？…），每步有對應工具
