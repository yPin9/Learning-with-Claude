# Ch 21 — 管線哲學：組合小工具

> **目標**：理解 Unix 哲學的核心——「做一件事並做好」「用文字流當通用介面」「組合勝過內建」。這章不是新工具，而是把前面學的串成一套**設計思維**：為什麼 Unix 是一堆小工具加管線，而不是一個大程式？這個思維怎麼讓你解決真實問題。

> **環境**：通用概念章，例子在 bash 5.x。

## 為什麼需要一套「哲學」？

你學了 ls、grep、find、pipe……一堆工具。但真正的功力不在「會用某個工具」，而在「知道怎麼把它們組合起來解決沒見過的問題」。這需要一套思維框架——Unix 哲學。

這章是 Part 5 的轉折：從「pipe 怎麼運作」（Ch 20，機制）到「為什麼這樣設計、怎麼善用」（哲學與實踐）。理解了它，你看到一個新問題時，腦中會自動拆解成「ls 列出 → grep 篩選 → awk 提取 → sort 排序」這種管線思維，而不是想「我要寫個程式」。這是 Unix 高手和新手的根本差異。

## 先建立直覺：樂高 vs 一體成形

```
兩種軟體設計哲學：

  一體成形（monolith）：一個大程式做所有事
    ┌────────────────────────────┐
    │  超級檔案管理器              │
    │  - 列出檔案                  │
    │  - 篩選                      │
    │  - 排序                      │
    │  - 統計                      │
    │  - 匯出報表...              │  ← 全包在一個程式
    └────────────────────────────┘
    問題：想要新功能？改這個大程式（或它沒有你就沒轍）
        │
  Unix 哲學（組合）：一堆小工具 + 管線連接
    ls ──▶ grep ──▶ sort ──▶ awk ──▶ uniq
    每個只做一件事，用 pipe 串起來
        │
    想要新組合？把工具重新排列
    想要新功能？寫一個新小工具，插進管線
        │
  → 像樂高：小積木 + 標準接口（pipe 傳文字）
    能拼出無限組合，不用預先設計每種用途
```

關鍵心智：Unix 不是「一個做所有事的大程式」，而是「一堆做一件事的小工具 + 把它們連起來的管線」。每個工具只做一件事並做好，用文字流（text stream）當通用介面。組合產生威力——你能拼出工具作者從沒想過的用途。

## Unix 哲學的三條核心

Doug McIlroy（管線的發明者）總結的 Unix 哲學：

```
Unix 哲學三原則（McIlroy）：

  1. 「做一件事，並把它做好」（Do one thing well）
     grep 只管搜尋、sort 只管排序、wc 只管計數
     不是「grep 順便排序順便統計」
        │
  2. 「程式的輸出應能成為另一個程式的輸入」
     用文字流當通用介面 → 任何工具都能串接
     grep 的輸出能餵 sort，sort 的輸出能餵 uniq...
        │
  3. 「組合，而非堆疊功能」
     需要新功能 → 寫新小工具或重新組合
     不是把功能塞進已有的大程式
        │
  → 文字流是「通用接口」（universal interface）
    就像樂高的標準凸點，讓任何積木能接任何積木
```

```bash
# 「做一件事」的體現：每個工具職責單一
ls /etc           # 只負責「列出」
ls /etc | grep conf    # grep 只負責「篩選」
ls /etc | grep conf | sort    # sort 只負責「排序」
ls /etc | grep conf | sort | head -5   # head 只負責「取前 N」
# 沒有任何一個工具「列出 + 篩選 + 排序 + 取前 N」
# 但組合起來就做到了
```

> **「文字流當通用介面」是 Unix 哲學的技術核心**。為什麼工具能任意串接？因為它們都用同一種「資料格式」——文字行（lines of text）。grep 吃文字吐文字、sort 吃文字吐文字、awk 吃文字吐文字。這個共同格式讓 N 個工具有 N×N 種組合可能。對比現代很多工具用 JSON/protobuf/二進位格式——強型別但難以隨手組合（需要專門的 parser）。Unix 賭「文字夠用」，換來無與倫比的可組合性。這是一個深刻的設計取捨（後述「為什麼不」）。

## 管線思維：拆解一個真實問題

學哲學要看它怎麼解真實問題。拆解「找出存取 log 裡前 10 個最頻繁的 IP」：

```bash
# 問題：access.log 裡哪 10 個 IP 來訪最多次？
# 管線思維：拆成「提取 IP → 排序 → 計數 → 取前 10」

cat access.log \
  | awk '{print $1}' \          # 提取第一欄（IP）—— awk 做「提取」
  | sort \                       # 排序（讓相同 IP 相鄰）—— sort 做「排序」
  | uniq -c \                    # 計數相鄰重複 —— uniq 做「計數」
  | sort -rn \                   # 按次數反向數字排序 —— sort 做「再排序」
  | head -10                     # 取前 10 —— head 做「取前 N」

# 輸出：
#  4521 192.168.1.100
#  3201 10.0.0.5
#  ...

# 每個工具只做一件事，組合解決了複雜問題
# 沒有任何「分析 log 找熱門 IP」的工具——你用管線「發明」了它
```

```
管線思維的拆解過程：

  問題：「前 10 個最頻繁的 IP」
        │ 拆解成資料轉換步驟
        ▼
  原始 log 行 ──提取IP──▶ IP 列表 ──排序──▶ 排序的IP
        ──計數──▶ 次數+IP ──按次數排序──▶ 排序的次數 ──取前10──▶ 答案
        │
  每一步是一個「資料轉換」，對應一個工具
  管線把轉換串成資料流水線（pipeline）
        │
  → 解問題 = 把問題拆成一連串資料轉換 = 一條管線
```

> **管線思維是把問題拆解成「資料轉換的序列」**。看到「找前 10 熱門 IP」，不要想「我要寫個程式統計」，而要想「這是一連串轉換：提取 → 排序 → 計數 → 排序 → 取前 N」。每個轉換對應一個工具（awk/sort/uniq/sort/head）。這種思維讓你用現成工具拼出無限的一次性分析，不用寫程式、不用編譯、改一下管線就是新分析。這是 SysOps 和資料分析的日常超能力。練到後面，你看到 log 就會自動在腦中組管線。

## 對比：管線 vs 寫程式

| 面向 | 管線（組合工具） | 寫程式（如 Python） |
|---|---|---|
| 開發速度 | 秒級（一行命令） | 分鐘級（寫+測） |
| 一次性分析 | 完美（隨手改） | 殺雞用牛刀 |
| 複雜邏輯 | 難（管線變長變醜） | 強（完整語言） |
| 可重用 | 中（存成腳本） | 高（函式/模組） |
| 記憶體 | 低（streaming，Ch 20） | 看寫法（可能整個載入） |
| 可讀性 | 短管線清楚，長管線難讀 | 結構化，好維護 |
| 適合 | 探索、一次性、文字處理 | 複雜邏輯、長期維護、效能關鍵 |

```bash
# 同一個任務，兩種做法
# 管線（探索一次性問題，秒級）
cut -d: -f7 /etc/passwd | sort | uniq -c | sort -rn   # 統計各 shell 的使用人數

# Python（如果邏輯複雜、要長期維護）
# python3 -c "from collections import Counter; ..."（更長，但能做管線難做的事）
```

> **管線和寫程式不是對立，是互補**。管線適合**探索性、一次性、文字處理**的任務——你在 terminal 隨手組一條管線分析 log，秒級得到答案。但管線有極限：複雜的條件邏輯、需要資料結構、要長期維護的東西，硬塞進管線會變成沒人看得懂的怪物。經驗法則：**管線超過 5-6 個 stage 或出現複雜邏輯，考慮寫腳本**（Part 8）。高手知道什麼時候用哪個——不是「管線萬能」也不是「什麼都寫程式」，而是看任務選工具。awk 本身就是「管線和程式之間」的中間點（Ch 26）。

## 為什麼不選「大一統」設計？

Unix 哲學是個取捨，理解「為什麼不選大程式」比記住規則更重要：

```
設計空間：為什麼 Unix 選「小工具 + 管線」？

  替代方案 A：一個超級程式做所有事
    優點：功能整合、可以高度優化、強型別
    缺點：擴展難（要改大程式）、組合死板（只有作者想到的用法）
    例子：很多 IDE、Excel（強大但封閉）
        │
  替代方案 B：函式庫 + 寫程式
    優點：型別安全、效能、可組合（在程式內）
    缺點：每個任務都要寫+編譯，不能在 terminal 隨手用
        │
  Unix 選擇：小工具 + 文字流管線
    賭注：「文字夠用」「組合 > 內建功能」
    代價：文字解析脆弱（沒有型別，靠空白/欄位切）
          長管線難讀、錯誤處理弱
    回報：無與倫比的可組合性、可在 terminal 即時使用
        │
  → 沒有最好，只有取捨。Unix 賭「可組合性」最重要
    這個賭注在「探索和文字處理」場景大獲全勝
```

> Unix 哲學的代價是真實的，要誠實面對。**文字流沒有型別**——`awk '{print $2}'` 假設第 2 欄是你要的，欄位變了就壞（檔名有空白、log 格式變動都會出問題）。**錯誤處理弱**——管線中間一個 stage 失敗，預設不會中止整條管線（要 `pipefail`，Ch 35）。**長管線難維護**——10 個 stage 的管線沒人看得懂。現代有人嘗試「結構化」的替代（PowerShell 傳物件、nushell 傳結構化資料）來解決文字流的脆弱。但 Unix 的文字流贏在**普世性**——每個工具、每個語言都能產生和消費文字，這個最低共同標準讓一切能互通。知道它的限制，你才知道什麼時候該離開管線（去寫腳本或程式）。

## 進階：Unix 哲學的現代演進

Unix 哲學影響了現代很多系統，也有人挑戰它：

```bash
# 1. 結構化資料的挑戰：jq（JSON 的管線工具）
#    現代 API 回傳 JSON，文字行工具難處理，jq 是「JSON 版的 awk/grep」
curl -s api.example.com/users | jq '.[] | select(.active) | .name'
#    jq 把「管線思維」帶到 JSON（結構化資料）

# 2. PowerShell：傳「物件」而非文字（微軟的不同賭注）
#    Get-Process | Where-Object CPU -gt 10 | Select-Object Name
#    傳的是 .NET 物件（有型別），不是文字 —— 解決了文字流的脆弱
#    代價：只在 PowerShell 生態內可組合（不像文字到處能用）

# 3. nushell：結構化資料的現代 shell
#    ls | where size > 1mb | sort-by modified
#    把表格/結構化資料當一等公民

# 4. Unix 哲學在程式設計的影響
#    微服務（每個服務做一件事）、Docker（單一職責容器）
#    都是「組合小單元 > 大一統」的哲學延伸
```

> **Unix 哲學的爭論至今活躍**。文字流的脆弱（解析靠欄位切割、沒型別）是真問題，PowerShell（傳物件）、nushell（傳結構化資料）、jq（JSON 管線）都是嘗試「保留管線組合性、但給資料結構」的方案。這是個沒有定論的設計空間——文字流贏在普世互通（任何工具都懂文字），結構化贏在型別安全和可靠。實務上你會兩者都用：傳統文字管線處理 log 和系統工具的輸出，jq 處理 JSON API。理解這個演進，你會明白 Unix 哲學不是教條而是一組取捨，在不同場景有不同的最佳解。McIlroy 1978 年的原則，到今天仍是系統設計的北極星，但不是唯一的星。

## 動手練習

1. 拆解問題練習：用管線回答「/etc 下哪種副檔名的檔案最多？」（提示：ls → 提取副檔名 → sort → uniq -c → sort）

2. 體會「做一件事」：找出你常用的 5 個命令，說出每個「只做的那一件事」是什麼

3. 找管線的極限：嘗試用純管線做一個「需要記住狀態」的任務（如「找出連續 3 行都是 ERROR 的位置」），感受什麼時候管線不夠、該寫腳本

4. 對比 jq：`cat 某個.json | jq` vs 用 grep/awk 處理同個 JSON，感受結構化工具的優勢

## 本章重點整理

- Unix 哲學：「做一件事並做好」+「文字流當通用介面」+「組合勝過內建功能」
- 文字流是技術核心——共同格式讓 N 個工具有 N×N 種組合，換來無與倫比的可組合性
- 管線思維 = 把問題拆解成「資料轉換的序列」，每步對應一個工具
- 取捨：文字流脆弱（無型別）、錯誤處理弱、長管線難讀——管線超過 5-6 stage 或邏輯複雜就該寫腳本
- 現代演進（jq/PowerShell/nushell）在「組合性 vs 結構化」間探索，沒有定論
