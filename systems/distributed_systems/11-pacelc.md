# Ch 11 — PACELC 與延遲取捨

> **目標**：補上 CAP 沒講的那半邊天。CAP 只談「分區時（P）」的取捨，但系統 99.9% 的時間都沒在分區——那時你在**延遲（Latency）**和**一致性（Consistency）**之間同樣要選。PACELC 把這個「沒分區時（Else）」的取捨也納進來，給出一個更完整的分類框架。我們會用它把 Dynamo、Spanner、MongoDB 這些真實系統精準歸位，並講清楚**為什麼「低延遲」和「強一致」本質上衝突**。

上一章結尾我們留了一個洞：CAP 只描述「網路分區發生時」該選 C 還是 A，卻對「沒分區的那 99.9% 時間」隻字不提。這是 CAP 一個真實的盲區——Brewer 本人 2012 年就點出「分區是罕見的，所以沒分區時的行為才是系統平時的主戰場」。PACELC（2010，Daniel Abadi 提出）就是來補這個洞的。它不推翻 CAP，它把 CAP 包進一個更大的框架：**分區時（PAC）選 A 還是 C，沒分區時（ELC）選 L 還是 C。**

## 為什麼需要這個？

CAP 有個實務上很尷尬的地方：它描述的那個「取捨時刻」（網路分區）其實**很少發生**。一個經營良好的資料中心，網路分區可能幾個月才一次，每次幾秒到幾分鐘。也就是說，CAP 談的是系統 **0.01% 時間**的行為。

那另外 **99.99% 的時間**——網路好端端的、沒有任何分區——系統在權衡什麼？CAP 一個字都沒說。而這恰恰是使用者天天感受到的：**你每一次讀寫的延遲，就取決於系統在「沒分區時」怎麼權衡一致性和速度。**

具體說：就算網路完全正常，一個「強一致」的系統為了保證你讀到最新值，仍然得在回應前跟其他副本協調（Ch 9 那趟「等多數確認」的 RTT）。這趟協調**在沒有任何分區、網路完美的情況下也照付不誤**——它是強一致的固有成本，不是分區才有的。於是平時你就面對一個 CAP 完全沒涵蓋的取捨：

> **沒分區時，我要不要為了「保證讀到最新值」而多付一趟跨節點協調的延遲？還是我接受「可能讀到稍舊的值」來換取更低的延遲？**

這就是 PACELC 的 **ELC**（Else, Latency or Consistency）。Abadi 的洞見是：**一個系統的一致性個性，其實由兩個取捨共同決定**——分區時的（CAP 講的那個）和平時的（CAP 漏掉的那個）。只用 CAP 分類，會把兩個「都在分區時選一致」但「平時延遲策略完全不同」的系統混為一談。

## 先建立直覺：把 CAP 補成一個完整的 if-else

PACELC 這個名字本身就是一個條件式，讀出來就懂：

```
   if (Partition) {          // 如果發生網路分區……
       choose A or C;        // 在「可用性」和「一致性」之間選（這就是 CAP）
   } else {                  // 否則（沒分區，網路正常）……
       choose L or C;        // 在「低延遲」和「一致性」之間選（CAP 漏掉的）
   }
```

拆開這個縮寫：

```
  P  A  C   E  L  C
  │  │  │   │  │  └── Consistency（一致性）
  │  │  │   │  └───── Latency（低延遲）
  │  │  │   └──────── Else（否則，即「沒分區時」）
  │  │  └──────────── Consistency（一致性）
  │  └─────────────── Availability（可用性）
  └────────────────── if Partition（如果分區）
```

於是每個系統可以貼一個**兩段式標籤**：`PAC/ELC` 各取一個字母，四種組合：

```
                     沒分區時（ELC）
                  選延遲(L)    選一致(C)
              ┌──────────────┬──────────────┐
  分區時  A   │   PA / EL    │   PA / EC    │
  (PAC)       │ 一路把可用性 │  分區時保可用 │
              │ 和延遲擺第一 │  平時卻要強一致│
              │ (Dynamo,     │  (少見)       │
              │  Cassandra)  │              │
              ├──────────────┼──────────────┤
          C   │   PC / EL    │   PC / EC    │
              │ 分區時保一致 │ 一路強一致，  │
              │ 平時卻放鬆   │ 分區與平時都  │
              │ 換延遲(少見) │ 不妥協        │
              │              │ (Spanner)    │
              └──────────────┴──────────────┘
```

實務上對角線的兩格（`PA/EL` 和 `PC/EC`）最常見，因為一個系統的「一致性哲學」通常一以貫之：**要嘛可用性/延遲優先到底（PA/EL），要嘛一致性優先到底（PC/EC）。** 另外兩格（分區時和平時的態度相反）比較少見但存在，MongoDB 這種可調系統就能落在中間。

## 為什麼低延遲與強一致本質衝突

PACELC 的 ELC 之所以成立，根植於一個物理與邏輯的雙重約束：**強一致必然要求跨節點協調，而協調必然要花時間。** 把這個「必然」拆開看。

要保證線性一致（讀到的一定是最近寫的），一個節點回應請求前，**不能只相信自己**——它本地的值可能已經被別的節點更新了、它可能落後了。所以它必須：

```
  強一致的讀取（沒有任何分區、網路完美）：

   client ── read(x) ──> 節點 A
                          │
                          │ A 不敢直接回本地值：萬一我落後了？
                          │ 必須確認「我這個是不是全叢集最新的」
                          ▼
              A ──"最新的 x 是多少?"──> 多數其他節點
                          │  ← 這一趟跨節點往返（RTT）
                          │     在沒分區時也照付
              A <──── 回覆 ────────── 多數其他節點
                          │
                          ▼
   client <── x 的最新值 ── A     總延遲 = 本地處理 + 至少一趟跨節點 RTT
```

那趟「跨節點 RTT」就是強一致的稅。它在**網路完美、零分區**的情況下也**照收不誤**——因為協調的必要性來自「我可能落後」這個邏輯事實，不是來自網路故障。跨資料中心的話，這趟 RTT 動輒幾十上百毫秒（光速決定的，Ch 8 講過）。

反過來，低延遲的做法是**讓節點直接回本地值、不跟任何人協調**：

```
  低延遲的讀取：

   client ── read(x) ──> 節點 A
                          │ A 直接回本地值，不問任何人
                          ▼
   client <── 本地的 x ── A     總延遲 = 本地處理（快！）
                                但：本地值可能舊了 → 犧牲一致性
```

沒有協調，所以快；但沒有協調，所以你拿到的可能是舊值。**這就是衝突的本質：一致性要靠協調保證，協調要靠訊息往返實現，訊息往返要花時間。你想省掉那個時間，就得省掉那個協調，也就省掉了那個保證。** 這不是工程沒做好，是邏輯上的不可兼得——就像 CAP 的分區取捨一樣，只是這次的敵人不是「網路斷了」，而是「訊息傳遞不是瞬間的」。

> 一個常見的加速手法是把「等多數」改成「只讀本地 leader」或用租約（lease），但那要嘛依賴時鐘假設（Spanner 的 TrueTime）、要嘛把協調成本挪到別處（寫入時），天下沒有白吃的午餐——你總在某處付了協調的帳。

## 把 ELC 換算成毫秒：一個具體的帳

「多一趟協調 RTT」聽起來抽象，換成真實延遲數字就有痛感了。以下數量級來自公開的網路 RTT 觀測（同機房 <1ms、跨美國約 60–80ms、跨太平洋約 120–160ms，這些是光速加路由的物理下限，實測會更高），拿來估「選 EC vs 選 EL」的延遲差：

```
  情境：一次讀取（讀本地 vs 讀取要跟遠端多數確認）

  ┌────────────────────────┬──────────┬──────────────────────────┐
  │ 部署                   │ 選 EL    │ 選 EC（多付一趟到多數的 RTT） │
  ├────────────────────────┼──────────┼──────────────────────────┤
  │ 單機房 3 副本          │ ~0.5 ms  │ ~1–2 ms（+1 趟同機房 RTT）  │
  │ 跨美東西 3 副本        │ ~0.5 ms  │ ~60–80 ms（+1 趟跨美 RTT）  │
  │ 跨太平洋（美↔亞）3 副本 │ ~0.5 ms  │ ~150 ms+（+1 趟跨洋 RTT）   │
  └────────────────────────┴──────────┴──────────────────────────┘
```

讀出這張表的重點：**同機房裡，EC 的協調稅小到幾乎不用在乎（1–2ms，選 EC 幾乎白撿強一致）。但一旦跨洲，EC 的稅就從「零頭」變成「使用者能明顯感覺的卡頓」（150ms+，那是一次頁面載入的差別）。** 這解釋了為什麼：

- 單機房系統幾乎都樂意選 EC（強一致又不慢，何樂不為）；
- 為全球服務設計的系統（Dynamo）才會痛下決心選 EL——它們的使用者遍布全球，任何一次強一致協調都可能跨洋，累積起來就是體驗災難。

也解釋了 Spanner 的困難與偉大：它選 `PC/EC`（全球強一致），意味著它要在跨洲部署下**還是付那趟協調的帳**。它靠 TrueTime + commit-wait 把這筆帳的形態改變（用一個可控的等待取代不確定的協調延遲），加上 Google 的專屬網路把 RTT 壓到物理下限附近，才讓 `PC/EC` 在全球尺度上勉強跑得動。**普通人拿普通網路選 `PC/EC` 跨洲部署，會慢到不能用——這就是 ELC 取捨的現實重量。**

## 真實系統怎麼歸位

PACELC 的價值在於它能把真實系統分得比 CAP 細。逐個看：

**Dynamo / Cassandra / Riak → `PA/EL`**
分區時選可用（A，照樣服務、事後合併）；沒分區時也選低延遲（L，讀寫只碰少數副本、不強求最新）。它們從頭到尾把「快 + 永遠能服務」擺第一，一致性讓路。這是 Dynamo 那一脈的靈魂：Amazon 寧可偶爾讓兩個購物車版本需要合併，也不要使用者在結帳時看到轉圈。**注意：純用 CAP 你只會說它們是「AP」，看不出它們平時也犧牲一致性換延遲——PACELC 的 EL 才點出這一半。**

**Google Spanner → `PC/EC`**
分區時選一致（C，少數派不可寫）；沒分區時也選一致（C，讀寫都走 Paxos + TrueTime 保證線性一致）。它是「一致性不妥協」的典範——平時和分區時都選 C，代價是那趟協調延遲。Spanner 的本事在於用 TrueTime（GPS + 原子鐘）和極好的網路工程，把「協調延遲」和「分區機率」都壓到小得可接受，讓 `PC/EC` 在全球尺度上還跑得動（Ch 39 專講）。**它是活生生的反例，打臉「強一致在廣域網一定不可用/不可行」的迷思。**

**MongoDB → 可調，預設偏 `PC/EC`，可放鬆到偏 `PA/EL`**
MongoDB 用 single-leader 複製 + 可調的 read/write concern。預設（`majority` write concern + 從 primary 讀）偏 `PC/EC`：分區時少數派的 primary 會降級、寫入要等多數確認。但你可以放鬆——允許從 secondary 讀（`readPreference: secondary`，換低延遲但可能讀到舊值，偏 EL）、降低 write concern（換低延遲但可能丟資料）。**它示範了 PACELC 的取捨往往是「每個操作可調」，不是全系統一刀切**（呼應 Ch 9 踩雷 #4）。

**etcd / ZooKeeper → `PC/EC`**
共識驅動（Raft / Zab），分區時少數派拒絕服務（PC），平時線性一致讀寫也走協調（EC）。它們是拿來存「必須正確」的東西（叢集配置、鎖、leader 選舉結果），一致性壓倒一切，延遲是次要考量。

整理成表：

| 系統 | PACELC | 分區時（P） | 沒分區時（E） | 一句話 |
|---|---|---|---|---|
| Dynamo / Cassandra | PA/EL | 選可用 | 選低延遲 | 快 + 永遠能服務，一致性讓路 |
| Riak | PA/EL | 選可用 | 選低延遲 | 同上，高可用 KV |
| Spanner | PC/EC | 選一致 | 選一致 | 一致性全程不妥協（靠 TrueTime 撐住可用性/延遲） |
| etcd / ZooKeeper | PC/EC | 選一致 | 選一致 | 存「必須正確」的東西 |
| MongoDB | 可調（預設 PC/EC） | 可調 | 可調 | 每操作可調 read/write concern |
| PNUTS (Yahoo) | PC/EL | 選一致 | 選低延遲 | 少見的混合：分區保一致、平時放鬆換延遲 |

PNUTS 那格（`PC/EL`）值得留意——它是「非對角線」組合的真實例子：分區時它保一致（拒絕不確定的寫），但平時它為了廣域低延遲，允許讀到稍舊的值。這種「態度不一致」的系統證明了四格都有人住，PACELC 的細分是有意義的，不是為分而分。

## 底層機制：協調延遲花在哪、能不能省

把「強一致的協調延遲」拆到最細，看看它到底由什麼構成、工程上怎麼跟它搏鬥：

```
  一次強一致寫入的延遲組成（single-leader + 等多數，如 Raft）：

  client → leader     : 1 段網路（client 到 leader）
  leader 本地寫 log    : ~0（記憶體/SSD append）
  leader → followers  : 1 段網路（廣播給所有 follower）  ┐
  followers 本地寫 log : ~0                              ├ 這一來一回是「等多數」的核心
  followers → leader  : 1 段網路（ack 回 leader）        ┘
  leader 等到「多數 ack」: 被第 (n/2) 快的 follower 綁架（尾延遲）
  leader → client     : 1 段網路（回覆成功）

  關鍵成本 = leader↔follower 的「一來一回」RTT + 等多數的尾延遲
```

工程上和這個延遲搏鬥的手段（都在「省協調」和「保一致」之間找折衷）：

- **就近放 follower / 減少跨區**：把需要參與多數的節點放在網路近的地方，壓低那趟 RTT。但這和「容錯要地理分散」衝突——放太近，一個機房事故全滅。
- **租約（lease）讓 leader 能本地讀**：給 leader 一個有時限的「我保證這段時間內我是唯一 leader」租約，這段時間內 leader 讀取不用每次都問多數（省掉讀的協調）。代價是依賴時鐘（租約到期判斷要時鐘，Ch 4 說過時鐘會說謊）。
- **TrueTime（Spanner）**：用 GPS + 原子鐘把時鐘不確定性壓到已知的小區間，靠「等待不確定區間過去」（commit-wait）換取全球線性一致，把協調成本轉化成一個可控的小等待。這是把「協調延遲」用硬體工程壓到極限的代表作。
- **放鬆一致性換延遲**：最直接的——允許讀 follower（讀到舊值換低延遲）、降低 write concern（不等多數換低延遲）。這就是主動選 EL。

沒有一個手段能「零協調又強一致」——它們都是在「協調成本」的帳單上挪動數字，而不是讓帳單歸零。**PACELC 的 ELC 本質上就是問你：這張協調成本的帳單，你想在「延遲」欄付，還是在「一致性」欄付？**

## 怎麼替自己的系統選格子

PACELC 是分類框架，但真正的問題是「**我該把我的資料放進哪一格**」。給一套可操作的決策流程，逐個問：

```
  問題 1：這份資料，讀到「稍舊的值」會造成錯誤/損失嗎？
    ├─ 會（餘額、庫存、鎖、配置、選主結果）───────► 傾向 C（EC，且 PC）
    └─ 不會（按讚數、瀏覽次數、動態時間軸、快取）─► 可以 L（EL，且 PA）

  問題 2：這份資料的兩個副本「同時被改」，事後能自動合併嗎？
    ├─ 能（購物車=集合聯集、計數器=CRDT）────────► 放心選 A/EL，衝突可解
    └─ 不能（餘額轉帳、唯一性約束）──────────────► 必須 C，別讓它分歧

  問題 3：你的副本會跨洲嗎？（決定 EC 的「稅」有多重）
    ├─ 單機房 ──────► EC 幾乎免費，除非要極致低延遲否則選 C
    └─ 跨洲 ────────► EC 每次多付 100ms+，只在「必須正確」時才選

  問題 4：分區時，這個服務「暫時停擺」和「回可能錯的值」哪個後果輕？
    ├─ 停擺可接受（後台配置、金流）───────────────► PC（分區時拒絕服務）
    └─ 停擺不可接受（購物、首頁 feed）────────────► PA（分區時降級服務）
```

走一遍就會發現：**同一個應用裡不同的資料，答案往往不同。** 一個電商系統：

- **商品庫存扣減、下單** → 讀到舊值會超賣、下重複單 → **PC/EC**（寧可下單時稍慢/偶爾要重試，不能超賣）。
- **購物車** → 兩裝置同時加東西可以合併（集合聯集）→ **PA/EL**（Amazon 的經典選擇，永遠能加購、事後合併）。
- **商品瀏覽頁、推薦** → 讀到幾秒前的舊資料沒差、要極快 → **PA/EL**（讀快取/最近副本）。
- **後台的價格/促銷配置** → 全站要看到同一份、改錯會亂 → **PC/EC**（用 etcd/ZooKeeper 存）。

這就是為什麼「這家公司用 CP 還是 AP」是個假問題——**一家公司的不同子系統散落在 PACELC 的不同格子裡，這是成熟系統的常態，不是不一致的設計。** 選型的單位是「資料/操作」，不是「公司」或「整個資料庫」。真正的架構功力在於**認出每份資料屬於哪一格**，而不是找一個「最好的一致性」套用全部。

## 對比與取捨：CAP vs PACELC

| | CAP | PACELC |
|---|---|---|
| 涵蓋 | 只有分區時 | 分區時 + 沒分區時 |
| 分區時的取捨 | A vs C | A vs C（同 CAP） |
| 沒分區時的取捨 | **沒講** | **L vs C**（補上） |
| 對系統的分類 | 粗（CP / AP） | 細（PA/EL、PC/EC、PC/EL…） |
| 能區分 Dynamo 和「分區時選 A 但平時強一致」的系統嗎 | 不能（都叫 AP） | 能（PA/EL vs PA/EC） |

一句話：**PACELC = CAP + 「沒分區時的延遲取捨」。** 它不否定 CAP，它指出 CAP 只講了故事的一半——而且是比較少發生的那一半。對系統選型來說，`ELC` 那一半（平時的延遲 vs 一致性）往往比 `PAC` 那一半（罕見的分區）**影響你的日常體驗更大**，因為它決定了系統 99.9% 時間的延遲個性。

## 踩雷集錦

1. **以為 PACELC 取代或推翻了 CAP——不是。** PACELC **包含** CAP：它的前半段 `PAC` 就是 CAP 本身，只是後面加了 `ELC`。正確的關係是「PACELC 是 CAP 的超集/補全」，不是「新理論打倒舊理論」。用 PACELC 時，CAP 講的東西一個都沒少。

2. **把 ELC 的取捨也當成「分區造成的」。** ELC 的延遲成本**發生在網路完美、零分區的時候**。強一致的那趟協調 RTT 是「因為我可能落後、所以要確認」的邏輯後果，不是「因為網路斷了」。很多人以為「強一致慢是因為要處理故障」——不是，就算永遠不故障，強一致還是要多付那趟協調。這是它平時就慢的原因。

3. **用 CAP 的 CP/AP 標籤就以為夠了。** CAP 把 Dynamo 和一個「分區時選 A、平時卻強一致」的假想系統都叫「AP」，抹掉了它們平時延遲策略的天壤之別。要精確描述一個系統的一致性個性，`PA/EL` 和 `PA/EC` 是兩回事——前者平時也快也弱，後者平時慢而強。只貼 CAP 標籤會漏掉這一半資訊。

4. **以為 `PC/EC`（全程強一致）在廣域網不可行——Spanner 打臉。** 有種迷思說「強一致 + 全球分散 = 慢到不能用」。Spanner 證明了用夠好的網路工程 + TrueTime，`PC/EC` 可以在全球尺度上跑到五個九的可用性和可接受的延遲。強一致的協調成本是真的，但「真的」不等於「不可克服」——它可以被工程壓到很小。別拿 PACELC 當「所以只能做弱一致」的藉口（跟 Ch 10 踩雷 #3 同一個病）。

5. **忽略 ELC 往往是「每操作可調」而非「全系統固定」。** MongoDB、Cassandra 都讓你**逐個操作**選一致性等級（強一致讀 vs 快讀舊值）。所以「這個系統是 EL 還是 EC」常常問錯——正確的問法是「這個**操作**用了哪一級」。同一個系統，關鍵的餘額讀走 EC，不重要的統計讀走 EL，是常態。

## 進階：再往深一層

- **PACELC 也還不夠細——一致性有整條光譜。** PACELC 的 C 和 L 仍是二元的（強一致 or 低延遲）。但 Ch 9 告訴我們一致性是一整條光譜（linearizable / causal / eventual…），延遲也是連續的。真實系統活在一個**二維連續空間**裡：一致性強度 × 延遲。**bounded staleness**（保證讀到的值最多舊 T 毫秒/版本）就是這個空間裡的一個點——它既不是強一致也不是純最終一致，而是「可量化的舊」。Abadi 後來的工作和各種「可調一致性」都在填這個連續空間。PACELC 是個好用的粗分類，別把它當成一致性的全部真相。

- **ELC 的取捨對「地理分散」尤其致命。** 單一資料中心內，跨節點 RTT 是次毫秒級，強一致那趟協調的延遲稅小到常可忽略——EC 幾乎沒代價。但一旦跨洲（US↔Asia，RTT ~150ms+），那趟協調就變成使用者能明顯感覺到的卡頓。**所以 PACELC 的 ELC 取捨在多資料中心/全球部署時才真正咬人**，這也是為什麼 Dynamo（為 Amazon 全球購物設計）選 EL、而多數單機房系統可以輕鬆選 EC。地理尺度放大了協調延遲，也就放大了 ELC 的取捨。

- **和 Ch 8 同步/非同步複製的接續**：PACELC 的 ELC 其實就是 Ch 8「同步 vs 非同步複製」在一致性語言下的重述。**同步複製 = 等副本確認 = EC**（付延遲、保一致）；**非同步複製 = 不等 = EL**（省延遲、可能不一致/丟資料）。三章串起來：Ch 8 給了「等不等副本」的機制，Ch 9 給了「一致性有多強」的光譜，Ch 10/11 給了「這些取捨在分區時（CAP）和平時（PACELC）各是什麼」的框架。Part 2 的前四章到這裡收成一張完整的取捨地圖，接下來 Ch 12/13 就是把 single-leader 和 quorum 這兩種具體複製方案在這張地圖上落地。

## 本章重點整理

- CAP 只談「分區時（P）」的取捨，漏掉了系統 99.9% 時間所在的「沒分區時」。**PACELC 補上：沒分區時（Else），在低延遲（L）和一致性（C）之間也要選。**
- PACELC 讀作 if-else：`if Partition: A or C; else: L or C`。系統貼兩段式標籤 `PAC/ELC`。
- 常見組合是對角線：**PA/EL**（Dynamo、Cassandra，一路可用+低延遲）與 **PC/EC**（Spanner、etcd，一路強一致）。MongoDB 可調、PNUTS 走非對角的 PC/EL。
- **低延遲與強一致本質衝突**：強一致要靠跨節點協調保證，協調要靠訊息往返實現，往返要花時間（那趟 RTT）。這在**零分區、網路完美時也照付**——因為協調的必要性來自「我可能落後」的邏輯事實，不是網路故障。
- PACELC **包含**（不推翻）CAP：`PAC` 就是 CAP，`ELC` 是補全。ELC 那半往往比 PAC 那半更影響日常延遲體驗。
- ELC 常是「每操作可調」而非全系統固定；地理分散會放大協調延遲，讓 ELC 取捨更尖銳。
