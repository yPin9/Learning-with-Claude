# Ch 8 — 為什麼複製

> **目標**：講清楚「把同一份資料放在多台機器上」這件事到底是為了什麼、它立刻帶來什麼代價，以及同步 vs 非同步複製、single-leader / multi-leader / leaderless 三種拓樸的取捨。這一章不寫 code，但要把 Part 2 整條線的問題意識立起來——**複製是這一切一致性麻煩的源頭**。

我們花了 Part 1 把「時間與順序」挖到底：實體時鐘會說謊、Lamport 時鐘只保因果、vector clock 才偵測得出並行、total-order broadcast 要一群節點對「事件順序」達成一致。那整個 Part 存在的理由，其實就是為了服務這一章要開的頭：**一旦你把同一份資料複製到多台機器，這些機器對「現在的值是什麼」就會產生分歧，而你需要順序與一致性的工具來收拾它。**

## 為什麼需要這個？

先問一個更基本的問題：**為什麼不乾脆只放一份？** 一台機器、一份資料、所有讀寫都打到它。沒有複製，就沒有副本不一致的問題，Part 2 到 Part 4 大半內容都可以不用學。

單機方案在很長一段時間裡確實是主流。1990 年代的資料庫就是一台大型主機（mainframe）加一組昂貴的磁碟陣列，靠「把單機做得夠強、夠可靠」來扛。這條路撞牆的原因有三個，每一個都逼你走向複製：

1. **單機會死，而且是徹底地死。** 硬碟壞軌、電源燒掉、機房斷電、kernel panic。單機方案裡，這台機器一死，服務就是 100% 不可用，資料可能直接遺失。你可以買更貴的硬體降低故障率，但降不到零——而規模一大，「小機率」會變成「每天都有機器在死」。Google 的經驗法則是：一個上萬台機器的叢集，每天都有機器壞，這是常態不是意外。

2. **單機扛不住所有讀取。** 一台機器的 CPU、記憶體、網卡頻寬有上限。當讀取流量超過單機能處理的量，你沒有第二台可以分攤。垂直擴展（scale up，換更強的機器）有物理天花板，而且越接近天花板越貴——效能翻倍的機器價格常常是四倍五倍。

3. **單機在地理上只有一個位置。** 你的伺服器放在美國，台灣的使用者每次讀取都要吃一趟跨太平洋的來回延遲（round-trip time, RTT），輕鬆一兩百毫秒起跳。這不是頻寬問題，是光速問題——資料在光纖裡跑，物理上就是要那麼久。你沒辦法靠買更快的機器解決「資料離使用者太遠」。

複製（Replication）就是對這三件事的直接回應。把同一份資料維護在多個節點上，於是：一台死了還有別台、讀取可以分散到多台、資料可以放在離使用者近的地方。

> 注意複製（Replication）和分片（Partitioning / Sharding）是**兩個正交的維度**，別混。複製是「同一份資料放多份」，解決容錯與讀取擴展；分片是「不同資料放不同機器」，解決單機裝不下的容量問題。真實系統兩者都用（Ch 27 講分片）。這一章只談複製。

## 先建立直覺：複製買到三樣東西，但立刻欠一筆債

```
              單機                          複製（3 副本）
       ┌───────────────┐            ┌─────┐  ┌─────┐  ┌─────┐
       │   Node A      │            │  A  │  │  B  │  │  C  │
       │  [x = v1]     │            │x=v1 │  │x=v1 │  │x=v1 │
       └───────────────┘            └─────┘  └─────┘  └─────┘
              │                        │        │        │
     A 死 = 全部不可用          A 死 → B、C 還活著（容錯）
     所有讀打同一台            讀可分散到 A/B/C（增吞吐）
     資料只在一個地點          可就近讀最近的副本（降延遲）
```

複製買到三樣東西：

- **容錯（Fault Tolerance）**：一個副本掛了，其他副本還能服務。這是複製最不可退讓的理由。
- **降延遲（Lower Latency）**：把副本放在靠近使用者的地方，讀取走最近的副本。台灣使用者讀台灣的副本，不用跨太平洋。
- **增吞吐（Higher Throughput）**：讀取可以分散到多個副本，總讀取能力隨副本數上升。

但天下沒有白吃的午餐。你把 `x=v1` 複製到 A、B、C 三個節點的那一瞬間，就欠下一筆債：**當有人把 A 上的 `x` 改成 `v2`，B 和 C 上還是 `v1`。在這個更新傳播到 B、C 之前，你的系統裡同時存在 `v1` 和 `v2` 兩個「真相」。**

```
      client 寫 x=v2 到 A
             │
             ▼
       ┌─────┐        ┌─────┐        ┌─────┐
       │  A  │        │  B  │        │  C  │
       │x=v2 │───?───>│x=v1 │        │x=v1 │   ← 更新還在路上
       └─────┘        └─────┘        └─────┘
         ▲                              ▲
      讀到 v2                        讀到 v1   ← 同一時刻，不同答案
```

這就是**一致性問題（consistency problem）**的根源，也是 Part 2 剩下六章、乃至整個共識 Part 存在的理由。複製不是「加幾台備援機」這麼單純——它從根本上改變了「這份資料現在的值是什麼」這個問題有沒有唯一答案。**你一旦複製，就必須回答：多個副本不一致時，讀取該看到什麼？寫入該怎麼傳播？衝突了怎麼辦？**

Part 1 學的順序工具（Lamport、vector clock、total order）就是拿來回答這些問題的彈藥。這一章負責把問題問清楚，後面幾章負責回答。

## 同步複製 vs 非同步複製：延遲換資料安全

更新怎麼從主副本傳到其他副本？核心分歧在一個問題上：**寫入要不要等副本確認，才回覆客戶端「成功」？**

這決定了「同步（synchronous）」還是「非同步（asynchronous）」複製，是複製設計裡最根本的取捨。

**同步複製**：客戶端寫入 → 主節點更新 → 主節點把更新送給副本 → **等副本回 ack** → 才回覆客戶端「成功」。

```
  client         leader          follower
    │  write x=v2   │               │
    │──────────────>│               │
    │               │  replicate    │
    │               │──────────────>│
    │               │      ack       │  ← leader 等這個 ack
    │               │<──────────────│
    │   OK（成功）   │               │
    │<──────────────│               │
    │  ← client 收到 OK 時，follower 保證已經有 v2
```

**非同步複製**：客戶端寫入 → 主節點更新 → **立刻回覆客戶端「成功」** → 更新在背景慢慢傳給副本。

```
  client         leader          follower
    │  write x=v2   │               │
    │──────────────>│               │
    │   OK（成功）   │               │  ← leader 不等 follower，立刻回
    │<──────────────│               │
    │               │  replicate    │
    │               │ - - - - - - ->│  ← 背景傳播，可能還沒到
    │  ← client 已經收到 OK，但 follower 可能還是舊值
```

取捨的核心是一句話：**同步複製用延遲換資料安全，非同步複製用資料安全換延遲。**

| | 同步複製 | 非同步複製 |
|---|---|---|
| 寫入延遲 | 高（要等副本 ack，多一趟 RTT） | 低（不等，立刻回） |
| 主節點崩潰時的資料遺失 | 不會遺失（已回覆的寫入副本都有） | 可能遺失（已回覆但還沒傳到副本的寫入，隨主節點一起死） |
| 副本慢/掛時 | 寫入被拖慢甚至卡住（要等它） | 不受影響（不等它） |
| 適合 | 不能掉資料的場景（金流、訂單） | 高吞吐、能容忍少量遺失（社群動態、快取） |

非同步複製那個「可能遺失」的窗口是真的會咬人的。假設主節點回覆客戶端「你的轉帳成功」，但這筆更新還在往副本傳的半路上，此刻主節點崩潰、一個副本被提升為新主節點——這個新主節點上**沒有那筆轉帳**。客戶端手上握著「成功」的回執，系統裡卻查無此筆。這種「已確認寫入卻遺失」是分散式系統最難跟使用者交代的失敗之一。

那全用同步複製不就好了？問題是同步複製把「所有副本」綁成了一根鏈條：**只要有一個副本慢或掛，整個寫入就被拖住**。副本越多，遇到「至少一個副本有狀況」的機率越高，寫入延遲的尾巴（tail latency）就越長。極端情況下，一個卡死的副本能讓整個系統的寫入全部停擺。

實務上的折衷是**半同步（semi-synchronous）**：只要求「至少一個」（或「多數」）副本確認，而不是全部。這樣既有一份同步副本保底（主節點掛了它能頂上、不掉資料），又不會被最慢的那個副本綁架。這個「多數確認」的思路，正是 Ch 13 quorum 複製和整個共識 Part 的核心——**先記住「等多數，不等全部」這個原則，後面會反覆出現**。

## 三種複製拓樸：誰能接受寫入？

副本之間怎麼組織？關鍵區別在一個問題：**哪些節點可以接受寫入（write）？** 這切出三種拓樸，是 Part 2 後半（Ch 12、Ch 13）的骨架，這裡先建立全景。

### Single-Leader（單主）

一個節點被指定為 leader（主節點，也叫 primary / master），**所有寫入只能打到 leader**。leader 把變更複製給其他 follower（從節點）。讀取可以打到任何副本。

```
                  ┌──────────┐
      writes ───> │  Leader  │
                  └──────────┘
                    │      │
             replicate    replicate
                    ▼      ▼
              ┌────────┐ ┌────────┐
   reads ───> │Follower│ │Follower│ <─── reads
              └────────┘ └────────┘
```

- **好處**：寫入只有一個入口，天然沒有「兩個節點同時改同一筆」的寫寫衝突。是最好懂、最常用的模型（MySQL/PostgreSQL 主從、MongoDB、絕大多數傳統資料庫的複製）。
- **代價**：leader 是單點——它掛了要選出新 leader（failover），這個過程本身就是個大坑（Ch 12 會挖）。所有寫入集中在一台，寫入不隨副本數擴展。
- Ch 12「主從複製」深入這條線。

### Multi-Leader（多主）

**多個節點都能接受寫入**，每個 leader 再把自己收到的寫入複製給其他 leader。常見於多資料中心：每個資料中心有一個 leader，本地寫本地的，再跨資料中心同步。

```
   writes ──> ┌────────┐  <──replicate──> ┌────────┐ <── writes
              │Leader A│                   │Leader B│
              │ (US)   │                   │ (Asia) │
              └────────┘                   └────────┘
```

- **好處**：寫入可以在本地完成（降延遲），跨資料中心的網路斷了各地還能各自寫（可用性高）。
- **代價**：**寫寫衝突（write-write conflict）**變成家常便飯——US 和 Asia 同時改了同一筆，複製過去發現兩邊都動了，誰對？沒有 leader 能仲裁，得靠衝突解決策略（Ch 14 的 CRDT、last-write-wins 等）。這是 multi-leader 最痛的地方。

### Leaderless（無主）

**沒有 leader，客戶端直接把寫入送給多個副本**（或透過一個協調者轉發），讀取也同時問多個副本、自己挑最新的。靠 quorum（法定人數）來保證讀寫有交集。Amazon Dynamo 和它的後裔（Cassandra、Riak）走這條路。

```
              ┌─────┐
   write ───> │  A  │
        ├────>│  B  │   寫給多個，等「夠多」個 ack 就算成功
        └────>│  C  │
   read  ├───>│  A  │   讀問多個，挑版本最新的（quorum 保證讀寫有交集）
         └───>│  B  │
```

- **好處**：沒有單點 leader，任何節點掛了系統照跑，可用性極高。
- **代價**：一致性要靠 quorum 數學（Ch 13）精算，且仍可能讀到舊值或需要在讀取時修復（read repair）；衝突同樣要解。
- Ch 13「Quorum 複製」和練習 B 專攻這條線。

三者放在一起看：

| 拓樸 | 誰能寫 | 寫寫衝突 | 主要用途 | 對應章節 |
|---|---|---|---|---|
| Single-leader | 只有 leader | 不會發生 | 一般資料庫主從 | Ch 12 |
| Multi-leader | 多個 leader | 常發生，要解 | 多資料中心 | Ch 12/14 |
| Leaderless | 任何副本 | 會發生，靠 quorum + 修復 | 高可用 KV（Dynamo 系） | Ch 13 |

一條主軸：**越往「多個地方能寫」走，可用性和在地延遲越好，但寫寫衝突越嚴重、一致性越難保證。** 這正是下一章一致性模型和 Ch 10 CAP 定理要量化的取捨。

## 底層機制：一筆寫入在 single-leader 系統裡的完整旅程

把抽象落到具體。一筆 `SET x = v2` 在一個非同步 single-leader 系統裡經過什麼：

```
 (1) client ── SET x=v2 ──> Leader
 (2) Leader 寫入本地 storage，x: v1 → v2
 (3) Leader 把這筆變更追加進「複製日誌」（replication log）
       replication log: [ ..., (SET x=v2, offset=1043) ]
 (4) Leader ── OK ──> client         ← 非同步：這裡就回了，不等 follower
 (5) 背景：Leader 把 log offset 1043 之後的變更串流給每個 follower
       Leader ── (SET x=v2, offset=1043) ──> Follower1
       Leader ── (SET x=v2, offset=1043) ──> Follower2
 (6) 每個 follower 依序套用（apply）這筆變更，x: v1 → v2
       follower 記住自己套到哪個 offset 了（replication offset）
 (7) 若某 follower 之前斷線落後了，重連後從自己記的 offset 續傳
       ── "我套到 1000，給我 1001 之後的" ──> Leader
```

幾個要點，都是後面章節的伏筆：

- **複製日誌（replication log）是複製的核心資料結構**。變更不是「直接同步狀態」，而是被記成一串**有序的變更紀錄**，副本靠**重放（replay）這串日誌**來追上主節點。這個「有序日誌 + 重放」的模式會在 Ch 21 Raft 的 log replication、Ch 40 Kafka（日誌本身就是系統核心）反覆出現。**把「複製 = 傳一串有序的變更 log」這個心智圖像刻進去。**
- **replication offset（複製位移）讓落後的副本能續傳**，不用從頭複製整份資料。這是「副本斷線重連後怎麼追上」的關鍵。
- **步驟 (4) 在步驟 (5)(6) 之前，就是非同步複製的「資料遺失窗口」**——client 拿到 OK 了，但 follower 還沒 apply。這段窗口內 leader 崩潰，這筆寫入就懸了。

同步複製只是把步驟 (4) 挪到 (6) 之後（等 follower ack 才回 client），代價是 client 要多等一個 leader↔follower 的 RTT。整個取捨就濃縮在「(4) 放在哪」這一個位置上。

## Failover：複製最危險的時刻

複製的整個賣點是容錯——leader 掛了，副本頂上。但「頂上」這個動作（failover，故障轉移）本身是複製系統裡最容易出大事的環節。值得單獨拆開看，因為 Ch 12 會深入、而 Part 3 的共識演算法有一半力氣就是在把 failover 做對。

一次 single-leader 的 failover 要做三件事，每一件都是坑：

```
 (1) 偵測：確認舊 leader 真的掛了
       └─ 但你「偵測不到」它掛了 vs 只是慢/網路卡了一下！（Ch 2/16 的母題）
          等太久 → 服務中斷久；判太快 → 把只是慢的 leader 當死的，造成兩個 leader
 (2) 選新 leader：從 follower 裡挑一個提升
       └─ 挑哪個？挑「日誌最新」的，否則會丟資料（挑到落後的 follower = 丟掉舊
          leader 已提交但只在它身上的寫入）
 (3) 重新導向：讓所有 client 和 follower 改認新 leader
       └─ 舊 leader 若「詐屍」回來（其實沒真死，只是卡了一下）還以為自己是
          leader，繼續接受寫入 → split-brain（腦裂），兩個 leader 各寫各的
```

**split-brain（腦裂）是 failover 最惡名昭彰的失敗**：偵測誤判導致系統裡同時存在兩個都認為自己是 leader 的節點，各自接受寫入、各自複製，資料徹底分歧，事後幾乎無法自動合併。它的根源就是 Ch 2 會嚴謹講的那件事——**在非同步網路裡，你無法區分「一個節點死了」和「一個節點只是很慢/暫時失聯」**。你以為它死了、選了新 leader，結果它沒死。

```
         偵測誤判：以為 leader A 死了，提升 B
    ┌─────────┐                    ┌─────────┐
    │ Leader A│ ← 其實只是網路卡了  │ Leader B│ ← 新選出的
    │ (詐屍)  │   一下，又回來了    │         │
    └─────────┘                    └─────────┘
    client X 還連著 A →寫 A     client Y 連上 B →寫 B
         兩個 leader 同時收寫入 = split-brain，資料分歧無法合併
```

業界防 split-brain 的手段（都是 Part 3 的伏筆）：**多數決（quorum）**——規定「只有拿到多數節點認可的才是合法 leader」，這樣不可能同時有兩個 leader 拿到多數（多數之間必有交集，Ch 13）；**fencing（柵欄）**——給每任 leader 一個單調遞增的任期號（term / epoch），儲存層拒絕舊任期的寫入，詐屍的舊 leader 因為任期過期而被擋掉（Raft 的 term、ZooKeeper 的 epoch 都是這個）。

記住這個結論：**複製給你容錯，但容錯的兌現時刻（failover）本身是最危險的**。「多副本」不會自動等於「更可靠」，把 failover 做對才會（踩雷 #2 講的就是這個）。Raft 存在的一大理由就是把這三步做成一個有正確性證明的協定。

## 對比與取捨：複製到底換來什麼、賠上什麼

| 維度 | 不複製（單機） | 複製 |
|---|---|---|
| 容錯 | 無，機器死=服務死 | 有，副本頂上 |
| 讀吞吐 | 單機上限 | 隨副本數擴展 |
| 讀延遲 | 固定（就那台的距離） | 可就近讀，降低 |
| 寫延遲 | 低（不用協調） | 同步複製會升高 |
| 一致性 | 天然一致（只有一份） | 出現不一致問題 |
| 系統複雜度 | 低 | 高（要處理傳播、衝突、failover） |

這張表的重點是最後兩列：**複製把「一致性」和「複雜度」從『不存在的問題』變成『整個 Part 2–4 都在對付的問題』。** 你不是白白得到容錯和擴展的——你用「系統從此要面對副本分歧」這個代價換來的。工程上沒有「既要副本又要像單機一樣簡單」的選項，這是複製的原罪。

## 踩雷集錦

1. **「複製 = 備份」——錯。** 備份（backup）是把資料在某個時間點拷貝一份存起來，用於災難還原，通常是離線、滯後的。複製是**持續、線上**地維護多個活躍副本，副本隨時能服務讀寫。備份救的是「資料被誤刪/損毀」，複製救的是「一台機器當機服務不中斷」——兩者都要有，不能互相取代。用複製當備份，等於沒備份：一筆錯誤的 `DELETE` 會被複製到所有副本，「多份一模一樣的錯資料」救不了你。

2. **「多副本 = 更可靠」不是無條件成立。** 複製提升的是「單一節點故障」的容錯，但它同時**引入了新的故障模式**：副本間的網路可能分區、副本可能分歧、failover 可能選錯 leader 或選出兩個 leader（split-brain）。設計不當的複製系統，可用性可能**比單機還差**——因為你多了一堆會壞的協調邏輯。可靠性來自「正確的複製協定」，不是「副本數量」。

3. **「非同步複製反正資料最終會到，沒差」——差很多。** 「最終會到」在主節點崩潰前確實成立，但**崩潰正是你需要複製的時刻**。已回覆客戶端「成功」、卻還沒傳到副本的那些寫入，會隨崩潰的主節點一起消失。客戶端手上有「成功」回執、系統裡查無此筆——這是非同步複製的固有風險，不是 bug。你可以接受這個風險（很多場景可以），但不能假裝它不存在。

4. **把讀取全打到 follower 以為就均衡了——會讀到過時資料。** 非同步複製下 follower 落後於 leader，一個常見的坑是：使用者剛在 leader 上寫了一筆（改了暱稱），馬上重新整理頁面、讀取被導到還沒同步的 follower，看到**自己剛改的東西沒生效**（讀到舊暱稱）。這叫違反「read-your-writes（讀自己的寫）」一致性。要嘛把「剛寫過的使用者」的讀導回 leader，要嘛用更強的一致性保證——這正是下一章一致性模型要處理的。

5. **以為選了 single-leader 就沒有一致性問題。** single-leader 消除的是**寫寫衝突**（只有一個寫入點），但**沒消除讀到舊值**（follower 落後）、也沒消除 **failover 時的資料遺失/split-brain**。「只有一個 leader」是個乾淨的寫入模型，不是一致性的免死金牌。真正的一致性保證要看你怎麼做讀取路由、怎麼做 failover——這是 Ch 12 的重頭戲。

## 進階：再往深一層

- **鏈式複製（chain replication）**：副本排成一條鏈，寫入從鏈頭（head）進、沿鏈傳到鏈尾（tail），讀取只從鏈尾出。這樣能同時拿到強一致（tail 看到的一定是完整複製過的）和高吞吐（讀寫落在不同節點）。是 single-leader 的一個漂亮變體，值得讀原論文（van Renesse & Schneider, OSDI 2004）。

- **複製到底複製「什麼」**：這一章講的是**基於變更日誌的邏輯複製（logical / statement-based 或 row-based）**。另一種是**基於儲存引擎的物理複製**，例如 PostgreSQL 的 WAL（write-ahead log）串流複製——直接把儲存層的位元組級變更傳給副本。物理複製更緊耦合、效率高，但副本必須用一模一樣的儲存引擎版本。邏輯 vs 物理複製的取捨是資料庫複製的一大主題，DDIA 第 5 章講得很清楚。

- **複製與共識的關係**：這一章的「同步複製 + 等多數確認」再往前一步，就是共識（consensus）。共識協定（Paxos、Raft）本質上是「一群副本對『下一筆要 apply 的變更是什麼』達成一致」的複製協定，額外保證了即使 leader 崩潰、發生分區，副本們也不會分歧、不會丟已提交的寫入。你可以把 Part 3 整個共識 Part 看成「把複製做到極致正確」——這一章埋的每個坑（failover 選錯、非同步遺失、split-brain），Raft 都用嚴謹的協定堵掉。**複製是問題，共識是（其中一種）答案。**

## 本章重點整理

- 複製的三個理由：**容錯**（節點會死，副本頂上）、**降延遲**（就近讀）、**增吞吐**（分散讀）。容錯是最不可退讓的。
- 複製的原罪：**一旦有多份副本，就會不一致**——這是 Part 2–4 所有一致性麻煩的源頭。複製把一致性從「不存在的問題」變成「核心問題」。
- 同步 vs 非同步複製的取捨核心：**同步用延遲換資料安全，非同步用資料安全換延遲**。實務常用「等多數不等全部」的半同步折衷。
- 三種拓樸：**single-leader**（只有 leader 能寫，無寫寫衝突，最常用）、**multi-leader**（多寫入點，寫寫衝突嚴重）、**leaderless**（任何副本能寫，靠 quorum）。越往多寫入點走，可用性越好但一致性越難。
- 複製的核心資料結構是**有序的複製日誌 + 副本重放**，落後的副本靠 **offset 續傳**——這個模式在 Raft、Kafka 反覆出現。
- 別把複製當備份；別以為副本多就更可靠；別假裝非同步的遺失窗口不存在。
