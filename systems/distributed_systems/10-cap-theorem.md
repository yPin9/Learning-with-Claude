# Ch 10 — CAP 定理

> **目標**：把 CAP 定理正式陳述清楚，然後花大力氣**破除它被誤讀二十年的「三選二」神話**——真相是 P（分區）是分散式系統的既定前提，真正的抉擇是**分區發生時選 C 還是選 A**。我們用 Ch 0 的 `dsim` 寫一個真的會跑的 mini 演示：同一個分區下，一邊選一致（拒絕服務）、一邊選可用（回舊值），親眼看到取捨。最後接上 Brewer 本人「12 年後」的澄清與 PACELC。

> **環境**：Go 1.18.1, WSL2 / Linux x86-64。

上一章我們量化了一致性光譜，並在結尾埋了個伏筆：**linearizability 在網路分區時，會逼你在「回應但可能給錯」和「拒絕服務」之間二選一。** 這一章就是把那個「二選一」升格成一條定理，並且把圍繞它的無數誤解一次清乾淨。CAP 大概是分散式系統裡「被引用最多、被理解最少」的一句話——幾乎每個人都聽過「CAP 三選二」，而幾乎每個人聽到的都是錯的。

## 為什麼需要這個？

2000 年，Eric Brewer 在 PODC 會議的 keynote 提出一個猜想：一個分散式資料系統，**Consistency（一致性）、Availability（可用性）、Partition tolerance（分區容錯）三者不可兼得，最多同時滿足兩個**。2002 年 Gilbert 和 Lynch 把它形式化並證明，CAP 從「猜想」變成「定理」。

這條定理之所以重要，是因為它擊碎了一個很誘人的幻想：**「我能不能做一個既永遠一致、又永遠可用、還扛得住網路故障的系統？」** CAP 的答案是冷冰冰的「不能」。這不是工程能力不夠、不是還沒發明對的演算法——它是個**不可能結果（impossibility result）**，像光速上限一樣，是這個宇宙的規則。你設計任何跨網路的複製系統，都繞不過它。

但 CAP 真正的價值，不在那句朗朗上口的「三選二」——那句話其實是**錯的、有害的**，誤導了整個產業近二十年。它的價值在於逼你面對一個具體、無可迴避的工程決策：**當你的資料中心之間網路斷了（這一定會發生），你的系統該繼續服務還是該停下來？** 這一章要做的，就是把你從「三選二」的錯誤心智模型裡拉出來，換上正確的那個。

## 先建立直覺：三個字母到底指什麼

先把三個字母的**精確**意思釘死，因為誤解大多源於望文生義。

```
┌─────────────────────────────────────────────────────────────┐
│ C = Consistency（一致性）                                    │
│   這裡特指 linearizability（線性一致，Ch 9 那個最強的）。    │
│   不是 ACID 的 C，不是「最終一致」的一致。                   │
│   意思：系統表現得像只有一份資料，讀到的一定是最近寫的。    │
├─────────────────────────────────────────────────────────────┤
│ A = Availability（可用性）                                   │
│   每個「打到還活著的節點」的請求，都必須在有限時間內        │
│   收到一個「非錯誤」的回覆。                                 │
│   注意：回覆「錯誤」或「請稍後再試」或「超時」= 不可用。   │
├─────────────────────────────────────────────────────────────┤
│ P = Partition tolerance（分區容錯）                          │
│   系統在「網路把節點切成互不相通的孤島」時仍能運作。        │
│   注意：這不是「你選不選」的能力，是「網路會不會斷」的事實。│
└─────────────────────────────────────────────────────────────┘
```

三個字母裡，**P 和另外兩個根本不是同一種東西**——這是所有誤解的根源。C 和 A 是「你希望系統具備的性質」，是**你能設計的目標**。而 P 描述的是**環境會不會發生的事件**（網路分區）——網路斷不斷，由不得你。

```
      C、A：你想要的「系統性質」（你能選）
      P：   環境強加的「故障事實」（你不能選，只能面對）

      ┌────────────┐        ┌────────────┐
      │  DC (US)   │◄──╳──►│  DC (Asia) │   ← 網路分區 P：兩邊斷了
      │  node A    │  斷線  │  node B    │     這件事「會發生」，不由你決定
      └────────────┘        └────────────┘
```

一旦你接受「P 是既定事實不是選項」，「三選二」就自動崩塌了——你根本沒有「不選 P」的自由。

## 正式陳述

Gilbert-Lynch（2002）的形式化版本，講白話：

> **在一個會發生網路分區的非同步網路裡，一個複製的資料系統無法同時保證 linearizable consistency（C）與 availability（A）。**

再精確一點的因果鏈：**當網路分區發生時**，被分區隔開的兩邊節點無法互相通訊。此時系統面對一個讀寫請求，只有兩條路：

1. **維持一致（選 C）**：如果無法確認自己的值是最新的（聯絡不到分區另一邊），就**拒絕服務**——回錯誤或阻塞。這保住了 linearizability（絕不回可能過時的值），但**犧牲了可用性**（有請求沒被正常回應）。

2. **維持可用（選 A）**：**照樣回應**——回自己本地能給的值。這保住了可用性（每個請求都有非錯誤回覆），但因為兩邊各寫各的、看不到對方，**犧牲了一致性**（可能回過時的值，或兩邊分歧）。

```
             網路分區發生（P 已成事實）
                       │
          某節點聯絡不到分區另一邊，收到一個請求
                       │
           ┌───────────┴───────────┐
           ▼                       ▼
      選 C（一致）             選 A（可用）
      「我不確定我是最新的      「我照樣回我本地的值」
       → 拒絕/阻塞」            → 保住可用
      保住一致，失去可用        失去一致（可能回舊值/分歧）
           │                       │
      CP 系統                  AP 系統
   (etcd, ZooKeeper,        (Dynamo, Cassandra,
    Spanner, HBase)          Riak, 預設模式)
```

**這才是 CAP 的真正內容**：它不是「從 C/A/P 裡挑兩個」，而是「**既然 P 一定會發生，你必須事先決定：分區期間，我要當 CP 系統還是 AP 系統。**」

## 破除「三選二」：CA 系統根本不存在

「三選二」這個說法暗示有三種選擇：CA、CP、AP。我們來看為什麼 **CA 是個幻覺**。

所謂「CA 系統」是「放棄 P、保住 C 和 A」。但「放棄 P」是什麼意思？P 是「網路會不會分區」——你**無法讓網路保證不分區**。網路一定會斷（光纖被挖斷、交換機當機、GC 停頓長到像斷線、防火牆規則出錯）。所以「放棄 P」在實務上只有一個意思：**你假裝分區不會發生，於是根本沒為它設計。**

那當分區真的發生時（它一定會），一個「CA 系統」會怎樣？它沒有「分區時該選 C 還是 A」的邏輯——所以它會**同時失去 C 和 A**：兩邊的節點各自繼續服務（以為對方還在），資料分歧（失去 C），而當它們試圖協調卻聯絡不到對方時又會卡住或報錯（失去 A）。**號稱 CA，實際上分區一來 C、A 全丟。**

```
   「CA 系統」的真相：
                     分區前              分區時
   宣稱:  C ✓  A ✓  P ✗    ───────►   C ✗  A ✗   （兩個都丟！）
                                       因為它根本沒為分區設計，
                                       split-brain：兩邊各寫各的
```

所以正確的圖不是一個「三選二」的三角，而是：

```
       ┌──────────────────────────────────────────┐
       │  P 是前提（分區一定會發生，不是選項）     │
       │                                          │
       │  真正的選擇只有兩個：                     │
       │                                          │
       │     CP ──────────────────────── AP       │
       │  分區時選一致              分區時選可用    │
       │  （拒絕服務保 C）          （回舊值保 A）  │
       │                                          │
       │  「CA」不在這條線上——它是「沒考慮分區」  │
       │   的委婉說法，分區一來就 C、A 皆失。       │
       └──────────────────────────────────────────┘
```

**唯一「合法」宣稱 CA 的，是根本不跨網路的系統**——單機資料庫。單機沒有分區可言（只有一個節點，沒有網路要斷），它天然 C+A。但那也就不是分散式系統了，CAP 對它根本不適用。**只要你是「多節點 + 網路」，P 就在桌上，你只能在 CP 和 AP 之間選。**

## 底層機制：用 dsim 真跑一次 CAP 抉擇

光講定義沒有痛感。我們用 Ch 0 的模擬器，把 CAP 的抉擇**跑出來給你看**。

> 若對 `dsim` 的 `Partition` / `Heal` / `Send` / `Run` 不熟，回看 [Ch 0](./00-environment-setup.md)。

設計：一個複製到 3 個節點（0、1、2）的暫存器（register），節點 0 是協調者。同一份程式碼，只切換一個旋鈕 `mode`：

- **CP 模式**：讀取前檢查「我還連得到多數節點嗎」。連不到多數 → **拒絕服務**（保 C）。
- **AP 模式**：不管連不連得到，**照樣回本地值**（保 A，可能是舊值）。

然後製造分區 `{0,1} | {2}`：把節點 2 孤立，在多數側寫一個新值 `v2`，再從兩邊讀，看兩種模式各回什麼。核心程式碼（完整檔在 `code/ch10/`）：

```go
// read：CP 模式下若連不到多數就拒絕；AP 模式下直接回本地值（可能過時）。
func (r *register) read(reachablePeers int) (string, bool) {
	total := 1 + len(r.peers)     // 叢集大小 = 3
	visible := 1 + reachablePeers // 自己 + 還連得到的 peer
	haveMajority := visible*2 > total
	if r.mode == CP && !haveMajority {
		return "", false // 拒絕：無法保證讀到最新，寧可不回（犧牲 A，保 C）
	}
	return r.val, true // AP：或有多數的 CP，照回（AP 可能回舊值）
}
```

分區注入與寫入（節錄）：

```go
net.Partition([]NodeID{0, 1}, []NodeID{2}) // 節點 2 被孤立
n0.clientWrite("v2")                        // 只有 0、1 收得到 v2
net.Run(20)
// 多數側 n0：連得到 n1 → visible=2 > total/2 → 有多數
// 少數側 n2：連不到任何 peer → visible=1 → 沒有多數
vMaj, okMaj := n0.read(1) // 多數側讀
vMin, okMin := n2.read(0) // 少數側讀
```

真跑（WSL, Go 1.18.1），四個階段的**真實輸出**：

```
=== 階段 0：健康叢集，寫入 x=v1，全連通 ===
寫入 v1 後：n0.ver=1 n1.val="v1" n2.val="v1"  協調者收到 3 個 ack（含自己）
此時從 n0 讀取（連得到 2 個 peer）：val="v1" ok=true
------------------------------------------------------------
=== 階段 1：CP 系統 —— 分區 {0,1} | {2}，寫 x=v2，再從兩邊讀 ===
分區前：n0="v1" n1="v1" n2="v1"
分區後寫 v2：n0="v2" n1="v2" n2="v1"（n2 被孤立，沒收到，還是 v1）
CP 多數側 n0 讀：val="v2" ok=true  → 回最新值
CP 少數側 n2 讀：val="" ok=false  → 拒絕服務（犧牲 A，換 C）
------------------------------------------------------------
=== 階段 2：AP 系統 —— 同樣分區，少數側照樣回答 ===
分區後寫 v2：n0="v2" n1="v2" n2="v1"
AP 多數側 n0 讀：val="v2" ok=true
AP 少數側 n2 讀：val="v1" ok=true  → 照樣回答，但回的是舊值 v1（犧牲 C，換 A）
→ 此刻系統對外「不一致」：問 n0 得 v2，問 n2 得 v1
------------------------------------------------------------
=== 階段 3：Heal —— 分區修復，AP 系統最終收斂 ===
修復前：n0="v2" n2="v1"（分歧）
修復後：n0="v2" n1="v2" n2="v2"  Delivered=10 Dropped=1
→ 最終一致（eventual consistency）：收斂到 v2，但中間那段窗口讀得到舊值
```

把這四段讀懂，CAP 就活了：

- **階段 0**：健康時（無分區），C 和 A 都有——多數確認拿得到，讀到最新值。CAP 只在**分區時**才逼你選；沒分區時你兩個都要得到。這是下一章 PACELC 的伏筆。
- **階段 1（CP）**：分區後，多數側（0,1）照常給最新值 `v2`；**少數側 n2 的讀取被拒絕（`ok=false`）**——它聯絡不到多數，無法確認自己是最新的，於是為了保住一致性，**寧可不服務**。這就是「選 C 犧牲 A」。真實系統如 etcd、ZooKeeper 就是這樣：少數派分區的那些節點會拒絕寫入、拒絕線性一致讀。
- **階段 2（AP）**：同樣的分區，少數側 n2 **照樣回答**（`ok=true`），但回的是**舊值 `v1`**——它沒收到 `v2`。此刻系統對外自相矛盾：問 0 得 `v2`，問 2 得 `v1`。這就是「選 A 犧牲 C」。Dynamo、Cassandra 預設走這條。
- **階段 3（Heal）**：分區修復、協調者重送最新值後，所有副本收斂到 `v2`。這就是**最終一致（Ch 9）**——分區期間的分歧最終被抹平，但**中間那段窗口確實讀得到舊值**，那段不一致是真實發生過的、AP 系統為可用性付的帳。

`Dropped=1` 是分區期間那則從 0 送往被孤立的 2、在飛行途中被分區攔下的訊息（Ch 0 的「送達時再檢查一次 reachable」）——模擬器忠實地把「分區隔離」演了出來。

> **一個模擬器的小坑，順手記下**：`net.Run(maxSteps)` 的 `maxSteps` 是**絕對**邏輯時刻，不是「再跑幾步」。我第一版寫成連續兩個 `net.Run(10)`，第二個完全沒推進時間（因為 `now` 已經是 10、`Run` 的迴圈是 `while now < maxSteps`），害我看到「同分區的 n1 竟然沒收到 v2」的假象，追了半天才發現是測試碼的 bug 不是模擬器的。修法是第二次給 `Run(20)`。這正是 Ch 0 踩雷 #5「maxSteps 給太小/沒推進」的活教材——**分散式測試裡「我以為在測 A、其實測到自己的計時 bug」的陷阱無所不在**。

## 一個讓 CAP 有痛感的真實場景：兩台 ATM

抽象定義配上一個具體到會痛的場景，CAP 才真正入腦。

你的銀行帳戶餘額 `$100`，複製在兩個資料中心（DC1、DC2）。你人在台北、你的共犯在紐約，你們約好**同時**去提款機領錢：你在 DC1 覆蓋的 ATM 領 `$100`，你共犯在 DC2 覆蓋的 ATM 也領 `$100`。就在這一刻，DC1↔DC2 的網路斷了（分區）。

```
        餘額 $100，複製在兩地，此刻網路分區
   ┌─────────────┐          ┌─────────────┐
   │    DC1      │◄──╳────►│    DC2      │
   │  餘額 $100  │   斷線   │  餘額 $100  │
   └─────────────┘          └─────────────┘
        │                        │
   台北 ATM：領 $100         紐約 ATM：領 $100
   「餘額夠嗎?」             「餘額夠嗎?」
```

兩台 ATM 都問「餘額夠不夠領 $100」，但它們**聯絡不到對方**，不知道對方正在領同一筆錢。CAP 逼你選：

- **選 A（可用，AP）**：兩台 ATM 都照樣吐錢——各自看本地的 `$100`，都判斷「夠」，都吐出 `$100`。結果：你們**共領了 $200**，但帳戶只有 $100。銀行倒貼 $100。等網路恢復，兩地餘額分歧（一邊記 $0、一邊記 $0，但實際被領走 $200），對帳對不平。**這就是選 A 犧牲 C 的代價——在金錢上，這個代價可能是致命的。**

- **選 C（一致，CP）**：ATM 發現聯絡不到另一個 DC、無法確認全域餘額，於是**拒絕出鈔**——螢幕顯示「系統忙碌，請稍後再試」。你們兩個都領不到錢（可用性沒了），但銀行的帳絕不會錯（一致性保住了）。等網路恢復，餘額還是正確的 $100。**這就是選 C 犧牲 A 的代價——服務暫時中斷，但帳目正確。**

哪個對？**看業務**。銀行餘額該選 CP——寧可讓你暫時領不到錢，也不能讓帳戶被領成負的。但如果這是「社群貼文的按讚數」而不是餘額呢？兩個 DC 各自 +1、事後合併成 +2，暫時對不上根本沒人在乎——那就該選 AP，別為了按讚數精確而讓使用者按讚時轉圈。

這個場景也戳破一個常見幻想：「我兩個都要，讓 ATM 先確認再吐錢不就好了？」——確認要聯絡對方，但**網路正是斷的**，確認不了。你只能選「不確認就吐（AP）」或「確認不了就不吐（CP）」。**CAP 的殘酷正在於：它剝奪了你「等網路好了再說」的選項，因為請求現在就來了，你現在就得答。**

## Brewer「12 年後」的澄清

2012 年，Brewer 本人寫了一篇 "CAP Twelve Years Later: How the 'Rules' Have Changed"，親自修正被誤讀的地方。重點：

1. **「三選二」是誤導。** Brewer 直說：「2-of-3 這個表述有誤導性。」因為 P 幾乎從不能被放棄，實際上你只在「C 和 A 之間、且只在分區期間」做取捨。他後悔當年那個過度簡化的講法。

2. **C 和 A 不是非黑即白，是可以細粒度、動態權衡的。** 系統可以「大部分操作選一致，某些操作選可用」；可以「這個資料項強一致，那個最終一致」；可以「分區偵測到後才切換策略」。CAP 不是把整個系統一刀切成 CP 或 AP。

3. **分區是罕見的，所以「沒分區時」的行為才是系統平時的主戰場。** 這句話直接催生了 PACELC（下一章）：CAP 只講了分區時（P）怎麼辦，卻沒講**平時（沒分區時）**的取捨。而系統 99.9% 的時間都在「沒分區」的狀態下運行——那時你在權衡的是**延遲 vs 一致性**，這是 CAP 完全沒涵蓋的一整塊。

4. **分區的「範圍」和「恢復」是可設計的。** 好的系統會：偵測分區進入「分區模式」→ 限制某些操作 → 分區恢復後執行**補償/合併**（reconcile），把分區期間的分歧收拾乾淨（就像我們演示的階段 3，只是真實系統的合併邏輯複雜得多）。

Brewer 這篇的精神一句話：**別把 CAP 當成一個要你二選二的枷鎖，把它當成一個提醒你「為分區這件必然會發生的事，事先想清楚策略」的框架。**

## 對比與取捨

| | CP 系統 | AP 系統 |
|---|---|---|
| 分區時，少數側 | 拒絕服務（保一致） | 照常服務（可能回舊值） |
| 分區時，犧牲的是 | 可用性（A） | 一致性（C） |
| 讀到的值 | 永遠最新（或拒絕） | 可能過時，最終收斂 |
| 分區恢復後 | 本來就一致，無需合併 | 需要合併/修復分歧（read repair、anti-entropy） |
| 適合場景 | 不能出錯的真相：配置、鎖、餘額、選主 | 高可用優先、能容忍暫時不一致：購物車、動態、快取 |
| 代表系統 | etcd, ZooKeeper, HBase, Spanner*, 大多數用共識的系統 | Dynamo, Cassandra, Riak, Voldemort |

（*Spanner 用 TrueTime + Paxos 提供強一致，分區時少數派不可寫，屬 CP；它靠極高品質的網路和硬體時鐘把「分區」壓到極罕見，讓 CP 的可用性代價在實務上小到可忽略——但定理上它仍是 CP。Ch 39 專講。）

沒有「CP 比 AP 好」或反過來——**取決於你的資料能不能容忍暫時不一致**。銀行餘額當然要 CP（不能因為分區就讓你在兩地各領一次錢）；社群按讚數大可 AP（數字暫時對不上沒人會死）。**同一家公司的不同子系統，常常一部分 CP、一部分 AP。**

## 踩雷集錦

1. **「CAP 是三選二」——這是最大的錯，整章都在拆它。** 正確版本：P 是分散式系統的**前提**（分區一定會發生），你**沒有「不選 P」的自由**；真正的抉擇是**分區發生時**在 C 和 A 之間二選一。你不是從三個裡挑兩個，你是被迫接受 P，然後在 CP 和 AP 之間選一個。

2. **「我的系統是 CA」——不存在（除非它是單機）。** 「CA」是「沒為分區設計」的委婉說法。多節點系統宣稱 CA，只代表它在分區時會**同時**失去 C 和 A（split-brain 分歧 + 協調卡死）。只要你跨網路複製，P 就在桌上，你不是 CP 就是 AP。聽到有人說產品是「CA 系統」，追問一句「那分區時怎麼辦」，通常會發現他們沒想過。

3. **把 CAP 的 C 當成 ACID 的 C 或「最終一致」的一致。** CAP 的 C 特指 **linearizability**（Ch 9 最強那級）。ACID 的 C（consistency）指「交易不違反完整性約束」，是完全不同的東西。而「最終一致」在 CAP 框架裡屬於 **AP**（放棄了 linearizable C 換取可用）。三個「一致」意思都不同，別混。

4. **以為 CAP 說「平時也只能二選一」。** CAP **只**談分區時。沒分區時，C 和 A 你**兩個都能要**（看我們演示的階段 0）。CAP 完全沒說「平時」的取捨——那是 PACELC 補的（延遲 vs 一致性）。把 CAP 套到「平時」是過度引用，很多「因為 CAP 所以強一致系統一定慢」的說法其實混淆了 CAP（分區時）和 PACELC 的 ELC（平時延遲）。

5. **以為選了 CP 就「永遠可用性差」、選了 AP 就「永遠不一致」。** 兩者的犧牲都**只在分區期間**發生。CP 系統平時可用性可以非常高（分區罕見）；AP 系統平時也可以很一致（複製延遲很小）。CAP 描述的是「分區這個罕見事件降臨時」的行為，不是系統的日常表現。把「分區時的取捨」誤當成「日常的性能標籤」，是很多選型爭論的根源。

## 進階：再往深一層

- **CAP 是「非同步網路」下的結果，同步網路呢？** Gilbert-Lynch 的證明假設**非同步網路**（訊息延遲無上界，無法區分「慢」和「斷」）。在一個能保證訊息延遲有上界的**同步網路**裡，理論上可以用超時來可靠偵測分區，取捨會鬆一點。但真實網路是非同步的（你永遠分不清對方是掛了還是只是很慢，這正是 Ch 2/16 FLP 的核心），所以 CAP 的悲觀結論成立。**「無法區分慢與斷」是分散式系統一切困難的母題**，CAP、FLP、failure detector 都繞著它轉。

- **CAP 的 C 和 A 都是「極端」定義，真實系統活在中間。** 定理裡 C = 完美 linearizable、A = 每個請求都有非錯誤回覆——都是全有全無。真實系統有大量中間地帶：**sticky availability**（只保證「一直連同一個節點」的客戶端可用）、**bounded staleness**（保證讀到的值最多舊 T 秒）、**probabilistic**（quorum 讀寫，一致性是機率性的，Ch 13）。CAP 給的是理論邊界，工程在邊界內找甜蜜點。Abadi 的 PACELC 和一整套「可調一致性」就是在填這個中間地帶。

- **CAP 常被誤用來「證明」不該做強一致——這是懶惰。** 有一派工程文化拿 CAP 當「所以我們只能最終一致啦」的擋箭牌。但 Spanner（Ch 39）證明了：靠夠好的網路工程（多路徑、快速重路由）把分區壓到極罕見，加上 TrueTime，你完全可以做全球強一致（CP）而可用性依然有五個九。CAP 沒說「別做強一致」，它只說「分區時強一致要付可用性的帳」——而你可以透過工程把「分區」這個事件變得極其罕見，讓那筆帳小到可忽略。**CAP 是取捨的框架，不是放棄一致性的許可證。**

- **和 Ch 9 的接續**：CAP 的 C 就是 Ch 9 的 linearizability。把兩章串起來看：Ch 9 說「強一致要多一趟到多數節點的協調」，CAP 說「分區時那趟協調到不了多數，於是你得選：拒絕（CP）還是不協調就回（AP）」。CAP 本質上是**「強一致的協調成本」在最壞情況（分區）下的必然後果**。理解了 Ch 9 的協調代價，CAP 就是它的一個推論。

## 本章重點整理

- CAP 三字母：**C** = linearizability（不是 ACID 的 C）、**A** = 每個請求有限時間內得到非錯誤回覆、**P** = 網路分區時仍運作。
- **「三選二」是錯的、有害的。** P 是**前提**（分區一定發生），不是選項。真正的抉擇是：**分區發生時，在 C 和 A 之間二選一** → CP 或 AP。
- **「CA 系統」不存在**（除非單機）。號稱 CA 的多節點系統，只是沒為分區設計，分區一來 C、A 皆失（split-brain）。
- **CP**：分區時少數側拒絕服務、保一致（etcd、ZooKeeper、Spanner）。**AP**：分區時照常服務、可能回舊值、事後合併（Dynamo、Cassandra）。
- dsim 演示真跑驗證：同一分區下，CP 少數側 `ok=false`（拒絕），AP 少數側回舊值 `v1`（vs 多數側 `v2`），heal 後收斂到 `v2`。取捨是真的，不是比喻。
- Brewer「12 年後」的澄清：三選二誤導、C/A 可細粒度動態權衡、分區罕見所以「沒分區時」才是主戰場（→ PACELC）、分區恢復要做合併。
- CAP **只**談分區時；沒分區時 C、A 兩者都能要。平時的「延遲 vs 一致性」取捨要靠下一章的 PACELC。
