# Ch 45 — 設計陷阱與反模式

> **目標**：把整門課的血淚濃縮成一份可貼在牆上的清單。這一章不教新東西——它是全課精華的收束。列出分散式系統一再重演、幾乎每個團隊都踩過的反模式（anti-pattern），每一條給「反模式 → 為什麼錯 → 正確做法」，並連回它對應的章。最後給一份「設計分散式系統的檢查清單」，讓你未來動手前有個 checklist 對照。

## 為什麼需要這個？

分散式系統的錯誤有一個殘酷的性質：**它們是重複的**。同一批陷阱，從 2000 年代早期的 MongoDB、到 2010 年代的一票 NoSQL、到今天某個新創的微服務架構，一再地被踩。Jepsen（Ch 43）逐一處刑真實資料庫時，抓到的違反類型翻來覆去就那幾種——分區下丟寫入、腦裂雙寫、時鐘偏移造成的資料錯亂。

為什麼會重複？因為分散式系統的直覺陷阱太反人性。我們的大腦是在「單機、順序、可靠」的世界裡長大的——你按下儲存，資料就存了；你呼叫函式，它就回傳了；時間就是時間，往前流。這些在分散式世界**全部不成立**，但直覺會不斷把你拉回那個舒適的假設。

這一章存在的意義，是給你一份「反直覺清單」。你未來設計系統踩到某個抉擇點時，這份清單會像一個警報——「等等，這是不是那個反模式？」。它不會幫你想出方案，但會幫你**別掉進已知的坑**。

每一條反模式後面都有一整章的推導撐著。這章是索引，不是替代——看到某條有感覺的，回去讀對應章。

## 先建立直覺

所有分散式反模式，追根究柢都源自對**同一批殘酷事實**的否認：

```
   單機世界的舒適假設              分散式世界的殘酷現實
   ┌──────────────────┐        ┌────────────────────────────┐
   │ 網路可靠、零延遲    │  X      │ 網路會丟包、延遲、分區（八謬誤）│  Ch 1, 2
   │ 呼叫要嘛成功要嘛失敗│  X      │ 還有第三態：不知道（部分失敗）  │  Ch 1, 3
   │ 時間往前流、全域一致 │  X      │ 每台機器時鐘各異、會倒退       │  Ch 4
   │ 訊息剛好送一次      │  X      │ at-least / at-most，沒有剛好   │  Ch 3
   │ 我看到的就是全域狀態 │  X      │ 你只有局部視角、無全域快照     │  Ch 44
   │ 多就是好、拆就是強   │  X      │ 分散式的複雜度是超線性成長的   │  Ch 1
   └──────────────────┘        └────────────────────────────┘

   每一條反模式 = 某個團隊在某個地方，讓左邊的假設偷偷溜了進來
```

反模式的共通結構：**你在某處不自覺地用了單機直覺**。抓反模式的訓練，就是訓練你聞到「這裡有個單機假設」的味道。下面十條，是這種味道最濃、代價最慘的十個地方。

## 反模式清單

### 1. 假設網路可靠（八謬誤之首）

**反模式**：寫程式時預設「訊息會送到、會即時送到、只送一次」。RPC 呼叫寫得像本地函式呼叫，沒有 timeout、沒有重試、沒有「送不到怎麼辦」的分支。

**為什麼錯**：這是 Peter Deutsch「分散式運算八大謬誤」的第一條。網路**會**丟包、**會**延遲抖動、**會**分區。你的 RPC 在 99.9% 的時候像本地呼叫，但那 0.1% 會在最糟的時刻咬你——而且分散式系統跑久了，0.1% 每天發生無數次。把 RPC 當本地呼叫，等於把系統的正確性押注在網路永不出錯上。

**正確做法**：每個跨網路呼叫都當成**可能失敗、可能超時、可能重複**來設計。設 timeout、設重試（帶退避）、設冪等（見第 9 條）。把「網路不可靠」當公理，不是例外。

> 對應 [Ch 1 為什麼分散式這麼難](./01-why-distributed-is-hard.md)、[Ch 2 失敗與網路模型](./02-failure-and-network-models.md)。

### 2. 忽略部分失敗（partial failure）

**反模式**：把系統當成「要嘛全好、要嘛全壞」。一個操作要嘛成功、要嘛失敗，兩態思考。

**為什麼錯**：分散式系統的本質難點就是**第三態：不知道**。你送了個請求出去，沒收到回覆——是對方沒收到？收到了在處理？處理完了回覆在路上丟了？對方掛了？**你分不出來**。這個「不知道」不是暫時的、可以等清楚的——它可能永遠不會清楚（Ch 2 的失敗偵測不可能完美）。把系統當兩態設計，你就沒有處理這第三態的機制，而它一定會發生。

**正確做法**：接受「不知道」是一等公民。用 timeout 把「不知道」轉成「假設失敗然後重試 + 冪等」；用 quorum 讓「一部分節點掛了」不等於「系統掛了」；設計時永遠問「如果這一步的回覆丟了，我怎麼恢復？」。

> 對應 [Ch 1](./01-why-distributed-is-hard.md)、[Ch 3 RPC 與訊息語意](./03-rpc-and-message-semantics.md)。

### 3. 用實體時鐘排序事件

**反模式**：用 `timestamp` 決定「誰先誰後」——「這筆寫入的時間戳比較晚，所以它是最新的，用它覆蓋」（last-write-wins by wall clock）。

**為什麼錯**：不同機器的實體時鐘**不同步**，會漂移、會被 NTP 往回調、會跳。A 機的 12:00:05 可能實際上早於 B 機的 12:00:03。用時間戳排序，你會把因果關係搞反——把後發生的事當成先發生、用舊值覆蓋新值，靜默丟資料。這是無數「LWW 資料庫在時鐘偏移下丟寫入」事故的根源。

**正確做法**：排序**因果相關**的事件用**邏輯時鐘**（Lamport clock，Ch 5）或**向量時鐘**（vector clock，Ch 6），不是牆上時鐘。要偵測並發衝突用 vector clock。真的需要接近實體時間的全序（如 Spanner），得像 TrueTime 那樣**量化時鐘不確定性並等待它過去**（commit-wait），而不是假裝時鐘準。

> 對應 [Ch 4 實體時鐘的謊言](./04-physical-clocks.md)、[Ch 5](./05-lamport-clocks.md)、[Ch 6](./06-vector-clocks.md)、[Ch 39 Google Spanner](./39-google-spanner.md)。

### 4. 以為 exactly-once 交付存在

**反模式**：設計一個「訊息剛好送達一次」的系統，然後基於「每則訊息只會被處理一次」寫業務邏輯（例如「收到扣款訊息就扣一次錢」）。

**為什麼錯**：**網路層的 exactly-once 交付不存在**，這是 Ch 3 的核心。你只有兩個選擇：at-most-once（可能丟）或 at-least-once（可能重複）。任何「看起來像 exactly-once」的系統，底層都是 at-least-once + 去重/冪等。你若假設每則訊息只處理一次，那則重複的扣款訊息就會扣兩次錢。

**正確做法**：接受 at-least-once，然後用**冪等（idempotency）**把「處理多次」變得和「處理一次」等效——給每個操作一個唯一 id，處理前查「這個 id 處理過沒」。所謂的 exactly-once 語意（Kafka、Flink 有），是 at-least-once 交付 + 冪等處理 + 事務性去重的組合，不是網路真的只送一次。

> 對應 [Ch 3 RPC 與訊息語意](./03-rpc-and-message-semantics.md)、[Ch 40 Kafka](./40-kafka-log.md)。

### 5. 忽略腦裂（split-brain）

**反模式**：主從架構裡，「主掛了就把備升為主」——但沒有機制確保**同一時刻只有一個主**。網路分區時，舊主那側還自認是主、新主這側也開始服務，兩個主各寫各的。

**為什麼錯**：網路分區時，被隔離的舊主**不知道自己被隔離了**（它只看到「其他節點都沒回應」，這和「其他節點都掛了」長得一模一樣，見第 2 條）。如果升備為主的邏輯不夠嚴謹，你會得到兩個主——它們各自接受寫入、資料分岔，heal 之後無法合併（誰的寫入算數？）。這是分散式系統最經典、最致命的災難。

**正確做法**：任何「選主」都必須基於**多數決（quorum）**——只有拿到多數節點認可的節點才能當主，而多數只有一個（兩個不重疊的多數在 N 節點裡不可能同時存在）。這正是 Raft/Paxos 的核心保證（Ch 20-22）。少數派那側**無法**湊到多數，因此**無法**當主、無法 commit——它會卡住而非分岔。若用外部協調（如 ZooKeeper/etcd 做 leader lease），也要靠它的 quorum 保證唯一性。

> 對應 [Ch 12 主從複製](./12-primary-backup-replication.md)、[Ch 13 Quorum 複製](./13-quorum-replication.md)、[Ch 20 Raft Leader Election](./20-raft-leader-election.md)、[Ch 22 Raft Safety](./22-raft-safety.md)。這也正是 Ch 43 我們把 `majority()` 改壞一行、nemesis 立刻掃出 split-brain 的那個災難。

### 6. 過度分散式（能單機就別分散式）

**反模式**：一上來就上微服務、上分散式資料庫、上 K8s，把一個本來單機就能跑得很好的系統，拆成十個服務、跑在十台機器上。「為了可擴展性」「為了高可用」。

**為什麼錯**：分散式是**有成本的**——你買到可擴展/高可用，付出的是上面 1-5 條全部變成你的問題：網路不可靠、部分失敗、時鐘、一致性、腦裂。一個單機系統這些問題**一個都沒有**。很多團隊在還沒有規模問題時就分散式化，結果是把一個簡單問題換成一堆難題，可用性反而**下降**（現在任何一個服務掛了或網路抖一下，整個系統就出問題）。「分散式單體」（distributed monolith）——拆成微服務卻互相緊耦合、要一起部署——是這條的變種，拿到了分散式的全部成本卻沒拿到任何好處。

**正確做法**：**能單機就單機**。單機的垂直擴展（更大的機器）能撐到的規模，比大多數人以為的高得多（現代單機幾 TB 記憶體、幾百核）。只有當你**真的**撞到單機天花板（容量、吞吐、地理分布、可用性要求），才付分散式的成本，且一次只分散必要的那部分。分散式是最後手段，不是預設架構。

> 對應 [Ch 1 為什麼分散式這麼難](./01-why-distributed-is-hard.md)——這章的整個論點就是「分散式的難不是更大的單機，是質變」。

### 7. 重試風暴與驚群（retry storm / thundering herd）

**反模式**：呼叫失敗就立刻重試、固定間隔重試、所有 client 同時重試。或者：一個快取失效的瞬間，所有請求同時湧向後端（驚群）。

**為什麼錯**：當一個服務因為過載而開始變慢/失敗，「立刻重試」會**加倍**打向它的流量——它更過載、更多失敗、更多重試……正回饋雪崩。這叫重試風暴，是把「一個服務短暫抖動」升級成「整個系統崩潰」的放大器。固定間隔重試讓所有 client 同步化（大家在同一時刻重試），驚群則是所有請求在同一瞬間湧入。這些都是「協調的同步行為」造成的自我 DDoS。

**正確做法**：重試要用**指數退避（exponential backoff）+ 抖動（jitter）**——失敗後等的時間指數增長，且加隨機抖動打散 client 的重試時刻，避免同步。用**斷路器（circuit breaker）**：偵測到下游持續失敗就直接快速失敗、停止重試一段時間，給下游喘息。快取驚群用「請求合併（request coalescing）」或「提前非同步刷新」。核心思想：失敗時**減少**而非增加對受害者的壓力。

> 這是實務工程的重災區。呼應 [Ch 2 失敗模型](./02-failure-and-network-models.md) 對「級聯失敗」的討論、以及 [Ch 29 SWIM/Gossip](./29-membership-failure-detection-swim.md) 為什麼用 gossip 而非全體互探（避免 O(N²) 的探測風暴）。

### 8. 缺乏冪等（non-idempotent operations）

**反模式**：把操作寫成非冪等——「餘額 += 100」「計數器 +1」「append 一筆記錄」——然後在一個 at-least-once 的世界裡執行它。

**為什麼錯**：at-least-once（第 4 條）意味著操作**可能被執行多次**。「餘額 += 100」執行兩次就多加了 100。網路重試、client 超時重發、訊息中介重投——任何一個都會讓非冪等操作重複執行，靜默地把資料弄錯。而且這種 bug 極難查：大部分時候只執行一次、看起來很正常，偶爾重複一次就錯一筆，你在海量資料裡根本找不到那一筆。

**正確做法**：把操作設計成**冪等**——執行 N 次和執行 1 次結果相同。手段：(a) 用**唯一請求 id + 去重表**（處理前查這個 id 做過沒）；(b) 用**冪等的操作形式**（「設餘額為 X」而非「餘額 += 100」，「確保存在」而非「插入」）；(c) 用**條件式操作**（compare-and-set，帶版本號）。冪等是 at-least-once 世界裡保持正確的地基，不是可選項。

> 對應 [Ch 3 RPC 與訊息語意](./03-rpc-and-message-semantics.md)（冪等是 at-least-once 的解藥）、[Ch 30 分散式交易](./30-distributed-transactions-2pc-3pc.md)、[Ch 31 Saga](./31-saga-percolator.md)（Saga 的每個補償步驟都必須冪等）。

### 9. 忽略時鐘偏移（clock skew）

**反模式**：用時鐘做安全關鍵的決定——「這個 lease 到 12:00:00 過期，現在我的時鐘 11:59:59，所以我還持有 lease，可以放心寫入」。或者用時間戳做分散式鎖的過期判斷。

**為什麼錯**：這是第 3 條的近親，但更危險，因為它直接影響**安全性**（不只是排序）。你的時鐘和別人的時鐘不同步——你以為 lease 還沒過期，但持有 lease 授予方的時鐘已經過了，它已經把 lease 給了別人。現在兩個節點都以為自己持有鎖 → 兩個寫入者 → 資料損壞。GC 停頓讓這更糟：你檢查完「lease 還有效」，然後 GC 停了 10 秒，醒來時 lease 早過期了但你不知道，繼續寫。

**正確做法**：安全關鍵的決定**不要單靠時鐘**。用 **fencing token**（單調遞增的版本號）——每次授予 lease 給一個遞增的 token，儲存端拒絕比它見過的更小的 token 的寫入。這樣就算舊持有者時鐘錯亂、以為自己還持有，它的舊 token 也會被儲存端擋下。時鐘可以用來做**效能優化**（大部分時候快速判過期），但**正確性**必須靠 fencing token 這種不依賴時鐘同步的機制兜底。

> 對應 [Ch 4 實體時鐘的謊言](./04-physical-clocks.md)（時鐘不可信）、[Ch 13 Quorum](./13-quorum-replication.md)、[Ch 39 Spanner](./39-google-spanner.md)（TrueTime 怎麼正面處理時鐘不確定性）。

### 10. 誤用一致性模型（拿 CAP 當免死金牌 / 錯配一致性等級）

**反模式**：兩個極端。一種是**無腦選強一致**——所有東西都要線性一致，結果在該用最終一致（AP）的地方付了不必要的延遲和可用性代價（Ch 11 PACELC 的 L）。另一種是**無腦選最終一致**——把需要強一致的東西（庫存扣減、餘額）也做成最終一致，然後在「超賣」「餘額變負」時傻眼。還有人拿「CAP 定理說分區時只能選 C 或 A」當藉口，不去想自己真正需要什麼。

**為什麼錯**：一致性不是「越強越好」，是**越強越貴**（延遲、可用性、吞吐都要付代價）。強一致用在不需要的地方是浪費；弱一致用在需要強一致的地方是災難。CAP 只在**分區發生時**逼你二選一，而且它是個粗糙的三選二框架——PACELC 才完整（分區時 C/A，正常時 L/C）。真正的問題不是「CAP 選哪個」，是「**我的每一類資料各自需要什麼一致性**」。

**正確做法**：**按資料分類選一致性**。金流、庫存、唯一性約束 → 強一致（線性一致，付延遲代價值得）。社交動態、瀏覽計數、推薦 → 最終一致（要可用性和低延遲，短暫不一致無所謂）。理解 CAP/PACELC 是為了**做這個分類決定**，不是為了拿它當藉口。同一個系統裡不同資料用不同一致性等級是正常且正確的。

> 對應 [Ch 9 一致性模型光譜](./09-consistency-models.md)、[Ch 10 CAP 定理](./10-cap-theorem.md)、[Ch 11 PACELC](./11-pacelc.md)、[Ch 14 CRDT](./14-conflict-resolution-crdt.md)。

| 9 | 忽略時鐘偏移 | 時鐘可信到能做安全決定 | fencing token，時鐘只做優化 | Ch 4, 13, 39 |
| 10 | 誤用一致性模型 | 越強越好 / CAP 當藉口 | 按資料分類選一致性等級 | Ch 9, 10, 11, 14 |

## 踩雷集錦（反模式的反模式：矯枉過正）

避開上面十條之後，還有一批「因為怕犯錯而過度反應」造成的新坑：

1. **因為怕腦裂，什麼都上 Raft**：共識有成本（每個寫入至少一輪多數派往返的延遲、需要多數存活）。不是所有東西都需要線性一致的共識。無狀態服務、最終一致的資料、可以重算的快取——用共識是殺雞用牛刀，還把可用性綁死在多數存活上。**先問「這需要共識嗎」**（Ch 15 共識問題定義），大部分東西不需要。

2. **因為怕時鐘不準，完全不用時鐘**：時鐘不能用來做**安全**決定（第 9 條），但它是很好的**效能優化**和**粗略排序**工具。完全不用時鐘會讓你在該快速判斷過期時，被迫走昂貴的協調。正確是「時鐘做優化、fencing token 兜底正確性」，不是「時鐘一律不碰」。

3. **因為怕重試風暴，關掉重試**：矯枉過正到另一頭。沒有重試，一個瞬時網路抖動就變成使用者看到的錯誤。要的是**聰明的重試**（退避+jitter+斷路器+冪等），不是**沒有重試**。

4. **因為 CAP 說分區時二選一，就不做分區處理**：「反正分區時只能犧牲 C 或 A，那我就不管分區了」——這是把粗糙的理論當成不作為的藉口。真實系統要**明確設計**分區時的行為（哪些操作繼續、哪些拒絕、heal 後怎麼合併），而不是讓它變成未定義行為。

5. **把冪等當成「重複執行沒關係」的萬能藥**：冪等保證「重複執行結果相同」，但不保證「順序無關」。兩個冪等操作以不同順序執行結果可能不同（設 x=1 然後設 x=2，vs 反過來）。冪等 ≠ 可交換（commutative）。需要順序無關性時要另外用 CRDT（Ch 14）或定序機制。

## 進階：再往深一層

- **這些反模式為什麼一再重演——組織層面**：技術上都有解，但它們重複出現的深層原因常是**組織壓力**：趕上線、沒時間做失敗注入測試、資深工程師離職帶走了「為什麼這裡不能省」的知識。Jepsen 之所以有價值，一半是技術、一半是它用鐵證逼組織正視這些「大部分時候不會出事」的坑。這也是 Ch 43 DST/Jepsen 的意義——把「偶爾出事」變成「可重現的必然」，組織才會認真對待。

- **反模式的形式化**：這十條的很多可以用你學過的形式化工具精確表達。「腦裂」= 違反 Raft 的 Election Safety（Ch 22）；「用時鐘排序」= 混淆了 happens-before 偏序和實時全序（Ch 5）；「誤用一致性」= 沒搞清楚線性一致 vs 因果一致 vs 最終一致的精確定義（Ch 9）。形式化不是學術裝飾——它給你精確的語言去說「這裡到底違反了什麼」。

- **反模式清單的邊界**：這十條不是全部。還有一整批這門課碰得少的：schema 演進（如何在不停機下改資料格式）、背壓（backpressure，下游慢了怎麼讓上游慢下來而非爆掉）、多租戶隔離、資料本地性、跨區複製的成本模型……分散式系統是一個你會終身學習的領域。這份清單是地基，不是天花板。

## 本章重點整理

- 分散式反模式是**重複的**——同一批坑被一再踩，因為它們都源自把**單機直覺**偷渡進分散式世界。
- 十條核心反模式：假設網路可靠、忽略部分失敗、用實體時鐘排序、以為 exactly-once、忽略腦裂、過度分散式、重試風暴、缺乏冪等、忽略時鐘偏移、誤用一致性模型。每一條都有一整章的推導撐著。
- 抓反模式的能力 = **聞到「這裡有個單機假設」的味道**。這是這門課要培養的核心直覺。
- 避坑之後還有「矯枉過正」的新坑：什麼都上 Raft、完全不用時鐘、關掉重試、拿 CAP 當不作為藉口。分寸感很重要。
- **能單機就別分散式**——分散式是最後手段。這條值得單獨記住，因為它能讓你根本不掉進其他九條坑。

## 設計分散式系統的檢查清單

動手設計任何分散式系統前，逐條問自己。這是這門課能給你的最實用的一頁：

**需求與規模**
- [ ] 這**真的**需要分散式嗎？單機（垂直擴展）撐不住哪個具體指標（容量/吞吐/可用性/地理）？（反模式 6）
- [ ] 我的資料能不能分類？哪些需要強一致、哪些最終一致就夠？（反模式 10）

**失敗模型**
- [ ] 我假設了什麼失敗模型？crash-stop？crash-recovery？拜占庭？（Ch 2）
- [ ] 每個跨網路呼叫，如果**回覆丟了**，我怎麼恢復？（反模式 1, 2）
- [ ] 部分失敗（「不知道」第三態）在每個關鍵路徑上怎麼處理？（反模式 2）

**時間與順序**
- [ ] 我在哪裡用了時間戳排序？那裡的事件有因果關係嗎？該用邏輯/向量時鐘嗎？（反模式 3）
- [ ] 我有沒有用時鐘做**安全**決定（lease/鎖過期）？有沒有 fencing token 兜底？（反模式 9）

**一致性與複製**
- [ ] 選主/複製有沒有靠 quorum 保證唯一主？分區時少數派會卡住還是分岔？（反模式 5）
- [ ] 我宣稱的一致性等級，有沒有被對抗性測試（Jepsen/DST）驗過？（Ch 43）
- [ ] heal（分區恢復）之後，分岔的狀態怎麼合併？誰的寫入算數？（反模式 5, Ch 14）

**訊息與冪等**
- [ ] 我的交付語意是 at-least-once 還是 at-most-once？（沒有 exactly-once）（反模式 4）
- [ ] 每個可能被重複執行的操作，是冪等的嗎？靠什麼機制去重？（反模式 8）

**過載與韌性**
- [ ] 重試有退避+jitter嗎？有斷路器嗎？下游過載時我是加壓還是減壓？（反模式 7）
- [ ] 一個服務掛了/變慢，會不會級聯拖垮整個系統？（Ch 2, 反模式 7）

**可觀測性**
- [ ] 每筆 log 有 correlation id 嗎？能一鍵撈齊一個請求的跨節點足跡嗎？（Ch 44）
- [ ] 有分散式追蹤嗎？能定位「慢在哪一跳」嗎？（Ch 44）
- [ ] 出事時我能重現嗎？有確定性測試/失敗 seed 嗎？（Ch 43）

一條一條走完，你不會做出完美的系統——但你會**避開所有已知的坑**，這在分散式系統裡已經是巨大的勝利。
