# Ch 32 — 拜占庭將軍問題

> **目標**：理解拜占庭容錯（Byzantine Fault Tolerance，BFT）與 crash-fault 容錯的本質差異，推導出「為什麼需要 3f+1 個節點才能容忍 f 個拜占庭節點」的直覺，並理解簽章（authenticated messages）如何降低這個門檻。建立 Part 5 的地基。

## 為什麼需要這個？

你在 Ch 18–24 學的 Paxos、Raft、Zab，都建立在一個隱含假設上：**節點只會當機（crash），不會說謊**。當機的節點沉默——它不發任何訊息。一個沉默的節點，其他人用 timeout 就能偵測；多數派能在不等它的前提下繼續運作。這個「沉默的失敗者」模型叫做 **crash-fault**（或 fail-stop），是分散式系統最友善的失敗模型。

但現實更殘酷。考慮這些情境：

- 一個遭入侵的節點可以發任意訊息給任意對象，內容可以是謊言。
- 一個有 bug 的節點可以對不同的對等節點回傳不同的結果（非惡意但等效地製造矛盾）。
- 一個被勒索軟體加密的節點，可能在刪資料前做最後一批矛盾寫入。
- 區塊鏈網路的匿名節點，你根本不知道它是誰，遑論信任它。

這些情境下的節點不只是沉默——它**主動發送矛盾、精心設計的訊息**，破壞共識。Paxos 和 Raft 對此完全沒有防備：一個說謊的「leader」可以讓一半 follower 認為值是 A、另一半認為是 B，協定在那個假設下就崩了。

這就是 **Byzantine fault**（拜占庭故障）的定義：節點可以做任何事，包括主動傳送精心設計的謊言。而 **Byzantine Fault Tolerance** 是在「最多 f 個節點可以是拜占庭的」前提下，**仍然讓誠實節點達成一致**的問題。

這個問題由 Leslie Lamport、Robert Shostak、Marshall Pease 在 1982 年的論文《Byzantine Generals Problem》形式化。它不只是理論——現代區塊鏈共識、TEE（可信執行環境）叢集、航太容錯計算（fly-by-wire）都是它的直接應用。

> 若對 crash-fault 容錯的基礎還不熟，先回看 [Ch 2](./02-failure-and-network-models.md)（失敗模型）和 [Ch 18](./18-paxos-single-decree.md)（Paxos）。

## 先建立直覺：將軍的比喻

Lamport 用拜占庭帝國的將軍圍城來具象化這個問題。

想像一群將軍分幾支軍隊圍著敵城。他們必須協商一個統一的行動計劃：**全部進攻（attack），或全部撤退（retreat）**——只要大家一致，任何一個都行；但若有人進攻、有人撤退，就是災難。

將軍之間只能靠**信使**傳遞訊息（沒有廣播，信使可以被攔截）。問題是：**有些將軍是叛徒（traitor）**——他們會故意傳送矛盾命令給不同的忠誠將軍，試圖讓忠誠將軍之間無法達成一致。

把這個映射回分散式系統：

```
將軍       = 節點
信使       = 網路訊息
叛徒將軍   = 拜占庭節點（可以做任何事，包括對不同對象說不同的話）
忠誠將軍   = 誠實節點
統一行動   = 共識（所有誠實節點決定同一個值）
```

拜占庭將軍問題的正式定義：

1. **Agreement（一致性）**：所有忠誠的將軍必須做出相同的決定。
2. **Validity（有效性）**：若所有忠誠的將軍初始都偏向某個值，最終決定必須是那個值。
3. **Termination（終止性）**：所有忠誠的將軍最終都要做出決定。

這比 crash-fault 共識難在哪？難在**你不能相信任何單一訊息**。在 Raft 裡，leader 說「值是 X」，follower 就信。但如果 leader 可能是拜占庭的，它對一些人說「X」、對另一些人說「Y」——follower 單靠「收到 leader 的訊息」這個事實，什麼也判斷不了。

## crash-fault 與 Byzantine fault 的本質差異

```
              crash-fault（Paxos/Raft 的假設）
              ┌─────────────────────────────────────────┐
              │ 節點 A 故障                              │
              │                                         │
              │  ● 沉默：不發任何新訊息                  │
              │  ● 可能在某個點之前發了一些訊息           │
              │  ● 不會「主動說謊」                      │
              │                                         │
              │ 偵測方式：timeout（一段時間沒回應 = 掛了） │
              └─────────────────────────────────────────┘

              Byzantine fault（拜占庭模型）
              ┌─────────────────────────────────────────┐
              │ 節點 A 拜占庭                            │
              │                                         │
              │  ● 可以說任何話、做任何事                │
              │  ● 對 B 說「值是 X」，對 C 說「值是 Y」  │
              │  ● 可以選擇性地不回應某些節點            │
              │  ● 可以假裝當機、也可以假裝正常          │
              │  ● 可以偽造訊息（若沒有密碼學保護）      │
              │                                         │
              │ 偵測方式：幾乎不可能直接偵測！           │
              └─────────────────────────────────────────┘
```

這個差異的根本原因：**crash-fault 節點的行為空間是「沉默」這一個點，Byzantine fault 節點的行為空間是所有可能的行為**。

在 crash-fault 模型下，多數派（quorum）的力量在於：當你拿到多數派的回應，你知道那些回應都是「善意的、來自活著的節點」——就算它們之前說過不同的話，那是因為它們在不同時間點看到了不同狀態（用編號/term 可以排序）。

在拜占庭模型下，多數派的邏輯會被破壞：**一個拜占庭節點可以對不同的節點發送不同的訊息**，讓每個誠實節點都覺得自己得到了「多數支持」，但支持的是不同的值。

## 核心定理：為何需要 3f+1

這是整個 BFT 領域最基本的下界：

> **定理（Lamport-Shostak-Pease 1982）**：在有 f 個拜占庭節點的系統中，若要讓誠實節點達成共識，節點總數 N 必須滿足 **N ≥ 3f + 1**。

換句話說：f 個叛徒需要至少 3f + 1 個將軍（其中 2f + 1 個是忠誠的）。

### 直覺推導：3 將軍 1 叛徒無解

最簡單的反例：**3 個節點，1 個是叛徒（f=1，N=3）**，驗證 3f+1=4 的必要性。

假設節點是 A（忠誠）、B（忠誠）、C（叛徒）。指揮官（司令）想發命令給中尉們。

**情境一：C 是叛徒**

```
       A（忠誠指揮官）
          │
    attack│    attack
          ▼          ▼
     B（忠誠）    C（叛徒）
     
C 對 A 的訊息傳達：
  C 告訴 B：「A 說 retreat」
  
B 此時看到：A 直接說 attack，C 轉達說 A 說 retreat
B 無從判斷誰在說謊
```

**情境二：A 是叛徒（作為指揮官的叛徒）**

```
       A（叛徒指揮官）
          │
  attack  │   retreat
          ▼         ▼
     B（忠誠）   C（忠誠）
     
B 告訴 C：「A 說 attack」
C 告訴 B：「A 說 retreat」

B 看到：直接 attack + C 轉達 retreat → 衝突
C 看到：直接 retreat + B 轉達 attack → 衝突
```

**關鍵**：在情境二中，B 和 C 的「局部視角」與情境一（A 忠誠、C 叛徒）完全相同！B 在兩個情境下看到的訊息格局一模一樣：「自己直接收到 X，另一個人轉達了 Y」。既然它無法區分，它必須在兩個情境下做相同的決定——但這是不可能的，因為兩個情境的正確答案相反。

這證明了：**3 個節點容忍不了 1 個叛徒**。你需要第 4 個節點，打破對稱。

### 一般化：為什麼 3f+1

更嚴格的論證：

考慮 N 個節點，f 個拜占庭。誠實節點要決定一個值，它只能靠「收集到的訊息」來判斷。

設共識需要的最小支持數為 Q（quorum）。

**限制 1（活性）**：最壞情況下 f 個誠實節點不回應（或被隔離），剩下 N-f 個。我們必須能在沒有這 f 個人的情況下達成共識，所以 Q ≤ N-f。

**限制 2（安全性）**：任兩個 quorum 必須有足夠的重疊，使得重疊部分裡至少有 1 個**誠實**節點（否則叛徒可以讓兩個 quorum 分別支持不同的值，互不知道）。

兩個 quorum Q 各有 Q 個成員，總節點 N，最壞的重疊是 Q + Q - N = 2Q - N 個。其中最多 f 個是叛徒。所以誠實的重疊至少是 `2Q - N - f`，需要 ≥ 1：

```
2Q - N - f ≥ 1
2Q ≥ N + f + 1
```

由限制 1 代入 Q = N - f：

```
2(N - f) ≥ N + f + 1
2N - 2f ≥ N + f + 1
N ≥ 3f + 1
```

所以 **N ≥ 3f + 1 是必要條件**。且這個條件是緊的（tight）——存在協定在 N = 3f+1 時達成共識。

### 為什麼 f+1 不夠（對比 crash-fault）

Paxos/Raft 的多數派（majority quorum）設計來自 crash-fault：N = 2f+1 節點容忍 f 個崩潰。為什麼 BFT 需要更多？

直覺：在 crash-fault 裡，節點的「投票」是可信的——只要它投，它說的就是真話（基於它的真實狀態）。Quorum 交集 f+1 個節點，其中 0 個會說謊，所以你能從多數決裡抽出真相。

在 BFT 裡，投票可能是謊言。Quorum 交集 f+1 個節點，其中最多 f 個是叛徒，可能只剩 **1 個誠實節點**——一個節點不夠建立信任。你需要讓交集裡的誠實節點 > f，使得誠實節點能「壓過」叛徒的謊言，形成 f+1 個誠實節點，確保多數是誠實的。這就是為什麼要 3f+1 而非 2f+1。

數值對比：

| 容錯模型 | N | 最大容忍 f | 誠實最少（N-f） | Quorum 大小 | Quorum 交集最少誠實 |
|----------|---|-----------|----------------|------------|-------------------|
| Crash-fault（Paxos/Raft）| 2f+1 | f | f+1 | f+1 | 1 |
| Byzantine（PBFT/HotStuff）| 3f+1 | f | 2f+1 | 2f+1 | f+1 |

交集裡有 f+1 個誠實節點（BFT 的情況），其中做多數決：誠實 f+1 > 叛徒 f——所以誠實佔多數，你能信任這個交集的決定。這就是 3f+1 設計的數學根基。

## 口頭訊息（OM）演算法

Lamport 等人提出的 **OM(m) 演算法**（Oral Messages，m = 叛徒數）是第一個在同步模型下解決拜占庭共識的演算法。

OM(0)：若叛徒數 m = 0，指揮官說什麼就是什麼，直接送達。

OM(m)（m ≥ 1，共 3m+1 個節點）：
1. 指揮官把自己的值 v 發給所有 n-1 個中尉。
2. 每個中尉 i 拿到值（或若指揮官是叛徒而缺席則設預設值 retreat），對剩下的 n-2 個中尉遞迴跑 OM(m-1)，把「指揮官告訴我 v 這件事」散布出去。
3. 每個中尉拿到 n-1 個值（來自指揮官直接 + 其他中尉的遞迴），取**多數決**。

```
OM(1)，4 將軍（A 指揮官，B/C/D 中尉，D 叛徒）：

   A(忠誠指揮官)
   │ attack
   ├──────────────────────────────────┐
   │ attack          attack           │ attack
   ▼                 ▼                ▼
   B(忠誠)          C(忠誠)          D(叛徒)
   
D 謊稱：
  對B說「A說retreat」、對C說「A說retreat」
  
B 收集：直接收到attack + C說A說attack + D說A說retreat
        多數: attack(2) > retreat(1) → B 決定 attack

C 收集：直接收到attack + B說A說attack + D說A說retreat
        多數: attack(2) > retreat(1) → C 決定 attack

B 和 C 都決定 attack → 一致！
```

OM(m) 的缺點：

1. **同步模型**：OM(m) 需要同步網路——訊息在已知時間 T 內送達，否則演算法中的 timeout 無從設定。真實網路是部分同步或非同步的，OM(m) 無法直接用。
2. **指數通訊複雜度**：OM(m) 遞迴 m 層，每層每個節點廣播給所有人，訊息數量是 O(n^m)。在 f=33（100 個節點）的情況下，O(100^33) 訊息——完全不實用。
3. **不支援非同步**：FLP 定理（Ch 16）在非同步模型下拜占庭共識同樣不可能；OM(m) 的同步假設是逃離 FLP 的手段之一，但代價是在非同步網路上無法用。

### OM(m) 的完整歸納正確性

Lamport 等人對 OM(m) 的正確性用歸納法證明：

**基礎（m=0）**：沒有叛徒，指揮官的值直接送達，所有忠誠中尉拿到同樣的值，顯然一致且有效。

**歸納步驟（m > 0）**：假設 OM(m-1) 對 3m 個節點（含 m-1 個叛徒）正確，要證 OM(m) 對 3m+1 個節點（含 m 個叛徒）正確。

*情況 A：指揮官是忠誠的*。指揮官向所有 3m 個中尉發送同一個值 v。每個忠誠中尉（至少 2m 個）以 v 為起始，對其他 3m-1 個中尉（含 m-1 個叛徒）跑 OM(m-1)。歸納假設告訴我們這個遞迴正確——每個忠誠中尉最終從 3m 個子命令裡拿到：至少 2m 個忠誠中尉傳達的正確值 v，至多 m 個叛徒傳達的任意值。多數是 v（2m > m），所以所有忠誠中尉最終決定 v。有效性和一致性同時成立。

*情況 B：指揮官是叛徒*。指揮官可以對不同中尉說不同的值。但每個忠誠中尉以其收到的值為起始跑遞迴。關鍵在於：每個忠誠中尉的遞迴 OM(m-1) 對同一組 3m 個中尉（含 m-1 個叛徒，因為指揮官是叛徒那 m 個的其中一個）跑，歸納假設確保這個遞迴對所有忠誠中尉產生一致的結果。因此，每個忠誠中尉最終拿到同一個「從 3m 個子命令裡多數決」的向量，做出相同的決定，一致性成立。

**複雜度**：OM(m) 的訊息數 T(n,m) 滿足 T(n,m) = n·T(n-1, m-1)，解出 T(n,m) = n!/(n-m-1)! ≈ O(n^(m+1))。對 m=f=1 是 O(n²)，對 m=2 是 O(n³)——m 每增加 1，複雜度指數級上升。

## 簽章訊息：把門檻從 3f+1 降低的方法

OM(m) 是「口頭訊息」——你說 A 說了什麼，但沒有辦法驗證。如果我們加上**數位簽章（digital signature）**，情況會改變。

**Signed（SM）演算法**：指揮官簽章發送命令。中尉轉發時附上原始簽章。任何人都能驗證「這個訊息確實是 X 簽的」。

關鍵效果：**叛徒無法偽造誠實節點的簽章**。如果 A 說 attack，這條帶 A 簽章的訊息在流傳過程中不能被叛徒篡改成 retreat。

有了簽章，拜占庭問題的門檻確實降低了：

- **無簽章（OM）**：需要 N ≥ 3f+1（才能在同步下解）。
- **有簽章（SM）**：在同步模型下，N ≥ f+2 就夠了（理論最小值）——只要有 f+1 個誠實節點就能達成共識。

但這個降低有代價：

1. **密碼學假設**：簽章依賴「叛徒無法偽造簽章」——這在計算複雜性理論上成立（假設叛徒計算能力有限），但引入了密碼學假設。量子電腦到來後這個假設可能動搖。
2. **PKI（公鑰基礎設施）**：你需要一個可信的方式分發公鑰。如果你不知道誰是誰，簽章就沒用——這在開放（permissionless）網路（如比特幣）裡是真正的挑戰。
3. **延遲**：簽章/驗章有計算開銷。在高吞吐量場景下這是實際瓶頸。

現代 BFT 協定（如本 Part 的 PBFT、HotStuff、Tendermint）都使用簽章——因為沒有簽章的話，3f+1 的 N 在實用系統中往往不夠靈活，而且 N ≥ f+2 讓小叢集可行（4 節點容忍 1 個拜占庭，而非必須有 4 個，但需簽章才能把 f+2 用到底；實際 PBFT 仍用 3f+1 搭配簽章是為了非同步安全）。

### 簽章的另一個作用：不可否認性（non-repudiation）

有了簽章，不只能防偽造，還能防「賴帳」。在 OM(m)（口頭訊息）下，如果一個叛徒指揮官對 B 說「attack」、對 C 說「retreat」，B 拿著「我聽到 attack」這句話去告訴 C，C 無從核實——B 可能在撒謊，也可能指揮官真的說了兩個版本。

有了簽章版 SM 演算法，指揮官必須在命令上「親筆簽名」。B 把「attack + 指揮官的簽章」傳給 C，C 可以直接驗 signature——若指揮官真的發過 attack，簽章就在那裡，C 能確認。若叛徒指揮官想對 B 說 attack、對 C 說 retreat，它需要同時簽署兩則矛盾的命令，當這兩個版本在節點間流傳時，誠實節點會看到矛盾的兩份「親筆」，知道指揮官在說謊，並根據協定規則（例如：若看到矛盾就 retreat）做一致的決定。

這讓 SM 演算法能在 N = f+2 的情況下處理 1 個拜占庭指揮官：只有 f+2 = 3 個節點就能讓 2 個忠誠中尉不被一個叛徒指揮官分裂。

## 底層機制：不同失敗模型與系統實際形狀

理解 BFT 的最直接方式是把 3f+1 的要求對應到真實系統的 N：

| 想容忍的拜占庭節點數 f | 最小 N（3f+1） | 誠實節點數（≥ 2f+1） | 實際例子 |
|---|---|---|---|
| 0 | 1（沒意義） | 1 | 單點，不可用 |
| 1 | 4 | 3 | PBFT 最小可用部署 |
| 2 | 7 | 5 | 七節點聯盟鏈 |
| 10 | 31 | 21 | Cosmos 早期 validator 集 |
| 33 | 100 | 67 | PBFT 的實用上限 |
| 100 | 301 | 201 | HotStuff 才能支撐（O(n²)→O(n)） |

這張表說明了兩件事：

1. **BFT 系統通常要小（n < 100）**：f 越大，需要的節點越多，通訊成本隨 n 增加。PBFT 的 O(n²) 讓它在 n > 20 後實用性急降，HotStuff 的 O(n) 才讓 n=100 成為可行的設計點。
2. **三分之一是天花板**：即使 N 很大，最多容忍 ⌊(N-1)/3⌋ 個拜占庭節點——33% 的惡意節點上限。Cosmos 的 validator 集如果超過 1/3 的質押被惡意控制，BFT 保證就失效。這是任何 BFT 類協定共有的固有限制。

### 不同失敗模型的防禦能力

```
   失敗模型比較（從弱到強，攻擊者能力遞增）
   
   ┌──────────────────────────────────────────────────────────────┐
   │ Crash-Stop（Ch 2 的 fail-stop）                              │
   │   節點：沉默，不再發訊息                                      │
   │   例子：斷電、kernel panic、OOM kill                         │
   │   容忍 f 個：需要 N ≥ 2f+1（Paxos/Raft 用這個）              │
   └──────────────────────────────────────────────────────────────┘
                              ↓ 更強的攻擊者
   ┌──────────────────────────────────────────────────────────────┐
   │ Crash-Recovery（可重啟）                                     │
   │   節點：可以崩潰後重啟，但恢復前的狀態可能遺失或不一致        │
   │   例子：Raft 的 follower 重啟後要 catch up log               │
   │   容忍：Raft/Paxos 的持久化設計處理這個                      │
   └──────────────────────────────────────────────────────────────┘
                              ↓ 更強
   ┌──────────────────────────────────────────────────────────────┐
   │ Byzantine（本 Part 的主題）                                   │
   │   節點：做任意事，包括精心設計謊言、equivocation（對不同節點  │
   │         說不同的值）、選擇性回應、重放舊訊息                  │
   │   例子：入侵節點、被勒索軟體控制、有刻意 bug 的實作           │
   │   容忍 f 個：需要 N ≥ 3f+1（無簽章，同步下）                │
   │             N ≥ 3f+1（有簽章，非同步，PBFT 用這個）          │
   └──────────────────────────────────────────────────────────────┘
                              ↓ 更強
   ┌──────────────────────────────────────────────────────────────┐
   │ Byzantine + 網路控制者                                        │
   │   攻擊者不只控制 f 個節點，也控制網路路由，可以選擇性延遲、    │
   │   丟棄、重排訊息                                              │
   │   在非同步網路：FLP 說不可能達到拜占庭共識                    │
   │   解法：部分同步假設（GST）+ BFT 協定                        │
   └──────────────────────────────────────────────────────────────┘
```

**為什麼 BFT 仍需要 3f+1 而非 f+2（即便有簽章）？**

嚴格說，在同步模型下有簽章 f+2 就夠，但實際協定（PBFT、HotStuff）仍然要求 N ≥ 3f+1。原因是這些協定要在**部分同步（partial synchrony）**——而非完全同步——的模型下工作，且要抵抗某些更精細的攻擊（後面 Ch 33 會解釋 PBFT 的 3f+1 quorum 為何在部分同步下仍然必要）。

## 對比與取捨

| 性質 | Crash-fault（Paxos/Raft） | Byzantine（PBFT/HotStuff） |
|------|--------------------------|---------------------------|
| 故障模型 | 沉默失敗 | 任意行為（含惡意） |
| 最小節點數（容忍 f 個） | 2f+1 | 3f+1 |
| 誠實節點數（最壞） | f+1 | 2f+1 |
| 需要數位簽章 | 不必要 | 幾乎都用（防偽造） |
| 同步假設 | 部分同步（GST） | 部分同步（GST） |
| 通訊複雜度 | O(n)（Raft） | O(n²)（PBFT）~O(n)（HotStuff） |
| 適用場景 | 內部可信網路、資料中心 | 多組織聯盟、區塊鏈、敵意環境 |

## 踩雷集錦

1. **把 Byzantine fault 跟「節點說謊」畫等號，以為只有惡意節點才是 Byzantine**。錯。有 bug 的實作、宇宙射線翻轉記憶體 bit（Bitflip）、軟體版本不一致造成不同節點計算出不同結果，這些都是 Byzantine fault。「Byzantine」是「任意偏離正確行為」，不限於主觀惡意。

2. **以為加了 BFT 協定，系統就能容忍任意數量的壞節點**。不行。BFT 的保證是「容忍至多 f 個拜占庭節點，且 N ≥ 3f+1」。如果壞節點數超過 f，協定可能違反安全性——這就是 51% 攻擊的本質（Ch 36）。

3. **以為 crash-fault 容錯系統在有惡意節點的環境下「部分安全」**。不是的。Paxos/Raft 在面對一個拜占庭節點時，安全性保證**完全失效**——不是「差一點」，是「這個框架從根本就沒設計來處理這種情況」。一個拜占庭 leader 可以讓 Raft follower 接受任何 log。

4. **混淆「協定終止不了」和「協定是不安全的」**。在 BFT 中，面對超過 f 個拜占庭節點，協定可能停住（liveness 失敗）或做出錯誤決定（safety 失敗）——這兩件事的嚴重程度不同。Safety 失敗（決定出兩個不同的值）通常比 liveness 失敗（卡住不前進）更嚴重。好的 BFT 協定優先保 safety，在不能保 liveness 時選擇停住。

5. **忘記 3f+1 是「同時滿足 safety 和 liveness」的下界**。如果你只需要 safety（不需要 liveness），2f+1 就夠——只要有 2f+1 個節點就能「阻止任何壞決定」。但系統必須在「最壞情況下也能繼續決定」才有用，這就逼出了 3f+1。

6. **在 f ≥ N/3 的情況下以為 BFT 協定「還是能保 safety」**。不行。當 f ≥ N/3 時，3f+1 的前提被打破，任何 BFT 協定的安全性保證都失效。此時叛徒可以「控制多個 quorum」——讓 quorum A 見到 prepared(value-X)、quorum B 見到 prepared(value-Y)，而兩個 quorum 沒有誠實節點在交集中，split-brain 成為可能。這不是演算法缺陷，是 3f+1 模型的邊界。

7. **把「拜占庭節點」和「主動攻擊者」等同，忽略被動的 Byzantine 行為**。硬體 bitflip（Rowhammer 觸發的記憶體錯誤）、軟體版本不一致、NTP 問題導致的時間戳計算錯誤，這些都會讓節點的輸出偏離正確值，技術上都是 Byzantine fault——但沒有任何人在「攻擊」。在需要高可靠性的場景（金融交易、航太），對抗 Byzantine fault 不只是安全問題，也是可靠性問題。

## 進階：再往深一層

### 為什麼簽章不完全解決問題？

簽章解決了「轉發時被篡改」的問題，但對 **equivocation**（等值混淆）的防護有限：一個拜占庭 primary 可以合法地簽署兩則不同的訊息（對同一個序號簽兩個不同的值），分別發給不同的 replica。簽章無法防止拜占庭節點「簽了兩件互相矛盾的事」——只能讓其他人在看到兩份都合法的簽名時察覺矛盾。PBFT 的 prepare 階段就是為了讓大家把這個矛盾曝光（Ch 33 詳解）。

### 拜占庭容錯的資訊論下界

Lamport 等人的 3f+1 結果其實是一個資訊論下界，不依賴計算複雜性。它比「P ≠ NP」這類密碼學假設更強：**就算叛徒有無限計算能力**，也需要 3f+1 個節點——因為這是資訊結構（誰能看到誰的訊息）的問題，不是計算能力的問題。

有簽章的 f+2 下界則不同：它假設叛徒計算能力有限（不能偽造簽章），所以引入了密碼學假設。去掉這個假設（資訊論安全），你又回到 3f+1。

### 同步 vs. 非同步 BFT

- **同步 BFT**（OM 演算法）：所有訊息有已知上界時間。可以用 N = 3f+1 達成拜占庭共識。但真實網路不同步。
- **非同步 BFT**：FLP 定理說不可能。但「確定性非同步 BFT」——如 PBFT——實際上加了「部分同步（partial synchrony）」假設：存在一個 GST（Global Stabilization Time），在 GST 之後網路行為正常。這是繞過 FLP 的標準手法（[Ch 17](./17-circumventing-flp.md)）。

### BFT 的實際部署場景

哪些地方真的需要 BFT（而非 crash-fault 容錯）？

1. **聯盟鏈（consortium blockchain）**：多家企業各運一個節點，企業之間互不完全信任，其中某家可能受駭或作惡。例：Hyperledger Fabric、Quorum。
2. **TEE 叢集（Trusted Execution Environment）**：用 Intel SGX 等 TEE 的節點叢集，TEE 本身可能有 side-channel 漏洞被攻擊，已被攻陷的 TEE 節點是拜占庭節點。
3. **太空/航太容錯計算**：宇宙射線可能翻轉 bit，計算結果偏離——這是無惡意的 Byzantine fault，需要 BFT 風格的多數表決。
4. **去中心化 PoS 區塊鏈**：validator 是匿名的、可以被賄賂或入侵，Tendermint/HotStuff 是這類場景的主流選擇。
5. **多雲/多組織資料管道**：資料從多個組織的系統流入，任何一個組織的系統被攻陷都可能注入假資料，BFT 的共識確保最終決定不被少數被攻陷節點左右。

反過來說，哪些地方**不需要** BFT？
- 同一公司內部的分散式資料庫（etcd、Zookeeper）：節點雖然可能故障，但不會「說謊」，crash-fault 容錯完全夠用，BFT 的 3f+1 節點要求和 O(n²) 通訊是不必要的代價。

## 本章重點整理

- **Byzantine fault**：節點可以做任意事，包括對不同對象說不同的話（equivocation）——這是比 crash-fault 強得多的攻擊者模型。惡意、有 bug、bit flip 都算。
- **3f+1 下界**：容忍 f 個拜占庭節點需要 N ≥ 3f+1 個節點（同時保 safety 和 liveness）。這是資訊論下界，不假設計算能力，叛徒有無限計算能力也一樣需要 3f+1。
- **3 節點 1 叛徒無解**：最清晰的直覺——誠實節點無法區分「我是受害者」和「那個人是受害者」兩個情境，所以無法做正確決定。你需要第 4 個節點打破對稱。
- **quorum 交集保誠實**：3f+1 設計使得任兩個 2f+1 的 quorum 交集有 f+1 個節點，其中至少 1 個誠實——這就是 PBFT 能工作的根本。而 2f+1 設計的 crash-fault quorum 交集只有 f+1 個節點，其中 0 個在說謊，不需要這麼多。
- **簽章降門檻**：有數位簽章（可驗證、不可偽造）在同步模型下理論上 N ≥ f+2 就夠，但引入密碼學假設；實際 BFT 協定在部分同步模型仍需 3f+1。
- **OM(m) 演算法**：同步模型下的第一個解法，歸納法正確，但通訊複雜度 O(n^m) 不實用（m=1 是 O(n²)，m=2 是 O(n³)）。
- **crash-fault 協定面對 Byzantine 節點毫無保護**：Raft/Paxos 的安全性在有一個拜占庭節點時完全失效，不是部分失效。
- **BFT 的上限**：任何 BFT 協定都容不了 f ≥ N/3 個拜占庭節點；超過這個上限，協定的 safety 保證失效。在 PoS 鏈上，這對應「惡意質押 < 1/3 總質押」的要求。
