# Ch 1 — 為什麼分散式這麼難

> **目標**：說清楚分散式系統的難處到底來自哪裡。核心只有一個詞——**部分失敗（partial failure）**：系統的一部分壞了，其他部分還活著，而且**你分不清它是壞了、還是只是慢**。把八大謬誤（Fallacies of Distributed Computing）逐條拆穿，用一個「看似簡單的跨機轉帳」示範單機直覺為何全面失效，最後給出全書地圖：三大難題——不可靠網路、不可靠時鐘、順序。

## 為什麼需要這個？

在寫任何演算法之前，你得先相信一件事：**分散式系統的難，不是「一台更大的電腦」的難**。

單機程式裡，你呼叫一個函式，它要嘛回傳結果、要嘛拋例外、要嘛整個 process 一起死。這三種結局你都能處理。你從來不需要問：「這個函式呼叫，是成功了但回傳值在路上弄丟了？還是根本沒執行？還是執行到一半，機器在別的地方？」因為單機裡這種狀態**不存在**——函式跟你活在同一塊記憶體、同一個時脈、同一個生死。

跨機之後，這個保證消失了。你送一個請求給另一台機器，等回應。時間到了，沒回應。現在回答我：發生什麼事了？

- 對方根本沒收到請求（網路把請求丟了）？
- 對方收到了、做完了，但回應在路上丟了？
- 對方收到了、正在做，只是比較慢？
- 對方在做到一半時當機了？
- 對方好好的，只是你們之間的網路斷了，它其實還在服務別人？

**這五種情況，從你的視角看起來一模一樣：就是「沒回應」。** 而它們要求的處理方式完全不同——有的該重試，有的重試會鑄成大錯（想想上面那個「做完了但回應丟了」，你一重試就做了兩次）。

這就是部分失敗。它是分散式系統一切困難的源頭。歷史上，1980 年代的分散式運算研究者（尤其 Sun Microsystems 的一群人）曾經天真地相信「遠端呼叫可以做得跟本地呼叫一樣」，做了 RPC、CORBA、Java RMI 這些「透明遠端呼叫」的抽象。結果被現實反覆教育：**你可以把遠端呼叫的語法藏起來，但你藏不掉部分失敗的語意**。這個教訓濃縮成了業界流傳的「分散式運算八大謬誤」，我們這一章就逐條拆給你看。

## 先建立直覺

先給你一張圖，區分單機失敗與分散式失敗的本質差異。

```
        單機（全有或全無）                分散式（部分失敗）
   ┌───────────────────────┐      ┌────────────────────────────┐
   │   你的 process         │      │  Node A ───?───> Node B     │
   │   ┌───────────────┐    │      │    活著          活著/死了/慢？ │
   │   │ f() 要嘛回傳  │    │      │                             │
   │   │     要嘛拋例外 │    │      │  A 只知道「我沒收到回應」    │
   │   │  process 死→ 你也死│  │      │  A 分不清 B 是哪一種狀態     │
   │   └───────────────┘    │      │                             │
   └───────────────────────┘      └────────────────────────────┘
      失敗是「事件」                   失敗是「你無法觀測的狀態」
```

關鍵不在「機器會壞」——單機的硬碟也會壞。關鍵在**不對稱的資訊**：在分散式系統裡，一個節點永遠只能看到自己的局部狀態，加上「過去某個時間點別人送來的訊息」。它**沒有**全域快照，**沒有**別人的即時狀態，**沒有**一個神的視角告訴它「B 現在到底怎麼了」。它只能猜。

而最惡毒的是那個「慢」跟「死」分不清的問題。這在學術上叫做**無法可靠偵測失敗**——在一個訊息延遲沒有上界的網路裡，「沒回應」和「回應還在路上」在數學上就是無法區分的。這一句話，之後會長成整個 FLP 不可能定理（Ch 16）。現在你先記住這個直覺就好。

## 八大謬誤：逐條拆穿

「分散式運算的謬誤（Fallacies of Distributed Computing）」由 Sun 的 Peter Deutsch 與 James Gosling 等人在 1990 年代整理。它們是**新手寫分散式系統時會不自覺假設、但全都是錯的**八件事。每一條我們給一個具體反例。

### 謬誤 1：網路是可靠的

**錯誤假設**：我送出去的封包會到。

**現實**：封包會丟。交換器 buffer 滿了會丟、網路分區（partition）時整段不通、網卡壞了、電纜被工人挖斷。Google 的資料中心一年會遇到數十次網路分區事件（見 Kleppmann DDIA 第 8 章引用的 Bailis & Kingsbury 統計）。

**反例**：你寫 `send(request)` 然後 `resp = recv()`。網路把 request 丟了，你的 `recv()` 永遠等不到。你若沒設 timeout，這個 thread 就永遠掛在那。若設了 timeout，你又回到「沒回應到底是哪一種」的困境。

### 謬誤 2：延遲是零

**錯誤假設**：呼叫遠端跟呼叫本地一樣快。

**現實**：本地函式呼叫 ~1 奈秒；同機房 RPC ~0.5 毫秒（差 50 萬倍）；跨洲 RTT ~150 毫秒（差 1.5 億倍）。這不是常數的差別，是數量級的差別。

**反例**：你把一個單機演算法「無腦分散化」——原本迴圈裡讀一個陣列元素，現在每次去遠端讀一次。單機跑 1 秒的東西，變成 10000 次 × 0.5ms = 5 秒，還沒算失敗重試。**延遲逼你重新設計資料存取模式**（批次、快取、就近），不是換個函式名就好。

### 謬誤 3：頻寬是無限的

**錯誤假設**：我要傳多少資料都行。

**現實**：鏈路頻寬有上限，而且你跟所有人共享。你以為的「傳一個物件」在序列化後可能是幾 MB，一秒鐘幾千個請求就把鏈路塞爆。

**反例**：微服務化之後，一個頁面請求在後端扇出成 100 個內部 RPC，每個都帶著肥大的 JSON。單看一個沒事，尖峰時整個內網頻寬被自家服務吃光，外部請求開始 timeout。

### 謬誤 4：網路是安全的

**錯誤假設**：只有我的服務在跟我的服務講話。

**現實**：網路上有人竊聽、有人竄改、有人冒充、有人重放（replay）你的封包。內網也不安全——一旦有一台機器被打下來，攻擊者就在你的「可信」網路裡了。

**反例**：你的服務間 RPC 沒加密沒認證，因為「反正是內網」。攻擊者拿下一台邊緣機器，就能對你的資料庫發任意寫入請求——它長得跟合法服務一模一樣。（這條是你資安視角最熟的，Part 5 會把共識層本身當攻擊面來打。）

### 謬誤 5：拓樸不會變

**錯誤假設**：機器就是這幾台，位置固定。

**現實**：雲端環境裡機器隨時被增刪、被搬移、IP 變來變去、自動擴縮容。你寫死的 IP 清單三小時後就過期了。

**反例**：你在設定檔裡列了 5 個節點的 IP。運維把其中一台換到別的機架、IP 變了，你的服務還在往舊 IP 送，全部 timeout。這就是為什麼需要服務發現（service discovery）與成員協定（membership，Ch 29 的 SWIM/Gossip）。

### 謬誤 6：只有一個管理者

**錯誤假設**：整個系統由我一個人/一個團隊掌控。

**現實**：不同服務由不同團隊、不同公司維護，用不同的部署節奏、不同的版本、不同的設定。你依賴的下游可能在你不知情時改了行為、掛了、或做了不相容的升級。

**反例**：你依賴的內部服務半夜被別的團隊部署了新版，改了某個回應欄位的語意。你的服務沒動半行程式碼，隔天卻開始出錯。分散式系統沒有「一個人說了算」，協調本身就是難題。

### 謬誤 7：傳輸成本是零

**錯誤假設**：把資料送過去不用付出代價。

**現實**：序列化（serialization）/反序列化要花 CPU、記憶體、時間。把一個物件轉成 JSON/protobuf、送過去、再解回來，這中間的成本在高吞吐下非常可觀。跨可用區、跨區域的流量還要真的**付錢**（雲廠商的 egress 費用）。

**反例**：你的服務每秒處理十萬請求，每個都做一次「物件 → JSON → 網路 → JSON → 物件」。profiler 一跑，發現 40% CPU 花在序列化上，跟業務邏輯無關。

### 謬誤 8：網路是同質的

**錯誤假設**：所有節點、所有鏈路的特性都一樣。

**現實**：有的節點在同機架（快、穩），有的跨資料中心（慢、易丟）；有的走 10G 光纖，有的走公網 VPN。你不能假設「節點 A 到 B」和「A 到 C」有一樣的延遲與可靠度。

**反例**：你的 quorum 協定假設所有節點回應時間差不多，於是「等多數回應」很快。實際上有一個節點在地球另一端，它每次都是最慢那個，把你的 p99 延遲整個拉高。異質性逼你在協定裡處理「慢節點」這個一等公民。

**這八條的共同底色**：它們全都是「把分散式當單機」的一廂情願。而它們背後那個最深的、無法用工程手段消除的，就是**部分失敗 + 無法區分慢與死**。其他七條你砸錢砸工程多少能緩解，唯獨這一條是分散式系統的原罪。

## 一個看似簡單的跨機轉帳

來看單機直覺怎麼被徹底碾碎。需求普通到不能再普通：從帳戶 A 轉 100 元到帳戶 B。

### 單機版：五行搞定

假設 A、B 都在同一台機器、同一個資料庫：

```
begin transaction
  A.balance -= 100
  B.balance += 100
commit           ← 資料庫保證：要嘛兩行都成、要嘛兩行都不成（原子性）
```

原子性（atomicity）、一致性由本機資料庫的交易保證。你不用想任何失敗——commit 成功就是全成，失敗就是全不成，沒有中間狀態。這是你二十年來的直覺。

### 分散式版：A 在機器 1、B 在機器 2

現在 A 的餘額在機器 1、B 的餘額在機器 2。同一個交易跨了兩台機器。你天真地翻譯成：

```
機器1: A.balance -= 100          機器2: B.balance += 100
       送訊息叫機器2加100  ───────────────>  收到，加 100
```

問題來了。把上面那個 `───送訊息───>` 攤開，部分失敗在每一步都埋伏著：

```
機器1                                        機器2
  │ A -= 100（本地做完了）
  │
  │  send("B 加 100") ─────X 網路丟了───▶     （沒收到）
  │                                          B 沒加，A 卻扣了 → 錢憑空消失
  │
  │  send("B 加 100") ─────────────────▶     收到，B += 100
  │                                          send("done") ──X 丟了──▶
  │  等 ack... timeout                        （機器1 不知道成功了）
  │  以為失敗，重送 "B 加 100" ─────────▶     又收到，B 再 += 100 → 加了兩次
  │
  │  send("B 加 100") ─────────────────▶     收到，開始加...
  │                                          ✗ 機器2 這瞬間當機
  │  等 ack... timeout                        重啟後：B 到底加了沒？沒人知道
```

每一條單機直覺都失效了：

- **原子性沒了**：「A 扣款」和「B 加款」是兩台機器上的兩個獨立動作，中間隔著一個會丟訊息、會延遲、會讓機器當機的網路。沒有任何本機交易能同時涵蓋兩台機器。
- **「失敗就重試」變成陷阱**：因為你分不清「B 沒加」和「B 加了但 ack 丟了」，你的重試可能讓 B 加兩次（�RPC 的 at-least-once 語意，Ch 3 主題）。
- **沒有全域一致的瞬間**：在機器 1 已扣、機器 2 還沒加的那段時間裡，系統的總金額是錯的。任何人這時去查總帳，會看到 100 元憑空蒸發。

要正確做這件事，你需要的東西這門課後面全會教：可靠的訊息語意（Ch 3）、原子提交協定 2PC/3PC（Ch 30）、甚至共識（Part 3）來對「這筆轉帳到底成沒成」達成一致。**一個五行的單機交易，到了分散式世界要動用整套理論。** 這就是難度的量級差別。

## 後續三大難題：全書地圖

把上面所有的痛整理一下，分散式系統的困難可以收斂成三個彼此糾纏的難題。這門課接下來就是輪流深挖它們。

```
                    部分失敗（partial failure）
                    ┌──────────┴──────────┐
                    │  一切困難的總源頭     │
                    └──────────┬──────────┘
          ┌──────────────────┼──────────────────┐
          ▼                   ▼                   ▼
   ① 不可靠的網路         ② 不可靠的時鐘        ③ 順序
   訊息會丟/延遲/          每台機器的時鐘        沒有全域時間，
   重複/亂序；            都在漂移，你不能        怎麼決定「誰先誰後」？
   慢與死分不清           用「時間」判斷順序      因果、全序、共識

   → Ch 2 失敗模型        → Part 1 時間與順序    → Ch 5-7 邏輯時鐘
     Ch 3 RPC 語意          Ch 4 實體時鐘的謊言    → Part 3 共識
```

- **① 不可靠的網路**：訊息會丟、會延遲、會重複、會亂序，而且延遲沒有上界，導致「慢」與「死」不可區分。這是 Ch 2（失敗與網路模型）與 Ch 3（RPC 與訊息語意）的主題，也是全書所有協定都要對抗的基本敵人。

- **② 不可靠的時鐘**：每台機器有自己的石英振盪器，跑得有快有慢（漂移，drift），NTP 校時又會讓時鐘跳來跳去。你**不能**用「機器 A 的時間戳比 B 早，所以 A 先發生」來判斷順序——這個直覺在分散式裡是錯的，而且錯得很隱蔽。Part 1（Ch 4 起）專門處理時間。

- **③ 順序**：既然不能靠實體時間，那「事件的先後」到底怎麼定義？答案是用**因果關係（causality）**而非時間，這催生了 Lamport 時鐘、向量時鐘（Ch 5-6）、全序廣播（Ch 7），最終通向共識——讓一群機器對「事件的順序」達成一致，正是共識問題（Part 3）的核心。

這三者不是獨立的。它們糾纏在一起：因為網路不可靠，所以你想用時鐘來排序；因為時鐘也不可靠，所以你被迫改用因果與共識；而共識協定又必須在不可靠網路上運作。這門課就是沿著這條線，把它們一個一個拆開、再重新組裝成能容錯的真實系統。

## 對比與取捨

| 面向 | 單機系統 | 分散式系統 |
|---|---|---|
| 失敗模式 | 全有或全無（process 死你也死） | **部分失敗**（一部分死、其他活） |
| 失敗可觀測性 | 例外/回傳值，明確 | 「沒回應」，慢與死不可區分 |
| 全域狀態 | 有（同一塊記憶體） | 無（各節點只有局部視角） |
| 時間 | 單一時脈，可信 | 多個漂移時鐘，不可信 |
| 原子操作 | 本機交易保證 | 需要協定（2PC/共識）湊出來 |
| 重試安全 | 通常安全 | 危險（可能重複執行，需冪等） |
| 除錯 | 斷點、堆疊、可重現 | 時序依賴、難重現（故有 Ch 0 模擬器） |

右欄每一格的痛，都是這門課某一章的主題。你可以把這張表當成「為什麼要學後面那些東西」的動機清單。

## 踩雷集錦

1. **「沒回應」就當成「失敗了」直接重試**：錯誤直覺——timeout 了代表對方沒做。正確認識——timeout 只代表「你沒在時限內收到回應」，對方可能根本沒收到、也可能早就做完了。盲目重試會導致重複執行（轉帳加兩次）。正確做法是讓操作**冪等（idempotent）**再重試（Ch 3 詳談）。

2. **用時間戳判斷事件先後**：錯誤直覺——A 的時間戳 `10:00:01` 比 B 的 `10:00:02` 早，所以 A 先發生。正確認識——兩台機器的時鐘會漂移、會被 NTP 往回調，時間戳的大小關係跟真實因果關係沒有可靠的對應。跨機比較時間戳來排序是分散式最經典的 bug 之一（Part 1 會用因果時鐘取代它）。

3. **把 partition（分區）和 crash（當機）混為一談**：錯誤直覺——反正對方都不理我，一樣處理就好。正確認識——crash 是「對方死了，別人也連不上它」；partition 是「你連不上它，但它活得好好的、還在服務網路另一邊的人」。分區時如果兩邊都以為自己是唯一存活方各自做決定，就會產生**腦裂（split-brain）**——兩個 leader、兩份互相矛盾的資料。這是 CAP 定理（Ch 10）的核心場景。

4. **假設訊息只會到一次、且按送出順序到**：錯誤直覺——我先送 A 再送 B，對方就先收到 A。正確認識——底層網路（尤其 UDP、或重試機制介入後）可能亂序、重複送達。任何依賴「訊息恰好一次、依序到達」的邏輯，在真實網路上遲早會被打臉（Ch 3 的 exactly-once 迷思）。

5. **以為加機器一定讓系統更可靠**：錯誤直覺——一台會壞，那我用十台就更穩。正確認識——沒有正確的協調，機器越多，「其中至少一台在任一時刻出問題」的機率反而越高，而且它們之間的協調成本、失敗組合的複雜度是**超線性**增長的。可靠性來自正確的容錯設計，不是來自機器數量本身。

## 進階：再往深一層

**「慢」與「死」不可區分，到底有多根本？** 這不是工程沒做好，是理論下界。在一個**非同步（asynchronous）**網路模型裡——訊息延遲可以任意大但終會送達、沒有上界——你**不可能**寫出一個永遠正確的失敗偵測器（failure detector）。因為對任何你設的 timeout `T`，總存在一個「訊息延遲剛好超過 `T` 但對方其實活著」的執行，你會誤判它死了。Chandra 與 Toueg 在 1996 年的經典論文把失敗偵測器按「完整性」與「準確性」做了嚴謹分類，證明了「解共識所需的最弱失敗偵測器」長什麼樣。我們在 Ch 17（繞過 FLP）會回到這裡。

**那真實系統怎麼活下來的？** 靠**部分同步（partial synchrony）**假設：現實網路「大部分時候」延遲是有界的，只是偶爾抽風。系統設計成「在同步期做出進展、在非同步期只保證不做錯事」。這正是 Raft、Paxos 這些協定能在理論上「不可能」的前提下，實務上跑得好好的原因——它們不承諾「永遠能達成一致」，只承諾「達成一致時一定是對的，且在網路恢復正常後終會達成」。這個微妙的區別（安全性 safety vs 活性 liveness）是整個共識領域的靈魂，Ch 16 會講透。

## 本章重點整理

- 分散式系統的難，**不是**「一台更大的電腦」，而是**部分失敗**：一部分壞了、其他還活著，而且你**分不清它是壞了還是只是慢**。
- 「慢與死不可區分」是無法用工程消除的原罪，源於非同步網路裡訊息延遲沒有上界。它會長成 FLP 不可能定理。
- 八大謬誤是新手會不自覺假設、但全錯的八件事：網路可靠、延遲為零、頻寬無限、網路安全、拓樸不變、單一管理者、傳輸成本零、網路同質。
- 一個五行的單機轉帳，搬到分散式就需要動用可靠訊息、原子提交、甚至共識——難度是量級的跳躍，不是常數的差別。
- 全書地圖收斂成三大難題：**不可靠的網路**（Ch 2-3）、**不可靠的時鐘**（Part 1）、**順序**（因果 → 共識，Part 1 與 Part 3）。三者彼此糾纏。
