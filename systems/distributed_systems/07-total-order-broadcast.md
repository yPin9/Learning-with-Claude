# Ch 7 — 全序廣播

> **目標**：把 Part 1 收尾——從「能判斷順序」跳到「讓所有正確節點以完全相同的順序遞交完全相同的訊息集」。搞懂全序廣播（total order broadcast / atomic broadcast）的精確定義、它為什麼是複製狀態機（RSM）的核心原語，以及最關鍵的一件事：**它跟共識（consensus）等價**——兩者可以互相規約。看三種實作途徑各自的死穴，理解為什麼「排序」在有失敗的世界裡這麼難。

> 若對 Lamport clock 的「時戳 + tiebreak 得全序」不熟，回看 [Ch 5](./05-lamport-clocks.md)；對 vector clock 判因果不熟回看 [Ch 6](./06-vector-clocks.md)。

## 為什麼需要這個？

前兩章我們學會了「判斷順序」：Lamport clock 能給一個尊重因果的全序、vector clock 能判並發。但「一個旁觀者事後能排出順序」和「所有節點在運行時**即時、一致地**以相同順序處理訊息」是兩件差很遠的事。

看一個直接的需求。你想做一個容錯的服務——把同一個服務複製到 5 台機器上，任何一台掛了其他還能頂。作法叫**複製狀態機（Replicated State Machine, RSM，Ch 25 細講）**：每台機器跑一模一樣的確定性狀態機，只要**餵給它們的指令序列完全相同**，它們的狀態就永遠一致。

問題全在「完全相同的指令序列」這句話。客戶端從四面八方送指令來，網路會亂序、會延遲、會丟包，5 台機器各自收到的順序天差地別。如果機器 A 先執行「存 100」再「領 50」（餘額 50），機器 B 先執行「領 50」再「存 100」（若初始為 0，領 50 失敗、餘額 100），兩台狀態就分岔了——複製失去意義。

所以 RSM 需要一個更強的東西：一個**協定**，能保證「所有正確的機器，以完全相同的順序，遞交完全相同的一批指令」。這個協定就是**全序廣播**。它是把「一群機器」變成「一台容錯的機器」的關鍵齒輪。而本章的核心震撼是：**要做到這件事，本質上就是要解共識**——它們是同一個問題的兩張臉。

## 先建立直覺

先分清楚幾種「廣播」的強度，由弱到強：

```
   best-effort broadcast:  盡力送給所有人，送到誰算誰（可能有人沒收到）
        │  加上「可靠」保證
        ▼
   reliable broadcast:     若一個正確節點遞交了 m，所有正確節點最終都遞交 m
        │                  （但各節點遞交的「順序」可以不同!）
        │  加上「順序一致」保證
        ▼
   total order broadcast:  所有正確節點遞交「相同的訊息集」且「順序完全相同」
        （這是我們要的）
```

關鍵直覺：reliable broadcast 保證「大家最終都收到一樣的訊息集合」，但**不保證順序**——A 可能先遞交 m1 再 m2，B 可能先 m2 再 m1。total order broadcast 加上的那一層，正是「順序也必須一致」。而「讓分散在各地、會失敗的節點對一個順序達成一致」——這就踩進共識的地盤了。

一張圖看 total order broadcast 對 RSM 的作用：

```
   客戶端指令（亂序、延遲、來自四方）
        m_c, m_a, m_b, ...
              │
              ▼
        ┌──────────────────────┐
        │  Total Order Broadcast │  ← 決定唯一的全域順序：m_a, m_b, m_c
        └──────────────────────┘
              │         │         │        （每個正確節點收到相同序列）
              ▼         ▼         ▼
          [節點1]    [節點2]    [節點3]
        m_a,m_b,m_c m_a,m_b,m_c m_a,m_b,m_c  ← 相同順序餵給狀態機
              │         │         │
              ▼         ▼         ▼
           狀態相同   狀態相同   狀態相同     ← RSM 保持一致
```

TOB 把「不確定的輸入洪流」整流成「所有節點看到的同一條確定序列」。狀態機是確定的，同樣輸入 → 同樣輸出，於是複製成立。

## 精確定義：全序廣播的四條性質

全序廣播（也叫 atomic broadcast，「atomic」指的是「要嘛所有正確節點都以這個位置遞交、要嘛都不」）由兩個原語 `broadcast(m)` 和 `deliver(m)` 構成，滿足四條性質：

```
  1. Validity（有效性）：正確節點 broadcast 的 m，該節點最終會 deliver m
  2. Integrity（完整性）：每個 m 最多被 deliver 一次，且必須真的有人 broadcast 過
  3. Agreement（一致同意）：若一個正確節點 deliver m，所有正確節點最終都 deliver m
  4. Total Order（全序）：若正確節點 p 在 deliver m' 前 deliver m，
        則任何正確節點 deliver m' 前也必先 deliver m
```

第 3 條（Agreement）是 reliable broadcast 就有的；**第 4 條（Total Order）是全序廣播獨有的、也是最貴的那條**。它要求：任兩則訊息 m 和 m' 的相對順序，在所有正確節點上都一致。注意它不要求這個順序跟因果或實體時間有任何關係——它只要求**一致**。所有節點都把 m 排在 m' 前，或都排在後，不能有人排前有人排後。

> 有些定義還會加上第 5 條 **Causal Order（因果序）**：若 `broadcast(m) → broadcast(m')`（happens-before），則所有節點 deliver m 在 m' 前。這是「因果全序廣播」，比純全序更強。本 Part 練習 A 做的因果遞交是這條的一個方向；純 TOB 不強制因果。

## 廣播的四種順序保證，別搞混

「順序」這個詞在廣播裡有四種強度，常被混為一談。先把它們的關係釘清楚，因為工程上選錯強度不是「不夠強」就是「白付代價」。

```
   FIFO order:    來自同一寄件者的訊息，按寄件順序遞交
                  （p 先 broadcast m1 再 m2 => 大家都先 deliver m1）
                  但不同寄件者之間、以及有因果關係的訊息，順序不管

   Causal order:  FIFO + 因果。若 broadcast(m) → broadcast(m')（happens-before，
                  跨寄件者也算），則所有節點先 deliver m
                  （練習 A 做的就是這個。它是 FIFO 的超集）

   Total order:   所有節點遞交順序完全一致（但不保證這個順序尊重因果或 FIFO）

   FIFO-total / causal-total: 全序 + 額外保 FIFO / 因果
```

關鍵關係，記三句話：

- **Causal order 蘊含 FIFO order**（因果包含「同一寄件者的先後」這種本地 happens-before），反之不然。
- **Total order 與 Causal order 互不蘊含**：全序保證「大家順序一致」，但那個一致的順序**可能違反因果**（把 reply 排在 post 前，只要所有節點都這樣排，就仍滿足 total order）。反過來因果序保證尊重因果，但不同節點對**並發**訊息的順序可以不同（不是全序）。
- 真實系統想要的常是 **causal-total order**——既全序一致、又尊重因果。這最貴，因為它疊了兩層保證。

```
      強度關係（→ 表示「蘊含」）：

      Causal order ──→ FIFO order ──→ (reliable) broadcast
           ↑
      Causal-total order
           ↓
      Total order ──────────────────→ (reliable) broadcast

      Total 和 Causal 各管一件事，互不蘊含；疊起來才是 causal-total
```

為什麼這重要：本章談的「全序廣播」是 total order。它保證所有節點順序一致，但**不保證那個順序尊重你在 Ch 5-6 學的因果**。如果你的應用需要因果（社群訊息串、購物車），純 total order 不夠，你要 causal-total——或至少 causal order（練習 A）。搞清楚需求要哪一層，別無腦上最貴的。

## 底層機制：三種實作途徑，三個死穴

怎麼實作全序廣播？有三條經典路線，看它們各自在哪裡崩，你就懂了為什麼這件事難。

### 途徑一：中央 sequencer（單點編號）

最直白的想法：指定一個節點當 **sequencer（定序器）**，所有訊息先送給它，它給每則訊息貼一個單調遞增的序號，再廣播出去；大家按序號遞交。

```
        m_a ─┐
        m_b ─┼──> [Sequencer] ── 貼號 ──> broadcast(1:m_b, 2:m_a, 3:m_c)
        m_c ─┘        │
                  單調遞增計數器          所有節點按 1,2,3 遞交 => 全序達成
```

**死穴：sequencer 是單點故障（single point of failure）**。它一掛，整個系統停擺，沒人能定序。你想換一個 sequencer 頂上——但「大家對『誰是新 sequencer』達成一致」本身就是一個共識問題。而且舊 sequencer 是真掛了還是只是網路慢（你分不出來，Ch 2 的 partial failure）？如果它沒真掛、你又選了新的，兩個 sequencer 同時貼號，全序就毀了（腦裂）。Kafka 早期的單一 controller、以及很多 primary-based 系統，本質都是這個模式，也都得額外解決「controller 換人」的共識問題。

### 途徑二：Lamport clock 全序（去中心化但不容錯）

用 Ch 5 學的「Lamport timestamp + node id tiebreak」給每則訊息一個全域唯一、且尊重因果的時戳，大家按時戳排序遞交。聽起來很美——去中心化、沒有 sequencer 單點。

問題在**「什麼時候能安全遞交一則訊息」**。你收到一則時戳 15 的訊息，能立刻遞交嗎？不能——因為可能還有一則時戳 12 的訊息正在網路上飛，還沒到你這。你若先遞交 15，之後 12 到了就破壞全序了。**要安全遞交時戳 t 的訊息，你必須確定「不會再有時戳 ≤ t 的訊息出現」**。

Lamport 原論文的解法是：**每則訊息都要收到來自所有節點的 ack**（或每個節點都持續發訊息讓你知道它的時戳進度），你才知道某個時戳以下已經封閉、可以遞交。

```
   節點 i 想遞交時戳 t 的訊息 m：
     必須先收齊「所有其他節點時戳都已 > t」的證據
     └─ 靠：每個節點對每則訊息回 ack，或持續廣播自己的時戳
```

**死穴：要「所有節點」的 ack，一個節點掛了就永遠等不到，系統卡死——不容錯**。這正好對照 Ch 0 那句「pinger 丟一次就斷鏈」的精神：需要全體參與的協定，容不下任何一個失敗。只要有一個節點慢或掛，全序就推不進。

把這個「為什麼要等全體 ack」用一個具體例子跑一遍，你會秒懂那個死穴：

```
   三節點 P、Q、R，各自 broadcast 一則訊息，用 Lamport 時戳排序。
   假設 P 送出 m_P 帶時戳 5，Q 送出 m_Q 帶時戳 3。

   R 先收到 m_P (ts=5)。R 能遞交 m_P 嗎？
     不能! 因為 R 還沒收到 m_Q (ts=3)，而 3 < 5。
     若 R 先遞交 m_P、之後 m_Q 到了，R 就得把 ts=3 排在已遞交的 ts=5 後面
     => 破壞全序（別的節點可能先收到 m_Q、把它排前面）。

   R 怎麼確定「不會再有 ts <= 5 的訊息」？
     它得等到「每個節點的 Lamport clock 都已 > 5」的證據。
     作法：每個節點對收到的每則訊息回 ack（ack 也帶自己當前時戳），
     R 收齊「來自 P、Q、R 三方、時戳都 > 5」的 ack 後，
     才敢說「ts<=5 的訊息已全部到齊」，安全遞交 m_P。

   現在 Q 掛了。R 永遠收不到 Q 的 ack => R 永遠不敢遞交 m_P => 卡死。
```

這個例子把「不容錯」講死了：安全遞交的前提是「時戳窗口封閉」，而封閉需要**每一個**節點的確認。少一個節點的音訊，窗口就永遠不封閉。這不是實作笨，是「要全體同意」這個結構本身的宿命。要打破它，只能改成「多數同意就夠」——而「多數同意」正是共識。

### 途徑三：靠共識（唯一容錯的路）

前兩條路的死穴，都指向同一件事：**要在「有節點會失敗」的世界裡達成全序，你需要一個能容忍少數失敗、還能對順序達成一致的協定**——那就是共識。

作法是把「決定第 i 個位置放哪則訊息」變成一連串共識實例：對位置 1 跑一次共識，決定放 m_a；對位置 2 跑一次，決定放 m_b……只要共識協定能容忍少數節點失敗（如 Raft/Paxos 容忍不到半數掛掉），全序廣播就繼承這個容錯能力。

```
   position 1: [共識] => 大家同意放 m_a
   position 2: [共識] => 大家同意放 m_b
   position 3: [共識] => 大家同意放 m_c
   ...每個位置一次共識，多數活著就能推進，不怕少數掛掉
```

這就是 Raft、Multi-Paxos、Zab、Viewstamped Replication 在做的事——它們本質上都是全序廣播的實作。Raft 的「log」就是那個全序序列，「log replication」（Ch 21）就是讓所有節點在每個 log 位置放相同的 entry。**這也是為什麼 Part 3 整個在講共識：共識是全序廣播唯一容錯的實作路徑**。

## 核心事實：全序廣播 ≡ 共識（互相可規約）

這是本章最重要、也是連接 Part 1 和 Part 3 的那句話：**全序廣播和共識是等價的**——你有其中一個，就能實作另一個。這不是比喻，是可以嚴格證明的雙向規約。

**共識 → 全序廣播**（用共識做全序廣播）：就是途徑三。對每個 log 位置跑一次共識決定放哪則訊息，串起來就是全序廣播。

**全序廣播 → 共識**（用全序廣播解共識）：更漂亮。共識問題是「一群節點對『一個值』達成一致」。用全序廣播：每個節點把自己提議的值 `broadcast` 出去；因為全序廣播保證**所有正確節點遞交相同順序的相同訊息集**，於是每個節點都看到同一個「第一則被遞交的提議」——大家一致地選「第一則遞交到的值」當共識結果。順序一致 → 選出的第一個一致 → 共識達成。

```
   全序廣播 -> 共識：
     每個節點 broadcast(自己的提議值)
     全序廣播保證所有正確節點遞交順序相同
     => 大家看到相同的「第一則」訊息
     => 都選第一則的值 => 對「一個值」達成一致 => 共識!
```

這個等價的重量級後果：**Ch 16 的 FLP 不可能定理**（在非同步網路 + 一個節點可能失敗的前提下，沒有確定性演算法能保證解出共識）**直接適用於全序廣播**。也就是說——**在非同步網路裡，沒有全序廣播演算法能保證總是在有限時間內定序完成**。前面途徑一、二的死穴不是實作不夠聰明，是理論下界在說話。所有真實系統（Raft/Paxos）都是靠「引入部分同步假設 + timeout」來繞過 FLP（Ch 17），沒有誰真的違反了它。

## 對比與取捨

| 途徑 | 去中心化 | 容錯 | 順序保證 | 死穴 | 真實對應 |
|---|---|---|---|---|---|
| 中央 sequencer | 否 | 否（單點） | 全序 | sequencer 掛 = 停擺；換人要共識 | Kafka controller、primary-based |
| Lamport clock 全序 | 是 | **否** | 全序（尊重因果） | 要全體 ack，一個掛就卡死 | Lamport 原論文互斥鎖 |
| 靠共識 | 是 | **是（容忍少數失敗）** | 全序 | 慢（每位置一次共識）、受 FLP 限制 | **Raft/Multi-Paxos/Zab/VR** |

沒有免費午餐：想要**容錯**的全序，就得付共識的代價（多輪訊息往返的延遲、多數節點存活的要求、FLP 決定的「非同步下無法保證終止」）。這也是為什麼 Part 3 花十章講共識——它是全序廣播、也就是所有容錯複製系統的地基。

## 踩雷集錦

1. **「reliable broadcast 就夠了，反正大家都收到一樣的訊息」→ 順序不一致照樣讓 RSM 分岔**。reliable broadcast 只保證「相同的訊息集」，不保證「相同的順序」。RSM 要的是順序也一致（存款/取款換順序結果就不同）。差的那一層——Total Order——正是最貴、需要共識的那層。別把「大家都收到了」誤當成「大家順序一致」。

2. **「Lamport clock 能給全序，那全序廣播用它做不就好了，何必共識」→ 漏了『何時能安全遞交』**。Lamport clock 能**排序**，但無法容錯地決定「某時戳以下已封閉、可以遞交」——那需要全體參與，一個節點掛就卡死。能排序 ≠ 能容錯地即時遞交。這是 Ch 5 tiebreak 全序和真正全序廣播的關鍵鴻溝。

3. **「全序廣播和共識是兩個不同的問題」→ 它們等價，可互相規約**。很多人以為「排序訊息」和「對一個值達成一致」是兩回事。本章證明了雙向規約：有共識能做全序廣播，有全序廣播能解共識。所以 FLP 對共識的限制，一字不差地套用在全序廣播上。

4. **「換掉掛掉的 sequencer 很簡單，選一個新的就好」→ 選新 sequencer 本身是共識問題**。而且要先確定舊的「真的掛了」而非只是慢（partial failure 分不出來）。選錯 → 兩個 sequencer 同時定序 → 腦裂 → 全序毀。「換 leader」在共識協定裡（Raft 選舉、Ch 20）是整個協定最微妙、最容易出 safety bug 的部分，絕不是「選一個就好」。

5. **「全序廣播保證的順序反映因果或真實時間」→ 純 TOB 只保證『一致』，不保證因果**。Total Order 那條性質只要求所有節點順序**相同**，不要求這個順序尊重 happens-before。要因果全序得額外加 Causal Order 性質（練習 A 的方向）。別假設全序廣播出來的順序跟事件真實發生的因果一致。

## 進階：再往深一層

- **為什麼「atomic broadcast」叫 atomic**：這個別名來自它的「全有全無」性質——一則訊息要嘛被所有正確節點在**相同的邏輯位置**遞交，要嘛都不遞交，不會有「一半節點在位置 3 遞交它、另一半在位置 5」這種撕裂。這跟資料庫交易的 atomicity 是同一個精神：一批操作作為不可分割的整體生效。Ch 30 的 2PC（兩階段提交）處理的也是這種「全有全無」，只是場景是跨節點交易而非訊息排序。

- **TOB 是很多系統原語的共同祖先**：一旦你有了全序廣播，很多東西幾乎免費——線性一致的 KV store（Ch 26，把讀寫都當訊息廣播）、分散式鎖（etcd/ZooKeeper 的核心，Ch 41）、成員變更（把「加入/移除節點」當一則要定序的訊息）。ZooKeeper 的 Zab 協定就是一個為「主備 + 全序廣播」量身打造的共識變體。理解 TOB 是理解這整類協調服務的鑰匙。

- **FLP 的繞法預告**：既然 FLP 說非同步下沒有確定性演算法能保證全序廣播終止，真實系統怎麼辦？它們引入**部分同步（partial synchrony）**假設——「網路大部分時候夠快，只是偶爾慢」——並用 timeout 來偵測疑似失敗、觸發 leader 選舉。這不違反 FLP（FLP 講的是「保證」，真實系統只求「通常能終止」），細節是 Ch 16-17 的主題。本章你只要記住：全序廣播的難度有一個理論下界，且那個下界就是 FLP。

## 本章重點整理

- 全序廣播（total order / atomic broadcast）要求**所有正確節點遞交相同的訊息集、且順序完全相同**——比 reliable broadcast 多的「Total Order」那條是最貴的。
- 它是**複製狀態機（RSM）的核心原語**：把亂序的指令洪流整流成所有節點看到的同一條確定序列，讓確定性狀態機保持一致。
- 三種實作途徑各有死穴：中央 sequencer（單點故障、換人要共識）、Lamport clock 全序（要全體 ack、不容錯）、**靠共識（唯一容錯路徑）**。
- **全序廣播與共識等價**：可雙向規約。有共識能做 TOB（每位置一次共識），有 TOB 能解共識（選第一則遞交的值）。
- 這個等價的後果：**FLP 不可能定理直接適用於全序廣播**——非同步網路下沒有確定性演算法能保證定序總在有限時間完成。真實系統靠部分同步 + timeout 繞過（Ch 17），沒人真的違反 FLP。
