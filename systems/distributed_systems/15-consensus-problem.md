# Ch 15 — 共識問題定義

> **目標**：把「共識（Consensus）」從一個模糊的口語詞，變成一個有形式定義、能拿來證明的數學問題。我們要搞清楚共識到底要求哪三件事、為什麼這三件事湊在一起這麼難、以及為什麼幾乎整個分散式協調（leader election、原子提交、成員變更）最後都歸約到這一個問題。這一章不寫程式，但它是 Part 3 之後所有硬核推導（FLP、Paxos、Raft）的地基。

## 為什麼需要這個？

前兩個 Part 我們談了時間、順序、複製、一致性模型。你可能已經隱隱感覺到：這些東西背後有一個共同的核心問題——**一群各自獨立、會當機、彼此只能靠會延遲會丟失的訊息溝通的節點，怎麼對「某一件事」達成一致？**

「達成一致」聽起來很簡單，簡單到不像個研究問題。你可能會說：「不就投票嗎？多數決不就好了？」

問題出在「一致」這個詞被我們用得太隨便。到底什麼叫一致？

- 如果三個節點各自收到不同的客戶端請求，最後要「一致」——是要它們都選同一個嗎？
- 如果投票時有節點當機了，剩下的能不能決定？
- 如果網路把節點切成兩半，兩半各自「多數決」出不同結果，這算達成一致嗎？
- 如果永遠有節點在當機、重啟、當機、重啟，這個系統是不是永遠決定不了？

在 1980 年代之前，工程師處理這些問題全靠直覺和 ad hoc 的協定，結果就是一堆看似能動、實則在特定時序下會腦裂（split-brain）的系統。直到 Lamport、Fischer、Lynch 這批人把「共識」形式化成一個有嚴格定義的問題，我們才第一次能問出精確的問題：「在這個失敗模型下，這個要求可不可能被滿足？」——然後給出**可以被證明**的答案。

這一章就是要把那個精確定義建立起來。沒有這個定義，FLP 不可能定理（Ch 16）就無從陳述，Paxos（Ch 18）的正確性也無從論證。

## 先建立直覺

先給一個最乾淨的心智圖像。想像 N 個節點，每個節點手上握著一個**提議值（proposed value）**——可能是它收到的客戶端請求、可能是它想選的 leader、可能是它對某筆交易的表決（commit / abort）。

```
     節點 P0        節點 P1        節點 P2        節點 P3
     propose        propose        propose        propose
       "A"            "B"            "A"            "C"
        │              │              │              │
        └──────────────┴──────┬───────┴──────────────┘
                              │
                   （一陣訊息往返、可能有節點當機）
                              │
        ┌──────────────┬──────┴───────┬──────────────┐
        ▼              ▼              ▼              ▼
      decide         decide         decide         decide
       "B"            "B"           (當機)          "B"
```

共識問題就是：設計一個協定，讓每個沒當機的節點最後都 `decide` 出一個值，而且這些 decide 出來的值要滿足一組性質。**注意上圖的關鍵細節**：最後大家都決定了 `"B"`，但 `"B"` 是 P1 提議的——只要它是**某個節點真的提議過**的值就合法，不需要是多數提議的值，也不需要是「最好」的值。共識不保證你選到最優，它只保證大家**選到同一個、而且是有人提過的**。

還有一個容易漏掉的點：當機的 P2 不需要 decide。共識只約束「還活著的」節點。這個放寬非常重要——如果要求連當機節點都得達成一致，那問題直接無解（死人不會投票）。

### 一個具體場景：為什麼「投票」不夠

先把「共識很難」變得可感。設想三台伺服器要選一個 leader，用最直覺的「大家投票、多數決」：

```
   P0 提議自己       P1 提議 P2        P2 提議自己
        │               │                │
   場景 A（同步、無失敗）：
     三則票都及時送達，大家算票 → P2 得 2 票 → 一致選 P2。皆大歡喜。

   場景 B（P1 的票延遲了）：
     P0 只收到自己的票 + P2 的票（各 1），P2 也是。
     兩邊都「還在等 P1」。要等多久？非同步下沒有上界。
     若 P0 等不下去、自行決定「我贏（1 vs 1 平手我優先）」
       而 P2 也同時「我贏」→ 兩個 leader → 腦裂。

   場景 C（P1 其實當機了，不是慢）：
     P0、P2 永遠等不到 P1 的票。它們分不出「P1 死了」還是「P1 的票還在路上」。
       等下去 → 可能永遠不 decide（違反 termination）
       不等 → 可能誤判、腦裂（違反 agreement）
```

場景 C 是整個共識問題的縮影，也是下一章 FLP 的靶心：**在非同步網路裡，「一個節點沒回應」和「一個節點死了」長得一模一樣，而你被迫在「等到腦裂」和「不等就終止」之間二選一。** 「多數決」這三個字完全沒告訴你該怎麼處理場景 B、C——這就是為什麼共識是一個需要嚴謹協定（Paxos、Raft）而非一句口號的問題。

## 共識的三個性質

一個正確的共識協定必須同時滿足以下三個性質。這三個是這一整章、甚至整個 Part 3 的核心，值得逐字咬清楚。

### 1. Agreement（一致性）

> **沒有兩個正確的節點會 decide 出不同的值。**

這是最直覺的一條：不能腦裂。如果 P0 決定 `"A"` 而 P1 決定 `"B"`，協定就錯了。注意它說的是「正確的（correct，指沒當機、沒說謊的）節點」——在 crash 模型下就是「還活著的節點」，在拜占庭模型（Ch 32）下還要排除說謊的節點。

有些教科書把這條再細分成：

- **Uniform Agreement**：連「即將當機」的節點 decide 的值也不能與別人衝突。也就是說，一個節點就算 decide 完下一秒就死，它 decide 的值也必須跟活著的人一致。
- **(Non-uniform) Agreement**：只要求活到最後的節點之間一致，允許一個快死的節點 decide 一個「錯」的值（反正它馬上就消失了）。

差別很微妙但在實務上要命：如果一個快死的節點先 decide 了一個孤兒值、還把它回覆給了客戶端，然後才死——客戶端記得的答案就跟系統最終的不一致。多數嚴肅的協定（Paxos、Raft）都做到 uniform agreement，我們預設講的就是它。

### 2. Validity / Integrity（有效性 / 完整性）

> **被 decide 的值，必須是某個節點真的 propose 過的。**

這條防止一個作弊的「捷徑」：假如沒有這條，我可以寫一個「共識協定」——所有節點無條件 decide 常數 `42`。它滿足 Agreement（大家都選 42）、滿足 Termination（馬上就決定），但它完全沒用，因為 42 可能根本沒人提過。Validity 把這種退化解排除掉：**輸出必須來自輸入。**

這條有幾個常見變體，強度不同：

| 變體 | 要求 |
|---|---|
| **Validity（弱）** | decide 的值是**某個**節點提議過的 |
| **Integrity** | 每個節點**最多 decide 一次**（不能反悔改答案） |
| **Non-triviality** | 若所有節點都提議同一個 v，則只能 decide v |

Non-triviality 是一個特別有用的加強版：如果全體一致提議 `commit`，那結果不能莫名其妙變成 `abort`。原子提交（atomic commit）協定就需要這種強度——只要有一個參與者說 abort，結果就得是 abort；全體說 commit，結果才能 commit。這比一般共識的 validity 更嚴格，我們在 Ch 30 講 2PC 時會回來。

### 3. Termination（終止性）

> **每個正確的節點最終都會 decide 一個值。**

前兩條是 **safety（安全性）**——它們規定「壞事永遠不會發生」（不會腦裂、不會憑空捏值）。Termination 則是 **liveness（活性）**——它規定「好事最終會發生」（大家終究會決定）。

這個 safety / liveness 的二分法是整個分散式理論的骨幹，一定要內化：

```
  safety   : "什麼壞事永遠不發生"  →  違反的話，你能在有限時間指出「就是這裡錯了」
             （腦裂發生的那一刻，你抓得到現行犯）

  liveness : "什麼好事最終會發生"  →  違反的話，你永遠指不出「就是這裡卡住了」
             （系統只是還沒決定——你怎麼知道它是卡死還是再等一下就好？）
```

這個不對稱正是共識之難的根源，也是下一章 FLP 定理的靶心。**FLP 說的正是：在完全非同步的世界裡，只要有一個節點可能當機，你就沒辦法同時保住 safety 和 liveness。**你可以放棄 liveness 換 safety（寧可卡住也不腦裂——這是 Paxos/Raft 的選擇），但你不能兩個都要。這一句話現在聽像口號，Ch 16 會把它證明出來。

> 若對 safety / liveness 的區分還沒感覺，可以回想 Ch 10 CAP 定理：CAP 的「C」（一致性）是 safety，「A」（可用性）是 liveness 的一種，「P」（分區容忍）則是你被迫接受的失敗模型。共識問題其實就是 CAP 在「單一決定」這個最小場景下的濃縮版。

## 為什麼共識是分散式的核心？

共識之所以值得一整個 Part 死磕，是因為分散式系統裡幾乎所有「要大家對某件事說法一致」的問題，**都能歸約（reduce）到共識**。歸約的意思是：如果你有一個共識黑盒子，你就能用它解掉這些問題。反過來，這些問題也都至少和共識一樣難。

### Leader election ≈ 共識

選 leader 就是：一群節點對「誰是 leader」達成一致。提議值是候選人的 ID，decide 出來的就是 leader。Agreement 保證不會選出兩個 leader（否則腦裂），Validity 保證選出來的是真的有參選的節點，Termination 保證最終選得出來。**Raft 的選舉（Ch 20）本質上就是拿共識來選 leader**——只是它把共識和選舉揉在同一套協定裡了。

### 原子提交（atomic commit）≈ 共識

分散式交易要嘛全體 commit、要嘛全體 abort，不能一半 commit 一半 abort。這就是對「commit 還是 abort」達成一致。它需要前面說的 non-triviality 加強版（一票否決 → abort）。2PC（Ch 30）是一個**不容錯**的原子提交協定；把它做成容錯的，就得在底下墊一層真正的共識（Paxos Commit）。

### 成員變更（membership change）≈ 共識

叢集要加一台機器、踢掉一台當機的機器——所有節點必須對「現在的成員名單是什麼」達成一致，否則有人以為叢集有 5 台、有人以為有 3 台，quorum 的計算就會打架，直接腦裂。Raft 的 joint consensus（Ch 23）就是拿共識來變更成員。

### 互斥鎖（distributed lock）≈ 共識

分散式鎖要保證「同一時刻最多一個客戶端持有鎖」。這就是對「誰現在持有鎖」達成一致——Agreement 防止兩個客戶端同時以為自己拿到鎖（否則兩個都去改同一份資料，資料損毀）。這也是為什麼「用 Redis SETNX 做分散式鎖」在網路分區下不可靠：它沒有真正的共識底層，分區時兩邊各自 SETNX 成功就雙持鎖。要正確的分散式鎖，底下得是 etcd / ZooKeeper 這種有共識的系統。這是 Ch 44 會回頭談的一個經典陷阱（Martin Kleppmann 那篇著名的「How to do distributed locking」）。

### 一句話總結歸約

```
         ┌─────────────────────────────────────────┐
         │            共識（Consensus）              │
         │   "對單一值達成一致"                       │
         └─────────────────────────────────────────┘
              ▲          ▲            ▲          ▲
              │          │            │          │
        leader       原子提交      成員變更     互斥鎖
        election    atomic commit  membership  distributed lock
              │          │            │          │
        全都能用共識這個黑盒子解，也全都至少和共識一樣難
```

所以我們死磕共識不是學術潔癖：把這一個問題解對、解到能證明，上面這一整排實務問題就都有了正確的地基。

## 共識 ≡ 全序廣播（total order broadcast）

還有一個更深的等價關係，值得單獨拉出來講，因為它把 Ch 7 的內容和 Part 3 縫在了一起。

> 若對全序廣播不熟，回看 [Ch 7 全序廣播](./07-total-order-broadcast.md)。

**全序廣播（total order broadcast，又稱 atomic broadcast）** 要求：所有節點以**完全相同的順序**遞交（deliver）一串訊息。不是只有單一個值達成一致，而是對「一整串訊息的順序」達成一致。

它跟共識是**雙向可規約**的——兩者難度完全相同：

**共識 → 全序廣播（用共識實作全序廣播）**：把「決定第 i 筆訊息是什麼」跑一次獨立的共識。第 0 筆跑一次共識、第 1 筆跑一次共識……每一輪共識決定 log 裡下一個位置放誰。因為每個位置都由共識定死，所有節點看到的順序自然相同。**這正是 multi-Paxos（Ch 19）和 Raft log replication（Ch 21）在做的事**——一連串共識實例（instance）串成一本 log。

```
  共識實例 #0 ─decide→ msgA ┐
  共識實例 #1 ─decide→ msgC ├─► 所有節點看到的全序 log: [A, C, B, ...]
  共識實例 #2 ─decide→ msgB ┘   （每個格子由一次獨立共識定死，故全體一致）
```

**全序廣播 → 共識（用全序廣播實作共識）**：想 propose 一個值，就把它廣播出去；規則是「大家 deliver 到的**第一則**訊息，就是 decide 的值」。因為全序廣播保證所有人 deliver 順序相同，所以所有人看到的第一則訊息必然是同一則 → 大家 decide 同一個值，Agreement 成立。

這個等價關係的意義極大：它告訴我們，「複製狀態機（RSM）」——讓一群機器對同一串指令達成一致並依序執行——**本質上就是共識問題的實用化身**。你之後看到的所有「用 Raft 做一個 KV store」（Ch 26）、「Kafka 的 replicated log」（Ch 40），骨子裡都是全序廣播，也就都是共識。

## 失敗模型下的難度：一個預告

到目前為止我們只定義了問題，還沒說它有多難。難度**完全取決於失敗模型**——同一個共識問題，在不同假設下難度天差地別。

> 若對失敗模型與同步/非同步的區分不熟，回看 [Ch 2 失敗與網路模型](./02-failure-and-network-models.md)。

用一張表先給你一個地圖，接下來三章會逐格填滿：

| 失敗模型 | 網路模型 | 共識可解嗎？ | 對應章節 |
|---|---|---|---|
| 無失敗（節點都不當） | 任意 | 可解，且簡單 | — |
| Crash（會當但不說謊） | **完全同步**（訊息延遲有已知上界） | 可解 | Ch 2 |
| Crash | **完全非同步**（延遲無上界） | **不可能**（確定性、保證終止） | **Ch 16 FLP** |
| Crash | **部分同步**（最終會變同步） | 可解（放棄「總是」終止） | Ch 17, 18, 20 |
| Byzantine（會任意說謊） | 部分同步 | 可解，但要 3f+1 節點 | Ch 32, 33 |

這張表裡最刺眼的一格是第三列：**完全非同步 + 只要一個節點可能 crash → 不可能有保證終止的確定性共識**。這就是 FLP 不可能定理，是整個領域最重要的負面結果。它不是說「共識永遠做不到」——你日常在用的 etcd、ZooKeeper、Spanner 全都在做共識——而是說「你不能在最悲觀的網路假設下，同時要求 100% 保證終止」。真實系統怎麼繞過這個天花板（Ch 17），是這整個 Part 的主線。

## 對比與取捨

把幾個容易混淆的近親問題並排，看清楚共識的邊界：

| 問題 | 要決定什麼 | 和共識的關係 |
|---|---|---|
| **共識（Consensus）** | 單一個值 | 本體 |
| **全序廣播** | 一串訊息的順序 | 與共識等價（雙向規約） |
| **原子提交** | commit / abort | 共識 + non-triviality 加強 |
| **Leader election** | 誰是 leader | 規約到共識 |
| **可靠廣播（reliable broadcast）** | 「訊息有沒有送到所有人」 | **比共識弱**（不要求順序一致，非同步下可解） |
| **failure detector** | 「誰死了」 | 是**解共識的工具**（Ch 17），本身不是共識 |

最後兩列是關鍵的「比共識容易」的問題。可靠廣播只要求「送到就大家都送到」，不管順序，所以它在非同步下可解，不受 FLP 限制。這告訴我們：**FLP 卡的不是「傳訊息」，而是「對順序/單一值達成一致並保證終止」**。搞清楚哪些問題比共識弱、哪些和它一樣難，是這一領域的基本功。

## 踩雷集錦

1. **「共識就是多數決」**：錯得離譜但極常見。多數決是共識協定裡**用到的一個機制**（quorum），不是共識本身。多數決沒有處理「投票時有人當機怎麼辦」「網路分區讓兩邊各自多數怎麼辦」「訊息延遲讓你不知道該等多久」——這些才是共識的真正難點。把共識等同於多數決，你就會寫出在 partition 下腦裂的系統。

2. **「decide 的值一定是多數提議的值」**：不是。Validity 只要求 decide 的值是**某一個**節點提議過的，可以是少數派提議的、甚至是唯一一個節點提議的。Paxos 裡最後被決定的值，往往是「第一個成功寫進多數 acceptor 的提議」，跟「多少人提議它」無關（Ch 18 會看得很清楚）。

3. **「Termination 是理所當然的，協定寫對了自然會終止」**：這是最貴的一個誤解。Termination 是 liveness，而 FLP 證明了它在非同步下無法被確定性協定保證。所有真實協定為了 safety，都**主動放棄了「總是終止」**——它們只保證「在網路夠好的時候終止」。你以為理所當然的東西，是整個領域最難的部分。

4. **「當機的節點也得達成一致」**：不需要。共識只約束 correct（活著且誠實）的節點。硬要求死掉的節點達成一致，問題直接無解。但要小心 uniform agreement 的陷阱：一個**還沒死但即將死**的節點若先 decide 了並回覆客戶端，它的答案也必須和大家一致——這是實務上真的會咬人的地方（Ch 22 Raft 的 committed 定義就在防這個）。

5. **「共識能保證選到最好 / 最正確的值」**：不能，也不該期待。共識只保證「大家選到同一個、而且有人提過的值」。至於那個值好不好、對不對，是應用層的事。把共識當成「找出正確答案的機器」，你會問錯問題——它是「讓大家對某個答案達成一致的機器」，答案本身的品質不歸它管。

## 進階：再往深一層

- **共識的下界（lower bound）**：不只是「可不可能」，還有「至少要幾個節點、幾輪訊息」。在 crash 模型下容忍 f 個失敗需要 `2f+1` 個節點（多數決要能在死了 f 個之後還湊得出多數）；拜占庭模型下需要 `3f+1`（Ch 32 會推導為什麼多這麼多）。同步模型下，容忍 f 個 crash 的共識**至少需要 f+1 輪**訊息——這是 Dolev-Strong 那條線的結果，證明相當漂亮，有興趣可查「consensus round complexity lower bound」。

- **共識數（consensus number）**：Herlihy 的 wait-free hierarchy 從**共享記憶體原語**的角度給共識分級。純 read/write 暫存器的共識數是 1（解不了兩個以上節點的共識），而 compare-and-swap（CAS）的共識數是 ∞（能解任意多節點的共識）。這解釋了為什麼你在寫 lock-free 資料結構時 CAS 這麼萬能——它在共享記憶體世界裡的地位，等同於共識在訊息傳遞世界裡的地位。這條線把分散式共識和你在 kernel / lock-free 裡碰到的 CAS 縫在了一起。

- **k-set agreement**：把「大家 decide 同一個值」放寬成「大家 decide 的值最多有 k 種」。k=1 就是共識。這個放寬讓某些原本不可能的情況變可能，是研究「共識到底難在哪一步」的解剖刀。

## 本章重點整理

- 共識 = 一群會當機、只能靠不可靠訊息溝通的節點，對**單一個值**達成一致。
- 三個性質缺一不可：**Agreement**（不腦裂，safety）、**Validity/Integrity**（值來自輸入、不反悔，safety）、**Termination**（最終決定，liveness）。
- safety / liveness 的二分是骨幹：safety 違反抓得到現行犯，liveness 違反你永遠不知道是卡死還是快好了。FLP 卡的正是「非同步下 safety 和 liveness 不可兼得」。
- 共識是分散式協調的核心：leader election、原子提交、成員變更全部**歸約到共識**。
- 共識 **≡ 全序廣播**（雙向可規約），而全序廣播就是複製狀態機的骨架——這條等價把 Ch 7 和整個 Part 3 縫起來，也是 multi-Paxos / Raft log 的本質。
- 難度完全取決於失敗模型。最刺眼的一格：**非同步 + 一個 crash → 不可能保證終止**（下一章證明）。
