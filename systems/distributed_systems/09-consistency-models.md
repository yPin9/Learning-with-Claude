# Ch 9 — 一致性模型光譜

> **目標**：把「一致性」這個被講爛卻很少講清楚的詞，拆成一整條有嚴謹定義的光譜。我們會**精確定義** linearizability（線性一致）、sequential consistency（順序一致）、causal consistency（因果一致）、eventual consistency（最終一致），每一個都配一張讀寫時序的 ASCII 圖，說清楚它允許什麼、禁止什麼。並且要一勞永逸地分開兩個最常被混淆的詞：**一致性模型（consistency model）≠ 共識（consensus）**。這是 Part 2 最重、最需要慢讀的一章。

上一章我們讓資料有了多個副本，也埋下了原罪：副本會不一致。但「不一致」到底有多不一致？「一致」又一致到什麼程度？工程師嘴上天天講「這個系統是強一致的」「那個是最終一致的」，但如果你追問「強到什麼程度、允許讀到多舊的值、允許看到別人沒看到的順序嗎」，多數人答不出來。原因是**一致性不是一個布林值，是一整條光譜**，而這條光譜有數十年的形式化研究把每一級釘死了。這一章就是帶你把這些定義吃進去。

> 這一章大量用到「事件的順序」「因果關係」「並行」這些概念。若對它們不熟，強烈建議回看 [Ch 5 Lamport 邏輯時鐘](./05-lamport-clocks.md) 和 [Ch 6 Vector Clock](./06-vector-clocks.md)——因果一致性直接建立在 vector clock 偵測到的因果關係上。

## 為什麼需要這個？

回到最實際的問題。你有一個複製的計數器，兩個客戶端在操作：

```
  Client 1:  write(x, 1)         // 把 x 設成 1
  Client 2:               read(x) // 讀 x
```

Client 1 寫完，Client 2 讀。Client 2 該讀到什麼？

「當然是 1 啊。」——這是單機直覺。但在複製系統裡，Client 1 寫的是副本 A，Client 2 讀的是副本 B，而 A→B 的複製還在路上。Client 2 讀到舊值（比如 0 或「不存在」）是**完全可能**的。

那到底允不允許 Client 2 讀到舊值？答案是：**看你的系統承諾了哪一種一致性模型。** 有的模型（linearizable）保證「寫完之後開始的讀，一定看到新值」，讀到舊值就是違約、是 bug。有的模型（eventual）只保證「最終會看到新值」，中間讀到舊值完全合法。

**一致性模型就是系統與使用者之間的一紙合約**：它精確規定「在有並行、有複製的情況下，一個讀取被允許回傳哪些值」。沒有這紙合約，你根本無法判斷一個回傳「舊值」的讀取到底是正確行為還是 bug——因為你不知道系統承諾了什麼。

歷史上這條光譜是逐步形式化出來的。1979 年 Lamport 定義了 sequential consistency（本來是為了多處理器的共享記憶體）；1990 年 Herlihy & Wing 定義了 linearizability，給出「最強、最像單機」的那一端；中間 causal consistency、各種 session 保證陸續補上；eventual consistency 則是 Dynamo（2007）把「弱到極致但高可用」那一端帶進主流視野。今天我們把它們排成一條**強 → 弱**的光譜。

## 先建立直覺：一條從「像單機」到「最終會對」的光譜

先給你整條光譜的地圖，細節後面逐一展開：

```
  強 ◄─────────────────────────────────────────────────────► 弱
  協調成本高、延遲高                           協調成本低、延遲低、高可用

 ┌──────────────┬──────────────┬──────────────┬───────────────┐
 │Linearizability│  Sequential  │    Causal    │   Eventual    │
 │  線性一致     │  Consistency │ Consistency  │  Consistency  │
 │              │  順序一致    │  因果一致    │  最終一致     │
 ├──────────────┼──────────────┼──────────────┼───────────────┤
 │「像只有一份  │ 有一個大家   │ 有因果關係的 │ 停止寫入後，  │
 │ 資料」，且   │ 同意的全序， │ 事件，順序   │ 副本最終收斂  │
 │ 尊重真實時間 │ 但可不合真   │ 一致；並行的 │ 到同一值；    │
 │ 的先後       │ 實時間先後   │ 事件各看各的 │ 中間隨便亂    │
 └──────────────┴──────────────┴──────────────┴───────────────┘
     要協調 →         要協調 →       不需全域協調 →   完全不需協調
```

貫穿整條光譜的**兩個對立力量**，先記住，後面所有取捨都是它們的展開：

- **越強的一致性 → 越接近「單機直覺」，程式好寫**，但**要求副本間更多協調**（等待彼此、多趟訊息往返），因此**延遲高、可用性低**（分區時可能得停止服務，Ch 10 CAP 會證明這件事）。
- **越弱的一致性 → 副本可以各跑各的、不用等**，因此**延遲低、可用性高**，但**程式難寫**（你得處理「讀到舊值」「不同節點看到不同順序」這些單機不會有的怪事）。

整條光譜就是在這兩股力量之間選點。沒有「最好的一致性模型」，只有「這個場景該選哪一級」。

## Linearizability（線性一致）：像只有一份資料

這是光譜最強的一端，也是直覺上「複製系統應該有的樣子」。

**嚴謹定義**：一個執行是 linearizable 的，若存在一個把所有操作排成的**全序（total order）**，滿足：

1. 這個全序**尊重每個操作的即時性（real-time order）**：如果操作 A 在真實時間上**完全早於** B（A 回傳的那一刻早於 B 開始的那一刻），那麼在全序裡 A 也排在 B 之前。
2. 每個讀取回傳的，是在這個全序裡「排在它前面的最後一個寫入」所寫的值。
3. 每個操作看起來像是在它的「開始」與「回傳」之間的**某一個瞬間原子地生效**。

一句話總結：**系統表現得像只有一份資料，所有操作在某個瞬間原子地作用其上，而且這些瞬間的先後尊重真實世界的時間。** 這就是為什麼 linearizability 也被叫做「atomic consistency」或口語的「強一致」。

關鍵字是 **real-time（即時性）**。這是 linearizability 和下一個 sequential consistency 的唯一差別，也是它「最強」的來源。

### 具體例子：什麼允許、什麼不允許

用時間軸看。橫軸是真實時間，`[----W(x,1)----]` 表示一個「把 x 寫成 1」的操作從開始到回傳的區間，`[--R(x)→?--]` 表示一個讀取。

**允許的執行**（linearizable）：

```
時間 ──────────────────────────────────────────────────►
C1:  [--W(x,1)--]
C2:                  [--R(x)→1--]        ← W 完全早於 R，R 必須看到 1  ✓
```
W(x,1) 在真實時間上完全早於 R（W 回傳了 R 才開始），所以 R 必須看到 1。看到 1，合法。

**違反的執行**（不是 linearizable）：

```
時間 ──────────────────────────────────────────────────►
C1:  [--W(x,1)--]
C2:                  [--R(x)→0--]        ← W 完全早於 R 卻讀到舊值 0  ✗
```
W 已經回傳（全世界都知道 x 是 1 了），R 才開始，卻讀到 0。這**違反 linearizability**——它違背了即時性。在真實的複製系統裡，這正是「讀到落後 follower 的舊值」會發生的事。linearizable 系統必須用額外協調堵掉這種讀取。

**重疊操作的處理**：如果兩個操作在時間上**重疊**（並行），linearizability 允許系統自由選擇它們的先後——只要選一個順序、且所有人看到的結果一致。

```
時間 ──────────────────────────────────────────────────►
C1:  [------W(x,1)------]
C2:      [------W(x,2)------]
C3:                        [--R(x)→?--]   R 完全晚於兩個 W
```
W(x,1) 和 W(x,2) 重疊，系統可以裁定「1 先 2 後」或「2 先 1 後」——兩者都 linearizable。但 R 完全晚於兩個寫入，所以 R 必須看到「系統裁定的最後一個寫入」的值：若裁定 2 後，R 看 2；若裁定 1 後，R 看 1。R **不能**看到 0（那是兩個寫入都還沒發生的值），也**不能**這個讀者看 1、另一個晚於它的讀者又看 2（那就違反了「只有一份資料」）。

這就是 linearizability 的精髓：**並行的操作可以任意定序，但一旦定序，這個順序對所有人一致，且尊重非並行操作的真實時間先後。** 它是唯一一個「可組合（composable）」的模型——多個各自 linearizable 的物件組起來，整體仍 linearizable，這讓它特別好推理。

## Sequential Consistency（順序一致）：放寬即時性

Lamport 1979 年的定義。它比 linearizability 弱一級，弱的正是那個 **real-time** 條件。

**嚴謹定義**：存在一個把所有操作排成的全序，滿足：

1. 這個全序**保留每個客戶端（process）自己內部的操作順序**（program order）——你自己先寫 A 再寫 B，全序裡 A 一定在 B 前。
2. 每個讀取回傳全序中排在它前面的最後一個寫入的值。
3. **但這個全序不必尊重跨客戶端的真實時間先後。**

差別就在第 3 點。linearizability 要求全序尊重真實時間；sequential consistency 只要求全序尊重「每個客戶端自己的順序」，跨客戶端之間，即使 A 在真實時間完全早於 B，全序裡也可以把 B 排在 A 前面。

### 具體例子：sequential 允許、linearizable 禁止的執行

```
時間 ──────────────────────────────────────────────────►
C1:  [--W(x,1)--]
C2:                        [--R(x)→0--]   ← 讀到舊值
```

這個執行**不是 linearizable**（W 完全早於 R 卻讀到 0，違反即時性），但**可以是 sequential consistent**——只要存在一個保留各自 program order 的全序解釋它。例如全序 `R(x)→0, W(x,1)`：把 R 排在 W 前面。這個全序沒違反任何客戶端內部順序（C1 只有一個操作，C2 只有一個操作），R 讀到「它前面沒有寫入」的初始值 0，合法。

換句話說，sequential consistency 說：「大家對事件的順序有共識（存在一個全序），但這個順序不必跟牆上的時鐘一致。」它像是「所有操作被塞進一個單一佇列依序執行，但這個佇列的排法可以跟真實時間脫節」。

**一個更能凸顯差別的經典例子**（兩個變數）：

```
初始 x=0, y=0
C1:  W(x,1); R(y)→0
C2:  W(y,1); R(x)→0
```

C1 先寫 x=1 再讀 y，讀到 0；C2 先寫 y=1 再讀 x，讀到 0。這**在 sequential consistency 下不允許**（找不到一個保留兩者 program order、又能同時讓兩個讀都看到 0 的全序——你試試就知道，任一全序裡總有一個寫排在另一個讀前面）。但在更弱的模型下可能發生。這個例子也正是多核 CPU 記憶體模型裡 store buffer 造成的經典重排——**sequential consistency 這個詞最早就是講 CPU 的**，分散式只是借用。

> 你在 kernel / 微架構課碰過的記憶體屏障（memory barrier）、`x86-TSO`、acquire/release，講的就是硬體提供哪一級一致性、以及怎麼用屏障補強到 sequential。分散式的一致性模型和硬體記憶體模型是**同一套理論**的兩個應用場景——這不是巧合，Herlihy 那批人兩邊都做。

## Causal Consistency（因果一致）：只保因果序

再弱一級。它放棄了「所有操作有一個全序」這個要求，只保證**有因果關係的操作，大家看到的順序一致**；沒有因果關係的（並行的）操作，不同節點可以看到不同順序。

**嚴謹定義**：所有節點看到的「有因果依賴（causally related）的寫入」順序一致。因果依賴指 Ch 5/6 的 happened-before（→）關係：

- 同一個客戶端先做 A 再做 B → A 因果先於 B；
- 一個客戶端讀到了另一個客戶端寫的值，則那個寫因果先於這個讀之後的操作（讀到了才做的事，依賴那個寫）。

**並行（concurrent，即互相沒有 → 關係）的寫入，允許不同節點以不同順序看到。**

### 具體例子：因果一致擋掉什麼、放過什麼

經典場景是「問題與回答」：

```
C1:  W(post, "在嗎?")
C2:  R(post)→"在嗎?" ; W(reply, "在")   ← C2 讀到問題「之後」才回答
C3:  觀察 post 和 reply
```

C2 是**讀到了問題才回答**的，所以 `W(post)` 因果先於 `W(reply)`。因果一致保證：**任何節點，若看到了 reply「在」，就一定也看到了 post「在嗎?」**——不會出現「看到有人回答『在』，卻看不到問題是什麼」這種鬼打牆。這是因果一致最實用的保證。

```
   合法（因果一致允許）：
   C3 看到:  post="在嗎?"  然後  reply="在"     ✓（尊重因果）
   C3 看到:  只有 post，reply 還沒到              ✓（reply 還在傳）

   非法（因果一致禁止）：
   C3 看到:  reply="在"  但看不到 post           ✗（違反因果：果先於因）
```

而**並行的寫入**，因果一致就放手了：

```
C1:  W(x,1)        ┐ 這兩個寫入之間沒有任何因果關係
C2:  W(x,2)        ┘ （C1、C2 沒讀到對方、不同客戶端）→ 並行

   節點 A 看到順序:  x=1 然後 x=2  →  最終 x=2
   節點 B 看到順序:  x=2 然後 x=1  →  最終 x=1     ← 因果一致「允許」不同！
```

兩個並行寫入，不同節點看到不同順序、甚至最終收斂到不同值——**因果一致允許這個**（要靠 Ch 14 的衝突解決來收斂）。這正是它比 sequential 弱的地方：sequential 要求「所有操作有唯一全序」，causal 只要求「因果相關的有序，並行的隨便」。

因果一致的巨大好處是：**它是「不需要全域協調就能達到」的最強一致性**。因為判斷因果關係靠 vector clock（Ch 6）這種本地就能算的東西即可，不需要所有節點停下來投票達成全序。這讓它在高可用系統裡特別誘人——它是「網路分區時仍能維持」的最強一致性（有個著名結果：causal + 收斂是分區可用系統能達到的最強一致性上限，見延伸閱讀 COPS/Attiya）。

## Eventual Consistency（最終一致）：最終收斂

光譜最弱的一端，也是 Dynamo、Cassandra 這類高可用系統的預設。

**嚴謹定義**（其實它的「保證」弱到只剩一句 liveness）：**如果停止對某個資料項的所有寫入，那麼最終（eventually）所有副本會收斂到同一個值。** 就這樣。

注意它有多弱：

- 它**只承諾「最終」**——沒說多久。可能一毫秒，可能一小時。
- 它**對「中間過程」不做任何承諾**。收斂之前，不同副本可以回不同的值、可以回舊值、可以來回跳（讀到 1，再讀到 0，再讀到 1）、可以違反因果。
- 它甚至**不保證「若一直有寫入就會收斂」**——它只在「停止寫入」的假設下承諾收斂。真實系統一直有寫入，所以嚴格說它是個關於「假想的靜止狀態」的承諾。

```
時間 ──────────────────────────────────────────────────►
       W(x,1) 到 A          背景複製傳播中……          收斂
       ┌──────┐
副本A: │ x=1  │───────────────────────────────────► x=1
副本B: │ x=0  │──R→0──────R→0──────R→1─────────────► x=1
副本C: │ x=0  │──R→0──────────R→1─────────────────► x=1
              ↑ 這段窗口內，讀 B、C 得到「舊值 0」，完全合法
                                    ↑ 傳播到了，開始看到新值
                    「最終」= 停止寫入後，某個時刻起全部 = x=1
```

聽起來弱到沒用？但它換來的是**最極致的可用性與最低的延遲**：副本永遠不用等彼此、不用協調，任何時刻任何副本都能立刻回應讀寫（就算跟別人斷線也行）。這對「可用性壓倒一切、且能容忍短暫不一致」的場景（購物車、社群按讚數、DNS）是划算的交易。

**強化版：strong eventual consistency（強最終一致）**——不只保證「最終收斂」，還保證「收到同一組更新的副本，狀態必然相同」（收斂到什麼值是**確定**的，不靠時序）。CRDT（Ch 14）就是為此設計的。這比裸的 eventual 好用得多，因為它把「會收斂」升級成「收斂到可預測的結果」。

## 一勞永逸：consistency（一致性模型）≠ consensus（共識）

這是整章最重要的一節，因為這兩個詞被混淆的程度到了災難級別。它們英文開頭都是 con-，中文都常被含糊地講成「一致」，於是無數人以為它們是同一件事。**它們是完全不同層次的東西。**

```
┌─────────────────────────────────────────────────────────────┐
│ 一致性模型（Consistency Model）                              │
│  = 一紙「合約 / 規格」                                       │
│  = 描述「在有並行與複製時，讀取被允許回傳哪些值」            │
│  = 是一個「性質（property）」，你拿它來『判斷一個執行對不對』│
│  例：這個系統是 linearizable 的 ← 在說它滿足某個性質         │
└─────────────────────────────────────────────────────────────┘
                          ↑ 用來「規範/判斷」
                          │
                          │ 一種可能的「實現手段」
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 共識（Consensus）                                            │
│  = 一個「問題 / 演算法」                                     │
│  = 「一群節點對『某一個值』達成一致決定」的具體問題          │
│  = Paxos、Raft 是解它的演算法（Part 3 的主角）              │
│  例：用 Raft 讓 5 個節點對「下一筆 log 是什麼」達成一致      │
└─────────────────────────────────────────────────────────────┘
```

講清楚它們的關係：

- **一致性模型是「要什麼」，共識是「怎麼做到（其中一種）」。** 一致性模型是規格層次的性質——它不告訴你怎麼實現，只告訴你「一個正確的實現該表現成什麼樣」。共識是機制層次的演算法——它是**達成 linearizability 的常用手段之一**，但不是唯一手段，也不是唯一用途。

- **你可以有 linearizability 而不(直接)用共識演算法**：例如單機資料庫天然 linearizable（只有一份資料，根本沒有副本要協調），它連共識都不需要。主從複製配上正確的 failover，某些設定下也能提供 linearizable，未必跑 Paxos。

- **共識也不只用來做一致性**：共識還用來做 leader 選舉、成員變更、分散式鎖、原子廣播（atomic broadcast）等。「對一個值達成一致」這個原語（primitive）的用途遠不止「讓副本一致」。

- **最鋒利的區分**：一致性模型是**用來『檢驗』的性質**——給你一段執行紀錄（history），你可以問「這段執行是不是 linearizable？」（Jepsen 的 Knossos/Elle 就是幹這個的，Ch 43）。共識是**用來『達成』某事的演算法**——你不會問「Raft 是不是 linearizable」，那是類別錯誤（category error），就像問「螺絲起子是不是紅色的重量」。

一句話刻進腦裡：**「Linearizability 是一種一致性模型（一個性質）；Raft 是一個共識演算法（一個機制）。前者說『系統該像什麼』，後者說『我怎麼讓它像那樣』。用共識來實現線性一致，是最常見的組合，但『是什麼』和『怎麼做』永遠是兩回事。」**

## 動手判讀：這段執行是哪一級一致？

定義吃進去了，來練「拿一段真實執行紀錄（history），判斷它滿足哪些模型」——這正是 Jepsen（Ch 43）自動化在做的事，手動走一遍能把定義變成肌肉記憶。

給定這段執行，初始 `x=0`：

```
時間 ────────────────────────────────────────────────────────►
C1:  [--W(x,1)--]
C2:                [----R(x)→?----]
C3:                        [--R(x)→?----]
```

C1 把 x 寫成 1（完全早於 C2、C3 的讀）。C2 讀到 1、C3 也讀到 1：

- **linearizable 嗎？** 是。W 完全早於兩個讀，兩個讀都看到 1，存在全序 `W(x,1), R→1, R→1` 尊重真實時間。合法。

現在把 C2 改成讀到 **0**（其餘不變）：

```
C1:  [--W(x,1)--]
C2:                [----R(x)→0----]     ← W 完全早於它，卻讀到 0
C3:                        [--R(x)→1----]
```

- **linearizable 嗎？** 否。W 完全早於 C2 的讀，C2 卻讀到舊值 0，違反即時性。
- **sequential 嗎？** 也否——但原因更微妙。要 sequential，得找一個保留各 client program order 的全序。C2 讀到 0，逼你把 C2 的讀排在 W **之前**。但 C3 讀到 1，逼你把 C3 的讀排在 W **之後**。於是全序是 `R2→0, W(x,1), R3→1`。問題在：這個全序裡 C2 的讀在 C3 的讀「之前」，但真實時間上 **C2 完全早於 C3**——sequential 不要求尊重真實時間，所以這不算違反……**等等**，它其實可以是 sequential！只要沒有跨 client 的 program order 被破壞（這裡每個 client 各只一兩個操作，沒衝突）。所以這段是 **sequential 但非 linearizable**——正好演示兩者只差一個 real-time 條件。

再看一段「連 sequential 都不是」的（兩個變數，初始 `x=y=0`）：

```
C1:  W(x,1); R(y)→0
C2:  W(y,1); R(x)→0
```

- **sequential 嗎？** 否。要保留 program order，全序裡 `W(x,1)` 必須在 `R(y)→0` 前、`W(y,1)` 必須在 `R(x)→0` 前。但 `R(y)→0` 要成立，`W(y,1)` 必須排在它後面；`R(x)→0` 要成立，`W(x,1)` 必須排在它後面。把四個約束畫成依賴圖，會出現一個環——無解。所以**沒有任何全序能解釋它**，非 sequential。（這段在弱記憶體模型下卻可能發生，靠 store buffer 重排——它是 sequential consistency 存在意義的經典反例。）

判讀的通用心法：**linearizable 看「有沒有尊重真實時間的全序」，sequential 看「有沒有尊重各自 program order 的全序（可無視真實時間）」，causal 看「因果相關的順序有沒有被違反（並行的不管）」。** 找不到符合的全序/順序 = 違反該模型。這套「找一個解釋一切的順序」的思路，就是形式化一致性驗證的核心。

## 底層機制：線性一致的代價從哪來

為什麼越強的一致性越貴？把 linearizability 的代價拆到訊息層次看就懂了。

要做到 linearizable，系統必須保證「一個寫入回傳後，任何後續的讀取都看到它」。在複製系統裡，這意味著：

```
  要 linearizable 的一次讀取，節點不能只看自己：

  節點 A 收到 read(x)
     │
     │ A 不能直接回自己本地的 x —— 它可能落後了！
     │ 別的節點可能剛提交了新的 x，A 還沒收到。
     ▼
  A 必須先「跟多數節點確認」自己的值是不是最新的
     A ──"現在 x 的最新版本是多少?"──> B, C, D, E
     A <────────── 回覆 ─────────────  B, C, D, E
     │  收到多數回覆，確認 / 更新到最新版本
     ▼
  A 才能回覆 read(x)  ← 多花了「至少一趟到多數節點的 RTT」
```

代價的本質：**強一致要求節點在回應前跟其他節點協調**（等多數確認），這**至少多一趟跨節點的往返（round-trip）**。於是：

- **延遲上升**：每個操作多付一趟 RTT，跨資料中心的話就是幾十上百毫秒。
- **吞吐下降 / 尾延遲惡化**：要等「多數」，就被第 (n/2+1) 快的節點綁架，慢節點拖累整體。
- **可用性下降**：如果網路分區導致某個節點聯絡不到多數節點，它**沒辦法安全地回應**（無法確認自己是最新的）——只能**拒絕服務**。

最後這一點是關鍵伏筆：**線性一致在網路分區時，會逼你在「回應但可能給錯（放棄一致）」和「拒絕服務（放棄可用）」之間二選一**。而分區一定會發生。這正是下一章 **CAP 定理**要嚴謹陳述的東西——原來 linearizability 的代價，最終會撞上一個不可能結果。這一章我們把「一致性有多強」量化了，下一章告訴你「你最多能同時要到多強的一致性和多高的可用性」。

## 對比與取捨

| 模型 | 核心保證 | 允許讀到舊值? | 允許不同節點看到不同順序? | 需全域協調? | 分區時可用? | 典型系統 |
|---|---|---|---|---|---|---|
| Linearizability | 像單機，尊重真實時間 | 否 | 否 | 是（等多數） | 否（要選 C） | etcd, ZooKeeper, Spanner |
| Sequential | 有全序，但不合真實時間 | 是（對舊操作） | 否（有唯一全序） | 是 | 否 | 多核記憶體模型（借用） |
| Causal | 因果序一致，並行隨意 | 是 | 是（僅並行的） | **否** | **是** | COPS, 部分 CRDT 系統 |
| Eventual | 停寫後最終收斂 | 是 | 是 | 否 | 是 | Dynamo, Cassandra, DNS |

讀這張表的方式：**從左到右，「保證」越來越少，但「分區時可用」和「不需協調」越來越好**。第 5、6 欄（需協調、分區可用）的分水嶺就落在 causal 和 sequential 之間——**causal 是「不需全域協調、分區仍可用」的最強一致性**，這是它在高可用系統裡的黃金地位。

## 踩雷集錦

1. **「強一致 = 讀到的一定是最新寫的」——不精確。** linearizability 的保證是「尊重真實時間的先後」，關鍵在**兩個操作有沒有時間上的先後**。兩個**並行**（時間重疊）的操作之間，linearizable 系統可以自由裁定順序，你「後開始」的讀未必看到「先開始但重疊」的寫。別把 linearizability 想成「永遠讀到牆上時鐘最新的那個」——它是「存在一個尊重非並行先後的全序」，並行的部分它有自由。

2. **把 consistency（一致性模型）和 consensus（共識）當同義詞。** 上一節整節在講這個，這裡再釘一次：一致性模型是「性質/合約」，共識是「演算法/機制」。「這系統一致嗎」問的是前者，「這系統用什麼共識」問的是後者。混用會讓你連問題都問錯。順帶一提，CAP 裡的 C 指的是 linearizability（一致性模型），不是 consensus。

3. **「最終一致」聽起來很溫和，其實中間什麼都可能發生。** eventual consistency **只**承諾「停寫後最終收斂」，收斂前它**不保證任何東西**：可以讀到舊值、可以讀到的值來回跳、可以違反因果（看到回答卻看不到問題）、不同副本可以回不同值。用最終一致的系統，你必須假設「任何時刻讀到的都可能是任意一個歷史值或並行值」來寫程式。低估這個弱度是線上事故的常客。

4. **以為一致性模型是「系統的固有屬性，選了就全系統適用」。** 很多系統是**可調的**：同一個 Cassandra，你可以逐個操作選一致性等級（`ONE` / `QUORUM` / `ALL`）；同一個 MongoDB，讀寫關注點（read/write concern）可調。一致性往往是**每個操作**的選擇，不是全系統一刀切。「這系統是強一致還是最終一致」這個問題本身可能就問錯了——正確的問法是「這個操作用了哪一級」。

5. **把 sequential consistency 當成 linearizability。** 兩者差別**只有一個** real-time 條件，很多人以為「有全序就是強一致」。不是。sequential 允許「已經回傳的寫入，被一個晚它開始的讀取讀不到」（因為全序可以無視真實時間把讀排前面）。linearizable 禁止這個。差一個 real-time 條件，可組合性、能不能拿來當鎖，全變了——linearizable 可組合、可當鎖，sequential 不行。

## 進階：再往深一層

- **Session / client-centric 一致性**：光譜上還有一整族「以單一客戶端視角」定義的保證，比 causal 弱但很實用：**read-your-writes**（讀得到自己剛寫的）、**monotonic reads**（讀到的值不會倒退回更舊的）、**monotonic writes**（自己的寫入按序生效）、**writes-follow-reads**。它們是 Ch 8 踩雷 #4 那種「重整頁面看到自己的改動不見了」的解藥，且比 causal 便宜。causal consistency 其實可以由這幾個 session 保證組合逼近。Terry 等人 1994 年的 Bayou 論文是源頭。

- **一致性模型的「可組合性（composability / locality）」**：linearizability 有一個 sequential 沒有的珍貴性質——**局部性（locality）**：如果每個物件各自 linearizable，那麼整個系統（所有物件合起來）也 linearizable。這讓你能一個物件一個物件地推理正確性，再組起來。sequential consistency **不具**這個性質，兩個各自 sequential 的物件組起來可能整體不 sequential。這是 linearizability 在理論上如此受偏愛的深層原因（Herlihy & Wing 1990 原論文的核心貢獻之一）。

- **CAP 只是冰山一角，還有 consistency-availability 的更細權衡**：causal consistency 有一個漂亮的理論地位——**它是「網路分區下仍能保持高可用」的系統所能提供的最強一致性**（Attiya、Mahajan、Bailis 等人的一系列結果，關鍵詞 "convergent causal consistency is the strongest achievable under partition"）。這給了 causal 一個「最強的可用一致性」的桂冠，也解釋了為什麼認真做高可用又不想完全放棄一致性的系統（COPS、部分 CRDT 系統）都停在 causal 這一級。

- **怎麼「驗證」一個系統真的滿足某個一致性模型**：這是 Jepsen（Ch 43）的核心。給定一段真實執行紀錄（哪個客戶端在哪個時間點做了什麼操作、拿到什麼回傳），演算法（Knossos 用模型檢查、Elle 用依賴圖找環）判定「存不存在一個滿足該模型定義的全序解釋這段紀錄」。判定 linearizability 一般是 NP-hard，但實務上這些工具跑得動、抓出過無數真實資料庫的一致性 bug。**一致性模型是可驗證的性質，這正是它作為「合約」的價值——你能拿它去告系統違約。**

## 本章重點整理

- 一致性不是布林值，是一整條**強→弱的光譜**：Linearizability > Sequential > Causal > Eventual。
- **Linearizability（線性一致）**：像只有一份資料，存在一個**尊重真實時間先後**的全序，讀看到最近的寫。最強、可組合、可當鎖，但要協調、分區時得放棄可用。
- **Sequential（順序一致）**：有全序、保留各客戶端自己的順序，**但不必尊重跨客戶端的真實時間**。比 linearizable 弱在「少一個 real-time 條件」。源自多核記憶體模型。
- **Causal（因果一致）**：只保證**因果相關**的操作大家看到同序，並行的可各看各的。是**不需全域協調、分區仍可用的最強一致性**。靠 vector clock 就能實現。
- **Eventual（最終一致）**：只承諾「停寫後最終收斂」，中間什麼都可能發生。換來極致可用與最低延遲。CRDT 提供更好用的「強最終一致」。
- **一致性模型 ≠ 共識**：前者是「合約/性質」（判斷執行對不對），後者是「演算法/機制」（Paxos/Raft，達成一致的手段之一）。用共識實現線性一致是常見組合，但「是什麼」和「怎麼做」是兩回事。
- **越強一致 → 越貴**：強一致要求節點回應前跟多數協調（多一趟 RTT），代價是延遲、吞吐、以及分區時的可用性。這是下一章 CAP 的引子。
